## 1. ★배치를 만들기 전 — 구현 게이트

**최상위 `.bat` 은 문서가 아니라 실행 가능한 물건이다.** 거기 있으면 사용자는 돌려도 되는
것으로 읽는다. 실제로 두 번 그렇게 됐다.

| # | 확인 | 방법 |
|---|---|---|
| 1 | 계획이 요구하는 **플래그가 파서에 있는가** | `python scripts/check_batch_flags.py` |
| 2 | 그 플래그가 **실제로 연결돼 있는가**(파서 → 함수 → 동작) | 코드 경로를 **눈으로 따라간다**. ★1번은 이걸 못 본다 |
| 3 | 계획이 요구하는 **동작이 구현돼 있는가** | 계획서 §측정·판정 항목을 한 줄씩 대조 |
| 4 | 코드를 고쳤으면 **스모크** | `run_smoke_check.bat` (`[VERIFY]` 줄만 읽는다) |
| 5 | **린트** | `python scripts/lint_bat.py --fix` |

> **2번이 왜 따로 있나**: 2026-08-06 에 `--doc-filter` 가 `train` 파서에 **있었는데**
> `trainer.train()` → `prepare()` 로 **전달되지 않았다.** 필터 캐시를 만들 수는 있어도
> **그것으로 학습할 방법이 없었다.** 1번 검사는 통과했을 것이다.
>
> **구현이 선결이면 배치를 만들지 않는다. 계획서에만 설계를 남긴다.**
> 불가피하면 헤더 첫 줄에 선결 조건 + `:NOTIMPL` 가드를 넣는다(그러면 1번이 경고로 낮춘다).

## 2. ★실험 간 독립성 (사용자 요청, 2026-08-06)

한 실험이 다른 실험을 **막거나 오염시키지 않게** 설계한다. 이유는 두 가지다 —
① 하나가 실패해도 나머지가 살아야 하고 ② **AI 사용량이 소진된 동안 사용자가 긴 학습을
혼자 돌릴 수 있어야** 한다.

| 축 | 규칙 |
|---|---|
| **체크포인트** | 항상 `--tag` 를 붙인다. 정본 `dense`/`tied` 를 덮어쓰지 않는다 |
| **데이터 캐시** | 내용이 달라지면 **디렉터리를 분리**한다(`_filtered` 방식). 기존 캐시 무변 |
| **플래그 기본값** | 새 기능은 **기본 off**. 켜지 않으면 **비트 동일**이어야 한다 |
| **속도 측정** | 다른 실험과 **동시 실행 금지**. 직전 5분 유휴 |
| **선행 의존** | 있으면 배치 헤더에 **명시**하고 `goto ERROR` 로 막는다. 없으면 `[WARN] continuing` |

### 2.1 "무인 실행" 배치의 조건

사용자가 시작만 하고 자리를 뜰 수 있으려면:

- [ ] **중간에 판단이 필요 없다**(분기·확인 프롬프트 없음)
- [ ] **선결 조건을 헤더에서 검사하고 없으면 즉시 멈춘다**(GPU 를 태우기 전에)
- [ ] **예상 소요 시간이 헤더에 있다**
- [ ] **판정 기준이 꼬리말에 있다** — 로그만 받아도 다음 세션이 문서를 쓸 수 있게
- [ ] **다른 실험의 산출물을 건드리지 않는다**

### 2.2 우선순위를 매길 때

| 우선 | 성격 | 왜 |
|---|---|---|
| 1 | **GPU 0 · 수분** | 값싼 진단이 비싼 학습의 게이트다. 먼저 돌려서 설계를 고친다 |
| 2 | **구현 선결이 없는 긴 GPU 런** | AI 사용량과 무관하게 굴릴 수 있다 → **대기시간을 자산으로** |
| 3 | 구현이 필요한 것 | AI 가 있을 때만 진행 |

## 3. 실험 한 사이클

```
exp-preflight  (조건 정합성 — docs/EXPERIMENT_BASELINES.md 와 대조)
      +
exp-plan       (계획서 양식 — ★예측 절과 한계 절을 반드시 쓴다)
      ↓
구현 게이트 (§1)
      ↓
run-batch      (.bat 작성 → lint_bat.py + check_batch_flags.py)
      ↓
[사용자가 실행]
      ↓
log-to-result  (결과문서 → ★계획서 본문 갱신 → 연쇄 갱신)
      ↓
핸드오프 (ai_dev_tool/02)
```

**`exp-plan` 과 `exp-preflight` 는 대체 관계가 아니다.** 전자는 문서 양식·절차,
후자는 실험 조건의 정합성. 새 계획을 쓸 때는 **둘 다** 돈다.

## 4. 결과를 읽기 전에 예측을 적는다

계획서와 배치 헤더 **양쪽에** 예측을 적는다. 이유:

- 예측이 없으면 **어떤 결과든 "예상대로" 로 읽힌다**
- 예측이 있으면 **틀렸을 때 그것 자체가 결과가 된다**(가설 기각도 성과다)
- 배치 헤더에 적으면 **사용자가 로그를 볼 때 이미 기준을 갖고 본다**

그리고 결과문서에서 **예측 대조 절을 명시적으로** 쓴다. 계획서에 예측을 써 놓고
대조하지 않으면 쓴 의미가 없다.

### 4.1 대조군을 반드시 하나 넣는다

**"아무것도 안 변해야 하는 조건"** 을 같은 배치에 넣는다. 그게 계측 결함을 잡는다.

- P034 단계3C: `p6d`(공유 없음)가 **안 변해야** 한다 → 변하면 환경이 변한 것
- P037 단계2C: `ko-en` 대조군이 **완전 불변**이어야 스코핑이 맞다
- 속도 배치: 기준선 조건을 같은 로그에 넣어 **비율로 읽는다**(열·부하가 상쇄된다)
