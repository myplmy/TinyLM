```
TinyLM 세션 시작. 너는 Claude Code 라서 Cowork 의 프로젝트 지침·메모리를
못 읽는다. 그래서 아래 순서로 먼저 읽어라.

2. ai_dev_tool/06_ClaudeCode용_프로젝트지침과_메모리.md   (프로젝트 맥락 - 필수)

4. docs/EXPERIMENT_BASELINES.md 의 B.6            (표준조건)

그 다음 python scripts/check_static_all.py 로 정적 게이트 13종을 확인해라.

지켜야 하는 것 세 가지를 먼저 확인한다:
- 학습/GPU 는 네가 돌리지 않는다. run100m.py train 과 run_*.bat 은 내가 돌린다.
- 파일을 지우지 않는다. 삭제 권한도 요청하지 않는다. 지울 것은 핸드오프에
  목록으로 적어라. mv(개명)는 네가 해도 된다.
- git commit / push 는 내가 한다. 커밋 메시지 제목과 본문만 한국어로 제안해라.

결과문서 번호는 실험군 번호다 - 로그 파일명 앞 세 자리가 그것을 말한다.
큐는 이름으로 안내해라(함정 36). id 가 필요하면
python scripts/queue_menu.py --ids <배치명> 이 계산하게 해라.
```

> ★**짧게 쓰고 싶으면** 1~4 만 남긴다. **2번은 절대 빼지 않는다** — 그게 이 문서의 존재 이유다.

## 2. ★Claude Code 에서 **더 위험한 것** — 두 줄로 요약

| # | 무엇 | 왜 Claude Code 에서 더 위험한가 |
|---|---|---|
| ★**1** | **학습을 직접 돌린다** | Cowork 에서는 능력이 없어 자동으로 지켜졌다. Claude Code 는 **Bash 로 정말 돌릴 수 있고** 한 런이 **2~6시간**이다. **GPU 시간은 사용자 자원**이다 |
| ★**2** | **파일을 지운다** | `rm` 이 그냥 된다. **능력 문제가 아니라 정책**이다(2026-08-14 위반 1회, D11). *"차단돼 있다"* 라고 적으면 **차단이 풀리는 순간 정책도 풀린 것처럼 읽힌다** |

★**허가 설정 권고** — 사람이 기억하는 대신 도구가 막게 한다.
`.claude/settings.local.json`(또는 `settings.json`)에:

```json
{
  "permissions": {
    "deny": [
      "Bash(rm:*)",
      "Bash(rmdir:*)",
      "Bash(del:*)",
      "Bash(git commit:*)",
      "Bash(git push:*)",
      "Bash(python run100m.py train:*)",
      "Bash(run_smoke_check.bat)"
    ]
  }
}
```

> ⚠️**이건 제안이다.** 키 이름·매칭 규약은 Claude Code 판마다 달라질 수 있으니
> **넣은 뒤 실제로 막히는지 한 번 확인**하고, 막히지 않으면 그 사실을 여기 적는다(함정 13).
> 🚫**설정이 있어도 규범이 우선이다** — 설정은 그물이지 근거가 아니다.

## 4. ★자주 쓰는 작업지시 — **복사해서 쓰는 프롬프트 8종**

### 4-1. 로그를 받았을 때

```
로그를 받았다: test_result/{파일명}
log-to-result 절차로 반영해라. 연쇄 갱신 대상은 결과문서 · 계획서 본문 ·
test_result/실험목록.md · test_plan/실험계획목록.md · docs/EXPERIMENT_BASELINES.md 다.
번호는 로그 파일명 앞 세 자리를 따른다(실험군 번호이지 세션 번호가 아니다).

읽는 규칙:
- 판정은 runs/logs/*.json 이다. 인쇄값이 아니다.
- 안정성은 grad_max 이고 인쇄 |g| 가 아니다.
- val - train_ce 를 판정 전에 먼저 본다. 0.3 이 넘으면 계측을 먼저 의심해라.
- 분해능은 조건 의존이다. 무KD 는 2σ=0.0034, dense/부모없음은 0.024 다.
  어느 자를 썼는지 적어라.
- 계획서의 예측 절과 대조해서 맞았는지 틀렸는지 명시해라.
  빗나간 예측은 감추지 말고 적어라.
반영 뒤 check_static_all.py 를 돌리고 결과를 보고해라.
```

### 4-2. 새 실험을 설계할 때

```
{목적}을 검증하는 실험을 설계해라. 순서는 이렇다.
1. exp-preflight - docs/EXPERIMENT_BASELINES.md 와 대조해서 조건 중복 ·
   토큰 환산 · 태그 충돌 · 무효 비교를 먼저 걸러라.
   runs/ckpt 와 runs/logs 를 실제로 조회해서 이미 돈 조건인지 확인해라.
2. exp-plan - 계획서에 예측 절과 한계 절을 반드시 넣어라.
3. 구현이 선결이면 배치를 만들지 말고 계획서에만 설계를 남겨라.
   지금 돌아가는 것만 배치로 만든다.
4. 배치를 만들었으면 check_batch_flags.py 와 lint_bat.py --fix 를 돌리고,
   플래그가 파서에서 함수까지 실제로 전달되는지 코드로 따라가라.
5. experiments.tsv 에 한 줄 추가하고 queue_menu.py --audit 로 확인해라.
6. 새 축을 뚫었으면 그 축을 켠 스모크 팔을 tool_smoke.bat 에 함께 넣어라.
실행은 내가 한다. 명령과 순서만 제시해라.
```

### 4-3. 코드를 고쳐야 할 때

```
{내용}을 고쳐라. 조건:
- 새 플래그는 기본 off 로 만들고 미지정 시 비트 동일이어야 한다.
- 적용 대상 집합을 두 곳에서 정의하지 마라(함정 18). 정본을 한 곳에 두고
  나머지가 import 하게 해라.
- 학습 경로를 바꾸는 플래그면 "평가는 무엇을 도는가" 를 같은 변경에서 답해라(함정 39).
- 고친 뒤 check_static_all.py 를 돌리고, run_smoke_check.bat 이 필요한지
  판단해서 알려줘라. 필요하면 스모크 팔도 함께 추가해라.
```

### 4-4. 다음에 뭘 돌릴지 물을 때

```
지금 돌릴 수 있는 실험을 우선순위대로 보고해라. 각 항목에
실험번호 · 단계 · 배치 파일명 · 예상 시간 · 권장 근거를 적어라.
큐 입력은 이름으로 주고, id 는 queue_menu.py --ids 로 계산해라.
선결이 있는 것은 무엇이 선결이고 그것이 몇 시간인지 숫자로 적어라
(숫자가 없으면 그건 선결이 아니라 미루는 이유다 - D1).
```

### 4-5. 핸드오프

```
핸드오프 메모를 써라. 양식은 ai_dev_tool/02_핸드오프_규약.md 다.
고정 섹션 8개를 전부 채우고, "사용자에게 부탁하는 것" 절은 요청이 없어도
"요청할 것이 없다" 라고 명시해라. -done 배치 삭제 판정을 항상 포함해라.
쓴 뒤 python scripts/check_handoff.py 로 확인해라.
```

### 4-6. 커밋 제안

```
지금까지의 변경으로 커밋 메시지 제목과 본문을 한국어로 제안해라.
본문은 무엇을 왜 바꿨는지 서술형으로 쓰고, 숫자가 있으면 숫자를 적어라.
커밋은 내가 한다 - git 명령을 돌리지 마라.
```

### 4-7. 외부 검토문서를 받았을 때

```
외부 AI 가 쓴 검토문서다: {경로}
우리 실측으로 반증을 먼저 시도해라. 코드 인용은 대개 맞지만 우선순위는
자주 틀린다. 각 주장에 대해
(a) 우리 결과문서 중 무엇이 그것을 지지/반박하는가
(b) 반박할 근거가 없으면 "우리는 안 쟀다" 라고 명시
를 적어라. 논문을 인용하면 arXiv id 로 실제 조회한 뒤에 써라.
```

### 4-8. 문서가 낡았는지 볼 때

```
{문서}가 낡았는지 확인해라. 판정 방법:
- 거기 적힌 숫자를 runs/logs/*.json 과 대조해라.
- "예약" "미실행" 이라 적힌 것이 runs/ckpt 에 이미 있는지 확인해라.
- "구현 선결" 이라 적힌 것이 run100m.py train --help 의 파서에 이미 있는지 확인해라.
"조치 완료" 를 파일 diff 없이 적지 마라.
```
