# A16 — TinyLM 벤치마크의 원래 과제·평가 규약 대조와 대체 경로

작성: 2026-09-09. 대상: 현재 원본 코드와 로컬 데이터, P064/P069/P085의 벤치마크 결과. 상태: **분석·코드 작성 / Python·검사 스크립트·벤치마크 실행 안 함 / 동작·수치 검증 미완료**.

## 1. 결론과 적용 범위

**현재 점수를 이름만 같은 공개 리더보드 수치와 그대로 대조하면 안 된다.** 다만 원인을 전부 “벤치마크 오용”으로 묶는 것도 부정확하다.

- **다른 양을 측정하거나 정답을 잘못 적용한 경우**: YNAT accuracy 대 macro F1, KorQuAD 정답 CE 대 EM/F1, IFEval 부분 제약, HumanEval 문법 대 기능 검사, BFCL JSON 문법 대 함수 호출 정답, MMLU-Redux 수정 정답 미반영. 실제 대체 채점 경로가 필요하다.
- **유효한 예측 방법이지만 비교 프로토콜이 다른 경우**: 선택형 문항에서 PMI 분류기를 쓰는 것 자체가 금지된 것은 아니다. 그러나 그것을 특정 모델 카드의 일반 LL/정규화 LL, 다른 few-shot 설정, 다른 문항 집합의 점수와 **동일 조건 측정**으로 취급할 수 없다.
- **기본 방식이 맞거나 내부 전용인 경우**: WinoGrande의 후보를 문맥에 넣고 공통 뒷문장을 평가하는 구조, KLUE-NLI의 accuracy, LAMBADA의 단어 NLL 기반 PPL은 무조건 잘못된 것이 아니다. 내부 held-out과 ARC 합본도 의도적으로 이름을 구분한 진단이다.

벤치마크마다 논문의 최초 실험, 공식 제출 평가, lm-evaluation-harness, 특정 모델 카드의 프로토콜이 다를 수 있다. A16은 **모든 과제에 유일한 ‘공식 프롬프트’가 있다고 가정하지 않는다.** 일반 LM 과제는 명시한 harness 버전, 기능·지시·도구 과제는 해당 공식 평가기, 한국어 과제는 공식 지표와 데이터 버전을 기준으로 연결한다. 새 코드로 평가해도 다른 모델의 **같은 버전·split·few-shot·출력 처리 조건** 확인이 필요하다.

기존 평가기와 기록은 보존한다. A16은 replacement/에 새 모듈과 새 진입점만 추가하며 A01–A15 및 ALL/을 변경하지 않는다. 설치·실행 설명은 [README](README.md), 확인 범위와 실행하지 않은 검증은 [VERIFICATION](VERIFICATION.md)에 있다.

### 3.1 선택형: PMI를 끄는 것만으로 해결되지 않는다

현재 run_mc는 대체로 **조건부 후보 token 평균 CE − 빈 문맥 후보 평균 CE**가 가장 작은 후보를 고른다. 함께 출력하는 acc_norm도 합 CE / token 수이므로 PMI 없는 token 평균 CE 순위다.

따라서 --no-pmi만 주어도 일반적인 **합 로그우도**가 되지 않는다. 빈 문맥 prefix, prompt와 continuation을 **각각 encode하는 방식**, special token, HellaSwag 전처리, few-shot까지 차이가 남는다. acc_norm이라는 이름만 같아도 정규화 단위와 task version이 같다는 보장이 없다. A16은 normalization을 하나로 자작하지 않고 **설치된 pinned task/scorer**에 맡긴다.

새 adapter가 반환하는 것은 자연로그 확률의 **합**과 정답 continuation의 token별 argmax 일치 여부다. 공백 경계를 옮기는 _encode_pair는 upstream TemplateLM을 상속한다. 모델별 calibration을 연구하려면 현재 PMI 경로를 실험 팔로 유지하면 된다. [harness 모델 API](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/lm_eval/api/model.py), [task·metric 규약](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/task_guide.md).

정규화 교체 후 점수가 오르리라고 예측하지 않는다. PMI가 현재 작은 모델의 점수를 더 높일 수도 있다. 목적은 **실제 차이를 측정하고 조건을 정확히 명명하는 것**이다.

### 3.2 MMLU-Redux: 현재도 남아 있는 정답 문제

로컬 57과목 5,700문항의 answer, correct_answer, error_type을 전수 대조했다.

- 숫자 0–3 수정값만 보면 기존 정답과 다른 문항은 **48개**다.
- A–D 표기도 0–3으로 해석하면 **103개**가 다르다.
- 103개의 오류 분류는 wrong_groundtruth 100, ok 2, bad_question_clarity 1이다.
- 전체에는 wrong_groundtruth 106개 외에도 복수 정답 39, 정답 없음 36, 질문 명확성 문제 132, 보기 명확성 문제 25, expert 32가 있다.

**103개를 일괄 치환하면 공식 Redux가 완성된다는 뜻은 아니다.** 빈 수정값, 복수·무정답, 정제 버전의 질문 변경은 별도 규약이 필요하다. 현재 파일은 오류 주석 데이터 성격을 갖고 있고, reference task가 사용하는 수정 배포본과 동일하지 않을 수 있다. [MMLU-Redux 원 저자 저장소](https://github.com/aryopg/mmlu-redux), [harness Redux 데이터셋 구분 논의](https://github.com/EleutherAI/lm-evaluation-harness/issues/3345).

조치: upstream 정제 task로 재평가하고 dataset path/config를 보존한다. mmlu_redux가 비-Redux dataset을 가리키면 완료 처리하지 않는 검사도 넣었다. 비교기는 **정답을 join key에서 제외**하여 동일 입력의 정답 변경을 기록한다. 입력 자체가 바뀐 문항은 억지로 대응시키지 않는다. 103건 전체가 과거 n=300 표본에 들어갔다고 주장하지 않는다.

### 3.3 IFEval·GSM8K·LAMBADA: 출력 조건과 채점기를 각각 비교

IFEval에서 미지원 제약을 ‘실패’ 대신 ‘미평가’로 표시한 기존 설명은 정직하다. 그러나 평가한 부분만의 통과율은 공식 점수가 아니다. 공백 분리 단어 수, 단순 문장부호 분할, 부분 문자열 검색, 대소문자 동등 비교 등도 공식 checker와 다르다. 빈 문자열은 기존 resp == resp.upper()를 통과하지만 공식 strict 경로는 빈 응답을 통과시키지 않는다. 표준 입력의 kwargs 반복·zip 자체를 이번에 **항목 오정렬 버그라고 판정하지 않았다**. [Google IFEval 평가 구현](https://github.com/google-research/google-research/blob/master/instruction_following_eval/evaluation_lib.py).

GSM8K는 새 task의 기본 5-shot과 strict/flexible 결과를 구분한다. 0-shot은 명시한다. 특정 논문·모델 카드의 8-shot CoT 숫자를 재현하려면 별도 프로토콜을 맞춰야 한다. 생성 budget을 줄이면 그 조건을 붙인다. [harness GSM8K task](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/lm_eval/tasks/gsm8k/gsm8k.yaml).

LAMBADA 기존 PPL은 exp(mean(단어 NLL))라서 식 자체를 폐기하지 않는다. **정확도 경로와 token boundary 차이**를 분리해 확인한다. 일반 corpus token PPL, LAMBADA last-word PPL, 다른 tokenizer의 PPL은 같은 양이 아니다.

### 3.4 HumanEval·HumanEval+: 실제 기능 검사 경로

기존 문서는 parse rate와 pass@1이 다름을 이미 알고 있었다. 미완인 것은 **공식 테스트로 넘어가는 재현 가능한 실행 연결**이다. 현재 저장물은 append되므로 여러 모델·재실행이 섞일 수 있다.

A16은 공식 problem ID 164개, 모델·problem·sample hash, task별 sample 개수를 검증한다. generate는 completion만 저장하고 **생성 코드를 실행하지 않는다**. evaluate는 사용자가 별도 실행하는 공식 기능 검사다. HumanEval은 OpenAI의 evaluate_functional_correctness, HumanEval+는 EvalPlus를 호출하며 문자열 정답 비교기로 대체하지 않는다. [OpenAI HumanEval](https://github.com/openai/human-eval), [공식 평가 함수](https://github.com/openai/human-eval/blob/master/human_eval/evaluation.py), [EvalPlus 출력 형식](https://github.com/evalplus/evalplus/blob/master/docs/cli.md).

greedy 1개/문항은 pass@1이다. 같은 응답을 복제해 pass@10 표본처럼 계산하지 않는다. sampling은 개수·온도·top-p·seed를 명시한다. 자동 코드 복구·sanitize는 별도의 변경 조건이다.

### 3.5 BFCL: 현재 캐시와 실제 평가의 차이

로컬 2,351문항의 _src는 **모두 BFCL_v3**다. 현재 파일이 v4와 실제 혼합되었다고 판정하지 않는다. 원래 수집기가 revision을 고정하지 않는 문제는 남아 있다.

| 현재 포함 범주 | 문항 수 |
|---|---:|
| simple / multiple / parallel / parallel_multiple | 400 / 200 / 200 / 200 |
| live_simple / live_multiple / live_parallel / live_parallel_multiple | 258 / 1,053 / 16 / 24 |

BFCL v3 전체 범주는 아니다. ground_truth 필드가 있는 문항은 **0개**다. 기존 adapter가 만드는 json.dumps("")의 CE는 함수 호출 정답 CE가 아니다. _dump가 읽는 meta.task_id와 BFCL adapter의 meta.id도 달라 저장 ID가 비게 된다.

JSON 유효성은 BFCL AST 정답 판정과 다르다. 함수명·인수·순서 허용 규칙·병렬 호출·호출 불필요·다중 턴 상태는 공식 runner/checker가 맡아야 한다. A16은 TinyLM의 **completions transport와 prompt-model handler**를 추가한다. 함수 스키마와 대화 이력은 공식 전처리와 multi-turn loop를 거친다. [BFCL 모델 연결 규약](https://github.com/ShishirPatil/gorilla/blob/main/berkeley-function-call-leaderboard/CONTRIBUTING.md), [공식 OSS handler](https://github.com/ShishirPatil/gorilla/blob/main/berkeley-function-call-leaderboard/bfcl_eval/model_handler/local_inference/base_oss_handler.py).

v3 고정에는 [Gorilla v1.3/BFCL v3 안정 릴리스 안내](https://github.com/ShishirPatil/gorilla/discussions/1119)를 기준으로 사용자가 확보한 checkout을 사용한다. **최신 main은 v3 고정본이 아니다.** 파일명 접두사만으로 버전을 확정하지 않는다. freeze는 코드·데이터 bytes를 고정하지만 release label의 진위를 인증하지는 않는다. 이번 조사에서 v1.3 tag 전체 소스를 설치·실행하지 못했으므로 해당 checkout과의 API 호환은 **사용자 사전 검증 항목**이다. 현재 공개 OSS/CLI API를 기준으로 작성했고 mismatch 시 우회 점수를 내지 않고 중단한다.

legacy-export는 같은 공식 ID·원문이 로컬 캐시와 일치하는 single-turn 범주에서 **기존 1,500자 절단·문자열화·greedy·stop**을 재현한다. 이를 공식 scorer에 넣으면 ‘기존 JSON parse rate’, ‘같은 생성물의 실제 정답률’, ‘새 공식 prompt 경로의 정답률’을 나누어 볼 수 있다. ID가 없는 혼합 dump를 행 위치만으로 복원하지 않는다.

### 3.6 한국어·MuSR: 논문 표와 동일하다고 과장하지 않기

KoBEST 논문 §4.2.1은 후보 perplexity 비교를, Table 7은 COPA의 원인/결과 연결자와 HellaSwag의 ‘문장:’ 형식을 제시한다. 기존 TinyLM prompt는 다르다. [harness KoBEST utils](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/lm_eval/tasks/kobest/utils.py)는 해당 연결자·prefix와 macro F1 reducer를 제공한다. A16은 이 경로를 지원한다. 다만 **논문 본문만으로 모든 token mask·정규화 세부가 확정되지는 않는다.** 정확한 task version이 원 논문 설정과 일치하기 전에는 ‘39B 논문 결과 재현’이라고 부르지 않는다. [KoBEST 논문 §2.7·§4.2.1·Table 4·Table 7](https://arxiv.org/pdf/2204.04541).

YNAT은 같은 예측 라벨에 macro F1을 추가하면 모델 재생성 없이 metric 차이를 볼 수 있다. NLI accuracy 자체는 오용이 아니며 **분류기를 반드시 fine-tuning해야 accuracy가 유효해지는 것도 아니다.** 공개 test leaderboard와 dev, supervised와 zero-shot을 동일 설정인 것처럼 쓰지 않는다. [KLUE 공식 metric](https://github.com/KLUE-benchmark/KLUE).

KorQuAD는 로컬 evaluate-2.0.py를 v1.0에 재사용하지 않는다. 문서 구조·HTML 정리가 v1.0과 다르다. 새 경로는 v1.0 원문·예측 ID 전체를 보존하여 **사용자가 확보한 공식 evaluate-v1.0.py**를 호출한다. 이번에는 그 scorer 파일 본문을 내려받지 못했다. 자체 근사 F1을 공식 코드라고 끼워 넣지 않았으며 파일과 SHA-256이 외부 선행조건이다. [KorQuAD 1.0 공식 페이지](https://korquad.github.io/category/1.0_KOR.html).

MuSR reference profile은 세 하위 과제를 포함하는 **Open LLM Leaderboard v2의 0-shot multiple-choice**다. 원 논문의 CoT 생성 결과와 혼합하지 않는다. 길이가 부족하면 max_seq_len만 무조건 늘리는 대신, 명시적 left-truncated 평가와 장문 수용 모델을 구분한다. [harness leaderboard task 안내](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/lm_eval/tasks/leaderboard/README.md).

## 5. 대체 코드의 설계와 보존 계약

- 원본 평가기·downloader·W&B/TSV는 그대로 둔다. 새 scripts/eval_reference_*.py, compare_reference_bench.py, serve_reference_bfcl.py가 새 tinylm/eval/reference_bench/를 호출한다.
- 기존 평가기 두 파일을 legacy_sources/에 **byte-identical 복사**했다. 복사본 해시가 바뀌면 중단한다. frozen 재생은 그 scoring/generation 함수를 공통 canonical 모델 로더·명시한 tokenizer로 대조한다. 원본 main의 tag 추정·기본 32k tokenizer 자동 선택까지 재현한다는 뜻은 아니다. 원본 main도 그대로 남아 있다. 모델 코드 동일성은 실행별 source hash로 대조한다.
- A01–A15 선설치가 필요 없다. 기존 load_model의 anneal/freeze와 학습된 visit schedule을 이용한다.
- 기본 batch=1, CPU FP32, no-cache reference. CUDA BF16과 KV cache는 사용자 선택이며 별도 수치 검증이 필요하다.
- 새 출력 디렉터리만 사용한다. overwrite·append로 결과를 섞지 않는다.
- checkpoint/tokenizer/source/data/sample hashes, upstream configs, 문항 ID·입력·target·응답·metric을 남긴다.
- 긴 입력은 기본 overflow=error. left 선택 시 잘린 요청 수와 token 수를 기록한다. 학습된 최대 길이 이상으로 RoPE를 임의 확장하지 않는다.
- HumanEval 기능 검사 및 BFCL simulator/채점은 사용자의 별도 실행 단계다. 이번에는 실행하지 않았다.

harness는 조사일 [release v0.4.13](https://github.com/EleutherAI/lm-evaluation-harness/releases)를 목표 버전으로 고정했다. 버전 문자열만으로 재현성을 주장하지 않도록 설치본 소스 해시도 남긴다. 패키지 설치·import를 하지 않았으므로 **설치 조합 호환성·테스트 통과를 보증한 상태는 아니다**.

일반 corpus PPL/paired loss 및 bench_infer·GEMM 속도 도구는 외부 정답 benchmark가 아니므로 A16에서 대체하지 않는다. 자체 evaluate의 PPL에는 exp(min(loss,20)) 상한도 있다. 다른 tokenizer·corpus의 perplexity나 LAMBADA word-PPL과 같은 숫자로 비교하면 안 된다.

## 6. 재실험 순서와 판정 기준

### 6.1 먼저 비교할 팔

기존 최종 후보의 **같은 checkpoint 1개**로 evaluator 차이부터 확인한다. 이후 후보 전부와 seed별로 확대한다.

| 팔 | 입력·생성 | 채점 | 목적 |
|---|---|---|---|
| L | frozen 기존 prompt/LL/생성 | 기존 PMI·부분 checker·parse | 이전 수치의 의미 보존 |
| R | 선언된 reference task | upstream scorer | 외부 동일 프로토콜 대조 |
| S | **R과 동일한 생성 문자열** | 기존 GSM8K/IFEval checker | 생성 차이를 제거하고 채점기만 비교 |
| C | 기존 HumanEval/BFCL 생성 방식 | 공식 기능/BFCL scorer | 기존 출력이 실제로 맞았는지 확인 |

선택형 L−R에는 prompt·전처리·token boundary·정규화·few-shot 차이가 함께 들어갈 수 있다. **전체 차이를 PMI 한 가지의 효과라고 부르지 않는다.** 먼저 0-shot끼리 비교하고 공개 5-shot 조건은 별도 팔로 둔다. 정규화의 인과 효과만 필요하면 동일 prompt의 후보별 점수를 저장한 추가 ablation으로 분리한다.

### 6.2 우선순위

1. **P0 짧은 과제**: HellaSwag/PIQA/ARC-Easy/KoBEST의 L/R 및 외부 소형 모델 R. 별도 학습 없이 방향 판단에 연결된다.
2. **P0 정답·metric**: MMLU-Redux reference, YNAT 같은 예측의 macro F1. 원본과 reference 문항이 다르면 그 사실부터 보고한다.
3. **P1 생성 채점 분리**: GSM8K·IFEval R/S. budget·context 실패를 점수 0으로 바꾸지 않는다.
4. **P1 실행 검사**: HumanEval/+/BFCL C/R. 기존 ‘못 푼다’를 실제 기능 지표로 검증한다.
5. **P2 길이 제약**: MuSR·KorQuAD full dev. 1,024 context에 못 담으면 truncated 결과와 context 개선 실험을 구분한다.

현재 장비에서는 teacher와 TinyLM을 동시에 VRAM에 올리지 않는다. TinyLM R과 외부 HF R은 순차 프로세스로 실행한다. batch 1부터 시작하며 시간·VRAM은 **실측하지 않았으므로 수치 예산을 꾸며 쓰지 않는다**. few-shot을 늘릴 때 입력·출력 길이부터 확인한다.

### 6.3 완료와 비교 가능 판정

- 최초 2–5문항 smoke는 실행 검증이며 품질 점수가 아니다. 이후 지정 split 전량으로 실행한다.
- 문항별 ID·선택지·target·실제 prompt·생성 응답을 남긴다.
- skip·요청 실패·task 로딩 실패는 **불완전 실행**이다. 정답을 못 맞혀 score 0인 정상 실행과 구분한다.
- 후보 모델은 같은 reference source/data/config, sampling, few-shot, budget을 쓴다. 다른 tokenizer는 각 모델의 구성 요소이며 원문 문항을 동일하게 제공한다.
- truncation·prompt·data exposure가 다른 공개 값에는 차이를 명시한다. macro F1/accuracy, token PPL/word PPL, parser rate/pass@1을 비율로 환산하지 않는다.
- canonical latent/frozen 추론 점수는 **40 MiB 배포 품질·RSS 검증이 아니다**. 배포 양자화·상주·속도는 A06의 동일 배포 모델 측정과 함께 판단한다.

## 7. 이번 작성의 한계와 사용자 적용 단계

완성한 것은 **대체 구현과 실험 절차**다. 모델·CPU unit test·Python 구문 검사·pip 설치·원본 프로그램·공식 scorer 모두 실행하지 않았다. 미검증 상태를 ‘정상 동작 확인’으로 바꾸지 않는다.

외부 선행조건은 pinned harness와 task 데이터, 공식 HumanEval/EvalPlus, BFCL v3 checkout/의존성, KorQuAD v1.0 공식 scorer다. **KorQuAD scorer 본문 미확보와 BFCL v1.3 호환 미실행**은 남아 있는 검증 사항이다.

사용자 적용 순서는 [README](README.md)의 merge-copy → 별도 환경 의존성 → CPU 테스트 → 과제별 smoke → full split이다. completion.json 없는 실행은 완료로 세지 않는다. BFCL 일부 범주만 평가한 summary에서 누락 범주 0은 모델 성능 0이 아니다. 평가한 범주 점수만 보고한다. [BFCL 실행·부분 평가 안내](https://github.com/ShishirPatil/gorilla/blob/main/berkeley-function-call-leaderboard/README.md).

사용자에게 부탁하는 것: 위 검증은 아직 수행되지 않았다. 원본 적용과 실제 실행 후 결과를 판정해야 한다. 기존 -done.bat 삭제·이동은 이번 범위에 없고 관련 파일을 생성하거나 삭제하지 않았다.
