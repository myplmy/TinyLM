# TinyLM 총괄 작업 지시 — 2026-10-23

당신은 TinyLM 프로젝트의 작업 총괄 GPT이며, 프로젝트의 실제 로컬 경로에 직접 접근할 수 있다. 아래 지시는 이전 논의와 이번 사용자 지시를 통합한 실행 지시다. 로컬 프로젝트의 현재 상태를 직접 확인하고 이미 승인된 범위에서 주도적으로 작업하라. 계획이나 가능성 설명만 제출하고 멈추지 말고, 남은 시간 안에서 실제 구현·실험·평가·기록까지 진행하라.

## 0. 우선순위, 허가, 기한

### 0.1. 반드시 지킬 진행 순서

1. 중단되었거나 진행 중인 기존 작업을 먼저 이어서 완료한다. 초기 상태 확인에는 1.2절의 Gemma270M 증류 체크포인트 추론 오류 조사와 1.3절의 기존 recurrent·공유형 실험 결과 정리를 포함한다.
2. 기존 chat32 경로에서 학습 속도·데이터 효율 개선 실험을 먼저 수행한다.
3. 가속된 chat32 경로에서 교사 증류 방법의 효과를 확인한다.
4. 유망한 증류 방법이 확인된 뒤 기존 recurrent·공유형 실험 결과와 구현을 기준으로 개선·확장한다. prelude + 공유 recurrent core/MLP + coda + MTP 등의 추가 구조 변경은 기존 결과에서 필요한 부분을 정한 후 시험한다.
5. 각 단계 사이와 자원 여유 시간에 공통 벤치마크를 수행한다. 속도 측정은 다른 작업과 자원 경쟁이 없는 구간에 한다.

뒤 단계의 대규모 구조 변경을 먼저 시작하여 위 순서를 뒤집지 않는다. 기존 작업을 계속하기 어려운 경우 원인·보존 상태·재개 방법을 기록하고 가능한 다음 독립 작업을 진행한다.

### 0.3. 해석이 바뀐 사항

- 외부 비교 모델을 Q4로 통일할 필요는 없다.
- 기존 HF 폴더에 같은 모델의 실행 가능한 파일이 있으면 Q4/다른 양자화/BF16/FP16, Base/PT/IT 여부 때문에 중복 다운로드를 강제하지 않는다.
- 다만 특정 IQ2 배포본 대비 성능 목표를 판정할 때는 그 정확한 파일의 결과가 필요하다. 다른 정밀도나 Base/IT 결과로 대신하지 않는다.
- “100M급 고정 삼진이 아니고 공유형으로”라는 후속 지시는 앞서 확정한 고정 삼진을 기본 유지하면서, 이후 구조를 MLP 공유형 기존 재귀추론형으로 함을 의미한다
- 본체와 큰 임베딩/LM head의 고정 삼진을 목표로 하고, scale·norm·projection·cache의 실제 정밀도와 예외 범위를 별도 기록한다. 성능 개선을 위해 몰래 혼합 비트 모델로 바꾸지 않는다.
- 목표는 실제 정상 답변 능력, 적은 상주 메모리, 학습·추론 효율의 동시 개선이다. 40MB는 목표이며 실측 달성치와 구분한다.

## 1. 시작할 때 확인할 로컬 프로젝트 상태

작업 대상은 현재 작업 중인 실제 로컬 TinyLM 프로젝트다. 현재 작업 디렉터리, 기존 세션·작업 기록과 설정에서 프로젝트 루트를 확인하고 실제 절대경로를 기록하라. 경로를 임의로 추정하지 않는다.

프로젝트의 현재 상태는 로컬 코드, 미커밋 변경, 체크포인트, 로그와 실험 기록을 기준으로 판단한다. TinyLM 코드를 확인하기 위해 GitHub에 접속하거나 새로 clone할 필요가 없으며, 원격 조회·동기화를 작업 시작의 선행조건으로 두지 않는다. Git 정보는 로컬 HEAD·변경 내역·이력 확인에 사용한다. 참고문헌의 외부 논문·공식 구현·모델 배포 링크는 필요한 경우 계속 활용한다.

1. 로컬 프로젝트의 현재 HEAD, 변경 파일, 활성 작업/프로세스, 최근 체크포인트, 완료·실패·중단된 실험, 남은 자원을 확인한다. 이미 끝난 작업을 반복하지 않는다.
2. 이전 감사 기준은 e67bc93eb48e8059e649b6c104c1f76e827a7789였다. 이는 과거 참고 식별자이며, 로컬 HEAD 이후 변경과 미커밋 작업까지 포함한 실제 현재 상태를 우선한다. 과거 감사 커밋으로 되돌리라는 지시가 아니다.
3. Muon, 저랭크 tied embedding/head, MLP 공유, CLA2, MTP 보조 head 등은 이미 적용되었거나 실험한 내용일 수 있다. 구현·활성 설정·실패 기록을 확인하고 신규 개선으로 중복 보고하지 않는다.
4. 현재 사용자는 기존 학습 모델에서 정상 답변이 거의 또는 전혀 나오지 않는다고 평가한다. 과거 체크포인트끼리 순위를 가리는 작업을 새 증류 시작의 전제조건으로 삼지 않는다.
5. 실제 tokenizer, chat/completion template, BOS/EOS, label shift, loss mask, 생성 종료, 삼진 실행 경로를 작은 진단으로 확인한다. 낮은 CE나 객관식 점수만으로 정상 대화 능력을 확보했다고 선언하지 않는다.

### 1.1. 이전 감사에서 확인한 사실

아래 내용은 이전 감사 시점의 기록이다. 로컬의 더 최근 코드·체크포인트·실험 기록과 차이가 있으면 최신 로컬 근거로 갱신한다.

- TinyLM 기본 어휘 V=32,768, 본체 d=768, 임베딩 rank r=256.
- 입력 임베딩과 출력 head가 공유되고 projection도 공유된다.
- 어휘 관련 파라미터는 Vr+rd이며, 입력/출력 행렬을 두 번 세지 않는다.
- 공유형 m100R1c/CLA2는 약 63.50M 고유 파라미터, 기존 chat32 m100s10 dense/CLA2는 약 93.27M이었다. “현재 약 100M”과 “공유형”을 같은 구성이라고 가정하지 않는다.
- Qwen3-0.6B-Base의 토크나이저 V=151,936과 Gemma3-270M의 출력 V=262,144를 사용한 교사 증류 실험이 있었다.
- Gemma270M 실험은 300M draw를 완주했다. 앞선 Gemma1B의 OOM과 혼동하지 않는다.
- 기존 외부 SQuAD 평가에는 8.7% 중복 오염 기록이 있어, 과거 수치로 tokenizer 우열이나 정상 대화 달성을 확정하지 않는다.
- rank256→128 통제 실험에서 validation loss가 약 +0.0681 nats 악화한 기록이 있다. 사용자 지정 rank256을 기본 유지하고 임의 축소하지 않는다.
- 현재 embedding의 ternary 저장은 int8 배열이다. 삼진 값과 실제 비트 패킹을 구분한다.
- 이전 로컬 GSQ 보정 실험의 실패는 외부 교사 CE/KD를 이용한 새 end-to-end 삼진 학습 전체가 불가능하다는 증거가 아니다.

### 1.2. 추가 진단 — Gemma270M 증류 체크포인트의 tokenizer 어휘 불일치

사용자는 이전 Gemma3-270M 교사 지식증류 실험 결과인 m100R1c_ko-en_300M_G270Tfull.pt를 현재 inference하려고 할 때 "체크포인트와 tokenizer 어휘 크기가 다름" 오류가 나온다고 보고했다. 이 문제의 원인 조사와 추론 경로 복구를 기존 작업 재개·완료 범위의 초기 진단에 포함한다. 여기서 확인된 것은 사용자의 오류 보고이며, 실제 원인은 로컬 증거로 확인하기 전까지 단정하지 않는다.

확인할 사항:

1. 실제 실행 명령, 실행 디렉터리, 전체 오류 로그·traceback, 오류를 발생시키는 코드 조건을 확보한다. 사전 vocab 검사 실패인지 state_dict 로딩 중 shape mismatch인지 구분하고, 비교한 두 실제 숫자와 변수의 출처를 기록한다.
2. interactive_infer.sh와 실제 Python 진입점을 읽는다. 기본 인자, 환경변수, 상대 경로, 심볼릭 링크, CLI 인자 전달을 추적하여 의도한 체크포인트·tokenizer·config가 실제 선택되는지 확인한다. 현재 셸의 기본 tokenizer나 다른 실험 설정이 끼어드는지는 가설로 조사한다.
3. 체크포인트의 절대경로·SHA256·저장 구조·학습 config·tokenizer 메타데이터와 입력 embedding 및 출력 head의 실제 tensor shape를 확인한다. 여러 가중치 묶음이 있으면 추론이 선택한 묶음을 명시한다. factorized/tied/packed 구조는 실제 논리적 vocabulary dimension을 확인한다.
4. 해당 학생을 학습할 때 사용한 tokenizer를 당시 명령·config·로그·저장 산출물로 확인한다. Gemma270M을 교사로 썼다는 사실이나 G270Tfull 파일명만으로 학생도 Gemma tokenizer를 썼다고 가정하지 않는다. teacher tokenizer, student tokenizer, 현재 inference tokenizer를 각각 구분한다.
5. checkpoint config의 vocab_size, 입력 embedding의 논리적 행 수, 출력 head의 논리적 행 수, tokenizer.vocab_size, len(tokenizer), 실제 최대 token ID+1을 표로 비교한다. added tokens, ID의 빈 구간, 예약 행과 padded output rows도 별도 표기한다. 단순히 수치가 같거나 다르다는 사실만으로 정합성을 확정하지 않는다.
6. 학습 당시와 현재 tokenizer의 token↔ID 대응, 파일 hash/revision, normalizer, merges, tokenizer 클래스, BOS/EOS/PAD/UNK 및 추가 special tokens를 대조한다. 같은 vocab 크기라도 ID 의미가 다르면 잘못된 조합이다. 최초 tokenizer의 mapping을 복구할 근거가 없으면 체크포인트만으로 복원할 수 있다고 주장하지 않는다.
7. 추론 초기화 중 add_tokens/add_special_tokens 등으로 어휘 수가 달라지는지 확인한다. tokenizer.json, tokenizer.model, tokenizer_config.json, special_tokens_map.json, added_tokens.json 등은 실제 구현에 존재하는 파일만 확인하고 서로 같은 학습 산출물인지 대조한다.
8. 정상적인 padding과 잘못된 tokenizer 선택을 구분한다. weight tying, 예약 행의 용도, 사용하지 않는 출력 ID의 masking·decode 처리까지 살핀다. 구현 근거가 있는 padding 차이이면 검증 조건을 정확하게 고치되, 의미가 다른 tokenizer를 허용하도록 검사를 무조건 제거하지 않는다.
9. 로더·캐시·로컬 tokenizer 경로·revision·라이브러리 버전과 기본값을 확인한다. 로컬에서 정상 학습 산출물을 찾는 작업을 우선하고, 원인 확인 없이 패키지 업그레이드·tokenizer 재생성·원격 재다운로드를 해결책으로 삼지 않는다.
10. 올바른 학습 당시 checkpoint/tokenizer 조합과 로딩 설정을 복원하는 최소 변경을 우선한다. 원본 가중치를 보존하며, 임의 resize, 행 삭제·재배열, 무작위 초기화, token ID 재지정으로 오류만 통과시키지 않는다. 메타데이터나 wrapper 오류가 확인되면 그 원인을 수정한다. 실제 필요한 가중치·mapping이 없는 경우 무손실 복구가 불가능한 범위와 필요한 산출물을 밝힌다.
11. 실제 interactive_infer.sh와 Python CLI가 지원하는 옵션을 확인한 뒤, 실행 위치·환경·체크포인트·tokenizer의 실제 로컬 경로를 포함한 복사 실행 가능한 명령을 제공한다. 존재하지 않는 옵션이나 추정 경로를 만들지 않는다.
12. 수정 전 오류 재현과 수정 후 로딩, token ID 유효 범위, 한국어·영어 인코딩 및 생성·디코딩, 종료 처리의 결과를 비교한다. missing/unexpected keys 및 shape mismatch를 숨기지 않는다. 가중치 보존을 주장하면 원본 tensor 값·ID 의미의 유지 여부를 검증한다. 로딩 성공과 답변 품질 개선은 별도로 보고한다.

필수 보고: 확정된 원인과 근거, 확인된 vocab 비교표, 수정한 파일·항목, 올바른 실행 명령, 수정 전후 결과, 미확인 사항. 과거 실험의 tokenizer 선택에 대한 기존 설명이 틀렸다면 관련 기록도 근거와 함께 정정한다.

이 체크포인트의 복구 여부를 새로운 chat32 증류 실험 전체의 시작 조건으로 만들지 않는다. 복구가 막히면 산출물과 원인을 기록하고 독립적으로 가능한 작업을 계속한다.

### 1.3. 기존 recurrent·공유형 실험 결과 우선 확인

사용자는 기존 recurrent 구조 관련 실험 결과가 이미 있다고 명시했다. 초기 로컬 상태 확인에서 해당 결과와 구현을 먼저 조사한다. 새 Huginn 구조를 처음부터 설계해야 한다고 전제하지 않는다.

- 로컬 프로젝트의 handoff, 실험 문서, config, 학습·평가 로그, 체크포인트와 실행 코드를 찾아 기존 recurrent/looped/shared/prelude/core/coda/input-injection/CLA 관련 작업을 연결한다. 문서뿐 아니라 실제 코드·실행 설정·산출물로 확인한다.
- m100R1c 등 이름이나 공유형이라는 표현만으로 recurrent 구조라고 판단하지 않는다. 단순 레이어 간 MLP 공유, attention을 포함한 full-core 반복, recurrent state 갱신을 실제 구현으로 구분한다.
- 실험별로 ID·문서 경로·code commit·checkpoint/hash, 공유 범위, width/FFN, prelude/core/coda, 학습·추론 반복 수 R, 유효 깊이, input injection, 상태 초기화, KV/CLA 처리, MTP, tokenizer, 정밀도·packing 범위를 기록한다.
- 학습 데이터·토큰 예산·교사·증류법·optimizer·seed·평가 규약과 함께 성능, 생성 사례, 파일 크기·실제 상주량·속도, 성공/실패/보류/미실행과 그 근거를 표로 정리한다. 항목이 없으면 미확인으로 남긴다.
- 과거 실패가 구조 자체의 문제인지, tokenizer/loader 오류, cache 구현, 학습량·데이터·증류법, 특정 엔진/정밀도 문제인지 구분한다. 과거의 낮은 지능이나 실행 오류를 recurrent 구조 전체의 실패로 일반화하지 않는다.
- 기존에 검증한 코드·checkpoint·평가 결과를 우선 재사용한다. 현재 구현·배포 조건·평가 규약 변화로 생긴 구체적인 불확실성만 필요한 범위에서 재검증한다. 동일 조건의 완료 실험을 관례적으로 다시 돌리지 않는다.
- 과거 float/다른 tokenizer/다른 지표의 수치를 새 고정 삼진 공통 벤치마크 점수로 옮기지 않는다. 구조 선택에 쓸 과거 근거와 새 배포본의 실측 결과를 구분한다.
- 산출물은 기존 결과 목록, 재사용할 기준선, 확정된 성공·실패 요인, 미확인 사항, 아직 해결되지 않은 문제와 추가 확인 필요 항목이다.

이 조사는 초기 상태 확인에 포함한다. 현재 진행 중이던 recurrent 작업의 재개·마무리는 기존 작업 완료에 포함하고, 새로운 recurrent 구조 변경·확장 실험은 학습 가속과 chat32 증류 검증 이후에 진행한다.

## 2. 1단계 — 학습 가속을 먼저 실험

현재 chat32의 재현 가능한 기준 실행을 잡고 아래 항목을 가능한 한 독립적으로 시험한다. 이미 검증한 동일 실험은 결과를 재사용한다. 짧은 정확성·성능 측정 후 유망한 후보만 학습을 연장하고, 효과 없는 후보를 무한 탐색하지 않는다.

### 2.1. Fused output-head/CE — 최우선

- CCE 및 Liger FusedLinearCrossEntropy를 참고한다.
- TinyLM의 factorized tied head h→r→V 구조에 맞춘다.
- B×T×V 전체 logits를 상주시키지 않는 경로를 목표로 한다.
- label shift, ignore_index, loss reduction, scaling/softcap, embedding 입력 경로와 출력 경로의 gradient, 공유 projection의 gradient를 보존한다.
- 작은 배치에서 기존 구현 대비 loss·gradient·업데이트의 동등성과 허용 오차를 확인한다.
- 평균 scalar CE만 반환해서 ALM/ACTD의 token probability, adaptive masking의 per-token loss, KD의 top-k/분포 계산을 막지 않도록 한다.
- fused CE가 full-distribution KL까지 자동으로 fused해 주는 것은 아니다. KD에 필요한 확률과 잔여 질량을 얻는 경로를 설계한다.
- 현재 32K 어휘에서의 이득과 향후 248K 어휘에서의 이득을 구분한다.

### 2.2. NorMuon / AdaMuon

- 기존 Muon과 NorMuon, AdaMuon을 비교한다. NorMuon을 기존 Muon RMS scaling과 동일시하지 않는다.
- 공식 논문의 learning-rate·RMS·parameter-group 규약을 확인한다.
- embedding, 1D norm/scale, 향후 GSQ code-selection logits를 본체 행렬과 무조건 같은 optimizer group에 넣지 않는다.
- optimizer step 시간뿐 아니라 총 학습 시간, optimizer-state 메모리, 같은 품질에 도달하는 시간을 비교한다.
- AdaMuon의 추가 second-moment state 비용을 기록한다.

### 2.3. 점진적 문맥 길이

- 초기 후보: 128→256→512→1024 또는 256→512→1024.
- 단계별 batch/accumulation과 token budget을 명시한다.
- 문서 경계, packing, 원문 노출량, 처리 토큰량을 기록한다.
- 최종 1024-token 문맥에서의 validation과 생성 능력을 확인한다.
- 짧은 문맥으로 step이 빨라진 것과 최종 품질까지 빨라진 것을 구분한다.

### 2.4. Causal + MNTP, adaptive masking

- 사용자 표기의 casual은 causal로 해석한다.
- GPT-BERT의 causal+MNTP를 참고하되 단순 loss 항 추가로 취급하지 않는다. masking, shifted target, attention visibility, causal/masked 배치 비율을 함께 설계한다.
- adaptive masking은 uniform masking을 대조군으로 비교한다. 한국어·희귀 토큰·숫자 편향과 token 통계 갱신 비용을 확인한다.
- mask-rate schedule, 문맥 길이, optimizer를 한 번에 모두 바꾸지 않는다.
- 초기 증류 결합에서는 causal batch에 KD를 적용하고 masked batch는 별도 CE로 시작하는 방안을 우선 검토한다. 양방향 문맥을 본 학생과 causal 교사를 같은 조건이라고 취급하지 않는다.
- 최종 평가는 causal 생성과 causal likelihood를 기준으로 한다.

### 2.5. 가속 채택 기준

다음을 함께 기록한다.
- train tokens/s, 원문 bytes/s, step 시간, GPU-hours
- compile/warmup 포함 총 시간 및 steady-state 시간
- peak RAM/VRAM, optimizer-state 메모리
- 동일 validation quality에 도달하는 wall-clock time
- 고정된 생성·이해 dev 평가의 변화

같은 token budget 비교와 같은 wall-clock budget 비교를 분리한다. tokenizer가 다르면 같은 원문 노출량 비교도 추가한다. MNTP/adaptive masking의 데이터 효율 향상을 순수 처리량 향상으로 보고하지 않는다. 개별 실험에서 유망한 항목만 결합한다.

Modded-NanoGPT는 목표 loss 도달 시간, Parameter Golf는 압축 크기·BPB, BabyLM은 소량 데이터 학습이라는 서로 다른 기준이다. 리더보드 상위 stack 전체의 개선을 단일 기법의 효과로 귀속시키지 않는다. Parameter Golf의 압축 파일 크기를 실행 RAM으로 간주하거나 test-time training을 주 비교에 몰래 도입하지 않는다.

## 3. 2단계 — 기존 chat32에서 교사 증류법 확인

처음에는 현재 chat32 구조와 tokenizer를 유지하여 증류 방법의 효과를 확인한다. recurrent 구조, 전체 어휘 교체, optimizer 변경을 동시에 시작하여 원인을 알 수 없게 만들지 않는다.

### 3.1. 교사 우선순위

1. 주교사:
   - ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF
   - Qwen3.8-27B-GSQ-RCO-IQ2_XS-mtp.gguf
2. 주교사 사용이 어렵거나 충분한 개선이 확인되지 않으면 다음 대체 교사를 검토:
   - unsloth/gemma-4-12b-it-GGUF의 gemma-4-12b-it-Q4_0.gguf와 대응 MTP
   - Bonsai-2-27B의 PTQ1_0 본체 + Q8_0 MTP head 구성(사용자 표기: Bonsai-2-27B-PTQ1_0-MTP-Q8_0)
3. 위 대형 대체 교사도 적절하지 않으면 작은 교사로 범위를 낮춰 검토:
   - Qwen3.5-0.8B-Base
   - Bonsai-2-2B
   - Gemma3-270M
   - 이미 확보한 관련 소형 모델도 진단용으로 활용 가능

“불가”는 로딩/OOM, 엔진·확률 추출 미지원, 구현 오류, 최적화 불안정, 실제 지식 전달 실패로 구분한다. 한 번의 NaN이나 잘못된 template 때문에 교사 능력이 부족하다고 결론내리지 않는다. 반복 확인으로 시간을 소진하지 말고 원인을 기록한 뒤 다음 가능한 방법/교사로 진행한다.

교사를 바꾸기 전후에 데이터·학습량·학생 설정을 가능한 한 맞추고, 방법 비교와 교사 비교를 구분한다. 학생에게 지나치게 긴 reasoning trace만 주지 말고 검증 가능한 짧은 한국어·영어 답, 지문 기반 답변, 단계적 난도의 과제를 포함한다.

### 3.2. 파일명과 MTP 해석

- Gemma4 MTP는 Q4 본체와 별도 파일일 수 있다:
  - MTP/mtp-gemma-4-12b-it-Q8_0.gguf
  - root의 mtp-gemma-4-12b-it.gguf
- Bonsai27B의 MTP 결합 배포는 제3자 head graft일 수 있다. 사용자가 말한 파일의 실제 출처·hash·본체·MTP head provenance를 확인한다.
- 파일명에 MTP가 있어도 실제 엔진 지원·활성 여부를 확인한다.
- 교사 MTP는 추론 가속 기능이다. 미지원만으로 교사 증류 전체를 중단하지 말고 정상적인 본체 next-token logits 경로로 계속한다.
- 교사 MTP, 학생 MTP 보조 학습, 학생 speculative decoding은 별도 항목이다.
- 검증하지 않은 draft-only 분포를 교사의 주 next-token 분포로 대신 사용하지 않는다.

### 3.3. 시험할 방법과 권고 순서

기준 실험:
- 같은 교사 답변 데이터의 CE/SFT-only 대조군.
- ALM + 현재 삼진 학습 경로.
- 가능하면 ALM + GSQ에서 가져온 이산 최적화를 동일 CE/KD 목표로 비교.

이어서 ACTD, DWA-KD/DSKDv2, DVLM의 최소 구현·단기 학습을 비교한다. 사용자가 요청한 각 방법에 대해 구현 상태, 실제 실행 여부, 실패 원인, 시간·메모리·성능을 남긴다. DVLM은 교사 실행 경로 수정이 커질 수 있으므로 준비를 병행하되 ALM 등의 검증을 막지 않는다.

각 방법의 요점:
- ALM: 다른 tokenizer의 동일 텍스트 구간을 대응시키는 기준 방법. 임의의 단순 log-prob MSE로 대체하고 ALM이라고 부르지 않는다.
- ACTD: 신뢰할 수 있는 teacher top-k anchor와 잔여 확률 정규화. 공개 코드 상태를 확인하고, 미공개면 논문 기반 최소 구현 가능성을 검토한다.
- DSKD/DWA-KD: 표현 공간 projection, tokenizer 정렬, 불확실성 weighting. hidden state/head 접근과 추가 비용을 확인한다.
- DVLM: 학생 어휘를 유지하면서 교사 쪽에 학생 어휘 head와 입력 정렬 구조를 만든다. head 하나만 붙이면 입력 불일치까지 해결된다고 가정하지 않는다.
- X-Token/BLD: 기존 방법이 막히거나 정렬 병목이 확인될 때 비교 가능한 대안.
- BPM/ESCD/CAST/BSD: 정상적인 학생 rollout이 가능해진 이후 후속 후보. 현재 무응답 학생에 on-policy-only 학습이나 약한 학생의 self-teacher를 첫 필수 경로로 강제하지 않는다.

일부 최신 논문은 사전학습된 0.6B~수B 학생에서 검증됐다. ROUGE-L·Avg@8·GSM8K 개선을 TinyLM의 보장 점수나 “교사 지능 이식 비율”로 바꾸지 않는다.

### 3.4. GSQ는 정상 답변이 나오기 전부터 시작 가능

- 정상 답변 능력은 GSQ 증류 시작의 필수 조건이 아니다.
- 정답 prefix를 제공하는 teacher forcing으로 처음부터 CE+KD를 학습할 수 있다.
- 원래 GSQ는 기존 모델의 사후 양자화 방법이다. 이종 교사-학생에서는 기존 학생의 나쁜 출력을 재구성하는 목표 대신 외부 교사의 정답과 분포를 목표로 한다.
- 제안 목표:
  L = lambda_CE × verified-text CE + lambda_KD × aligned-teacher KD
  W = scale × Q, Q ∈ {-1,0,+1}
- GSQ의 Gumbel/이산 선택 최적화를 가져오되 이는 새로운 TinyLM용 QAT/KD 설계라는 점을 명시한다.
- hard 삼진 forward/evaluation, code/scale 초기화, 온도 schedule, 삼진 선택 붕괴, gradient 유효성을 확인한다.
- embedding/head도 최종 삼진 제약을 학습에 반영한다.
- 기존 STE와 같은 손실·데이터 조건의 대조군을 둔다. 정상 답변을 먼저 확보해야 STE 대조를 끝내고 GSQ를 시작할 수 있다는 조건은 만들지 않는다.
- 고정 삼진에서는 RCO의 혼합 비트 배분을 기본 적용하지 않는다.
- 최종 40MB 배포 목표와 학습 중 code logits·optimizer·activation·교사 메모리를 구분한다.

### 3.5. 교사 신호 추출·캐시

- GGUF에서 reference sequence에 대한 teacher-forced token log-probability/logits를 얻을 수 있는지 먼저 확인한다.
- 일반 채팅 응답 텍스트만 있으면 sequence-level KD는 가능하지만 ALM/full KL/hidden-state KD를 이미 구현했다고 볼 수 없다.
- teacher top-k를 저장하면 probability normalization, log-normalizer와 tail/residual mass 처리 방식을 명시한다. 저장된 top-k만 임의 재정규화한 것을 full-vocab KL이라고 부르지 않는다.
- 데이터 ID, 원문 hash, 교사 파일 hash, tokenizer revision, template, temperature, EOS, loss mask를 캐시와 연결한다.
- 공식 평가 문항·정답과 자체 final holdout을 교사 데이터 생성·선별·KD 학습에 사용하지 않는다.
- teacher cache 생성 시간을 포함한 총 time-to-quality와 cache 재사용 이후 학생 학습 시간을 모두 보고한다.

### 3.6. 정상 답변의 판정

별도의 한국어 100 + 영어 100 final holdout을 고정하고, 개발용 prompt 집합은 따로 둔다.

각 응답을 다음 세 축으로 판정한다.
1. 출력 안정성: 비어 있지 않고, 심한 파손·무한 반복·역할 토큰 노출·종료 실패가 없는가.
2. 질문 대응성: 질문에 관련된 답을 요구한 언어·형식으로 제공하는가.
3. 내용 정확성: 지문·정답·규칙에 비추어 핵심 내용이 맞는가.

세 조건을 모두 만족하는 usable-response rate와 각 실패율을 보고한다. 단순한 문법성이나 유창함을 정답으로 처리하지 않는다. 짧은 지문 QA, 추출/변환, 형식 지시, 기초 계산/추론, 일상 질문을 포함한다.

초기 0%도 실험 시작을 막지 않는다. 방법 채택은 held-out 일반화, 이해 벤치마크, 자원 비용을 함께 판단하며, 임의의 “정상 답변 확보” 조건 때문에 연구를 중단하지 않는다.

## 4. 3단계 — 기존 recurrent 결과에 기반한 구조 개선·확장 + MTP

### 4.0. 기존 결과에서 출발하는 진행 순서

1. 1.3절에서 조사한 기존 recurrent·공유형 코드, 실험 결과와 체크포인트를 먼저 확인한다.
2. 현재 목표에 맞게 재사용할 기존 기준선을 확정한다. 기준선의 구성·학습 조건·장점·제약을 명시한다.
3. 기존 결과에서 확인된 미해결 문제를 구체화한다. 예: 반복 증가 시 품질 저하, KV 증가, 학습 불안정, 실제 상주량, prefill/decode 비용. 확인되지 않은 문제를 임의로 만들어 내지 않는다.
4. 4.5절·11장의 연구를 각 문제와 연결하고 이미 적용한 것, 추가로 시험할 것, 현재 필요 없는 것을 구분한다.
5. 필요한 변경만 통제된 추가 실험으로 수행한다. 기존 성공·실패 실험의 반복은 조건 변화나 미해결 원인 등 구체적인 이유가 있을 때에 한한다.

이 단계의 출발점은 기존 결과다. 새로운 논문이나 아래 예비 grid가 검증된 로컬 결과보다 자동으로 우선하지 않는다. 기존 구성이 유망하면 이를 개선·확장하고, 판단할 근거가 부족한 부분에만 새로운 구조 후보를 사용한다.

### 4.1. 구조 원칙

- prelude → 반복 core → coda 구조로 작은 고유 가중치와 유효 깊이를 함께 확보한다.
- 기존 MLP-only sharing과 Huginn-inspired full-core recurrence를 구분한다.
- 공유 범위(attention/MLP/norm), prelude/coda 깊이, core 깊이, 반복 횟수 R, input injection, 초기 recurrent state를 config에 명시한다.
- 먼저 단일 recurrent state와 명확한 실행 구조를 검증한다.
- 학습/추론에서 R을 바꿀 때 실제 성능·속도·KV 크기의 곡선을 측정한다. 반복을 늘리면 성능이 자동으로 좋아진다고 가정하지 않는다.

### 4.2. 기존 결과로 결정하기 어려울 때 참고할 구조 후보

기존 recurrent·공유형 실험에서 유망한 구성이 확인되었다면 그 구성을 우선 기준선으로 삼는다. 아래 A/B/C는 기존 결과만으로 width·depth·공유 범위를 결정하기 어려울 때 참고하는 예비 후보이며, 새로 전부 실행해야 하는 실험 목록이나 기존 결과보다 우선하는 권고가 아니다. 이전에 제시한 B 우선 검토 제안도 이 원칙에 종속된다. 기존 결과와 kernel·자원 제약으로 후보를 줄이고 실제로 추가할 필요가 있는 변경만 시험한다.

공통: Qwen/Bonsai 전체 어휘 채택 시 V=248,320, rank256 tied embedding, 고정 삼진 본체, segment 내부 CLA2, MTP는 우선 t+2 한 개.

| 후보 | width / FFN | Q/KV heads, head_dim | prelude/core/coda | R 후보 | 유효 깊이 | 고유 파라미터 개략 |
|---|---|---|---|---|---|---|
| A 메모리 우선 | 512 / 1536 | 8/2, 64 | 2/2/2 | 4,6,8 | 12,16,20 | 약 81.40M |
| B 기존 폭 비교용 예비안 | 768 / 2048 | 12/3, 64 | 2/2/2 | 4,6,8 | 12,16,20 | 약 100.04M |
| C 표현력 확대 | 768 / 2048 | 12/3, 64 | 2/4/2 | 2,4,6 | 12,20,28 | 약 112.13M |

개략 파라미터는 full recurrent core 공유, 3-matrix MLP, CLA2 owner 구조 가정이며 norm·MTP·추가 injection 변수 등은 제외한 산술이다. 실제 구현 후 공유를 중복 제거한 논리적 고유 가중치 수와 실제 storage bytes를 별도로 재계산한다. MLP만 공유하는 모델에는 이 숫자를 그대로 적용하지 않는다.

### 4.3. Recurrent KV와 CLA2

- 가중치 공유가 KV cache 공유를 뜻하지 않는다.
- 기본 정답 경로는 segment, recurrent iteration, core layer, sequence position을 구분한다.
- 물리적 공유 레이어 ID만으로 KV를 저장하여 이전 iteration을 덮어쓰지 않는다.
- CLA2의 KV owner/consumer를 명시한다.
- full-prefill과 incremental decoding의 logits 동등성, cache reset, RoPE 위치를 확인한다.
- iteration 간 KV 공유/압축은 기본 정답 경로 이후 별도의 근사 실험으로 둔다.
- 반복 횟수에 따라 FLOPs·latency·학습 activation·정확한 KV 메모리가 늘어날 수 있음을 보고한다.

### 4.4. 학생 MTP

- 기존 TinyLM MTP 구현을 감사하고 가능한 부분을 재사용한다.
- 먼저 학습 보조 목표로 t+2 하나를 시험하고, 효과가 있으면 t+3/t+4를 추가한다.
- 각 head마다 248K embedding을 복제하지 않고 tied vocabulary table을 공유한다.
- 주 next-token head의 벤치마크·생성 능력으로 기본 품질을 평가한다.
- 추론 가속은 별도로 draft–verify, acceptance rate, cache rollback, greedy 결과 일치를 확인한다.
- MTP를 학습했다는 사실만으로 추론 가속을 달성했다고 보고하지 않는다.

### 4.5. 사용자 제공 Huginn·반복형 모델 후속 연구 검토

1.3절과 4.0절의 기존 실험 결과·미해결 문제를 먼저 정리한 뒤, 11장의 사용자 제공 연구 요약과 아래 9개 연구를 해당 문제의 개선 후보에 연결한다. 자료의 성격은 참고문헌이며, 모든 방법을 즉시 구현하거나 기존 작업 → 학습 가속 → chat32 증류 → recurrent 구조의 순서를 바꾸라는 지시가 아니다. 실제 채택 판단에 사용하는 논문 버전·표·평가 조건·공개 구현을 확인하고, 사용자 요약과 차이가 있으면 정정 근거를 기록한다.

| 연구 / 참고문헌 | TinyLM에서 검토할 사항 | 비교·검증 조건 |
|---|---|---|
| LoopCD [C4] | 반복 단계 예측을 이용한 디코딩 보정. 큰 어휘에서 추가 head 계산을 피하는 Hidden 변형 | 학습 개선과 decoding 변경을 구분한다. 같은 반복 수와 같은 총 추론 비용의 비교를 각각 수행한다. 보정된 주모델 분포를 사용할 경우 MTP의 검증 분포도 그 정의와 맞춘다. |
| MoDr [C5] | 공유 core에 작은 LoRA 분기와 router를 추가하는 방법 | 추가 파라미터·정밀도·routing 계산·상주 메모리를 포함한다. 고정 삼진 예외를 임의로 늘리지 않으며 다중 분기를 초기 필수 구조로 강제하지 않는다. |
| Continuous Depth Batching [C6] | 토큰별 반복 깊이가 달라진 이후의 스케줄링 | 단일 요청·CPU 추론과 다중 요청·GPU 배치 서빙을 구분한다. iteration별 상태·KV 정합성이 먼저이며, 서빙 처리량 개선을 학습 가속으로 보고하지 않는다. |
| Towards Looped Models Done Right, Part I [C2] | prelude/core/coda, input injection, recurrent-state 초기화·구성 | 같은 고유 파라미터·유효 깊이·학습량·계산량을 가능한 범위에서 맞추고 변경 요인을 분리한다. 기존 [C2]와 동일 문헌이다. |
| Part II: Rethinking at Fixed Points [C7] | depth prior, orthogonal input injection, terminal-state KV 재사용, prefill 증류 | 정확한 iteration별 KV 기준선 이후의 근사 실험으로 둔다. 캐시 절감·prefill 가속·RL 업데이트 가속을 한 설정의 누적 성과로 합치지 않는다. |
| Closing the Loop [C8] | mid-training, input-mixing scalar, exit-gate 정규화, smoothed exit loss | 처음부터 학습과 Dense→looped 변환을 구분한다. 기존 chat32 증류 경로와 결합 가능성을 검토하며 추가 학습량과 데이터가 같은 대조군을 둔다. |
| STARS [C9] | 무작위 반복 깊이 학습과 recurrent dynamics 안정화 | 학습보다 많은 반복에서의 성능 유지와 Jacobian 관련 정규화의 추가 시간·메모리를 측정한다. Ouro 결과를 Huginn/TinyLM 재현 결과로 표현하지 않는다. |
| TaH2 [C10] | 토큰별 iteration decider, updater, lookahead supervision | 고정 반복 기준선 이후에 가변 깊이를 검토한다. 평균 반복 수·분포·정확도와 cache/batching 정합성을 함께 보고한다. |

운영 원칙:
- 기존 결과에서 재사용할 기준선과 해결할 문제가 확인된 후 Part I와 Closing the Loop 등을 기본 구조·학습 레시피 검토에 연결한다. 이미 검증한 고정 반복·정확한 iteration별 KV 경로는 재사용하고, 없는 부분만 보완한다.
- 이후 디코딩 보정, 반복 안정화, 동적 종료, KV 근사, 분기·보상 선택을 변경 단위별로 검토한다. 남은 시간과 실제 이득에 따라 유망한 후보만 확장한다.
- 고정 삼진 본체, rank256 tied embedding/head, CLA2, MTP와의 호환성을 항목별로 기록한다. router·adapter·decider·reward model 및 반복 상태·cache·작업 버퍼를 메모리 계산에서 빼지 않는다.
- 논문이 보고한 모델 규모·데이터·반복 수·benchmark·%와 %p·FLOPs와 wall-clock을 구분한다. TinyLM의 성능 보장치로 대입하거나 서로 다른 논문의 가속 배수를 곱하지 않는다.
- LoopCD 등의 추론 변경 결과는 6장의 공통 배포 기준선과 별도 행으로 보고한다. likelihood·생성·MTP 비교에 어느 분포와 실행 경로를 썼는지 명시한다.
- 각 후보의 근거, 필요한 구현, 추가 파라미터·정밀도, 학습·추론 비용, 실제 상주량, 성능과 채택/보류 이유를 표로 남긴다. 자료 검토와 실제 실험 완료를 구분한다.

## 5. Qwen/Bonsai 248K × rank256 임베딩 패킹

### 5.1. 정확한 tokenizer 일치

V가 같다는 사실만으로 Qwen3.8, Qwen3.5, Bonsai가 동일 tokenizer라고 판단하지 않는다. 실제 채택한 교사의 token ID, tokenizer 파일 hash/revision, merges, normalizer, special tokens, padded output rows, BOS/EOS를 확인한다.

정확히 일치하면 직접 token KL+CE를 기준 방법으로 삼는다. ALM 정렬을 불필요하게 계속 적용하지 않는다. template과 response 위치의 loss mask 정렬은 여전히 확인한다.

기존 32K 유지+ALM 계열과 전체 교사 어휘+직접 KL을 비교할 수 있지만, 토크나이저 변경으로 파라미터·출력층 계산량·원문 노출량도 바뀐다는 점을 기록한다.

### 5.2. 크기와 구현 목표

- 기존 r256에서 Qwen/Bonsai V248,320으로 변경: +55,181,312 파라미터.
- Gemma3 V262,144로 변경: +58,720,256 파라미터.
- 입력/출력 embedding과 projection을 중복 계산하지 않는다.
- 5개 삼진 값을 1바이트에 패킹하고 행별 FP32 scale을 두면:
  M_table = V × (ceil(256/5)+4)
- Qwen/Bonsai: 13,905,920 bytes ≈ 13.91MB.
- Gemma3: 14,680,064 bytes ≈ 14.68MB.
- 이는 표와 scale만의 크기이며 projection·본체·KV·logits·tokenizer·runtime은 별도다.
- 현재 int8 기반 ternary table은 같은 Qwen 어휘에서 약 64.56MB이므로 실제 패킹 구현이 필요하다.
- lookup과 output head 모두 packed/blockwise 실행하여 전체 FP16/FP32 vocabulary matrix를 상주시키지 않는다.
- packing round-trip, 삼진 코드/scale 복원, 배포 경로 logits, 응답 품질을 확인한다.
- 파일 크기, 실제 tensor storage, weights+cache, peak RSS, peak VRAM을 각각 측정한다.
- 이전 공유형 본체에 새 패킹을 대입한 약 32.4MiB(Qwen)/33.2MiB(Gemma) weights+KV 추정은 구현·작업버퍼·품질이 검증된 실측값이 아니다. 새 모델의 40MB 달성을 대신하지 않는다.

## 6. 공통 벤치마크와 외부 비교 모델

### 6.1. 주 비교의 목적

“TinyLM의 실제 고정 삼진 배포 모델이 기존 소형 모델과 정확도·한국어 능력·답변 생성·메모리·속도에서 얼마나 차이 나는가?”

외부 모델의 FP16/BF16 원본 전체 평가나 원본 대비 양자화 손실 측정은 필수 아니다. 기존 HF에 있는 FP16/BF16 모델은 실제 비교본으로 사용할 수 있다. 모든 행에 실제 정밀도와 Base/PT/IT를 표시한다.

### 6.2. 외부 모델 목록

### 6.3. TinyLM 평가본 확정

- 실제 평가할 배포 checkpoint 이름, 학습 config, commit, SHA256을 기록한다.
- 고정 삼진 적용 범위, packed 여부, scale/norm/projection/cache 정밀도를 기록한다.
- 기존 native595_ternary를 이름만 보고 새 최종 배포본으로 간주하지 않는다.
- float checkpoint는 개발·진단용으로 둘 수 있으나 주 비교의 삼진 점수를 대신하지 않는다.
- 기존 TinyLM float MC768 44.92%, Falcon MC768 51.82%, 차이 6.90%p는 새로운 비교 결론으로 재사용하지 않는다.

### 6.5. 지표 이름의 중요한 차이

이전 TinyLM 내부:
- acc = 평균 CE 및 기본 PMI 보정 기반
- acc_norm = 토큰 길이 정규화
- harness_acc = 로그우도 합, PMI 없음
- harness_acc_norm = 문자 길이 정규화

공식 harness의 acc_norm은 선택지 문자열 문자 수로 정규화한다. 주 비교는 공식 harness adapter 또는 검증된 harness_acc/harness_acc_norm 대응을 사용한다. 내부 이름만 보고 공식 점수와 비교하지 않는다. prompt·공백·split·few-shot도 일치시킨다.

### 6.6. 공통 실행 규약

1. 동일한 문항 ID, 정답, 전처리, 채점 규칙을 적용한다.
2. 공통 객관식은 0-shot 전체 선택지 conditional log-likelihood로 평가한다.
3. 객관식 공통 트랙에는 chat template과 생성형 thinking을 사용하지 않는다. 모델의 필수 BOS 등 처리 규약은 기록한다.
4. 실제 생성은 IT의 공식 template, Base/TinyLM의 사전 확정 completion 형식을 사용한다.
5. 생성 기본은 greedy이며 출력 예산·종료·답 추출을 고정한다. tokenizer별 토큰 수 차이와 한도 도달을 기록한다.
6. 공통 문맥 목표는 총 1,024토큰이다. 모든 tokenizer에서 동일 원문과 모든 선택지가 들어가는 공통 문항 집합을 먼저 확정한다.
7. 모델마다 원문을 다르게 자르지 않는다. 제외 문항과 공통 subset 비율을 공개한다.
8. 후보 답변 전체의 확률을 계산한다. 자유 생성 A/B/C/D나 일부 top-logprob로 대체하지 않는다.
9. 문항·선택지·독립 생성 사이에 KV와 recurrent state가 섞이지 않게 한다.
10. 가능한 모델은 같은 llama.cpp commit·실행 설정을 사용한다. Prism/TinyLM 별도 엔진이면 차이를 명시한다.
11. weight 정밀도와 KV/recurrent cache 정밀도를 분리한다.
12. MTP off의 기본 정확도와 MTP on의 속도 실험을 구분하고 출력 분포 보존을 검증한다.
13. 학습이 같은 CPU/GPU를 점유한 상태의 속도를 단독 성능으로 보고하지 않는다.
14. 중간 의사결정에는 dev subset, 최종 보고에는 사전 고정 final holdout을 사용한다. 반복적 final 평가를 학습 데이터 선정이나 튜닝 신호로 사용하지 않는다.
15. 공식 IFEval과 내부 간이 지시 검사, lambada_openai와 lambada_standard, 한국어 Ko-LAMBADA의 다른 구성/채점을 구분한다.

### 6.7. BabyLM 다운로드·실행

- 공식 평가 문항의 새 다운로드와 평가 전용 저장은 이미 허가되었다.
- train/SFT/KD 데이터 경로와 분리하고 dataset revision·문항 ID·다운로드 출처를 기록한다.
- 최신 공식 pipeline을 우선 확인한다. 과거 연도의 평가 구성으로 고정하지 않는다.
- 2026 공식 zero-shot 구성과 fine-tuning 평가를 구분한다. task fine-tuning 파생본의 점수를 원래 배포본 점수에 섞지 않는다.
- 대형 외부 교사를 쓴 TinyLM 개발과 BabyLM 대회 참가 자격은 별개다. 공식 평가 수행을 공식 대회 적격/순위 달성으로 표현하지 않는다.
- 대회 출품 시에는 최신 teacher/data 제한을 재확인하되, 그 규정 때문에 이번에 승인된 대형 교사 개발 실험을 중단하지 않는다.

### 6.8. 비교 차이·통계·자원

주 차이 = 외부 모델 실제 실행본 점수 - TinyLM 실제 고정 삼진 실행본 점수.
단위는 퍼센트포인트(%p)다.

- 동일 문항 paired bootstrap으로 95% CI 계산.
- Core6 평균은 과제별 동일 가중치를 유지하는 계층적 bootstrap.
- Belebele은 link/question_number 등 공식 대응키를 확인하고 같은 지문을 묶어 재표집.
- CI가 학습 seed 간 변동까지 포함한다고 주장하지 않는다.

함께 기록:
파일 크기, 고유 파라미터 수, 유효 깊이/R, 실제 tensor storage, weights+cache, peak RAM/RSS/VRAM, TTFT, 전체 응답 시간, tokens/s, chars/s 또는 bytes/s, 출력 길이, 한도 도달률, Base/PT/IT, 정밀도, 엔진/commit, thread/offload/cache 설정, hardware.

해석:
A. 비슷한 규모: GPT-2 small, Falcon-H1-Tiny-90M.
B. 더 큰 실제 배포 모델: Gemma270M, Qwen0.6/0.8B, Gemma1B, Bonsai2B.
정확도와 자원 절감을 함께 보여준다. 비트 수가 같아도 학습량·모델 크기·IT 여부가 같아지는 것은 아니다.

## 7. 성능 목표의 수학적 정의

Qwen3.5-0.8B IQ2_XXS의 “무작위 초과 능력 절반”:
- Q_i = 해당 정확한 IQ2 파일의 실측 점수
- c_i = 과제별 균등 무작위 선택 기준
- 목표 S_i >= c_i + 0.5 × (Q_i-c_i), 단 Q_i>c_i

PIQA/WinoGrande/BoolQ는 50%, HellaSwag는 25%, ARC는 문항별 선택지 수 평균으로 약25%다. Core6 동일가중치 무작위 기준은 약37.5%다. 모든 과제에서25%를 빼지 않는다.

Gemma3-270M 한국어 75%:
- 비교할 Base/IT 및 정밀도·template을 먼저 고정한다.
- 사용자가 요청한 원점수 비율 S_i>=0.75G_i를 표시하되, 객관식에는 c_i+0.75(G_i-c_i)도 보조로 제시한다.
- 기준 모델이 무작위 이하이거나 원점수75%가 무작위보다 낮으면 이를 유효한 언어 능력 확보라고 해석하지 않는다.
- macro-F1·IFEval·자유 생성에25%를 임의로 빼지 않는다.
- 한국어 실제 usable-response rate를 반드시 함께 보고한다.
- BF16 모델 카드 점수를 IQ2/Q4 실측으로 쓰지 않는다.

## 8. 실험 운영

마감 전 모든 단계를 억지로 완료했다고 선언하지 않는다. 실제 완료한 단계, 부분 결과, 미실행 후보를 명확히 나눈다. 최신 방법을 모두 한 번에 결합하지 말고 유망한 결과를 중심으로 남은 시간을 배분한다.

## 10. 지금 실행할 첫 행동

현재 시각과 실제 로컬 프로젝트 루트, 진행·중단 작업을 직접 확인하라. 초기 작업에는 1.2절의 Gemma270M 체크포인트 추론 오류 조사와 1.3절의 기존 recurrent 결과 확인을 포함한다. 기존 작업 재개·완료 → 학습 가속 → chat32 증류 검증 → 기존 recurrent 기준선의 개선·확장 순서의 실행 큐를 작성한 뒤 첫 작업을 실제로 시작하라. TinyLM GitHub 조회 없이 로컬 작업을 바로 이어서 진행하라. 새 recurrent 실험은 기존 결과에서 필요한 변경을 정한 뒤 수행하고, 4.5절·11장의 연구는 그 문제와 연결하여 검토하라. 남은 시간 안에서 자원과 결과를 보며 주도적으로 진행하고, 마감 전에 보존 가능한 상태와 근거 있는 보고서를 남겨라.

## 11. 부록 — 사용자 제공 Huginn·반복형 모델 연구 요약

이 부록은 사용자가 추가 제공한 연구 설명·평가 수치·출처·용어를 전달용으로 정리하여 보존한 자료다. 이번 전달문 편집에서 모든 논문 수치를 독립 재검증한 것은 아니다. 총괄 GPT는 실제 적용 판단에 사용하는 원문의 버전·표·평가 조건을 확인하고, 차이가 있으면 사용자 요약과 정정 근거를 함께 기록한다.

이 자료는 기존 로컬 recurrent 실험 결과를 먼저 확인한 뒤 참고한다. 문헌의 결과가 기존 TinyLM 실험을 대체하거나, 제시된 모든 방법을 바로 구현하라는 뜻은 아니다. 본문의 작업 순서와 4.0절·4.5절을 따른다.

### 11.0. 자료 목적 및 범위

- 목적: Huginn 및 Looped Language Models의 성능 개선, 잠재 추론, 학습 효율과 추론 비용 최적화에 관한 연구 참고자료 제공.
- 사용자 자료의 주요 조사 기간: 2026-01-01~2026-10-23.
- 포함 범위: Huginn 직접 실험, Huginn형 아키텍처, 반복형 모델 학습·추론 최적화.
- LTO는 arXiv 최초 공개가 2025년이지만 ICLR 2026 발표 논문이어서 별도 포함.
- 원자료는 문헌 검토를 위한 연구 소개이며 연구 종합 결론·최종 권고·후속 계획·신규 아이디어를 제시하는 문서가 아니다. 이 제한은 제공받은 자료의 성격을 설명하며, 본문에서 총괄 GPT에게 요구한 적용 검토·실험 판단은 별도로 수행한다.
- 서로 다른 논문의 모델 규모·학습량·반복 횟수·평가 방식이 다르므로 수치를 직접 비교하거나 TinyLM 예상 성능으로 환산하지 않는다.

### 11.1. LoopCD [C4]

제목: Decoding Looped Transformers Better for (Almost) Free
저자: Weihao Liu, Huangjie Zheng, Tianrong Chen, Rohit Dilip, Richard He Bai, Yizhu Jiao, Yuyang Wang, Ruixiang Zhang
공개일: 2026-10-01
arXiv: 2610.02185
논문: https://arxiv.org/abs/2610.02185

반복형 Transformer의 앞선 반복에서 얻은 예측을 마지막 반복 예측과 대조하여 토큰 선택을 보정하는 학습 없는 contrastive decoding 기법이다. 기존에는 일반적으로 마지막 반복의 출력만 사용한다.

- LoopCD-Logits: 반복 단계별 logits를 대조하며 추가 출력 계산이 필요하다.
- LoopCD-Hidden: 최종 출력 계층 이전의 hidden state를 결합하여 추가 LM head 계산을 피하도록 설계된다.

사용자 자료에 기재된 결과:

| 모델·평가·반복 수 | 기본 모델 | LoopCD |
|---|---:|---:|
| Huginn-0125 3.5B, HumanEval pass@1, R=32 | 22.56% | 31.71% |
| Huginn-0125 3.5B, HumanEval pass@1, R=16 | 21.95% | 28.05% |
| Ouro-2.6B-Thinking, AIME 2024 pass@1 | 61.88% | 73.33% |

- Huginn을 포함한 네 가지 반복형 Transformer 계열을 평가했다.
- Huginn R=16의 LoopCD-Hidden은 기본 모델 R=32의 HumanEval 점수보다 높았다고 요약되어 있다.
- 반복 깊이를 절반으로 줄인 여러 설정에서 정확도를 유지·개선하면서 forward FLOPs를 22.5~48.2% 줄였다고 보고했다. Huginn R=32→16은 48.2% 감소에 해당한다.
- 코드 생성 이외에도 수학·객관식 과제를 평가했으나 개선 폭은 모델과 과제별로 다르다.
- Huginn의 HumanEval은 직접 실험이며 다른 모델의 AIME 결과와 구분한다. FLOPs 감소를 같은 비율의 wall-clock 개선으로 간주하지 않는다.

### 11.2. MoDr [C5]

제목: MoDr: Mixture-of-Depth-Recurrent Transformers for Test-Time Reasoning
저자: Xiaojing Zhang, Haifeng Wu, Gang He, Jiyang Shen, Bochen Lyu, Zhanxing Zhu
발표: ICLR 2026
논문: https://proceedings.iclr.cc/paper_files/paper/2026/hash/8a81180649011d1690e05c68bfeaa57c-Abstract-Conference.html

Huginn의 동일 반복 블록을 연속 적용하는 경로에 LoRA 기반 다중 분기와 학습 가능한 hard-gate routing을 도입한다. hidden state에 따라 변환 경로를 선택하고, 별도 보조 손실 없이 routing 부하를 균형화하는 방법을 포함한다.

기반 모델: Huginn 3.5B.

| 평가 | 기본 Huginn 대비 | Huginn 미세조정 모델 대비 |
|---|---:|---:|
| 수학 추론 평균 정확도 | +7.2% | +2.48% |
| 상식 추론 평균 정확도 | +21.21% | +1.52% |

- 위 개선량은 사용자 자료의 논문 표기를 보존한 것이다. 상대 %와 절대 %p를 원문 확인 없이 동일시하지 않는다.
- 수학 과제에는 GSM8K, MAWPS, AQuA, MultiArith, AddSub, SingleEq 등이 포함된다.
- 기반 모델 약 3.56B, 추가 학습 파라미터 약 8.13M.
- 보고된 학습 메모리 54GB, 배포 메모리 13GB.
- 보고된 학습 시간 약 16시간 26분.
- 생성 속도 약 13 tokens/s, 비교 Huginn 약 15 tokens/s.
- 실행 환경·배치·장치에 종속된 값이며 TinyLM의 메모리·속도 예상치로 사용하지 않는다.

### 11.3. Continuous Depth Batching [C6]

제목: Depth-adaptive Inference of Looped Language Models via Continuous Depth Batching
저자: Kristian Schwethelm, Daniel Rueckert, Georgios Kaissis
공개일: 2026-08-10
arXiv: 2608.09444
논문: https://arxiv.org/abs/2608.09444

토큰마다 필요한 반복 깊이가 다를 때 생기는 배치 실행 비효율을 줄이는 추론 시스템 연구다. 개별 반복 단계를 스케줄링 단위로 사용한다.

핵심 구성:
- 반복 단계와 비반복 경계 단계에 별도 우선순위 큐.
- 반복 종료 여부를 한 단계 앞서 결정하는 scheduling.
- CPU scheduling과 GPU 계산의 중첩.
- 가변 깊이 실행을 고려한 end-to-end inference.

평가 모델: Ouro 1.4B, Huginn 3.5B.

사용자 자료에 기재된 결과:
- 오프라인 처리량 최대 1.5~1.9배.
- 동적 서빙 부하의 정규화 지연시간 45~90% 감소.
- 가변 깊이의 이론적 최대 가속 중 최대 99% 실현.

가중치나 학습된 추론 능력을 직접 바꾸는 기법은 아니다. 정규화 지연시간·동적 부하 조건을 확인해야 하며 모든 단일 요청에서 같은 감소율이 나온다고 해석하지 않는다.

### 11.4. Towards Looped Models Done Right, Part I [C2]

제목: Towards Looped Models Done Right, Part I: Topology, Input Injection, Recurrent-State Design
저자: Benhao Huang, Chufan Shi, Junlin Chen, Shicheng Wen, Zhengzhong Liu, Eric Xing, Xuezhe Ma
공개일: 2026-10-16
arXiv: 2610.23036
논문: https://arxiv.org/abs/2610.23036
기존 전달문의 구현 참고: https://github.com/ifm-ai/xllm-loop

반복 블록 위치·네트워크 topology, input injection, recurrent hidden-state 구성·초기화를 분리 비교한다.

- Ouro형: 전체 모델 stack 반복.
- Huginn형: prelude + recurrent middle + coda의 sandwich 구조.
- 파라미터 규모·논리적 깊이·학습 토큰 예산을 통제한 비교 후 MoE에도 적용.

730M / 336B 학습 토큰:
- 전체 Huginn 구조가 평가한 10개 benchmark 모두에서 Ouro보다 높았다고 보고.
- sandwich topology는 문맥 추출·추론 집약 과제에서 효과.
- input injection은 지식 검색·문맥 활용에서 효과.
- 무작위 초기화와 별도 H/L recurrent state의 효과는 혼합적 또는 부정적.

MoE:
- 상주 파라미터 8B, 활성 파라미터 0.8B.
- 비반복 구조로 펼치면 상주 32B, 활성 3B.
- 학습 토큰 500B.
- Huginn형이 Ouro형보다 지식·추론·코딩 등 대부분의 benchmark에서 높았다고 보고.
- 112-layer feed-forward MoE와 학습·추론 FLOPs를 맞춘 비교에서 상주 파라미터 75% 감소.
- 해당 비교에서 DROP·GSM8K는 높고 MATH500은 동등한 수준.

기존 Huginn 체크포인트의 단순 decoding 변경이 아니라 구조 요소를 통제하여 모델을 학습한 연구다. 기존 [C2]와 동일 문헌이므로 중복 계산하지 않는다.

### 11.5. Towards Looped Models Done Right, Part II [C7]

제목: Towards Looped Models Done Right, Part II: Rethinking at Fixed Points
저자: Benhao Huang, Chufan Shi, Junlin Chen, Shicheng Wen, Zhengzhong Liu, Eric Xing, Xuezhe Ma
공개일: 2026-10-05
arXiv: 2610.06833
논문: https://arxiv.org/abs/2610.06833

반복 상태가 fixed point에 가까워지면 계산 경로의 차이가 작아질 수 있다는 특성을 이용하여 학습·decoding·prefill·RL에서 계산 결과를 재사용하는 연구다.

주요 구성:
- 예측 결과를 바탕으로 학습하는 depth prior.
- 입력 벡터와 직교하는 성분을 활용한 orthogonal input injection.
- 종료 반복 상태의 KV cache 재사용.
- 저장된 recurrent state를 활용한 RL 업데이트.
- recurrent state를 이용한 학생 증류와 prefill 최적화.

사용자 자료에 기재된 결과:
- 100M~1.6B 규모에서 평가.
- 학습한 depth prior와 orthogonal injection이 비교 설정보다 perplexity를 낮췄다고 보고.
- 1.6B에서 KV를 3배 줄인 조건이 고정 깊이·전체 cache 모델의 downstream 평균 성능과 동등.
- 증류 학생의 prefill 최대 1.79배 가속.
- 저장된 rollout state를 이용한 RL 업데이트는 기존 궤적 역전파보다 약 2배 빠름.
- 종료 상태의 KV 공유가 정확도를 거의 낮추지 않는 설정을 보고.

각 수치는 서로 다른 실험 구성의 결과다. 한 모델에서 모든 효과를 동시에 얻은 것으로 합치지 않는다. TinyLM에서는 정확한 cache 경로 이후 근사 cache 실험으로 검토한다.

### 11.6. Closing the Loop [C8]

제목: Closing the Loop: Practical Training Recipes for Looped Language Models
저자: Andrei Marchenko, Viacheslav Bezrukov, Oleg Kashurin, Inessa Fedorova, Dmitry Bocharov, Yuliana Shakhvalieva, Maria Tikhonova, Valerii Ternovskii
공개일: 2026-09-30
arXiv: 2610.00673
논문: https://arxiv.org/abs/2610.00673

처음부터 반복형 모델을 학습할 때 필요한 단계·토큰 예산을 줄이는 방법과, 사전학습 Dense 모델을 반복형 모델로 전환하는 학습 레시피를 연구한다.

주요 요소:
- 고품질 mid-training.
- 초기 learning-rate warmup.
- exit-gate 정규화 강화.
- 반복 입력 혼합을 위한 학습 가능한 단일 scalar.
- 모든 반복 단계에서 학습 신호를 유지하는 smoothed exit loss.

처음부터 학습:
- 1.4B LoopLM, 310B 학습 토큰.
- 같은 데이터·토큰 예산과 같은 파라미터 규모의 Dense 대조군.

| benchmark | LoopLM과 Dense 간 보고 차이 |
|---|---:|
| GSM8K | +14점 |
| MATH | 약 +10점 |
| DROP | +22점 |
| CRUXEval-I | +17점 |

- 12개 평가 benchmark 모두에서 LoopLM이 같은 파라미터 규모의 Dense보다 높았다고 보고.
- 기존 Ouro 레시피의 7.7T 토큰과 비교하여 약 25배 적은 310B 토큰.
- 사용자 자료는 동일 구조 기준의 계산량 비교에서 기존 Ouro 학습 레시피 계산량 약 3%라고 기술한다. 계산 정의는 원문에서 확인한다.
- 토큰 수 비율을 실제 wall-clock이나 모든 하드웨어에서의 FLOPs 비율로 동일시하지 않는다.

Dense→looped:
- Qwen3-1.7B-Base 기반.
- 학습 가능한 input-mixing scalar 하나, smoothed exit loss.
- 반복 단계별 별도 파라미터 없이 구현 가능.
- 같은 추가 학습 조건의 Dense 기준선보다 평가한 모든 benchmark에서 높았다고 보고.
- GSM8K, MATH, MMLU-Pro에서 통계적으로 뚜렷한 차이가 보고되었다고 요약되어 있다.

### 11.7. STARS [C9]

제목: Stabilizing Recurrent Dynamics for Test-Time Scalable Latent Reasoning in Looped Language Models
저자: Xiao-Wen Yang, Ziyu Han, Xi-Hua Zhang, Wen-Da Wei, Jie-Jing Shao, Lan-Zhe Guo, Yu-Feng Li
공개일: 2026-05-26
arXiv: 2605.26733
논문: https://arxiv.org/abs/2605.26733

반복 횟수를 늘릴수록 일정 수준 이후 성능이 하락하는 문제를 다룬다. STARS(Stability-driven Recurrent Scaling)는 잠재 상태가 안정적인 fixed point로 접근하도록 유도한다.

- Jacobian spectral radius regularization.
- Random loop sampling.
- 반복 상태 안정성과 추론 효과를 함께 고려한 학습.

평가: Ouro-1.4B 계열, 6개 과제 평균 정확도.

| 모델 | R=4 | R=8 |
|---|---:|---:|
| Ouro-1.4B-SFT | 70.46% | 52.97% |
| Ouro-1.4B-STARS | 74.18% | 65.55% |

- R=4에서 +3.72%p, R=8에서 +12.58%p.
- STARS도 제시된 표에서는 R=4보다 R=8 점수가 낮다. 반복 증가의 성능 하락을 완전히 없앴다고 읽지 않는다.
- Ouro의 결과이며 Huginn/TinyLM 직접 재현 결과와 구분한다.

### 11.8. TaH2 [C10]

제목: Improving Test-Time Scaling with Adaptive Looped Transformers
저자: Yichen You, Tianyu Fu, Aosong Feng, Xingtai Lv, Xuefei Ning, Ning Ding, Yu Wang
공개일: 2026-09-28
arXiv: 2609.35748
논문: https://arxiv.org/abs/2609.35748
공식 구현: https://github.com/thu-nics/TaH

토큰마다 추가 반복이 도움이 되는지 학습하도록 backbone과 iteration decider를 함께 미세조정한다. 한 번 더 반복하면 next-token 예측이 나아지는지를 나타내는 온라인 감독 신호를 사용한다.

구성:
- 토큰별 반복 깊이 결정기.
- 반복 사이 input injection을 위한 updater.
- Lookahead depth supervision.
- 반복 깊이별 예측과 종료 확률을 이용한 출력 구성.

기반 모델: Qwen3 1.7B, 4B, 8B.

1.7B의 AIME 2024~2026 평균:
- 정확도–연산량 곡선 기울기 1.79→2.74.
- 논문 정의의 기울기 개선 약 53%.
- 같은 추론 계산 예산에서 비반복 기준선 최고 정확도보다 약 +3.4점.
- 최대 반복 깊이 2회에서 +2.8점, 8회에서 +3.9점.

4B·8B에서는 평균 정확도 약 +3.2점·+2.4점. 수학 이외에 코드·QA·도구 사용 과제도 포함된다.

Qwen3 기반 반복 구조·종료 학습 연구이며 Huginn 체크포인트에 직접 적용한 성능 수치가 아니다.

### 11.9. LTO — Latent Thinking Optimization [C11]

제목: Latent Thinking Optimization: Your Latent Reasoning Language Model Secretly Encodes Reward Signals in its Latent Thoughts
저자: Hanwen Du, Yuxin Dong, Xia Ning
arXiv 최초 공개: 2025-09-30
발표: ICLR 2026
arXiv: 2509.26314
논문: https://arxiv.org/abs/2509.26314
학회: https://proceedings.iclr.cc/paper_files/paper/2026/hash/a4b1a25e1b37a17733c1fea50d0b7446-Abstract-Conference.html

Huginn-3.5B의 latent thinking trajectory에서 정답·오답을 구분할 수 있는 내부 신호를 조사한다. 잠재 궤적의 정답 가능성을 추정하는 classifier를 학습하고, 이를 LRM(Latent Reward Model)으로 사용해 더 유망한 궤적을 높은 확률로 선택한다.

핵심 구성:
- latent trajectory의 정답 가능성 classifier.
- classifier 기반 LRM.
- reward에 따른 확률적 latent sample 선택.
- 원래 latent policy와의 차이를 제어하는 KL 정규화.
- LRM 기반 weighted majority voting.

Huginn-3.5B의 사용자 제공 정확도 표:

| benchmark | 기본 모델 | LTO+LRM |
|---|---:|---:|
| GSM8K | 32.6% | 38.5% |
| GSM-Symbolic | 26.5% | 30.5% |
| SVAMP | 51.7% | 53.8% |
| CommonsenseQA | 50.0% | 51.7% |
| MBPP | 27.8% | 29.9% |

- 다섯 과제 모두 향상했고 표에 통계적 유의성 표시가 있다고 요약되어 있다.
- 일반 majority voting, confidence 기반 자기 수정, 자연어 평가 기반 자기 수정과도 비교.
- 일반 다수결의 효과는 제한적이었고 LRM 가중 다수결 및 LTO에서 더 높은 결과가 관찰되었다고 보고.
- OLMo-7B·Llama-2 계열 등의 일반 LM에서도 hidden representation으로 정답 가능성을 예측하는 classifier를 평가.
- 일반 LM의 classifier 실험과 Huginn에서의 전체 LTO 성능 실험은 구분한다.

### 11.11. 용어 요약

- Looped Language Model: 같은 신경망 블록을 반복 실행하여 유효 계산 깊이를 늘리는 언어 모델.
- Latent Reasoning: 자연어 중간 추론 대신 hidden state 등 연속 표현에서 추론하는 방식.
- Recurrent Depth: 반복 블록의 실행 횟수.
- Input Injection: 반복 단계 사이에 원래 입력 embedding 또는 정보를 다시 주입하는 방법.
- Exit Gate / Iteration Decider: 반복을 계속할지 종료할지 결정하는 구성 요소.
- Contrastive Decoding: 서로 다른 예측 분포나 표현을 대조하여 next-token 선택을 보정하는 방법.
- Activation Patching: 특정 위치의 activation을 교체하여 출력에 미치는 인과적 영향을 조사하는 방법.
- Latent Reward Model: 잠재 궤적의 정답 가능성·품질을 추정하는 보상 모델.
- Depth Prior: 학습 중 반복 깊이 사용을 규정하는 사전분포.
- Fixed Point: 반복에 따른 상태 변화가 작아지는 수렴 상태.
- Continuous Depth Batching: 반복 깊이가 다른 토큰을 개별 반복 단계 단위로 scheduling하는 방식.
- Test-Time Compute: 학습 이후 실제 추론에서 사용하는 추가 계산 예산.
- Forward FLOPs: 순방향 추론의 부동소수점 연산량.
- Perplexity: next-token 예측 분포의 평가 지표이며 benchmark 정답률과 구별한다.
