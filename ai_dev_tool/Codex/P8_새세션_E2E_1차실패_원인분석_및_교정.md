# P8 새 세션 E2E 1차 실패 원인분석 및 교정

> 관찰일: 2026-09-12  
> 범위: 사용자가 제공한 새 Codex 세션 P8 결과, 저장소측 훅 실행 경로, 상태 문서 정합성  
> 판정: **P8 1차 `FAIL/PARTIAL` / 저장소측 Windows handler 교정 완료 / 새 세션 재검증 대기**  
> 현재 증거 수준: **`STATIC_ONLY / E2E_NOT_RUN` 유지**

## 1. 사용자 관찰

| 항목 | 관찰 | 판정 |
|---|---|---|
| 프로젝트 훅 | `/hooks`에서 `.codex/hooks.json`, enabled/trusted, 변경 hash 검토 | 전제 PASS |
| `AGENTS.md` | 새 세션 자동 적용 | PASS |
| 저장소 스킬 | 17개 자동 발견, `session-handoff`·`wip-ledger` 포함 | PASS |
| 정상 probe | 루트에서 차단 없이 exit 0 | PASS |
| 차단 probe | 루트와 `scripts` workdir 모두 deny 없이 exit 0 | FAIL |
| fail-open 경고 | 없음 | 원인 식별 정보 없음 |
| probe 파일 | 생성 0건 | `$false` 안전장치 PASS, 훅 작동 증거는 아님 |

환경 지침과 스킬 발견은 실제 새 세션에서 확인됐다. 그러나 두 차단 probe가 모두 실행되어
`PreToolUse` 보호의 활성 증거는 확보되지 않았다.

## 2. 확정한 저장소측 원인

기존 `.codex/hooks.json`의 Windows handler는 다음 구조였다.

```text
powershell.exe ... -Command "<PowerShell 본문>"
```

Windows Codex는 훅 명령 전체를 `cmd.exe /C "<commandWindows>"` 형태로 감싸 실행한다.
따라서 handler 안의 `-Command "..."`가 바깥 따옴표와 충돌해 PowerShell 본문과 Python
guard가 실행되지 않을 수 있다. OpenAI Codex 공개 이슈
[#38168](https://github.com/openai/codex/issues/38168)에 같은 무동작과 `Completed` 오보고가
재현되어 있다.

현재 저장소에서도 같은 합성 이벤트로 다음을 재현했다.

진단 호스트에서 관측한 버전은 Codex Desktop `26.903.9818.0`, Codex CLI `0.153.4`다.

| 경로 | 결과 |
|---|---|
| `guard_backslash.py` 직접 호출 | 구조화된 `deny`, exit 0 |
| 기존 `commandWindows`를 outer-quote 없이 호출 | 구조화된 `deny`, exit 0 |
| 기존 `commandWindows`를 Codex식 outer-quote로 호출 | exit 1, guard 미도달 |

따라서 Python guard의 판정식이나 `Bash` matcher보다 먼저, Windows handler 실행 문자열이
끊긴 것이 저장소에서 재현된 1차 원인이다.

## 3. 교정 내용

- `commandWindows`를 embedded double quote가 없는 중첩 `cmd.exe /d /q /c` +
  PowerShell 진입점으로 바꿨다. 세션을 하위 폴더에서 시작해도 안정적이도록
  `git rev-parse --show-toplevel`의 결과에서 wrapper 경로를 조립한다.
  이는 명령 훅이 세션 cwd에서 실행되므로 저장소 훅은 Git 루트에서 해석하라는
  [공식 Hooks 지침](https://learn.chatgpt.com/ko-KR/docs/hooks)과도 맞춘 것이다.
- `.codex/hooks/guard_backslash_windows.ps1`을 추가해 UTF-8 stdin을 명시적으로 읽고
  독립 Python guard에 전달한다.
- wrapper 내부 오류는 조용히 통과시키지 않고 `systemMessage` 경고를 반환한다.
- 훅 테스트에 Windows handler 형태 검사와 UTF-8 stdin을 포함한 Codex식 outer-quote
  실제 프로세스 검사를 추가했다. 루트와 `scripts` cwd를 모두 검사하며,
  기존 14개에서 **16개**로 늘었다.
- P7 환경 검사기는 embedded double quote 재도입, Git 루트 해석·중첩 `cmd` 누락,
  wrapper 계약 누락을 실패로 잡도록 보강했다.

교정 뒤 로컬 검증 결과는 다음과 같다.

| 검사 | 결과 | 증거 한계 |
|---|---|---|
| 훅 테스트 | 16/16 PASS | Windows outer-quote 실제 프로세스를 루트·`scripts` cwd에서 각각 deny 확인 |
| Codex 환경 전용 P7 | 20/20 PASS | 설정·구문·링크·스킬·훅 계약의 정적 증거 |

두 검사는 Codex 런타임이 실제 `PreToolUse` 이벤트를 dispatch했다는 새 세션 증거가 아니다.

## 4. 남은 런타임 위험

저장소측 handler 결함을 제거했어도 새 세션 P8 재검증은 필요하다. Codex의 Code Mode
`exec` 경로가 `PreToolUse`를 발생시키지 않는 별도 공개 이슈
[#23411](https://github.com/openai/codex/issues/23411)가 있기 때문이다. 현재 공식 문서는
Code Mode의 중첩 도구 호출에도 훅 결정이 적용된다고 설명하지만, 런타임 버전에 따라 실제
dispatch가 다를 가능성을 저장소 파일만으로 배제할 수 없다.

재검증에서 수정된 handler의 deny가 관찰되면 저장소측 원인 교정이 확인된다. 다시 deny가
없다면 matcher를 추측해 넓히지 말고, 실제 사용한 도구 경로와 Codex 버전을 함께 기록해
런타임 dispatch 결함으로 분리한다.

## 5. P8 재검증 조건

1. Codex를 종료 후 재시작하고 `Z:\TinyLM` 프로젝트에 깨끗한 새 세션을 만든다.
2. `.codex/hooks.json` 변경으로 hash가 달라졌으므로 `/hooks`에서 내용을 다시 검토하고
   새 hash를 신뢰한다.
3. `Write-Output 'a\nb'`가 정상 통과하는지 본다.
4. 다음 안전 probe가 루트와 `scripts` workdir에서 모두 `PreToolUse deny`되는지 본다.

```powershell
if ($false) { Set-Content -LiteralPath '.codex/hook-probe.txt' -Value 'a\nb' }
```

5. 두 예상 경로의 probe 파일이 모두 없음을 확인한다.
6. 실제 deny 두 건까지 모두 관찰한 뒤에만 `ACTIVE_VERIFIED` 승격을 검토한다.

이번 교정 세션 자체는 새 세션 E2E가 아니므로 현재 상태를 승격하지 않는다.
