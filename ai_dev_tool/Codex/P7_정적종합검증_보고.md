## 1. 결론

Codex 전용 설정·스킬·장기기억·얇은 `AGENTS.md`·훅을 대상으로 한 20개 정적
종합검사를 모두 통과했다. P5 훅은 Codex 프로젝트 경로 안에 독립 구현했으며, 정상·차단·
경계·손상 입력·내부 오류 정책을 포함한 14개 모의 테스트를 통과했다.

이 P7 검증은 파일 구문·참조·계약과 모의 입력 증거다. 작성 시점에는 신뢰된 새 Codex
세션에서 실제 발견·라우팅·훅 호출을 관찰하는 P8을 수행하지 않았으므로
`ACTIVE_VERIFIED` 또는 “완전분리 구축 완료”로 승격하지 않았다. 후속 P8 1차 결과도
전체 통과가 아니므로 현재 승격하지 않는다.

## 5. 수행하지 않은 항목

P7 작성 시점에는 다음이 모두 `NOT_RUN`이었다.

- P7 작성 시점의 P8 새 Codex 세션 E2E
- GPU·학습·평가·모델 로딩·체크포인트 실행
- `run_smoke_check.bat`와 프로젝트 종합 스모크
- 보호 데이터 접근
- 실험 배치 실행
- 삭제·staging·commit·push·PR 및 외부 상태 변경

따라서 현재 최고 증거 수준은 `STATIC_ONLY / E2E_NOT_RUN`이다.

## 6. P8 사용자 재검증 방법

2026-09-12 1차 실패 뒤 `.codex/hooks.json`의 Windows handler hash가 변경됐다. 현재
세션을 재사용하지 말고 사용자가 변경 내용을 다시 신뢰한 깨끗한 새 Codex 작업에서 수행한다.

1. 저장소 루트에서 새 Codex 작업을 시작하고 프로젝트 신뢰 상태를 확인한다.
2. `/hooks`에서 프로젝트 훅 원천이 `<repo>/.codex/hooks.json`인지 확인한다.
3. 변경된 비관리 훅 hash가 표시되면 파일 내용을 검토한 뒤 그 정확한 hash를 신뢰한다.
4. 읽기 전용 질문으로 활성 지침·스킬·장기기억 원천을 보고하게 한다. 기대값은
   `AGENTS.md`, `.agents/**`, `.codex/**`, `ai_dev_tool/Codex/00~08`이며 다른
   에이전트 환경을 fallback으로 사용하지 않아야 한다.
5. `session-handoff`, `wip-ledger` 등 저장소 스킬이 발견되는지 확인한다.
6. 정상 통과 probe를 Codex에게 실행시킨다.

```powershell
Write-Output 'a\nb'
```

예상: 파일 쓰기 의도가 없으므로 훅 차단 없이 출력된다.

7. 안전한 차단 probe를 Codex에게 실행시킨다.

```powershell
if ($false) { Set-Content -LiteralPath '.codex/hook-probe.txt' -Value 'a\nb' }
```

예상: `PreToolUse` 단계에서 guard가 `deny`한다. 훅이 작동하지 않아도 `$false` 때문에
파일은 생성되지 않는다.

8. 작업 디렉터리를 저장소 하위 `scripts`로 지정해 7번 probe를 다시 요청한다.
   예상: Git 루트 동적 해석으로 동일하게 차단된다.
9. 훅 원천·정상 통과·루트 차단·하위 디렉터리 차단·스킬 발견·다른 환경 비참조를 모두
   실제 관찰했을 때만 `ACTIVE_VERIFIED` 승격을 검토한다. 하나라도 실패하면 현재
   `STATIC_ONLY / E2E_NOT_RUN` 판정을 유지하고 관찰 로그를 회신한다.

교정 뒤에도 두 차단 probe가 모두 실행되면 matcher를 추측해 넓히지 않는다. 실제 도구
경로와 Codex 버전을 기록하고, Code Mode `PreToolUse` dispatch 공개 이슈
[#23411](https://github.com/openai/codex/issues/23411)와 분리 대조한다.
