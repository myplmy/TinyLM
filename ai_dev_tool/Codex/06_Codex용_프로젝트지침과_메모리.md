## 1. 프로젝트 목적과 환경

TinyLM은 저사양 CPU·엣지·모바일 배포를 위한 초경량 LLM 아키텍처 연구 프로젝트다. 사전학습 모델을 단순 변환하는 작업이 아니라 PyTorch에서 from-scratch 학습하며, 연산 절감보다 **배포 상주 메모리 절감**을 우선한다.

| 항목 | 현재 지침 |
|---|---|
| 작업 루트 | 정본 `/home/uranus/tinyLM`; Windows 편의 링크 `Z:\TinyLM` |
| 사용자 하드웨어 | Windows, RTX 4070 Ti Super 16GB 단일 GPU |
| 배포 목표 | 상주 ≤16 MiB(엔트리), 32 MiB(메인스트림), 40 MiB(데스크톱 상한). 현 연구 의사결정은 주로 32·40 MiB |
| 속도 기준 | 단일 CPU·단일 코어 ≥15 tok/s. 속도는 현재 우선순위 ③이며 단독 종결 게이트가 아님 |
| 목표 우선순위 | ① 상주 메모리 ② 지능/품질 ③ 속도 |
| 코드 계보 | 코드 v6(`tinylm/`), 아키텍처 v5. 정확한 현재 구조는 코드와 최신 핸드오프가 정본 |

메모리 단위는 MiB다. 숫자를 인용할 때 저장(`packed`)과 상주(`runtime`), 모델/KV dtype/컨텍스트, 실측인지 식(⚙)인지를 함께 적는다.

## 2. Codex 작업 보호선

### 2.1 절대 금지와 승인 경계

- Codex는 학습·GPU 코드·모델 로딩 진단·실험 배치·`run_smoke_check.bat`·`run_smoke_check.sh`를 직접 실행하지 않는다. 실행 파일과 절차를 준비하고 사용자가 실행한다.
- 파일을 삭제하지 않고 삭제 권한도 요청하지 않는다. 삭제 후보는 핸드오프의 사용자 요청 표에 적는다.
- `run_cleanup_checkpoints.bat`와 `run_cleanup_checkpoints.sh`는 사용자 실행 전용이다. Codex는 검사·TSV 갱신과 후보 보고까지만 하고 이 진입점들을 실행하지 않는다.
- commit·push·PR·광범위 staging은 사용자의 명시 지시 없이는 하지 않는다. `git add .`와 `git add -A`는 사용하지 않는다.
- `datasets/TinyDataset/**`는 2026-09-11 현재 데이터셋 팀이 생성 작업 중이다. P0~P7과
  현재 P8 교정 작업에서 열람·열거·해시·검색·검사·수정·staging을 모두 하지 않는다.
- 사용자 또는 다른 작업자의 dirty/untracked 파일은 해당 작업자의 소유다. 변경 허용목록 밖 파일을 정리하거나 되돌리지 않는다.
- 비자명한 변경 전에는 `파일·경로 / 예정 동작 / 권한 근거 / NOT_RUN·제외`를 행별로 고정한다.
  검토는 읽기 전용이며, 이미 승인된 문서 작성만 지정 경로·행위 안에서 수행한다. 문서 검토·작성은 구현 승인이 아니다. `.agents/**`, `.codex/**`,
  작업흐름 생성기·검사기는 직접 지시 또는 승인된 구현 제안이 있어야 변경한다. 같은 권한의 패치
  묶음 뒤 `scripts/check_change_scope.py`로 실제 변경 경로를 대조하되, 보호 데이터 경로는 이
  검사기의 allowlist에도 넣지 않는다.
- 설치·다운로드·외부 획득, 장시간 계산, 보호 데이터 변경은 별도 승인을 받는다.
- 현재 사용자 지시에 별도 시간이 없으면 다음 실험 배치의 편성 목표는 **48시간**이다. 이는 중복·저가치
  실험으로 채우는 최소 할당량이 아니며, 유효한 후보가 부족하면 수치와 선결을 포함한 미달 사유를 남긴다.
  세션별 명시 목표는 공유 검사기의 `--hours-target` 인수로 전달하고 기본 표준을 다시 쓰지 않는다.

세부 규약과 증거는 Codex 00, 반복 사고는 01·04·08을 따른다.

### 2.2 정적 검사와 실제 실행을 분리한다

| 수준 | 의미 | 완료 표현 |
|---|---|---|
| 제안/계획 | 무엇을 할지 정함 | `PLANNED`, 구현 아님 |
| 정적 검사 | 구문·링크·정본·계약 확인 | `STATIC_ONLY`, 동작 증명 아님 |
| 모의 검증 | 합성 입력에서 도구 계약 확인 | 실제 프로젝트 E2E 아님 |
| 동적 스모크 | 실제 경로·모델 로딩 확인 | 사용자 실행 증거가 있어야 함 |
| 학습/벤치 | GPU·장시간 실제 실행 | 사용자 로그와 JSON이 있어야 함 |
| 배포 | 목표 환경에서 상주·속도·기능 확인 | 별도 배포 증거가 있어야 함 |

정적 통과를 학습·품질·훅 활성화 증거로 승격하지 않는다. 실행하지 않은 항목은 `NOT_RUN`으로 남긴다.

2026-09-21 이후 새 WIP의 종료 증거는 handoff 본문에 검사 출력을 누적하지 않는다.
`check_static_all.py --profile codex-safe`가 만든 세션별 `handoff/audit/*_STATIC_AUDIT.json`이
오류·조치경고·NOT_RUN과 exact WIP/session을 소유하고, 기록 단위는 handoff·WIP·audit 세 문서다.
handoff §2는 사용자에게 `관측/의미/사용자 영향/다음 행동`을 설명하고, 내부 hash·검사 전문은
audit와 상세 절에 둔다.

명시적인 소유 입력 검사에는 scripts/validation_scope.py의 manifest와 고정 SHA를
TL_VALIDATION_SCOPE/TL_VALIDATION_SCOPE_SHA256으로 함께 제공한다. 기본 USER_GLOBAL은
바꾸지 않으며 OWN_SCOPED는 파일 집합·제외·검사별 판독과 자식 영수증을 가진 별도 범위다.
목록 밖 검사는 NOT_RUN이고 범위 밖 판독을 잡아 무시해도 worker는 오류로 닫는다.
소유 모음은 TINYLM_SCOPED_STATIC_AUDIT_V1을 사용하므로 기존 전역 V1 종결 증거를 대신하지 못한다.
Python 자식은 명시 target을 전달·검증하며 native/shell·미등록 자식은 거부한다.
Python audit 경계는 OS sandbox가 아니므로 임의 네이티브 확장의 비접근까지 보증하지 않는다.
모델·학습 인수는 바꾸지 않고 scope를 모델 환경에 전파하지 않는다. CPU 범위 검증을
새 전체 smoke·전역 PASS로 승격하지 않으며, 승인된 새 실행창이 없으면 전체는 NOT_RUN이다.

### 2.3 Windows와 문서 편집

- 긴 문서와 백슬래시가 많은 본문은 셸 문자열 조립으로 쓰지 않고 전용 패치/편집 수단을 쓴다.
- PowerShell에서 UTF-8이 필요한 사용자 명령은 `$env:PYTHONIOENCODING='utf-8'`을 먼저 설정한다. `cmd.exe` 예시는 `set PYTHONIOENCODING=utf-8`을 쓴다.
- `.bat`은 ASCII·CRLF 규약을 따르며 전용 `run-batch` 절차를 사용한다.
- 경로 대소문자에 의존하지 않는다. Codex 네이티브 설정 폴더 표기는 `.codex`, 저장소 스킬은 `.agents/skills`다.

### 2.4 보조 에이전트의 역할과 권한

사용자가 지정한 역할과 해당 작업의 승인 범위가 먼저다. 총괄에게 주어진 주도 연구·CPU/GPU·Git 권한을
보조의 코드 편집이나 실행 권한으로 해석하지 않는다. 역할 이름, 같은 파일 접근 가능성, 도구 가용성은 권한 근거가 아니다.
역할 전환에는 사용자의 현재 명시 승인이 필요하며 이미 승인한 구체 범위를 다시 승인받도록 만들지는 않는다.
R58의 원칙을 아래 위임 명세로 구체화하고, 현재 모델·추론강도·개수·마감은 WIP의 사용자 지시에서 확인한다.

| 역할 | 기본 허용 | 기본 금지 |
|---|---|---|
| 문헌·아이디어 | 승인된 자료 읽기·웹 검색·근거와 가설·한계 보고 | 코드·테스트·런처·설정 편집, 모델·실험 실행 |
| 정 검토 | 읽기 전용 타당성·설계·코드 검토와 근거 보고 | 검토 대상 구현, 검사·문턱 변경, 모델·실험 실행 |
| 반 검토 | 읽기 전용 반례·실패경로·증거 충분성 검토 | 검토 대상 구현, 오류의 임의 수리, 모델·실험 실행 |
| 원문 작업 | 사용자가 허용한 텍스트의 판독·정제·번역·문장 재구성 | 분석·전처리·테스트 코드의 편집·실행, 범위 밖 원문 접근, 전문용어의 임의 동의어 치환 |
| 실행 전용 보조 | 별도 명시 허가된 런처 한 개 실행, 같은 실행 대기, 종료·중단 보고 | 코드·인자·조건 변경, 새 실험 선택, 자동 재시도·추가 실행, 설치·Git·삭제 |
| 총괄 | 승인된 구현·검증·실행·판단·기록과 권한 관리 | 보조의 허용 범위를 임의 확대하거나 보조 의견만으로 검증·채택 완료 선언 |

문헌·정·반은 기본 읽기 전용이다. 사용자 범위 안에서 검토 보고서 작성을 별도로 위임할 때에는 정확한
문서 경로와 허용 동작을 적는다. 문서 작성 허가를 코드 편집 허가로 확대하지 않는다. 원문 작업도
텍스트 허용 경로만 지정하고 원문·파생본을 분리한다. Luna 등 특정 모델의 이름만으로 경로 권한을 만들지 않는다.
원문 작업의 일반 텍스트 읽기·승인된 텍스트 저장과 분석/전처리 스크립트 실행은 다르다. 기존 코드라도
실행은 별도 명시 범위가 있어야 하며 총괄의 실행 권한을 가져다 쓰지 않는다.

위임 전에 현재 WIP 또는 연결된 명세에 다음을 남긴다.

1. 사용자 지시 근거와 역할, 사용할 모델·추론강도, 동시 사용 한도.
2. 읽기 대상과 보호/제외 경로, 허용 쓰기 경로와 행위. 읽기 전용이면 코드 쓰기0을 명시한다.
3. 명시 실행이 허용됐는지, 허용 시 정확한 런처·인자·소스·선결·시간/자원 한도와 소유 출력.
4. 반환할 근거와 실제 수행/미수행, 오류·중단의 보고 방식, 자동 재실행 금지.
5. 총괄과 보조의 파일 소유 구분 및 현재 실행 중 동결할 소스·프로필·평가 조건.

| 결정 상황 | 배정 | 필요한 회신 |
|---|---|---|
| 기존 JSON·결과나 한 함수에서 판정 가능 | 총괄이 증거 재사용 | 기존 근거와 이번 조건이 만나는 위치 |
| 하나의 모호함이 구현이나 실행을 바꿀 수 있음 | 해당 역할 한 명 | 근거 위치, 바뀔 판정, 가장 작은 확인 |
| 적용 조건과 실패 경로가 각각 설계를 바꿈 | 정·반을 독립 병행 | 정은 적용 조건과 예측, 반은 구체 반례와 차단 조건 |
| 기존 기록으로 외부 기법의 전제나 적용 한계를 확인할 수 없음 | 문헌·탐색 한 명 | 1차 출처의 정확한 위치와 TinyLM에 적용할 조건 |

요청에는 결정 한 건, 이미 확인한 값, 정확한 읽기 구간, 결정이 필요한 시점, 총괄이 즉시 착수할 독립 작업을
넣는다. 앞선 회신으로 해결된 쟁점은 근거를 재사용한다. 열린 쟁점은 같은 역할의 기존 보조에게 먼저 묻는다.
입력 봉인에 필요한 회신의 마지막 시점을 정하고, 봉인 이후에 받은 의견은 결과 해석과 후속 실험에 쓴다.
보조는 결정을 바꾸는 근거를 확인하는 즉시 알린다. 총괄은 반례를 재현하거나 독립 근거를 확인한 뒤 배정·첫
유효 회신 시각, 바뀐 판단이나 검증 항목, 적용한 산출물 위치를 같은 원장 항목에 남긴다. 배정 효과는
수정된 비교 조건, 회피한 재실행, 실제 대기처럼 관찰할 수 있는 변화로 판단한다.

한 쟁점의 배정은 한 명으로 시작하고, 독립 근거가 필요한 경우에 정과 반을 함께 쓴다.
이번 결정이 바뀌는 조건을 한 문장으로 주고, 회신은 판정·근거 위치·필요한 조치부터 받는다.
총괄은 독립 작업을 수행하는 동안 보조에게 맡긴 전체 검토를 중복하지 않는다.
봉인이나 결과 판정을 막는 구체적인 조건만 결정 시점까지 기다린다. 새 근거가 없거나 늦은 회신은
판정에 영향이 없었던 이유나 후속 검토 항목을 간단히 남긴다.

보조가 범위 밖 변경을 시작하면 해당 작업을 중단하고 실제 변경 경로와 검사·실행 여부를 회수한다.
기존 변경을 숨기거나 임의 삭제·복원하지 않는다. 미검증 패치는 미검증으로 보존하고 총괄이 diff와
실제 검증을 직접 확인한다. 이후 총괄이 검토했다고 최초 권한 위반이 없어지는 것은 아니다.
공유 worktree의 diff만으로 작성 주체를 단정하지 않고 도구 기록·위임·보조 보고를 함께 대조한다.
이 명세는 운영 규칙이며 플랫폼의 파일시스템 격리가 구현·검증됐다는 뜻은 아니다.

### 2.5 비동기 GPU 실행과 독립 작업 병행

별도 CPU/GPU 실행 승인이 있을 때만 사용한다. 기본 금지나 마감·보호·단일 GPU 경계를 넓히지 않는다.
계획·preflight가 닫힌 정확한 런처를 실행하고 실제 프로세스 ID/세션·출력·STOP·소스 핀·마감을 WIP에 남긴다.

| 방식 | 적합한 상황 | 비용·제약 |
|---|---|---|
| A. 총괄의 비동기 실행 | 실행 도구가 세션 ID를 반환하고 상태·종료를 회수할 수 있음 | 총괄이 실행을 소유한 채 독립 CPU 작업을 병행한다. 장시간에는 지정 감시가 종료 증거를 전달한다 |
| B. 실행 전용 보조 한 개 | 사용자에게 별도 허가됐고 총괄의 실행 감시를 나누는 이득이 있음 | 허용 한도 안의 한 자리를 사용하며 런처 한 개의 실행·보고만 맡긴다 |
| C. 짧은 동기 대기 | 소스 의존·복구·종결 등 때문에 다른 작업을 안전하게 병행할 수 없음 | 독립 작업이 없음을 기록하고 필요한 구간만 대기한다 |

실행 중 해당 소스·프로필·토크나이저·학습자료·평가 조건은 동결한다. 문서·검토·독립 CPU 검사는
다른 소유 경로에서 병행할 수 있지만 파일/메모리/CPU 자원 충돌을 확인한다. 속도 비교에서는 병행 CPU 작업과
실행 순서·컴파일 캐시가 같았는지 기록하고 전체 wall 차이를 알고리즘 단독 효과로 단정하지 않는다.
단일 GPU의 모델 실험은 기본 직렬이며 VRAM 여유만으로 동시 상주를 승인하거나 안전하다고 선언하지 않는다.

이 작업용 WSL에서 논리 CPU가 0–15로 보이면 15번은 연구 작업에 배정하지 않는다. 학습·평가·감시와
병행 CPU 작업은 `taskset -c 0-14` 범위로 실행한다. 진행 중에 적용할 때는 이번에 소유한 프로세스의
각 스레드와 다음 자식의 상속을 확인한다. 제한 변경 시점은 결과에 적는다.

진행 조회는 필요한 요약만 읽고 표준출력 생략이 원로그 유실이 되지 않도록 한다. 제한된 대기 중에도
사용자 진행 보고를 유지하며, 실패·HOLD·비정상 정리 때 자동 재시도하지 않는다. 총괄이 원인을 판단한다.
보조가 실행하면 정확한 명령·실행 ID·시작/종료·실제 코드·정리 상태와 로그 경로만 반환하고 직접 수리하지 않는다.

GPU 전환은 고유 STOP으로 현재 증분/체크포인트와 소유 정리를 닫은 뒤 수행한다. 임의 PID·다른 작업을
종료하지 않는다. 실행 전환·중단·대기 판단과 실제 종료를 구분하며 원형과 실패 증거를 보존한다.
승인 마감 전에 모든 소유 실행의 종료와 정리를 회수한다. 마감 뒤 새 실험·재개는 새 승인 전 금지다.
원장·결과·핸드오프·명령 보존·완료 런처 정리·로컬 커밋도 승인된 범위에서 함께 마친다.

GPU 감시는 사용자가 지정한 읽기 전용 보조 한 명을 재사용한다. 1분 이내로 예상하는 작업은 총괄이
회수하며 이후 배정에는 같은 조건의 실제 시간을 쓴다. 긴 작업은 고유 태그, 실행 소유 정보, 정확한 종료
JSON·오류 로그 경로, 마감을 전달한다. 감시는 기한을 둔 좁은 조회로 정상 종료·오류·중단을 발견하면
시각, 종료 코드·정지 사유, 종료 후 가용 VRAM·계산 PID를 한 번에 알린다. 정상 진행 중에는 회신 없이
관찰한다. 종료 근거가 비었거나 상충하면 확인한 로그와 미확인 항목을 알리고 총괄이 실제 세션을 대조한다.

총괄은 GPU 실행 중 원장의 다음 후보를 확인하고 선결, 검증된 실행 명령, 고유 출력, 소요 시간과 마감을
준비한다. 선결을 충족하고 결과가 서로 독립인 후보는 순차 큐에 둔다. 큐는 앞 실행의 성공·소유 자식
종료·종료 이후 장치 반환을 확인해야 다음 실행을 시작한다. 오류·반환 미확인·마감은 정지로 남긴다.
정제 인계나 직전 판정에 달린 후보는 빠진 선결을 기록하고 독립 CPU 작업을 잇는다.

교대 분석에는 실측 가능한 종료·반환, 최초 감시 확인, 다음 후보 준비 완료와 실제 시작 시각을 쓴다.
감시 확인까지의 짧은 지연과 다음 실행 준비 시간을 따로 본다. 둘 이상 준비되어 큐에 둔 경우에는 종료
증거가 자동으로 교대를 열고 감시 회신이 그 시작 조건을 대신하지 않는다.
앞 실행이 시작된 뒤에 준비된 후보도 종료 기록의 소유 PID, 종료 코드, 결과 보고서,
종료 후 장치 표본과 CUDA 잠금 해제를 확인하는 방식으로 예약할 수 있다. P109의 이 확인은
[`wait_p109_cuda_return.py`](../../scripts/wait_p109_cuda_return.py)가 수행한다. 뒤 실행은
기존 감독기의 현재 장치·잠금 검사를 거친다. 총괄은 준비 완료·장치 반환·실제 시작 시간을 회수하고,
감시는 원래 실행의 오류나 반환을 알린다.
기록을 재구성할 수 있으면 반환부터 다음 시작까지의 시간을 후보의 준비 대기와 시작 대기로 나눈다.
실행할 후보가 남아 있어도 결과·자료·권한이 선결이면 해당 항목과 근거를 남긴다. 종료 회신을 받은 직후
총괄이 이미 봉인된 후보를 시작하거나 큐의 실제 시작을 확인한다. 감시 보조의 업무는 그 실행의 상태 증거까지다.

### 3.3 다음 실행 큐

실제 실행 순서·현재 배치명·예상 시간은 최신 공유 핸드오프 §6b·§7이 정본이다. 이름과 시간이 변하므로 이 문서에 복제하지 않는다.

- 동적 스모크가 장시간 큐보다 먼저다.

## 7. 이 문서의 갱신 조건

다음 중 하나가 발생한 세션이 이 문서를 갱신한다.

1. 사용자 확정 표준조건·배포 목표·우선순위가 바뀜.
2. 프로젝트의 대표 후보 또는 연구축 상태가 크게 바뀜.
3. 반복 도구 사고가 새 보호선·라우팅 변경을 요구함.
4. Codex 환경 단계(P0~P8)의 상태가 바뀜.
5. 시작 순서·정본 위치·공유/금지 경로가 바뀜.

다음 변화만으로는 갱신하지 않는다.

- 개별 실험 수치 한 줄 추가.
- 게이트 개수만 변함.
- 스크립트 하나가 생김.
- 큐 id나 배치 순서가 바뀜.

그 정보는 각 정본이 소유한다. 이 문서는 링크와 현재 의사결정에 영향을 주는 요약만 고친다.

## 2026-10-19 실물 결과와 격리 등록 경로

관계·대상·표현/위치의 실제 학습과 내용 진단은 결과101 §273~323, 정답 이력과 자기 이력의 차이는 결과104 §10~12가 소유한다. 제한된 Boolean/JSON·종료 개선을 일반 한국어 대화나 Falcon 동등성으로 승격하지 않는다. 남은 런처는 동적으로 고른 최신 인계의 선결·기원을 확인하며, 보존 백로그를 자동 사용자 실행 요청으로 해석하지 않는다.
