# 02 — 핸드오프 메모 규약 (장기기억)

> **최신 갱신일자**: 2026-09-23 · **문서 유형**: live

> **Codex 전용 이식본.** 환경 경계는 [`README.md`](README.md)다. 활성 규범은 `AGENTS.md`,
> 장기기억은 `ai_dev_tool/Codex/`, 단기기억은 공유 `handoff/`다. 아래의 `.claude` 표기는
> 범용 양식과 충돌했던 과거 사례를 설명하는 역사 기록이며 직접 사용하지 않는다.

> **목적**: 세션이 끊겨도 **작업 기록이 유실되지 않게** 한다.
> 새 세션이 `handoff/` 의 최신 메모 **하나만 읽고** 이어받을 수 있어야 한다.

## 1. 언제 쓰나

| 시점 | 무엇 |
|---|---|
| **동일 작업을 이어서 수행할 때** | CONTINUE: 기존 핸드오프는 읽고 열린 WIP만 갱신. 새 핸드오프는 만들지 않음 |
| **이전 상태 확인만 할 때** | RECOVERY_READ: 인계·WIP를 읽고 보고. 새 파일 없음 |
| **현재 요청에서 종료·중단·다음 세션 이전 또는 새 핸드오프 작성을 명시할 때** | FINAL_HANDOFF: 작업 종료 시 새 핸드오프 한 건과 다음 세션 시작 프롬프트 작성 |

이어/계속은 새 핸드오프 작성 승인이 아니다. 컨텍스트 압축이나 지시 한 항목 완료만으로
FINAL_HANDOFF를 추정하지 않는다. 진행 중 복구 상태는 WIP의 한 줄 상태·append-only
작업 로그가 소유한다. 이 A안은 AI 트리거 규칙이며 생성기의 동일-WIP 재호출 차단을
구현했다는 뜻은 아니다. 같은 오류가 재발하면 제안서의 B안을 다시 판단한다.

## 2. 파일 규약

- 경로: `handoff/{YYYYMMDDHHMM}_HANDOFF.md`
- 첫 줄: `# HANDOFF {날짜 시각} — {이 세션이 남긴 것 한 줄}`
- 둘째 줄: 이전 핸드오프 링크
- **요약하지 않는다.** 신규 세션이 이것만 읽고 이어받을 수 있게 쓴다.
- `AGENTS.md`에 특정 핸드오프 파일명을 하드코딩하지 않는다. 최신 유효 파일은 이름·체인·생성 증거로
  동적으로 고르고, 현재 상태 요약이 바뀌면 Codex 06의 링크·요약만 함께 갱신한다.

## 3. ★고정 섹션 (이 순서로)

```markdown
# HANDOFF {시각} — {한 줄}

이전: [{이전파일}]({이전파일}).
**코드가 정본**(`tinylm/`). 영구 규범은 `AGENTS.md`. 장기기억은 `ai_dev_tool/Codex/`.
**★AI 는 학습/GPU 코드를 직접 실행하지 않는다** — 배치·스크립트만 만들고 **실행은 사용자**.

> **이 문서는 요약하지 않는다.**

## 0. 사용자 지시사항과 그 목적

| # | 사용자가 지시한 것 | **AI 가 판단한 목적** | **그래서 필요했던 작업** | **실제로 한 것** | 결과 |
|---|---|---|---|---|---|

★"지시한 것" 과 "목적" 을 따로 적는다. 목적을 잘못 읽으면 지시를 다 지켜도 헛일이 된다.
★"필요했던 작업" 과 "실제로 한 것" 이 다르면 **그 차이를 반드시 남긴다** — 다음 세션이
  그 자리에서 이어야 할 지점이다.
★★상위 번호에 A·B 같은 하위 항목이 있더라도 **상위 지시를 제목으로 간주해 생략하지 않는다.**
WIP와 §0에는 상위 번호와 각 하위 번호를 모두 독립 행으로 보존한다. 하위 답변이 공통 보고·기록
요구까지 자동 충족한다고 추측하지 않는다(2026-09-14 A34).

## 1. ★가장 중요한 것 세 가지 (먼저 읽을 것)

## 2. ~ N. 항목별 상세 (근거·수치·판정)

## N+1. 사용자에게 부탁하는 것
(실행할 배치 / 확인할 판단 / git 명령 — **AI 가 못 하는 것만**)

## N+2. 다음에 하면 좋을 것 (권장 순서)
| 순 | 실험 | 배치 | GPU | 예상 시간 | 권장 근거 |

## N+3. 커밋 메시지 제안 (한국어 제목 + 본문)

## N+4. 신규 세션 시작 프롬프트 (제안)

## N+5. 참조 치트시트
```

## 4. ★반드시 들어가야 하는 것

- [ ] **사용자 지시사항 원문**과 **AI 가 이해한 목적**을 **분리**해서
- [ ] **하려던 것 vs 실제로 한 것**의 차이(있으면)
- [ ] **판정이 뒤집힌 것**과 그 이유 — 조용히 덮어쓰지 않는다
- [ ] **아직 답이 없는 질문**(가장 자주 유실되는 항목)
- [ ] **사용자 대기 항목**(실행·승인·git) — AI 가 못 하는 것만
- [ ] **다음 권장 실험**: 실험번호 · 단계 · **배치 파일명** · **예상 시간** · **권장 근거**
- [ ] **커밋 메시지**(한국어 제목 + 본문)
- [ ] **신규 세션 시작 프롬프트**

## 5. 쓰지 말아야 하는 것

- **"~할 예정"** 만 적고 실제 상태를 안 적는 것. 상태는 ✅/⏸/🚫 로 명시한다
- **결론만 적고 근거 수치를 뺀 것.** 다음 세션이 재검증할 수 없다
- **"조치 완료" 를 파일 diff 없이 적는 것**(결과 014 초판 사고)
- 이전 핸드오프의 **요약본**. 링크를 걸고 **새 내용만** 쓴다

## 6. 3층 기억 구조 (이 저장소의 규약)

| 층 | 위치 | 무엇 | 수명 |
|---|---|---|---|
| **영구 규범** | `AGENTS.md` | **매 프롬프트 반드시 확인해야 하는 것만.** 컴팩트 유지 | 프로젝트 전체 |
| **장기기억** | `ai_dev_tool/Codex/00~08` | 함정 원장 · 규약 · 절차. **펼쳐 볼 때 읽는다** | 프로젝트 전체 |
| **단기기억** | `handoff/*.md` | 세션 컨텍스트. 다음 세션이 이어받는 유일한 통로 | 세션 |

> **판단 기준**: "이걸 몰라서 **매 프롬프트** 사고가 나는가?" → `AGENTS.md`.
> "필요할 때 찾아보면 되는가?" → `ai_dev_tool/Codex/`.
> "이번 세션에서만 유효한가?" → `handoff/`.

## ★7. 2026-08-13 개정 (사용자 지적) — **빠지면 안 되는 두 절**

> *"어느순간 세션 핸드오프 메모에 사용자가 해줘야 할 것이 없어진 것 같은데 ...
>  AI가 요청할 사항이 없으면 '요청할 것이 없다'고라도 작성필요.
>  덧붙여 -done으로 완료된 실험 배치파일 중 삭제가능한 것도 항시 보고하도록"*

**진단**: §3 고정 섹션에 *"N+1. 사용자에게 부탁하는 것"* 이 이미 있는데,
**요청이 없는 세션에서 그 절을 통째로 빼 버렸다.** 그러면 다음 세션이
*"요청이 없었나, 아니면 쓰다 잊었나"* 를 구분할 수 없다. **빈 절도 정보다.**

### 규칙 (핸드오프 작성 시 **무조건**)

| # | 규칙 |
|---|---|
| **A** | **"사용자에게 부탁하는 것" 절은 언제나 쓴다.** 요청이 없으면 **"이번에는 요청할 것이 없다"** 라고 **명시**한다. 절을 지우지 않는다 |
| **B** | 그 절에 **`-done` 배치 삭제 판정을 항상 포함**한다. 삭제 가능한 것이 없으면 **"삭제 가능한 `-done` 배치 없음"** 이라고 적는다 |
| **C** | 삭제 판정은 3조건으로 한다 — ① 실험 완료 ② **재현 명령이 결과문서에 보존** ③ 재실행 예정 없음. **②를 문자열로 대조**한 뒤에 적는다(011 §0.5-7 전례) |
| **D** | 체크포인트·로그·캐시가 **10 GB 이상 쌓였으면** 정리 목록도 이 절에 넣는다 |

⚠️ **왜 규칙 A 가 필요한가**: 이 저장소의 사고 다수가 *"안 적혀 있어서 안 한 것인지,
안 해도 되는 것인지 몰랐다"* 에서 나왔다(함정 13 "조치 완료 표기", 결과 031 "조용한 무동작").
**빈 절을 명시하는 것은 그 계열의 예방이다.**

```markdown

## 2. ~ K. 지시별 상세 (근거·수치·판정)
```

## 8.6 ★★**파일명의 시각** — 지어내지 않는다 (2026-09-06 신설, 사용자 지시)

### 무엇이 있었나

2026-08-31 에 **파일명의 날짜가 순번**이라 48건을 개명했다. 그때 게이트
**파일명 날짜 == 본문 첫 줄 날짜**를 넣었다. ★**시각(HHMM)은 그대로 남았다.**

2026-09-06 전수 재감사(70건):

| 검사 | 결과 |
|---|---:|
| 파일명 시각 == 본문 시각 (**기존 게이트**) | ✅**70/70 일치 · 불일치 0** |
| 파일명 시각 ≤ **최초 git 커밋 시각** | 🚫★**13건 불가능** · 최대 **+18.6시간** |
| 분이 `:00`·`:30` | **15건** (우연 기대 2.3, **z +8.43**) |
| ★그 15건 중 §위 "불가능" 목록에 있는 것 | ★**12건 (80%)** |

> 🚫★★**2026-09-07 사용자 지시 3 — 이 통계 규칙은 판정에 쓰지 않는다.**
> *"00, 30이라고 지어낸것으로 판정하지 말고 (…) **코드로 실측가능한 사항**으로 확인하고,
>  통계 예측으로 00분 30분과 같은 기준 사용하지 말 것."*
>
> ✅**그 조건이 더 좋다.** `:00` 규칙은 두 방향으로 나쁘다 —
> 🚫**미탐**: 실제 13건 중 `…2359`(:59)를 놓친다. 다음번엔 `:07` 로 지어내면 그만이다.
> 🚫**오탐**: 진짜로 `:00` 에 쓸 수 있는데 그것을 반증할 방법이 규칙 안에 없다.
>
> ★**대신 쓰는 규칙(정본 `scripts/handoff_time.py`)**:
> **파일명 시각 > 최초 존재 증거 + 10분 → 에러.** 증거는 ①그 파일을 담은 **최초 git 커밋**,
> 없으면 ②**파일 `mtime`**. **한쪽만 본다** — 나중에 고쳐 `mtime` 이 뒤로 가는 것은 정상이고,
> **미래를 주장하는 것만** 잡는다. 🚫추측이 아니라 **모순**이다.
> ✅**검출 확인**: 실제 사고 13건 중 넷을 스크래치패드에 재구성해 **6/6**(오탐 케이스 셋 포함).
> ★★**그리고 커밋 전에도 돈다** — 갓 만든 파일의 `mtime` 이 곧 *지금* 이므로
> AI 가 23:30 이라고 지어내고 실제가 14:00 이면 **그 자리에서 잡힌다**(제안서 §8 위험 2 해소).

★**분 분포는 여전히 사실이지만 판정이 아니라 *정황*이다** — 위 표는 **원인 진단의 근거**로만 남긴다.

### ★★왜 게이트가 못 잡았나 — **같은 추측의 사본 둘을 비교했다**

파일명과 본문 첫 줄은 **같은 순간, 같은 추측**으로 쓰인다. 지어낸 값이면 **둘 다 같은 값**이라
**영원히 통과한다.** 실측이 그것이다 — **일치 100%, 불가능 13건.**

> ★★**함정 43 — 자기 사본과 대조하는 게이트는 게이트가 아니다.**
> 검증에는 **바깥의 증거**가 필요하다(여기서는 **git 커밋 시각**).
> ★**일치율 100% 는 통과가 아니라 경보다.**

### ★원인 — AI 에게 **시계가 없었다**

세션 프롬프트에 **`Today's date is YYYY-MM-DD`** 만 있고 **시각이 없다.**
규약은 HHMM 을 요구한다 → AI 는 **도구를 부르거나 지어내야** 하는데
🚫**부르라고 적힌 곳이 없었다.** ✅**`date` 는 실제로 된다**(2026-09-06 실측).

## §9. ★**권장순서 표에 `선결` 열은 필수다** (2026-08-20 신설, 의사결정함정 D15)

### §9.2 ★★2026-09-08(2차) 개정 (사용자 지시 2F) — **부탁 표의 한 행은 한 가지 일이다**

사용자가 물었다: *"6b 항목 표의 4번에 ⏸5차 리뷰 ⏸는 무슨 의미인지?"*

그 행은 이렇게 쓰여 있었다:

```
| ★4 | ★제안서 판단 셋 — [옵티마이저 P005b] · [길잡이 파일] · ⏸ 5차 리뷰(실험 여섯이 끝난 뒤 최종 승인) |
```

★**⏸ 는 `docs/용어설명.md` 대로 "보류"** 이고, 여기서는 *"이 건은 **지금** 판단을 요청하지
않는다 — 선결이 끝난 뒤"* 라는 뜻이었다. 🚫**그런데 같은 행의 제목이 "판단 **셋**" 이다.**
**셋을 판단해 달라고 적어 놓고 그중 하나에 "판단하지 마세요" 표를 붙인 것**이라
사용자가 무엇을 해야 하는지 행 하나만 봐서는 알 수 없다.

> ★★**규칙**: **`K+1 사용자에게 부탁하는 것` 표의 한 행 = 사용자가 할 일 하나.**
> - **지금 해야 하는 것**과 **선결 때문에 지금은 안 하는 것**을 **한 행에 섞지 않는다.**
> - 후자는 **별도 행**으로 내리고 **⏸ + 선결을 숫자로**(D1) 적는다.
> - 개수를 쓰려면(*"판단 셋"*) 그 행에 **정말 그 개수만큼의 즉시 행동**이 있어야 한다.
>
> ⚠️**기계로 못 잡는다** — `check_handoff` 는 ⏸ 옆 선결은 보지만 *"이 행이 몇 가지 일인가"* 는
> 셀 수 없다. **사람이 지키는 규칙**이고, 그래서 여기 적는다.

## §10. ★★**WIP 작업원장 v2** (2026-08-28 신설, 2026-09-13 C안 승인)

그 시점에 남아 있던 구조화 기록이 **없었다** — 이어받는 쪽이 로그를 처음부터 다시 읽어야 했다.

> ★**규칙**: 지시가 **3건 이상**이거나 로그 판독·결과문서 반영이 포함되거나
> 코드 수정이 **2파일 이상**이면, **작업 착수 전에** `scripts/wip.py --new`로
> `handoff/WIP_{YYYYMMDD}[a-z]_작업원장.md`를 만든다. **작업 중에** 같은 도구로 갱신하고,
> 모두 끝나면 `scripts/wip.py --close`로 **`-done`** 개명한다(🚫삭제하지 않는다).

별도 지시가 없으면 **사용자의 한 번의 작업지시 묶음당 WIP도 하나**다. 한 메시지 안의 번호별
지시, 그 작업을 검증하며 발견한 결함, 같은 묶음에 대한 사용자의 후속 추가지시는 새 원장으로
쪼개지 않고 열린 원장에 `--add`한다. 최종 자체감사와 핸드오프 초안 대조가 끝나기 전에 원장을
닫지 않는다. 별도 원장은 사용자가 독립 작업으로 명시했거나 §10.1의 동시 WIP 승인을 받은 경우만
허용한다.

| 시점 | 무엇 |
|---|---|
| 착수 **전** | 6열 v2 지시 표(정본) + 허용목록·NOT_RUN·사용자 소유 실행·철회 주장 |
| 항목 착수·대기·막힘·완료마다 | 상태·최신 한 줄·산출물·이어받을 지점을 스크립트로 갱신 |
| ★**수치를 뽑은 즉시** | **`## 확보한 수치` 절에 표로** — 중단은 대개 **판독 다음, 집필 전**에 온다 |
| 완료 | 캡슐 해시가 최신이고 열린 항목 0건일 때 `scripts/wip.py --close --file ...` |

고정 헤더는 다음과 같다.

```text
# | 사용자 지시 | 상태 | 작업 내용 | 산출물 | 이어받을 지점
```

- `작업 내용`은 최신 한 줄만 두고 전체 전이는 `## 3. 작업 로그 (append-only)`에 남긴다.
- `이어받을 지점`은 열린 행의 다음 한 행동이며 완료 행은 `—`다.
- 모든 표 셀에 `<br>`과 실제 개행을 금지한다.
- v2 원장은 `## 4. 오버라이드 수정 이력 (append-only)`와 상황판 SHA-256을 가진
  `## 5. Compact 상태 캡슐 (v1)`을 유지한다.
- 레거시 원장은 조회만 허용한다. 완료 원장은 변환하지 않고, 열린 레거시 변환은 사용자 승인
  참조를 둔 `--migrate-v2`만 허용한다.

★★**정상 쓰기 경로는 `scripts/wip.py` 하나다.** 모든 변경 명령에 선택한 `--file`을 명시한다.
수동 `apply_patch`, 셸 리다이렉션, `Set-Content`로 WIP를 바꾸지 않는다. 정상 상태 명령으로
표현할 수 없는 단일 셀 교정만 `--override`의 정확한 before/after·근거·승인 참조를 요구하고,
도구가 시각·SHA-256·축약 CLI 계약을 같은 파일에 기록한다. `상태`는 오버라이드할 수 없고,
사용자 지시는 별도 `--allow-directive-correction`과 구체 승인이 필요하다.

같은 디렉터리 임시파일, 원본 바이트 비교, lock, 원자 교체를 한 트랜잭션으로 사용한다. Windows
CP949 콘솔에서도 저장 뒤 성공 메시지가 예외를 내지 않도록 스트림을 UTF-8로 재설정한다.
PreToolUse의 직접 수정 차단은 보조선이며 mock PASS나 fail-open 경고를 실제 새 세션 E2E PASS로
쓰지 않는다.

절차와 명령 전문은 `.agents/skills/wip-ledger/SKILL.md`, 구현 정본은 `scripts/wip.py`다.
⚠️**원장의 항목 수와 핸드오프 §0 의 항목 수는 같아야 한다** — 갈라지면 정본이 둘이 된다(함정 18).

### 10.1 동시 WIP 예외 계약 (2026-09-13 사용자 승인)

기본값은 열린 WIP 하나이며, 기존 원장이 있으면 새 원장 생성을 거부한다. 서로 다른 세션의
범위가 실제로 겹치지 않고 사용자가 동시 지원을 별도로 승인한 경우에만
`--new --allow-concurrent --concurrent-reason <승인 근거>`를 사용한다. 새 원장은
`CODEX_SESSION_ID` 또는 명시한 `--session-id`를 머리말에 기록한다.

- 둘 이상의 열린 원장이 있으면 모든 변경 명령에 `--file`이 필수다.
- 인자 없는 `--list`는 열린 원장 전부를 표시하며 하나를 최신순으로 추측하지 않는다.
- compact 훅은 공식 hook 공통 입력의 `session_id`와 정확히 결합된 원장 하나만 주입한다.
- 세션 ID가 없거나 일치 원장이 0개면 결합되지 않은 기존 원장이나 다른 세션 원장을 대체
  주입하지 않는다. 이 경우는 상태 손상이 아니라 **현재 세션 캡슐 부재**이므로 경고와 무주입
  복구 문맥을 남기고 compact를 계속한다. 다른 세션 원장을 현재 작업으로 선택·수정·종료하지 않는다.
- 같은 세션 ID에 원장이 2개 이상 정확히 일치하거나, 정확히 일치한 원장의 캡슐이 손상·구식이면
  소유권·상태 모호성이므로 fail-closed로 compact를 중단한다.
- 새 원장 이름을 정할 때 열린 파일과 같은 stem의 `-done` 파일을 모두 점유 슬롯으로 센다. 이미
  닫기 대상이 존재하는 이름 충돌은 직접 개명하지 않고 감사형 `--repair-name-collision`로 교정한다.
- 기능 도입 전에 생성돼 세션 ID가 없는 기존 원장은 소유 세션·사용자 승인을 확인한 뒤에만
  `--bind-session --file <정확한 원장> --session-id <소유 세션> --reason <근거>
  --approval-ref <승인>`로 한 번 결합한다. 자동 추정, 완료 원장 결합, 재결합은 금지한다.
- 기존 병렬 원장은 소유 세션의 파일이므로 승인 없이 결합·수정·닫지 않는다.

이 계약은 [OpenAI Hooks 문서](https://learn.chatgpt.com/docs/hooks)의 공통 입력
`session_id`를 사용한다. 훅 파일 변경 뒤에는 새 hash 신뢰와 사용자 수동·자동 compact E2E가
다시 필요하며, 그 전 증거 수준은 `STATIC_ONLY`/`E2E_NOT_RUN`이다.

사용자는 `COMPASS-핸드오프-행동요청` B안과 `핸드오프-실험큐와-스모크` B→D안을 승인했다.

### 11.1 정본 동기화

결과·계획·기준표·방법론·COMPASS 등 연쇄 대상마다 다음 표의 한 행을 쓴다. `없음`은 정확한

```text
산출물 | 필요 여부 | 실제 diff | 미갱신 사유
```

### 11.2 사용자 행동 요청

`사용자에게 부탁하는 것`의 한 행은 다음 여섯 요소를 모두 가진다.

```text
대상 | 정확한 위치 | 근거 | 사용자가 할 행동 | 완료 신호 | AI 후속 처리
```

실행·삭제·기타 순서를 지키고 `-done` 삭제 판정은 항상 적는다. 부탁이 없어도 여섯 요소 표를
유지하고 `요청 없음`의 근거와 후속을 명시한다. 최종 채팅 보고는 이 표에서 더하거나 빼지 않는다.

### 11.3 시작 프롬프트 상태 분기

- 열린 WIP 있음: 정확한 WIP 파일명, 첫 미완료 번호, 첫 행동과 선결을 적는다.
- 열린 WIP 없음: “중단 작업”을 쓰지 않고 새 요청 시작 상태라고 적는다.
- 승인 대기 있음: 정확한 대상과 승인 전 금지 행동을 적는다.
- 미해결 검사·FAIL 있음: `검사 / 정확한 대상 / 증거와 상태 / 운영 영향 / 권장 조치 / 대안 /
  승인 주체` 7요소를 한 행에 모두 적는다. `FAIL 1건`처럼 개수만 쓰는 보고는 불완전하다.

### 11.4 직전 실험 큐 — B 계약을 먼저, D 자동 입력을 나중에 적용

직전 핸드오프의 미완료 배치는 새 §7에 모두 남기거나 `이전 큐 제외·완료 이관` 표에서 파일별
완료·취소·대체 근거를 적는다. 재감사하지 않았다는 사실은 행 삭제 사유가 아니라
`REVALIDATE` 상태의 근거다.

```text
순 | id | 실험 | 배치 파일 | ⚙ | 누적 | 인벤토리 | 실행상태 | 선결 | 근거
```

- 인벤토리: `PRESENT`, `DONE`, `MISSING`, `REPLACED`, `UNVERIFIED`(진행 중 큐 잠금)
- 실행상태: `READY`, `GATED`, `HOLD`, `DONE`, `REVALIDATE`
- `scripts/handoff_queue.py`는 직전 행을 파싱하고 `queue_menu.py`의 현재 id와
  `experiments.tsv` 시간을 넣는 D 보조 입력이다. 자동 행은 과학적 판단을 하지 않고
  `REVALIDATE`로 시작한다.
- 검사기는 직전 미완료 배치 집합과 현재 행·이관 근거의 합집합을 대조한다.
- 현재 큐의 배치 수·시간 합계는 §7 본표만 집계한다. §7.1 이하의 완료·제외 이관 표는
  계승 근거이며 현재 큐 합계에 다시 넣지 않는다. `run_queue.bat` 같은 운영 실행기는
  `experiments.tsv` 실험 배치가 아니므로 배치 수·시간에서 제외한다.

### 11.5 스모크 disposition

핸드오프 §4에는 `run_smoke_check.bat`의 상태를 다음 중 하나로 적는다.

- `REQUIRED_USER_RUN`
- `NOT_RUN_PENDING`
- `NOT_REQUIRED(정확한 근거)`

앞의 두 상태는 §6b 사용자 행동 표에 정확한 명령·PASS 기준·큐보다 먼저라는 선결을 둔다.
AI는 스모크를 실행하지 않으며 이전 PASS를 후속 코드·훅 변경 뒤 새 PASS로 재사용하지 않는다.

### 11.6 compact 절의 과도기 상태

compact B안 M0~M3의 정적 구현 뒤에도 수동·자동 E2E인 M4·M5가 통과하기 전에는 기존
`compact 프롬프트` 절을 제거하지 않는다. 절 머리에 **수동 보조이며 자동 소비 계약이 아님**을
명시한다. M4·M5가 모두 PASS하고 M6가 별도로 승인되면 이 절을 제거하고 §11.1 정본 동기화
표를 완전한 대체물로 확정한다.

## §12. 2026-09-21 승인 계약 — 사용자 설명과 AI 복구정보를 분리한다

핸드오프에는 다음 세션 AI가 읽을 경로·hash·상태뿐 아니라 사용자가 결과를 판단할 설명도 있다.
종전에는 내부 파일명과 `STATIC_ONLY`, `GATED` 같은 코드만 자세하고, 그 결과가 사용자에게 어떤
뜻인지 짧아 사용자가 다시 질문해야 했다. 반대로 검사 전문을 모두 붙이면 문서는 끝없이 길어진다.

새 핸드오프의 §2에는 다음 네 열의 **사용자용 판독 표**를 둔다.

```text
관측 | 의미 | 사용자 영향 | 다음 행동
```

- `관측`: 로그·코드에서 직접 확인한 사실과 수치.
- `의미`: 왜 성공·실패·음성·미확인인지 평이한 문장으로 설명.
- `사용자 영향`: 지금 실행·선택·모델 판정이 무엇이 달라지는지.
- `다음 행동`: 사용자가 할 일 또는 AI가 이어 할 일을 한 가지로 특정.

AI 복구용 경로·명령·condition signature는 기존 상세 절이 소유한다. 같은 내용을 사용자 표에
전문 복사하지 않는다. 정적검사 출력도 handoff에 누적하지 않고 `handoff/audit/`의 세션별
`TINYLM_STATIC_AUDIT_V1` JSON이 소유하며, handoff 머리말은 그 파일을 링크만 한다. 따라서 세션
기록 단위는 **handoff + WIP + static audit record** 세 문서이고, 각 문서는 각각 설명·진행상태·
검사증거를 소유한다.

## §13. 2026-09-23 결과문서 한정 closure와 큐 잠금

사용자 조건부 승인에 따라 결과 회수의 독립 raw-log 입력 집합은
`TINYLM_RESULT_CLOSURE_V1` manifest로 보존하고 결과문서의 정확한
절·basename과 한정 대조한다. 이 계약은 **결과문서 전용**이다.
review 문서는 checker의 탐색·갱신·완료 차단 대상이 아니다.
핸드오프에는 회수 manifest의 위치와 결과만 짧게 남기고
원본 수치나 review disposition을 중복 저장하지 않는다.

진행 중 큐의 로그·실험 런처 .sh를 읽지 말라는 사용자 잠금이 있으면
직전 §7을 `scripts/new_handoff.py --queue-locked`로만 계승한다.
이 모드는 live `experiments.tsv`와 런처 존재 여부도 조회하지 않고
인벤토리 `UNVERIFIED`, 실행상태 `REVALIDATE`, id 미확인으로
표시한다. 직전 예상시간을 현재 READY 시간이나 실행 권장으로
승격하지 않는다. 시간 미달 사유에는 잠금과 재감사 선결을 쓴다.

잠금 때문에 전체 `check_static_all.py --profile codex-safe`가
로그·런처에 접근할 수 있다면 실행하지 않는다. 대신 같은 세션의
`handoff/audit/`에 `profile=queue-locked-scoped`, `status=PARTIAL`,
검사별 `PASS/NOT_RUN`과 범위를 명시한 한정 기록을 둘 수 있다.
**그 기록은 전체 codex-safe 감사도 아니고 원장 닫기 증거도 아니다.**
잠금이 풀린 뒤 exact 범위의 전체 검사를 새로 수행하기 전에는
열린 항목을 남겨 다음 세션의 첫 행동으로 인계한다.
