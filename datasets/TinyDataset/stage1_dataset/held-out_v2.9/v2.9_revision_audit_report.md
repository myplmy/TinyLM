# Stage1 held-out v2.9 작성 설계 및 감사 보고서

## 1. 결론

- v2.8의 4,500문항은 삭제하거나 덮어쓰지 않고 읽기 전용 입력으로 사용했다.
- v2.9도 4,500문항으로 유지했다. v2.8 census의 D9 미달은 문항 수 부족보다 문항 구성과 난이도 보정의 문제이므로, 같은 분포를 단순 증보하지 않았다.
- 후보의 반복 정형구 몫을 40.3%에서 **13.9%**로 줄였다.
- 후보 핵심 내용문의 문자 길이비는 모든 문항에서 `최장/최단 <= 1.10`이다.
- 문자·토큰 최장/최단 선택기는 모두 요청 상한 30%를 통과했다.
- JSON과 JSONL은 동일한 4,500개 레코드를 담는다.
- CPU 감사는 완료했다. 체크포인트와 GPU가 필요한 v2.9 D9 census는 생성 측에서 실행하지 않았다.

v2.8과 v2.9를 ID 순서로 대조했을 때 `id`, `gold`, `relation`, `difficulty_target`은 4,500/4,500건에서 유지됐다. 기존 `v28-####` ID는 판본 간 census 추적을 위해 그대로 두었다. v2.8 입력 파일에는 쓰기 작업을 하지 않았다.

## 3. 4,500문항 유지 판단

확인한 v2.8 census는 체크포인트 4개, 문항 4,500개를 사용했다.

| census 지표 | v2.8 결과 | 판단 |
|---|---:|---|
| B1 전부 맞힘 | 632 (14.0%) | 포화 문항은 일부 |
| B2 전부 틀림 | 1,868 (41.5%) | 바닥 문항이 큰 비중 |
| B1·B2 밖의 문항 | 2,000 (44.4%) | 실제 모델 쌍 비교에 쓰이는 문항은 충분히 존재 |
| D9 변별 대역 0.3~0.7 | 576 (12.8%) | 목표 60%에는 크게 미달 |
| 정보량 | 평균 0.3847 bit, 합계 1,731.3 bit | 절대 정보량은 작지 않음 |
| 정보 0 문항 | 2,500 (55.6%) | 증보보다 구성 개선이 우선 |
| 모델 쌍별 McNemar 불일치 | 931~1,233 | 각 모델 쌍을 가르는 문항은 이미 상당수 존재 |

D9는 비율 지표이므로 같은 분포의 문항을 더 넣으면 절대 문항 수만 늘고 12.8%라는 비율은 본질적으로 개선되지 않는다. 또한 체크포인트가 4개뿐이어서 문항별 정답률 격자가 성기다. 따라서 이번 판은 4,500개를 유지하고, 정형구 희석을 줄인 v2.9를 동일 체크포인트로 다시 census한 뒤 증보 여부를 판단하는 것이 적절하다.

v2.8의 난이도 라벨도 실측과 단조로 맞지 않았다. 평균 정답률은 easy 34.6%, mid 30.5%, hard 51.4%였다. 요청에 따라 라벨과 10/70/20 비율은 유지했지만, 이를 실측 난이도로 확정하지 않는다.

## 4. 수정 설계

### 4.1 후보 내용과 정형구

v2.8 후보에 붙어 있던 두 개의 긴 보조 문장을 제거했다. 남긴 핵심 명제를 관계별로 다시 정리해 네 후보가 같은 논리 축에서 경쟁하도록 했다.

- 인과: 원인 방향, 결과 방향, 공통 원인, 무관 관계를 구분했다.
- 시간순서: 먼저, 나중, 동시, 순서 미정의 대안을 맞췄다.
- 부분전체: 직접 구성 부분, 방향 역전, 내부의 별도 물체, 독립 구조를 구분했다.
- 반의: 반대, 동의, 하위 의미, 인과 관계를 구분했다.
- 상하위: 하위 범주, 방향 역전, 동일 범주, 별개 범주를 구분했다.
- 목적수단: 직접·간접 수단, 방향 역전, 다른 목표, 부수 결과를 구분했다.
- 조건: 필요조건, 충분조건, 필요충분조건, 독립 사실을 구분했다.
- 대조: 공통점과 차이점의 조합을 명시해 대안을 배타적으로 유지했다.

각 문항의 핵심 내용문 네 개는 문자 기준 `최장/최단 <= 1.10`이 되게 압축·정렬했다. 4,500문항 모두 통과했으며 최대 비율은 1.1000, 중위 비율은 1.0455였다. 핵심 내용문의 문항 내 문자 차이는 최대 5자, 중위 2자였다.

최종 후보에는 짧은 동일 문장 `추측은 아니다.`를 네 후보 모두에 한 번만 붙였다. 이는 길이를 채우기 위한 가변 패딩이 아니라, 부정형 후보가 하나뿐일 때 생기는 D4 표면 지름길을 중립화하기 위한 동일 표지다. 네 후보에서 완전히 같고 정답 위치를 예측하지 않으며, 공식 H6 기준 전체 후보 문자의 13.9%를 차지한다. 따라서 요청된 방법 (b)의 “한 문장, 네 후보 완전 동일” 조건과 15% 상한을 만족한다.

### 4.2 질문 다양성

문두의 사실·가상 대상·관계는 유지하고, 마지막 질문에 36개의 자연스러운 판단 도입구를 순환 적용했다. 여덟 관계 유형 각각에서 36종이 모두 사용됐다. 예시는 `제시된 정보만 기준으로 삼으면`, `각 항의 역할을 바꾸지 않으면`, `주어진 관계의 순서를 보존하면`이다.

금지집합 문자 8-gram과 겹치던 일반 표현은 뜻을 바꾸지 않고 다음처럼 바꿨다.

- `관계는 무엇인가?` → `관계를 고르시오.`
- `성립하지 않을 수 있다.` → `성립하지 않는 경우도 있다.`

## 5. 요청 표

| 검사 항목 | v2.9 결과 | 기준/판정 |
|---|---:|---|
| 후보 문자 중 정형구 몫 | **13.9%** | <=15%, 통과 |
| 문자 최장 선택기 | **11.4%** | <=30%, 통과 |
| 문자 최단 선택기 | **21.4%** | <=30%, 통과 |
| 토큰 최장 선택기 | **17.4%** | <=30%, 통과 |
| 토큰 최단 선택기 | **20.3%** | <=30%, 통과 |
| gold=0 | 1,125 (25.0%) | 22~28%, 통과 |
| gold=1 | 1,125 (25.0%) | 22~28%, 통과 |
| gold=2 | 1,125 (25.0%) | 22~28%, 통과 |
| gold=3 | 1,125 (25.0%) | 22~28%, 통과 |
| 질문 문장 고유 종수 | **2,676종** | v2.8 1,956종보다 증가 |
| 질문 문장 최빈 반복 | **20회** | v2.8 408회보다 감소 |

최장·최단 비율이 25%보다 낮은 것은 mid 문항에서 정답을 양 극단에 두지 않는 기존 설계를 유지했기 때문이다. 이번 게이트는 어느 축의 최장·최단 선택기도 30%를 넘지 않는지 확인한다.

토크나이저로 센 `ctx + choices` 전체는 884,419토큰, 문항당 평균 197토큰이다. 사용자가 보고한 v2.8의 문항당 312토큰보다 약 36.9% 줄었다.

### 6.1 `audit_heldout_v28.py`

`tinydataset` 환경과 `tok-ko-en-32768.json`을 명시하고, 근접중복 표본을 4,500으로 지정해 전체 문항을 감사했다.

| H3 문자·토큰 길이 | 네 선택기 모두 30% 이하 |
| H4 난이도 비율 | easy 10.0%, mid 70.0%, hard 20.0% |
| H5 후보 배타성 | 문항 내 동일 후보 0 |

H8의 75쌍은 남은 제한이다. 최고 유사도는 낮아졌지만, 일부 가상 대상 교체형 문두는 여전히 0.70 이상이다. 이번 판을 더 증보하기 전에 이 75쌍과 v2.9 D9 결과를 함께 보고 재작성 우선순위를 정해야 한다.

### 6.3 학습 풀 토큰 겹침

원본 `diag_bench_overlap.py`를 수정하지 않고 `--k 8 --sample 400`으로 실행했다.

| 학습 스트림 | 검사/건너뜀 | 토큰 8-gram 겹침 | 판정 |
|---|---:|---:|---|
| ko-en 600M (실제 597,000,000토큰) | 400/0 | 0 (0.00%) | 배경 수준 |
| ko-en 1200M (실제 1,194,000,000토큰) | 400/0 | 0 (0.00%) | 배경 수준 |

`tinydataset` 환경에는 `torch`가 없고, 원본 도구는 GPU·torch를 쓰지 않으면서도 패키지 초기화 과정에서 `torch`를 간접 import한다. 원본 감사 파일은 그대로 둔 채, `tokenizers.Tokenizer.from_file`과 v2.9 벤치 폴더만 메모리에서 연결하는 임시 실행 어댑터로 원본 `main`을 호출했다. 측정 뒤 임시 어댑터는 삭제했다. 이 검사는 정확한 토큰 창 재현만 찾으므로, 같은 사실을 다른 문장으로 학습한 경우까지 “오염 없음”으로 증명하지는 않는다.

`diag_dataset_tokens.py`도 확인했으나 해당 도구의 본문 추출기는 `text` 필드만 읽는다. v2.9의 `ctx`와 `choices`를 재는 용도가 아니므로 실행 결과가 이 데이터셋의 토큰 길이를 나타내지 않는다. 토큰 길이와 선택기 수치는 v2.8 스키마를 직접 지원하는 `audit_heldout_v28.py --tokenizer ...`로 측정했다. 감사 스크립트는 하나도 수정하지 않았다.

## 7. 남은 GPU 감사

v2.9의 실제 D9, B1/B2/B3, 문항당 정보량, McNemar 불일치, 난이도 라벨 단조성은 아직 미측정이다. `census_heldout_discrimination.py`는 GPU와 체크포인트를 사용하므로 사용자 지시에 따라 실행하지 않았다.

사용자 측에서는 먼저 v2.9를 `stage1_heldout` 평가 캐시에 연결한 뒤, v2.8과 같은 네 체크포인트·seed·PMI 설정으로 `--heldout-version 2.9 --n 4500`을 실행해야 한다. 그 결과로 다음을 결정한다.

1. D9 비율이 개선됐고 모델 쌍별 불일치가 유지되면 4,500개를 확정한다.
2. D9가 여전히 낮으면 단순 증보하지 않고 정보 0 문항과 실제 난이도 역전 문항을 우선 교체한다.
3. 교체 후에도 유효 문항 절대 수나 McNemar 불일치가 부족할 때만 증보한다.
