# log-to-result

> **TinyLM Codex 이식본.** 현재 사용자 범위와 [AGENTS.md](../../../AGENTS.md)가 우선한다.
> 로그 판독·결과 반영은 학습 또는 모델 실행 권한을 뜻하지 않는다.

## 왜 이 스킬이 필요한가

로그를 그대로 옮겨 적으면 **틀린 문서가 남는다.** 이 저장소에서 실제로 일어난 사례:

- `compare` 출력의 배포메모리를 그대로 인용해 sparse34 감축비율이 **3.26×**(실제 3.00×)로 기록될 뻔했다.
- 인쇄된 `|g|` 최대가 4.51 이라 "안정"으로 판정할 뻔했다. json `grad_max` 는 **10.79** 였다.
- 누적평균 `ms/step` 을 서로 다른 스텝 수의 런끼리 직접 비교하면 compile 상각 차이로 왜곡된다.
- 풀이 다른 런의 val 을 나란히 놓으면 **무효 비교**인데 표가 그걸 감춘다.

## 절차

### 0. ★★**먼저 그 번호에 문서가 있는지 본다** (2026-08-27 신설)

```
python scripts/new_result.py test_result/{번호}_log_{...}.txt
```

| 종료코드 | 뜻 | 할 일 |
|---|---|---|
| **0** | 그 번호에 결과문서가 **없다** | 새로 만든다 |
| **3** | 그 번호에 결과문서가 **있다** | 🚫**새 파일을 만들지 않는다.** 그 문서에 **새 절(§)** 로 이어 쓴다 |

> ⚠️**왜 절차가 됐나**: 이 스킬은 아래 §3 에서 *"같은 실험군이면 기존 번호에 이어 쓴다"* 고
> **적어만** 뒀고 **"먼저 있는지 본다" 는 단계가 없었다.** 그래서 `031` 이 20일 동안
> 결과문서 두 개로 갈라져 있었고 실험목록에도 031 행이 두 줄이었다.
> 이제 `check_result_numbers` R2 가 **에러**다 — 만들고 나서 알면 늦다.

### 1. 원본 확보

1. 로그 원본을 `test_result/{번호}_log_{YYYYMMDD}_{요약}.txt` 로 보존(사용자가 이미 넣어둔 경우가 많다).
2. **수치 정본은 로그가 아니라 `runs/logs/*.json`.** 관련 태그를 모두 덤프해 대조한다:

```
python -c "
import json,glob,os
for p in sorted(glob.glob('runs/logs/*.json')):
    d=json.load(open(p)); f=d.get('final')
    if not f: continue
    print(os.path.basename(p)[:-5], '| val', f['val_loss'], '| best', d['best_val'],
          '| bpb', f.get('bpb'), '| min', round(d['wall_sec']/60,1),
          '| grad_max', d.get('grad_max'), '| deploy_mb', d.get('deploy_mb'))
"
```

3. `python scripts/check_run_registry.py` 로 안정성·메모리·풀 상태를 함께 본다.

### 2. 파생값 계산 (직접 계산할 것 — 로그에 없다)

| 값 | 식 | 주의 |
|---|---|---|
| 정상상태 ms/step | `(누적평균×N − step0)/(N−1)` | 로그 `ms/step` 은 **누적 평균** |
| 토큰당 정규화 | `ms/step ÷ 유효배치` | 유효배치가 다른 런끼리 비교할 때 필수 |
| 격차 | `우 val − 좌 val` | **같은 풀·같은 토크나이저·같은 학습토큰**일 때만 |
| 배포 메모리 | json `deploy_mb`, 없으면 학습 로그 상단 `report()` 블록 | `compare` 의 구 로그 근사(`~`)는 sparse34 에서 과소 |
| 안정성 | json `grad_max`(warmup 이후) + `grad_peak_warmup` | 인쇄 `\|g\|` 는 10스텝 샘플 |

### 2.1 ★수치 해석 전에 비교 조건 서명을 먼저 고정한다 (2026-09-13)

결과를 비교하는 각 쌍마다 `TINYLM_CONDITION_SIGNATURE_V1` 블록을 결과문서에 둔다. 필수 필드는
`scripts/check_result_conditions.py`가 소유하며 최소한 풀·실제 train 풀 길이·draw 산식·복원추출 여부·
WSD의 절대 지평·학습 기대/관측 언어비·평가 언어·토크나이저·grad checkpoint·비교 태그·축 분류·
허용 주장 등급을 포함한다.

판정 어휘는 다음 네 개만 쓴다.

| 값 | 허용 범위 |
|---|---|
| `DIRECT_PAIRED` | 인과 대조에 필요한 통제축이 모두 같고 변경축만 결론에 대응한다 |
| `PARTIAL_CONFOUNDED` | 유효한 비교지만 두 축 이상이 함께 바뀌어 단일 원인의 크기로 분해할 수 없다 |
| `DESCRIPTIVE_ONLY` | 서로 다른 가족의 방향·크기 관측만 보존하며 직접 인과주장을 하지 않는다 |
| `NOT_RUN` | 해당 능력·평가를 실행하지 않아 어느 방향도 주장하지 않는다 |

`UNKNOWN`·`NOT_MEASURED`를 임의로 같은 조건으로 바꾸지 않는다. 같은 seed와 설정으로 실제 샘플
위치가 같다는 근거가 있으면 그 근거를 명시하고, 없으면 미계측 축으로 분류한다. WSD에서 steps가
달라지면 `actual_draw_tokens`뿐 아니라 `absolute_schedule_horizon`도 변경축이다. 평가셋 한국어가
0%이면 `not_run_claims`에 `KOREAN_QUALITY`를 반드시 남긴다.

```powershell
python -X utf8 scripts/check_result_conditions.py `
  "test_result/NNN_YYYYMMDD_결과.md"
```

검사기는 경로를 자동 발견하지 않는다. 현재 승인 범위의 결과문서를 명시적으로 넘기며, 이 정적 PASS를
GPU·모델 품질 검증으로 해석하지 않는다.

### 3. 문서 작성

파일명 `test_result/{번호}_{YYYYMMDDHHMMSS}_{요약}.md`. 같은 실험군이면 기존 번호에 이어 쓰고,
성격이 다르면 새 번호로 분리한다. **번호는 실험군 번호이지 실행 횟수가 아니다** —
재실행·후속 단계·사고 기록은 전부 **한 문서**다(§0 이 이것을 강제한다).
제목이 더 이상 내용을 대표하지 않으면 `python scripts/rename_result.py` 로 개명한다.

고정 섹션:

```markdown
# {번호} — {계획 P번호} {한 줄 결론}

- **계획**: [P0NN](../test_plan/...)   - **로그**: {로그 파일명}   - **배치**: {bat}
- **설정**: 프리셋/데이터/풀/steps/micro-bs/accum/seq/lr/스케줄/플래그 (전부)
- **비교 대상**: 재사용한 기존 런 태그와 그 값

## 1. 측정 결과
(표. 메모리는 report 기준, grad_max 포함, 시간 포함)

## 2. ★핵심 발견
((1)(2)(3)... 각 항목은 "무엇을 관측했고 그래서 무엇이 참인가")

## 3. 판정
(항목별 성립/불성립 + 판정기준 대입. σ 미측정 단서 포함)

## 4. 후속
([필수]/[중]/[저] 우선순위 + 구체 명령)

## 5. 재현 명령
(그대로 복붙 가능한 전체 명령)
```

### 3.1 시간순 누적 — 새 실험은 기존 실험 아래에

같은 결과번호의 후속 실행은 **과거 측정 절 사이에 끼워 넣지 않고**
마지막 역사 실험 절 아래 새 번호 절로 누적한다. 상단 한 줄 요약은
최신 결론을 가리켜도 되지만, 수치표·조건서명·실행일의 본문은
시간순을 유지한다. 재현 명령 부록은 해당 단계에 연관시키되
뒤에 온 새로운 실험을 앞선 날짜로 오인하게 배치하지 않는다.

기존 절의 위치를 교정할 때는 옛 Markdown anchor를 참조하는
정본 문서의 링크를 먼저 찾고, 필요한 경우 별칭 anchor를 남긴다.
[결과 088](../../../test_result/088_20260919_P060B-forced-GQA는-문턱을-못-넘었지만-default는-살았다.md)는
기존 2026-09-22 Stage2W·Stage3W 절을 §10으로 내려 이 규약을 적용한 사례다.
진행 중 큐의 로그·런처 잠금은 이 작업에도 항상 우선한다.

      깨끗한 패턴**이 나오면(예: FLOPs 가 같은데 2배 빠름) 계측 결함을 먼저 의심한다

### 4.1 결과 원본 closure — 2026-09-23 조건부 승인 범위

사용자가 정확히 지정한 입력 raw log 목록은 결과문서에서 역추론하지 않고
별도 manifest의 `input_logs`에 고정한다. 각 로그는 `mappings`의
정확한 결과문서·Markdown 절·원본 basename으로 1:1 대응시킨다.
`scripts/check_result_closure.py --manifest <정확한 JSON>`은 중복·누락·
섹션 내 축약/오기를 검사한다. 해당 결과문서와 원본 로그가 확정된 뒤에만
검사하고 감사 산출물을 WIP/session에 연결한다. 진행 중 큐의 로그는
사용자 잠금이 풀릴 때까지 검사기에도 전달하지 않는다.

이 계약은 **result-only**다. `docs/review/**`의 탐색·갱신·disposition을
manifest에 넣지 않고 review 미갱신으로 이 closure를 실패시키지 않는다.
위 §6의 사람이 하는 연쇄 갱신 조언은 그대로지만, 이 검사기의 PASS는
review 최신성이나 과학적 판정의 PASS가 아니다. 정확한 적용 범위는
[조건부 승인 제안서](../../../proposal/20260922_실험결과-증거추적과-live-review-연쇄누락-재발방지-제안서-approved-on-going.md) §9.1이 소유한다.

### 5. ★계획서로 돌아간다 (가장 자주 빠지는 절차 — 목록만 고치고 본문을 안 고친다)

**결과문서를 쓴 직후, 그 실험의 `test_plan/P0NN_*.md` 본문을 연다.** `exp-plan` 스킬 참조.
`실험계획목록.md` 한 줄만 고치는 것으로 끝내지 않는다 — 다음 세션은 **계획서 본문**을 읽고,
거기가 "미실행"이면 **이미 끝난 실험을 다시 설계한다.** 실제로 그런 일이 있었다.

- [ ] **§실행 이력** — 실행일 · 결과문서 링크 · 계획과 달라진 점
- [ ] **§예측 대조** — 예측이 맞았는지 **명시적으로**. 틀렸으면 취소선 + 이유.
      (예측 절을 써 놓고 대조하지 않으면 쓴 의미가 없다)
- [ ] **단계별 상태** — `✅ 완료(결과 0NN)` / `⏸ 대기` / `🚫 폐기` 를 각 단계 제목에
- [ ] **후속 단계 신설** — 결과가 새 질문을 열었으면 **같은 계획서에 단계로** 붙인다.
      새 P번호 남발 금지(같은 주제면 단계, 다른 주제면 새 번호)
- [ ] **계획이 무효가 됐으면 상단에 배너.** 조용히 지우지 않는다 —
      **왜 무효인지가 다음 사람에게 필요한 정보다**

### 7. 결과가 기존 결론을 뒤집을 때

**조용히 덮어쓰지 않는다.** 사용자에게 먼저 알리고 수위를 확인한다:

- 전면 정정 / 병기 후 확인런 대기 / 관측만 기록
- 어느 쪽이든 **두 수치가 왜 다른지**(어떤 조건이 달랐는지)를 문서에 남긴다
- 기존 결과문서·실험목록에 **교차 링크**를 걸어 나중에 헷갈리지 않게 한다
