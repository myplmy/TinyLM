# 제안 — held-out 변별정보·실측 난이도·관계 가족 품질을 실제로 높인다

> **작성** 2026-09-14 · **상태** ⏳판단 대기 · **분류** 데이터셋 품질 / 문항 선별
> 양식: [`proposal/README.md`](README.md) §3. 이 문서는 생성·선별 방법의 제안이며,
> 데이터 원본 수정·GPU 실행·새 판본 생성은 아직 승인된 구현 범위가 아니다.

## 1. 배경 — 왜 지금 이 제안을 하나

승인된 [`재작성 품질저하 방지 게이트`](done/20260914_held-out-재작성-품질저하-방지-게이트-제안서-approved.md)는
같은 패널 baseline, 작은 canary, rollback, 반복 상한으로 **나빠지는 판본을 막는 절차**를 정한다.
그러나 그 절차만으로는 새 문항이 왜 더 많은 정보를 주는지, 생성자가 붙인 `easy/mid/hard`를
실제 모델 난이도로 어떻게 바꾸는지, 관계별 하위 가족의 실패를 어떻게 고치는지는 답하지 않는다.

v3.0 독립 seed2 여섯 모델 실측은 이 생성 문제를 직접 드러냈다.

| 문제 | v3.0 관측 | 뜻 |
|---|---:|---|
| 정보 0 | **2,933/4,500 = 65.2%** | 전원 정답 또는 전원 오답이라 모델 비교에 기여하지 않음 |
| 문항당 정보 | 평균 **0.2826 bit**, 합계 1,271.7 bit | 이진 엔트로피 1 bit인 이상점에서 멂 |
| 실제 난이도 | mid 35.5% > hard 34.5% > easy 33.0% | 생성 라벨이 경험 난이도를 나타내지 않음 |
| 관계별 D9 하위 | 목적수단 7.1%, 인과 9.9%, 시간순서 14.0% | 상위 `relation` 균형만으로 하위 가족 편향을 못 고침 |
| 패널 분리 | v2.9 Muon15, v3.0 seed2 | 현재 원시 판본 차이는 인과 비교가 아님 |

핵심은 문장을 더 다양하게 다시 쓰는 것이 아니다. **정답을 결정하는 형식 의미 구조를 먼저
만들고, 여러 후보를 실제 설계 패널로 계측한 뒤, 정보량·모델쌍 불일치·가족 다양성을 동시에
만족하는 문항만 제한된 횟수로 선별**해야 한다.

## 2. 목적 — 무엇을 알아내거나 얻으려 하나

의미적으로 유효한 후보 은행에서 정보 0 문항을 제거하고, 문항당 정보와 모델쌍 구분 범위를
높이며, 경험적 `easy > mid > hard`와 관계 하위 가족 비퇴행을 만족하는 4,500문항 benchmark를
**canary 2회·full 1회·봉인 final 1회 상한 안에서** 만든다.

맞혔는지로 난이도를 배정하고, 서로 다른 모델을 갈라 준 문항을 골라 담는다.

## 5. 원리·근거

### 우리 실측

| 근거 | 값 | 출처 |
|---|---|---|

| 난이도 라벨 실패 | v3.0 `mid > hard > easy` | 같은 v3.0 census |
| 가족 편향 | 관계별 D9 7.1~33.6% 하위와 57.8% 상위가 공존 | 같은 v3.0 census |
| 동일패널 필요 | 판본과 모델 패널이 동시에 달라 원시 -11.2pp는 교락 | 승인된 품질저하 방지 게이트 §1.1 |

### 정보량과 변별의 원리

현재 도구의 문항 정보는 모델 패널의 정오 비율 `p`에 대한 이진 엔트로피
`H(p) = -p log2 p - (1-p) log2(1-p)`다. 모든 모델이 같게 반응하는 `p=0` 또는 `1`은
0 bit이고, 절반이 맞히는 `p=0.5`는 1 bit다. 다만 **애매하거나 정답이 틀린 문항도 우연히
0.5가 될 수 있으므로 entropy만 최대화하면 안 된다.** 정답 증명·사람 의미감사를 먼저 통과하고,
모델 능력 순서와 모델쌍 불일치가 함께 설명되는 문항만 고른다.

외부 논문은 이번 제안 작성에서 새로 조회하지 않았다. 따라서 특정 IRT 추정량이나 논문 구현과
일치한다고 주장하지 않고, 현재 census가 실제 저장하는 정오 행렬과 엔트로피 정의만 사용한다.

쉬운 설명: 반반으로 갈리는 문제는 비교에는 유용하지만, 문제가 애매해서 반반인 것일 수 있다.
먼저 정답이 확실한지 확인한 뒤에만 “잘 갈린다”를 장점으로 센다.

## 6. 방법

### 6.1 문장보다 먼저 형식 의미 구조를 만든다

각 문항은 먼저 기계 판독 가능한 작은 관계 그래프로 만든다. 자연어 지문과 선택지는 그 그래프의
표현일 뿐이며, 정답은 그래프 규칙으로 다시 계산할 수 있어야 한다.

| 필드 | 역할 |
|---|---|
| `relation` | 현재 8개 상위 관계 |
| `relation_subtype` | 충분/필요/필요충분/독립, 직접/매개 인과 등 의미 하위형 |
| `family_id` | 같은 논리 골격·오답 구조를 공유하는 재표집 단위 |
| `template_id` | 표면 문장 틀; 한 family가 여러 template을 가져야 함 |
| `gold_proof` | 전제에서 정답까지의 기계 검증 가능한 경로 |
| `distractor_error_type` | 역관계, 필요충분 혼동, 시간 역전, 인과/상관 혼동 등 |
| `difficulty_knobs` | hop 수, 전제 명시성, 경쟁 단서 수, 오답의 의미 거리 |

정답 증명이 하나로 닫히지 않거나 오답도 성립하면 모델 계측 전에 기각한다. 길이 늘리기, 부정어
추가, 드문 단어 사용은 난이도 손잡이로 세지 않는다. 그것은 추론 난이도가 아니라 읽기 잡음이다.

### 6.2 정보 0 문항을 생성 단계에서 줄이는 방법

생성만으로 모델 반응을 보장할 수는 없다. 따라서 “방지”는 한 번에 완벽한 문장을 만드는 것이
아니라 다음의 닫힌 후보-선별 회로다.

1. G0에서 기존 문항의 응답 벡터를 얻고, `k=0` 또는 `k=M`인 ID만 우선 교체 대상으로 둔다.
2. 한 자리에는 최대 2후보만 만든다. 첫 후보는 난이도 손잡이를 한 단계 올리거나 내리고,
   둘째는 오답 오류형만 바꾼다. 둘을 동시에 바꾸지 않아 원인을 남긴다.
3. 이제 결과가 알려진 Muon15·seed2를 합친 **설계 패널**에서 후보를 채점한다. v3.1 설계에
   사용한 순간 seed2는 final이 아니라 설계 패널로 강등한다.
4. `k=0`·`k=M`, skip, 정답 증명 실패, 선택지 위치/문구 shortcut, 근사중복 후보는 기각한다.
5. 같은 모델쌍만 반복해서 가르는 대신 아직 불일치가 부족한 모델쌍을 추가로 덮는 후보를 우선한다.

완성 문항에서 정보 0을 “절대 0건”으로 요구하면 새로운 독립 모델에서 다시 생길 수 있다.
현실적인 계약은 **설계 패널에서 0건을 목표로 선별하되, 봉인 final에서는 paired baseline 대비
비증가와 절대 비율을 함께 보고 실패를 보존**하는 것이다.

### 6.3 레코드당 정보량을 높이는 방법

가중합의 임의 계수를 결과 뒤에 고하지 않도록 선별을 **사전 제약 + 사전순서**로 한다.

1. 의미 유효성·오염·중복·정답 균형을 hard constraint로 통과한다.
2. 정보 0 후보를 제거한다.
3. 관계×하위형×난이도×오답형의 최소 quota를 채운다.
4. 남은 자리에서는 총 `H(p)`를 최대화한다.
5. 같은 총 bit이면 아직 덜 구분된 모델쌍의 불일치 수를 더 늘리는 후보를 고른다.
6. 다시 동률이면 template/family 중복이 낮은 후보를 고른다.

이 방식은 3/6만 무조건 모으지 않는다. 2/6·4/6도 약 0.918 bit이고 서로 다른 능력 구간의 모델을
가를 수 있다. 총 bit와 **15개 모델쌍별 불일치 최소값**을 함께 보면 일부 모델쌍만 잘 가르는
편향을 줄일 수 있다.

### 6.4 `easy > mid > hard`를 실제 모델 기준으로 만든다

`difficulty_target`은 생성 전 목표, `difficulty_empirical`은 계측 후 결과로 분리한다. 여섯 모델
최종 표에서는 D9 대역 자체와 정확히 맞는 다음 세 칸을 사용한다.

| 실측 라벨 | 여섯 모델 중 정답 | 정답률 | 정보량 |
|---|---:|---:|---:|
| `easy` | 4/6 | 66.7% | 약 0.918 bit |
| `mid` | 3/6 | 50.0% | 1.000 bit |
| `hard` | 2/6 | 33.3% | 약 0.918 bit |

설계 패널이 12개라면 이에 대응해 easy 7~8/12, mid 6/12, hard 4~5/12를 후보 버킷으로 쓴다.
각 버킷 안에서 relation·family quota를 맞춘다. 이렇게 하면 라벨별 평균이 정의상 단조가 되지만,
그것만으로 일반화가 증명되지는 않으므로 봉인 final에서 다시 `easy > mid > hard`를 검사한다.

난이도 손잡이는 한 번에 하나만 움직인다.

- easy: 1-hop, 관계가 명시된 전제, 명백하지만 사실이 아닌 오답.
- mid: 2-hop 또는 한 개의 경쟁 단서, 같은 관계 안의 오답.
- hard: 2~3-hop, 가까운 오류형 오답, 불필요한 전제 한 개.
- 금지: 정답 누락, 두 정답, 모호한 지시어, 단순 장문화, 희귀어, 부정문 중첩으로 hard를 만드는 것.

사람 난이도가 필요하면 별도 `difficulty_human` 필드로 두며 TinyLM 패널 라벨과 섞지 않는다.

### 6.5 관계별 D9 하위 가족 편향을 고치는 방법

현재 `relation` 8개는 재표집 단위로 너무 거칠다. 같은 “인과” 안에서도 직접 인과, 매개 인과,
필요조건 혼동, 상관/인과 혼동은 모델 반응이 다르다. 다음을 모두 적용한다.

- 각 relation마다 최소 4개 `relation_subtype`, subtype마다 여러 `family_id`를 둔다.
- 한 `family_id`나 `template_id`가 relation의 5%를 넘지 않도록 생성 manifest에서 검사한다.
- 관계별 전체 D9뿐 아니라 relation×subtype×difficulty 표를 낸다.
- 바닥 세 관계만 늘리지 않고, 기존에 잘 작동한 ID는 보존하며 실패 family만 교체한다.
- 관계별 paired 비퇴행을 hard gate로 두고, 최하위 관계의 개선과 15개 모델쌍 최소 불일치 증가를
  동시에 요구한다. 정확한 허용 폭은 G0 paired 결과 전에 동결한다.
- 통계 판정은 문항 4,500개가 아니라 `family_id` cluster bootstrap과 leave-one-family-out
  민감도에서 같은 방향인지 확인한다.

### 6.6 단계와 중단 게이트

| 단계 | 무엇 | 비용 | ★다음으로 가는 조건 |
|---|---|---:|---|
| **Q0** | Stage10c G0로 v2.9/v3.0 동일패널 전이 분해 | ⚙0.9 GPU-h | 조건 핵심 일치·skip 0·paired JSON 존재 |
| **Q1** | 의미 스키마·solver·family taxonomy와 난이도 손잡이 정적 테스트 | ⚙2~3h AI + 팀 | 정답 유일성·오답 거짓·필드 누락 0 |
| **Q2** | 10% canary 450자리, 자리당 최대 2후보 생성 | 팀 1회 | 후보 수 상한·기존 유효 ID 보존 |
| **Q3** | 설계 패널 계측과 제약 기반 450개 선별 | ⚙0.3 GPU-h/회 | 정보 0 제거, bit·쌍 coverage 증가, 가족 비퇴행 |
| **Q4** | 사람 의미감사와 canary paired 판정 | 사람 표본 | 오류 0, 사전등록 벡터 통과; 실패 시 수정은 최대 1회 |
| **Q5** | 통과한 규칙만 full에 1회 적용 | 팀 1회 + ⚙1.2 GPU-h 상한 | 정적·설계패널 paired 통과 |
| **Q6** | 새로 봉인한 독립 6모델 final 1회 | ⚙0.9 GPU-h | 절대 D9·비퇴행·단조성·가족 판정 통과 시 승격 |
| **Q7** | 실패 시 현행 유지·후보 HOLD | 0 | 새 가설·새 패널·새 비용 승인 전 재작성 금지 |

canary는 최대 2회, full은 최대 1회, final은 최대 1회다. Q3에서 두 번 실패하면 문구를 또
고치는 대신 생성 가설을 폐기한다. Q6 결과를 다음 판 설계에 쓰면 그 패널은 즉시 설계군으로
강등하고, 새 봉인 패널이 없으면 다음 판은 `FINAL_NOT_RUN`이다.

---

## 7. 거절하면 못 하는 것

v3.0을 HOLD하고 v2.9 또는 더 이른 판을 계속 사용하는 것은 가능하다. 다만 품질저하 방지 게이트는
“나빠졌는가”만 가르고 “어떤 후보를 골라야 실제 정보량이 늘어나는가”를 제공하지 않는다.
따라서 다음 데이터팀 지시는 다시 문체·분포 proxy에 의존하게 되고, 정보 0·난이도 비단조·관계
하위가족 편향을 직접 줄였다는 증거를 만들 수 없다.

## 8. 위험 — 실행하면 무엇이 잘못될 수 있나

| 위험 | 어떻게 드러나나 | 완화 |
|---|---|---|
| 설계 패널 과적합 | 설계 패널 bit는 오르고 봉인 final에서 무너짐 | 두 기존 패널은 설계용으로만 쓰고 새 final 1회 봉인 |
| entropy가 애매함을 보상 | 반반 갈리지만 사람도 정답을 못 정함 | 형식 정답 증명 + 사람 의미감사를 entropy보다 먼저 |
| 모델쌍 편식 | 총 bit는 높지만 특정 쌍 discordance가 거의 0 | 15개 쌍 최소 coverage와 하위 쌍 우선 선택 |
| 경험 라벨의 순환논리 | 패널 반응으로 라벨하고 같은 패널에서 단조성 PASS | 라벨은 설계용; final 단조성을 별도 보고 |
| 하위 가족 수만 부풀림 | 이름만 다른 family가 같은 논리·문장 틀 공유 | `gold_proof`·오답 오류형·template fingerprint로 family 독립성 검사 |
| 좋은 문항까지 손실 | 전면 재작성으로 다른 관계가 급락 | 기존 고정보 문항 보존, 실패 자리만 최대 2후보 |
| GPU 비용 팽창 | 후보를 무제한 생성·채점 | 자리당 2후보, canary 2회, full/final 각 1회 hard stop |
| 새 패널 확보 실패 | 진짜 독립 final을 만들 수 없음 | 후보를 `CALIBRATED / FINAL_NOT_RUN`으로 보존하고 승격 금지 |

## 9. 대안

| 안 | 무엇 | 장점 | 단점 | 영향도 | 수행비용 |
|---|---|---|---|---|---:|
| **A** | 문체·길이·정답 위치만 더 균형화해 다시 전면 작성 | 생성팀이 익숙함 | v3.0처럼 정적 proxy PASS와 동적 실패가 공존 | 데이터 전체 | 중간 |
| **B** | **형식 의미 생성 + 응답 보정 후보은행 + 제약 기반 Pareto 선별** | 정보 0·bit·난이도·가족을 직접 최적화, 좋은 ID 보존 | 도구·새 봉인 패널 필요 | 생성·계측·manifest | 중간~높음 |
| **C** | v2.9/v3.0을 HOLD하고 새 판을 만들지 않음 | 비용 0, 과적합 없음 | benchmark 변별력 문제를 해결하지 못함 | 상태 문서 | 0 |
| **D** | 평가 때마다 모델에 맞춰 적응형 문항을 고름 | 주어진 모델쌍 검정력 최대화 | 고정 benchmark 재현성 상실, 결과 간 비교 어려움 | 평가 프로토콜 전체 | 높음 |

### ★권장안과 근거

**B안을 권장한다.** A는 이미 v3.0에서 실패한 정적 proxy 중심 접근이고, D는 고정 held-out의
재현성을 버린다. B는 정답 타당성을 먼저 고정한 뒤 실제 응답 행렬로 정보량을 높이되, 승인된
품질저하 방지 게이트의 canary·보존·봉인·hard stop을 그대로 사용한다. 즉 “좋아질 때까지 다시
쓰기”가 아니라 **최대 두 후보 중 기준을 충족한 것만 한 번 선별하고, 실패하면 멈추는 방식**이다.

승인 시에도 Q0 결과 회수 → Q1 스키마/도구 승인 → Q2 데이터팀 canary 지시 순으로 단계적으로
연다. 이 제안 승인만으로 보호 데이터 접근이나 데이터 재작성·GPU 실행 권한이 생기지 않는다.
