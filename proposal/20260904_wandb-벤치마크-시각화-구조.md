## 1. 배경 — **먼저 사용자가 본 증상의 원인을 밝힌다**

### 1.1 🚫증상 A: *"마지막 모델만 업로드"* — 원인은 W&B 가 아니었다

> *"3개의 모델에 대해 벤치마크 수행했으나 **가장 마지막 벤치마크한 모델의 데이터만 업로드**"*

로그가 원인을 그대로 찍고 있었다:

```
[건너뜀] d12_cla2_r20: 학습 json 이 없다(m100R1c_ko-en_300M_d12_cla2_r20.json)
[건너뜀] d16_cla2_r20: 학습 json 이 없다(m100R1c_ko-en_300M_d16_cla2_r20.json)
```

`_run_name()` 이 **CLI 가 준 `--preset`** 으로 런 이름을 만드는데 배치가 세 모델 전부에
`m100R1c` 를 줬다(실제는 `m100s8` / `m100s12` / `m100R1c`). **체크포인트 로딩은 전역 검색으로
자기 복구**해서 수치는 정상이었지만 **런 이름은 복구가 안 돼 두 모델이 `_bench_eligible` 에서
걸렸다.** ✅**2026-09-04 에 고쳤고**(체크포인트 파일명에서 프리셋을 읽는다)
**2026-09-05 에 실전 재현 시험을 통과했다** — 일부러 틀린 프리셋을 줬는데 **3/3 올라갔다**
(결과 [074 §11.1](../test_result/074_20260904_P085-정답CE는-9쌍-전부-맞고-정확도는-끝까지-못-가른다.md)).

### 1.2 🚫증상 B: *"x 축에 태그명과 지표명이 함께 표시된다"* (2026-09-05 지시 (5))

> *"W&B 의 chart 에서 metric 에 `bench/arc_easy/acc` 나 `bench/hellaswag/gold_ce` 와 같은 값을
> 넣어서 지금도 차트를 만들 수는 있으나 **차트 내의 x 축에 태그명과 지표명이 함께 표시되는 문제**가 있음."*

★**원인은 데이터 모양이다. 설정으로 못 고친다.**

지금 우리가 올리는 것은 **런당 스칼라 9개**다:

```
bench/hellaswag/acc = 0.2832
bench/arc_easy/acc  = 0.3560
bench/piqa/acc      = 0.5376
...
```

**과제 이름이 "값" 이 아니라 "키" 안에 들어 있다.** W&B 의 workspace 차트는
*"런 하나 = 점 하나, 지표 하나 = 계열 하나"* 로 그리므로 x 축이 될 수 있는 것은 **런(=태그)** 뿐이고
과제는 **계열 이름**으로만 나타난다 → 라벨이 `태그 + 지표` 로 붙어 보인다.

★★**처방은 하나뿐이다 — 과제를 키에서 꺼내 열로 만든다.** 그것이 long-format Table 이다.

| 지금(wide, 키에 과제) | ★제안(long, 열에 과제) |
|---|---|
| `bench/hellaswag/acc = 0.2832` | `model=… , task=hellaswag , metric=acc , value=0.2832` |
| x 축이 될 수 있는 것: **런** | x 축이 될 수 있는 것: ★**task · metric · model 아무거나** |

## 2. 요구사항 — **검토요청서 전문을 여기 옮긴다**(그 파일은 삭제 예정)

### 2.1 기본 원칙 (검토서 §2)

1. 벤치마크 결과는 가능한 한 **그 모델의 기존 학습 Run 에 결합**한다.
2. 🚫**벤치마크 전용 Run 이나 dashboard 용 관리 Run 을 불필요하게 추가하지 않는다.**
3. **50M 토큰 미만 프로브 제외** 등 기존 W&B 업로드 필터를 유지한다.
4. 🚫현재 `bench/<task>/<metric>` **Summary 스칼라를 제거하거나 다른 의미로 바꾸지 않는다.**
5. W&B Table 은 **정본이 아니라 시각화용 파생 데이터**다.

### 2.2 표 스키마 (검토서 §3) — **long format**

| model | task | metric | value | n | n_asked | skipped | seed | pmi |
|---|---|---|---:|---:|---:|---:|---:|---|
| mC_cla2_ag4_r20 | hellaswag | acc | 0.2814 | 5000 | 5000 | 0 | 99 | true |
| mC_cla2_ag4_r20 | hellaswag | acc_norm | 0.2606 | 5000 | 5000 | 0 | 99 | true |
| mC_cla2_ag4_r20 | hellaswag | gold_ce | 3.7108 | 5000 | 5000 | 0 | 99 | true |
| … | arc_easy · piqa 도 같은 모양 | | | | | | | |

핵심 열은 **`model` · `task` · `metric` · `value`** 넷이고 나머지는 해석용 metadata 다.
키는 **`bench/table`** 하나. 🚫과제마다 키를 나누지 않는다.

### 2.3 ★원하는 차트 세 개 (검토서 §4) — **이것이 목표다**

| 차트 | x | y | 색/범례 | filter |
|---|---|---|---|---|
| **ACC** | `task` | `value` | `model` | `metric == "acc"` |
| **ACC_NORM** | `task` | `value` | `model` | `metric == "acc_norm"` |
| **GOLD_CE** | `task` | `value` | `model` | `metric == "gold_ce"` |

```
                hellaswag        arc_easy          piqa
model_A             #               #               #
model_B             #               #               #
model_C             #               #               #
```

- x 축은 **hellaswag / arc_easy / piqa** 이고 **이후 추가되는 벤치마크가 자동으로 칸을 늘린다.**
- 🚫**Python 으로 그림을 만들어 올리지 않는다**(검토서 §5) — matplotlib·Plotly 이미지 금지.
  **W&B Workspace 의 Custom Chart 에서 직접** 만든다.
- `gold_ce` 는 **낮을수록 좋다** — 차트 제목에 `Gold CE ↓` 를 넣는다(검토서 §11).
- acc·acc_norm 의 Y 축은 **0~1 고정**을 권한다(§9 에 조건부 반대 의견이 있다).

### 2.4 🚫하지 말 것 (검토서 §12)

벤치 전용 프로젝트 · 벤치마다 Run · 벤치마다 Table 키 · Python plot · 이미지 업로드 ·
Plotly 자동 생성 · 기존 Summary 제거 · 로컬 결과 형식 변경 · **`trainer.py` 수정**.

### 2.5 검증 항목 16개 (검토서 §13) — **§8 이 이것을 단계에 배분한다**

**데이터** ①기존 Summary 유지 ②`bench/table` 생성 ③`model/task/metric/value` 정확
④`n/n_asked/skipped/seed/pmi` 보존 ⑤문자열이 score 로 안 들어감
**증분** ⑥HellaSwag 후 PIQA 만 돌려도 둘 다 남음 ⑦그 뒤 ARC 만 돌려도 셋 다 남음
⑧재실행해도 같은 `(model,task,metric)` 이 **중복 누적 안 됨**
**모델 비교** ⑨스키마 동일 ⑩여러 모델 동시 비교 ⑪x=task·y=value·color=model
⑫filter 로 세 차트
**기존 규약** ⑬50M 필터 유지 ⑭W&B 오류가 로컬 결과를 안 바꿈 ⑮standalone 모드 호환
⑯새 벤치에 **과제별 분기 불필요**

## 3. ★★핵심 질문에 답한다 — *"런마다 table 이 하나씩 생기는 것 아닌가"*

> 2026-09-05 사용자 지시 (2)C: *"각 모델 런마다 `bench/table` 을 올리면 **각 런에 table 이
> 한개씩 다 생기는 것이 아닌지** 확인바람. (…) **개별 모델 json 마다 벤치마크 테이블이 있는 경우
> 해당 요청사항과 다른 방식으로 차트가 그려질 가능성이 있는지 검토필요.**"*

### 3.1 ✅**맞다 — 런마다 하나씩 생긴다. 그리고 그것이 옳은 모양이다.**

W&B 공식 문서 확인(2026-09-05 조회, `docs.wandb.ai/guides/app/features/custom-charts/walkthrough/`):

| 사실 | 근거 |
|---|---|
| Custom Chart 의 질의는 **`runSets`** 로 **선택된 여러 런을 한 번에** 읽는다 | 필드 이름이 `runSets_…` 로 나온다 |
| 표는 **`summaryTable`** + **`tableKey`** 로 고른다(시간축이면 `historyTable`) | 문서가 두 이름을 다 든다 |
| 권고 상한 **키당 10,000점** | 우리는 모델당 **9행** — 40모델이어도 360행 |

→ ★**런마다 9행짜리 표가 하나씩 있고, 차트가 그것들을 이어 붙여 한 데이터프레임으로 본다.**
그 데이터프레임에는 `model` 열이 있으므로 **색상 범례가 자동으로 모델별로 갈린다** = §2.3 그대로다.

🚫**"모델 수만큼 차트가 생긴다" 가 아니다** — 차트는 하나이고 **런 선택이 데이터를 정한다.**
모델을 추가해도 **차트 정의를 안 고친다**(검토서 §16 요구 충족).

### 3.2 ⚠️★**그런데 진짜 위험은 다른 데 있다 — 같은 키를 다시 올리면 표가 통째로 바뀐다**

`summaryTable` 은 이름 그대로 **summary 에 있는 표 하나**를 읽는다. 같은 런에 `bench/table` 을
**두 번 `log` 하면 summary 의 표는 두 번째 것으로 교체된다.**

★**그래서 지금 구조 그대로 표를 붙이면 증상 A 가 형태만 바꿔 재발한다**:

```
eval_bench_suite --task hellaswag ...   -> bench/table = [hellaswag 3행]
eval_bench_suite --task piqa      ...   -> bench/table = [piqa 3행]        # ★hellaswag 사라짐
eval_bench_suite --task arc_easy  ...   -> bench/table = [arc_easy 3행]    # ★piqa 사라짐
```

우리 배치는 **과제마다 호출을 나눈다**(`[1/3] hellaswag` `[2/3] piqa` `[3/3] arc_easy`).
→ ★**마지막 과제만 남는다.** 이것이 검증 항목 ⑥⑦이 묻는 바로 그것이다.

⚠️**Summary 스칼라는 이 문제가 없다** — `r.summary.update(flat)` 는 **키를 합친다.**
실제로 2026-09-04 로그의 hellaswag 블록에서 이미 `bench/arc_easy/skipped 0` 이 보인다.
🚫**그래서 "지금 잘 되니 표도 되겠지" 라고 유추하면 틀린다** — **스칼라와 표는 갱신 규약이 다르다**(함정 28).

### 3.3 ✅처방 — **표를 매번 정본에서 통째로 다시 만든다**

| 무엇 | 어디 |
|---|---|
| ★**정본** | 신설 **`test_result/bench_results.tsv`** — `(model, task, metric)` 를 열쇠로 **upsert** |
| 올리는 것 | 그 정본에서 **그 모델의 전 과제 행**을 뽑아 **표 하나로** |

이러면 검증 ⑥⑦⑧이 **한 번에** 만족된다: 증분 실행은 정본에 행을 더하고, 재실행은 같은 열쇠를
**덮어쓰므로 중복이 안 쌓인다.** 🚫**W&B 를 정본으로 삼지 않는다**(검토서 §2 원칙 5와 일치).

### 4.2 (사용자 작성) 브라우저 내 Workspace 에서 더미 데이터로 차트 생성 테스트 완료

아래의 생성 순서에 따라 브라우저 내 workspace 에서 더미 데이터를 통해 차트 생성 테스트 완료하였음.
단, metric choice기능이 작동하지 않는 문제가 있어, Table을 wide format으로 변경하여 4.2.1 항목의 방법으로 추가 테스트 필요.

생성 순서

(1)워크스페이스에서 + → Custom Chart를 선택합니다.
(2)데이터 쿼리에서 **Summary Table (summaryTable)**을 선택합니다.
(3)Table key로 **bench/table**을 입력하거나 선택합니다.
(4)기본 차트 프리셋 하나를 선택한 뒤 Edit을 눌러 Vega 편집기를 엽니다.
(5)Vega spec을 다음 내용으로 교체합니다.
```
{
  "$schema": "https://vega.github.io/schema/vega-lite/v6.json",
  "title": "Benchmark metric by task and model",
  "data": {
    "name": "wandb"
  },
  "params": [
    {
      "name": "metric_choice",
      "value": "acc",
      "bind": {
        "input": "select",
        "options": [
          "acc",
          "acc_norm",
          "gold_ce"
        ],
        "name": "Metric: "
      }
    }
  ],
  "transform": [
    {
      "filter": "datum['${field:metric}'] === metric_choice"
    }
  ],
  "mark": {
    "type": "bar",
    "tooltip": true
  },
  "encoding": {
    "x": {
      "field": "${field:task}",
      "type": "nominal",
      "title": "Task",
      "sort": [
        "hellaswag",
```

## 9. ⚠️조건부 반대 1건 — **Y 축 0~1 고정**

검토서 §11 은 *"모델 간 작은 차이를 과장하지 않기 위해 acc 축을 0~1 로 고정"* 을 권한다.

🚫**우리 정확도는 27~36% 대**라 0~1 축에서는 **세 모델이 거의 같은 높이로 보인다.**
그리고 결과 [074 §11](../test_result/074_20260904_P085-정답CE는-9쌍-전부-맞고-정확도는-끝까지-못-가른다.md)
은 그 차이가 **대부분 통계적으로 못 갈리는 크기**임을 보였다 — 즉 **과장하지 않는 것이 옳다.**

★**대안**: 축은 자동으로 두되 **우연 수준(hellaswag·arc_easy 25% · piqa 50%)을 기준선으로 긋는다.**
그것이 *"작은 차이를 과장하지 않는다"* 의 정직한 구현이다. **최종 판단은 사용자.**
