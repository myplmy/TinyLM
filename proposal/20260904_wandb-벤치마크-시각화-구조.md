## 1. 배경 — **먼저 사용자가 본 증상의 원인을 밝힌다**

> *"3개의 모델에 대해 벤치마크 수행했으나 **가장 마지막 벤치마크한 모델의 데이터만 업로드**"*

🚫★**이것은 W&B 문제도 Table 구조 문제도 아니다.** 로그가 원인을 그대로 찍고 있었다:

```
[건너뜀] d12_cla2_r20: 학습 json 이 없다(m100R1c_ko-en_300M_d12_cla2_r20.json)
[건너뜀] d16_cla2_r20: 학습 json 이 없다(m100R1c_ko-en_300M_d16_cla2_r20.json)
```

`_run_name()` 은 **CLI 가 준 `--preset`** 으로 런 이름을 만든다:

```python
return f"{a.preset}_{a.data}_{a.tokens}_{tag}"        # eval_bench_suite.py:616
```

배치가 세 모델 전부에 `--preset m100R1c` 를 줬는데 **실제 프리셋은
`m100s8`(d12) · `m100s12`(d16) · `m100R1c`(mC)** 다.
★**체크포인트 로딩은 전역 검색으로 자기 복구**했지만(`cfg` 는 체크포인트에서 읽으므로 **수치는 정상**),
**런 이름은 복구되지 않아** 두 모델이 `_bench_eligible` 에서 걸렸다.

→ ★**세 모델 중 `mC_cla2_ag4_r20` 만 실제로 `m100R1c` 라서 그 하나만 올라갔다.**

✅**고칠 것 둘**(이 제안과 별개로 **지금 해야 한다**):

| # | 무엇 | 크기 |
|---|---|---|
| **1** | 배치를 **모델별 프리셋**으로 나눈다(결과 067 이 이미 그렇게 했다) | ⚙0.1h |
| ★**2** | `_run_name` 이 **체크포인트에서 프리셋을 읽게** 한다 — 사람이 안 틀리게 | ⚙0.2h |

★**2 가 근본 처방**이다. `resolve_ckpt` 가 전역 검색으로 찾은 **실제 파일명**이
`m100s8_ko-en_300M_d12_cla2_r20.pt` 이므로 **거기서 프리셋을 그대로 떼면 된다.**

## 2. 검토요청서 §14 의 일곱 물음에 답한다

### 2.1 현재 업로드 경로

```
main()                      eval_bench_suite.py
  └─ _push_wandb(all_summary, a)                      :~640
       ├─ (기본)   태그별로 모아 학습 런 하나에 얹는다
       │     rid  = _run_name(a, tag)                  # {preset}_{data}_{tokens}_{tag}
       │     gate = _bench_eligible(a, tag)            # 학습 json 없으면 건너뜀
       │     wandb.init(id=rid, resume="allow")
       │     r.summary.update(flat)                    # bench/<task>/<metric>
       └─ (--wandb-standalone) bench-<task>-<tag> 독립 런
```

### 2.2 Table 을 어디서 만드나 — **같은 루프, 같은 `rec`**

★**`flat` 를 다 만든 직후, `r.summary.update()` **앞**** 이 최소 변경점이다.
검토서 §8 의 *"Summary 와 Table 이 다른 계산 경로를 거치지 않게"* 가 **구조적으로** 지켜진다 —
같은 `rec` 를 두 번 읽는 것이 아니라 **한 번 순회하면서 둘을 함께** 만든다.

⚙**추가 코드 약 25줄. 다른 파일은 안 건드린다.**

### 2.3 누적 Table 을 **어느 정본에서** 재구성하나

🚫★**W&B 를 읽지 않는다**(검토서 §7 의 우려 그대로 — 그러면 W&B 가 정본이 된다).

🚫**그런데 문제가 하나 있다: 지금 우리에게 "벤치마크 결과의 로컬 정본" 이 없다.**
수치는 **로그 txt 의 인쇄문**과 **결과문서**에만 있고 **기계가 읽을 형식이 아니다.**
→ ★**그것부터 만든다.**

```
test_result/bench_results.tsv     (git 추적 · diff 됨)
run_name <TAB> model <TAB> task <TAB> metric <TAB> value <TAB> n <TAB> n_asked
         <TAB> skipped <TAB> seed <TAB> pmi <TAB> date
```

- `eval_bench_suite` 가 **W&B 를 부르기 전에** 이 파일을 **`(run_name, task, metric)` 키로 upsert** 한다.
- Table 은 **이 파일에서** 만든다 → 증분 실행이 자연히 누적되고 재평가는 **덮어쓴다**
  (검토서 §7 의 두 요구를 **한 자료구조로** 동시에 만족한다).
- ★`--wandb` 를 안 줘도 쌓인다 — **결과 067 §12 의 다운스트림 21행이 로그에만 남은 사고**가 막힌다.
- ★★**지시 7 의 실험 기록 제안과 이어진다** — 그 제안의 *"추후 벤치마크 열 추가"* 가 **이 파일**이다.

### 2.4 여러 Run 의 Table 을 한 Custom Chart 에서 합칠 수 있나

⚠️★★**모른다. 그리고 추측하지 않는다.**

🚫**나는 W&B 를 실행하지 않는다**(AI 는 GPU·외부 서비스를 안 돌린다). 검토서 §10 자신이
*"불가능하거나 예상과 다르면 우회 구현하지 말고 **먼저 제약을 보고**할 것"* 이라고 적었다.

★**그래서 Stage0 을 둔다** — 코드 변경 **0**, 사용자 조작 **⚙0.2h**:

| 단계 | 무엇 | 판정 |
|---|---|---|
| **0a** | 아무 두 런에 손으로 `bench/table` 을 하나씩 올린다(3행짜리 더미) | 올라가나 |
| ★**0b** | Workspace 에서 Custom Chart 를 만들어 **두 런을 선택**하고 `summaryTable` 을 데이터 소스로 | ★**두 런의 행이 함께 보이나** |
| **0c** | X=`task` · Y=`value` · Color=`model` · filter `metric == "acc"` | 세 축이 잡히나 |

🚫**0b 가 안 되면 §3 의 안 B 로 간다.** 그때 결정하고, **지금 미리 만들지 않는다.**

### 2.5 `summaryTable` 이 맞나

✅**맞다.** `r.summary["bench/table"] = wandb.Table(...)` 은 **최신 스냅샷 하나**만 남긴다.
`r.log({...})` 은 **history 에 append** 되어 증분 실행마다 행이 겹쳐 쌓인다(검토서 §9 의 우려 그대로).
★**우리 Table 은 `test_result/bench_results.tsv` 전체를 매번 다시 그린 것**이므로
스냅샷 하나로 충분하고, 그것이 곧 *"현재 모델의 최신 상태"* 다.

### 2.6 Summary 와 Table 의 중복·불일치 위험

| 위험 | 실제로 나나 |
|---|---|
| 값이 갈린다 | 🚫**안 난다** — §2.2 대로 같은 `rec` 한 번 순회로 둘을 만든다 |
| ★**Summary 는 이번 실행만, Table 은 누적** | ★**난다.** Summary 의 `bench/hellaswag/*` 는 **이번에 안 돌린 과제면 옛 값**이고 Table 은 TSV 전체다 |
| 스키마가 모델마다 다르다 | 🚫안 난다 — 열이 고정이다 |

→ ★**두 번째를 문서로 못 박는다**: *"Summary 는 그 런에 마지막으로 얹힌 값, Table 은 로컬 정본의
현재 스냅샷"*. **둘이 다르면 Table 이 맞다.**
