# Windows 관리 샌드박스의 Git Bash 권한 오탐 재발 방지 제안서

> 작성일: 2026-09-12  
> 대상: `.codex/check_environment.py`의 POSIX shell 문법 검사와 Windows Codex 실행 경계  
> 상태: **원인 분석 및 개선 제안만 작성**. 검사기·샌드박스·시스템 권한은 변경하지 않았다.

## 1. 결론

이번 19/20은 `.sh` 파일의 문법 실패가 아니다. **Windows 관리 샌드박스 안에서 Git for
Windows의 MSYS 런타임이 시작 중 signal pipe를 만들지 못한 실행 인프라 실패**를
`.codex/check_environment.py`가 소스 문법 실패로 잘못 분류한 것이다.

직접 확인된 인과관계는 다음과 같다.

1. 검사기는 `.sh` 5개마다 `bash.exe -n <파일>`을 조건 없이 실행한다.
2. 관리 샌드박스 안에서는 `bash --version`, `bash -c "exit 0"`, `bash -n <정상 파일>`이
   모두 파일을 읽기 전에 `couldn't create signal pipe, Win32 error 5`로 끝난다.
3. 이때 반환값은 `-1073741502`, unsigned hexadecimal로 `0xC0000142`다. 이 값은
   Windows NTSTATUS의 `STATUS_DLL_INIT_FAILED`다.
4. 같은 저장소와 같은 검사 명령을 샌드박스 밖에서 읽기 전용으로 실행하면 20/20 통과한다.
5. 현 검사기는 Bash의 모든 non-zero를 해당 `.sh`의 문법 오류 문자열에 붙인다. 따라서
   **런타임을 시작하지 못한 NOT_RUN이 소스 FAIL로 승격되는 오탐**이 생긴다.

권장안은 Git Bash 권한을 저장소 차원에서 풀거나 샌드박스를 끄는 것이 아니다. 검사기에
**Bash 1회 사전 점검과 `PASS / FAIL / NOT_RUN` 삼상 판정**을 넣고, Windows 샌드박스의
정상 경로에서는 PowerShell·Python 검사를 계속 수행하되 POSIX shell 검사는 Linux CI 또는
별도 승인된 샌드박스 밖 읽기 전용 검사로 보완하는 것이다.

쉽게 말하면, 시험지가 틀린 것이 아니라 시험 감독 도구가 켜지지 않은 상황이다. 현재 도구는
둘을 모두 “시험지 오답”이라고 기록한다. 앞으로는 도구가 켜지지 않은 경우를 별도 상태로
남겨야 한다.

## 2. 재현 증거

### 2.1 동일 입력의 경계별 결과

| 관측 | 관리 샌드박스 안 | 샌드박스 밖 읽기 전용 실행 | 해석 |
|---|---:|---:|---|
| `git --exec-path` 및 `bash.exe` 탐색 | 성공 | 성공 | Git/Bash 설치 경로 부재가 아님 |
| `bash --version` | signal pipe Error 5 | 성공 | 쉘 스크립트를 읽기 전 런타임 초기화 실패 |
| `bash -c "exit 0"` | 같은 오류 | 성공 | 명령 내용과 무관 |
| `bash -n <유효 .sh>` | 같은 오류 | 성공 | 대상 `.sh` 문법이 원인이 아님 |
| `.codex/check_environment.py` | 19/20 | 20/20 | 경계에 의존하는 검사 인프라 차이 |
| PowerShell 및 Python 검사 | 성공 | 성공 | 전체 subprocess 실행이 금지된 것은 아님 |

재현 당시 로컬 Codex는 `codex-cli 0.153.4`였다. OpenAI Codex 공개 이슈에도 같은 문구와
조건이 보고되어 있다. 해당 보고는 Windows sandbox를 켜면 Git Bash가 즉시 실패하고,
PowerShell은 작동하며, sandbox를 제거하면 다시 작동한다고 기술한다. 보고자는 0.114.0에서
작동하다 0.115.0부터 재현됐다고 기록했다. 2026-09-12 조회 시 이슈는 열린 상태다.

- OpenAI Codex issue: [Git Bash fails inside Windows sandbox with "couldn't create signal pipe, Win32 error 5"](https://github.com/openai/codex/issues/15016)
- Microsoft: [Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)
- Microsoft: [NTSTATUS 오류 코드 표](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55)

Microsoft 문서상 named pipe 생성·접속에는 호출 스레드의 access token과 DACL에 대한 접근
검사가 적용되고, 서버 인스턴스 생성에는 `FILE_CREATE_PIPE_INSTANCE` 권한이 필요하다.
이는 “signal pipe 생성에서 Win32 Error 5”라는 관측과 정합적이다.

### 2.2 검사기의 오분류 지점

현재 `.codex/check_environment.py`의 흐름은 다음과 같다.

```text
find_git_bash()
  -> git --exec-path로 C:\Program Files\Git\bin\bash.exe 탐색
  -> 각 .sh에 bash.exe -n 실행
  -> returncode != 0이면 해당 파일의 syntax error로 추가
```

문제는 두 가지다.

- Bash 실행 가능성을 먼저 검사하지 않아 같은 런타임 오류가 `.sh` 5개마다 반복된다.
- `bash -n`의 non-zero를 `문법 오류`와 `Bash 자체 시작 실패`로 구분하지 않는다.

대상 `.sh`는 `pr-workflow`의 4개와 `session-handoff`의 1개다. Windows의 실제 운영 경로는
각 스킬의 PowerShell 스크립트이며, POSIX 이식성 검사는 중요하지만 Windows 관리 샌드박스의
필수 동작 판정과 같은 칸에 합쳐서는 안 된다.

## 3. 원인 판정의 확실도

### 3.1 확인된 사실

- Bash는 대상 파일을 파싱하기 전에 실패한다.
- 실패는 관리 샌드박스 경계에 의존하고, 샌드박스 밖의 동일 검사에서는 사라진다.
- stderr가 MSYS의 signal pipe 생성 실패와 Win32 Error 5를 직접 보고한다.
- 현 검사기는 이 실행 실패를 소스 문법 FAIL로 기록한다.
- 동일 증상의 공개 Codex Windows sandbox 이슈가 존재한다.

### 3.2 근거가 강한 추론

관리 샌드박스의 제한된 Windows 보안 토큰·개체 namespace 또는 ACL과 Git for Windows의
MSYS signal 처리 초기화가 충돌한 것으로 판단한다. named pipe/유사 IPC 개체 생성 시 접근
검사가 있다는 Microsoft 설명도 이 방향을 지지한다.

### 3.3 아직 확인하지 않은 것

어느 정확한 Windows 개체 이름, ACL 또는 API 호출이 거부됐는지는 확인하지 않았다.
이를 확정하려면 Process Monitor 또는 ETW로 샌드박스 안/밖을 추적해야 한다. 이는 추가 도구
실행과 시스템 수준 관측 승인이 필요한 별도 진단이다. 따라서 이 제안서는 “특정 DACL 한 줄이
원인”이라고 단정하지 않는다. 또한 `0xC0000142`만 보고 일반적인 DLL 손상으로 진단하지 않는다.
같은 실행 파일이 샌드박스 밖에서 정상 동작하기 때문이다.

## 5. 권장 구현 계약

### 5.1 P0 — Bash 사전 점검을 한 번만 수행

`find_git_bash()` 뒤에 `probe_git_bash()`를 두고 실제 파일 검사 전에 한 번 실행한다.

```text
READY
  bash -c "exit 0" 성공

SANDBOX_UNAVAILABLE
  stderr에 "couldn't create signal pipe"와 "Win32 error 5"가 함께 있고
  return code가 0xC0000142인 알려진 Windows sandbox 증상

MISSING
  실행 파일을 찾지 못함

BROKEN
  그 밖의 시작 실패 또는 예기치 않은 결과
```

서명 문자열만 보거나 return code만 보지 않고 둘을 함께 본다. 알려진 오류와 우연히 같은
코드를 내는 다른 장애를 잘못 흡수하지 않기 위해서다.

### 5.2 P0 — 소스 결과와 검사 인프라 결과를 분리

권장 출력은 다음과 같다.

```text
[PASS] Python syntax
[PASS] PowerShell syntax
[NOT_RUN] POSIX shell syntax — Git Bash unavailable in managed Windows sandbox
[PASS] remaining environment checks

SUMMARY: PASS=19 FAIL=0 NOT_RUN=1
```

판정 규칙은 다음과 같다.

- Bash가 `READY`이고 `bash -n`이 특정 파일에서 non-zero이면 **소스 FAIL**이다.
- 알려진 sandbox 초기화 실패이면 **인프라 NOT_RUN**이다. PASS도 FAIL도 아니다.
- Bash가 없으면 **NOT_RUN**이다.
- 알 수 없는 Bash 실행 실패이면 **인프라 FAIL**이다. 파일명별 문법 FAIL로 복제하지 않는다.
- 전체 검사 기본 exit는 `FAIL > 0`이면 1, `NOT_RUN > 0`이면 2, 모두 통과면 0을 권장한다.
- CI나 릴리스 게이트는 `--require-shell-syntax`를 사용해 NOT_RUN을 허용하지 않는다.

현재 `Ledger`가 boolean만 받는다면 즉시 boolean에 NOT_RUN을 억지로 넣지 말고 enum 또는
별도 `record_not_run()`을 추가한다. 상태 이름이 출력·요약·exit code까지 일관돼야 한다.

### 5.3 P1 — 호스트별 검증 경로를 명시

- Windows 관리 샌드박스: Python·PowerShell·구조·훅 검사를 정식 실행한다.
- Linux CI 또는 GitHub Actions: `.sh` 전체에 `bash -n`을 필수 실행한다.
- 로컬 Windows에서 사용자가 추가 증거를 원할 때만: 정확한 읽기 전용 명령을 제시하고
  샌드박스 밖 실행 승인을 받아 POSIX 검사를 보완한다.
- 문서에는 “Windows 19 PASS + shell NOT_RUN + Linux/외부 shell PASS”처럼 증거 출처를
  나눠 기록한다. 어느 한쪽을 합쳐 단순 20/20로 축약하지 않는다.

### 5.4 P2 — 선택적 네이티브 parser

Linux CI를 즉시 쓸 수 없다면 Windows 네이티브 `shfmt` 또는 tree-sitter-bash를 보조 검사로
검토한다. 단, 설치·다운로드와 버전 고정은 별도 승인 사항이다. 네이티브 parser PASS는 실제
Git Bash 실행 PASS와 같은 증거가 아니므로 `NATIVE_PARSE_PASS`처럼 출처를 남긴다.

## 6. 회귀 테스트

| # | 조건 | 기대 결과 |
|---:|---|---|
| 1 | 사용 가능한 Bash + 유효 `.sh` | POSIX syntax PASS |
| 2 | 사용 가능한 Bash + 고의 문법 오류 | 해당 파일만 source FAIL |
| 3 | Bash 미설치 | NOT_RUN 1회, 파일별 오류 반복 없음 |
| 4 | signal pipe Error 5 + `0xC0000142` 모의 응답 | SANDBOX_UNAVAILABLE / NOT_RUN 1회 |
| 5 | Bash의 그 밖의 시작 실패 | infrastructure FAIL 1회, source FAIL 아님 |
| 6 | POSIX NOT_RUN 상태에서 Python·PowerShell 오류 | 각 실제 오류는 독립 FAIL로 유지 |
| 7 | `--require-shell-syntax` + NOT_RUN | 비성공 exit로 CI 게이트 차단 |
| 8 | 샌드박스 밖 동일 정상 파일 | POSIX syntax PASS |

테스트는 subprocess runner를 주입하거나 mock하여 시스템 ACL을 바꾸지 않고 수행한다. 실제
Git Bash E2E는 Windows sandbox 안과 밖을 각각 한 번만 관측하고, 밖 실행은 사용자 승인
아래 읽기 전용으로 제한한다.

## 8. 적용 순서와 종료 기준

1. 검사기 ledger를 삼상 상태로 확장한다.
2. Bash 1회 사전 점검과 오류 분류를 추가한다.
3. 위 8개 회귀 테스트를 추가한다.
4. 관리 샌드박스 안에서 `FAIL=0, NOT_RUN=1`을 확인한다.
5. 승인된 샌드박스 밖 또는 Linux CI에서 같은 `.sh` 5개가 PASS인지 확인한다.
6. 두 증거를 분리한 상태로 환경 문서를 갱신한다.

종료 기준은 “오류 문구가 사라짐”이 아니다. 다음 네 조건을 모두 만족해야 한다.

- 유효 `.sh`를 Windows sandbox 결함 때문에 source FAIL로 보고하지 않는다.
- shell 검사를 실제로 못 했는데 PASS라고 하지 않는다.
- 실제 `.sh` 문법 오류는 Bash 사용 가능 환경에서 계속 차단한다.
- 샌드박스·시스템 ACL·Git 설치 권한을 저장소 작업 편의를 위해 완화하지 않는다.

## 9. 사용자에게 권장하는 당장 운용법

구현 전에는 Windows 관리 샌드박스 안의 19/20을 **“환경 전체 실패” 또는 “`.sh` 문법
실패”라고 해석하지 말고**, 다음처럼 기록하는 것이 정확하다.

```text
Windows managed sandbox: 19 PASS, POSIX shell syntax NOT_RUN
Approved read-only external check: 20/20 PASS
Active hook E2E: 별도 관측 결과로 기록
```

Git Bash를 쓰기 위해 sandbox를 상시 해제하거나 시스템 ACL을 바꾸는 조치는 권장하지 않는다.
PowerShell 경로로 작업을 유지하고, 꼭 필요한 POSIX 검증만 좁은 읽기 전용 승인 또는 Linux
CI에서 보완한다.
