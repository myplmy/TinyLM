# 제안 — 동일 WIP 연속 작업에서 핸드오프를 여러 번 신설하지 않도록 한다

> **작성** 2026-09-23 · **상태** ⏳판단 대기 · **분류** 작업방식 / 핸드오프 / 인계
> 양식: [proposal/README.md](README.md) §3. 이번에는 **제안서만** 작성한다. 생성기·스킬·기존 핸드오프 파일의 소급 수정/삭제는 이 승인 전 범위가 아니다.

## 1. 배경 — 실제 재발과 직접 원인

같은 열린 [WIP](../handoff/WIP_20260923_작업원장.md)가 계속 존재하는 동안
[05:21 메모](../handoff/202609230521_HANDOFF.md),
[13:05 메모](../handoff/202609231305_HANDOFF.md),
[14:10 메모](../handoff/202609231410_HANDOFF.md)가 차례로 생성됐다.
사용자의 중간 지시는 “중단된 작업 이어서” 또는 “작업원장 및
세션핸드오프메모에 이어서 작업”이었지, 매 진행 턴마다 **새 최종
핸드오프를 만들라는 지시**가 아니었다. 따라서 파일마다 내용이
틀렸다는 주장보다 **새 파일 생성의 시점·횟수가 사용자 의도와
어긋난 것**이 정확한 사고다.

직접 원인은 둘이 결합됐다.

1. AI가 ‘이전 핸드오프를 읽고 이어간다’를 ‘이번 턴 종료 때 또 하나
   만든다’로 잘못 확장했다. 진행 상태는 WIP로 갱신하면 되는데
   종료 스냅샷인 handoff를 진행 로그처럼 사용했다.
2. [session-handoff 스킬](../.agents/skills/session-handoff/SKILL.md)은
   ‘종료·중단·이전 요청’을 트리거로 쓰지만, **동일 열린 WIP에
   이미 이번 논리 작업의 handoff가 있는 경우의 재호출 차단**은 없다.
   [new_handoff.py](../scripts/new_handoff.py)는 매 호출마다 현재
   분의 새 이름을 만들고 최신 메모를 이전으로 잇는다. 같은 분
   덮어쓰기만 막으며 같은 WIP·논리 작업의 두 번째 생성은 막지 않는다.

후속 메모들이 현재 큐 정보를 `UNVERIFIED`로 재계승하는 구조라
내용이 늘고 사용자는 어느 스냅샷이 종료판인지 판단해야 한다.
이는 길이·탐색비용·잘못된 최신성의 문제다. 세 파일은 역사 증거이므로
이 제안만으로 삭제하거나 하나로 기계 병합하지 않는다.

## 2. 목적 — 어떤 계약을 바꾸나

**진행 중 동일 논리 작업은 WIP만 갱신하고, 실제 인계·중단 또는
사용자가 현재 요청에서 명시한 최종 핸드오프 때만 정확히 한 번
새 메모를 만든다.** 새 요청의 시작과 단순 계속 지시를 구분한다.

## 3. 성과물 — 승인하면 무엇이 생기나

| 산출물 | 완료 기준 |
|---|---|
| Codex 02·session-handoff 트리거 규칙 | “읽고 이어서”는 새 파일 승인 아님, 같은 WIP 진행 턴의 종료 전 자동 신설 금지, 최종 스냅샷 시점 정의 |
| 생성기 dry-run 안전 게이트 | 열린 WIP의 session ID/진행상태/최근 동일 WIP handoff를 확인해 중복 경고. 새 최종 메모가 명시된 때만 생성 허용 |
| WIP↔handoff 연결 필드 | 기존 WIP가 어느 handoff를 인계했는지 단일 포인터/마지막 생성 시각; 신규 세션에서 역추적 가능 |
| 회귀 fixture | 단순 계속→신설 0, 명시 최종 인계→1, 같은 WIP 재호출→경고·기본 거부, 다른 소유 세션은 손대지 않음 |
| 기존 세 파일 처리 | 역사 파일 보존, 최신 유효 chain과 각 파일의 역할을 한 번 판독. 자동 삭제·이름 변경 없음 |

| 항목 | 양 |

## 5. 원리·근거

현재 WIP v2는 작업 중 항목 상태·이어받을 지점과 append-only 작업 로그를
소유하고, handoff는 종료·중단·이전의 스냅샷이다([Codex 02](../ai_dev_tool/Codex/02_핸드오프_규약.md),
[WIP 스킬](../.agents/skills/wip-ledger/SKILL.md)). 생성기는 한 번 호출되면
날짜·시각에 따라 새 파일을 만드는 도구라, 이를 빈번한 중간 상태 갱신에
사용하면 세 파일처럼 사슬만 길어진다.

**추론**: 같은 WIP의 이전 handoff는 새 최종판의 기준이 될 수 있어야
하지만 매 실행 턴의 자동 출력 대상은 아니다. 따라서 판단은 AI의
“끝났을 것 같다”가 아니라 **사용자 명시 인계/중단/종료 지시 또는
정말 종료되는 턴의 단일 최종화 호출**로 고정하고, 도구가 동일 WIP
중복 호출을 추가로 감시하는 이중 안전장치를 둔다.

## 6. 방법 — 두 층에서 재발을 막는다

| 단계 | 작업 | 게이트 |
|---|---|---|
| H0 | 세 파일의 최초 존재 시각·이전 체인·WIP 연결을 문서 읽기로 확인, 현 파일 보존 | 어느 것도 자동 삭제/병합하지 않음 |
| H1 | 스킬·Codex 02에 `CONTINUE`(WIP 갱신만), `FINAL_HANDOFF`(새 파일 1건), `RECOVERY_READ`(읽기만) 분기와 사용자 문구 예시 추가 | “이어서 작업” fixture에서 신설 0 |
| H2 | `new_handoff.py`에 동일 WIP/session 기준 중복 경고와 명시 최종화 플래그를 설계. dry-run 먼저, force는 사유·승인 참조 필수 | 명시 최종화 1건, 재호출 기본 거부 |
| H3 | 핸드오프 린터에 WIP item 수·정적 감사 링크·chain 검증은 유지하고 중복 상태 진단을 추가 | 구 handoff는 역사 예외, 신규 계약만 강제 |
| H4 | 한 논리 작업에서 계속→결과회수→최종 인계 시나리오를 fixture로 재현 | handoff 1개, WIP 상태 누락 0, 다른 세션 파일 수정 0 |

이번 사용자 요청은 **명시적으로 세션 핸드오프 작성**을 포함하므로
작업 종료 시 현재 요청용 한 개를 생성한다. 그 전에 WIP만 갱신한다.
앞선 세 핸드오프는 과거 인계 기록으로 남긴다.

## 7. 거절하면 못 하는 것

WIP·handoff를 사람이 조심해도 작업은 계속할 수 있다. 다만 같은
“이어서 작업” 지시를 AI가 또 최종 인계로 오독하면 같은 WIP에
새 타임스탬프 메모가 계속 붙을 수 있고, 도구가 이를 막지 못한다.

## 8. 위험 — 무엇을 잘못 막을 수 있나

| 위험 | 계측에서 어떻게 드러나나 | 완화 |
|---|---|---|
| 실제 중단 전 인계 거부 | 명시 중단 요청인데 동일 WIP 중복으로 오탐 | 명시 `FINAL_HANDOFF`/사유로 1회 허용, 무조건 차단 아닌 상태 분기 |
| 세션 ID 부재·다른 세션 소유 | 잘못된 WIP를 현재 것으로 추정 | ID exact-match 없으면 fail-closed 경고, 다른 원장 손대지 않음 |
| 생성기 결합 범위 과대 | 큐/로그까지 뒤져 간섭 | WIP header·최신 handoff link만 조회, 실험 파일 접근 금지 |
| 역사 문서 소급 오류 | 기존 파일에 새 규칙을 적용해 false FAIL | 도입 시점 이후 생성분만 강제, 과거 3건은 이력 보존 |
| WIP가 길어짐 | handoff를 줄인 대신 원장 셀에 전문 적재 | 6열 한 줄 최신 상태·append-only 로그를 유지, 정적 감사/결과는 별도 파일 |

## 9. 대안

| 안 | 내용 | 장점 | 단점·영향도·비용 |
|---|---|---|---|
| A | AI가 스킬 문구만 기억해 조심 | 구현 비용 낮음 | compact/연속 턴에서 재발 가능, 검증 약함 |
| **B** | 트리거 분기 + 동일 WIP 생성기 중복 게이트 | 사용자의 계속/최종 의도를 도구까지 보존 | 스킬·생성기·fixture 변경 ⚙2~4h |
| C | 기존 최신 handoff를 매 턴 덮어쓰기 | 파일 수가 늘지 않음 | 역사·최초 존재 증거·이전 체인 손상, 복구성 저하 |

### 권장안

**B를 권장한다.** 이번 작업에서는 도구를 변경하지 않고
**핸드오프는 요청 종료 직전에 한 번만** 생성한다.
승인되면 H0~H4를 별도 구현하되, 기존 세 파일은 삭제하지 않는다.
