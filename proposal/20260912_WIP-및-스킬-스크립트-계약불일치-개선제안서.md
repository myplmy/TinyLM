# WIP 및 스킬-스크립트 계약 불일치 개선제안서

> 작성일: 2026-09-12  
> 범위: `.agents/skills/**/SKILL.md` 17개와 그 문서가 명시적으로 호출하는 저장소·번들 스크립트  
> 상태: **제안만 작성**. 이 문서 작성 시 스킬·스크립트 구현은 변경하지 않았다.

## 1. 결론

문서와 현행 코드 중 하나를 기계적으로 정본으로 고르는 방식은 부적합하다. 두 쪽이 서로
다른 필수 정보를 갖고 있기 때문이다.

- 현행 `scripts/wip.py`가 보존한 고유 정보: 상태 변경 때 누적되는 **`작업 내용`**과 최종 **`산출물`**.
- `wip-ledger/SKILL.md`가 보존한 고유 정보: 중단 뒤 첫 행동을 구조화한 **`이어받을 지점`**.

따라서 권장 정본은 둘의 합집합인 **6열 v2**다.

```text
# | 지시 | 상태 | 작업 내용 | 산출물 | 이어받을 지점
```

각 셀은 한 줄 최신 요약만 두고 `<br>`을 넣지 않는다. 상세 착수·완료 이력은 표 아래
append-only 작업 로그가 소유한다. 이 설계는 현재 코드의 감사 이력과 기존 스킬의 재개 정보를
모두 보존한다.

현재 `scripts/wip.py`는 다음 5개 열을 계약으로 삼는다.

```text
# | 지시 | 상태 | 작업 내용 | 산출물
```

반면 스킬은 다음 열을 만들라고 지시한다.

```text
# | 지시 | 상태 | 산출물 | 이어받을 지점
```

두 표는 열 개수가 같아서 도구가 오류를 내지 않는다. 그 대신 스킬식 `산출물`을 도구가
`작업 내용`으로, `이어받을 지점`을 `산출물`로 해석한다. 따라서 **조용한 의미 뒤바뀜**이다.

권장 이행은 다음과 같다.

1. 사용자 승인 전에는 스킬·스크립트를 바꾸지 않는다.
2. 승인 뒤 스킬·생성기·파서를 한 변경 묶음에서 6열 v2로 정합한다.
3. `wip.py`는 헤더 의미와 스키마 버전을 검사하고 레거시 파일은 읽기 전용으로만 연다.
4. 과거 원장은 일괄 재작성하지 않는다.

쉽게 말하면, **코드가 실제로 쓰고 있다는 사실은 현상 증거이지 자동 정본 승인으로 볼 수 없고,
문서에 먼저 적혀 있다는 사실도 다른 정보를 버릴 근거가 아니다.** 사용자 요구와 정보 무손실을
충족하는 새 계약을 승인받아 두 쪽을 함께 맞추는 것이 정합 기준이다.

## 2. 재현 근거

### 2.1 주 불일치

| 근거 | 관측 |
|---|---|
| `.agents/skills/wip-ledger/SKILL.md` 템플릿 | `# / 지시 / 상태 / 산출물 / 이어받을 지점` |
| `scripts/wip.py:77,110` | `# / 지시 / 상태 / 작업 내용 / 산출물`로 해석 |
| `scripts/wip.py:123~136` | `--note`는 4번째 업무 열에 누적하고 `--artifact`는 5번째 업무 열을 덮어씀 |
| 현행 열린 원장 | `handoff/WIP_20260912b_작업원장.md`는 스크립트형 헤더를 사용 |
| 레거시 재현 | `python -X utf8 scripts/wip.py --list --file handoff/WIP_20260911c_작업원장-done.md`가 실제 산출물 경로를 작업 노트처럼 인쇄 |

핵심 원인은 `wip.py`가 **열 개수만 검사하고 헤더 의미는 검사하지 않는 것**이다. 두 스키마가
모두 5열이므로 파싱은 성공하지만 의미가 틀린다. 이는 단순 표시 문제가 아니다. 레거시 원장에
`--done --note ... --artifact ...`를 실행하면 두 열을 원래 뜻과 다르게 갱신한다.

### 2.2 저장소 안의 혼재

`handoff/WIP_*_작업원장*.md` 헤더를 전수 검색한 결과 세 형태가 공존한다.

- 구형: `상태 | 산출물 | 이어받을 지점`
- 신형: `상태 | 작업 내용 | 산출물`
- 더 오래된 최소형: `상태`까지만 존재

따라서 과거 파일을 한꺼번에 새 스키마로 바꾸는 것은 기록 보존 원칙과 맞지 않는다. 도구가
스키마를 식별하여 읽기와 쓰기 권한을 달리하는 편이 안전하다.

| 순위 | 기준 | 이번 판단 |
|---:|---|---|
| 1 | 사용자의 직접 요구와 승인 범위 | `<br>` 없는 가독성, 중단 후 재개, 승인 전 미구현을 모두 만족해야 함 |
| 2 | 의미 소유권 | WIP는 현재 상태뿐 아니라 작업 이력과 다음 행동을 함께 소유함 |
| 3 | 정보 손실 | A는 작업 이력, B는 재개 지점을 잃으므로 둘 다 단독 정본으로 부족함 |

이 기준에 따라 **의미 정본은 승인된 6열 v2 사양**, 구현 정본은 그 사양을 통과하는
`SKILL.md`·생성기·파서·검사기의 동시 버전으로 정한다. 어느 한 파일을 먼저 고쳐 다른 파일을
일시적으로 틀리게 만드는 순차 배포는 하지 않는다.

## 4. 권장 상세 변경

### 4.1 `wip-ledger/SKILL.md` — 승인 후 P0

- 템플릿 헤더를 `| # | 지시 | 상태 | 작업 내용 | 산출물 | 이어받을 지점 |`으로 변경한다.
- `작업 내용`에는 `wip.py --note`가 최신 한 줄 요약을 쓰고, 착수·완료 전체 이력은 표 아래
  append-only 작업 로그에 남긴다고 명시한다.
- `산출물`에는 `--artifact`가 최종 경로를 기록한다고 명시한다.
- `이어받을 지점`에는 완료 항목이면 `—`, 진행·막힘·대기 항목이면 **다음 한 행동**을 적는다.
- 표 셀에는 `<br>`을 쓰지 않고 한 줄 최신 요약만 둔다. 상세 이력은 별도 작업 로그에 쓴다.
- 상태 변경 예시는 항상 선택한 원장을 `--file`로 명시한다. 현재 기본 동작은 열린 원장이
  여러 개면 사전순 마지막 파일을 고르므로, 동시 작업에서 엉뚱한 원장을 바꿀 수 있다.
- 같은 날짜의 두 번째 원장을 수동 고정명으로 덮어쓰지 않도록 고유 접미사 규칙 또는
  `wip.py --new` 생성 기능을 후속 도입한다.

### 4.2 `scripts/wip.py` — 승인 후 P0 방어 보강

- 상황판 헤더를 찾아 `작업 내용`, `산출물`, `이어받을 지점`의 정확한 위치를 검증한다.
- `--resume` 또는 동등한 명시 인수로 6번째 열을 갱신하고, 완료 시 `—`로 정규화한다.
- `--note`는 표 셀을 `<br>`로 누적하지 않고 최신 한 줄로 교체하며, 전체 이력은 작업 로그에 append한다.
- 구형 헤더는 `--list`만 허용하고 출력 첫 줄에 `LEGACY_READ_ONLY`를 표시한다.
- 구형·최소형 원장에 대한 `--start/--done/--block/--wait/--close`는 명시적 오류로 중단한다.
- 열 개수뿐 아니라 헤더 스키마 버전도 검사하는 단위 테스트를 추가한다.
- 여러 열린 원장이 있으면 기본 선택을 하지 말고 `--file`을 요구하는 편이 안전하다.

### 4.3 과거 원장 — 수정하지 않음

과거 완료 원장은 당시 기록이다. 헤더를 소급 변환하면 해시·감사 이력이 달라지고, 열 내용이
어느 의미로 작성됐는지 자동 판정하기도 어렵다. 새 도구가 레거시를 읽기만 하도록 한다.

## 6. 구현 순서와 수용 기준

### 단계 0 — 사용자 승인

이 문서의 권장안 C와 정확한 변경 파일 목록을 사용자가 승인해야 한다. **제안서 수정 지시는
스킬·스크립트 구현 승인으로 해석하지 않는다.** 승인 전 구현 변경의 수용 기준은 0건이다.

### 단계 1 — v2 계약 동시 정합

1. `wip-ledger/SKILL.md` 템플릿·예시 수정
2. `wip.py`의 v2 파서·쓰기·레거시 거부를 같은 변경 묶음에 추가
3. 새 원장 생성 경로와 테스트 fixture를 v2로 동기화

수용 기준: 스킬에 나온 모든 명시 경로가 존재하고, 새 WIP 템플릿으로 만든 표에서
`--start`, `--done --artifact`, `--list`, `--close`가 의도한 열만 바꾼다.

### 단계 2 — 도구 방어와 회귀 검사

1. `wip.py` 헤더 검증과 레거시 읽기 전용 모드
2. 복수 열린 원장일 때 `--file` 강제
3. `<br>` 생성 금지와 작업 로그 append-only 검사

수용 기준:

- 신형 표: 상태 변경 성공
- 구형 표: 목록 조회 성공 + 상태 변경 거부
- 최소형 표: 명시적 스키마 오류
- 이스케이프 파이프, `2A` 같은 번호, 상황판 밖 유사 표에 대한 기존 회귀 테스트 유지
- 열린 항목이 있으면 `--close` 거부

### 단계 3 — 별도 승인 대상

`session-handoff`, `run-batch`, 다른 스킬·스크립트의 감사 발견은 이 WIP 계약 구현과 묶지 않는다.
각 파일의 수정 필요성과 테스트 범위를 별도로 승인받는다. 기존 완료 원장의 소급 변환은 하지 않는다.

## 8. 최종 판정

- **주 질문:** 문서나 현행 코드 어느 한쪽을 그대로 정본으로 삼지 않는다. 양쪽 고유 정보를 보존한
  6열 v2 계약을 새 정본 후보로 삼는다.
- **동시 필수 방어:** 승인 뒤 스킬·생성기·파서·검사를 한 변경 묶음으로 정합하고,
  `<br>` 없는 단일행 표와 append-only 로그를 강제한다.
- **하지 않을 것:** 과거 완료 WIP 일괄 변환, 상태 의미를 구형 템플릿에 맞추는 역행,
  정적 통과만으로 Codex 환경 E2E 완료 선언, **사용자 승인 전 스킬·스크립트 수정**.

## 9. 대안과 승인 요청

- **권장안 C:** 6열 v2. 정보 손실이 없고 WIP의 감사·재개 목적을 함께 충족한다.
- **대안 B:** 현행 5열을 유지하고 `이어받을 지점`은 작업 로그에만 둔다. 구현량은 작지만 다음
  세션이 표만 보고 재개하기 어렵다.
- **대안 A:** 스킬의 구형 5열로 회귀한다. `작업 내용`을 잃으므로 권하지 않는다.

현재 상태는 **제안 대기**다. 사용자가 권장안과 변경 파일을 승인하기 전까지
`.agents/skills/**`, `scripts/wip.py` 및 관련 생성기·검사기는 수정하지 않는다.
