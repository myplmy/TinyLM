# `ai_dev_tool` 문서 갱신일자·메타데이터 검증 제안서

> **실험번호**: `PNone`

## 1. 배경

`ai_dev_tool`에는 현재 규약처럼 계속 갱신되는 문서, 특정 시점의 감사 보고서, 승인 전 검토
초안이 함께 있다. 이들을 모두 파일 수정시각 하나로 판정하면 Git checkout·복사만으로 날짜가
바뀌는 오탐이 생기고, 반대로 아무 검증도 하지 않으면 문서 상단 날짜가 실제 내용보다 낡는다.

실사한 55개 문서는 다음 세 유형으로 나뉜다.

| 유형 | 수 | 정책 |
|---|---:|---|
| 살아 있는 정본 | 23 | 상단 `최신 갱신일자` 필수, 엄격 검증 대상 |
| 검토 초안·분석 산출물 | 6 | `작성일`과 `상태` 필수, 수정 때 선택적으로 `최종 수정일` 추가 |
| 시점 고정 보고·이식 증거 | 26 | `기준일/작성일` 유지, 현재 날짜로 강제 갱신하지 않음 |

## 2. 목적

문서 유형에 맞는 날짜 의미를 먼저 선언하고, 살아 있는 정본의 상단 날짜가 실제 변경 증거와
어긋날 때만 오류를 내는 단일 검증 계약을 만든다.

## 3. 성과물

승인하면 다음이 생긴다.

1. 실행 때 `ai_dev_tool/**/*.md`를 직접 순회해 만드는 자동 인벤토리(별도 파일 목록 없음).
2. 각 문서가 스스로 선언하는 유형·날짜 메타데이터와, 유형 규칙·pair 예외만 가진 작은 정책 파일.
3. 살아 있는 정본 23개 상단의 표준 메타데이터.
4. 문서 날짜·Git 변경 증거·선택적 로컬 mtime을 파일별로 직접 대조하는 정적 검사기 1개.
5. 누락·미래 날짜·파싱 불가·정본 간 날짜 드리프트·신규 파일 무등록을 잡는 fixture.
6. 기존 Codex 환경 검사에는 Codex 소유 11개만 연결하고, Claude 문서는 런타임 지침으로 읽지 않는 경계.

## 4. 비용

- 55개 분류 재검토와 manifest 작성: 약 1.0 engineer-hour.
- 살아 있는 정본 23개 메타데이터 추가: 약 1.0 engineer-hour.
- 검사기와 fixture: 약 1.5 engineer-hour.
- GPU·학습·모델·데이터셋 비용: **0**.
- 사용자 작업: 정책 및 정확한 변경 allowlist 승인 1회.

## 5. 원리·근거

파일시스템 mtime은 내용 정본이 아니다. Git checkout, 압축 해제, 파일 복사, 복원 도구가 내용
변경 없이 mtime을 바꿀 수 있다. 따라서 다음 세 값을 분리해야 한다.

- **문서 선언일**: 작성자가 의미 변경을 완료했다고 선언한 날짜.
- **Git 내용 변경일**: 추적 파일의 마지막 내용 커밋 날짜. 저장소 간 재현 가능한 증거.
- **로컬 mtime**: 현재 작업공간에서 마지막로 기록된 시각. 사용자가 요구한 로컬 드리프트 검사에
  유용하지만 checkout 오탐 가능성이 있는 환경 증거.

작업규약 영문·한글판처럼 두 문서가 같은 규칙을 소유하면 날짜와 분류 개수까지 동일해야 한다.
반면 P7/P8 보고서나 20260909 보고서는 과거 관찰 증거이므로 오늘 mtime과 맞추려고 본문 날짜를
바꾸면 역사가 왜곡된다.

### 6.2 작성일·상태 대상 6개

유형 선언이 없으면 실패한다.

않는다. 후속 정정은 원문 날짜를 바꾸기보다 정정일을 별도 필드로 추가한다.

### 6.4 검사기 수정안 B2 — 파일 인벤토리는 직접 발견하고 정책만 작게 둔다

`scripts/check_doc_metadata.py`와 `docs/doc_metadata_policy.tsv`를 제안하되, TSV에는 **파일 목록을
넣지 않는다.** 검사기는 매 실행마다 `ai_dev_tool/**/*.md`를 직접 순회한다. 각 Markdown 머리말의
`문서 유형: live|draft|snapshot`이 파일별 분류 정본이고, TSV는 유형별 필수 날짜 필드와 이름만으로
도출할 수 없는 영문·한글 pair 예외처럼 드물고 안정적인 규칙만 가진다.

```text
type | required_date_field | git_policy | mtime_policy
pair_pattern | paired_pattern | required_equal_fields | pair_reason
```

검사기는 다음을 오류로 낸다.

1. 직접 발견한 Markdown의 `문서 유형`·해당 날짜 필드 누락, 중복, 파싱 오류, 미래 날짜.
2. `live` 문서의 상단 `최신 갱신일자`가 파일별 Git 내용일보다 과거인 상태.
3. 영문·한글 pair의 선언일 또는 함께 검증하도록 정한 개수 필드 불일치.
4. `--local-mtime-warn`에서 선언일과 로컬 mtime 달력 날짜 불일치(경고).
5. `--local-mtime-strict`에서 같은 불일치(오류).
6. 정책 TSV에 같은 유형·pair 규칙이 중복되거나 존재하지 않는 고정 pair를 가리키는 상태.

Git 내용일도 목록에서 복사하지 않고 각 발견 파일에 `git log -1 --format=%cs -- <path>`를 직접
실행해 얻는다. 다만 아직 커밋하지 않은 dirty 파일에는 “마지막 커밋일”만으로 이번 수정일을 알 수 없다.
따라서 dirty 파일은 선언일의 형식·미래 여부를 검사하고 `--as-of YYYY-MM-DD`가 주어진 검토 실행에서
선언일이 그 날짜보다 과거면 오류를 낸다. mtime은 보조 증거일 뿐 기본 실패 근거로 쓰지 않는다.

mtime 검사는 checkout 오탐 가능성이 있으므로 로컬 엄격 모드에서 명시적으로 사용한다.
CI 정본 판정은 문서 자체 메타데이터·직접 발견 인벤토리·Git 내용 변경일을 우선한다. 이번 사용자 지시로 이미 구현한 Codex
작업규약 두 판은 환경 검사에서 로컬 mtime까지 엄격 비교하는 좁은 예외다.

2. 읽기 전용 discovery 모드로 현재 Markdown 전수를 나열하고 머리말 없는 파일을 보고.
3. 유형 규칙·pair 예외만 담은 작은 정책 TSV와 fixture를 먼저 구현.
4. 23개 live 문서 머리말 추가. 새 파일 음성 fixture가 정책 TSV 수정 없이도 누락으로 잡히는지 확인.
5. 정상·누락·불일치·dirty·checkout-mtime fixture 검사.
6. Codex 검사에는 Codex 11개만 연결하고 루트 Claude 00~08은 활성 지침으로 읽지 않음.

## 7. 거절하면 못 하는 것

문서 자체는 계속 수동 갱신할 수 있다. 다만 어떤 파일이 살아 있는 정본인지, 상단 날짜가
낡았는지, 시점 고정 보고서를 잘못 “최신화”했는지를 한 명령으로 판별할 수 없다.

## 8. 위험

| 위험 | 통제 |
|---|---|
| checkout만으로 mtime 오류 | mtime은 로컬 엄격 모드, Git 내용일은 재현 가능한 기준으로 분리 |
| 역사 보고서 날짜 덮어쓰기 | `snapshot`은 작성일 형식만 검사하고 현재 날짜 강제 금지 |
| Codex가 Claude 문서를 환경 지침으로 읽음 | 검사기는 바이트·메타데이터만 파싱하고 명령으로 해석하지 않음; Codex 환경 연결은 Codex 11개로 제한 |
| 55개 일괄 패치 중 사용자 변경 충돌 | 단계별 allowlist와 파일별 diff, 광범위 치환 금지 |
| 날짜만 맞고 내용 정합은 틀림 | 날짜 검사는 내용 검토를 대체하지 않으며 `STATIC_ONLY`로 표기 |

## 9. 대안과 권장안

| 안 | 장점 | 단점 |
|---|---|---|
| A. 모든 파일 mtime 엄격 일치 | 단순함 | checkout 오탐과 역사 왜곡이 큼 |
| B. 파일별 전체 manifest + Git 내용일 + 선택적 mtime | 유형을 한 표에서 볼 수 있음 | 새 파일마다 manifest도 고쳐야 해 동일한 누락이 재발할 수 있음 |
| **B2. 런타임 직접 순회 + 문서 자기선언 + 작은 정책 규칙 + Git 내용일 + 선택적 mtime** | 새 파일이 자동 검사되고 목록 정본이 하나 늘지 않음 | 기존 문서 머리말 이행과 pair 예외 규칙은 필요 |
| C. 문서 날짜만 수동 관리 | 구현 0 | 누락과 pair 드리프트를 자동 검출 못 함 |

**수정 권장안은 B2**다. 사용자가 제안한 “각 파일 직접 순회”가 전체 경로 manifest보다 누락에
강하다. 다만 파일 유형을 이름만으로 추측하면 검토 초안·시점 보고서를 잘못 최신화할 수 있으므로,
각 문서가 유형을 자기 선언하고 작은 정책 파일은 유형 규칙과 pair 예외만 소유한다. 이 정책 파일을
갱신하지 않아도 새 Markdown은 자동 발견되어 유형 머리말 누락으로 실패한다. 이 문서는 구현 승인이
아니며, 사용자 승인 전에는 23개 문서 일괄 수정이나 새 검사기·정책 파일을 작성하지 않는다.

## 10. B2 승인·구현 기록 — 2026-09-13

사용자가 B2를 승인해 다음 범위만 단계적으로 구현했다. 위 9절 끝의 “승인 전” 문구는 역사적
게이트로 보존하며 현재 상태는 이 절이 우선한다.

1. `docs/doc_metadata_policy.tsv`에는 세 유형의 필드·Git·mtime 정책과 영문/한글 pair 두 쌍만
   두었다. 55개 파일 경로 목록은 두지 않았다.
2. `scripts/check_doc_metadata.py`가 실행 때마다 `ai_dev_tool/**/*.md`를 직접 발견한다. 새 파일은
   TSV 수정 없이도 문서 유형 누락으로 실패한다.
3. live 23개, draft 6개, snapshot 26개에 유형별 머리말을 이행했다. snapshot의 역사 날짜는
   현재 날짜로 덮지 않았다.
4. Git 내용일, dirty `--as-of`, 미래 날짜, pair 날짜·Codex 규칙 분류 개수, 선택적 mtime
   warn/strict를 분리했다. root Claude 문서는 바이트 메타데이터만 검사하며 Codex 지침으로 읽지 않는다.
5. `scripts/check_static_all.py`의 정적 게이트에 연결했다. 전용 회귀 5/5, 전수 55/55,
   Codex 범위 14개(그중 live 11), local-mtime strict 55/55를 통과했다.

이 판정은 문서 머리말과 정적 검사 계약에 대한 `STATIC_ONLY`다. 날짜가 맞는다는 사실이 본문 최신성이나
의미 정합을 증명하지 않으며, 전체 `check_static_all.py`와 사용자 스모크를 실행했다는 뜻도 아니다.
