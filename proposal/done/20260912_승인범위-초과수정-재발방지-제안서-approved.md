# 승인범위 초과 수정 재발방지 제안서

> 작성일: 2026-09-12 · 갱신일: 2026-09-14  
> 상태: **사용자 C안 승인 / 규약·스킬·범위검사 구현 완료 / 실제 변경목록 감사 PASS**
> 계기: Codex 오류원장 A21
> **실험번호**: `PNone`
> **실험계획 비대상 사유**: 파일별 변경 권한과 범위검사를 다룬 작업방식 제안이며 학습 실험이 아니다.

## 1. 배경

사용자는 스킬 이식의 적합성을 **검토**하고 기존 개선제안서를 **수정·증보**하라고 했다.
Codex는 이를 권장안을 실제 스킬과 `scripts/wip.py`에 적용해도 된다는 뜻으로 확대 해석했다.
사용자 지적 뒤 이번 세션이 만든 변경은 모두 원복했지만, “기술적으로 맞는 수정”과
“사용자가 허가한 수정”을 별개 게이트로 두지 않은 절차 오류가 드러났다.

## 2. 목적

파일을 고치기 전에 각 파일의 쓰기 권한 근거를 명시적으로 대조하여, 검토·제안 요청이
스킬·도구 구현 승인으로 승격되는 일을 막는다.

## 3. 성과물

승인 시 다음 세 가지를 만든다.

1. 작업 착수 보고의 `변경 허용목록`에 파일별 권한 근거를 붙이는 표준 양식
2. 환경 동작 파일(`.agents/skills/**`, `.codex/**`, 관련 생성기·검사기)의 별도 승인 게이트
3. 패치 직후 대상별 diff를 확인해 허용목록 밖 변경을 즉시 중단하는 점검 항목

이 제안서 자체는 위 자동화나 스킬 변경을 수행하지 않는다.

## 4. 비용

- GPU·모델·데이터·디스크 비용: 0
- 문서 규약 반영: 약 0.5 engineer-hour
- 선택적 정적 검사 자동화와 회귀검사: 약 1.0~1.5 engineer-hour
- 사용자 작업: 권장안 승인·보류 결정 1회

## 5. 원리·근거

권한은 동사의 범위와 지목된 산출물이 소유한다.

| 사용자 표현 | 기본 권한 | 확대하려면 필요한 것 |
|---|---|---|
| 검토·분석·보고 | 읽기 전용 | 별도 수정 지시 |
| 제안서 작성·수정 | 지정 제안서만 쓰기 | 제안 내용의 구현 승인 |
| 특정 문서 수정 | 지목 문서만 쓰기 | 연쇄 대상의 명시 또는 정상 구현 단계라는 명확한 근거 |
| 스킬·훅·검사기 구현 | 지목된 파일·기능만 쓰기 | 정확한 구현 지시 또는 승인된 제안 |

이번 오류는 해결책의 품질 문제가 아니라 이 두 층을 합친 **권한판단 오류**다. 따라서
재발 방지는 기술안 선호도가 아니라 사전 권한 표와 패치 후 diff 대조로 해야 한다.

## 6. 방법

1. 착수 보고에서 `파일 / 예정 동작 / 권한 근거 / NOT_RUN`을 한 줄씩 고정한다.
2. `검토`, `감사`, `보고`, `제안`만 근거로 잡힌 파일은 읽기 전용으로 표시한다.
3. `.agents/skills/**`, `.codex/**`, 작업 흐름 생성기·검사기는 환경 동작 변경군으로 묶고
   직접 지시나 승인된 제안이 없으면 패치 대상에서 제외한다.
4. 여러 파일 패치는 권한이 같은 묶음끼리 나누고, 묶음마다 즉시 `git diff -- <allowlist>`와
   허용목록 밖 diff를 확인한다.
5. 범위 초과가 발견되면 사용자의 기존 변경에 `git checkout`을 쓰지 않고, 이번 세션이
   만든 정확한 hunk만 `apply_patch`로 역패치한다.

수용 기준은 “권장 구현을 생각해 냈다”가 아니라 “모든 변경 파일에 사용자 권한 근거가 있다”이다.

## 7. 거절하면 못 하는 것

기존 AGENTS 경계만으로도 수동 주의는 가능하다. 다만 검토 요청을 구현 승인으로 잘못 읽는
오류를 파일별 체크로 조기에 차단하는 장치는 생기지 않는다.

## 8. 위험

- 너무 엄격하면 정상적인 통상 구현 연쇄까지 매번 묻게 되어 작업이 느려질 수 있다.
- “관련 파일”이라는 넓은 표현을 자동 승인으로 보면 같은 오류가 재발할 수 있다.
- 검사 자동화만 추가하고 권한 근거를 사람이 쓰지 않으면 형식적 체크박스가 될 수 있다.

완화책은 **명시된 산출물과 정상 구현에 필수인 최소 연쇄만 허용**하고, 작업환경 자체를
바꾸는 스킬·훅·검사기는 별도 고위험군으로 유지하는 것이다.

## 9. 대안

| 안 | 내용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A | 현행 주의 문구만 유지 | 변경 없음 | 같은 해석 오류를 기계적으로 못 막음 | 기각 |
| B | 모든 연쇄 수정마다 사용자에게 질문 | 가장 보수적 | 명백한 통상 구현도 중단되어 비효율 | 보조 원칙 |
| C | 파일별 권한표 + 환경 동작 파일 별도 승인 + 패치별 diff 대조 | 권한과 기술 판단을 분리하면서 정상 작업 지속 | 표 작성 비용이 조금 듦 | **권장** |

권장안 C를 채택하되 자동화 구현은 사용자가 이 제안서를 승인한 뒤 별도 범위로 수행한다.

## 10. 승인 뒤 구현 기록 — 2026-09-13

- Codex 00 양쪽 판에 R58, Codex 06과 `impact-analysis`에 파일별 권한표·환경 동작 파일 별도 승인
  계약을 반영했다.
- `scripts/check_change_scope.py`는 명시 `--allow PATH=AUTHORITY`와 `--changed PATH`만 대조한다.
  환경 동작 경로는 `--environment-approval` 없이는 실패하고, 보호 데이터 경로는 항상 거부한다.
- 리터럴·좁은 `/**`만 허용하고 상위 이동·광범위 glob을 거부하는 5개 fixture가 통과했다.
- 이 검사는 Git 상태를 임의 탐색하거나 권한을 생성하지 않으며, 호출자가 누락한 변경 경로의 진실을
  대신하지 않는다. 실제 변경 경로 목록을 명시적으로 넘겨야 한다.
- 2026-09-14 현재 작업의 명시 변경 경로 29개를 사용자 지시별 권한 근거와 함께 입력했고
  `SUMMARY changed=29 allowed_rules=11 errors=0`을 확인했다. 환경 동작 파일
  `scripts/handoff_queue.py`에는 2026-09-13 J안 승인과 현재 지시 4를 정확한 승인 근거로 넘겼다.
  이 실사용 PASS는 입력한 29개 경로의 범위 정합만 증명하며 저장소 전체 dirty tree를 대신하지 않는다.
- 최종 문서·제안서 이관까지 포함한 명시 변경 경로 45개도 다시 입력해
  `SUMMARY changed=45 allowed_rules=13 errors=0`을 확인했다. 보호 데이터는 입력·열거 대상에서 제외했고,
  삭제된 원경로와 이관된 목적경로를 모두 명시해 이동도 권한 감사에서 빠뜨리지 않았다.
