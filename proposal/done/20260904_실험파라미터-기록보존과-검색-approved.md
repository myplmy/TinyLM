## 4. ★안 A — **DB(SQLite)로 관리**

### 4.1 모양

```
runs/registry.db          (gitignore)      <- 질의용
scripts/registry.py       --rebuild / --query / --record
```

`--record` 는 `runlog.py` 가 **종료코드 0 일 때만** 부른다.

```sql
SELECT tag, loss, bpb FROM runs
 WHERE json_extract(params,'$.cla_group')=2
   AND json_extract(params,'$.train_repeat')=2.0
 ORDER BY loss;
```

### 4.2 장

- ★**진짜 질의가 된다.** 위 SQL 이 그대로 돈다. 정렬·집계·조인 전부.
- **파이썬 표준 라이브러리**다(`sqlite3`) — 새 의존성 0.
- 224행이든 5,000행이든 **속도가 같다**.

### 4.3 🚫단

- ★★**git 에서 diff 가 안 된다.** 이 저장소의 검토는 **전부 diff 기반**이고,
  게이트 28종이 **전부 텍스트를 읽는다**. 🚫**바이너리는 그 그물 밖**이다.
- **머지 충돌을 사람이 못 푼다** — 두 세션이 각자 기록하면 파일이 통째로 충돌한다.
- ★**`.gitignore` 로 빼면 "기록 보존" 이 아니다** — 기계가 바뀌면 사라진다.
  → **보존은 json 이 하고 DB 는 캐시**라고 규정해야 한다(그러면 DB 는 *편의*이지 *보존*이 아니다).

## 5. ★안 B — **규격화된 MD 문서로 관리**

### 5.1 모양

```
docs/RUN_REGISTRY.md      (git 추적)       <- 사람이 읽는 정본 색인
scripts/registry.py       --record / --verify
```

한 런 = 표 한 줄. 열은 §3 그대로.

### 5.2 장

- ★**diff 가 된다.** 새 런은 **+1줄**이고 리뷰에 그대로 보인다.
- ★**게이트를 붙일 수 있다** — `check_static_all` 에 등재해 **json ↔ 표 양방향 대조**.
  (`check_flag_whitelist` 가 오늘 쓴 것과 **같은 구조**다)
- `grep` 로 찾는다. 새 도구를 안 배워도 된다.

### 5.3 🚫단

- ★**질의가 약하다.** *"cla2 이고 r20 이고 상주 32 MiB 이하"* 는 grep 으로 안 된다.
- ★★**열 폭발**: 113키를 다 적으면 표가 못 읽는다.
  → **"기본값과 다른 키만" 적는다**(예: `cla_group=2 train_repeat=2.0 no_ckpt`).
  ⚠️그러면 *"기본값이 무엇이었나" 가 시점 의존*이 된다 — **프리셋을 함께 적어야** 복원된다.
- **224행 × 긴 줄** = 파일이 커진다(⚙80~120 KB).

## 7. 언제 어떻게 기록하나 — **세 안 공통**

### 7.1 ★기록 시점 = `runlog.py` 의 종료 처리

`runlog` 만이 **네 가지를 동시에** 안다:

| 아는 것 | 어디서 |
|---|---|
| **종료코드** | 자식 프로세스 |
| ★**계획번호-단계** | `--name P084_stage2_main` |
| ★**로그 파일명** | 자기가 만든 경로 |
| ★**태그·프리셋·데이터·토큰** | `--` 뒤 **자식 명령줄**(`--tag`, `--preset`, …) |

→ ★**json 파일명 `{preset}_{data}_{tokens}_{tag}.json` 을 정확히 재구성**할 수 있다.
🚫**mtime 으로 추측하지 않는다**(같은 시각에 두 런이 끝날 수 있다).

```
if 종료코드 == 0 and 자식이 `run100m.py train`:
    registry.record(plan_stage=name, log=path.name, json=재구성한 경로)
```

⚠️**학습이 아닌 호출**(진단·벤치)은 **기록하지 않는다** — `--tag` 가 없거나 json 이 안 생긴다.

### 7.2 🚫**이 설계의 약점을 먼저 적는다**

- ★**`runlog` 를 안 거치면 기록이 안 된다.** 지금 배치는 전부 거치지만 **손으로 돌리면 빠진다.**
  → **보완**: `registry.py --scan` 이 **json 중 표에 없는 것**을 찾아 **경고**한다(게이트).
- ★**계획번호가 틀리면 그대로 들어간다.** 오늘 `P085` 배치가 `--name P079_…` 였던 것이 정확히 그 사고다.
  → ✅**오늘 신설한 `lint_bat` 규칙 26 이 그 앞을 막는다.** 두 장치가 짝이다.

## 12. 권장

### ★**안 C** — TSV 정본 + MD 뷰 + (선택) DB 캐시

**근거 셋**:
1. ★**이 저장소의 검토가 diff 기반**이다. 바이너리 DB 는 게이트 28종의 그물 **밖**에 있다.
2. ★**같은 구조가 이미 돌고 있다**(`experiments.tsv` + `queue_menu --audit`) — 배울 것이 없다.
3. ★**질의가 필요하면 DB 를 TSV 에서 30줄로 만든다.** 반대 방향(DB → 텍스트)은 어렵다.

⚠️**안 A 도 나쁘지 않다** — *"cla2 이고 r20 이고 상주 32 이하"* 같은 질의가 **주 용도**라면
DB 가 낫다. 🚫**그러나 그 질의를 실제로 몇 번 했는지 우리는 모른다** — 세어 본 적이 없다.
★**그래서 C 로 시작하고, TSV 가 답 못 하는 질문이 3번 쌓이면 그때 DB 를 켠다.**

> ★**승인하면**: 도구 작업이므로 계획서 없이 구현한다. 🚫**단 소급 반영(§8 단계 1~3)을
> 같은 커밋에** 넣는다 — 빈 표를 만들어 두면 그것이 곧 낡은 표다.
