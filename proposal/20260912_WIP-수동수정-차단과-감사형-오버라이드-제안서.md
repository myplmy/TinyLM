# 제안 — WIP 수동수정 차단과 감사형 오버라이드

> **작성** 2026-09-12 · **상태** ⏳판단 대기 · **분류** 스킬 / 작업방식
> 양식: [`proposal/README.md`](README.md) §3. **승인 전 구현하지 않는다.**

---

## 1. 배경 — 왜 지금 이 제안을 하나

`scripts/wip.py`의 첫 문장은 자신을 WIP 상태 변경의 **유일한 통로**로 정의한다. 그러나 현재 구현에는
`--new`, `--add`, `--override`가 없고, 기존 작업내용이 있는 행에 노트를 추가하면 코드 133에서 HTML
줄바꿈 태그를 삽입한다. 후속 실사에서는 상태 변경 로그 위치도 고정된 작업 로그 절이 아니라 파일
끝의 임의 백틱 목록을 역탐색해, 19~21번 완료 로그를 §4.4 안에 잘못 삽입했다. 이번
`WIP_20260912c_작업원장-done.md`는 최초 생성, 16번 추가·진행 표시,
1~16번 상태 갱신이 모두 `apply_patch`로 수행됐다. 현재 파일 내용은 산출물과 대체로 맞지만 수정 전·후,
근거, 수행 시각, 승인 근거를 저장소만으로 완전 재구성할 수 없다.

OpenAI 공식 훅 문서는 `PreToolUse`가 Bash와 `apply_patch`를 모두 차단할 수 있고 `apply_patch`의
canonical `tool_name`도 제공한다고 설명한다. 동시에 특수 도구 경로는 기본 훅 경로를 벗어날 수 있으므로
훅을 완전한 보안 경계로 보지 말라고 명시한다. 따라서 스크립트 단일 쓰기 경로와 훅 보조 차단을 함께
설계하는 것이 가능하다. 근거: [OpenAI Docs — Hooks](https://learn.chatgpt.com/docs/hooks).

## 2. 목적 — 무엇을 알아내거나 얻으려 하나

WIP의 정상 변경은 모두 검증된 스크립트 명령으로 수행하고, 불가피한 예외 수정은 **대상·수정 전·수정
후·근거·실측 일자·승인 근거**가 남지 않으면 실행되지 않도록 한다.

## 3. 성과물 — 승인하면 무엇이 생기나

| 산출물 | 형태 |
|---|---|
| WIP v2 단일 쓰기 API | `scripts/wip.py`의 `--new`, `--add`, 기존 상태 명령, `--override` |
| 감사 기록 | 각 WIP의 `오버라이드 수정 이력` append-only 절과 before/after SHA-256 |
| 직접 수정 보조 차단 | Bash·`apply_patch`를 감시하는 프로젝트 `PreToolUse` 경로 가드 |
| 정본 정합 | Codex 02, `wip-ledger/SKILL.md`, 스크립트 help의 동일한 열·전이 계약 |
| 회귀 검사 | 정상 변경, 직접 패치 deny, stale-before deny, 태그 0건, fail-open 검출 fixture |

기존 완료 원장은 소급 수정하지 않는다. 현재 열린 원장을 v2로 변환할지는 구현 승인과 별도로 사용자가
정한다.

## 4. 비용

| 항목 | 양 |
|---|---:|
| GPU | 0 GPU-h |
| AI 작업 | ⚙4~6 engineer-h |
| 사용자 검토 | ⚙20~30분; CLI와 훅 변경을 각각 승인·신뢰 |
| 디스크 | ⚙100 KiB 미만; 코드·fixture·작은 감사 로그 |

실제 WIP 데이터 이관을 승인하면 현재 원장 1개에 대해 추가 검토 약 15분이 든다.

## 5. 원리·근거

**우리 실측**

| 근거 | 값 | 출처 |
|---|---|---|
| 현행 WIP 도구의 생성·추가·오버라이드 명령 | 0개 | `scripts/wip.py` argparse |
| 기존 노트 뒤 HTML 줄바꿈 태그 삽입 | 1개 코드 경로 | `scripts/wip.py:133` |
| 완료 로그의 임의 목록 뒤 삽입 | 1개 코드 경로; 19~21번에서 재현 | `scripts/wip.py`의 파일 끝 역탐색 |
| 이번 원장의 수동 상태 갱신 | 1~16번 | 이번 세션 도구 기록과 WIP 로그 부재 |
| 현재 프로젝트 훅 matcher | Bash만 | `.codex/hooks.json`의 `^Bash$` |

**외부 근거**

[OpenAI Docs의 Hooks 문서](https://learn.chatgpt.com/docs/hooks)는 `PreToolUse`가 Bash,
`apply_patch`, MCP 및 다수 로컬 함수 도구를 관찰하며 deny 결정을 쓸 수 있다고 설명한다. 같은 문서는
일부 특수 도구 경로가 빠질 수 있으므로 훅을 완전한 강제 경계가 아니라 guardrail로 다루라고 한다.

## 6. 방법

| 단계 | 무엇 | 비용 | 다음으로 가는 조건 |
|---|---|---:|---|
| 0 | 사용자가 스크립트·스킬·훅 구현 범위를 각각 승인 | 0.2h | 승인 파일 allowlist 확정 |
| 1 | WIP v2 헤더와 상태 전이·로그 schema를 한 정본으로 확정 | 0.7h | Codex 02·스킬·help fixture 일치 |
| 2 | `--new`, `--add`, `--start/done/block/wait`, `--close`와 고정 절 locator를 atomic write로 구현 | 1.5h | 정상 경로 테스트와 로그 위치 검사 전부 PASS |
| 3 | 제한된 `--override`와 append-only 감사 레코드 구현 | 1.2h | stale-before·누락 근거가 모두 fail-closed |
| 4 | Bash·`apply_patch` WIP 직접쓰기 보조 차단 훅 구현 | 1.0h | 정상 스크립트 허용·직접 쓰기 deny E2E |
| 5 | 레거시 읽기 전용·태그 0건·fail-open 회귀 검사 | 1.0h | 정적·실제 Code Mode fixture 모두 PASS |

권장 오버라이드 인터페이스는 자유로운 전체 파일 패치가 아니라 한 항목·한 필드의 compare-and-set이다.

```powershell
python scripts/wip.py --override --file handoff/WIP_YYYYMMDD_작업원장.md `
  --item 2 --field "작업 내용" `
  --expect-before "현재 정확한 값" --set-after "바꿀 정확한 값" `
  --reason "왜 정상 상태 명령으로 표현할 수 없는가" `
  --approval-ref "사용자 지시 YYYY-MM-DD"
```

스크립트는 사용자가 시간을 입력하게 하지 않고 `datetime.now().astimezone()`으로 수정일자를 측정한다.
성공 시 같은 원장의 `## 오버라이드 수정 이력`에 다음을 한 트랜잭션으로 append한다.

- 고유 변경 ID와 수정일자
- 항목 번호·필드·수정 대상 locator
- 수정 전 전문과 SHA-256
- 수정 후 전문과 SHA-256
- 수정 근거와 사용자 승인 참조
- 실행한 CLI argv에서 민감값을 제거한 재현 정보

`--expect-before`가 현재 셀과 한 글자라도 다르면 파일을 쓰지 않는다. 지시 원문 필드는 기본적으로
오버라이드 대상에서 제외하고, 별도 `--allow-directive-correction`과 구체 사용자 승인 참조가 함께 있어야
허용한다. 훅은 WIP 경로를 포함한 직접 `apply_patch`, `Set-Content`, 리다이렉션을 deny하되 정확한
`scripts/wip.py` 명령만 통과시킨다.

## 7. 거절하면 못 하는 것

이번 원장의 내용 감사와 새 핸드오프 작성은 이 제안을 거절해도 할 수 있다. 다만 다음 세션에도 도구가
HTML 줄바꿈 태그를 만들거나 기능 부족 때문에 AI가 수동 패치를 선택할 가능성을 기계적으로 차단할 수
없고, 수동 변경의 before/after·승인 근거를 저장소 자체에서 복원할 수 없다.

## 8. 위험 — 실행하면 무엇이 잘못될 수 있나

| 위험 | 어떻게 드러나나 | 완화 |
|---|---|---|
| 훅이 정상 `wip.py` 실행도 차단 | 정상 상태 전이가 PreToolUse deny | 명령 parser fixture와 명시적 allow, 새 세션 E2E |
| 오버라이드가 범용 우회구가 됨 | 전체 파일·복수 필드 변경 가능 | 한 항목·한 필드, exact-before, 승인 참조 강제 |
| 감사 로그 안의 표 구분자·개행이 원장을 깨뜨림 | `--list` 행 수 변화 | 표가 아닌 fenced JSON 레코드 또는 길이 접두 블록 사용 |
| 로그가 다른 절의 백틱 목록에 삽입 | 감사·설명 문맥 손상 | 정확한 heading 범위 locator, 중복 heading 거부, 쓰기 뒤 구조검사 |
| 훅 fail-open을 강제 차단으로 오인 | 경고 뒤 직접 쓰기가 실행됨 | fail-open을 PASS로 세지 않고 별도 FAIL/NOT_RUN 판정 |
| 레거시 원장이 새 parser로 변형됨 | 과거 기록 diff 발생 | 레거시는 읽기 전용, 변환은 파일별 별도 승인 |
| 여러 세션 동시 쓰기 충돌 | 한쪽 상태·로그 유실 | 임시파일+원자 교체, 원본 SHA 비교, lock 파일 |

## 9. 대안

| 안 | 무엇 | 장점 | 단점 | 영향도 | 수행비용 |
|---|---|---|---|---|---|
| A | 규약으로만 수동 수정 금지 | 변경이 가장 작음 | 이번처럼 GPT가 우회하면 막지 못함 | 문서만 | 낮음 |
| B | `wip.py` 기능과 감사 로그만 보강 | 사람·AI 정상 경로가 명확함 | 직접 `apply_patch`는 기술적으로 가능 | 스크립트·문서·fixture | 중간 |
| **C** | B + `PreToolUse` 직접쓰기 보조 차단 | 정상 API와 사전 차단을 함께 제공 | 훅 신뢰·E2E와 fail-open 관리 필요 | 스크립트·스킬·Codex 02·훅·검사 | 높음 |
| D | OS ACL로 WIP를 read-only 고정 | 편집기 수준에서도 강함 | Windows 종속, 스크립트도 권한 토글 필요, 사용자 작업 방해 | 파일시스템 운영까지 | 높음 |

### ★권장안과 근거

**C를 권장한다.** B가 의미·감사 정본이고 훅은 수동 패치를 사전에 잡는 보조선이다. 공식 문서가
훅을 완전 경계로 보지 말라고 하므로 훅 단독안은 두지 않는다. A는 이미 실패했고 D는 저장소의 이식성과
사용자 직접 편집을 과도하게 해친다.

영향도는 다음과 같다.

| 축 | 영향 | 내용 |
|---|---|---|
| 코드 | 있음 | `scripts/wip.py`, 새 guard와 fixture; 기존 호출 CLI 호환 유지 필요 |
| 데이터 | 있음 | WIP v2와 append-only 감사 레코드; 완료 원장 소급 변경 금지 |
| 테스트 | 있음 | parser·atomic write·동시성·PreToolUse 실제 deny 검증 필요 |
| 정본 문서 | 있음 | Codex 02·스킬·help를 같은 변경에서 동기화 |
| 기술부채·우선순위 | 있음 | 스크립트만 또는 훅만 먼저 넣으면 다시 계약이 갈라짐 |
| GPU·학습 | 없음 | 학습·모델 경로와 무관 |
| 데이터셋·체크포인트 | 없음 | 보호 경로를 읽거나 변경하지 않음 |
| 증거 수준 | 있음 | 정적 parser PASS와 실제 PreToolUse deny를 별도로 판정 |

이 문서는 제안이며 `scripts/wip.py`, 스킬, Codex 02, 훅을 변경하는 승인이 아니다.
