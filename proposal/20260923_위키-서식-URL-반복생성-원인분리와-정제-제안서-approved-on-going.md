# 제안 — 위키 표제·URL 반복 생성의 원인을 분리하고 코퍼스를 보수적으로 정제한다

> **작성** 2026-09-23 · **상태** 🔄승인 후 진행 중(`-approved-on-going`) · **분류** 데이터 품질 / 학습방법 / 생성 평가
> 양식: [proposal/README.md](README.md) §3. 제정 당시 큐 잠금은 역사 기록이다. 2026-09-25 권장 B안 승인 뒤 현재 산출물·남은 gate는 §10을 따른다. 현재 모델의 동적 원인 판정은 여전히 `NOT_RUN`이다.

## 1. 배경 — 관찰된 현상과 아직 모르는 것

사용자는 현재 생성에서 `같이 보기`, `참고 문헌`, `외부 링크`,
`http://` 문자열이 반복돼 모델이 학습을 잘 못한 것처럼 보인다고 보고했다.
**현재 checkpoint·프롬프트·decoding별 빈도는 아직 측정하지 않았다.**
진행 중 큐의 결과 로그도 열지 않았으므로 현상 재현과 원인 확정은
`E2E_NOT_RUN`이다. 사용자의 실제 관찰을 부정하거나 정적 코드만으로
현재 모델의 오류를 PASS/FAIL 처리하지 않는다.

역사적 [P029 결과 013](../test_result/013_20260730190000_P029-정성프로브-1차.md)는
5개 프롬프트·2개 온도·2개 모델의 20생성에서 `같이 보기`와
`외부 링크` 표제, 위키식 카테고리, 반복 붕괴를 **정성적으로 관찰**했다.
그 기록은 작은 표본이라 빈도 추정이 아니며, `http://` 반복의
실측값도 제공하지 않는다. 당시 한국어 문서 뒤 영어 난입은
EOS를 멈추지 않던 **당시 생성 도구**가 기여했다고 기록했다.
현재 [생성 함수](../tinylm/infer/generate.py)는 기본 `stop_at_eos=True`로
바뀌었으므로 **현재에도 같은 EOS 결함이라고 복사해서 말할 수 없다**.
tokenizer에 EOS ID가 없으면 stop은 꺼지는 코드 경계가 있어 실제
checkpoint·tokenizer 조합의 동적 확인은 남는다.

명칭도 정확히 구분해야 한다. 현재 주 학습 ID `ko-en`은
[데이터 준비 코드](../tinylm/data/prepare.py)의
`wikimedia/wikipedia@20231101.ko`와 영어
`HuggingFaceFW/fineweb-edu` 혼합이다. `Salesforce/wikitext`
WikiText-103은 별도 `en` ID이며 주 `ko-en`의 한국어 원천이 아니다.
[코퍼스 원장](../docs/methods/07_corpus_selection.md)과
[P097](../test_plan/P097_한영-코퍼스-조합-300M-품질-대조.md)을
따라 아래에서는 **한국어 Wikipedia 꼬리 서식**이라고 부른다.

코드상 문서별 토큰 뒤에 EOS를 붙이고, 선택적 `doc_filter`는
거대 SEO 스팸 서명만 검사한다. `같이 보기/참고 문헌/외부 링크`
꼬리 절·URL 전용 제거는 없다. 따라서 그런 텍스트가 source에
들어 있으면 학습 대상으로 남을 **경로는 확인**된다.
하지만 실제 cache에서 차지하는 토큰 비율은 이 턴에 측정하지 않았다.

사용자가 읽기를 허용한 **현재 큐 런처만** 확인했다. P092 Stage2W는
`--data ko-en`이고, P097 Stage3의 control 두 팔은
`ko-en-control-v2`, 대응 두 팔은 `ko-en-fw2`다. 뒤의 두 recipe는
같은 300M draw·600M pool·seed 2024/31415를 선언한다. 따라서
큐 종료 뒤 **이미 실행 중인** P097 대조의 결과를 먼저 재사용해야 하며,
새 정제 실험을 중복 편성하지 않는다. 이 런처 읽기만으로 실제 완주·
품질 결과는 알 수 없다.


## 2. 목적 — 무엇을 알아내나

**같은 부모·토크나이저·학습토큰·평가 경로에서** 위키 꼬리/URL의
source 노출, EOS/디코딩, SFT 부재와 학습량 부족을 각각 분리해,
원하는 한국어 지식과 문맥 활용은 보존하면서 원치 않는 서식 출력만
줄일 수 있는지 검증한다.

## 3. 성과물 — 승인하면 무엇이 생기나

| 산출물 | 관측·판정 계약 |
|---|---|
| 원천 감사표 | Wikipedia·FineWeb-Edu별 표제/URL 문서율·토큰율, 위치(본문/꼬리), 중복·언어 비율, EOS 양옆의 실제 예시를 SHA/표본 ID와 기록 |
| 생성 패널 | 같은 checkpoint와 prompt에서 EOS on/off, 온도·top-k 조건을 고정해 표제·URL 재현율, 반복률, 사실·문맥·형식 점수를 분리 |
| 보수적 꼬리 정제본 | 별도 신규 cache/manifest. `같이 보기/참고 문헌/외부 링크`가 **꼬리 절로 확인된 문서만** 보수적으로 잘라내고 제거 byte/token·문서 수·오탐 예시 보존; 기존 cache는 그대로 |
| 대조 실험 | raw 대조, 꼬리 정제, 비위키 한국어 원천 혼합을 분리; 같은 parent/seed/tokenizer/draw/pool 또는 교락을 명시 |
| 판정 보고 | 생성 표제·URL 빈도와 한국어 지식/추론/held-out·영어 비퇴행, source 분포와 메모리·학습시간을 나란히 기재 |

사용자 큐의 P097 추가 seed 결과는 회수 전이다. 그 결과를 읽기 전에는
FineWeb2 한국어가 위키 대체 승자라고 전제하지 않는다.

[기준표](../docs/EXPERIMENT_BASELINES.md)와 registry preflight가 선결이다.

## 5. 원리·근거

**우리 관측**: 결과 013에서 표제 재현과 low-temperature 반복 붕괴가
실제 관찰됐다. 그러나 그 한 번의 패널은 현재 모델의 `http://`
원인이나 train-source별 토큰 기여를 알려주지 않는다.
`prepare.py`의 EOS append는 문서 경계 토큰을 가르치지만,
주어진 block 안에서 다음 문서 토큰까지 loss를 계산할 수 있다.
현재 생성의 EOS stop은 역사적 도구 결함을 줄였지만, 같은 문서
안의 꼬리 서식 학습까지 지우지는 않는다. 이 마지막 문장은
**코드에 근거한 추론**이며 현 모델 실측 결론은 아니다.

**외부 근거**: [FineWeb 논문](https://arxiv.org/abs/2406.17557)은
대규모 사전학습 데이터의 필터·중복 제거 선택을 ablation으로
검증한다. [FineWeb2 논문](https://arxiv.org/abs/2506.20920)은
언어별 필터·중복 처리가 다국어 corpus에서 중요함을 다룬다.
[Holtzman 등 생성 퇴화 연구](https://arxiv.org/abs/1904.09751)는
디코딩 선택이 반복 출력에 영향을 준다는 근거다. 이 연구들이
TinyLM의 위키 꼬리 제거 효과를 이미 증명한 것은 아니다.

## 6. 방법 — 값싼 계측이 비싼 학습을 연다

| 단계 | 독립변수·검사 | 다음으로 가는 조건 |
|---|---|---|
| W0 관측 고정 | 큐 종료 후 사용자 지정 현 checkpoint 2~3개, 한국어 일반/위키/링크 요청/제공문단 프롬프트를 각 조건 5회 이상; 생성 원문·seed·temperature·top-k·EOS 사용 기록 | 표제·URL이 **원치 않는 맥락에서** 실제 재현되는지 확인. 링크 요청 시 URL 생성은 결함으로 세지 않음 |
| W1 source 감사 | 동일 계보의 원문 source에서 꼬리 표제·URL/참고문헌의 문서율·토큰율·위치·언어비율 측정, 20~50건 오탐 눈검토. 현재 큐 cache는 종료 전 읽지 않음 | 꼬리 source 노출이 낮으면 정제보다 decoding/SFT/학습량 가설 우선 |
| W2 순수 정제 fixture | 본문 제목·인용·실제 필요한 링크는 보존, 꼬리 절만 절단하는 parser를 합성·실문서 fixture로 검사. 제거량/중복/오염 기록, **새 cache 이름** | 오탐과 정보 손실이 허용 가능한지 사용자 검토, cache fingerprint 분리 |
| W3 생성/데이터 대조 | 같은 parent/tokenizer/pool/draw/optimizer/seed의 raw 대 정제 팔. 필요하면 P097 FineWeb2 교체 팔은 **별도** 비교. 디코딩-only 팔은 모델 개선 아님 | marker/URL 반복↓와 일반 답변·한국어/영어 benchmark·full-val 비퇴행이 함께 성립해야 채택 |
| W4 원인 귀속 | source 제거만 효과인지, EOS/temperature/top-k만 효과인지, SFT format 학습 후 효과인지 대조 | 교락이면 `UNIDENTIFIABLE`; 데이터 교정 전역 적용 금지 |

반복 학습량이 원인이라는 가설은 P087/P100의 **동일 원천 재노출**
축에서 별도로 검증한다. 데이터 정제와 epoch·학습토큰을 동시에
바꾸지 않는다. W3는 새 실험 승인 뒤 test_plan에 번호를 부여하고
`exp-preflight`를 다시 수행한다. 현재 `check_run_registry.py`는
진행 중 큐의 live JSON을 읽을 수 있으므로 **NOT_RUN**이다.

**학습방법 대안도 별도 축이다.** 원천 내 꼬리 노출은 낮은데 모델이
질문마다 위키 표제로 빠지면 [P090](../test_plan/P090_SFT-경로.md)의
같은 부모·같은 지도 토큰 예산으로 문답 형식 SFT를 먼저 대조한다.
반대로 문서 경계 뒤의 토큰 예측 자체가 문제로 실측되면 EOS 이후
타 문서로 넘어가는 loss/attention을 차단하는 실험을 별도 제안한다.
꼬리 토큰 loss만 낮추는 방법은 지식·URL 생성까지 희생할 수 있어
source 분포와 W2 보존율을 확인한 뒤에만 검토한다. 세 방법을 한 런에
합치거나 디코딩 억제를 학습 성과로 부르지 않는다.

> 이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.

## 7. 거절하면 못 하는 것

기존 P097/P090/P100 계획은 계속할 수 있다. 다만 원치 않는 위키
서식 출력이 source 노출인지, 생성 선택인지, 지식·SFT 부족인지
구분하지 못해 `http://` 억제 같은 임시 대책을 실제 품질 향상으로
오인할 위험이 남는다.

## 8. 위험 — 실행하면 무엇이 잘못될 수 있나

| 위험 | 어떻게 드러나나 | 완화 |
|---|---|---|
| 본문 과삭제 | `같이 보기`가 설명 문장·인용에도 나오는데 정규식이 뒤를 자름 | 문서 말미의 독립 절 제목만 인정, 절단 전후 문맥·삭제량 눈검토, 원본·SHA 보존 |

| 디코딩 과장 | 억제 후 URL이 줄어도 사실성은 그대로 | 생성 억제를 모델 품질이 아닌 표시 정책으로 별도 표기 |

## 9. 대안

| 안 | 내용 | 장점 | 단점·영향도·비용 |
|---|---|---|---|
| A | URL·표제 문자열을 전역 정규식으로 삭제 | 빠르다 | 본문·인용·유용한 링크 손상, 언어/코퍼스 전반에 영향; 구현 낮음·재작업 높음 |
| **B** | W0/W1 증거 → 꼬리 절만 정제 → matched 학습 대조 | 데이터 대 생성 원인 분리, 원본 보존 | 별도 cache·평가 필요; 영향 중간, AI ⚙5~9h + 조건부 GPU |
| C | 생성시 URL/표제 억제·top-p만 조정 | 빠른 사용자 체감, 구 학습 보존 | 지식·원천 편향 교정 아님; 영향 낮음, GPU 0 |

### 권장안

**B를 권장한다.** 단 W0/W1에서 current source/출력의 표제 과다를
실제로 확인하지 못하면 정제 구현은 열지 않고 C를 표시 정책 진단으로만
사용한다. 원본 `ko-en` cache와 진행 중 큐는 보존하며, 제안서
승인만으로 학습 파일이나 기본 데이터셋을 변경하지 않는다.

## 10. 2026-09-25 권장 B안 승인과 현재 진행 범위

사용자가 §9의 **W0/W1 증거→조건부 꼬리 정제→matched 대조** 순서를 승인했다. [P105 계획](../test_plan/P105_위키-꼬리서식-노출과-생성원인-분리.md)에 Stage0W 무모델 집계 계약을 배정했고 [독립 진단기](../scripts/diag_p105_wiki_format.py)의 합성 source/generation JSONL fixture는 PASS다. 이것은 실제 문서나 모델의 재현 빈도 PASS가 아니다.
