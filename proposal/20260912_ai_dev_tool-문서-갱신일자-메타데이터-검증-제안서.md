> 상태: **제안 대기 / 문서 일괄 수정·검사기 구현은 하지 않음**  
> 실사 범위: `ai_dev_tool/**/*.md` 55개

## 1. 배경

`ai_dev_tool`에는 현재 규약처럼 계속 갱신되는 문서, 특정 시점의 감사 보고서, 승인 전 검토
초안이 함께 있다. 이들을 모두 파일 수정시각 하나로 판정하면 Git checkout·복사만으로 날짜가
바뀌는 오탐이 생기고, 반대로 아무 검증도 하지 않으면 문서 상단 날짜가 실제 내용보다 낡는다.

실사한 55개 문서는 다음 세 유형으로 나뉜다.

| 유형 | 수 | 정책 |
|---|---:|---|
| 살아 있는 정본 | 23 | 상단 `최신 갱신일자` 필수, 엄격 검증 대상 |
| 검토 초안·분석 산출물 | 6 | `작성일`과 `상태` 필수, 수정 때 선택적으로 `최종 수정일` 추가 |
| 시점 고정 보고·이식 증거 | 26 | `기준일/작성일` 유지, 현재 날짜로 강제 갱신하지 않음 |

## 2. 목적

문서 유형에 맞는 날짜 의미를 먼저 선언하고, 살아 있는 정본의 상단 날짜가 실제 변경 증거와
어긋날 때만 오류를 내는 단일 검증 계약을 만든다.

## 3. 성과물

승인하면 다음이 생긴다.

1. `ai_dev_tool` 문서 유형과 날짜 정책을 가진 manifest 1개.
2. 살아 있는 정본 23개 상단의 표준 메타데이터.
3. 문서 날짜·manifest·Git 변경 증거·로컬 mtime을 구분해 검사하는 정적 검사기 1개.
4. 누락·미래 날짜·파싱 불가·정본 간 날짜 드리프트를 잡는 fixture.
5. 기존 Codex 환경 검사에는 Codex 소유 11개만 연결하고, Claude 문서는 런타임 지침으로 읽지 않는 경계.

## 4. 비용

- 55개 분류 재검토와 manifest 작성: 약 1.0 engineer-hour.
- 살아 있는 정본 23개 메타데이터 추가: 약 1.0 engineer-hour.
- 검사기와 fixture: 약 1.5 engineer-hour.
- GPU·학습·모델·데이터셋 비용: **0**.
- 사용자 작업: 정책 및 정확한 변경 allowlist 승인 1회.

## 5. 원리·근거

파일시스템 mtime은 내용 정본이 아니다. Git checkout, 압축 해제, 파일 복사, 복원 도구가 내용
변경 없이 mtime을 바꿀 수 있다. 따라서 다음 세 값을 분리해야 한다.

- **문서 선언일**: 작성자가 의미 변경을 완료했다고 선언한 날짜.
- **Git 내용 변경일**: 추적 파일의 마지막 내용 커밋 날짜. 저장소 간 재현 가능한 증거.
- **로컬 mtime**: 현재 작업공간에서 마지막로 기록된 시각. 사용자가 요구한 로컬 드리프트 검사에
  유용하지만 checkout 오탐 가능성이 있는 환경 증거.

작업규약 영문·한글판처럼 두 문서가 같은 규칙을 소유하면 날짜와 분류 개수까지 동일해야 한다.
반면 P7/P8 보고서나 20260909 보고서는 과거 관찰 증거이므로 오늘 mtime과 맞추려고 본문 날짜를
바꾸면 역사가 왜곡된다.

### 6.4 검사기 제안

`scripts/check_doc_metadata.py`와 `docs/doc_metadata_policy.tsv`를 제안한다.

```text
path | type | paired_with | date_policy
```

검사기는 다음을 오류로 낸다.

1. manifest 파일 누락·중복·미등록 Markdown.
2. `live` 문서의 상단 갱신일자 누락·미래 날짜·파싱 오류.
3. 영문·한글 pair의 선언일 불일치.
4. `--local-mtime-strict`일 때 선언일과 로컬 mtime의 달력 날짜 불일치.
5. clean worktree에서 선언일이 마지막 Git 내용 변경일보다 과거인 상태.

mtime 검사는 checkout 오탐 가능성이 있으므로 로컬 엄격 모드에서 명시적으로 사용한다.
CI 정본 판정은 manifest와 Git 내용 변경일을 우선한다. 이번 사용자 지시로 이미 구현한 Codex
작업규약 두 판은 환경 검사에서 로컬 mtime까지 엄격 비교하는 좁은 예외다.

문서 자체는 계속 수동 갱신할 수 있다. 다만 어떤 파일이 살아 있는 정본인지, 상단 날짜가
낡았는지, 시점 고정 보고서를 잘못 “최신화”했는지를 한 명령으로 판별할 수 없다.

## 8. 위험

| 위험 | 통제 |
|---|---|
| checkout만으로 mtime 오류 | mtime은 로컬 엄격 모드, Git 내용일은 재현 가능한 기준으로 분리 |
| 역사 보고서 날짜 덮어쓰기 | `snapshot`은 작성일 형식만 검사하고 현재 날짜 강제 금지 |
| Codex가 Claude 문서를 환경 지침으로 읽음 | 검사기는 바이트·메타데이터만 파싱하고 명령으로 해석하지 않음; Codex 환경 연결은 Codex 11개로 제한 |
| 55개 일괄 패치 중 사용자 변경 충돌 | 단계별 allowlist와 파일별 diff, 광범위 치환 금지 |
| 날짜만 맞고 내용 정합은 틀림 | 날짜 검사는 내용 검토를 대체하지 않으며 `STATIC_ONLY`로 표기 |

## 9. 대안과 권장안

| 안 | 장점 | 단점 |
|---|---|---|
| A. 모든 파일 mtime 엄격 일치 | 단순함 | checkout 오탐과 역사 왜곡이 큼 |
| **B. 유형별 manifest + Git 내용일 + 선택적 mtime** | 의미·재현성·로컬 감시의 균형 | manifest 유지 비용 |
| C. 문서 날짜만 수동 관리 | 구현 0 | 누락과 pair 드리프트를 자동 검출 못 함 |

**권장안은 B**다. 이 문서는 구현 승인이 아니며, 사용자 승인 전에는 23개 문서 일괄 수정이나
새 검사기·manifest 작성을 수행하지 않는다.
