# COMPASS·핸드오프·사용자 행동요청 누락 재발방지 제안서

> 작성일: 2026-09-12  
> 상태: **제안 대기 / 구현 승인 아님**  
> 범위: 결과 문서 연쇄, 세션 핸드오프, 다음 세션 시작문, 사용자 행동 요청의 완결성

## 1. 배경

2026-09-11 결과 074·075·077·078·079가 갱신됐지만 `handoff/COMPASS.md`의 폭·재귀·타잉·
토큰·옵티마이저·지능 축은 이전 “다음 단계”를 계속 가리켰다. 최신 핸드오프는 완료된 WIP를
참조하면서도 다음 세션에 “중단 작업을 이어라”라고 했고, WSD 원문 요청은 저자 순서와
`article/` 위치만 적어 정확한 파일·식별자·검토 후 행동을 생략했다.

세 문제의 공통 원인은 **긴 작업을 요약하는 마지막 단계에서 정본 갱신과 사용자 행동의
필수 필드를 검증하지 않은 것**이다. 이는 단순 GPT 누락이며, 결과·핸드오프 파일이 존재한다는
사실을 내용 완결성 증거로 잘못 간주한 오류다.

## 2. 목적

결과가 바뀐 축의 정본 연쇄, 다음 세션의 정확한 첫 행동, 사용자가 수행할 외부 행동을
각각 구조화하여 “문서는 썼지만 무엇을 해야 하는지 모르는” 상태를 막는다.

## 3. 성과물

승인하면 다음 계약과 검사 설계가 생긴다.

1. 결과 문서별 `COMPASS 필요/불필요/보류 사유` 체크.
2. 핸드오프의 `정본 동기화·미갱신 사유` 표.
3. 열린 WIP가 없을 때 “중단 작업” 표현을 금지하는 시작 프롬프트 규칙.
4. 사용자 행동 요청의 `대상/위치/근거/행동/완료 신호/후속 처리` 6요소 검사.
5. 생성기·검사기·정본 규약을 한 번에 바꾸는 회귀 fixture.

## 4. 비용

- 설계·문서 정합: 약 1.0 engineer-hour.
- 생성기·검사기 회귀 테스트: 약 1.0 engineer-hour.
- GPU·모델·데이터셋·체크포인트 비용: **0**.
- 사용자 작업: 변경안 승인 여부 결정 1회. 실제 구현은 별도 승인 뒤 수행.

## 5. 원리·근거

### 5.1 COMPASS 누락

`.agents/project.json`은 COMPASS를 연구 축 상태의 단일 소스로 두고, `log-to-result` 연쇄는
축 판정이 바뀐 세션에 COMPASS를 마지막 고리로 갱신하도록 한다. 결과 문서가 바뀌었는데
COMPASS가 낡았던 것은 연구 판단이 아니라 완료 체크 누락이다.

### 5.2 모호한 시작 프롬프트

`WIP_20260912b_작업원장-done.md`는 열린 항목이 없는 완료 원장이었다. 그러므로 “중단 작업을
이어라”는 실제 상태와 맞지 않는다. 시작 프롬프트는 추상 동사가 아니라 **정확한 열린 항목,
첫 읽기 경로, 첫 행동, 금지 경계**를 적어야 한다. 열린 작업이 없으면 “새 요청을 시작하되
아래 미결은 승인 전 실행하지 않는다”가 맞다.

### 5.3 불완전한 사용자 행동 요청

“논문을 저장한다”는 요청은 저자명만으로는 같은 저자의 다른 판본이나 잘못된 제목을 가를 수
없다. 최소한 정확한 제목·arXiv/DOI·권장 파일명·저장 위치·왜 필요한지·저장 후 무엇을 알려야
하는지를 함께 줘야 한다. 이전 요청은 이 중 대부분을 생략했다.

## 6. 방법

### 게이트 0 — 승인 범위

이 제안서 승인 전에는 스킬·생성기·검사기를 수정하지 않는다. 과거 핸드오프도 역사 기록이므로
소급 수정하지 않는다.

### 게이트 1 — 결과 연쇄 표

결과를 문서화할 때 아래를 한 행씩 남긴다.

| 산출물 | 필요 여부 | 실제 diff | 미갱신 사유 |
|---|---|---|---|
| 결과 본문 | 필수 | 경로 | — |
| 계획·목록·기준표·방법론 | 조건부 | 경로 또는 `없음` | 정확한 이유 |
| COMPASS | 축 판정 변경 시 필수 | 경로 또는 `없음` | 정확한 이유 |

`없음`은 허용하되 빈칸은 허용하지 않는다.

### 게이트 2 — 시작 프롬프트 상태 분기

- 열린 WIP 있음: 정확한 WIP 파일과 첫 미완료 번호를 적는다.
- 열린 WIP 없음: “중단 작업”을 쓰지 않고 새 요청 시작 상태임을 적는다.
- 사용자 승인 대기: 대상 제안서와 **승인 전 금지 행동**을 적는다.

### 게이트 3 — 사용자 행동 요청 6요소

각 부탁은 다음 여섯 요소를 한 항목 안에 둔다.

```text
대상 / 정확한 위치 / 근거 / 사용자가 할 행동 / 완료를 알리는 방법 / AI의 후속 처리
```

### 게이트 4 — 생성기와 검사기의 동시 회귀

정본 규약, 생성기 skeleton, 검사기 fixture를 같은 변경으로 갱신한다. 최소 fixture는
`열린 WIP 있음`, `열린 WIP 없음`, `사용자 다운로드 요청`, `COMPASS 미갱신 사유 있음` 네 가지다.

## 7. 거절하면 못 하는 것

현재 문서를 사람이 주의 깊게 작성하면 작업 자체는 계속할 수 있다. 다만 결과 문서 갱신 뒤
COMPASS가 또 빠지거나, 완료 원장을 “중단 작업”으로 소개하거나, 사용자 부탁이 행동 가능한
수준인지 자동으로 잡는 보장은 없다.

## 8. 위험

| 위험 | 통제 |
|---|---|
| 모든 결과에 COMPASS 갱신을 강제해 불필요한 diff 발생 | `필요/불필요/보류 사유`를 허용하고 축 판정 변경 때만 필수 |
| 핸드오프가 다시 장황해짐 | 6요소를 한 문장 또는 짧은 표 한 행으로 제한 |
| 검사기가 내용의 진실까지 보증한다고 오해 | 구조 검사는 `STATIC_ONLY`; 수치·판정은 결과 정본을 사람이 대조 |
| 과거 기록 소급 변경 | 최신 생성물에만 적용하고 과거 핸드오프는 수정하지 않음 |
| 제안 승인을 구현 승인으로 오해 | 변경 파일 allowlist를 별도 승인받기 전 구현 0건 |

## 9. 대안과 권장안

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 사람 체크리스트만 추가 | 구현이 작음 | 이전과 같은 완료 착각을 기계가 못 잡음 |
| **B** | 체크리스트 + 상태 분기 + 최소 구조 검사 | 누락 방지와 문서 유연성의 균형 | fixture 유지 비용이 있음 |
| C | 모든 문서 연쇄를 자동 수정 | 편리함 | 의미 판단 오류와 사용자 파일 과수정 위험이 큼 |

**권장안은 B**다. 다만 이는 아직 제안이며, `.agents/skills/**`, `scripts/new_handoff.py`,
핸드오프 검사기 등 실제 동작 파일은 사용자의 별도 구현 승인 전까지 수정하지 않는다.
