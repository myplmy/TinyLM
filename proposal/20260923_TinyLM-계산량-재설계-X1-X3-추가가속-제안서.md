## 1. 배경 — 왜 지금 이 제안을 하나

### 1.1 기존 커널 최적화와 다른 질문

기존 S1/S2/S3는 출력 헤드 융합, 한 optimizer update 안의 양자화 전처리 재사용, 보조 head 계산과 패딩 감소다. 이번에는 **Transformer 몸통이 처리해야 하는 실제 계산 자체**를 줄인다.

- X1: 서로 다른 학습 사례가 가진 동일한 입력 접두부를 여러 번 계산하는 중복을 제거한다.
- X2: 모든 층·어텐션은 유지하되 학습 초·중반에 실제 실행하는 FFN 중간 채널을 줄이고 마지막에는 전체 폭을 학습한다.
- X3: 정해진 후속학습 구간에 한해 앞쪽 층의 파라미터를 고정하고, 그 출력 활성값을 저장해 반복 노출에서 앞부분 forward/backward를 생략한다.

X1은 동일 논리 batch와 dropout0 등 명시 조건에서 loss·gradient 보존을 목표로 한다. X2와 X3는 **다른 학습 알고리즘**이며 동일 토큰에서 빨라져도 동일 지능까지 빨라진다는 보장은 없다.

새 하드웨어 구매, 다른 GPU에 교사 상시 배치, 더 강한 TinyLM 교사 선행학습, 코퍼스 교체 반복을 전제로 삼지 않는다. **모든 안에서 2배를 약속하지 않는다.** 중복·반복이 실제 있는 학습 구간에서 큰 절감 가능성을 찾고, 일반 NTP에는 적용 범위를 구별한다.

### 1.2 기존 연구와 겹치는 부분을 숨기지 않는다

| 기존 항목 | 이미 확인된 경계 | 이번 추가안의 차이 |
|---|---|---|
| S2 update-local 양자화 캐시 | 같은 W의 양자화 전처리만 재사용 | X1은 동일 접두부의 모든 층 활성·KV와 backward를 공유 |
| S3 패딩 제거 | 없는 토큰의 슬롯 연산 제거 | X1은 실제 존재하지만 중복인 문맥 연산을 제거 |
| P031/P049/P062 | 학습·추론 깊이 mismatch와 재귀/중복층의 비용 | X1은 층을 생략하거나 유사한 hidden으로 대체하지 않음 |
| P092/P025B | dense mask가 GEMM을 줄이지 않음; 후속 primitive wall 이득 미확정 | X2는 행렬 크기 자체를2048→512/1024로 축소, zero mask를 큰 GEMM에 곱하지 않음 |
| P024/RAPTR 원장 항목 | progressive subnetwork 개념은 이미 언급됨 | X2는 그 계열의 구체적인 CLA-safe FFN-only 파생 설계. 새로운 원리의 최초 발견이라고 주장하지 않음 |
| P091 | adaptive selector의 실효성 미확정, local optimizer 갱신과 속도는 다름 | X3는 불안정 selector를 쓰지 않고 연속된 앞12층의 정확한 캐시 재사용 조건을 고정 |
| inference KV cache | 생성 시 과거 토큰 상태 보관 | X1은 학습 gradient를 복원하고, X3는 고정된 하부 parameter와 입력의 버전 일치를 요구 |

기존 상태는 학습속도 원장 [L1]과 P091 계획 [L2], 현재 transformer의 CLA/cache 코드 [L3]에 근거한다. P024/P091과 연구 범위가 겹치는 부분은 승인 후 기존 계획의 후속 절로 흡수할지 결정하며 새 P번호를 임의로 선점하지 않는다.

### 1.3 공통 비교 단위

`B`는 해당 학습 작업에서 이미 채택한 T1 및 S1/S2/S3를 적용한 **동일 논리 학습량의 실제 wall**이다. S1/S2/S3가 아직 구현되지 않았다면 현재 T0를 사용하고 baseline signature를 바꿔 기록한다. 아래 절감률을 예전344.6분 또는424.3분에 무조건 곱하지 않는다.

| 이름 | 주 대상 | 고정 논리 학습량에서의 조건부 절감 목표 | 중심 계산 예 |
|---|---|---:|---:|
| X1 | 공통 원문을 공유하는 KnowledgePack/SFT·선호쌍·오류교정 후보 | 전체 해당 작업25~50%; 고중복 부분은 더 클 수 있음 | **39%**, 1.64배 |

이는 미측정 설계 범위이지 실측·신뢰구간이 아니다. 데이터 중복이 없거나 회복비용·I/O가 크면 절감0 또는 악화가 된다.

## 2. 목적 — 무엇을 알아내거나 얻으려 하나

**일반 커널 융합을 넘어 중복되는 문맥 계산, FFN의 초·중반 전폭 연산, 반복 후속학습의 고정 하부 연산을 실제로 제거하여, 같은 직접질의 지능 기준을 유지하는 wall-time 절감 경로를 확보한다.**

권장 첫 실행은 **X1의 공통 접두부 학습**이다. 목표 보존이 가능한 유일한 주 경로이기 때문이다. 일반 NTP처럼 접두부 중복이 없는 작업에는 X2가 연구 후보이며, X3는 새 능력 획득을 제한할 위험 때문에 후속학습에만 조건부 적용한다.

## 5. 원리·근거

### 5.1 X1의 원리

인과적 Transformer에서 같은 parameter와 동일 token-prefix는 뒤에 어떤 응답이 붙는지와 무관하게 같은 앞부분 계산을 가진다. 따라서 같은 update에 속한 여러 분기의 공통 계산 그래프를 하나로 만들고, 각 분기의 gradient를 공유 노드로 합치면 중복을 제거할 수 있다. 독립 분기끼리 서로의 답변을 보게 하면 다른 문제다.

외부 연구 [E1]은 DPO의 공통 프롬프트 공유와 sparse mask를 다루고, [E2]는 일반 분기형 학습과 gradient restoration을 다룬다. 본문에서 방법·mask·position·gradient 설명을 확인했다. 논문의 H100/대형 모델 가속 수치를 4070 Ti SUPER·TinyLM에 전이하지 않는다.

### 5.2 X2의 원리

SwiGLU는 중간 채널 집합에 대한 합으로 분해할 수 있다. gate/up의 해당 행과 down의 같은 열만 계산하면 FFN의 세 GEMM 크기를 실제로 줄일 수 있다. 큰 행렬에0 마스크만 씌우는 dense-sparse 방식과는 다르다.

Progressive subnetworks/RAPTR [E3]의 초록에서 단계적으로 계산 부분을 키우는 원리와 다른 모델에서의 실험을 확인했다. 전문 HTML 취득은 실패했으므로 논문의 구체 파라미터를 재현했다고 주장하지 않는다. 이 문서의 FFN-only·512tile·40/40/20 schedule은 **별도 TinyLM용 설계**다.

### 5.3 X3의 원리

연속된 앞부분 함수 F가 고정되면, 같은 입력 x에 대한 F(x)를 한 번 저장하고 뒤쪽 G만 여러 번 학습할 수 있다. F를 갱신한 순간 이전 활성값은 틀린 입력이 되므로 캐시는 반드시 무효화한다.

AutoFreeze [E4]의 초록과 저자 저장소 README에서 frozen-block·intermediate activation caching 접근을 확인했다. BERT 미세조정 결과이며, 삼진 TinyLM의 새 지능 획득까지 보장하는 근거는 아니다. 저자들은 단순한 정적 freezing이 정확도를 떨어뜨리는 경우도 보고한다. 본안의 마지막 전층학습과 비퇴행 중단선은 그 위험을 인정한 설계다.

### 5.4 기대를 제한하는 반대 근거

- S1로 head가 이미 빨라졌어도 attention kernel fallback·작은 실제 batch가 X1 이득을 소거할 수 있다.
- X2의 부분 FFN 출력은 전체 모델과 같지 않으며, 학습 후 전체 폭에서 손실이 악화될 수 있다.
- X3의 현재 하부 표현이 부족하면 tail만 학습해서 새 개념·추론 규칙을 얻지 못한다.
- 큰 속도비는 특정 학습 단계에만 해당한다. 코퍼스 생성·정답검토·일반 NTP까지 같은 비율로 빨라지지 않는다.

## 6. 방법

### 6.1 X1 — gradient를 보존하는 공통 접두부 학습

#### 6.1.1 대상과 비대상

우선 KnowledgePack의 같은 원문 기반 G1/G2/G3, 동일 문제의 정답/오답 비교, R3 후보의 동일 prompt를 대상으로 한다. G4 근거 제거형은 원문이 입력에 없으므로 긴 원문 공유율에 합산하지 않는다. 무작위 위키 크롭이 같은 문서에서 왔다는 이유만으로 공유하지 않는다.

공유 조건은 **같은 source_id가 아니라 직렬화 후 정확히 같은 앞부분 token IDs와 position IDs**다. 질문이 문서보다 앞에 있어 prefix가 짧으면 이득이 줄어든다. 속도를 위해 serializer를 바꿔야 한다면 새로운 별도 대조를 만들고 원형과 같은 실험이라고 하지 않는다. 원본 canonical은 수정하지 않고 인덱스만 생성한다.

#### 6.1.2 구체적 계산 예

원문512토큰 + 질문/응답 분기128토큰, 같은 원문 분기4개가 있다고 하자.

```text
현재 독립 처리: 4 × (512 + 128) = 2560 logical/physical token occurrences
공유 처리:     512 + 4 × 128 = 1024 physical token occurrences
논리 학습량:  여전히 2560 token occurrences, 응답·정답 수 동일
```

선형 projection/FFN에 대한 token-work는60% 줄 수 있다. attention은 suffix가 계속 전체 prefix를 읽어야 하므로 별도 계산한다.

```text
독립 causal score 수 = k × (C+U) × (C+U+1) / 2
공유 causal score 수 = C × (C+1) / 2 + k × (U×C + U×(U+1)/2)
```

이 예의 score 수도 약48% 줄지만, sparsity 처리와 커널 효율을 포함한 wall 단축률은 이 수치와 같지 않다. 물리 flatten 길이가1024를 넘더라도 각 논리 경로가 context limit 안에 있어야 하며, RoPE 위치는 root-to-leaf 경로를 기준으로 복원한다.

#### 6.1.3 첫 구현 규격

| 항목 | 규격 |
|---|---|
| 분기 수 | 자연적으로 존재하는4개까지. 이득을 늘리려고 같은 답을 복제하지 않음 |
| 유효 batch | 독립 leaf 실행과 같은 논리 batch·같은 loss 가중·같은 optimizer update 경계 |
| 샘플링 | 같은 leaf 묶음을 두 구현에 전달. 원래 랜덤 batch→source-cluster 변경 효과는 별도 실험 |
| attention | ancestor+same-branch-only mask. sibling answer·미래 token 접근0 |
| 위치 | leaf를 단독 실행했을 때와 같은 position; RoPE의 단일 연속 slice로 대체 금지 |
| CLA | owner별 공유 prefix K/V에 모든 소비 branch·layer gradient 합산 |
| dropout | 첫 비교는 양쪽0. 독립 dropout mask와 공유 mask를 같다고 하지 않음 |
| 캐시 생명 | 정확히 한 optimizer update. W가 바뀌면 폐기 |
| 작은 batch 방지 | 같은 macro-batch 안의 여러 tree를 함께 처리. logical batch를 무단 확대하지 않음 |
| 배포 | 학습만 변경. 기존 inference 경로 유지 |

현재 모델의 `past_kv`·`use_cache`는 출발 코드지만 분기 학습이 완성됐다는 뜻이 아니다. 기존 `logits_last_only`는 학습에서 거절되므로 그 플래그로 우회하지 않는다. 저장 KV dtype을 임의로 낮추지 않는다.[L3]

권장 구현은 training 전용 prefix state와 branch-aware attention이다. 길이512의 prefix를 한 번 처리하고 각 branch를 sibling 차단 상태로 연결한다. 브랜치가 커져 graph를 동시에 담기 어려우면 prefix state를 gradient-requiring leaf 경계로 노출하여 branch VJP들을 합산한 뒤 prefix VJP를 한 번 실행하는 방식으로 확장한다. **no_grad prefix cache로 치환하지 않는다.**

Dense N×N tree mask가 기존 flash 경로를 math로 떨어뜨리면 그 방식은 버린다. 선택지는 block-sparse training kernel 또는 prefix/suffix attention의 정확한 분해이며, 두 attention 결과는 하나의 softmax 분모에 대해 결합해야 한다. 별도 softmax 출력 둘을 단순히 더하면 틀린 함수다.

#### 6.1.4 MTP와의 특수 계약

공통 prefix의 마지막 위치에서 분기별 다음 token이 다를 수 있다. 하나의 shared label을 임의로 고르지 않는다. 주·보조 head마다 **branch별 target과 loss multiplicity**를 보존한다. 공통 hidden에 여러 label loss가 붙을 수 있으며, 그 gradient를 합산한다. prompt-loss가 원래0이면 해당 위치를 새 지도 대상으로 추가하지 않는다.

MTP horizon2/4의 fork 경계도 동일하다. 존재하지 않는 sibling 경로의 미래 token을 타깃으로 가져오지 않는다.

#### 6.1.5 동등성·품질 게이트

작은 FP32 reference에서 leaf별 logits, 합산loss, 모든 parameter gradient를 비교한다. 같은 정답·가중·dropout0 조건의 gradient 상대L2 1e-5를 첫 기준으로 제안하며 0-gradient는 절대오차로 검사한다. BF16은 baseline 커널 변경 오차를 먼저 계측한다.

실제 지능 평가에서는 group sampler로 바뀐 경우도 함께 판정한다. 수학적 공유 동등성이 sampler 변경에 대한 품질 동등성까지 증명하지 않는다.

#### 6.1.6 wall 예측

```text
w = 전체 작업시간 중 공유가 가능한 묶음의 비중
s = 그 묶음의 시간 중 prefix forward/backward처럼 실제 공유 가능한 비중
k = 평균 분기수
epsilon = mask/합산/낮은 GEMM효율 등의 새 overhead, 전체 B 대비 비율
T_X1 / B ≈ 1 - w×s×(1-1/k) + epsilon
```

중심 가정 `w=0.8, s=0.7, k=4, epsilon=0.03`이면 시간비0.61, **39% 단축·1.64배**다. B=10시간인 해당 작업을 예로 들면6.1시간이다. 이는 미래 작업시간 약속이 아니라 동일 workload 기준의 산술 예다.

실제 w와 s가 작으면 이득이 없다. `G1/G2/G3 레코드80%`를 `wall80%`로 치환하지 않는다. **부분작업 speedup이3배여도 전체시간의20%에만 적용되면 전체 절감은13.3%**다. 제작·검토 비용은 별도다.

### 6.2 X2 — 모든 층을 유지하는 FFN-only 구조적 계산 커리큘럼

#### 6.2.1 정확히 무엇이 달라지는가

각 FFN2048을512채널 tile4개로 구분한다. 기존 gate/up/down의 full-shaped master parameter는 유지한다. 선택된 tile만 실행하되 마지막 단계에서는 전체2048채널로 돌아온다.

```text
gate: [2048,768]에서 활성 행만 사용
up:   [2048,768]에서 같은 활성 행만 사용
down: [768,2048]에서 같은 활성 열만 사용

첫 단계 GEMM 중간 폭: 512
두 번째 단계: 1024
마지막 단계 및 최종 배포: 2048
```

Layer·Q/K/V/O·CLA owner·residual 순서는 전부 유지한다. 따라서 층을 삭제하거나 KV 공급자를 건너뛰는 P031류 오류를 피한다. 하지만 FFN 함수 자체는 달라지는 학습이므로 품질 동등성을 선험적으로 주장하지 않는다.

#### 6.2.2 시작 파라미터와 schedule

| 학습 구간 | 활성 tile 수 | 실제 FFN 폭 | 순전파 FFN 보정 |
|---|---:|---:|---:|
| 0~40% | 1/4 | 512 | 선택 합×4 |
| 40~80% | 2/4 | 1024 | 선택 합×2 |
| 80~100% | 4/4 | 2048 | 보정 없음 |

보정은 고정 h에서 선택 FFN 출력의 기댓값을 full 출력에 맞추려는 규격이다. **비선형 뒤층을 포함한 전체 loss/gradient의 불편추정은 아니다.** 처음0~40%에서 학습이 불안정하면 초반폭을1024로 바꾸는 별도 수정안이 필요하며, 원안을 성공으로 포장하지 않는다.

무작위 tile는 update마다 선택하고 그 update의 모든 accumulation micro-batch에 고정한다. 4-update 단위 균형을 유지하되 layer마다 순환 offset을 달리하여 모든 층이 같은 tile만 실행하지 않도록 한다. 평가·배포는 처음부터 끝까지 full 폭으로도 기록한다.

#### 6.2.3 삼진·Muon·compile 함정

- 큰 FFN을 계산한 뒤0으로 만드는 구현은 금지한다. profile의 실제 GEMM shape가512/1024인지 확인한다.
- M0의 g128 그룹 경계를512 tile가 정확히 포함한다. 전체 규약에서 계산한 유효 weight를 정렬된 그룹 단위로 사용한다. 선택 폭에 맞춰 per-row α를 새로 추정하면 다른 양자화다.
- down의 비연속 열 gather/contiguous packing 비용도 timing에 포함한다. update 내 pack 재사용은 허용하되 gradient는 원래 full master에 scatter한다.
- Muon NS는 **원래 full-shaped 행렬**에 적용한다. 512짜리 별도 Muon parameter로 쪼개면 optimizer가 달라지므로 원안에서 하지 않는다.
- 비활성 채널에 data gradient가0이어도 momentum/직교화로 갱신될 수 있다. 그것까지 중단했다고 주장하지 않는다. 본안은 optimizer비용을 거의 줄이지 않고 FFN 실행비를 줄인다.
- compiler는3개의 폭 또는 작은 유한 route bank로 제한한다. 모든 layer의4가지 선택 조합을4의 layer수만큼 컴파일하지 않는다.
- 선택된 shape의 학습률·NS scale 재정의는 별도 변수다. 본안은 기존 full-matrix optimizer recipe를 우선 유지한다.
- 입력 토큰 수·보조 head target·batch·WSD/quant schedule은 paired 기준과 동일하게 두고, MTP를 꺼서 얻은 절감을 본안의 효과로 세지 않는다.

#### 6.2.4 wall 예측과 회복 예산

```text
평균 FFN 계산폭 비율 q = 0.4×0.25 + 0.4×0.5 + 0.2×1 = 0.50
f = B에서 FFN forward/backward가 차지하는 비중
epsilon = gather·scatter·compile·관리 overhead
T_X2 / B ≈ (1-f) + f×q + epsilon
```

중심 가정 `f=0.65, epsilon=0.03`이면0.705, **29.5% 단축·1.42배**다. 계획 범위는20~35%다. 이 범위에는 예정한 마지막20% full폭 학습이 이미 포함돼 있다.

별도의 추가 full-width 회복 학습이 B의10% 필요하면 총시간비는0.805로 올라가 절감19.5%다. **회복·재컴파일·추가 평가를 반드시 합산**한다. 추가 회복 상한은B의10%로 두고, 그 안에서도 baseline 지능을 회복하지 못하면 효율안으로 기각한다.

초기 full폭 CE 악화를 단순한 수렴 지연이라고 무시하지 않는다. 같은 입력량 및 같은 지능 품질 도달시간 두 축으로 보고한다. 이미 약한 모델을 더 약한 부분망으로 시작하는 것이 불리할 수 있으므로, 첫 적용은100M 대조이며 전체1.2B를 자동 시작하지 않는다.

### 6.3 X3 — 고정 하부 활성 캐시와 마지막 전층 회복

#### 6.3.1 적용 범위

새 어휘·개념을 처음 학습시키는 주 사전학습에 기본 적용하지 않는다. **이미 있는 M0/U2 checkpoint를 고정된 후속학습 pack에 여러 번 노출시키는 구간**에서만 시험한다. 교사·추가 정답 생성은 필요 없다.

첫 구성은16층 모델에서 **앞12층+입력 경로를 고정하고 뒤4층을 학습**한다. CLA2의 owner/consumer pair를 가르는 위치로 자르지 않는다. 논리적 12/4 경계가 현재 actual owner graph와 맞는지 검사하고 어긋나면 실제 완결된 그룹 경계로 조정하여 다른 조건으로 기록한다.

#### 6.3.2 반드시 함께 고정해야 하는 것

현재 모델은 입력·출력에 임베딩/투영을 공유한다. 하부를 고정하면서 shared `emb.weight`·`emb_up.weight`를 출력 head에서 갱신하면 prefix 함수가 변해 cache가 틀린다. 따라서 캐시 구간에는 **공유 입출력 embedding과 투영도 고정**한다. 뒤쪽 hidden에는 고정된 head를 거친 gradient가 계속 흐른다.

그 밖에 하부 norm·QK scale·RoPE 규약·양자화 어닐·dropout·mask·분기 설정도 고정한다. optimizer에서 제외하고 weight decay·EMA·momentum으로 조용히 변경되지 않도록 버전과 hash를 검사한다. freeze 상태에서 finite grad0이라고 해서 모델이 수렴했다고 판단하지 않는다.

**새 E384의 추가 차원이나 QK scale이 아직 적응하지 않은 직후에는 이 안을 켜지 않는다.** 필요한 전층 적응 시간이 있다면 전체 비용에 추가하거나 baseline 양쪽에 같은 선행을 둔다. 강한 교사가 필요하다는 뜻은 아니지만, 하부의 부족한 표현을 고정할 위험은 남는다.

#### 6.3.3 첫 phase 규격

비교는 같은 레코드·같은 순서의 **4회 노출**로 고정한다.

| 구간 | baseline | X3 |
|---|---|---|
| cache 준비 | 없음 | 현재 고정 하부의 boundary hidden을1회 계산·저장 |
| 노출1~3 | 모든 parameter 전층 학습 | cached boundary를 읽고 뒤4층만 학습 |
| 노출4 | 전층 학습 | cache를 사용하지 않고 모든 parameter를 다시 학습 |

학습 모멘텀 상태는 parameter별 freeze/resume 계약을 기록한다. freeze 중 silent WD/update를 금지하고, 해제 후의 LR·warm ramp도 비용과 학습 조건에 포함한다. 동일 schedule을 갖는 full-layer 대조를 둔다.

이 캐시는 추론 KV cache가 아니라 **하부 모델 출력의 저장물**이다. 원래 dtype이FP32라면 FP32로 저장한다. 임의 BF16/int8 저장은 별도 근사 실험이며 본안의 exact cache라고 부르지 않는다.

캐시 key에는 checkpoint와 하부 함수 hash, tokenizer hash, exact token IDs, position IDs, segment/mask, sequence 길이, precision/backend signature를 넣는다. 문장 순서·truncation·증강이 바뀌면 다른 key다. 모델 hash가 바뀌면 전부 무효화하며 stale cache를 허용하지 않는다.

#### 6.3.4 메모리와 I/O의 실제 비용

```text
hidden 차원 = 768
고유 입력 토큰 = 20,000,000
FP32 cache = 20,000,000 × 768 × 4 = 61.44GB ≈57.22GiB
BF16 cache = 30.72GB ≈28.61GiB  # 원래 계산 dtype이BF16인 경우에만
```

131072토큰의 FP32 boundary batch는384MiB다. 저장장치에서0.4초에 읽으려면 대략1GB/s의 실효 읽기속도가 필요하다. 정적 토큰열을 mini-batch 단위 contiguous shard에 넣고 double-buffer prefetch를 사용하되, 실제 tail계산과의 overlap만 이득으로 인정한다. 작은 무작위 read의 이름상 NVMe 속도를 사용하지 않는다.

cache 준비·쓰기·읽기·validation overhead를 모두 포함한다. 데이터가 한 번만 사용되거나 매번 다른 random crop이면 캐시가 거의 재사용되지 않아 부적합하다. 기존 랜덤 crop의 각 위치를 고유한 새로운 학습문서로 바꾸거나 중복을 늘려 속도를 과장하지 않는다.

#### 6.3.5 wall 예측

```text
B = 같은4회 노출을 전층 학습한 시간
rho = 전층 update 비용 중 고정 하부 forward/backward의 비중
cache 단계 비율 = 3/4
하부 캐시1회 생성 = 하부 forward 약1/3 full-training-pass로 근사
epsilon = B 대비 미중첩 I/O·관리·phase transition 시간

T_X3 / B ≈ 1/4 + (3/4)×(1-rho) + rho/(3×4) + epsilon
```

중심 가정 `rho=0.675, epsilon=0.04`이면0.590, **41% 단축·1.69배**다. 이 값에는cache 생성과 마지막1회 전층 학습을 포함한다. 1/3 근사는 실제 forward/backward profile로 교정한다. 계획 범위는30~50%이며 별도의 추가 품질회복이 필요하면 절감은 더 작아진다.

전체 프로젝트에서 이 반복SFT가시간20%라면, 중심41%가 전체 프로젝트를 줄이는 비율은8.2%에 불과하다. 1.2B NTP 전체에 이 수치를 붙이지 않는다.

#### 6.3.6 선택과 중단

초기2M-token 고정 pack으로 cached/uncached frozen-prefix가 수치적으로 같은지 먼저 검사한다. 그다음 `전층4회`, `고정하부3회+전층1회(cache off)`, `같은 학습(cache on)`의 세 팔로 분리한다.

- 두 frozen 학습끼리의 차이는 cache 구현 효과다.
- full-layer 대비 차이는 학습 범위 변경의 대가다.
- tail만의 높은 훈련정답률은 전체 새 지능 확보의 증거가 아니다.
- 추가 회복 상한B의10% 안에서도 목표 품질을 회복하지 못하면 X3를 기각한다.
- 동결하지 않은 임베딩·하부가 필요하다고 진단되면 freeze범위를 조정한 새 안을 설계하되 원래41% 예측을 유지하지 않는다.

### 6.4 공통 실행 순서

| 단계 | 수행 | 비용/게이트 |
|---|---|---|
| G0 | 실제 corpus·baseline에서 공유율w/s, FFN비중f, 하부비중rho, 읽기속도 계측 | 선행0.2~0.5 GPU-h 규모. 효율 가능성이 없으면 큰 구현·학습 중지 |
| G1 | 작은 CPU/FP32 loss·gradient·mask·cache fixture | X1 exact 동등성, X2 full-mode 원복, X3 frozen-cache 동등성 |
| G2 | M0/U2 actual microtrainer의 warm wall | 동일 논리 batch·same weights/seed, 실제 compute shape 기록 |
| G3 | 100M 또는해당 fixed pack의 짧은 paired 품질 평가 | 직접질의·새 표현/조합 비퇴행; 학습시간에 회복 포함 |
| G4 | 실제 반복 캠페인에 최종1개 경로 적용 | 앞 단계 통과와 별도 승인 후 |

X1을 최우선으로 두고, prefix 공유율이 부족한 일반 NTP에는X2를 조사한다. X3는 후반 반복SFT에서만 사용한다. 셋을 모두 먼저 구현하고 대규모 학습하는 계획이 아니다.

### 6.5 시간·지능 판정과 합산 금지

각 방법은 cold/warm compile, 준비·캐시 생성, H2D/읽기, 학습, 평가·저장, 마지막 동기화, 추가 회복 시간을 각각 기록한다. 기존 profiler-on 시간과 production-off 시간을 섞지 않는다.

```text
time_ratio_total = (준비 + 학습 + 평가/저장 + 회복) / 동일작업 baseline_wall
speedup = 1 / time_ratio_total
```

X1의 공유 가능한 구간이 줄어들면X2의 FFN비중도 달라진다. X3는 하부계산을 없애므로X1이 재사용할 prefix계산 일부를 먼저 제거한다. 따라서 **39%+29.5%+41% 합산도, 각 비율 무조건 곱하기도 금지**한다.

고정 토큰에서 빠른 것과 같은 품질에서 빠른 것을 구별한다. 기존 직접질의 패널을 사용하고 새 거대 benchmark 프로젝트를 선결로 만들지 않는다. 권장 첫 비열등성 허용폭은 전체 정답률−2%p와 주요 능력별 사전 중단선이며, 지식·추론·한국어 능력은 별도 집계한다. 평가문항을 학습에 넣지 않는다. 작은 표본에서 유의차가 없다는 이유만으로 비열등을 선언하지 않는다.

원본과 정확한 수치 동등성이 목표인X1도 batch sampling을 바꾸면 별도의 품질 영향이 있으므로 원형 sampler와 grouping sampler의 영향을 분리한다.

## 7. 거절하면 못 하는 것

기존 T0/T1/S1/S2/S3와 지능향상 학습은 그대로 수행할 수 있다. 이번 추가안의 거절이 지능향상을 막지는 않는다. 다만 공통 문맥·반복 하부·초중반 FFN 계산의 큰 몫을 줄일 기회를 활용하지 못한다. 신규 구현·품질 위험을 감수하지 않고 더 긴 학습시간을 지불하는 선택은 정당한 대안이다.

### 권장안과 근거

**A안을 권장하되 첫 구현 승격은 X1 하나로 제한한다.** 원문의 여러 질문을 이미 만드는 KnowledgePack은 새 데이터셋 교체 없이 이 중복을 활용할 수 있다. 실제 prefix 분포가 게이트를 못 넘으면 X1을 확대하지 않는다. 그때 일반 NTP는 X2의 물리 FFN 축소를 별도로 시도하고, X3는 기초 지능 획득이 아니라 정해진 반복 후속학습에만 사용한다.

X1은 조건이 맞으면 loss와 gradient를 보존할 수 있다. X2/X3는 더 큰 근사적 가속 여지를 얻는 대신 품질 위험을 지불한다. **획기적인 가능성은 있지만, 모든 자료·모든 학습 단계에서 무조건 2배 빨라진다는 뜻은 아니다.**

## 10. 2026-09-24 타당성 재검토 — X3는 8비트 활성 캐시만 조건부 재설계

이 절은 원안 1~9절을 보존한 후속 분석이다. 현 [모델](../tinylm/model/transformer.py), [삼진 가중치](../tinylm/model/ternary.py), [훈련 경로](../tinylm/train/trainer.py), [기준표](../docs/EXPERIMENT_BASELINES.md)를 대조했다. 신규 구현·모델 로딩·GPU 측정은 `NOT_RUN`이다.

### 10.1 X1/X2/X3 중 유지할 원리와 제한

| 축 | 타당한 부분 | 수정·미확인 |
|---|---|---|
| X1 | 인과 모델의 **동일 직렬화 prefix**는 공유 계산과 branch별 gradient 합산이 가능하다. [prefix-sharing 연구](https://arxiv.org/html/2410.20305v2)는 mask·position을 통제한 실제 예다 | 그 연구는 DPO/H100/FlexAttention 조건이다. TinyLM의 실제 중복률·CLA/GQA kernel·sm89 whole-wall은 `NOT_RUN`. 원안 39%는 `w,s,k,epsilon` 가정값이지 예측 성과가 아니다. G0 중복률·backend profile 이전에 X1 우선 구현 확정 금지 |
| X2 | 2048 FFN에서 선택된 행/열만 곱하면 dense mask와 달리 물리 GEMM 형상이 준다 | [progressive subnetwork 연구](https://arxiv.org/abs/2402.05913)는 동기일 뿐 512/1024 FFN-only의 TinyLM 품질 근거가 아니다. 작은 GEMM underfill·gather/scatter·Muon full-state·회복 학습을 합산 |
| X3 | 고정된 하부 함수와 완전히 같은 token/position/mask라면 boundary hidden을 재사용할 수 있다. [AutoFreeze](https://arxiv.org/abs/2102.01386)는 중간 활성 cache의 선례다 | AutoFreeze는 BERT 미세조정이며 본 모델의 언어능력·4회 반복·저정밀 저장 안전성을 보증하지 않는다. 캐시 양자화는 **frozen-prefix exact 기준과 다른 근사 실험** |

### 10.2 마스터 가중치와 X3 캐시는 **다른 크기의 물건**

X3의 약60GB는 **20M개 token position × hidden 768개 값의 활성 캐시**다. 학습 master weight를 FP32→BF16으로 바꿔도 이 토큰 수·캐시 dtype을 따로 낮추지 않으면 `61.44GB`는 그대로다. M0 약105.4M 전체 parameter를 단순 4B로 잡아도 master **0.4216GB**, 2B면 **0.2108GB**여서 절감은 약0.21GB에 불과하다. 실제 학습 메모리에는 optimizer·gradient·quant 사본이 따로 있다. [혼합정밀도 훈련 원논문](https://arxiv.org/abs/1710.03740)은 작은 갱신의 누적 손실을 피하려 FP32 master 사본을 유지한다. 따라서 **저정밀 master의 안정성은 별도 학습 실험**이고 20GB cache 문제의 해결 조건이 아니다.

고정 하부 phase에서는 원 checkpoint를 변경하지 않고 하부·공유 emb/emb_up을 optimizer에서 제외한다. cache 생성 후 하부 weight를 반복 epoch의 GPU 상주에서 내려놓을 수 있는지는 별도 구현 문제다. 마지막 전층 phase는 원래 master와 정확한 optimizer/freeze-resume 규약으로 다시 열어야 한다. BF16/FP8 master를 기존 학습 master의 조용한 대체로 취급하지 않는다.

### 10.3 20M token × 768 저장량 — 20GB는 **십진 byte 상한**

| boundary 저장안 | 값 payload와 scale 가정 | 원시 크기 | 20GB 판정 |
|---|---|---:|---|
| FP32 | 4B/값 | 61.44GB = 57.22GiB | **불가** |
| BF16 또는 FP16 | 2B/값 | 30.72GB = 28.61GiB | **불가** |
| INT8 + 토큰당 BF16 scale 1개 | 1B/값 + 2B/token | 15.40GB = 14.34GiB | 크기만 통과; outlier 정밀도 위험 |
| INT8 + 토큰당 64채널마다 BF16 scale | 1B/값 + 12×2B/token | 15.84GB = 14.75GiB | scale 반올림까지 검정할 대조군 |
| **INT8 + 토큰당 64채널마다 FP32 scale** | 1B/값 + 12×4B/token | **16.32GB = 15.20GiB** | **수치 보수적 조건부 1순위** |
| FP8 E4M3 + 토큰당 2B scale | 1B/값 + 2B/token | 15.40GB = 14.34GiB | 비교군; range/정밀도 실측 필요 |
| packed INT4 + 64채널별 2B scale | 0.5B/값 + 12×2B/token | 8.16GB = 7.60GiB | 크기 이득, 품질·packer 위험 커서 후순위 |

수치는 `20,000,000 × (768×bytes_per_value + scales_per_token)`으로 직접 계산했다. 예를 들어 64채널 INT8+FP32 scale에 token ID 4B/token과 offset 4B/token을 각각 더하면 약`16.48GB`다(BF16 scale이면 16.00GB). 실제 파일 헤더·정렬·index·중복 buffer·RAM allocator는 **포함하지 않았다**. [FP8 형식 연구](https://arxiv.org/abs/2209.05433)는 FP8 표현의 가능성을, [ActNN](https://arxiv.org/abs/2104.14129)은 다른 목적의 quantized activation 저장 가능성을 보여줄 뿐, **고정 TinyLM 하부 경계의 INT8/FP8 캐시가 품질에 무해하다는 증거가 아니다**.

2026-09-24 WSL에서 읽기 전용 `free -h`는 RAM 총30GiB·가용28GiB였다. 따라서 **16.32GB 파일 한 벌의 RAM 상주 가능성은 있다**. 하지만 원안 4절의 host RAM 2~4GiB는 **disk streaming용 준비 버퍼**이고, 전량 RAM 모드의 총 사용량 추정으로 사용할 수 없다. page-cache와 사용자 버퍼의 이중 상주, DataLoader·GPU pinned staging, WSL의 다른 작업 및 swap을 합산해야 한다. 사용 직전 `MemAvailable`과 cache payload·peak RSS·major page faults를 재고, 전량을 pinned memory로 복제하지 않는다. 20GB 미만 **파일**과 20GB 미만 **실제 RSS**도 다른 판정이다.

또한 현재 trainer는 BF16 autocast를 사용하지만 제안 경계의 실제 emitted hidden dtype을 정적으로 확정할 수 없다. `RMSNorm`은 입력 dtype을 보존하고 잔차·kernel dtype은 경로에 따른다. 2M-token 소형 probe에서 경계 dtype을 기록해 **그 dtype 그대로 보존한 exact-cache 기준**을 먼저 만든다. FP32 값이었다면 BF16조차 근사, BF16 값이었다면 BF16 원본은 저장형식 동등 후보이지만 20M에서는 20GB 초과다.

### 10.4 선택지와 엄격한 진행 gate

| 안 | 구성 | 장점 | 대가·위험 | 판단 |
|---|---|---|---|---|
| A | 원 dtype RAM 기준 FP32 약6.5M token 이하 또는 BF16 약13M 이하(부가정보 전), 초과는 disk streaming | 수치 기준·작은 pilot 구축 용이 | 20M 전량 RAM 목표는 안 됨 | **정합 기준선** |
| B | **20M token INT8 64채널 FP32 scale, RAM 단일 사본** | 약16.32GB 원시, 20GB 목표와 비교 가능 | 양자화 오차·dequant/H2D·RSS 복사 비용 | **조건부 권장** |
| C | FP8 E4M3 scaled 또는 packed INT4 | FP8은 약15.4GB, INT4는 약8.16GB | E4M3 outlier/INT4 품질·packing과 커널 비용 미확인 | B와 동일 입력에서 대조 후만 |

1. **2M 고정 pack에서** unfrozen 원본은 그대로 두고, frozen-prefix uncached와 **원 dtype exact cache**의 hidden·tail logits/loss·모든 trainable gradient·한 update를 먼저 비교한다. 이는 cache 구현 gate다. 같은 입력·position·segment·CLA owner와 mask, sampler 순서를 고정한다. cache 생성 wall과 메모리도 기록한다.
2. 그 **동일한 boundary tensor**를 INT8 per-token, INT8 per-64(FP32 scale 기준·BF16 scale 별도), FP8로 별도 인코딩한다. dequant 후 hidden의 상대오차·max/outlier·cosine과 tail NTP/SFT loss·logit/정답·gradient, 4회 노출 뒤 고정 한국어·영어 문답을 **원 dtype cache 및 uncached frozen**과 paired 비교한다. 허용오차는 기준선 반복 노이즈와 task 판정자를 먼저 재고 사전 등록한다. 크기만 맞으면 PASS라는 문턱은 없다.
3. 위 단계가 통과하면 20M 고유 token에서 실제 **RAM 단일 사본**, index·staging 포함 peak RSS, swap/major faults, H2D와 dequant, cache build+read+마지막 전층 회복을 포함한 end-to-end wall을 잰다. 원안 41%는 이 측정 전까지 `DESIGNED`다. 20GB 파일 상한·실제 RAM headroom·품질 중 하나라도 실패하면 X3 확장을 중단한다.
4. 최종 전층 phase 시작 전에 캐시를 폐기하고 frozen 하부/공유 embedding·anneal·optimizer 상태를 명시적으로 복원한다. 이 변경은 기본 모델 경로에 선제 통합하지 않는다.

**결론:** 사용자가 제시한 “20GB 이내면 RAM”은 **INT8 또는 FP8 활성 캐시에서 산술상 가능**하다. 최우선은 FP32 master를 저정밀으로 바꾸는 것이 아니라, **원 checkpoint를 유지한 채 INT8 boundary cache의 품질·RSS·wall을 검증**하는 것이다. 현재 상태는 크기 계산 `PASS` / 정밀도·훈련 품질·실제 RAM 운용 `NOT_RUN`이다.

> 이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.
