# 제안 — 정적검사 부채를 누적시키지 않는 종료 게이트와 경고 정상화

> **작성** 2026-09-19 · **상태** ⏳판단 대기 · **분류** 작업방식 / 정적검사
> **실험번호**: `PNone`
> **실험계획 비대상 사유**: 문서·검사기·세션 종료 계약을 다루며 GPU 학습이나 모델 비교 실험이 아니다.
> 양식: [`proposal/README.md`](README.md) §3.

---

## 1. 배경 — 왜 지금 이 제안을 하나

2026-09-19 최종 검증에서 이번 기능 변경과 직접 관계없는 기존 부채가 동시에 드러났다.

| 검사 | 최초 재현 | 실제 원인 |
|---|---:|---|
| `check_doc_metadata.py --scope codex` | 오류 3 | live 문서의 Git 내용일은 2026-09-18인데 선언 갱신일은 2026-09-15에 머묾 |
| `check_pending.py` | 오류 2 | 완료 이관된 비실험 제안서에 구조화한 `PNone`·비대상 사유가 없음 |
| `check_doc_ownership.py` | 오류 8 · 경고 17 | E2가 표준 재현조건 표를 본문 복사로 오인, H1 parser가 `# 결과 NNN`을 미지원, 승인된 중복도 경고 수에 포함 |
| `check_control_chars.py` | 오류 1 | 원본 W&B 로그의 완결된 ANSI 색상 CSI를 패치 사고의 고립 ESC로 오인 |
| `check_lr_factor_sync.py` | 오류 1 | LR 수식 정본이 별도 모듈로 이동했는데 검사기는 의존성 없는 trainer wrapper만 떼어 실행 |
| `check_pending.py` | 오류 3 | WSL handoff의 실재 `.sh`를 Windows 전용 `.bat` regex가 “진입점 없음”으로 오인 |

세 검사 모두 문제를 찾았지만, 이전 세션은 이를 핸드오프에 “기존 부채”라고 기록하고도 WIP를
닫을 수 있었다. 다음 세션은 새 변경을 진행하면서 같은 실패를 다시 발견했고, 검사 출력의
`경고`에는 실제 조치가 필요한 항목과 이미 검토·허용된 정보가 섞여 있었고, 원본 로그의 정상
터미널 제어 시퀀스와 소스 파일에 잘못 박힌 제어문자도 구분하지 못했다.

이번 사용자 지시에 따라 위 실물 부채는 즉시 교정했다. 이 문서가 제안하는 것은 그 교정을
다음 변경에서도 자동으로 유지하는 후속 계약이며, 제안서 작성 자체가 후속 구현 승인은 아니다.

## 2. 목적 — 무엇을 알아내거나 얻으려 하나

Codex가 실행 가능한 정적 검사에서 발생한 실패와 조치 가능한 경고를 **WIP 종료 전에 0건으로
만들거나 명시적 사용자 보류 상태로 전환**하고, 허용 정보·보호경로 때문에 실행할 수 없는 검사를
부채와 분리하는 단일 종료 계약을 얻는다.

## 3. 성과물 — 승인하면 무엇이 생기나

| 산출물 | 형태 |
|---|---|
| Codex 안전 정적 프로필 | 보호 데이터·GPU·모델을 읽지 않는 검사만 묶은 명시적 실행 프로필 |
| 부채 종료 게이트 | 안전 프로필의 오류 또는 조치 가능한 경고가 남으면 WIP `--close`를 거부하는 검사 |
| 경고 등급 계약 | `ERROR`, `ACTIONABLE_WARNING`, `ACCEPTED_INFO`, `NOT_RUN`을 종료코드·요약에서 분리 |
| 문서 상태 전이 검사 | 완료 제안서의 P번호 또는 정확한 `PNone` 사유, live 문서 날짜를 이관 시점에 검사 |
| 회귀 fixture | 표준표 중복은 허용하되 서술 복사·H1 소유번호 오류는 계속 잡는 독립 테스트 |
| 핸드오프 필드 | 실행 프로필, 오류 수, 조치 가능한 경고 수, NOT_RUN 이유를 구조화해 계승 |

정본 수치는 각 검사기의 실행 결과가 소유한다. 별도 수동 부채 목록을 만들어 숫자를 복제하지 않는다.

## 4. 비용

| 항목 | 양 |
|---|---:|
| GPU | 0 GPU-h |
| AI 작업 | ⚙ 3~5 engineer-hour |
| ★**사용자가 직접 해야 하는 일** | 권장안 승인 또는 보류 결정 1회; GPU·데이터 실행 없음 |
| 디스크 | 회귀 fixture와 문서 합계 ⚙ 100 KiB 미만 |

이번 즉시 교정은 이미 사용자 직접 지시 범위에서 수행했으며, 위 비용은 후속 자동화의 추정치다.

## 5. 원리·근거

**우리 실측**

| 근거 | 값 | 출처 |
|---|---|---|
| 기존 부채가 최종 handoff까지 계승됨 | 6개 검사군, 오류 18 · 경고 17 | 2026-09-19 교정 전·추가 안전검사 출력 |
| E2 오경보 구성 | 8/8 문서쌍이 표준 재현조건 표의 연속 행 | `check_doc_ownership.py` 위치 재현 |
| 표 행 제외 후 과거 결함 검출력 | 파괴 커밋 `86d24c9`에서 서술 중복 문서쌍 17개 유지 | `git show` 기반 read-only 재현 |
| H1 경고 구성 | 16/16이 유효한 `# 결과 NNN` 양식 | 결과 061~068, 077~084 |
| 허용 중복 경고 | 1건은 `ALLOW`에 이유까지 기록된 정보 | `check_doc_ownership.py`의 `ALLOW` |
| 제어문자 오경보 | 1건은 W&B의 완결된 `ESC[1;34m`·`ESC[0m` | 결과 074 원본 로그와 `check_control_chars.py` |
| LR 동기 검사 중단 | 정본 함수 이동 뒤 wrapper 외부 이름을 못 찾아 `NameError` | `check_lr_factor_sync.py`와 `anneal_schedule.py` |
| WSL launcher 오인 | 권장표의 5개 `.sh` 중 선결이 `없음`인 3개를 W1 오류로 판정 | 최종 safe-profile의 `check_pending.py` 출력 |

반복의 근본 원인은 네 가지다.

1. **종료조건 부재**: 검사 결과는 보고되지만 WIP close와 기계적으로 연결되지 않는다.
2. **심각도 혼합**: 검토가 끝난 허용 정보도 경고 수에 더해져 “경고는 늘 남는 것”이라는 관행을 만든다.
3. **전이 시점 누락**: 제안서 완료 이관과 live 문서 수정 시 그 상태에 필요한 메타데이터를 같은
   트랜잭션에서 검사하지 않는다.
4. **실행 프로필 충돌**: 종합 정적 스위트에는 Codex가 접근 금지된 보호 데이터 검사도 섞여 있어,
   안전하게 전수 실행할 수 있는 명령 하나가 없다. 부분 실행은 누락 여부를 사람이 기억하게 만든다.
5. **의존성 이동 회귀 부재**: AST로 함수 하나만 떼는 검사가 함수의 외부 의존성 이동을 별도 계약으로
   확인하지 않아, 정본 분리 뒤 검사기 자체가 실행 불능이 되어도 오래 누적됐다.
6. **교차 플랫폼 계약의 부분 이관**: queue와 handoff 검사는 `.sh`를 지원했지만 pending 검사는
   `.bat` regex를 그대로 유지했다. 개별 검사 PASS만 봐서는 같은 “실행 진입점” 개념의 분기를 못 본다.

**외부 근거**

없다. 저장소 내부 절차와 실제 검사 출력만으로 원인과 수용 기준을 정의할 수 있어 외부 자료를
조회하지 않았다.

## 6. 방법

| 단계 | 무엇 | 비용 | ★**다음으로 가는 조건** |
|---|---|---:|---|
| M0 | 각 검사를 보호경로 접근 여부로 분류하고 `codex-safe`·`project-full` 프로필 정의 | ⚙ 0.5h | 모든 검사에 소유 프로필과 NOT_RUN 이유가 하나씩 있음 |
| M1 | 출력 심각도를 오류·조치경고·허용정보·NOT_RUN으로 표준화 | ⚙ 0.5h | 허용정보가 warning count를 올리지 않음 |
| M2 | 제안서 상태 전이와 live 문서 수정 직후 metadata 검사를 실행하는 좁은 진입점 추가 | ⚙ 0.5~1h | P번호/PNone·날짜 결함 fixture가 실패를 재현 |
| M3 | `wip.py --close` 앞에 현재 WIP의 안전 프로필 증거를 요구하는 독립 pre-close 검사 추가 | ⚙ 1~2h | 오류·조치경고가 있으면 close 거부, NOT_RUN은 이유와 함께 보존 |
| M4 | `new_handoff.py`가 프로필·오류·조치경고·NOT_RUN을 구조화해 기록 | ⚙ 0.5~1h | 새 handoff 회귀와 기존 handoff read-only 호환 PASS |

구현 원칙은 다음과 같다.

- 검사기를 약하게 만드는 allowlist 증가는 마지막 수단이며, 이유와 결함 주입 fixture를 함께 둔다.
- 공통 스키마처럼 동일해야 하는 정보는 소유권 신호에서 제외하되, 서술 본문 복사는 계속 검출한다.
- `NOT_RUN`은 실패를 숨기는 0으로 바꾸지 않고 금지 경로·도구 부재·사용자 실행 경계를 명시한다.
- 과거 완료 WIP를 소급 수정하지 않는다. 새 종료 계약 적용 이후의 WIP부터 강제한다.

## 7. 거절하면 못 하는 것

현재 부채 자체는 이번 교정으로 해소할 수 있다. 다만 후속 자동화를 거절하면 새 세션이 정적 실패를
“기존 부채”로 분류해 WIP를 닫는 일을 기계적으로 막지 못하고, 보호경로 때문에 전체 스위트를
실행하지 못하는 상황에서 검사 누락을 계속 사람이 기억해야 한다.

## 8. 위험 — 실행하면 무엇이 잘못될 수 있나

| 위험 | 어떻게 드러나나 | 완화 |
|---|---|---|
| pre-close가 다른 세션 WIP까지 검사 | 현재 작업과 무관한 원장 때문에 close 실패 | 정확한 `--file`과 세션 ID만 검사 |
| 허용정보 전환이 진짜 경고를 숨김 | warning 수는 0인데 결함 fixture도 통과 | 심각도 변경마다 독립 결함 주입 fixture 필수 |
| 안전 프로필이 새 검사를 누락 | 새 검사 파일은 생겼지만 어느 프로필에도 없음 | 검사 목록 양방향 inventory gate 추가 |
| 날짜 자동수정이 의미 없는 churn 생성 | 내용 변화 없이 날짜만 매번 바뀜 | 수정 파일만 검사하고 날짜 쓰기는 자동이 아니라 명시 패치로 유지 |
| 보호경로 검사를 PASS처럼 표시 | `codex-safe` 성공이 project-full 성공으로 보고됨 | 프로필명과 NOT_RUN 개수를 결과·handoff에 항상 병기 |
| 종료 게이트가 오래된 경고를 일괄 숨김 | accepted 항목에 근거가 없거나 만료됨 | 허용 근거·소유자·재검토 조건 없이는 `ACCEPTED_INFO` 금지 |

계측 위험은 “경고 0” 자체를 성공으로 오인하는 것이다. 따라서 수용 기준에는 실제 결함 fixture가
계속 실패하는지와 금지된 검사가 `NOT_RUN`으로 남는지를 함께 둔다.

## 9. 대안

| 안 | 무엇 | 장점 | 단점 |
|---|---|---|---|
| **A** | 문서에 “부채를 남기지 말라”는 규칙만 추가 | 구현비가 가장 작음 | 이번처럼 보고 후 close하는 흐름을 기계적으로 막지 못함 |
| **B** | **권장:** 안전 프로필 + 심각도 분리 + pre-close 증거 + 상태 전이 검사 | 보호경계를 지키면서 조치 가능 부채를 종료 전에 차단 | 도구·회귀·handoff 계약을 함께 바꿔야 함 |
| **C** | 모든 경고를 오류로 승격 | 규칙이 단순함 | 승인정보·환경 NOT_RUN까지 작업을 막아 경고 무시 관행을 재생산 |
| **D** | 아무것도 안 한다 | 비용 0 | 기존 부채라는 이름으로 같은 실패가 다시 누적될 수 있음 |

### ★권장안과 근거

**B안을 권장한다.** 이번 재현은 “검사가 없어서”가 아니라 검사 결과의 심각도와 WIP 종료가 연결되지
않아서 생겼다. 안전 프로필은 보호 데이터 접근 금지와 전수검증 요구를 동시에 만족시키고,
pre-close 증거는 보고만 하고 넘기는 경로를 직접 차단한다. 구현 후에도 이는 정적 절차
`STATIC_ONLY`이며, GPU·모델·smoke E2E 성공을 의미하지 않는다.
