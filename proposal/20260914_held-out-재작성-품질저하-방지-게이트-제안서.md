## 1. 배경 — 왜 지금 이 제안을 하나

[`review_request/20260908_held-out-v2.7-증보-요청서.md`](../review_request/20260908_held-out-v2.7-증보-요청서.md)
§8은 v2.9의 위치·문장 길이·정형구 편향을 줄이면서 D9를 높이도록 v3.0 재작성을 요청했다.
v3.0은 구조 감사에서는 통과했지만, 사용자가 독립 seed2 체크포인트 여섯 개로 수행한 실제
census에서 다음과 같이 합격선을 크게 밑돌았다.

| v3.0 독립 seed2 관측 | 값 | 판정 |
|---|---:|---|
| D9(2/6·3/6·4/6 정답 문항) | 854/4,500 = **19.0%** | 목표 60% 미달 |
| 전부 맞힘 B1 | 861 = 19.1% | 정보 0 |
| 전부 틀림 B2 | 2,072 = 46.0% | 정보 0 |
| 정보 0 합계 | 2,933 = **65.2%** | 계산비의 약 3분의 2 |
| 정보량 | 평균 0.2826 bit, 합계 1,271.7 bit | 낮음 |
| 실제 난이도 | mid 35.5% > hard 34.5% > easy 33.0% | `easy > mid > hard` 실패 |
| 관계별 D9 하위 | 목적수단 7.1%, 인과 9.9%, 시간순서 14.0% | 가족 편향 지속 |

### 1.1 v2.9와의 원시 비교 — 숫자는 보이지만 인과 비교는 아니다

| 지표 | v2.9 | v3.0 | 원시 차이 |
|---|---:|---:|---:|
| B1 전부 맞힘 | 552(12.3%) | 861(19.1%) | +309, **+6.9pp** |
| B2 전부 틀림 | 1,656(36.8%) | 2,072(46.0%) | +416, **+9.2pp** |
| B1·B2 밖에서 일한 문항 | 2,292(50.9%) | 1,567(34.8%) | -725, **-16.1pp** |
| D9 | 1,357(30.2%) | 854(19.0%) | -503, **-11.2pp** |
| 정보 0 | 2,208(49.1%) | 2,933(65.2%) | +725, **+16.1pp** |
| 정보 합계 | 1,893.7 bit | 1,271.7 bit | -622.0 bit, **-32.8%** |

그러나 위 표에는 **판본과 모델 패널이 동시에 바뀐 교락**이 있다.

| 조건축 | v2.9 기록 | v3.0 기록 | 같나 |
|---|---|---|---|
| 문항 수·seed·PMI | 4,500 · 99 · on | 4,500 · 99 · on | 같다 |
| 체크포인트 수 | 6 | 6 | 같다 |
| 모델 패널 | `*_muon15` 여섯 개 | 독립 `*_s2` 여섯 개 | **다르다** |
| 모델 정확도 범위 | 29.8~40.7%, 폭 10.9pp | 34.4~36.4%, 폭 2.0pp | **다르다** |

D9는 문항 특성뿐 아니라 모델들의 능력 폭과 응답 상관에도 달라진다. 따라서 원시 차이는
“v3.0 독립 합격 실패”에는 충분하지만, **-11.2pp 전부가 재작성 때문이라는 인과 주장에는
불충분**하다. 같은 seed2 여섯 개로 v2.9를 한 번 재야 판본 효과를 분리할 수 있다.

### 1.2 확인된 개선과 악화

**개선으로 확인되거나 유력한 항목**

- v3.0의 gold는 각 1,125개이고, 여섯 모델의 선택 위치도 각각 24.1~26.1%라 위치 단서는
  관측되지 않았다.
- 조건·시간순서·부분전체의 네 의미형은 생성·정적 감사에서 각각 141/141/141/140으로
  균형화됐다. 선택지 문구만 쓰는 기준선도 23.1%로 우연 25% 수준이었다.
- 관계별 원시 D9에서 조건은 2.1%→33.6%, 부분전체는 11.5%→17.2%였다. 다만 모델 패널이
  달라 **후보 개선**이지 통제된 개선 판정은 아니다.
- 새 JSON은 모델별 `per_pick` 4,500개와 15개 모델쌍의 family CI를 모두 보존한다. 이는
  데이터 품질보다 **감사 가능성의 개선**이며, v3.0에서 3/15쌍만 `b_better`, 12/15는
  `overlap`이었다.

**악화 또는 독립 합격 실패로 확인된 항목**

- v3.0 자체의 D9 19.0%, 정보 0 65.2%, 난이도 비단조는 패널 비교 없이도 실패다.
- 원시 관계별 D9는 대조 -15.5pp, 상하위 -31.6pp, 반의 -18.0pp, 시간순서 -3.9pp,
  인과 -27.6pp, 목적수단 -29.9pp였다. 조건·부분전체를 고치는 동안 다른 가족의 유용성을
  보존하는 게이트가 없었다는 경고다.
- 난이도 라벨은 v2.9의 `easy > hard > mid`에서 v3.0의 `mid > hard > easy`로 바뀌었고,
  세 평균의 폭도 2.5pp뿐이다. 생성 라벨 분포 10/70/20을 맞춘 것과 실제 난이도를 맞춘 것은
  별개였다.

### 1.3 왜 이런 일이 생겼나 — 확인 사실과 추론의 경계

| 원인 후보 | 근거 수준 | 설명 |
|---|---|---|
| 통제군 누락 | **확인** | 요청서는 v3.0 최종 패널을 Muon→seed2로 바꿨지만, 같은 seed2로 v2.9를 재는 교차 셀을 요구하지 않았다. |
| 전면 재작성 | **확인** | v3.0은 4,500개 ctx·choices를 전부 바꿨다. v2.9에서 이미 일하던 문항을 보존할 canary·rollback 계약이 없었다. |
| 정적 proxy와 동적 목적의 불일치 | **확인** | 위치·길이·의미형 균형은 통과했는데 D9·정보량·난이도는 실패했다. 형식 균형만으로 모델 변별력을 보장하지 못한다. |
| 독립 파일럿 계약의 실행성 부족 | **확인** | 요청서는 독립 파일럿을 요구했지만 정확한 패널·로그·전면 생성 전 중단 조건을 제출물 계약으로 고정하지 않았다. |
| 6개라는 수만 확인한 D9 문턱 | **분석** | 이론적 격자 상한 78.1%는 패널의 실효 다양성을 보장하지 않는다. v3 패널 정확도 폭 2.0pp는 D9를 낮출 수 있다. |
| 특정 문장 결함이 직접 원인 | **미확인** | 이번 범위에서는 보호 데이터 원문을 읽지 않았다. 개별 문항의 의미 오류·자연성 때문에 실패했다고 단정하지 않는다. |

이 문제는 데이터셋 팀만의 단순 작성 오류로 돌릴 수 없다. **이전 AI 지시가 독립 검증을
요구하면서도 통제 baseline, 작은 canary, 보존·rollback, 반복 상한을 함께 주지 않은 설계
결함**이 핵심이다. §8.4의 “우선 세 관계 최소 1,800개”와 최종 관계 균형상 가능한 1,689개가
모순됐던 점도 생성 전에 기계적으로 거르지 못했다.

## 2. 목적 — 무엇을 알아내거나 얻으려 하나

held-out 새 판을 한 번에 전면 재작성해 결과가 나빠지는 일을 막고, **같은 모델 패널의 paired
baseline → 작은 canary → 한 번의 full candidate → 한 번의 봉인된 독립 판정**으로 품질을
올리되 재작성 횟수와 GPU 비용을 사전에 제한한다.

## 3. 성과물 — 승인하면 무엇이 생기나

| 산출물 | 형태 |
|---|---|
| 판본×모델 패널 조건 서명 | JSON에 판본, 모델 spec, preset, data, tokens, seed, PMI, n을 명시 |
| paired baseline 보고 | 같은 seed2 패널의 v2.9↔v3.0 D9·정보량·관계·ID별 차이 |
| canary 생성 계약 | 전체의 10%인 450개를 관계별 56/57개로 층화한 후보와 보존 대조군 |
| 다목적 승격 게이트 | D9뿐 아니라 정보 0, bit, 관계별 비퇴행, 난이도 단조성, 중복·오염을 함께 판정 |
| 중단·rollback 계약 | canary 최대 2회, full candidate 최대 1회, 독립 패널 최대 1회 |
| 감사 가능 산출물 | 콘솔 로그, JSON, 변경 ID, `relation`·`difficulty`·`family_id`를 잇는 진단 manifest |

이 성과물은 “다시 써 보면 언젠가 좋아질 것”을 “어느 단계에서 얼마를 쓰고 중단할지”로
바꾼다. 실패한 후보는 결과로 보존하고 현행 benchmark를 자동 교체하지 않는다.

## 6. 방법

### 6.1 판정 벡터와 조건 서명을 먼저 고정

새 판본을 쓰기 전에 다음을 한 행의 조건 서명으로 동결한다.

```text
dataset_version / ids / model_tag=preset 6개 / checkpoint family / data / tokens /
seed / PMI / n / code revision / JSON path / log path
```

D9 60%는 절대 목표로 유지하되 단독 승격 기준으로 쓰지 않는다. 같은 패널의 직전 판본 대비
`D9`, `zero_info`, `bits_total`, 관계별 D9, 난이도 순서를 함께 본다. 패널 정확도 폭과 모델쌍
불일치도도 기록해 “모델 여섯 개”가 곧 “독립 계기 여섯 개”라는 오해를 막는다.

### 6.2 단계와 게이트

| 단계 | 무엇 | 비용 | 다음으로 가는 조건 |
|---|---|---:|---|
| **G0 통제 baseline** | 같은 seed2 여섯 개로 v2.9를 1회 평가해 v3.0과 paired 비교 | ⚙0.9 GPU-h | 조건 서명 일치, skip 0, JSON·자동 로그 존재 |
| **G1 원인 분리** | ID·relation·difficulty별 `v2.9→v3.0` 전이를 계산하고 패널 효과와 판본 효과 분리 | ⚙1h AI | 보존할 가족과 교체 후보가 수치로 분리됨 |
| **G2 10% canary** | 450개만 층화 교체. 기존 450개와 후보 450개를 같은 설계 패널로 paired 평가 | ⚙0.15h/회 | D9·bit 비퇴행, 정보 0 비증가, 목표 가족 개선, 비목표 가족 급락 없음 |
| **G3 full candidate** | canary를 통과한 규칙만 적용하고 기존 유효 문항은 보존 | 데이터팀 1회 | 정적 게이트 전부 PASS; 설계 패널에서 paired 개선 |
| **G4 봉인 final** | 데이터팀이 보지 않은 독립 패널로 딱 1회 평가 | ⚙0.9 GPU-h | 절대 목표와 비퇴행 벡터 충족 시에만 승격 |
| **G5 중단/rollback** | final 실패 시 현행 판본 유지, 후보는 HOLD로 보존 | 0 GPU-h | 새 독립 패널·새 가설 승인 전 재작성 금지 |

`G2`의 통계 문턱은 결과를 본 뒤 정하지 않는다. 구현 승인 때 직전 판본 paired bootstrap의
95% CI와 허용 비퇴행 폭을 먼저 문서에 동결한다. 가족 수가 8개뿐인 현 `relation` bootstrap을
과신하지 않도록 `family_id`를 추가하고, 관계 안의 여러 의미 가족을 재표집 단위로 쓴다.

### 6.3 무한 반복을 막는 hard stop

1. canary 수정은 **최대 2회**다. 두 번 모두 게이트를 못 넘으면 생성 규칙을 폐기하고 데이터는
   더 쓰지 않는다.
2. full 4,500 후보 생성은 **최대 1회**다. 전면 재작성 대신 통제 baseline에서 유효한 문항을
   보존한다.
3. 봉인된 독립 패널은 **판본당 1회**만 연다. 결과의 item ID를 데이터셋 팀에 되돌려 같은
   패널에 맞추지 않는다.
4. 독립 패널 결과를 사용해 다음 판을 설계하려면 그 패널은 설계군으로 강등되고, 새 final
   패널이 확보될 때까지 다음 판은 `CALIBRATED / FINAL_NOT_RUN`으로 남는다.
5. “60%가 될 때까지 재작성”은 금지한다. 두 canary 또는 한 final 실패 뒤에는 새 가설·새 패널·
   새 비용 승인을 받아야 한다.

### 6.4 현재 v3.0에 적용할 최소 조치

- v3.0은 **`STATIC_PASS / INDEPENDENT_D9_FAIL / PROMOTION_HOLD`**로 보존한다.
- 먼저 v2.9×seed2 한 셀만 채운다. 이 결과 전에는 “v3.0이 v2.9보다 11.2pp 악화”라고
  확정하지 않는다.
- v2.9×seed2에서도 D9가 비슷하게 낮다면 주원인은 패널/문턱 교락일 수 있으므로 데이터 재작성
  대신 panel 계약을 고친다.
- 같은 패널에서도 v3.0이 낮다면 전면 재작성의 회귀로 판정하되 즉시 v3.1 전면 재작성을 하지
  않고, 보존 가능한 v2.9 가족과 v3.0의 후보 개선 가족을 canary 설계 입력으로만 쓴다.

## 7. 거절하면 못 하는 것

현재 v3.0을 승격하지 않고 v2.9 또는 기존 평가판을 계속 쓰는 것은 가능하다. 다만 v3.0 실패가
데이터 재작성 때문인지 seed2 패널 특성 때문인지 분리할 수 없고, 다음 재작성도 같은 방식으로
전면 생성·사후 GPU 판정·재실패를 반복할 위험이 남는다.

## 9. 대안

| 안 | 무엇 | 장점 | 단점 | 영향도 | 수행비용 |
|---|---|---|---|---|---|
| **A** | v3.1을 다시 4,500개 전면 재작성하고 같은 S2로 반복 | 가장 단순 | 과적합·회귀·무한 반복, 원인 분리 불가 | 데이터 전체 | 높음 |
| **B** | **같은 패널 baseline + 10% canary + 보존형 full + 봉인 final + hard stop** | 인과 비교, 회귀 차단, 비용 상한 | 도구·manifest 계약을 먼저 만들어야 함 | 코드·데이터·검증 문서 | 중간 |
| **C** | v3.0을 폐기하지 않고 HOLD로 두며 v2.9를 계속 사용 | 추가 GPU·생성 비용 0 | 구조 개선을 동적 품질로 연결하지 못함 | 상태 문서만 | 낮음 |
| **D** | 관계별로 v2.9/v3.0 중 나은 부분을 즉시 혼합 | 일부 수치 빠른 회복 가능 | 현재 패널 교락과 acceptance 재사용 때문에 선택 편향 | 데이터·평가 계약 | 중간~높음 |

### ★권장안과 근거

**B안을 권장한다.** 현재 필요한 첫 조치는 새 데이터를 또 쓰는 것이 아니라 v2.9×seed2
통제 셀 하나를 채우는 것이다. 그 뒤에도 canary 두 번과 full 한 번이라는 상한을 넘지 않으므로
품질이 좋아질 때까지 무한 재작성을 반복하지 않는다. A·D는 현재 실패 응답에 과적합할 위험이
크고, C는 안전하지만 이미 확인한 구조 개선을 살릴 방법을 닫는다.

승인 범위는 별도로 나눈다.

1. 이 제안 승인
2. G0 비교 실험 계획·사용자 실행 승인
3. G1 결과를 본 뒤 canary 도구·데이터 요청 승인

제안 승인만으로 데이터셋 수정, 모델 실행, 새 판본 생성, 실험계획 작성을 시작하지 않는다.
