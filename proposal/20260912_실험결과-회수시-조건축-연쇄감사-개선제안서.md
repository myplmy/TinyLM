# 제안 — 실험결과 회수 시 조건축·인과주장 연쇄감사를 강제한다

> **작성** 2026-09-12 · **갱신** 2026-09-13 · **상태** ✅B안 승인·`STATIC_ONLY` 구현 · **분류** 작업방식 / 계측
> 양식: [`proposal/README.md`](README.md) §3. 승인 전에는 스킬·스크립트를 구현하지 않았고, 사용자 승인 뒤 B안 범위만 구현했다.

---

## 1. 배경 — 왜 지금 이 제안을 하나

P088 Stage10 결과를 처음 회수할 때 같은 1.2B 풀의 AdamW/Muon 최종 손실 차이
**−0.0246875**와 `pool/tokens=1.0`은 기록했지만, 600M→1.2B가 무엇을 바꾼 실험인지 끝까지
분해하지 않았다. 사용자 지적 뒤 다시 대조하자 다음 조건이 한꺼번에 드러났다.

| 조건축 | 실제 P088 Stage10 조건 | 처음 해석에서 빠진 영향 |
|---|---|---|
| 데이터 풀 | t600·t1200 모두 명목 1.2B, 실제 train 약 1.194B | 풀 확대가 아님 |
| 학습 draw | 600,047,616→1,200,095,232 | 약 0.503→1.005 epoch-equivalent 노출 증가 |
| 샘플러 | 균등 무작위 시작점, 복원추출 | 순차 epoch 증가가 아님; 기대 유니크 약 472M→759M |
| 스케줄 | WSD 비율형, 전체 steps 4,578→9,156 | 노출량뿐 아니라 절대 WSD 지평도 증가 |
| 학습 언어 | 기대 한국어/영어 25/75 | 두 팔은 같은 기대 구성이나 실제 draw별 비율은 미계측 |
| 평가 언어 | val 한국어 0% | 한국어 품질과 한영 종합 품질은 `NOT_RUN` |

이 정보는 새로 생긴 것이 아니었다. Codex 00 R37·R39, Codex 01의 풀·언어 함정, P088 계획,
결과 075의 앞 절, 실제 Loader 코드에 흩어져 있었다. 현행 `log-to-result` 체크리스트도
풀·토크나이저·학습토큰·steps·grad-ckpt 일치를 묻지만, **실제 draw·샘플링 방식·스케줄의
절대 지평·학습/평가 언어 구성을 한 묶음으로 재구성해 허용 가능한 주장까지 제한하지는 않는다.**

따라서 직접 원인은 GPT가 이미 읽은 조건축을 결론에 합성하지 않은 판단착오이고, 구조적 원인은
조건을 한 행의 서명으로 만들고 주장 유형과 대조하는 강제 장치가 없다는 점이다.

## 2. 목적 — 무엇을 알아내거나 얻으려 하나

실험 결과를 문서화할 때 비교쌍의 **풀·draw·샘플러·스케줄·언어·평가 경로**를 먼저 하나의
조건 서명으로 확정하고, 일치하지 않는 축이 있으면 직접 인과주장을 자동으로 보류하도록 한다.

## 3. 성과물 — 승인하면 무엇이 생기나

| 산출물 | 형태 |
|---|---|
| 조건 서명 계약 | 결과문서의 `비교 조건 서명` 표와 필수 필드 정의 |
| 결과 회수 절차 | `.agents/skills/log-to-result/SKILL.md`의 선행 감사·완료 체크리스트 보강 |
| 정적 대조기 | `scripts/check_result_conditions.py` 또는 기존 결과 검사기의 독립 규칙 |
| 회귀 fixture | 같은 풀/다른 draw, 다른 풀/같은 steps, 언어비·val 변화, 비율형 WSD 사례 |
| 판정 어휘 | `DIRECT_PAIRED`, `PARTIAL_CONFOUNDED`, `DESCRIPTIVE_ONLY`, `NOT_RUN` |
| 연쇄 갱신표 | 결과→계획→목록→기준표→COMPASS에 같은 한계가 남았는지 대조 |

과거 결과 전수를 소급 재작성하지 않는다. 이미 재감사한 P088 §19와 이후 신규·갱신 결과에 먼저
적용하고, 과거 문서는 실제 의사결정에 다시 쓰일 때만 별도 승인 아래 감사한다.

## 4. 비용

| 항목 | 양 |
|---|---:|
| GPU | 0 GPU-h |
| AI 작업 | ⚙4~6 engineer-h |
| ★사용자가 직접 해야 하는 일 | ⚙20~30분; 필드·판정 어휘와 구현 파일 승인 |
| 디스크 | ⚙200 KiB 미만; 스크립트·fixture·문서 |

기존 결과 전수 소급감사는 이 비용에 포함하지 않는다. P088 외 과거 결과 1건당 조건 원본 대조에
⚙15~30분이 추가될 수 있다.

## 5. 원리·근거

**우리 실측**

| 근거 | 값 | 출처 |
|---|---|---|
| P088 Stage10 동일 풀 | t600·t1200 모두 `--pool-tokens 1200M --exact-cache` | 결과 075 §19, P088 계획 |
| 실제 draw | 600,047,616→1,200,095,232 | `steps × micro_bs × accum × seq` |
| 샘플러 | 무작위 시작점 복원추출 | `tinylm/data/loader.py` |
| 평가 언어 경계 | val 한국어 0% | 결과 075 §19, P088 계획 |
| 최초 문서화의 누락 | Muon 차이와 풀/토큰 비만 연결하고 sampler·WSD·언어축 결합 누락 | 현 WIP 8~9번 재감사 |
| 현행 절차의 빈틈 | 비교 일치 체크는 있으나 조건 서명·주장 등급·언어축 필수 필드 없음 | `log-to-result/SKILL.md` §4 |

**외부 근거**는 필요하지 않다. 이 제안은 새 학습 방법이 아니라 저장소에서 이미 관측한 조건을
잃지 않게 하는 내부 계측·감사 계약이다. 외부 논문을 인용해도 Loader와 실제 배치의 조건을 대신
증명할 수 없다.

## 6. 방법

| 단계 | 무엇 | 비용 | ★다음으로 가는 조건 |
|---|---|---:|---|
| 0 | 사용자가 스킬·스크립트·문서 계약 변경을 명시 승인 | 0.2h | 정확한 allowlist 확정 |
| 1 | 조건 서명 필드와 판정 어휘를 fixture 문서로 먼저 확정 | 0.8h | P088 네 비교가 기대 판정으로 분류 |
| 2 | `log-to-result`에 결과 수치 판독보다 앞선 조건축 재구성 단계를 추가 | 0.8h | 누락 필드가 있으면 완료 체크가 실패 |
| 3 | JSON·배치·계획·Loader 정본을 대조하는 정적 검사 구현 | 2.0h | 양성·음성 fixture 전부 기대 exit code |
| 4 | 결과·계획·기준표·COMPASS의 주장 등급 연쇄 대조 추가 | 1.2h | 한 문서만 한계를 누락하면 실패 |
| 5 | P088 §19를 비파괴 회귀 fixture로 검사하고 사용자 E2E 범위를 분리 보고 | 0.8h | 정적 PASS, GPU·모델 `NOT_RUN` 유지 |

필수 조건 서명은 최소 다음 필드를 가진다.

```text
pool_id / actual_pool_tokens / pool_override
steps / micro_bs / accum / seq / actual_draw_tokens
sampler_with_replacement / expected_unique_tokens / sequential_epoch_claim
scheduler / warmup / anneal_start / decay_fraction / absolute_schedule_horizon
train_language_expected / train_language_observed
eval_dataset / eval_language / tokenizer / grad_ckpt
comparator_tag / matched_axes / changed_axes / unmeasured_axes / permitted_claim
```

검사기는 수치를 대신 추측하지 않는다. JSON·배치·계획에서 확정되지 않는 필드는 `UNKNOWN`으로
남기며, `UNKNOWN`이 인과주장에 필요한 축이면 `DIRECT_PAIRED`를 거부한다. 비율형 스케줄에서 steps가
바뀌면 “학습토큰만 변화”라고 쓸 수 없고, 평가 언어가 0%인 능력은 자동으로 `NOT_RUN` 경고를 낸다.

## 7. 거절하면 못 하는 것

P088의 현재 정정 결과를 사용하는 데는 문제가 없다. 이미 사람 재감사로 풀·반복·WSD·언어 한계를
반영했다. 다만 다음 결과 회수에서도 정보가 여러 문서에 흩어져 있으면 같은 판단 누락을 기계적으로
막을 수 없고, 사용자가 다시 특정 축을 물어야 뒤늦게 일반화 범위가 좁아질 수 있다.

## 8. 위험 — 실행하면 무엇이 잘못될 수 있나

| 위험 | 어떻게 드러나나 | 완화 |
|---|---|---|
| 조건 서명이 또 다른 수치 사본이 됨 | 계획·JSON과 값이 달라짐 | 값 옆에 소유 정본과 추출법을 기록하고 기계 대조 |
| Loader 의미를 파일명으로 추측 | `epoch`·`unique` 판정 오기 | 실제 sampler 코드 또는 기록 필드가 없으면 `UNKNOWN` |
| 기대 언어비를 실제 draw 비율로 오인 | 미계측 값을 실측처럼 보고 | expected/observed 필드를 분리하고 observed 없으면 `NOT_MEASURED` |
| 비교축이 너무 엄격해 모든 결과가 무효 | 유용한 방향 관측까지 사라짐 | 인과 판정만 제한하고 기술적 관측은 `DESCRIPTIVE_ONLY`로 보존 |
| 과거 문서를 대량 변경 | 역사 기록·diff가 오염 | 신규/현재 의사결정 결과부터 적용, 소급은 파일별 승인 |
| 스킬만 먼저 바뀌어 검사와 불일치 | 문서상 필수인데 도구가 안 봄 | 스킬·schema·fixture·검사를 한 승인 묶음으로 배포 |
| 정적 PASS를 실험 유효성으로 과장 | GPU·평가를 돌린 것처럼 읽힘 | 정적 계약은 `STATIC_ONLY`, 실제 품질은 사용자 로그만 |

영향 축은 결과 문서·계획·기준표·COMPASS·결과 회수 스킬·정적 검사이며, 데이터 원본·체크포인트·
GPU 학습에는 영향이 없다. 구현 중에도 `datasets/TinyDataset/**`는 접근하지 않는다.

## 9. 대안

| 안 | 무엇 | 장점 | 단점 |
|---|---|---|---|
| **A** | `log-to-result` 체크리스트에 네 문장만 추가 | 비용이 가장 작음 | 이미 있던 규칙을 합성하지 못한 사고라 재발 방지력이 약함 |
| **B** | 조건 서명 + 주장 등급 + 정적 대조기 | 조건 차이를 한눈에 보고 인과 과장을 기계적으로 차단 | schema·fixture·검사 구현 비용이 듦 |
| **C** | 현행 유지, 사람 재검토에 의존 | 비용 0 | 사용자 지적 전까지 누락을 발견하지 못한 방식이 그대로 남음 |

### ★권장안과 근거

**B를 권장한다.** 이번 사고는 정보가 없어서가 아니라 이미 읽은 정보를 결론에 결합하지 못해서
발생했다. A처럼 문장을 더 복제하면 Codex 00 R42의 “규칙 사본은 강제가 아니다” 문제를 반복한다.
B는 비교 전에 조건축을 구조화하고, 서로 다른 축이 있으면 허용 가능한 주장 등급을 낮추므로 직접
원인을 막는다. 다만 이 문서는 구현 승인이 아니며, 사용자가 정확한 변경 파일을 승인하기 전에는
`.agents/skills/log-to-result/SKILL.md`와 검사 스크립트를 수정하지 않는다.

## 10. 사용자 결정과 도입 결과 (2026-09-13)

- 사용자가 **B안 권장안 도입을 승인**했다.
- `scripts/check_result_conditions.py`와 회귀 fixture를 추가하고 `log-to-result` 절차를 갱신했다.
- 결과 075 §19의 네 비교는 각각 `DIRECT_PAIRED` 2건, `PARTIAL_CONFOUNDED` 1건,
  `DESCRIPTIVE_ONLY` 1건으로 구조화했다. 결과 076 §12~13의 세 비교는 `DIRECT_PAIRED`다.
- P005·P088 계획, 실험목록, 기준표, COMPASS에 같은 주장 등급과 한계를 연쇄 반영했다.
- 정적 검사는 문서에 적힌 조건의 내부 정합만 보며 GPU·모델·새 평가를 실행하지 않았다.
