## 2. ★핵심 발견

### (1) 데이터 풀 다양성 자체가 0.12 nats 짜리 레버
같은 **300M 학습토큰**인데 풀만 다르다:

| 조건 | dense val |
|---|---|
| 300M 풀에서 300M 학습 (정본 dense, 결과 001) | 3.8241 |
| **600M 풀에서 300M 학습** (p6d) | **3.7045** |

**차이 -0.1196.** 300M 풀 = 사실상 1 epoch → 반복 노출로 dense가 손해를 봤다. 학습토큰을
늘리지 않고 **풀만 2×로 키워 얻는 이득이 타잉 격차(+0.17)의 70%** 에 달한다.
→ **앞으로 모든 신규 기준선은 풀 ≥ 2× 학습토큰**에서 뽑아야 한다. (`--pool-tokens`)

### (2) plain tied 격차는 토큰이 늘어도 닫히지 않는다 (가설 기각)
+0.1486 → +0.1681 → +0.1656. 100M→600M **6배** 토큰에서 격차는 평평하다.
P002 시점의 "300M은 undertrained라 격차가 과대추정일 것"이라는 가설은 **기각**.
MLP 타잉의 손실은 학습 부족이 아니라 **용량 상한**에서 온다.

### (3) KD의 이득은 예산이 커질수록 줄어든다 (역스케일링)
p6tk 격차: **-0.1100(100M) → +0.0616(300M) → +0.0983(600M)**.
저예산에서는 KD+부모초기화가 정칙화처럼 작동해 **교사(dense)를 능가**하지만, 예산이 커지면
tied의 용량 상한이 드러나 격차가 벌어진다. 즉 **"KD가 타잉 격차를 소멸시킨다"는 결론에는
예산 의존 조건이 붙는다** — 300M에서는 판정기준 `≤+0.07` 성립, 600M에서는 불성립(+0.0983).

### (4) P017 헤드라인과의 관계 — **정정하지 않고 병기**(확인런 대기)
- 결과 005(P017)는 **정본 dense(3.8241, 300M 풀)** 대비 `t_kd_g8_k4` 가 **-0.0366** 으로 우세.
- 본 클린판은 **공정 풀(600M) dense(3.7045)** 대비 `p6tk` 가 **+0.0616** 으로 열세.
- 두 수치는 **직접 비교 대상이 아니다**(풀이 다름). 다만 (1)에 의해 정본 dense가 풀 핸디캡을
  안고 있었으므로, "tied+KD가 dense를 능가"는 **풀 아티팩트일 가능성**이 크다.
- **단정 보류 사유**: p6tk는 **full KD**(매 스텝 교사 forward)인데, P017은 **정적 k4가 full KD보다
  0.0417 우수**(3.7875 vs 3.8292)임을 보였다. k4 이득을 그대로 인정하면 공정 풀 300M 격차는
  **≈+0.020**, 600M은 **≈+0.057** 로 둘 다 판정기준 안에 들어온다.
- → **확인런 필요**: 600M 풀에서 `p6tk` 를 `--kd-every 4` 로 300M·600M 예산 재측정(§4).

### (5) 300M dense 의 `|g|max 4.3`
p6d 300M만 유일하게 4.3(다른 런 1.2~1.7). 발산은 없었고(skip 0) 최종 손실도 정상이라
치명적이지 않지만, 판정기준의 "`|g|max` 10 이상이면 학습 문제" 선에는 한참 못 미친다.
**dense 쪽 그래디언트가 tied보다 일관되게 큼**(tied는 전 예산 1.2~1.3) — 타잉·KD의
그래디언트 평활 효과로 해석.

### (6) 수확체감 곡선
dense: 4.3650 → 3.7045 → 3.5197. 100M→300M 이 **-0.6605**, 300M→600M 이 **-0.1848**.
3배·2배 증가임을 감안해도 기울기가 급격히 눕는다. **600M 이후 dense 품질 개선은 토큰보다
데이터 품질·아키텍처 쪽 레버가 유리하다**(P012 계열의 동기이지만 P012 측정은 결과 009 참조).

### (7) KD의 벽시계 비용은 예산에 비례해 악화
p6tk/p6d 시간비: 1.42× (100M) → 1.45× (300M) → **1.53×** (600M). full KD 는 교사 forward가
매 스텝이라 예산이 커질수록 총 오버헤드가 그대로 누적된다. → k4(교사 25%) 채택의 근거가 강해짐.

## 4. 후속 (우선순위)

1. **[필수] 공정 풀 k4 확인런** — `--pool-tokens 600M --exact-cache --init-from-tag p6d
   --kd-teacher-tag p6d --kd-every 4 --tag p6tk4` 로 300M(2289) · 600M(4578) 2건.
   비용 ≈ 2.1h + 4.3h. 이것으로 §2-(4) 를 확정하거나 P017 헤드라인을 정정한다.
2. **[중] 풀 스윕** — 300M 학습토큰 고정, 풀 300M/600M/1200M. (1)의 이득이 어디서 포화되는지.
   현재 데이터로는 "풀 2×가 0.12" 뿐이고 포화점을 모른다.
3. **[저] 600M 예산에서 g↓(g4) 또는 prelude/coda↑** — 판정기준이 지시하는 대응.

## 5. 재현 명령

```
python run100m.py prepare --data ko-en --tokens 600M --exact-cache
python run100m.py train --arch dense --data ko-en --tokens 300M --steps 2289 --micro-bs 8 --accum 16 --seq 1024 --lr 1e-3 --eval-every 100 --compile --pool-tokens 600M --exact-cache --tag p6d
python run100m.py train --arch tied  --data ko-en --tokens 300M --steps 2289 --micro-bs 8 --accum 16 --seq 1024 --lr 1e-3 --eval-every 100 --compile --pool-tokens 600M --exact-cache --mlp-group 8 --tag p6t
python run100m.py train --arch tied  --data ko-en --tokens 300M --steps 2289 --micro-bs 8 --accum 16 --seq 1024 --lr 1e-3 --eval-every 100 --compile --pool-tokens 600M --exact-cache --mlp-group 8 --init-from-tag p6d --kd --kd-teacher-tag p6d --ema 0.999 --tag p6tk
python run100m.py compare --data ko-en --tokens 300M --tag p6d --vs p6tk
```
(100M = `--tokens 100M --steps 763`, 600M = `--tokens 600M --steps 4578`)
