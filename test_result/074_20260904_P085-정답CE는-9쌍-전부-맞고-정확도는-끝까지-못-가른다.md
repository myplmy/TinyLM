## 1. 결론 세 줄

1. ★★**정답CE 서열은 세 과제 × 세 쌍 = 9쌍 전부 full-val 서열과 같다** (`d16 < d12 < mC`).
   n=400 에서 이미 3/3 이었고 **n=5,000 에서 9/9 로 굳었다.**
2. 🚫★★**정확도(argmax)는 끝까지 못 가른다.** n=400 → n=5,000 에서 격차가 **1.1~18배 줄었지만
   부호는 3/3 그대로**다. ★**piqa·arc_easy 는 이번에 문항을 전부 썼다**(1,838 / 2,376) —
   **더 늘릴 문항이 없다.** hellaswag 는 유도 필요 N 이 **약 45,000** 인데 전체가 10,042 다.
3. ✅**세 모델 전부 세 과제에서 우연을 넘었다** — n=400 에서 CI 가 우연을 포함하던 칸이 **다 닫혔다.**

→ ★**판정 3층의 ②(다운스트림)를 "정답CE" 로 좁힌다.** argmax 는 **우리 크기에서 반증력이 없다.**

## 3. ★★n=400 → n=5,000 — **무엇이 변했나**

⚠️**두 표본은 독립이 아니다.** `random.Random(99).shuffle(idx)` 뒤 앞에서 잘라 쓰므로
**n=400 은 n=5,000 의 부분집합**이다(`eval_bench_suite.py:418`). → *"뒤집혔나"* 가 아니라
*"4,600 문항이 더해지면서 어디로 갔나"* 가 옳은 질문이다.

| 비교 | 지표 | n=400 | ★**n=5,000** | 축소 |
|---|---|---:|---:|---:|
| d16 − d12 | 정확도 hellaswag | −2.3pp | **−0.6pp** | **3.8배** |
| | 정확도 piqa | −0.8pp | −0.7pp | 1.1배 |
| | 정확도 arc_easy | +0.8pp | +0.4pp | 2.0배 |
| | ★정답CE hellaswag | −0.1099 | **−0.1003** | **1.10배** |
| | ★정답CE piqa | −0.0386 | −0.0465 | 0.83배 |
| | ★정답CE arc_easy | −0.0869 | −0.0757 | 1.15배 |
| d12 − mC | 정확도 hellaswag | +3.6pp | **+0.2pp** | ★**18배** |
| | 정확도 piqa | +5.0pp | +0.4pp | ★**12.5배** |
| | 정확도 arc_easy | +3.2pp | +1.6pp | 2.0배 |

★★**정답CE 는 0.83~1.15배 = 사실상 불변**이고 **정확도만 1.1~18배 줄었다.**
→ 🚫**결과 067 §12.5 의 다운스트림 정확도 표는 크기가 최대 18배 부풀어 있었다.**
✅**부호는 다 살았다** — *"틀렸다" 가 아니라 "그 크기로 읽으면 안 됐다"* 이다.

### 3.1 그래서 067 §12.5 의 *"어긋난다"* 는 어떻게 되나

**여전히 어긋난다 — 그리고 이제 그것이 잡음이 아니라는 것도 안다.**
`d16` 은 full-val 을 −0.0412(자의 20배)로 이기면서 **정확도로는 hellaswag −0.6 · piqa −0.7 로 진다.**
🚫**piqa 는 전량을 썼으므로 그 −0.7pp 에는 표집 잡음이 없다** — 이 벤치마크 위에서는
**d16 이 실제로 진다.**

★**해석**: 정답 토큰열의 **확률은 d16 이 높은데**(CE), **오답보다 높은 확률을 주는 문항 수는 안 늘었다**(argmax).
= **분포가 전체적으로 좋아져도 결정 경계가 안 움직인다.** 우리 크기에서 **일반화된 관찰**이다.

### 3.2 ✅우연 수준은 이제 전부 넘었다

n=400 에서 `d16` 의 hellaswag CI 하한이 23.4(우연 포함), `mC` 는 두 과제가 포함이었다.
**n=5,000 에서는 아홉 칸 전부 CI 하한이 우연 위**다(최저 `d16` hellaswag 26.4 > 25.0).
★**"우리 81M 모델은 세 과제 전부에서 우연을 넘는다" 가 처음으로 확정**됐다.

## 4. ★검정력 — **정확도 축은 여기서 끝난다**

`p ≈ 0.28`, 비대응 근사 `SE(Δ) = √(2p(1−p)/n)`:

| 과제 | 현재 n | 현재 SE(Δ) | 관측 Δ | 유도 필요 n(t=2) | 전체 문항 |
|---|---:|---:|---:|---:|---:|
| hellaswag | 5,000 | 0.90pp | 0.6pp | ⚙**45,000** | **10,042** |
| piqa | 1,838 | 1.65pp | 0.7pp | ⚙**102,000** | ★**1,838(전량)** |
| arc_easy | 2,376 | 1.31pp | 0.4pp | ⚙**254,000** | ★**2,376(전량)** |

🚫★★**세 과제 모두 도달 불가**다. piqa·arc_easy 는 **문항이 더 없다.**

⚠️★**이 필요 n 은 비대응 근사라 상한**이다. **대응(McNemar)이면 크게 줄 수 있는데
🚫`eval_bench_suite` 가 문항별 정오를 안 남기고 버린다**(`run_mc` 의 `ok` 가 wilson 뒤 사라진다).
✅**고쳤다** — §6.

| arc_easy | d12 − d16 | −0.46pp | 236/247 | −0.50 | 37,938 | 2,376 | 16.0배 |
| piqa | d12 − mC | +0.44pp | 255/247 | +0.36 | 57,668 | 1,838 | 31.4배 |
| hellaswag | d12 − mC | +0.18pp | 275/266 | +0.39 | 133,581 | 5,000 | 26.7배 |
| piqa | d16 − mC | −0.27pp | 265/270 | −0.22 | 157,333 | 1,838 | 85.6배 |

★**최선의 짝이 45,000 → 2,451 로 18.4배 싸졌다.** 그리고 **보유 2,376 과의 차이가 3.2%** 다.

### 11.4 ★그래서 정확도 축을 **한 번만 더** 열 수 있다 — 문항이 있다

`arc_easy` 는 **test 2,376** 만 쓰고 있다. ★로컬 데이터셋 카드를 열어 확인했다
(`HF/datasets--allenai--ai2_arc/snapshots/*/README.md` 의 `dataset_info`):
**train 2,251 · test 2,376 · validation 570 = 5,197.**
전부 쓰면 필요 n 2,451 의 **2.1배**다.

| 무엇 | 지금 | 세 split 전부 |
|---|---:|---:|
| 문항 | 2,376 | ★**5,197** |
| `d16 − mC` 예상 z | +1.97 | ★**+2.9**(z ∝ √n) |
| `d12 − mC` 예상 z | +1.56 | +2.3 |

→ ★**"정확도로 두 모델을 가른 최초의 사례"** 가 여기서 나올 수 있다. ⚙0.6h · 학습 0.
⚠️**단 train split 을 쓰면 오염 위험을 함께 적는다** — ARC 는 우리 학습 스트림에 없지만
(fineweb-edu · 위키), **fineweb-edu 가 웹 전체를 긁으므로 문항이 섞였을 가능성은 0 이 아니다.**
🚫**KorQuAD 사고(결과 060 §7 · 우리 스트림의 94.8%)를 되풀이하지 않으려면 겹침을 먼저 잰다.**

### 11.5 ★§4·§8 정정 — **정확도 축은 "끝났다" 가 아니라 "비싸다"**

| 무엇 | §4·§8 의 문장 | ★**정정** |
|---|---|---|
| 필요 n | 45,000~254,000 | ★**2,451~157,333**(대응 검정) |
| 판정 | *"셋 다 도달 불가"* | ★**`arc_easy` 는 문항을 다 모으면 닿는다** |
| 규약 | *"판정 3층의 ②를 정답CE 로 좁힌다"* | ✅**유지** — 다만 근거를 *"argmax 는 원리적으로 못 쓴다"* 가 아니라 ★*"argmax 는 문항당 정보가 정답CE 의 1/18~1/100 이라 비싸다"* 로 바꾼다 |

★**정답CE 가 문항 하나에서 실수(real number)를 뽑고 argmax 는 비트 하나를 뽑는다** —
그 차이가 필요 n 의 배수로 그대로 나타났다. **규약은 그대로 두되 이유를 정확히 적는다.**

### 11.6 ⚠️W&B summary 가 **과제를 누적한다** — 시각화 제안서에 반영했다

`hellaswag` 업로드 블록의 세 번째 런 요약에 `bench/arc_easy/skipped 0` 이 이미 보인다.
같은 런 이름으로 `resume` 하므로 **summary 키는 지워지지 않고 쌓인다.**

✅**좋은 성질이다** — 한 모델의 세 과제가 **한 런의 summary 에 모인다**. 🚫**그런데 그것이
"모델 × 과제" 표를 만들지는 않는다** — W&B 의 Workspace 차트는 **런을 x 축에 놓지 과제를
놓지 않는다.** 이것이 사용자가 본 *"x 축에 태그명과 지표명이 함께 뜬다"* 의 정체다.
→ 처방은 [W&B 시각화 제안서](../proposal/20260904_wandb-벤치마크-시각화-구조.md) §3 이 갖는다.
