## 1. 측정 결과

`ms/step` 은 로그의 **누적 평균**이므로 compile 첫 스텝을 제거한 **정상상태**를 계산해 비교한다.
정상상태 = `(누적평균×250 − step0)/249`.

## 2. ★핵심 발견

### (1) `--no-ckpt` = -17.3% (단일 최대 엔지니어링 레버, 확정)
2982 → **2467 ms/step**. gradient checkpointing 의 재계산(forward 2회)이 사라진 만큼 그대로 이득.
비용은 VRAM **13.5GB** — WDDM 스필벽(~13~14GB) **바로 아래**. 즉 dense 300M 라인에서는
**`--no-ckpt` 가 쓸 수 있는 마지막 여유**이며, 여기서 micro_bs 나 seq 를 더 올릴 공간은 없다.

### (2) micro_bs↑ 는 이득이 없다 (연산바운드 확증)
mb12 는 OOM(16.8~17GB). 사용자 대체런 mb10/accum13(유효배치 133K, 15.2GB)은 2481 ms/step —
토큰당으로 정규화하면 **2481×131/133 ≈ 2444**, no-ckpt(2467)와 **-0.9%**(측정 노이즈 수준).
→ **SM 이용률은 이미 포화**. m100(d=768) GEMM은 mb8×seq1024 = M 8192 만으로도 연산바운드이며,
micro_bs 를 올려 얻을 런치오버헤드 절감은 없다. **VRAM만 1.7GB 더 쓰고 이득 0.**
핸드오프 §6의 "micro_bs↑" 레버는 **본 측정으로 폐기**.

### (3) KD 조합(k4 + 압축교사 + no-ckpt) = dense-nockpt 대비 +19% 만
tied+KD 의 교사 forward 오버헤드가 **2940 vs 2467 = +19.2%** 로 축소됐다.
비교 기준: P017 정본 `t_kd_g8` full KD(grad-ckpt ON) = 165.2분/2289 = **4331 ms/step**,
`k4` = 141.0분/2289 = **3696 ms/step**.
→ 세 레버(k4 + 압축교사 + no-ckpt)를 합치면 full-KD 대비 **-32%** 수준의 스텝시간.
단 §4 주의(측정 프로토콜이 달라 절대값 직접 비교는 참고용).

### (4) ★250스텝 런은 **불안정 구간**이라 품질 비교가 불가능하다 (0.11 발산의 진짜 원인)
#1 과 #2 는 **수학적으로 동일한 학습**이다(grad-ckpt 는 재계산일 뿐 수식 불변, 시드 동일).
그런데 step0 부터 미세하게 다르고(10.4122 vs 10.4120), 250스텝에서 **6.1156 vs 6.0034 = 0.1122**
로 벌어졌다.

**초기 진단(bf16 리덕션 순서만의 혼돈적 증폭)은 불완전했다.** 결과 json 의 `grad_max` 를 보면
원인이 더 구체적이다:

| 태그 | `grad_max`(warmup 이후) | `grad_peak_warmup` | n_skip |
|---|---|---|---|
| `sp_base` | **10.79** | 10.79 | 0 |
| `sp_nockpt` | **35.38** | 35.38 | 0 |
| `sp_nockpt_mb10` | 5.11 | 5.16 | 0 |
| `sp_kd_k4_comp` | 1.06 | 15.70 | 0 |
| (참조) 2289스텝 `dense` | **1.22** | 3.19 | 0 |
| (참조) 2289스텝 `t_kd_g8_k4` | **0.65** | 15.74 | 0 |

- 250스텝 런은 `warm = max(5, min(250//10, 100)) = 25` 라 warmup 이 짧고, **anneal 이 시작되는
  구간에서 LR 이 아직 peak 근처**다. 그래서 `|g|` 가 **10.8 / 35.4** 까지 튀었다 —
  **우리 판정기준의 "10 이상이면 학습 문제" 선을 두 런 모두 넘는다.**
- 즉 두 런의 0.11 격차는 "수렴한 모델 두 개의 재현 오차"가 아니라 **불안정 구간에서 서로 다른
  그래디언트 스파이크를 맞은 결과**다. 같은 설정인데 스파이크가 3배 차이(35.4 vs 10.8) 난 것이
  bf16 비결정성의 증폭을 보여주긴 하지만, **수렴 구간 σ 의 추정치로는 쓸 수 없다.**

**수정된 함의:**

- **250스텝급 짧은 런의 val 비교는 무의미**하다(결론 불변, 근거는 더 강해짐). mb10 의 5.8331 이
  "좋아 보이는" 것도 이 구간의 산물이다. P021 로그의 val 열은 **속도 벤치의 부산물**이다.
- **판정기준 `±0.07` 은 여전히 근거가 없지만, 0.11 을 그 반례로 인용해선 안 된다.**
  2289스텝 런들은 `grad_max` 0.5~1.2 로 안정적이므로 수렴 구간 드리프트는 훨씬 작을 가능성이 높다.
  **σ 는 미측정이라는 사실만 참**이다 → 캘리브레이션 런은 여전히 필요(P021 추가검증 A).
- **`--no-ckpt` 는 같은 설정에서 `|g|` 스파이크를 3배로 키웠다.** 수식은 같으므로 이는 고LR 초기
  구간의 수치적 취약성을 뜻한다. 긴 런에서는 `grad_max` 가 1.2 수준으로 안정됐지만,
  **`--no-ckpt` 런은 `grad_max` 를 확인하는 습관**을 들일 근거가 된다.
- **로그에 찍히는 `|g|` 는 10스텝 샘플이라 실제 최대를 숨긴다.** sp_base 의 인쇄값은 최대 4.51
  이었지만 실제 `grad_max` 는 10.79 다. **불안정 판정은 인쇄값이 아니라 json `grad_max` 로 한다.**

### (5) 배치파일 견고성 문제
`if errorlevel 1 goto ERROR` 때문에 [3/4] OOM 에서 배치가 중단되어 [4/4]를 사용자가 수동 실행해야
했다. **속도·스윕성 배치는 개별 런 실패가 후속 런을 막지 않도록** 해야 한다
(각 런 뒤 `if errorlevel 1 echo [WARN] skipped` 로 계속 진행). 신규 배치에 반영.

## 4. 측정 프로토콜 주의 (기록)

- 로그의 `ms/step` 은 **누적 평균**이라 스텝 수가 다른 런끼리 직접 비교하면 compile 첫 스텝의
  상각 정도가 달라 왜곡된다. 250스텝 런은 60초 compile 이 240ms/step 을 부풀린다.
  → **정상상태 환산식** `(누적평균×N − step0)/(N−1)` 을 쓰거나, 총 분/스텝을 쓴다.
- 2289스텝 런과의 절대 비교는 eval 횟수(`--eval-every 100 vs 999`)까지 달라 참고용.
- **인쇄되는 `|g|` 는 10스텝 샘플**이다. 안정성 판정은 json 의 `grad_max`(warmup 이후 전 스텝 최대)
  와 `grad_peak_warmup`(warmup 구간 최대)으로 한다. 본 결과 §2-(4)가 그 사례.
- **짧은 런은 `warm` 도 짧다**(`max(5, min(steps//10, 100))`). 250스텝이면 warmup 25스텝뿐이라
  스케줄 형태 자체가 긴 런과 다르다 → 속도 외 어떤 것도 이전하지 말 것.

## 5. 재현 명령 (전 5런 — `run100m_P021.bat` 원본 + 사용자 대체런)

```
REM [1] 기준
python run100m.py train --arch dense --data ko-en --tokens 300M --steps 250 --micro-bs 8 --accum 16 --seq 1024 --lr 1e-3 --eval-every 999 --compile --tag sp_base

REM [2] no-ckpt (채택)
python run100m.py train --arch dense --data ko-en --tokens 300M --steps 250 --micro-bs 8 --accum 16 --seq 1024 --lr 1e-3 --eval-every 999 --compile --no-ckpt --tag sp_nockpt

REM [3] mb12/accum11 -- ★OOM 확정. 재실행하지 말 것(16.8~17GB 필요, 한계 16GB).
REM     음성결과의 근거로만 보존한다.
python run100m.py train --arch dense --data ko-en --tokens 300M --steps 250 --micro-bs 12 --accum 11 --seq 1024 --lr 1e-3 --eval-every 999 --compile --no-ckpt --tag sp_nockpt_mb12

REM [3'] 사용자 대체런: mb10/accum13 (15.2GB, 완주하되 토큰당 이득 -0.9%)
python run100m.py train --arch dense --data ko-en --tokens 300M --steps 250 --micro-bs 10 --accum 13 --seq 1024 --lr 1e-3 --eval-every 999 --compile --no-ckpt --tag sp_nockpt_mb10

REM [4] KD 조합 (배치 [3] OOM 으로 중단돼 사용자가 수동 실행)
python run100m.py train --arch tied --data ko-en --tokens 300M --steps 250 --micro-bs 8 --accum 16 --seq 1024 --lr 1e-3 --eval-every 999 --compile --no-ckpt --kd --init-from --mlp-group 8 --kd-every 4 --kd-teacher-tag t_kd_g8 --tag sp_kd_k4_comp
```

> `sp_nockpt_mb12` 는 로그·체크포인트가 없다(backward 에서 OOM 종료). 위 명령은 **어떤 설정이
> OOM 이었는지**를 남기기 위한 기록이며 실행 대상이 아니다.
