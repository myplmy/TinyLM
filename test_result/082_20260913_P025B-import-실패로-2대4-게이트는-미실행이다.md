## 1. 한 줄

★★**이번 실행은 `tinylm` 패키지 import 실패로 첫 2:4 연산 전에 종료됐다.** 따라서 native 2:4 지원·정확성·input-gradient·속도는 실패가 아니라 모두 `NOT_RUN`이며, 진입 경로를 고친 새 Stage0b 재실행이 필요하다.

## 6. Stage0b 재실행(2026-09-14) — **import는 통과했고 native backend에서 지원 불가로 닫혔다**

> **로그**: `test_result/082_log_20260914_P025B_stage0b_sparse24_backend.txt`
>
> **배치**: `run_P025B_Stage0b_sparse24_backend-done.bat`
>
> **환경**: NVIDIA GeForce RTX 4070 Ti SUPER · `sm_89` · PyTorch 2.10.0
>
> **종료**: 진단 종료코드 3, 배치의 음성 게이트 분기

저장소 import는 정상 통과했다. 첫 실제 형상 `M=8192, K=768, N=2048`에서 다음과 같이
native 경로가 거부됐다.

```text
[GATE FAIL] M=8192 K=768 N=2048: RuntimeError: cuSPARSELt not supported on your machine.
```

이는 2:4 아이디어의 품질 실패가 아니라 ★**현재 GPU·드라이버·PyTorch 빌드 조합에서 이
진단의 native cuSPARSELt 경로를 사용할 수 없다는 환경 게이트 실패**다. 로그만으로 하드웨어,
드라이버, PyTorch 빌드 중 어느 하나를 단독 원인으로 분해할 수 없다. 첫 형상에서 멈췄으므로
forward 정합, input-gradient, 두 형상 속도와 1.25× 문턱은 모두 `NOT_RUN`이다.

계획의 사전등록 규칙에 따라 현 환경의 **학습 가속 분기는 종료**한다. 같은 배치를 같은 환경에서
재실행할 근거는 없다. inactive weight·optimizer state를 실제로 없애는 sparse-master 메모리
분기는 native 속도와 별개지만, 자동 진행하지 않고 별도 재승인·설계를 받아야 한다.

## 7. Stage0bW WSL 재탐지(2026-09-18) — **판정 철회와 진단 구현 오류**

> **원본 로그 상태**: 🚫`test_result/` 파일 없음. 이는 실험 실패가 로그를 지운 것이 아니라,
> 당시 WSL launcher가 `scripts/runlog.py`를 호출하지 않은 **로깅 프로그램의 코드 오류**다.
> 아래 관측은 사용자가 회신한 queue transcript이며 원본 로그로 승격하지 않는다.
>
> **환경**: Linux `6.18.33.2-microsoft-standard-WSL2` · Ubuntu · NVIDIA GeForce RTX 4070 Ti
> SUPER `sm_89` · PyTorch `2.10.0+cu130` · CUDA `13.0` · cuDNN `91501` ·
> `nvidia-cusparselt-cu13=0.8.0`
>
> **queue 판정**: launcher nonzero, queue는 나머지 결과를 보존한 뒤 최종 exit `4`

Python package import와 `to_sparse_semi_structured` 진입은 이뤄졌고 prototype API 경고까지
출력됐다. 당시 진단은 변환·forward·input-gradient·속도를 하나의 `try`로 묶어 어느 단계가
실패했는지 인쇄하지 않은 채 다음 한 줄만 남겼다.

```text
[GATE FAIL] M=8192 K=768 N=2048: NotImplementedError: `SparseSemiStructuredTensorCUSPARSELT` matmul: operation is not supported
```

2026-09-19 PyTorch 2.10 소스와 당시 코드 순서를 다시 대조한 결과, 이 문구를 “첫 forward
matmul 미지원”으로 읽은 판정은 틀렸다.

1. `to_sparse_semi_structured(W)`가 만든 cuSPARSELt 객체는 원래 방향 `packed`만 갖고
   `packed_t=None`이다.
2. `F.linear(X, W_sparse)` forward는 내부의 두 번 transpose를 거쳐 원래 `packed`를 사용한다.
3. 이어 실행한 input-gradient backward는 `grad @ W_sparse`에서 전치 방향을 요구한다.
   이때 `W_sparse.t().packed`는 원래 `packed_t`, 즉 `None`이다.
4. `SparseSemiStructuredTensorCUSPARSELT._mm()`는 바로 이 조건에서만 transcript와 정확히 같은
   `matmul: operation is not supported`를 낸다.

따라서 **형상이나 cuSPARSELt 설치 실패가 아니라, one-way inference pack을 input-gradient까지
사용한 진단 구현 오류가 직접 원인**이다. 실제 transcript에는 단계 표지가 없으므로 forward
정합 자체를 새 동적 PASS로 승격하지는 않는다. 다만 소스·실행순서상 오류는 dgrad 경로에서
발생한 것으로 재구성되며, 종전의 “WSL backend 불가·가속 분기 종료” 결론은 철회한다.

교정한 Stage0bWb는 다음을 각각 인쇄하고 따로 판정한다.

- inference pack의 `shape`, `packed`, `packed_t`, `t().packed`, `t().packed_t`
- one-way pack의 forward 정합과 예상되는 dgrad 제한
- `prune_dense_static_sort`가 만든 bidirectional training pack의 양 방향 존재
- training pack의 4×4 tile row/column 양방향 ≤2/4, forward·input-gradient dense 정합,
  두 MLP 형상 속도. 양방향 greedy pruner가 7/8개만 보존할 수 있어 exact 2/4는 요구하지 않음

새 진입점은 `run_P025B_Stage0bWb_wsl_sparse24_training_pack.sh`다. 코드 구문·shell 계약만
통과한 `STATIC_ONLY`이며, GPU 재실행·속도·학습·품질은 모두 `NOT_RUN`이다.

로그 미보존의 재발 방지는 launcher의 `runlog.py` 경유와 모든 `run_P*.sh` 정적 계약으로
구현했다. 그러나 과거 원본 로그는 소급 생성할 수 없으며, Stage0bWb의 동적 결과는 새 로그를
사용자가 회신하기 전까지 존재하지 않는다.
