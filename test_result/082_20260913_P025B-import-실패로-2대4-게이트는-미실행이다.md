## 7. Stage0bW WSL 재탐지(2026-09-18) — **판정 철회와 진단 구현 오류**

> **원본 로그 상태**: 🚫`test_result/` 파일 없음. 이는 실험 실패가 로그를 지운 것이 아니라,
> 당시 WSL launcher가 `scripts/runlog.py`를 호출하지 않은 **로깅 프로그램의 코드 오류**다.
> 아래 관측은 사용자가 회신한 queue transcript이며 원본 로그로 승격하지 않는다.
>
> **환경**: Linux `6.18.33.2-microsoft-standard-WSL2` · Ubuntu · NVIDIA GeForce RTX 4070 Ti
> SUPER `sm_89` · PyTorch `2.10.0+cu130` · CUDA `13.0` · cuDNN `91501` ·
> `nvidia-cusparselt-cu13=0.8.0`
>
> **queue 판정**: launcher nonzero, queue는 나머지 결과를 보존한 뒤 최종 exit `4`

Python package import와 `to_sparse_semi_structured` 진입은 이뤄졌고 prototype API 경고까지
출력됐다. 당시 진단은 변환·forward·input-gradient·속도를 하나의 `try`로 묶어 어느 단계가
실패했는지 인쇄하지 않은 채 다음 한 줄만 남겼다.

```text
[GATE FAIL] M=8192 K=768 N=2048: NotImplementedError: `SparseSemiStructuredTensorCUSPARSELT` matmul: operation is not supported
```

2026-09-19 PyTorch 2.10 소스와 당시 코드 순서를 다시 대조한 결과, 이 문구를 “첫 forward
matmul 미지원”으로 읽은 판정은 틀렸다.

1. `to_sparse_semi_structured(W)`가 만든 cuSPARSELt 객체는 원래 방향 `packed`만 갖고
   `packed_t=None`이다.
2. `F.linear(X, W_sparse)` forward는 내부의 두 번 transpose를 거쳐 원래 `packed`를 사용한다.
3. 이어 실행한 input-gradient backward는 `grad @ W_sparse`에서 전치 방향을 요구한다.
   이때 `W_sparse.t().packed`는 원래 `packed_t`, 즉 `None`이다.
4. `SparseSemiStructuredTensorCUSPARSELT._mm()`는 바로 이 조건에서만 transcript와 정확히 같은
   `matmul: operation is not supported`를 낸다.

따라서 **형상이나 cuSPARSELt 설치 실패가 아니라, one-way inference pack을 input-gradient까지
사용한 진단 구현 오류가 직접 원인**이다. 실제 transcript에는 단계 표지가 없으므로 forward
정합 자체를 새 동적 PASS로 승격하지는 않는다. 다만 소스·실행순서상 오류는 dgrad 경로에서
발생한 것으로 재구성되며, 종전의 “WSL backend 불가·가속 분기 종료” 결론은 철회한다.

교정한 Stage0bWb는 다음을 각각 인쇄하고 따로 판정한다.

- inference pack의 `shape`, `packed`, `packed_t`, `t().packed`, `t().packed_t`
- one-way pack의 forward 정합과 예상되는 dgrad 제한
- `prune_dense_static_sort`가 만든 bidirectional training pack의 양 방향 존재
- training pack의 4×4 tile row/column 양방향 ≤2/4, forward·input-gradient dense 정합,
  두 MLP 형상 속도. 양방향 greedy pruner가 7/8개만 보존할 수 있어 exact 2/4는 요구하지 않음

새 진입점은 `run_P025B_Stage0bWb_wsl_sparse24_training_pack.sh`다. 코드 구문·shell 계약만
통과한 `STATIC_ONLY`이며, GPU 재실행·속도·학습·품질은 모두 `NOT_RUN`이다.

로그 미보존의 재발 방지는 launcher의 `runlog.py` 경유와 모든 `run_P*.sh` 정적 계약으로
구현했다. 그러나 과거 원본 로그는 소급 생성할 수 없으며, Stage0bWb의 동적 결과는 새 로그를
사용자가 회신하기 전까지 존재하지 않는다.

### 11.1 We에서 유효한 것과 무효인 것

두 K/N 계열·inference/training·M=1/8/128/8192의 scale-aware 정합은 전부 통과했다.

전 행 같은 오류였다는 것이 독립 증거다. graph 값은 폐기하고 wall/event/host/profiler 값은 보존한다.

### 11.2 Wf의 정확한 판독

alg 0~3의 split_k=1은 실행됐고 alg4는 invalid, split_k 2/4는 local cuSPARSELt 0.8에서 internal
error로 지원되지 않았다. fresh confirmation에서 M8192의 event dense/sparse는 768→2048
**1.244×**, 2048→768 **1.390×**였지만 wall dense/sparse는 각각 **0.778×**, **0.841×**다.

이는 low-level sparse GPU-op 후보이지 algorithm tuning의 성공이 아니다. 첫 형상은 검색이 고른
alg3가 confirmation에서 alg0보다 느렸고, 둘째 형상은 alg0 자체가 선택됐다. 코드를 교정해 앞으로
`dense event speedup`, `dense wall speedup`, `non-default tuning gain over alg0`를 따로 인쇄하며,
같은 alg0을 두 이름으로 재측정한 noise를 tuning gain으로 세지 않는다.

### 11.3 조치와 다음 gate

- `_capture_graph()`가 capture 직후 한 번 replay·synchronize한 뒤 정합을 검사하도록 수정했다.

- 새 `run_P025B_Stage0bWg_wsl_sparse24_graph_recovery.sh`는 M1/M8192의 inference/training만
  재측정한다. 기존 We/Wf 전체 재실행은 불필요하다.
- raw op event 후보를 TLinear·whole-step·학습 후 inference 가속으로 승격하지 않는다.

현재 허용 주장은 `DESCRIPTIVE_ONLY`: **큰 M의 sparse kernel은 GPU stream 시간상 빠를 수 있지만

## 12. Stage0bWg CUDA Graph 복구(2026-09-21) — **구현 오류는 닫혔고 큰 M의 replay 후보는 성립했다**

We의 graph 32행을 실패시킨 원인은 backend가 아니라 capture 후 첫
`graph.replay()` 전 output buffer를 eager 결과와 비교한 진단 구현이었다. Wg에서는

1. **decode형 M=1은 graph로도 명확한 음성**이다. padding·고정 dispatch·작은 GEMM이
   지배해 sparse는 dense의 0.079~0.369×에 그친다.
2. **학습/prefill형 M=8192의 captured GPU work는 실제 후보**다. 그러나
   일반 `F.linear()` 동기 wall은 0.771~0.802×로 여전히 느리다. graph가
   Python/PyTorch 준비·launch를 상각한 경로와 현 모델의 일반 호출은 같은 양이 아니다.

따라서 Wg는 “graph backend 미지원”을 폐기하고 **Stage0c whole primitive를 열
근거**를 만든다. 다만 이 로그에는 TLinear, weight-gradient, optimizer, 매 step
weight re-pack, 전체 attention/MLP 비율이 없다. 그러므로 whole-step 학습 가속·실제
checkpoint 추론 가속·품질은 계속 `NOT_RUN`이다.

## 13. Stage0cW whole primitive(2026-09-22) — **GPU work는 양성, 동기 wall은 음성**

> 로그: `082_log_20260922_P025B_Stage0cW_sparse24_whole_primitive.txt` ·
> launcher: `run_P025B_Stage0cW_sparse24_whole_primitive-done.sh` · exit 0.

`M=8192`는 현 학습의 한 microbatch에서 `micro_bs 8 × seq 1024`를 평탄화한 행 수다.
각 형상에서 forward, input-gradient, **dense weight-gradient**를 하나의 primitive로 실행했고,
학습용 양방향 sparse pack은 optimizer step당 1회를 accum16으로 상각했다.

| 형상 `(M,K,N)` | pack/µstep | eager CUDA event | 동기 wall | CUDA Graph event |
|---|---:|---:|---:|---:|
| 8192,768,2048 | 0.002698 ms | **1.334×** | **0.959×** | **1.386×** |
| 8192,2048,768 | 0.003892 ms | **1.377×** | **0.926×** | **1.379×** |

정합성은 두 형상의 forward·input-gradient 모두 통과했다. pack 상각비는 작아 현 형상의
주 병목이 아니다. 순수 GPU 작업을 보는 event와 graph에서는 두 형상 모두 1.10×
문턱을 넘었지만, 사용자가 체감하는 동기 wall은 4.1%·7.4% 느리다. 따라서
**Stage0c의 낮은 수준 GPU primitive 후보는 통과**했으나 일반 PyTorch/TLinear 학습
가속 채택은 통과하지 않았다.

경고 `SparseSemiStructuredTensor... prototype stage`는 PyTorch API 안정성 경고이며 이 런의
실행 실패가 아니다. 다만 생산 기본 경로를 prototype API에 의존하게 할 근거는 더욱 아니다.
optimizer state, sparse weight-gradient, TLinear 삼진 양자화/STE, 전체 Transformer step,
체크포인트 추론, 품질은 계속 `NOT_RUN`이다. 다음 통합 단계는 이 호스트 wall 병목을
우회할 실제 실행 계획이 있을 때만 열고, sparse-master 메모리 축은 별도 판정한다.
