# 결과 082 — **현재 환경은 native 2:4 cuSPARSELt를 실행하지 못한다**

> 파일명은 최초 Stage0a 실패를 가리키는 역사적 앵커로 유지한다. 현재 판정은 §6의 유효한 Stage0b 재실행이다.

> **계획**: [P025B — 2:4 동적 희소 프리트레이닝과 sparse-master](../test_plan/P025B_2대4-동적희소-프리트레이닝-sparse-master.md) **Stage0a**  
> **로그**: `test_result/082_log_20260913_P025B_stage0a_sparse24_backend.txt`  
> **배치**: `run_P025B_Stage0a_sparse24_backend-done.bat`  
> **실행**: 2026-09-13 · 종료코드 1 · 과학적 게이트 진입 전 종료

## 1. 한 줄

★★**이번 실행은 `tinylm` 패키지 import 실패로 첫 2:4 연산 전에 종료됐다.** 따라서 native 2:4 지원·정확성·input-gradient·속도는 실패가 아니라 모두 `NOT_RUN`이며, 진입 경로를 고친 새 Stage0b 재실행이 필요하다.

## 2. 실패 지점과 원인

```text
File "z:\TinyLM\scripts\diag_sparse24_backend.py", line 32, in main
  from tinylm.model.sparse_connectivity import exact_nm_mask
ModuleNotFoundError: No module named 'tinylm'
```

`python scripts\diag_sparse24_backend.py`로 실행하면 Python의 첫 module 검색 경로가 `scripts/`가 된다. 이 스크립트에는 저장소 루트를 `sys.path`에 넣는 bootstrap이 없어 형제 디렉터리 `tinylm/`을 찾지 못했다. 데이터·GPU 지원·희소 kernel과 무관한 실행 진입 결함이다.

## 3. 조치와 현재 증거

- `scripts/diag_sparse24_backend.py`가 자기 위치에서 저장소 루트를 계산해 import 전에 `sys.path`에 넣도록 수정했다.
- `scripts/check_hf_redirect.py`, `python -m py_compile`, `git diff --check`는 통과했다.
- Codex는 GPU 진단을 실행하지 않았다. 수정 후 실제 2:4 게이트는 새 Stage0b 사용자 실행 전까지 `NOT_RUN`이다.

## 4. 후속

이 절은 최초 import 실패 시점의 역사적 후속이다. Windows 재실행은 §6, WSL 독립 재탐지는 §7에서
모두 첫 native matmul 지원 불가로 끝났다. 현재 두 runtime의 가속 후속은 닫혔고, 다른 지원 환경
증거 또는 sparse-master 메모리 트랙의 별도 재승인 전에는 Stage0c를 열지 않는다.

## 6. Stage0b 재실행(2026-09-14) — **import는 통과했고 native backend에서 지원 불가로 닫혔다**

> **로그**: `test_result/082_log_20260914_P025B_stage0b_sparse24_backend.txt`
>
> **배치**: `run_P025B_Stage0b_sparse24_backend-done.bat`
>
> **환경**: NVIDIA GeForce RTX 4070 Ti SUPER · `sm_89` · PyTorch 2.10.0
>
> **종료**: 진단 종료코드 3, 배치의 음성 게이트 분기

저장소 import는 정상 통과했다. 첫 실제 형상 `M=8192, K=768, N=2048`에서 다음과 같이
native 경로가 거부됐다.

```text
[GATE FAIL] M=8192 K=768 N=2048: RuntimeError: cuSPARSELt not supported on your machine.
```

이는 2:4 아이디어의 품질 실패가 아니라 ★**현재 GPU·드라이버·PyTorch 빌드 조합에서 이
진단의 native cuSPARSELt 경로를 사용할 수 없다는 환경 게이트 실패**다. 로그만으로 하드웨어,
드라이버, PyTorch 빌드 중 어느 하나를 단독 원인으로 분해할 수 없다. 첫 형상에서 멈췄으므로
forward 정합, input-gradient, 두 형상 속도와 1.25× 문턱은 모두 `NOT_RUN`이다.

계획의 사전등록 규칙에 따라 현 환경의 **학습 가속 분기는 종료**한다. 같은 배치를 같은 환경에서
재실행할 근거는 없다. inactive weight·optimizer state를 실제로 없애는 sparse-master 메모리
분기는 native 속도와 별개지만, 자동 진행하지 않고 별도 재승인·설계를 받아야 한다.

## 7. Stage0bW WSL 재탐지(2026-09-18) — **패키지는 로드됐지만 첫 sparse matmul이 지원되지 않았다**

> **원본 로그 상태**: 🚫`test_result/` 파일 없음. 당시 WSL 전용 launcher가
> `scripts/runlog.py`를 우회한 결함 때문에 콘솔에만 출력됐다. 아래 관측은 사용자가 회신한
> queue transcript를 보존한 것이며, 원본 로그가 존재한다고 쓰지 않는다.
>
> **환경**: Linux `6.18.33.2-microsoft-standard-WSL2` · Ubuntu · NVIDIA GeForce RTX 4070 Ti
> SUPER `sm_89` · PyTorch `2.10.0+cu130` · CUDA `13.0` · cuDNN `91501` ·
> `nvidia-cusparselt-cu13=0.8.0`
>
> **queue 판정**: launcher nonzero, queue는 나머지 결과를 보존한 뒤 최종 exit `4`

Python package import와 `to_sparse_semi_structured` 진입은 이뤄졌고 prototype API 경고까지
출력됐다. 그러나 첫 실제 형상 `M=8192, K=768, N=2048`의 matmul에서 다음과 같이 종료됐다.

```text
[GATE FAIL] M=8192 K=768 N=2048: NotImplementedError: `SparseSemiStructuredTensorCUSPARSELT` matmul: operation is not supported
```

따라서 Windows의 포괄적 `cuSPARSELt not supported`와 오류 문구는 달라졌지만, **이 WSL
runtime에서도 TinyLM 첫 대상 형상의 native matmul을 실행하지 못했다**는 의사결정은 같다.
forward 정합·input-gradient·두 형상 median과 1.25× 속도 문턱은 첫 matmul 뒤 단계이므로
`NOT_RUN`이다. 이 결과는 2:4 방법론의 품질 기각이 아니며, 현재 Windows/WSL runtime의
학습 가속 분기만 닫는다. sparse-master 메모리 트랙은 기존대로 별도 재승인 대상이다.

실험 로그 미보존 결함은 네 WSL gate launcher를 `runlog.py` 경유로 바꾸고, 모든
`run_P*.sh`에 로그 계약을 정적으로 강제하는 회귀를 추가해 교정했다. 같은 환경 재실행은
과학적 결론을 바꾸기 위한 선결이 아니라 **교정된 로그 보존 E2E를 확인할 때만** 의미가 있다.
