## 2. 무슨 일이 있었나

```
ValueError: 모르는 fmt: 'fp32'
  tinylm/model/transformer.py:290  quantize_embedding
  tinylm/infer/generate.py:64      load_model
  scripts/diag_decode_profile.py:135
```

문제의 줄:

```python
emb_quant=("int8" if path != "fp32" else "fp32")
```

★**`path` 는 *경로 이름*이고 `emb_quant` 는 *양자화 형식*이다.**
같은 문자열 `'fp32'` 가 **두 양을 가리켰다**(함정 28). 임베딩을 그대로 두라는 뜻은
`'fp32'` 가 아니라 **`None`** 이다 — `load_model` 이 `if emb_quant:` 로 분기하고
`quantize_embedding` 은 `int8`·`int4`·`ternary`·`bf16` 만 안다.

✅**수정**: `emb_quant=("int8" if path != "fp32" else None)`.

★**이 사고의 정체는 "새 도구를 만들고 한 번도 안 돌렸다"** 이다.
🚫**나는 GPU 도구를 돌리지 않으므로 스스로 못 돌린다** — 그래서 **첫 실행이 곧 시험**이 된다.

R19 를 지킨 덕에 **로그만 보고도 즉시 알았다**.

## 8. Stage0bW 교정 재실행(2026-09-20) — **프로파일은 완주했고 즉시 커널 착수 근거는 부족**

> 로그: `069_log_20260920_P014D_Stage0bW_decode_profile.txt` · 종료코드 0 · CPU 2.2분
> 주의: `torch.profiler`가 켜진 self CPU time이라 tok/s가 아니다.

| 모델 | 경로 | 토큰당 profiler ms | fp32 대비 | 언팩 확실~`+copy_` 대역 | GEMM 비중 |
|---|---|---:|---:|---:|---:|
| `mC_cla2_ag4` | fp32 | 34.72 | 기준 | 5.4~9.5% | 71.0% |
|  | int8 | 29.53 | **−15%** | 25.5~43.9% | 32.0% |
|  | LUT | 35.02 | **+1%** | 26.1~36.3% | 14.5% |
| `mC_cla2_ag4_r20` | fp32 | 49.33 | 기준 | 6.5~7.8% | 70.8% |
|  | int8 | 46.95 | **−5%** | 23.9~41.1% | 32.8% |
|  | LUT | 60.73 | **+23%** | 25.1~33.8% | 9.5% |

관측상 int8은 fp32보다 빠르지만 LUT reference 경로는 같거나 23% 느리다. int8의 언팩 대역은
기존 유도 40~55%와 걸쳐 있어 판정 불가이고, LUT 대역은 두 모델 모두 유도 하한 40% 아래다.
다만 사전등록의 명시적 중단선은 **상한 20% 미만**이므로 33.8~36.3%를 “축 종결”로 소급
바꾸지 않는다. 결론은 **6시간 직접 커널 구현을 즉시 열지 않는 HOLD**다. 다음 값싼 단계는
I2_S가 per-row alpha·shape를 수용하는지 2시간 정적 실사이며, 그 결과 없이 custom kernel을
권장하지 않는다.

## 9. Stage1W native LUT actual-model gate(2026-09-20) — **reference는 개선, int8 문턱은 미달**

> 로그: `069_log_20260920_P014D_Stage1W_native_lut_kernel.txt` · compiled/synthetic exit0 · model gate exit8

| 모델 | fp32 | int8 | Python LUT | native LUT | native/int8 | native/reference |
|---|---:|---:|---:|---:|---:|---:|
| `mC_cla2_ag4` | 46.25 tok/s | 34.70 | 24.27 | **43.33** | 1.249× | 1.785× |
| `mC_cla2_ag4_r20` | 28.48 tok/s | 21.58 | 14.32 | **25.63** | 1.188× | 1.790× |

C++ v0는 2-D·3-D·TLinear 정합을 통과했고 Python LUT overhead를 약 44% 줄였다. 그러나 사전등록
`native/int8≥1.50×`를 두 모델 모두 못 넘었고 fp32보다도 느리다. 따라서 **scalar C++ v0 자체는
배포 채택 음성**이다. packed 1.6bpw 메모리 가치는 남지만 속도 재개는 SIMD/vectorized layout 또는
외부 kernel ABI를 별도 단계로 구현할 때만 가능하다.

## 10. Stage1Wb(2026-09-22) — **커널 속도가 아니라 과도하게 좁은 단위시험에서 중단**

> 로그: `069_log_20260922_P014D_Stage1Wb_native_lut_incremental.txt` ·
> launcher: `run_P014D_Stage1Wb_native_lut_incremental-done.sh` · exit 1.

Stage1Wb는 첫 `test_lut_cpu_native.py --compile`에서 중단했다. 불일치는 42원소 중
9개, 최대 절대차 `5.7220459e-06`이었고 게이트는 `rtol=atol=1e-6`이었다.
따라서 합성 shape 및 actual checkpoint 속도 측정은 **모두 NOT_RUN**이며, 이 로그로
v1이 v0보다 빠르거나 느리다고 말할 수 없다.

원인은 base-3 증분표의 수학 오류가 아니라 **float32 누산 순서 차이를 bitwise에 가까운
1e-6 허용오차로 판정한 테스트 설계 결함**으로 판독했다. 참조 `einsum`은 곱·누산을
다른 순서로 수행하고, v1은 각 base-3 상태를 이전 상태에서 덧셈으로 갱신한다.
기존 `bench_lut_cpu_native.py`는 이 특성을 반영해 `rtol=1e-4, atol=5e-5`를 사용했고,
TLinear dispatch 검사도 `rtol=1e-5, atol=2e-5`였다.

조치는 합성 단위시험만 더 엄격한 `rtol=atol=1e-5`로 조정했다. `/tmp` 독립 extension
빌드 캐시에서 2-D·3-D·TLinear dispatch를 다시 컴파일·실행해 PASS했다. 이것은
합성 CPU 정합 수정의 동적 증거이지 actual checkpoint 속도 증거가 아니다.

`run_P014D_Stage1Wc_native_lut_tolerance_recovery.sh`는 같은 checkpoint·shape·
`native/int8 >= 1.50x` 문턱을 보존한 재실행 진입점이다. Wb는 재현 명령이 이 문서에
보존됐더라도 실행 실패를 다시 쓸 이유가 없으므로 삭제 후보이다. 다만 Wc 실행 전에
v1 속도 축은 계속 `NOT_RUN`이다.

## 11. Stage1Wc 실제 모델 속도(2026-09-23) — 정합 PASS, 1.50× 문턱 미달

원본 [069_log_20260923_P014D_Stage1Wc_native_lut_tolerance_recovery.txt](069_log_20260923_P014D_Stage1Wc_native_lut_tolerance_recovery.txt)은 세 구간을 보존한다. compiled 2-D/3-D·TLinear 정합과 합성 벤치는 exit 0이다. 두 actual checkpoint decode는 `[GATE NEGATIVE]`와 exit 8이다. 이는 코드 실행 실패가 아니라 **사전등록 속도 문턱의 유효한 음성**이다.

| checkpoint | native/int8 | native/reference | native tok/s | int8 tok/s | 판정 |
|---|---:|---:|---:|---:|---|
| `mC_cla2_ag4` | 1.314× | 2.003× | 45.366 | 34.514 | 1.50× 미달 |
| `mC_cla2_ag4_r20` | 1.231× | 2.003× | 25.591 | 20.792 | 1.50× 미달 |

합성 M=1 세 형상의 native/dense는 0.621×/0.378×/0.434×였다. 합성은 float32·1 thread·warmup 3/iters 10이고 actual 모델은 1 thread·32 decode token·warmup 2/iters 3이라 분모가 다르다. 현 scalar native v1은 reference보다 약 2× 빠르지만 int8 1.50× 채택선에 못 미치므로 **기본 배포 backend로 승격하지 않는다**. SIMD·다른 CPU·품질·상주 개선은 이 로그로 판정하지 않는다. GPU/학습 재실행도 없었다.

완료 보존 런처: `run_P014D_Stage1Wc_native_lut_tolerance_recovery-done.sh`. 단, suffix는 실행 이력이지 품질 PASS가 아니다.
