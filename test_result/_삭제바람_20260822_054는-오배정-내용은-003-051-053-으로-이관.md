## 2. ★P014 — LUT 이 실제로 돈다

### 2.1 게이트 (성공 기준값은 결과보다 먼저 인쇄됨)

| 게이트 | 기준 | ✅실측 |
|---|---|---|
| **L1** 패킹 왕복 | 불일치 0 | ✅**0개**, 경계 길이 5종(1·4·6·9·771) 전부 |
| **L2** LUT vs dense | < 1e-5 | ✅**2.958e-07** |
| **L3** per-row α | < 1e-5 | ✅**2.462e-07** |
| **L3b** `out_chunk` 불변 | < 1e-6 | ✅★**0.000e+00** — 출력채널 독립이 코드로 확인됐다 |
| **L4** bpw | 1.600 | ✅**1.6000** (1,572,864 가중치 → 314,573 바이트) |
| ★**L6** 통합 경로 | 전환됨 | ✅**`_lut_codes (512,52) uint8` / `_i8 None`** — 함정 37 통과 |

★**L6 상주**: **28,672 바이트** vs int8 **131,072 바이트** = **4.57배**.

### 2.2 ★★실측 상주 — **표준모델에서 삼진 항이 5.03배 줄었다**

`mem_runtime.py --drop-latent --lut` vs `--drop-latent --int8-store`, 같은 체크포인트:

| 경로 | 삼진 항 | 기타(임베딩 fp32) | **텐서합산 상주** |
|---|---:|---:|---:|
| fp32(2벌) | 346.4 | 33.2 | **379.7 MB** |
| int8 | **44.7** | 33.2 | **77.8 MB** |
| ★**LUT** | ★**8.88 MiB** | 33.2 | ★**42.1 MB** |

★★**44.7 → 8.88 = 5.03배.** 예측은 `8 / 1.585 = 5.05` 였다 — **거의 정확히 맞았다.**
(`mem_breakdown` 이 `삼진사본 0.0` 으로 찍는 것은 LUT 코드가 uint8 이라 fp32 텐서 합산에
안 잡히기 때문이다. **LUT 상주는 별도 줄(`8.88 MiB`)로 인쇄된다.**)

### 2.3 ★결과 052 의 18.3 MiB 재현 + **표준모델은 다르다**

| | |
|---|---|
| `m100R1q` 재현 | **17.35 MiB** vs 052 의 **18.3** → **차 −0.95 MiB**, ✅**1 MiB 안** |
| ★**표준모델**(임베딩 통짜) | LUT + emb **int8** = ✅**34.46 MiB** / emb bf16 58.46 / emb fp32 106.46 |

★★**표준모델도 40 MiB 를 통과한다** — 단 **임베딩 int8 이 필수**다.
🚫**emb bf16 으로는 58.5 로 못 간다.** → **P034 단계5(임베딩 양자화)가 선결이다.**

### 2.4 🚫★게이트 기준값이 틀렸다 — **함정 34 를 내가 다시 물었다**

로그가 **`로짓 차이 max|dlogit| = 1.615e+00 ★실패`** 를 찍었다.
🚫**그 "실패" 는 모델이 아니라 내가 정한 기준값(1.0)이 틀린 것**이다.

| | |
|---|---|
| 🚫**내가 한 것** | `dmax < 1.0` 이면 통과. **근거 없이 정한 수** |
| ★**왜 틀렸나** | 결과 028 이 잰 per-row 대가는 **bpb**(+0.0038~0.0068)다. **로짓 절대차와 단위가 다르다** — softmax 를 지나면 크게 줄고 감쇠율은 로짓 스케일에 의존한다 |
| ✅**정정** | `mem_runtime --lut` 은 이제 **"동작확인(품질 기준 아님)"** 만 찍는다. **품질은 `paired_eval`/`common_bpb` 가 소유** |

> ★**함정 34 원문**: *"게이트가 실패를 찍으면 모델보다 기준값을 먼저 의심한다(4번 중 4번)."*
> **5번 중 5번이 됐다.**

## 3. ★★P065 단계2 — **OOM 이지만 버그가 아니다**

### 3.1 실측

| 팔 | 조건 | 죽은 지점 | allocated | 필요 |
|---|---|---|---:|---:|
| `probe_d36_nock` | 36층 + `--no-ckpt` | ★**`F.cross_entropy`** | **14.73 GiB** | +512 MiB |
| `probe_r20_nock` | 20층 재귀 R2 + `--no-ckpt` | ★**`F.cross_entropy`** | **14.84 GiB** | +512 MiB |

**용량 15.99 GiB, free 0 bytes.** → ★**실질 부족 약 0.6~1.3 GiB**(단편화 여유 포함).

### 3.2 ★★죽은 지점이 답이다 — **모델 forward 가 아니다**

```
ce = F.cross_entropy(logits.reshape(-1, cfg.vocab_size), y.reshape(-1))
```

★**512 MiB = 8192 × 32768 × 2B**(bf16 로짓의 reshape·contiguous).

| 질문 | 답 |
|---|---|
| `--no-ckpt` 구현 버그인가 | 🚫**아니다.** grad checkpoint 를 끄면 전 층 활성이 살아 있고, 그 위에서 CE 가 자리를 못 잡는다. **설계상 예상되는 동작** |
| 모델 크기 문제인가 | ✅**그렇다.** 결과 051 의 20층 무KD `--no-ckpt` = **10.31 GiB** 에서 36층(1.8배 층)·재귀(2배 통과)로 올라간 결과가 14.7~14.8 이다. **일관적이다** |
| ★**그럼 내 예측은?** | 🚫**둘 다 틀렸다.** 핸드오프에 36층 ⚙11.5 / 재귀 ⚙12.6~14 라고 적었는데 **실제로는 둘 다 16 GiB 를 넘었다** |
| ★**고칠 여지는 있나** | ✅**있다** — §3.3 |

### 3.3 ★★고칠 여지 — **평범한 CE 는 한 번도 청킹된 적이 없었다**

`--kd-chunk` 는 **KD 손실만** 나눈다(P053/T-2). 🚫**평범한 CE 는 안 나눈다.**
★**무KD 런에서는 KD 청킹이 아무 일도 하지 않으므로, "무KD + `--no-ckpt`" 가
정확히 이 항이 노출되는 조합**이다.

✅**조치**: **`--ce-chunk N`** 신설. 기본 0 = **비트 동일**.
⚠️★**정직하게**: backward 가 저장해야 하는 것은 **안 준다.** 줄어드는 것은
**동시에 살아 있는 임시 텐서**이고, 우리를 죽인 것이 정확히 그 512 MiB 다.
**기대 절감은 수백 MiB 대**이지 GiB 대가 아니다.

## 4. ★★★P067 단계0-b — **게이트는 전부 통과했고, 죽은 것은 내 코드였다**

### 4.1 ✅T1~T6 전부 통과 — **외부 교사 경로가 실제로 돈다**

| 게이트 | 결과 |
|---|---|
| **T1** 교사 로드 | ✅ `Qwen3ForCausalLM` |
| **T2** 초과 id | ✅ **0개**(여유 14,464) |
| **T3** 로짓 shape | ✅ `(2, 64, 151936)` |
| **T4** 로짓 dtype | ✅ `torch.float32` |
| **T5** 토크나이저 왕복 | ✅ 한/영/혼합 3종 |
| ★**T6** dtype | ✅★**`uint32` 로 올림**(어휘 151,665 > 65,536) — **이것을 안 잡았으면 전부 쓰레기였다** |

✅**토큰화 12.3분**, ✅**어휘 32,768 → 151,936 교체**, ✅**교사만 로드(우리 dense 안 씀)**.

### 4.2 🚫★★그리고 죽었다 — **원인은 내가 쓴 한 줄**

```
_kd_kl -> F.kl_div: Tried to allocate 594.00 MiB, 14.96 GiB allocated, 0 bytes free
```

**594 MiB = 1024 × 151,936 × 4B** = KL 청크 하나. **청킹은 작동하고 있었다.**

★**그런데 그 앞에서 이미 죽어 있었다**:

```python
def forward(self, x):
    ...
    return lg.float()        # ← (4, 1024, 151936) bf16 -> fp32 = 2.32 GiB 단일 할당
```

| | |
|---|---|
| 🚫**내가 한 것** | 교사 로짓을 **통째로 fp32 로 승격** |
| ★**왜 넣었나** | *"bf16 log_softmax 는 꼬리를 뭉갠다"* — **규약 자체는 옳다** |
| 🚫**왜 틀렸나** | ★**언제 올리느냐를 안 봤다.** `_kd_kl` 이 청크로 나눠도 **이미 통째로 물질화된 뒤**다 |
| ✅**조치** | 교사는 **원 dtype 그대로** 반환. **fp32 승격은 `_kd_kl` 이 청크 안에서.** ⚙절감 **약 1.16 GiB** — 필요했던 594 MiB 보다 크다 |

> ★★**이것이 "모델 크기 문제인가 구현 문제인가" 의 답이다.**
> **P065 는 크기, P067 은 구현.** 같은 `OutOfMemoryError` 지만 **원인이 다르고 처방도 다르다.**

### 4.3 ⚠️**그래도 어휘 4.6배는 실재한다**

| 항목 | 실측/추정 |
|---|---|
| 학생 상주 | **567.9 MB**(임베딩 39.1M = 8.0 MB packed) vs 표준 451.5 |
| ⚙어휘 위 KD 손실 | **5.48 → ⚙25 GiB**(4.6배) |
| ★결론 | **fp32 승격 시점을 고쳐도 M 을 줄여야 할 수 있다** → 단계0-c 가 사다리로 확인 |
