# 결과 081 — **P022C FP8 backend는 되지만 cast·scaling 포함 경로는 이득이 없다**

- **파일명 역사 보존**: 최초 단계의 이름을 인용한 완료 WIP는 불변이므로 파일은 개명하지 않는다. 현재 판정은 H1과 최신 실행 절이 소유한다.

> **계획**: [P022C — FP8 compute와 shadow precision 분리](../test_plan/P022C_FP8-compute-shadow-precision-분리.md) **Stage0a(C0)**

## 1. 한 줄

★★**현 Ada/PyTorch 조합에서 TinyLM 세 형상의 CUDA `_scaled_mm`가 실제 실행됐고, 순수 GEMM은 attention 1.17×를 제외하면 1.77~2.09×였다.** 이것은 backend·순수 GEMM 상한의 PASS이며 cast/scaling·backward·whole-step·품질은 `NOT_RUN`이다.

## 2. 측정 결과

| 형상 | M | K | N | BF16 ms | FP8 ms | 순수 GEMM 배수 |

| MLP down(m100) | 8,192 | 2,048 | 768 | 0.366 | 0.185 | **1.97×** |

엄격 backend 진단의 세 TinyLM 형상은 모두 유한 BF16 출력을 반환했다. 학습 런이 아니므로 `runs/logs/*.json`은 없고 로그가 이 진단 수치의 정본이다.

## 3. 판정

- ✅ Stage0a(C0) 계속 조건인 실제 CUDA `_scaled_mm` 유한 forward 성공을 충족했다.
- ⚠️ attention q/o의 순수 GEMM 1.17×는 배치 안내의 경험적 1.2~1.3×보다 낮다. MLP 이득과 함께 C1에서 전체 workload 비중으로 재야 한다.
- 🚫 순수 GEMM 배수를 학습 step 배수로 읽지 않는다. cast, amax/scaling, graph break, backward가 아직 빠져 있다.
- 🚫 compute backend PASS는 shadow/write-back precision 성공이 아니다.

## 6. Stage0bW/C1 WSL scaling overhead(2026-09-19)

> **로그**: `081_log_20260919_P022C_Stage0bW_fp8_scaling_overhead.txt` · exit 4
> **정정**: 측정 실패가 아니라 **유효한 과학적 음성**이다. C1 승인 계약은 speed/memory
> gate인데 진단기가 별도 NRMS 선을 실행 실패 코드 4로 잘못 반환했다.

| 형상 `(K,N)` | current speedup | delayed speedup | BF16 → FP8 peak MiB | NRMS / cosine |
|---|---:|---:|---:|---:|
| 768,2048 | 0.816× | **1.015×** | 32.000 → 39.50 | 0.03771 / 0.999290 |
| 2048,768 | 0.622× | 0.867× | 12.000 → 48.00 | 0.03771 / 0.999290 |
| 768,768 | 0.534× | 0.751× | 12.000 → 18.56 | 0.03764 / 0.999291 |

세 형상 모두 current scaling은 느리고 delayed scaling의 최고도 +1.5%에 불과하며 peak
allocation은 줄지 않았다. 승인 제안의 C1 규칙인 “5% 미만이고 메모리 이득 없음”에 따라
**compute track은 여기서 음성 종결**한다. NRMS 3.76~3.77%는 C2 품질 위험 신호지만 C1
실행 실패가 아니다. 진단기는 유효 측정의 수치·속도 미달을 선언된 exit 8로 반환하도록
교정했고 Stage0bWb는 종료코드 계약 확인용일 뿐 같은 과학값의 필수 재측정은 아니다.

backward·whole-step·actual FP8 training은 `NOT_RUN`이며 compute 음성이 persistent
low-shadow/write-back 트랙을 기각하지 않는다.

## 7. Stage0bWb 종료코드 교정 재실행(2026-09-20) — **속도 한 행 양성·수치와 메모리 음성**

> 로그: `081_log_20260920_P022C_Stage0bWb_fp8_scaling_overhead.txt` · 종료코드 8
> 같은 CUDA 세션·M=8192·warmup 10·30회, forward만 측정

| `(K,N)` | current | delayed | BF16→FP8 peak MiB | NRMS / cosine |
|---|---:|---:|---:|---:|
| 768,2048 | 0.521× | **1.148×** | 32.000→39.50 | 0.03771 / 0.999290 |
| 2048,768 | 0.531× | 0.897× | 12.000→48.00 | 0.03771 / 0.999290 |
| 768,768 | 0.161× | 1.088× | 12.000→18.56 | 0.03764 / 0.999291 |

종전 W 로그의 best 1.015×와 달리 이번 세션에서는 delayed 첫 형상이 1.148×로 속도 문턱을
넘었다. 세션 드리프트가 경계값을 바꿨으므로 “cast/scaling은 항상 느리다”는 문장을 유지하지
않는다. 그러나 세 형상 모두 NRMS 3.76~3.77%로 3% 수치 문턱을 넘고, peak allocation도
BF16보다 증가했다. 따라서 종료코드 8은 실행 장애가 아니라 **속도·수치·메모리 중 전체 계약을
충족한 후보가 없다는 과학적 음성**이다.

이번 로그는 delayed가 scale만 재사용하고 FP8 weight를 매 호출 다시 만든다는 구조를 그대로
보존한다. weight 재변환을 제거하면 무엇이 남는지는 아직 측정하지 않았으므로, compute 트랙을
구현 불가능으로 종결하지 않고 Stage0bWc 원인 귀속만 연다.

## 8. Stage0bWc 원인 귀속 구현(2026-09-20) — **정적 완료·GPU NOT_RUN**

새 `scripts/diag_fp8_path_attribution.py`와
`run_P022C_Stage0bWc_fp8_path_attribution.sh`는 BF16(A), prepared FP8(B), FP8 weight
cache(C), 기존 delayed(D), 기존 current(E)를 동일한 교차 순서 계측으로 비교한다.

- synchronized wall, 연속 CUDA Event, host enqueue, profiler를 서로 다른 열로 둔다.
- absmax/scale, activation cast, weight cast, `_scaled_mm` component 시간을 따로 기록한다.
- cached tensor와 per-call temporary의 논리 바이트, observed peak를 함께 기록한다.
- speed, memory, NRMS/cosine을 독립 판정하며 세 조건을 모두 통과한 C 행만 TLinear 통합 후보가 된다.
- TLinear cache 생성·무효화, backward, whole step은 선제 구현하지 않았고 `NOT_RUN`이다.

CUDA Event 합계는 개별 GEMM kernel 시간이 아니다. 실제 kernel 귀속은 profiler 행만 사용한다.
