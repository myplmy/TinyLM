## 6. ★★★val 오염 — **바이트 단위로 확인했다**

### 6.1 왜 의심했나

§3.2 를 쓰려고 `prepare()` 를 읽다가 두 사실이 만났다:

1. `_stream()` 이 `np.random.default_rng(0)` **고정 시드**로 문서를 고른다(`prepare.py:57`).
   → **캐시 크기가 달라도 스트림 순서가 같다** = 작은 캐시는 큰 캐시의 **접두사**다.
2. val 은 `arr[-n_val:]` = **스트림 말미 0.5%**(`prepare.py:311~313`).

둘을 합치면 **작은 캐시의 val 은 큰 캐시의 train 안에 있다.**

### 6.2 실측 — 추론이 아니라 비교다

`numpy.memmap` 으로 직접 떠서 `array_equal` 했다(torch 0 · GPU 0):

| 검사 | 길이 | 결과 |
|---|---:|---|
| `ko-en_300M/val.bin` == `ko-en_600M/train.bin[298,500,000 : 300,000,000]` | 1,500,000 | ★**True** |
| `ko-en_300M/val.bin` == `ko-en_1200M/train.bin[298,500,000 : 300,000,000]` | 1,500,000 | ★**True** |
| `ko-en_600M/val.bin` == `ko-en_1200M/train.bin[597,000,000 : 600,000,000]` | 3,000,000 | ★**True** |

→ ★★**`paired_eval --tokens 300M`(모든 배치의 기본값)은 `--pool-tokens 600M` 런에게
"학습 중에 본 글" 로 채점한다.** `pool_tokens=600000000` 인 실런이 **142개**(전체 224 중 63%)다.

노출량: 597M 에서 300M 을 균등 복원추출하므로 토큰 하나가 학습에 등장할 확률은
`1 − e^(−0.5)` = **39.3%**. 즉 ★**full-val 크롭의 약 39%가 학습 중 한 번 이상 나왔다.**

### 6.3 ✅그런데 **헤드라인 수치는 안 흔들렸다** — 확인했다

학습로그 val 은 **각 런이 자기 캐시의 `val.bin`** 을 쓰므로 **깨끗하다**(600M 풀 런은
597M~600M 구간을 본 적이 없다). 두 자를 같은 짝에 대고 재면:

| 짝 | **오염된** full-val Δ | ★**깨끗한** 학습로그 val Δ | 차 |
|---|---:|---:|---:|
| `d12_cla2_r20` − `d12_cla2e_r20` | +0.0072 | **+0.0075** | **0.0003** |
| `d12_cla2_r20` − `d16_cla2_r20` | +0.0412 | **+0.0414** | **0.0002** |
| `d12_cla2_r20` − `d12_cla2_r20_lrm` | +0.0012 | +0.0005 | 0.0007 |
| `d12_cla2_r20` − `d12_cla2_r20_s2` | +0.0004 | −0.0014 | 0.0018 |

★**분해능을 넘는 두 효과가 0.0003 안에서 일치한다.** 아래 두 짝은 부호까지 흔들리지만
**애초에 "구분 불가" 판정**이라 결론이 없다.
→ ✅**결과 067·071 의 예산 승자 판정을 철회하지 않는다.**

⚠️★**단 편향의 방향은 중립이 아니다.** 암기는 **용량이 큰 모델에 유리**하므로 오염된
full-val 은 **깊은 모델을 과대평가**할 수 있다. 위 표에서 d16 의 Δ 가 오히려 **0.0002 작게**
나온 것이 그 걱정을 약화시키지만, ★**"측정했다" 가 아니라 "이 한 짝에서 안 보였다"** 다.

## 10. 단계4 (2026-09-06) — **2×2 를 닫았다. 깊이와 토큰은 곱해진다**

§4.1 이 *"2×2 가 안 닫혔다 — 배치 설계의 구멍이다"* 라고 적은 그 칸을 채웠다
(`d16_cla2_r20_p12_t300`, 138.0분, 종료코드 0, `grad_max` 0.894, `n_skip` 0).

★**네 런 전부 풀 1,200M** 이고 val 은 **자기 캐시의 말미 0.5%** 다 —
§6 의 오염이 **여기에는 없다**(자기 `train.bin` 밖이다). 같은 시험지·같은 조건.

| final val | **t300** | **t600** | 토큰 효과 |
|---|---:|---:|---:|
| **d12** | 3.63172 | 3.52500 | −0.10672 |
| **d16** | 3.59281 | 3.47922 | −0.11359 |
| **깊이 효과** | −0.03891 | −0.04578 | ★**교호작용 −0.00687** |

### 10.1 ★교호작용의 자 — **√2 배다**

교호작용은 **네 런의 조합**이라 단일 차이보다 분산이 크다:
`Var = 4σ²` vs 단일 차이 `2σ²` → **SD 가 √2 배**. dense 자 0.0021(2σ, 단일 차이) 이므로
**교호작용의 2σ = √2 × 0.0021 = 0.00297.**

**|−0.00687| / 0.00297 = 2.31배** → ★**유의하다. 그러나 작다.**
(보수적으로 2배를 쓰면 0.0042 → 1.6배. **어느 쪽이든 자를 넘는다.**)

★**뜻**: 깊이와 토큰은 **더해지지 않고 약하게 곱해진다.** 깊은 몸통이 **긴 학습을 더 잘 흡수한다** —
또는 같은 말로, **긴 학습이 깊이의 값어치를 6.4% 키운다**(0.00687 / 0.10672).
→ ★**열린 질문 2 해소.** REVIEW3 v2 안 B·안 C 가 두 축을 함께 쓰는 것은 **손해가 아니라 이득**이다.

⚠️★**단 1,200M 풀의 val 은 한국어가 0.0%** 다(§3.2). **이 교호작용은 영어에서 잰 것**이다.

### 11.1 ★★서열 역전 — **규약이 실측이 됐다**

`d12_cla2_r20`(풀 600M) 과 `d12_..._p12_t300`(풀 1,200M)은 **학습 토큰이 똑같이 300M** 이고
**풀만 다르다.**

| 자 | 이기는 쪽 | 크기 |
|---|---|---:|
| 학습로그 val | 풀 **600M** | **0.0745 nats** |
| ★**공통 bpb** | 풀 **1,200M** | **0.0150 bpb**(자 0.008 의 1.9배) |

★★★**부호가 반대다.** 종전 규약 *"풀이 다른 런끼리는 비교 금지"* 는 **주의사항이었는데
이제 실측된 사실**이다 — 그것도 **0.0745 nats 짜리 큰 오답**이다.
원인은 §3.2 가 이미 지목했다: **풀마다 val 의 한국어 비율이 13.5 / 5.5 / 0.0% 로 다르다.**

### 11.2 ★★두 축 법칙 — **R² 0.9905**

d12 여섯 점에 최소자승을 걸었다:

```
bpb = 1.2985 − 0.01807 · log2(steps / 300M) − 0.04235 · log2(유니크 / 189.6M)
```

| 모형 | R² | RMSE |
|---|---:|---:|
| steps 만 | 0.6859 | 0.01824 |
| 유니크 만 | 0.7988 | 0.01460 |
| ★**steps + 유니크** | ★**0.9905** | ★**0.00366** |
| steps + 풀 | 0.9762 | 0.00580 |

★**RMSE 0.00366 은 bpb 자(0.008)의 절반 아래** = **도구만큼 정확하다.** 잔차 최대 0.0052.
`유니크` 가 `풀` 보다 잘 맞고 둘의 상관은 0.578 이라 **구분된다.**

★★**유니크 배증(−0.0424)이 스텝 배증(−0.0181)의 2.34배 값지다.**

### 11.3 🚫★★그런데 유니크는 **스텝에 갇혀 있다** — 이것이 진짜 결론이다

★**유니크 토큰은 학습 토큰을 넘을 수 없다.** 유니크 = `P·(1 − e^(−T/P))` 이고 `P → ∞` 면 **T** 다.
표준 300M 토큰에서:

| 풀 | 유니크 | 표준(600M 풀) 대비 bpb |
|---|---:|---:|
| 300M | 189.6M | +0.0134 |
| ★**600M(표준)** | 236.1M | 0 |
| 1,200M | 265.4M | −0.0072 |
| 2,400M | 282.0M | −0.0109 |
| ★**무한** | **300.0M** | ★**−0.0146** |

★★★**풀 축에 남은 전부가 −0.0146 bpb 다.** 스텝 배증 하나가 **−0.0181** 이므로
**무한한 코퍼스가 학습시간 1.75배보다 못하다**(0.0146 / 0.0181 = 0.81 배증).

### 11.4 ✅★§3.1 정정 — **결론은 살고 이유가 바뀐다**

| | §3.1(학습로그 val · 다른 시험지) | ★**§11(공통 bpb · 같은 시험지)** |
|---|---:|---:|
| P087 e1→e2(300M 풀) | −0.11547 nats | **−0.0374 bpb** |
| P088 t300→t600(1.2B 풀) | −0.10672 nats | **−0.0466 bpb** |
| **총 이득이 큰 쪽** | **P087**(+8.2%) | 🚫★**P088**(+24.6%) |
| 유니크 100M 당 효율 | P087 이 **3.2배** | P087 이 **2.38배** |

★**총 이득의 서열은 뒤집혔고, 유니크 효율의 서열은 살아남았다.**

🚫★★**그래서 §1 의 헤드라인 *"유니크 토큰을 3배 더 줘도 이득이 안 커진다"* 를 정정한다.**
**이득은 커졌다**(−0.0374 → −0.0466). 종전 문장은 **다른 시험지에서 잰 두 수를 나란히 놓은 것**이고,
§3.2 가 예고한 바로 그 함정에 §3.1 이 걸렸다.

★**옳은 문장**: *"유니크 토큰은 스텝보다 2.34배 값지지만 **스텝 수에 갇혀 있어서**
우리 규모에서 풀 축의 잔여 이득이 −0.0146 bpb 뿐이다. **그래서 코퍼스보다 GPU 시간이 먼저다.**"*
★**실무 결론은 그대로이고 근거가 정반대**다 — 종전은 *"새 글이 값이 없다"*, 지금은
*"새 글이 값은 큰데 더 넣을 자리가 없다"*.

### 11.5 ⚠️★남은 교락 — **영어 예산**

`ko-en_1200M` 의 `mix_token_frac` 는 **[0.250 한국어, 0.750 영어]** 다. 600M·300M 풀의
`meta.json` 에는 그 필드가 **없다**(구 포맷). 즉 ★**풀이 커질수록 영어 비율이 오르는데
공통 원문이 영어 전용**이다 — §11.1 의 역전에는 *"유니크가 늘었다"* 와 *"영어를 더 봤다"* 가 섞여 있다.

★**분리 방법 둘**: ① **한국어 공통 원문**(아직 없다 — `07_corpus_selection` §3) ②
✅**KoBEST + held-out 으로 한국어 쪽을 따로 재기**(둘 다 2026-09-05·09-06 에 열렸다).
→ **후속 배치의 과제**로 남긴다.

### 11.6 🚫★내 배치 순서의 결함 — **표에 한 칸이 없다**

큐가 `common_bpb`(Stage5)를 **`d16_..._p12_t300`(Stage4) 보다 먼저** 돌렸다. 그래서
★**§10 에서 채운 그 모델이 §11 의 표에 없다.** 공통 자 위의 2×2 를 아직 못 그린다.
