사용자 지적에 따라 §9의 여덟 학습 JSON과 같은 날 체크포인트 파일 크기를 다시 대조했다.

dynamic50 **+0.65813→+0.19656**, dynamic25 **+0.51875→+0.33797**로
세 팔 모두 감소했다. 그러나 두 예산은 독립 시작·서로 다른 WSD 절대 지평이고
점도 둘뿐이므로 300M에서 +0.07을 통과할지 외삽할 수 없다. 특히 100M에서
dynamic50은 같은 밀도의 static50보다 +0.01703 열세다. 기존 30M +0.15와
100M +0.07 게이트 실패 사실은 유지한다.

| 100M 팔 | JSON 중앙 ms/step | dense 대비 | 학습 peak allocated/reserved GiB | checkpoint 파일 byte |
|---|---:|---:|---:|---:|
| dense | 1576.1 | 기준 | 8.009 / 8.852 | 780,040,939 |

**확인된 구현 원인**: `TLinear.refresh_quant()`는 connectivity mask를 적용해도
`TLinear.forward()`에서 `F.linear(x, wq)`의 **dense GEMM**을 그대로 호출한다.
0인 연결을 연산에서 건너뛰는 sparse kernel이나 작은 packed tensor를 쓰지 않는다.
`ConnectivityController`는 각 삼진 weight와 같은 형상의 `torch.bool` mask를
등록·보유하고, dynamic은 점수 clone·top-k·state reset 비용도 치른다.
따라서 현재 구현은 구조 희소성이 연산량/상주를 줄인다는 가설의 실행 경로가 아니다.
위 중앙값의 작은 차이를 개별 커널 원인으로 단정하는 profiler 계측은 아직 `NOT_RUN`이다.

**상주 회계 누락**: 여덟 JSON의 `runtime_mb=678.6671 MiB`와
`packed_mb=19.0868 MiB`는 dense/static/dynamic 모두 같지만,
`mem_breakdown()`은 `connectivity_mask` buffer를 합산하지 않는다.
JSON `mem_params.ternary=84,639,744`이므로 bool mask 하나의 **계산값**
84,639,744 byte = **80.71875 MiB**다. 따라서 sparse 팔의 현재 fp32
weight+_wq+mask **최소 텐서 상주 추정은 759.38585 MiB**이고,
dense의 보고식 678.66710 MiB보다 작지 않다. 이는 실제 RSS나 배포
컨테이너 실측값이 아니며 동적 controller score/임시 텐서도 별도다.
체크포인트도 sparse 쪽이 dense보다 약 84.67 MB 커서 현재 직렬화에
mask가 추가된 정황과 일치한다. 이론 packed 19.09 MiB를 실제 mask 포함
파일·상주 크기로 제시하면 안 된다. 40 MiB 상주 목표를 충족했다는
주장도 불가하다.

**다음 단계 선택**: 기존 `run_P092_Stage3W_full_trainer_300M_seeds.sh`는
추천 목록에서 삭제하지 않고 게이트 실패 `HOLD`로 보존한다. 사용자는
별도 Stage3Wb **속도·상주·로드 경로 진단 → 원인별 수정·재검증 →
동일조건 dense/DST50 300M 한 시드 탐색** 순서를 선택했다.
진단 결과가 없는 현재 300M 탐색의 품질·속도·실제 배포 상주는
`NOT_RUN`이며, 새 탐색은 옛 Stage3 게이트를 소급 통과시키지 않는다.
