## 1. Stage0W 관측 — 속도와 캐시

정확한 원본은 `100_log_20260926_P030B_Stage0W_wsl_cpu_d14_rms4.txt`다.

## 2. Stage0W 관측 — 상주와 잘못된 설명 문구

두 모델 모두 배포 변환 후 텐서 합산 116.2 MiB(삼진사본 83.2+기타 32.9), fp32 KV 회계 10.5 MiB @ seq1024였다. **합산 회계 하한만 126.7 MiB**여서 40 MiB 상한의 약 3.17배다. 저장 19.1 MiB는 아직 물리 packed 파일도 아니며 상주를 대신하지 않는다. 배포 변환 전 텐서합산 678.7 MiB 대비 후 116.2 MiB의 5.84×는 latent 해제 **와 int8 저장을 함께 켠** 결과다. 이때 도구가 인쇄한 `이론 상한은 2.00배`는 latent 해제만의 설명을 잘못 재사용한 것이다. 5.84×를 불가능하거나 메모리 계측 실패로 처리하지 않는다.

RSS는 기존 모델에서 로드 전/생성 후/변환 후 562.6/2092.9/2071.3 MiB, RMS4에서 1296.8/2642.3/2642.3 MiB였다. 뒤 팔의 시작 RSS가 높고 파이썬·torch 할당자가 메모리를 보유하므로 **모델 물리 상주의 순수 증분으로 읽을 수 없다.** 두 모델의 40 MiB 실패는 RSS 비율이 아니라 텐서+KV 회계 하한으로 충분히 확인된다. 로짓 동등성 `max|dlogit|=0`은 두 팔 모두 통과했다.

## 3. 예측 대조·판정

[계획 P030B](../test_plan/P030B_WSL-현행-RMS4-CPU배포-실측.md)의 현행 RMS4 1코어 바닥 질문은 이 호스트·이 프롬프트에서 **PASS**다. 같은 구조가 optimizer만으로 추론 연산량을 줄이지 않을 것이라는 예상은 타당하지만, 1코어 속도 수치의 차를 그 예상의 증명이나 반증으로 쓰지 않는다. `ag1`/타잉 등 다른 배포 후보와의 속도·상주 우열도 이 로그에 없다. 40 MiB 동시 배포 목표는 현재 int8-unpack 경로의 텐서+KV 회계로 **미달**이다.

## 4. 후속과 원본 보존

`bench_infer.py`의 동점 회계 자동 판정과 `mem_runtime.py`의 int8 병용 2× 문구는 2026-09-26 후속 코드에서 수정했다. 저장·상주 비가 모두 1 근처인데 속도만 차이 나면 `속도차 원인 미귀속`이라고 인쇄하고, 2× 상한은 **LUT뿐 아니라 INT8 저장 코드에서도 적용되지 않는다**고 명시한다. CPU 전용 `scripts/test_p030b_readout.py` 3/3 PASS는 문구·분기 회귀일 뿐 새 속도 측정이 아니다. 기존 원시 숫자와 1코어 15 tok/s 통과 자체는 재실행 없이 유효하지만, 1.149× 속도 차를 원인에 귀속하려면 순서 교차·반복별 분산의 별도 Stage0Wb가 필요하다. 깨끗한 모델 RSS가 필요한 질문은 각 팔을 별도 프로세스에서 기초 RSS부터 재야 한다. 새 사용자 결과를 보기 전 채택·기본값 변경은 하지 않는다.

실행 당시 진입점은 `run_P030B_Stage0W_wsl_cpu_d14_rms4.sh`였고 두 전체 명령은 아래 재현 부록에 기계 보존했다. 완료본 삭제 시 원래 SH 링크는 의도적으로 만들지 않는다.

## 6. 2026-09-27 Stage0Wb — 교차 순서에서 1코어 속도 우위가 재현되지 않았다

사용자 원본 [`100_log_20260927_P030B_Stage0Wb_cpu_order_rss.txt`](100_log_20260927_P030B_Stage0Wb_cpu_order_rss.txt)의 입력 check-only 1건, 별도 프로세스 1코어 decode 4건, 별도 프로세스 상주/RSS 4건은 모두 종료0이다. 같은 WSL 호스트·프롬프트 `대한민국의 수도 서울은`·128 생성토큰·호출별 3회 중위·`drop-latent/int8-store/unpack-cache/last-only`를 유지했다. **새 학습, 새 체크포인트, 모델 품질 시험은 없다.** 구 Stage0W의 속도비 1.149×와 현 교차 측정은 서로 다른 날짜·순서이므로 차이를 optimizer 효과로 바로 읽지 않는다.

### 6.2 원인·재현 한계와 후속

관측은 **고정순서 편향 또는 실행 시 변동으로 이전 1.149× 헤드라인이 설명될 수 있음**을 보여 주지만 원인을 특정하지는 못한다. CPU affinity·클럭·온도·allocator 상태와 모델별 세 반복 지연이 저장되지 않았기 때문이다. §5의 훈련 JSON이 같은 풀/seed/형상을 보였어도 가중치가 서로 달라 학습 optimizer만의 배포 효과는 별도 동일 가중치 대조 없이는 분리할 수 없다. 현 INT8 unpack 경로의 40MiB 동시 목표 미달 판정은 유지한다.

바로 위 기계 추출 부록의 `$tag`는 속도와 RSS 각각에서 **`d14_cla2_norecur → d14_cla2_norecur_rms4 → d14_cla2_norecur_rms4 → d14_cla2_norecur`** 순서였다. 새 쉘의 `set -uo pipefail`, `repo_root`, `tinylm_env.sh`, `python_bin`, `errors=0`, 위 두 `for tag in ...` 반복과 끝의 `errors != 0 → exit9`도 같은 실행 계약이다. 명령 템플릿만으로 루프 순서를 알 수 없으므로 이 줄을 재현 부록의 필수 보충으로 남긴다. 현재 단일 프롬프트 진단을 모델 선택 기준으로 승격하지 않으며, 추가 고비용 런은 frontier 우선순위·실제 packed 경로 선결을 다시 본 뒤 정한다.
