## 2. ★★★가장 중요한 발견 — **둘 다 어텐션을 버리고 있다**

| 모델 | 어텐션을 어떻게 줄이나 | 비율 |
|---|---|---|
| **Gemma-4-E2B** | ★**KV 를 20/35 층이 공유** + **28/35 층이 sliding 512** + **MQA(KV 헤드 1개)** | 전역 어텐션 **7/35 = 20%** |
| **Qwen3.5-0.8B** | ★★**18/24 층을 선형어텐션으로 교체** | 전역 어텐션 **6/24 = 25%** |
| ★**TinyLM 현재** | `cla_group 2` + ⏸`attn_group`(P057, 미확정) | **전 층이 full attention** |

> ★★★**이것이 우리 P057(어텐션 타잉)·CLA 축에 대한 가장 강한 외부 증거다.**
> **결과 041 §17 이 "복제층 어텐션 출력 cos 0.9882"** 를 쟀고, **결과 014 §11 이 "R8 의 값어치는
> 메모리뿐"** 이라고 했다. 두 프런티어 소형모델은 **같은 결론에 도달해 이미 배포**하고 있다.
>
> ★**그리고 우리 `--reuse-attn-on-dup`(6.5-1) 은 이 계열의 아이디어다** — 다만 **재귀 통과에 한정**한
> 형태다. **Gemma 의 `num_kv_shared_layers` 는 그것을 층 전체로 일반화한 것**이다.

### 2.1 ⚠️그런데 **우리 목적함수와 다르다**

🚫**둘 다 우리 목표(상주 40 MiB)를 겨냥하지 않는다.** 그들이 어텐션을 줄이는 이유는
**긴 문맥의 KV 캐시**(Gemma 131K, Qwen 262K 위치)다. **우리 seq 는 1024** 다.

| | 그들 | 우리 |
|---|---|---|
| 줄이려는 것 | ★**KV 캐시**(문맥 길이에 비례) | ★**가중치 상주**(문맥과 무관) |
| seq | 131K~262K | **1,024** |
| ⚠️함의 | sliding·linear attention 의 이득이 **seq 에 비례** | ★**우리 seq 1024 에서는 그 이득이 작다** |

> ⚠️★**그래서 "그들이 하니까 우리도" 가 아니다.**
> **KV 헤드 축소(MQA)·KV 공유는 우리에게도 가중치를 줄이지만**, **sliding·linear attention 은
> 주로 캐시를 줄이므로 우리 목적함수에 거의 기여하지 않는다.** 두 축을 섞지 않는다(함정 28).

> 🚫**"토큰이 적을수록 좋다" 는 틀렸다.**
>

## 8. 🚫★**gemma 교사는 이 형상에서 안 들어간다 — 어휘 262,144 가 KD 를 다시 막았다** (P067 단계2a, 2026-08-30)

> 로그 [`053_log_20260830_P067_stage2a_gemma_probe.txt`](053_log_20260830_P067_stage2a_gemma_probe.txt) · 계획 [P067](../test_plan/P067_외부-토크나이저와-외부-교사.md) 단계2a

### 8.1 ✅Q1 — 캐시가 만들어졌다

| 캐시 | `ko-en` 600M, `bytes_per_token` 스트림 **4.1385** / val **2.6223** |

⚠️★**`bytes_per_token` 이 스트림과 val 에서 −36.6% 차이**난다. 기존 32,768 어휘에서도 있던 성질이지만
**이 캐시의 bpb 를 기존 런과 비교할 수 없다**는 사실을 다시 확인해 둔다(함정 2) — 교차비교는 `common_bpb.py` 만.

### 8.2 ✅Q2 — 무교사(`GT0probe`)는 여유 있게 돈다

| | 값 |
|---|---:|
| 형상 | `micro-bs 2 × accum 64 × seq 1024`(**M=2,048**) · `--ce-chunk 1024` |
| VRAM reserved | ✅**8.27 GiB**(한계 15.0) |
| ms/step 정상상태 | **11,775** |
| 파라미터 | ★**122.2M**(어휘 32,768 일 때 48.2M → **2.53배**) |

🚫★★**속도 대가가 크다.** 토큰당으로 정규화하면:

| | M | ms/step | **ms/토큰** | 비 |
|---|---:|---:|---:|---:|
| 표준(어휘 32,768) | 8,192 | 2,485 | **0.0190** | 1.00 |
| ★gemma 어휘 262,144 | 2,048 | 11,775 | ★**0.0898** | ★**4.73배** |

→ ★**2289스텝 완주는 ⚙7.5시간**이다(표준 1.6h 의 4.7배). **단계2 의 예산 편성이 이 수를 써야 한다.**
⚠️**M 이 4배 작아 이 비교에는 형상 차이가 섞여 있다**(결과 007: M=2048 은 M=8192 보다 느리다).
**순수 어휘 대가는 이보다 작다** — 상한으로 읽는다.

### 8.3 ✅Q4 — step0 앵커가 맞았다

| | 값 |
|---|---:|
| step0 CE | **12.4917** |
| 이론 앵커 `ln(262,144)` | **12.4766** |
| 차 | ★**+0.0151** |

✅★**난수 초기화가 정확히 균등분포에서 출발했다.** 어휘 262,144 에는 부모가 없으므로
**부모초기화 앵커(7.7742)가 아니라 난수 앵커**를 쓰는 것이 맞고, 그 값이 맞았다.
★**함정 34 대비**: 기준값을 먼저 의심하라는 규칙대로 `ln(V)` 를 직접 계산해 대조했다.

### 8.4 🚫★★Q3 — **gemma-3-1b 교사는 OOM 이다**

```
torch.AcceleratorError: CUDA error: out of memory   (trainer.py:653  loss.backward())
```

| | |
|---|---|
| 조건 | 학생과 **같은 형상**(M=2,048) + `--kd --kd-every 4 --kd-chunk 512 --teacher-dtype bf16` |
| 교사 | **999.9M 파라미터** bf16 · vocab 262,144 |
| 실패 지점 | ★**`loss.backward()`** — forward 는 통과했다 |
| 소요 | 0.3분 |

★**원인은 알려진 항이다**: 학습 VRAM 의 최대 항목은 모델이 아니라 **"어휘 전체 위의 KD 손실 계산"**
(`docs/methods/09_training_memory.md`). 어휘가 **8배**(32,768 → 262,144)가 되면 그 항이 8배가 된다.
`--kd-chunk 512` 는 **KD 항만** 나누고 **backward 그래프는 못 나눈다.**

⚠️★**함정 29 대비**: 이번에는 `torch.AcceleratorError: CUDA error: out of memory` 라는
**이름 그대로** 왔다. (`CUBLAS_STATUS_EXECUTION_FAILED` 로 위장한 적이 있어 확인해 둔다.)

→ 🚫★**그 처방을 그대로 쓰면 교사 축과 속도 축을 동시에 못 본다.** 세 갈래가 있다:
