## 1. 가장 중요한 여섯 가지

### 1.1 과거 Triton 원인 판정

P014 정본 `test_result/003_20260725001000_P014-커널-어닐버그.md`에서 최초 reference 불일치는
anneal 항 누락, JIT 실패는 `G`의 `tl.constexpr` 위반, `--compile` 동반 5~7초/step은
anneal Python guard에 따른 Dynamo 재컴파일로 기록됐다. constexpr 수정 후 같은 Windows 실행에서
k_off 9.3181 / k_ref 9.3169 / k_triton 9.3181, fallback 경고 0이 관측됐다. 따라서 과거 증거는
일반적인 Windows Triton 라이브러리 장애를 지지하지 않는다.

### 1.2 삼진 커널의 현재 완성도

기존 경로는 **int8 {-1,0,+1} code를 만드는 정확성 prototype**이다. forward만 Triton이고
backward는 PyTorch 수식이며, `(O,I)` dense `wq` 생성과 `--compile` 금지 제약이 남아 있다.
따라서 “Triton 삼진 커널 구현 완료”를 완성된 packed/fused 학습 가속기로 표현하지 않는다.
PM001은 `ternary_kernel_status()`의 attempts/successes/fallbacks와 import/compile/launch 범주,
`--ternary-kernel-strict`를 추가해 실패를 성공처럼 기록하지 않게 했다.

### 1.3 5비트 패킹과 학습시간

학습은 `_TernarySTE` 3:4 mask 뒤 dense `F.linear`를 사용한다. `pack_sparse34()`는 진단·배포
caller뿐이라 패킹 수정이 학습 forward에 들어갈 호출 기회가 없다. 기존 같은-g 실측도 sparse34가
약 `+0.6%`였다. 따라서 패킹 수정만으로 학습시간 단축을 주장할 수 없고, 사용자의 조건에 따라
CPU 추론 LUT로 방향을 전환했다.

### 1.4 PM001 CPU LUT 경로

`tinylm/model/sparse34_cpu.py`의 `reference`는 PyTorch oracle이고 `native`는 지연 빌드하는
`tinylm/model/csrc/sparse34_lut_cpu.cpp` 확장이다. native는 `(O,row_bytes)` 행별 5-bit stream을
직접 읽고, 입력 4개마다 32상태 LUT를 만든 뒤 packed code를 조회하며 g128 alpha를 그룹별로
누산한다. `(O,I)` int8/fp32 복원 weight tensor를 만들지 않는다. code stream은 1.25bpw지만
g128 fp32 alpha가 0.25bpw를 더하므로 삼진 표현 회계는 대표 shape에서 1.50bpw이며, 이 수치는
모델 전체 RSS나 호출 중 workspace와 구분한다.

### 1.5 동적 증거 경계

사용자 `202609061405_smoke_fdce364.txt`는 sparse34 1,000,000개 왕복 mismatch 0, groups
1/2/7/8/9/17/32 tail/codebook PASS, 156,250 bytes와 1.250000bpw, 잘못된 입력 거부,
PM000 arm/contract PASS를 확인했다. 사후 요약은 34 arm 중 `check_links.py` exit 5 한 건이
남아 전체 smoke RED이므로 PM000 장기 Stage1은 HOLD다. PM001 구현은 그 smoke 뒤에 들어갔으므로
새 Stage0/1/2 로그가 필요하다.

### 1.6 현재 브랜치·환경

HEAD는 `3791a88`이며 `moonshot`이다. `3741bbd`에는 PM000 재스모크 로그·결과를, `3791a88`에는
PM001 코드·계획·진단·배치·완료 원장을 한국어 로컬 커밋했다. main과 merge/rebase/cherry-pick/push는
하지 않았다. AI interpreter `C:\Python311\python.exe`에는 torch, Triton, triton-windows, Ninja가
없고 `cl`도 PATH에 없었다. 이 사실로 사용자의 `.bat` interpreter를 판정하지 않는다.

   build 시간은 제외하고 dense/generic g5/native의 shape별 median을 비교한다. exit 0은 속도 승리가 아니다.
4. 로그를 전달하면 `moonshot_result/PM001__MOONSHOT__...__RESULT.md`를 새로 만들고 backend,
   오차, bytes, shape별 속도를 분석한다. 그 전에는 결과 문서를 만들지 않는다.
5. main merge/rebase/cherry-pick/push는 하지 않는다. 추가 구현·복잡한 코드 변경 요청이 생기면
   먼저 보고하고 사용자 허가 전에는 대기한다.
6. 삭제 가능한 `-done` 배치는 없다. 기존 사용자 삭제 대상은 복구·추가 삭제하지 않는다.
