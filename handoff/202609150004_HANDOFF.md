## 1. 가장 중요한 것 셋

1. **P005b의 다음 과학적 단계가 열렸다.** RMS x4는 jordan20보다 무재귀 네 형상 모두에서 0.0048~0.0062 낮은 full-val loss를 냈고 matrix weight decay 0이 0.1보다 나았다. 다만 아직 seed·긴 런 전이가 남아 전역 기본값은 아니다.
2. **P025B와 P092의 상태를 섞지 않는다.** P025B는 RTX 4070 Ti SUPER·PyTorch 2.10.0 환경에서 cuSPARSELt 지원 경로가 없어 backend 게이트가 닫혔다. P092는 코어 mask STE·inactive regrowth·birth/death 계약만 PASS이며 trainer·속도·품질은 `NOT_RUN`이다.
3. **TinyDataset은 먼저 이력 문제를 정리한 뒤 독립 저장소로 떼고, 그 저장소에서 SFT 구조를 한 번만 바꾸는 편이 안전하다.** 지금 monorepo에서 먼저 개명하면 분리 때 같은 참조를 두 번 고치게 된다.

### 2.1 P089 Stage2b — 폭 대가와 깊이 회복

- 두 학습과 paired full-val은 모두 exit 0, skip 0이다.
- `w512_d14_muon15_b` full-val 3.6625, `w512_d28_muon15_b` 3.5597, 기준 `d14_cla2_norecur_muon15` 3.5608이다.

### 2.2 P005b Stage2b — RMS 상단 괄호

- full-val은 RMS2 3.5444, RMS4 3.5279, RMS6 3.5278, RMS8 3.5368이다.
- RMS4와 RMS6 차이는 0.0001로 동급이고 RMS8은 RMS4보다 0.0089 나빠졌다. 상단은 x4~x6 plateau에서 닫혔으므로 단순하고 사전등록된 **RMS x4를 유지**한다.

### 2.3 P005b Stage3 — matrix weight decay

### 2.7 GitHub 대용량 push 거부 — 원인과 최소 복구안

- GitHub의 일반 Git blob 제한은 100 MiB이고, 50 MiB를 넘으면 경고한다. 이번 124.55 MiB·136.76 MiB 파일 두 개가 push를 막고 56.61 MiB·66.16 MiB ledger 두 개는 경고 대상이다.
- 네 파일은 `origin/main..main`의 23개 커밋 중 `46ac1b8`에서만 추가됐다. 이후 같은 경로 수정과 merge가 없고, 해당 커밋은 로컬 `main`에만 있다.
- 따라서 **새 삭제 커밋만 추가하면 실패한다.** 이전 커밋의 blob이 push pack에 남기 때문이다. 외부 백업 후 `46ac1b8` 자체를 편집해야 한다.

### 2.8 SFT `v1`·`v2`·`v2_r1` 구조 재정리안

현재 이름만 확인한 구조에 따른 목표 매핑은 다음과 같다.

| 현재 | 목표 | 처리 |
|---|---|---|
| `SFT/audit`, `authoring`, `eval`, `manifests`, `prompts`, `sources`, `tools`, `train` | 각각 `SFT/v1/` 아래 | v1 패키지로 이동 |
| `SFT/PHASE0_DESIGN_REVIEW_V1.md`, `SFT/PHASE1_PILOT_REPORT_V1.md` | `SFT/v1/` | v1 문서로 이동 |
| `SFT/README.md` | `SFT/README.md` | 루트 버전 색인으로 남기고 링크 갱신 |
| `SFT/v2/*` 중 `revision1` 밖 | 동일 `SFT/v2/*` | 유지 |
| `SFT/v2/revision1/*` | `SFT/v2_r1/*` | 형제 판으로 이동 |

세 대안을 비교했다.

- **A. monorepo에서 먼저 개명**: 즉시 경로는 깨끗해지지만 독립 저장소 분리 때 활성 참조를 두 번 고칠 위험이 있다.
- **B. 독립 저장소로 먼저 분리한 뒤 그 안에서 개명 — 권장**: TinyLM 소비자 계약을 한 번만 바꾸고 데이터팀이 새 저장소에서 구조를 검증할 수 있다.
- **C. junction·symlink로 구경로 유지**: Windows·Git·검사기에서 실제 정본이 둘처럼 보일 수 있어 장기안으로 부적합하다.

권장 순서는 데이터 작성 세션 동결과 병렬 WIP 종료 확인 → 저장소 밖 백업·파일 manifest 확보 → §2.7 이력 정리 → 독립 저장소 추출 → 새 저장소에서 정확한 매핑으로 이동 → 활성 참조 일괄 갱신 → 구조·레코드 수·해시·감사 회귀 → 구경로 제거다. 현재 확인된 활성 참조에는 `scripts/audit_sft_corpus.py`, `scripts/audit_heldout_v28.py`, `scripts/diag_sft_mask.py`, `scripts/fetch_bench_data.py`가 있다. 과거 결과·핸드오프의 경로 문자열은 당시 provenance이므로 소급 수정하지 않는다.

| 안 | 장점 | 비용·위험 | 판정 |
|---|---|---|---|
| sibling 독립 repo + `TINYDATASET_ROOT` | 데이터팀 작업·권한·이력·대용량 정책을 완전히 분리하고 TinyLM dirty tree를 오염시키지 않는다. | 개발자가 두 repo를 받아야 하고 버전 pin을 별도 파일로 관리해야 한다. | **우선 권장** |
| `datasets/TinyDataset` submodule | 기존 경로를 유지하고 TinyLM commit이 데이터 commit을 정확히 pin한다. | submodule update·detached HEAD·병렬 dirty 상태 운영 부담이 크다. | release pin이 필요해질 때 2단계 후보 |
| subtree | 한 번 clone으로 소스를 받기 쉽다. | 고빈도 데이터 이력을 TinyLM에 다시 끌어오며 양방향 sync와 대용량 문제가 반복된다. | 비권장 |

권장 이관 절차는 다음과 같다.

1. §2.7로 현재 TinyLM 이력을 먼저 정리하고 clean push를 확인한다.
2. **현재 작업 폴더가 아닌 disposable clone**에서 GitHub의 하위 폴더 분리 방식으로 이력만 추출한다.

```powershell
Set-Location Z:\
git clone https://github.com/myplmy/TinyLM.git TinyDataset-extract
Set-Location Z:\TinyDataset-extract
git filter-repo --subdirectory-filter datasets/TinyDataset
git branch --show-current
```

3. 빈 TinyDataset GitHub 저장소를 만든 뒤 추출 clone에 새 origin을 연결하고 현재 브랜치를 push한다. 실제 URL과 브랜치명은 생성 후 확인하며 추측하지 않는다.
4. 새 저장소에서 §2.8 구조 정규화를 별도 commit으로 수행한다. 네 대용량 파일은 백업에서 복사하되 먼저 artifact 정책을 정하고 일반 Git에는 다시 넣지 않는다.
5. TinyLM에는 작은 버전 계약만 둔다. 권장 필드는 데이터 repo URL, release/tag 또는 commit, schema/manifest version, 필요한 artifact SHA-256이다.
6. TinyLM의 모델 결합 진단은 `TINYDATASET_ROOT`를 명시적으로 받고, 데이터 생성·패키징·순수 감사 도구는 TinyDataset repo로 옮긴다. 외부 sibling 경로도 AGENTS·`.agents/project.json`·scope 검사·hook에서 보호 대상으로 처리하도록 별도 구현 승인을 받아야 한다.
7. 새 원격 clone, 작은 파일 이력, artifact 복구, 정적 감사, TinyLM 소비자 테스트가 모두 통과한 뒤에만 monorepo 원본 제거를 별도 승인한다. 원본 저장소와 백업 브랜치는 그때까지 롤백 정본이다.

대용량 canonical JSONL과 source ledger는 새 repo에서도 일반 Git에 넣지 않는 편이 낫다. 팀 공유가 필요하면 Git LFS 또는 별도 artifact/Hugging Face/DVC 계층 중 하나를 선택하고, Git에는 생성 recipe·license·manifest·hash만 둔다. 로컬 untracked만으로 팀 전달을 해결하면 다른 PC에서 재현되지 않으므로 `.git/info/exclude`는 이번 복구용이고 새 데이터 저장소의 장기 정책은 committed `.gitignore`와 artifact manifest가 소유해야 한다.
