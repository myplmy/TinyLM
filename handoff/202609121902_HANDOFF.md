### 2.4 P088 Stage10의 풀·반복·언어 축 재감사

- t600과 t1200은 모두 `--pool-tokens 1200M --exact-cache`다. 다른 것은 steps 4,578→9,156과
  실제 학습 토큰 draw 600,047,616→1,200,095,232다. 따라서 **학습데이터 풀을 600M에서 1.2B로
  늘린 실험이 아니다.**
- `trainer.py`는 명시된 `pool_tokens`를 `prepare()`에 넘기고, `tinylm/data/loader.py`의 `Loader`는
  `rng.integers(...)`로 시작점을 균등 복원추출한다. 그러므로 순차 epoch 증가도 아니며, 정확한 표현은
  **고정 1.2B 풀에서 약 0.5→1.0 epoch-equivalent로 무작위 노출량을 늘린 것**이다. 실제 train 길이
  1.194B 기준으로는 약 0.503→1.005이고, 명목 1.2B 근사의 기대 유니크는 약 472M→759M이다.
- WSD의 감쇠 구간은 전체 steps의 비율이므로 절대 감쇠 시작·종료도 함께 두 배로 밀린다. 따라서
  노출량만 고립한 대조가 아니라 **무작위 draw 수와 비례 WSD 학습 지평의 결합**이다.
- 한국어 원천은 300,186,620 토큰에서 소진되고 1.2B 풀의 학습 구성은 한국어/영어 25%/75%다.
  두 팔은 같은 풀이라 기대 언어 구성도 같아 Muon 이득 축소를 풀·언어비 변화로 설명할 수 없다.
  그러나 말미 0.5% val의 한국어는 **0.0%**이므로 이 결과는 영어 전용 지표이고 한국어 품질은
  **NOT_RUN**이다. 실제 draw별 언어 비율은 계측하지 않았다.
- 같은 1.2B 풀·val인 600M→1.2B 차이-의-차이는 **부분 중첩** 판정에 유효하다. 반면
  300M/600M과 600M/1.2B 가족은 풀과 val 한국어 비율(5.5%→0.0%)이 함께 달라, 종전
  **“300M→600M 순수 가산”이라는 인과 판정은 철회**했다. 두 가족에서 Muon 효과 크기가
  비슷했다는 기술적 관측과 방향 전이만 남긴다.

#### 왜 사용자 지적 전에는 이 연결을 하지 못했나

정보 부재가 아니라 **GPT의 조건축 합성·연쇄 갱신 판단착오**였다. 이전 회수에서는 동일조건
AdamW/Muon 짝, `pool/tokens=1.0`, 수치 차이-의-차이에 집중하면서 이미 문서에 있던 언어 축과
샘플러 의미를 Stage10 결론에 결합하지 않았다.

- Codex 00의 R37·R39에는 학습토큰 산식과 풀/토큰 2배 규칙이 있고, Codex 01 §2에는 한국어
  300.19M 소진과 val 한국어 13.5/5.5/0.0%가 **명시돼 있었다**.
- P088 계획 §6과 결과 075 §3.2·§11.5에도 val 한국어 0%와 1.2B 풀의 25/75 구성이 있었다.
- 레거시 `CLAUDE.md`도 443~446행에 같은 언어 경계를 명시했다. 다만 563행에는 동시에
  “Muon×토큰 순수 가산”이라는 현재 철회한 요약도 있어, 사실의 존재만으로 올바른 결합이 보장되지는 않았다.
  `CLAUDE.md`는 이번 사용자 요청의 비교 자료로만 읽었고 Codex 환경 지침으로 사용하지 않았다.
- 수정 전 COMPASS는 `pool/tokens=1.0`과 독립 bpb NOT_RUN만 적고, **고정 풀 무작위 노출**과
  **영어 전용 val**을 빠뜨렸다. 이번에 두 축을 추가했다.
- `AGENTS.md`는 풀·학습토큰·평가 경로를 확인하라는 일반 경계이고, `exp-plan` 체크리스트는
  `--tokens`를 캐시 크기라고 적지만 `--pool-tokens`가 이를 덮어쓰는 의미와 복원추출까지는 명시하지 않는다.
  이는 향후 개선 후보이나, 사용자의 별도 승인 없이 스킬은 수정하지 않았다.

일반화 범위는 더 엄격해졌다. 이 정정에는 GPU 재실행이 필요하지 않다.

### 2.5 WIP CP949 예외와 실패 뒤 처리

- CP949에서 `★`·`🚫`·`✅` 출력이 깨지는 **일반 문제는 신규가 아니다.** Codex 02 §9.3과
  `proposal/20260912_WIP-및-스킬-스크립트-계약불일치-개선제안서.md` §5.1이 이미
  `python -X utf8` 또는 `PYTHONIOENCODING=utf-8`을 권고한다.
- 이번에 새로 확인한 하위 문제는 **부분 성공**이다. `wip.py:set_state()`는 파일을 145행에서
  먼저 저장한 뒤 146~147행에서 `✅`와 노트를 출력한다. 기본 CP949가 체크표시를 인코딩하지
  못하면 `UnicodeEncodeError`로 프로세스는 실패처럼 끝나지만 원장 변경은 이미 커밋돼 있다.
- 실제 실패 명령은 9번을 `🔄진행`으로 바꾸고 착수 로그까지 저장한 뒤 출력에서 예외가 났다.
  직후 파일을 확인해 두 변경을 확인했으므로 **9번 상태를 수동으로 다시 고치지 않았다.** 이후
  7~14번 상태 전이는 모두 `python -X utf8 scripts/wip.py --file ...`로 수행했다.
- 완료 뒤 `<br>`을 ` / `로 바꾼 서식 보정, 완료 원장 재열기, 7~14번 행 추가는 CP949 실패
  복구가 아니다. 각각 현행 도구의 `<br>` 강제와 `--reopen`·`--add` 부재 때문에 생긴 기존
  기능 공백이며 WIP 로그와 오류원장 A27, `WIP-수동수정-차단과-감사형-오버라이드` 제안서가
  이미 소유한다. 따라서 “실패한 상태 갱신을 수동 복구했을 때”라는 조건의 새 오류원장 항목은 없다.
- 기존 제안들은 UTF-8 실행과 수동 오버라이드를 다루지만 **저장 성공 후 출력 실패를 하나의 실패로
  오인하는 원자성 문제**는 명시하지 않았다. 이는 신규 하위 문제이며, 승인 후 개선 시에는 콘솔
  UTF-8 자가설정, 쓰기 전 출력 가능성 검사 또는 성공 저널, 사후 상태 판독이 함께 필요하다.

## 3. 무엇이 바뀌었나 — 코드·도구

`scripts/sync_experiments_tsv.py`의 종전 비교 문자열은 Python 소스에서
`"call scripts\\batch\\"` 형태였다. 실행하면 `\\b`가 경로 문자가 아니라 **U+0008 백스페이스**가 되어 실제
`call scripts\\batch\\tool_wandb_push.bat`와 `startswith`가 항상 False였다.

- 도입: 커밋 `6e437e2`(2026-08-30).
- 종전 런타임: prefix `repr == 'call scripts\\x08atch\\\\'`, 실제 호출과 일치 False.
- 현행: 기존 정본 함수 `norm()`으로 슬래시·대소문자·공백을 정규화한 뒤 `call scripts/batch/`를 제외한다.
- 범위 근거: [`scripts/batch/README.md`](../scripts/batch/README.md)는 이 폴더의 `.bat`을 실험이 아닌 재사용 기능 모듈로 규정하고, 현행 파일 9개도 모두 `tool_*.bat`이다.
- 회귀 대조: 현재 완료배치 4개에서 필터 뒤 명령 집합이 `append_repro.py`와 **4/4 동일**했다.

왜 늦게 발견됐는지도 분리한다. 전용 회귀검사가 없고, 이 보고 도구는 설계상 언제나 exit 0이다. 더구나 전체 `test_result/*.md`를 하나의 코퍼스로 합치므로 공용 `tool_wandb_push` 호출이 기존 결과 5개에 7회 있어 잘못 보존된 호출도 “있음”으로 처리됐다. 따라서 이번 P088 경고의 **직접 원인은 학습 명령 누락**이고, 필터 오류는 “명령 2개”라는 잘못된 분모를 만들었지만 누락 1건 자체를 만든 것은 아니다.

현재 사용자가 다른 시간을 명시한 경우에만 쓰며 0 이하 값은 argparse 오류로 거부한다. 공유

> ★**시간 목표 판정**: 별도 지시가 없을 때의 표준은 **48시간**이며 현재 큐는 **48.4h**로
> 충족한다. 세션별 다른 명시 목표는 `check_handoff.py --hours-target N`으로 전달하고, 중복·저가치
