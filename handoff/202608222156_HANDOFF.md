## 1. 가장 중요한 세 가지

### 1.1 ★★★**LUT 이 목표를 통과했다 — 삼진 항이 5.03배 줄었다**

같은 체크포인트(`mC_d36_ag4_nokd`), `mem_runtime.py` 실측:

| 경로 | 삼진 항 | 기타(임베딩 fp32) | **텐서합산 상주** |
|---|---:|---:|---:|
| fp32(2벌) | 346.4 | 33.2 | **379.7 MB** |
| int8 | **44.7** | 33.2 | **77.8 MB** |
| ★**LUT** | ★**8.88 MiB** | 33.2 | ★**42.1 MB** |

★**44.7 → 8.88 = 5.03배.** 예측은 `8 / 1.585 = 5.05` 였다 — **거의 정확히 맞았다.**
★**계산상 표준모델 LUT + emb int8 = 34.46 MiB → 40 통과.**
⚠️**단 emb bf16 으로는 58.5 라 못 간다** → **P034 단계5(임베딩 양자화)가 선결이다.**

🚫**그리고 게이트 기준값을 내가 또 틀렸다**(함정 34, **5번 중 5번**) — §2.4 참조.

### 1.2 ★★★**OOM 세 건의 원인이 서로 다르다**

| 런 | 죽은 지점 | allocated | 필요 | ★**원인** |
|---|---|---:|---:|---|
| `probe_d36_nock` | ★**`F.cross_entropy`** | 14.73 GiB | +512 MiB | ⚠️**모델 크기** |
| `probe_r20_nock` | ★**`F.cross_entropy`** | 14.84 GiB | +512 MiB | ⚠️**모델 크기** |
| `probe_q3teach` | `_kd_kl` → `F.kl_div` | 14.96 GiB | +594 MiB | 🚫★**내 코드** |

**용량 15.99 GiB, free 0 bytes** → **실질 부족 0.6~1.5 GiB.**

#### ★P065 = 크기다. `--no-ckpt` 구현은 정상이다

`--no-ckpt` 는 전 층 활성을 살려 두고, 그 위에서 CE 가 자리를 못 잡는다. **설계상 예상되는 동작.**
결과 051 의 20층 무KD `--no-ckpt` = **10.31 GiB** 에서 36층(1.8배)·재귀(2배 통과)로
올라간 결과가 14.7~14.8 이다 — **일관적이다.**

⚠️★**내 예측 둘 다 틀렸다.** 이전 핸드오프에 36층 ⚙11.5 / 재귀 ⚙12.6~14 라고 적었는데
**실제로는 둘 다 16 GiB 를 넘었다.**

★**그러나 고칠 여지가 있다**: `--kd-chunk` 는 **KD 손실만** 나눈다.
🚫**평범한 CE 는 한 번도 청킹된 적이 없었고**, **무KD + `--no-ckpt` 가 정확히 그 항이
노출되는 조합**이다. → ✅**`--ce-chunk N` 신설**(기본 0 = 비트 동일).
⚠️**정직하게**: backward 가 저장할 것은 안 준다. **기대 절감은 수백 MiB 대**다.

#### ★★P067 = 내 코드다

T1~T6 이 **전부 통과**했고(uint32 승격 포함, 토큰화 12.3분) 그 다음에 죽었다.

```python
def forward(self, x):
    ...
    return lg.float()   # ← (4, 1024, 151936) bf16 -> fp32 = 2.32 GiB 단일 할당
```

**규약 자체는 옳았다**(*"bf16 log_softmax 는 꼬리를 뭉갠다"*). 🚫**틀린 것은 시점**이다 —
`_kd_kl` 이 청크로 나눠도 **이미 통째로 물질화된 뒤**였다.
✅**교사는 원 dtype 반환, fp32 승격은 청크 안에서.** ⚙절감 **약 1.16 GiB** > 필요했던 594 MiB.

### 1.3 ★★★**HF 캐시가 작업폴더 밖으로 갔다 — 리다이렉트는 있었는데 실행되지 않았다**

🚫**그런데 `fetch_bench_data.py` 는 `sys.path` 만 건드리고 `tinylm` 을 import 하지 않았다.**

★★**함정 37 의 다른 얼굴** — *"리다이렉트가 존재한다 ≠ 그 경로가 실행된다."*
그리고 **조용한 실패**였다: 다운로드는 성공했고 에러도 경고도 없었다.

✅**3중 조치**: ①`import tinylm`(datasets 보다 먼저) ②실행 시 **경로를 인쇄하고

## 6. 커밋 메시지 제안

**제목**

```
CE 청킹과 교사 로짓 dtype 수정, LUT 상주 실측, HF 캐시 경로 강제
```

**본문**

```
OOM 세 건을 원인별로 갈랐다. P065 두 팔은 F.cross_entropy 에서 죽었고
14.73 과 14.84 GiB 에서 512 MiB 를 더 잡지 못했다. 512 MiB 는
8192 x 32768 x 2B 다. --kd-chunk 는 KD 손실만 나누고 평범한 CE 는 한 번도
나눈 적이 없었으며, 무KD 와 --no-ckpt 를 함께 쓰는 조합이 정확히 그 항이
드러나는 자리다. --ce-chunk 를 신설했다. 기본 0 이면 종전 호출 그대로라
비트 동일하다. 다만 backward 가 저장해야 하는 것은 줄지 않는다 - 줄어드는
것은 동시에 살아 있는 임시 텐서이고, 우리를 죽인 것이 정확히 그것이었다.

P065 의 OOM 은 --no-ckpt 구현 결함이 아니다. grad checkpoint 를 끄면 전 층
활성이 살아 있고 그 위에서 CE 가 자리를 못 잡는 것이 설계상 예상되는 동작이다.
결과 051 의 20층 10.31 GiB 에서 36층과 재귀로 올라간 값이 14.7~14.8 로
일관적이다. 다만 이전 핸드오프에 적은 내 추정치 두 개는 둘 다 틀렸다.

P067 의 OOM 은 내 코드였다. HFTeacher.forward 가 lg.float() 로 끝나면서
(4, 1024, 151936) 을 fp32 2.32 GiB 단일 할당으로 물질화했고, _kd_kl 이
청크로 나눠도 이미 통째로 만들어진 뒤였다. bf16 log_softmax 가 꼬리를
뭉갠다는 규약 자체는 옳고, 틀린 것은 언제 올리느냐였다. 교사는 원 dtype 을
돌려주고 fp32 승격은 청크 안에서 한다. 절감은 약 1.16 GiB 로 필요했던
594 MiB 보다 크다. 참고로 그 직전까지 T1 부터 T6 이 전부 통과했다 -
교사 로드, 어휘 일치, 로짓 shape 과 dtype, 토크나이저 왕복, uint32 승격,
600M 토큰화 12.3분.

LUT 상주를 실측했다. 같은 체크포인트에서 삼진 항이 int8 44.7 MiB 에서
LUT 8.88 MiB 로 5.03배 줄었다. 예측은 8 나누기 1.585 = 5.05 였다.
전체 텐서합산은 77.8 에서 42.1 MB 가 된다. 결과 052 의 m100R1q 18.3 MiB 는
17.35 로 재현됐고 차이는 0.95 MiB 다. 표준모델은 임베딩이 통짜라 계산상
LUT 에 emb int8 을 더해 34.46 MiB 이고 40 을 통과하지만, emb bf16 으로는
```
