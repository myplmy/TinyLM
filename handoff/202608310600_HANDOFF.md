## 1. ★가장 중요한 것 세 가지

1. ★★★**임베딩은 BF16 하나로 L2+L3 안에 든다. 그리고 그건 대가가 음수일 수 있다.**
   우리 forward 는 **이미 `autocast(bf16)` 안**이라 `F.linear(h, emb.weight)` 가
   **어차피 emb 를 bf16 으로 캐스팅**한다. → **bf16 으로 *저장*하면 그 캐스팅이 사라진다.**
   **상주 32.75 → 16.38 MiB 이고 연산은 오히려 준다.** 청크도 복원 버퍼도 필요 없다.
   ⚙**LUT + emb bf16 = 27.98 MiB < 40** ✅. ★**구현 ⚙40줄.**

2. ★★★**"회계 미세차 약 5%" 는 회계 문제가 아니라 단위 혼용이었다.**
   `MB=10⁶` 와 `MiB=2²⁰` 를 섞어 썼다. MiB 로 다시 계산하니
   **346.5000 + 32.7500 + 0.4251 = 379.675079** vs json `runtime_mb` **379.675079**
   → ★**소수 6자리까지 일치, 차 0.000000000.** ✅**열린 질문 하나가 닫혔다.**
   ★**함정 1 의 또 다른 얼굴** — 같은 이름(`MB`)이 두 양을 가리켰다.

3. ★★**문헌이 허락한 혼합정밀도는 우리가 이미 다 했다.**
   DeepSeek-V3 §3.3.3 은 **모멘트만 BF16**, **master·gradient 는 FP32 유지**를 명시한다.
   모멘트 bf16 은 P022B 단계2 로 끝났다. → ★**P068 은 "문헌을 넘어서는" 부분을 재는 계획이고,
   그래서 예측이 대부분 부정적**이다. **그래도 재는 이유는 "안 된다" 를 근거 없이 적지 않기 위해서**다.

## 2. 지시 (1) — 임베딩 양자화

### 2.1 ⚠️**신규 번호를 안 만든 이유** (사용자 조건부 지시에 대한 답)

지시: *"기존 실험계획 파일에 동일한 실험 **없었으면** 신규 실험계획 문서도 작성할 것."*

🚫★**있었다.** `P034 단계5`(임베딩·헤드 패킹)가 **§10.2 에서 재정의까지** 돼 있고
`transformer.py` 주석이 *"선택지는 계획 P034 §단계5 에 기록"* 이라고 가리킨다.
→ **번호를 새로 붙이면 같은 축이 두 곳에서 정의된다**(함정 18) → **P034 §11 로 확정 설계**를 썼다.

### 2.2 ★★현재 상태 — **회계가 이미 거짓말을 하고 있었다**

```
transformer.py 주석: cfg.quantize_embedding=True 는 mem_breakdown() 의 저장 계산에만 쓰이고
                     self.emb 는 평범한 nn.Embedding(fp32) 이다.
```

★**`packed_mb` 가 "아직 없는 포맷" 을 임베딩 쪽에서 가정하고 있다.**
→ **이 단계를 구현하면 기존 packed 숫자가 비로소 참이 된다.** 그 자체가 산출물이다.

### 2.3 ★★왜 순진한 int8 이 상주를 **늘리는가** — 입력과 출력이 정반대

| | 입력 조회 | ★**출력 헤드** |
|---|---|---|
| 만지는 행 | **T개**(배치1 디코드면 1개) | 🚫★**V행 전부, 매 스텝** |
| 양자화 대가 | 거의 0 | ★**GEMM 에 직접 먹히거나 복원 필요** |

**int8 저장 8.19 + fp32 복원 32.75 = 40.94 MiB > 32.75** → **늘어난다.**
그래서 종전 주석이 *"설계를 마치기 전에는 넣지 않는다"* 라고 적었다.

★**해법 = 청크 복원.** `C=4096` 이면 동시 버퍼 **4 MiB**.
★★**우리는 이 수법을 이미 검증했다** — **P053 이 KD 손실에 써서 reserved −3.06 GiB**(결과 048).

### 2.4 ★§10.2 선택지 넷 중 셋이 **죽었다**

| 선택지 | 상태 |
|---|---|
| (a) 헤드 untie | 🚫 파라미터 +8.4M — 메모리 목표와 충돌 |

| (d) 랭크 축소 | ⚠️ 부분 생존(E192 +0.0154). **양자화와 직교** |
| ★**(e) 청크 복원 + 양자화 저장** | ★★**신설. 유일하게 살아 있다** |

### 2.5 ★★★5종 구현 가능성 판정

| 포맷 | ⚙상주(MiB) | 구현 | **가능?** | 핵심 위험 |

| # | 위험 |

### 2.7 ★★수확 체감 — **어디까지 내려갈 값어치가 있나**

## 3. 지시 (2) — 학습 혼합정밀도 (P068 신설)

### 3.1 ★왜 P022B 가 아니라 새 번호인가

| | P022B | ★**P068** |
|---|---|---|
| 포맷 | **FP8**(E4M3) | ★**BF16/FP16** |
| 질문 | *"삼진 α 를 유지한 채 FP8 GEMM 이 되는가"* — 수치·커널 | ★*"fp32 로 남은 텐서 중 무엇을 내릴 수 있나"* — 저장·안정성 |
| 대상 | **Linear GEMM 3개** | ★**GEMM 이 아닌 것들** |
| 장벽 | K축 그룹 스케일 커널 부재 | ★**정밀도 누적** |

### 3.2 ★문헌 — **확인한 것만**

DeepSeek-V3 §3.3.3(우리 문서가 원문 인용):
**모멘트 BF16**(*"without incurring observable performance degradation"*),
★**master weight·누적 gradient 는 FP32 유지**(*"To further guarantee numerical stability"*).

> ★★**허락된 것은 우리가 이미 다 했다**(P022B 단계2). **나머지는 문헌을 넘어서는 것**이다.

⚠️★**Mixed Precision Training(Micikevicius) 은 arXiv id 를 확인하지 않았다** →
**계획서에서 근거로 인용하지 않았다**(CLAUDE.md 규약).

### 3.3 ★★가설 H-A — **언더플로는 스케줄 *끝*에서 온다**

```
x ≈ 0.02
ulp(bf16) = 2^-13 = 1.22e-4    -> 소실 문턱 ≈ 6.1e-5
ulp(fp16) = 2^-16 = 1.53e-5
ulp(fp32) = 1.19e-8
```

| 구간 | ⚙유효 lr | ⚙스텝 | bf16 |
|---|---:|---:|---|
| 초반 | 1e-3 | ~1e-3 | ✅ ulp 의 8배 |
| 타잉 그룹(lr/√8) | 3.5e-4 | ~3.5e-4 | ✅ 2.9배 |
| ★**감쇠 꼬리**(`decay_frac 0.2`) | ⚙1e-5 | ~1e-5 | 🚫★**ulp 의 1/12 — 사라진다** |

> ★★★**bf16 master 는 학습 전체가 아니라 감쇠 구간에서 무너진다.**
> **우리 `--sched wsd --decay-frac 0.2` 에 특정된 예측이고 문헌에 없다.**
> ★**검정이 값싸다** — `--anneal-end 0.30 --decay-frac 0.6 --steps 500` 으로 **감쇠를 앞당긴다**(단계1b).

★**우리에게만 있는 두 번째 위험 S-1**: `mask = (|w| ≥ thr·mean|w|)` 는 **문턱 비교**다.
bf16 가수 7비트면 **문턱 근처에서 어느 가중치가 0 이 될지가 뒤집힌다.** 문헌에 이 항이 없다.

### 3.4 ★팔 넷과 예측

| 팔 | 무엇 | ⚙구현 | 예측 |
|---|---|---:|---|
| ★**A1** | ★**`_wq` bf16 *저장***(계산은 fp32) | **15줄** | ★**G3: Δ < 0.005** — **축적기가 아니라 매 스텝 재생성이라 오차가 안 쌓인다.** 가장 유망 |
| **A2** | gradient bf16 | 40줄 | G2: +0.005~+0.02 (`clip_grad_norm_` · accum 16) |
| ★**A3** | master bf16 | 50줄 | 🚫**G1: Δ > +0.02** (H-A + S-1) |

## 6. 커밋 메시지 제안

### 제목

```
임베딩 양자화 5종 확정설계와 학습 fp32 강등 계획 — 회계 5% 차는 단위 혼용이었다
```

### 본문

```
[임베딩 양자화 — P034 단계5 확정 설계]
- 신규 번호를 만들지 않았다. 동일 실험이 P034 단계5 로 이미 예약돼 있었고 §10.2 가
  재정의까지 해 뒀다. 번호를 새로 붙이면 같은 축이 두 곳에서 정의된다(함정 18, D16).
- 회계가 이미 거짓말을 하고 있었다: quantize_embedding=True 는 mem_breakdown() 의
  packed 계산에만 쓰이고 self.emb 는 fp32 다. 구현하면 기존 packed 숫자가 참이 된다.
- 입력 조회(행 1개)와 출력 헤드(V행 전부)가 정반대여서 순진한 int8 은 상주를 늘린다
  (8.19 + 32.75 = 40.94 > 32.75). 해법은 청크 복원이고, P053 이 KD 손실에 같은 수법을
  써서 reserved -3.06 GiB 를 이미 검증했다.
- BF16 은 복원조차 필요 없다. forward 가 이미 autocast(bf16) 안이라 emb 를 bf16 으로
  저장하면 캐스팅이 사라진다. 상주 32.75 -> 16.38 MiB 이고 연산은 오히려 준다.
  LUT + emb bf16 = 28.0 MiB 로 L2+L3 목표선 안이다. 구현 약 40줄.
- §10.2 선택지 4개 중 3개 사망: (b) int8 GEMM 은 P014C §14, (c) 어휘 축소는 P039
  (빈도 0 토큰 0.28%). (e) 청크 복원 + 양자화 저장만 살아 있다.
- int8->int4 는 4.0 MiB, int4->ternary 는 2.5 MiB. 이득은 급감하고 위험은 급증한다.
  ternary 는 될 것 같아서가 아니라 축의 끝을 표시하려고 넣었다(예측 Δ > 0.15).

[학습 fp32 강등 — P068 신설]
- P022B(FP8·GEMM·커널)와 축이 다르다. 이건 BF16/FP16 이고 대상이 비GEMM 텐서
  (master / gradient / _wq / norm / RoPE)다.
- 문헌이 허락한 것은 이미 다 했다. DeepSeek-V3 §3.3.3 은 모멘트만 BF16 이고
  master 와 gradient 는 FP32 로 지키라고 명시한다(P022B 단계2 로 완료).
- 가설 H-A: bf16 master 는 학습 전체가 아니라 감쇠 구간에서 무너진다.
  ulp(bf16)@0.02 = 1.22e-4 인데 decay_frac 0.2 꼬리의 스텝 크기가 ⚙1e-5 다.
  우리 스케줄에 특정된 예측이고 문헌에 없다. --anneal-end 를 앞당겨 짧은 런으로 본다.
- S-1: 삼진 문턱 비교(mask = |w| >= thr*mean|w|)는 bf16 가수 7비트에서 뒤집힐 수 있다.
- A1(_wq bf16, ⚙15줄)이 유일하게 통과할 것으로 본다. _wq 는 축적기가 아니라 매 스텝
  fp32 w 에서 새로 만들어져 오차가 쌓이지 않는다.
- 배치를 만들지 않았다. 구현 ⚙135줄이 선결이고 착수는 허가가 필요하다.

[회계 5% 차 해소 — 단위 혼용이었다]
- P066 §1 이 "약 398 MB, 5% 차, 미확인" 이라고 적었던 것은 MB(10^6)와 MiB(2^20)를
  섞어 쓴 결과였다. MiB 로 계산하면
    346.5000 + 32.7500 + 0.4251 = 379.675079  vs  json 379.675079
  소수 6자리까지 일치한다. 회계에는 아무 문제가 없었다. 함정 1 의 또 다른 얼굴.
- P066·02_memory.md 의 34.3 MB / 33 MB 표기를 32.75 MiB 로 정정.

[wandb]
- --check 3항목 전부 정상(키 있음 / v0.28.2 / 93런).
- final 이 중첩 dict 라 wandb 요약에서 정렬·차트가 안 된다. final_val_loss 처럼
  평평하게 펴도록 수정. 요약 필드 17 -> 25개.
```
