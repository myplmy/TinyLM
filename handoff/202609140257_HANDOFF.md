## 1. 가장 중요한 것 셋

1. 오류는 실제 코드 결함이다. `sorted(BASE.glob(...), key=heldout_version_key)`가 반복문 안의 `is_dir()`보다 먼저 모든 glob 항목에 엄격한 키를 적용해 `held-out_v1_archive`에서 중단했다.
2. 수정은 파서를 느슨하게 만든 것이 아니다. 디렉터리이고 숫자 판 이름인 항목만 선별한 뒤 `2.9 < 2.10 < 3.0`으로 정렬한다. 실제 사용자 fetch는 아직 재실행하지 않았다.
3. `audit_sft_corpus.py`는 자동 로그 파일을 쓰지 않는다. 직전 5B에서 추가한 로그·종료코드 계약은 `fetch_bench_data.py`만 대상으로 했고, 두 작업을 한 문장에 묶은 이전 보고가 불명확했다.

## 2. 무엇을 했나

### 2.1 fetch 실패 원인과 수정

- `heldout_dirs()`는 `BASE.glob("held-out_v*")`의 결과를 먼저 `heldout_version_key`로 정렬했다.
- Python의 `sorted(..., key=...)`는 반복문에 들어가기 전에 모든 원소의 key를 계산한다. 따라서 뒤쪽의 `if d.is_dir()`는 `held-out_v1_archive`를 거를 기회를 얻지 못했다.
- `heldout_version_key`가 `held-out_v숫자[.숫자...]` 외 이름에 `ValueError`를 내는 것은 올바른 fail-closed 계약이다. 호출부의 선별 순서만 잘못됐다.
- 수정 후에는 각 glob 후보에 대해 디렉터리 여부를 먼저 확인하고, 엄격한 키가 받아들이는 숫자 판만 모은 뒤 정렬한다. archive가 파일이어도, 디렉터리여도 무시한다.
- 임시 디렉터리에 `held-out_v2.9`, `held-out_v2.10`, `held-out_v3.0`, `held-out_v1_archive`, `held-out_vnotes`를 만들어 숫자 세 판만 올바른 순서로 반환하는 회귀를 추가했다.
- 실제 `datasets/TinyDataset/**`와 `runs/**`는 읽지 않았고 fetch도 실행하지 않았다.

### 2.2 SFT 감사 로그의 정확한 상태

- `audit_sft_corpus.py`에는 `--log`, `logging.FileHandler`, `open(..., write)`, `write_text` 같은 출력 저장 경로가 없다.
- 따라서 사용자가 실행한 3번 결과는 stdout/stderr 콘솔에만 있었다. 터미널 scrollback이 남아 있지 않고 셸 리다이렉션·tee를 사용하지 않았다면 기존 실행을 복구할 파일은 없다.
- 반면 fetch는 직전 변경에서 사용자가 지정한 `runs\census\20260914_stage1_heldout_v3.0_fetch.log`에 콘솔과 같은 내용을 기록한다. 이번 traceback의 started/argv/traceback/exit_code/ended가 그 계약이 실제 작동했다는 증거다.
- 직전 WIP 5B의 “실행 로그”는 문장상 바로 앞의 `fetch_bench_data.py` 실행건으로 이해했다. SFT 두 감사기에 자동 로그를 추가하라는 뜻으로는 이해하지 않았다.
- 다만 이전 보고에서 “SFT import/T1 검사와 fetch 로그·종료코드를 보강”이라고 한 문장에 묶은 것은 두 스크립트 모두 로깅된 것처럼 보일 수 있어 불명확했다. 앞으로는 `SFT: 콘솔 출력·감사 로직`, `fetch: 영구 로그·프로세스 종료코드`로 분리해 쓴다.
