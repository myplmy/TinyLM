## 1. ★가장 중요한 것 여섯

### 1.1 PM000 격리 후 동적 계약은 통과했다

- 최신 smoke PM tag: `tinygqa_synthetic_2M_dense_pm000__sm_gqapass`.
- schedule/order `latin/[0,1]`, R3, CLA2, final/best `9.884375/9.8825`, skip 0.
- Stage0B: params `36,136`, state keys `47`, R1 exact, R3 delta
  `6.521e-03`, cached/full `3.539e-08`, KV entries 4, finite backward.
- 이는 wiring/correctness 증거일 뿐 품질·일반지능 향상 증거가 아니다.

### 1.2 최신 전체 smoke는 수정 전 RED다

[202609060951_smoke_e0330e3.txt](../smoketest_logs/202609060951_smoke_e0330e3.txt)는
`e0330e3 +dirty 47개`에서 생성됐다. 사후 판독은 34 arm, nonzero 2,
exit-0 error marker 0, instrumentation error 0이다. 실패는
`check_links.py` exit 5와 `diag_sparse34_pack.py` exit 1이다.

### 1.3 sparse34 원인은 정보 손실 포맷이었다

3:4 한 group은 zero-position 2비트와 부호 3비트, 합계 5비트다. 기존 구현은
5비트 code 둘을 `code0 * 32 + code1`로 합친 뒤 `uint8`로 잘랐다.
최대 10비트의 상위 2비트가 사라져 첫 code의 zero-position이 손실됐다.
회계도 2 code/byte를 가정해 125,000 byte / 1,000,000 weight = 1.0 bpw를 냈다.

### 1.4 수정은 독립 커밋이다

`92b88f7`은 8 code = 40비트를 5바이트에 연속 패킹한다. 크기는
`ceil(groups*5/8)`이고 기본 진단의 기대값은 156,250 byte와 1.250000 bpw다.
API 시그니처는 유지했고 저장/load caller와 기존 packed blob은 저장소에서 검색되지 않았다.

### 1.5 검증 경계

- torch-free bit oracle 321건: 32 code × 8 위치와 tail 1~65 — PASS.
- py_compile, import, PM namespace, PM batch lint — PASS.
- 전체 정적 suite 29/32. 기존 held-out D6 `E-157/E-205`, 로컬 cache link 5,
  일반 `dense` JSON registry 미등재 1건이 남았다.
- 실제 sparse34 tensor 왕복과 수정 후 smoke는 **미실행**이다.

### 1.6 main과 사용자 변경은 보존했다

`Z:/TinyLM`의 updated main HEAD `486d71d`을 읽기 비교했지만 sparse34 관련
파일은 `e0330e3` 이후 바뀌지 않았다. 따라서 merge·rebase·cherry-pick하지 않았다.
착수 전부터 삭제 상태였던 기존 루트 배치 15건도 복구·추가 삭제·stage·commit하지 않았다.
