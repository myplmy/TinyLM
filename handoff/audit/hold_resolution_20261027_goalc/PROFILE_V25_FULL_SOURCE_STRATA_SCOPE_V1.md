# 잔여 전량 유형분석의 새 원문 회수 범위

v25의 미결 77,665고유/122,585위치 전량 유형분석은 진단 후보를 분석한 결과이며 원문 판독이 아니다. 그 결과의 238개 새 대표 가운데 ordinal27과 겹치는 1개를 제외한 237개를 실제 토큰 구간에서 다시 읽는다. 현재 진단 후보의 UTF-8 합계는 2,215,488바이트, 최대 187,922바이트이며 HAS_HANGUL194/NO_HANGUL43이다. 이 언어 신호를 위키 출처 분류로 쓰지 않는다.

| 안 | 이점 | 한계 |
| --- | --- | --- |
| 후보만 읽고 일반 처리 허용 | 원문 재생성 비용이 적음 | 후보의 기존 오삭제를 발견할 수 없음 |
| 전체 미결을 즉시 개별 판독 | 각 문맥을 확인 가능 | 많은 동일 형식의 비교가 길어지고 검증할 규칙이 분리되지 않음 |
| 전량에서 정한 새 유형 전부의 원문을 먼저 회수 | 각 유형에서 원문과 후보 차이를 확인하고 좁은 규칙을 도출 가능 | 대표 판독 뒤에도 전량 적용 및 별도 검산이 필요함 |

세 번째 안으로 진행한다. 대표를 임의 작업량 상한으로 삼지 않는다. 공통 규칙은 이 단계에서 자동 승인하지 않으며 이후 실제 적용 대상 전량을 다시 계수·검산한다.

기존 prepare_v23_structural_counter_v1.py의 OriginalReader·토크나이저·UTF-8·EOS·SHA 검증 및 역할별 배정기를 재사용한다. 각 원문에 v25 진단을 다시 적용하여 기존 진단 후보 SHA를 정확히 재현해야 한다. 이미 개별 보류된 자료와 보호 경로를 추가로 열지 않는다. 원본이나 기존 캐시를 덮지 않는다. 새 파일은 각각20,000,000바이트 미만이고 manifest로 연결한다.

동일한 기존 Luna 다섯 역할만 지정 원문/후보/순서뷰를 전부 읽고 새 txt/md 및 판독표를 작성한다. 코드·시험·통계·모델·GPU·Git·웹·규약 수정·다른 경로 접근은 맡기지 않는다. 기존579/ordinal27의 정정이 먼저다. 총괄이 코드/검산/판단/중재를 담당한다.

코드 영향은 자기 audit의 기존 exporter 재사용 adapter와 읽기뷰 생성기뿐이다. 모델 구조·품질·속도 지표를 바꾸는 단계가 아니며 GPU/모델 실행은0이다. 자료 계보·분할·토크나이저·기존 코드63개는 동결하고 source/body/review SHA와 판독 범위를 기록한다. 정본 수치·공유 계획·Git/index는 아직 변경하지 않는다.
