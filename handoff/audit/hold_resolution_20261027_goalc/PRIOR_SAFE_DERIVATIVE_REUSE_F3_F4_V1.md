# 원문 비교본을 재접근하지 않는 기존 세 정제본 재사용

현재 목표의 원형 보호·이미 승인한 정제본 보존·CPU 캐시 검증 범위다.

| 안 | 내용 | 장점 | 위험·영향 | 비용 |
|---|---|---|---|---|
| A | 과거 비교본을 다시 열어 코드/Unicode를 대조 | 옛 절차와 같음 | 현재 보호 관찰기가 읽기 전에 차단했으므로 재시도하지 않음 | 부적합 |
| B | 실제 cache15에서 검증한 정확 세 승인행·정제SHA와 과거 proof를 재사용 | 원문 재접근 없이 같은 정제본만 유지 | 새 원문 보존 검사와 과거 증거 재사용을 구분해야 함 | 중간 |
| C | 세 정제본을 철회/새로 편집 | 비교본 의존 제거 | 이미 승인한 내용과 학습 구성의 불필요한 변경 | 높음 |

선택 B. 1250821·15695·20624의 현재 ROOT38 행은 실제 cache15 입력인 ROOT29와
메타데이터 전체가 같다. 원문SHA·비교본 descriptor·정제본SHA와 승인행 서명을 고정했다.
cache15 build/consumer 실제 exit0 및 restricted ledger proof를 별도 고정한다.
원형이나 비교본을 열거나 해시하지 않는다. 이미 승인한 세 별도 정제본만 실제 해시·인코딩한다.

실제 발견: 새 guard6 runtime preflight의 옛 GuardedInputs 초기화가 비교본 해시를 요청했고
관찰기가 open 전에 차단했다. 이 시도의 payload bytes read는0이며, 새로운 성공 검사에서
시도0이라고 보고하더라도 이 과거 부정 증거를 지우지 않는다. 초기 두 metadata preflight는
기존 EXCLUDE를 부모 HOLD와 혼동한 엄격 조건 때문에 source I/O 전에 거절됐다.

변경 범위는 audit의 캐시9 초기화·정확 세 승인행의 metadata registry·회귀·보고뿐이다.
보호 관찰기를 완화/해제하거나 파일 읽기 결과를 다른 텍스트로 바꾸지 않는다.
코드/Unicode의 새 원문 대조를 했다고 주장하지 않고, 과거 source-preservation proof 재사용과
현재 승인 본문SHA/캐시 직렬화 검사를 분리한다. 다른 문서는 기존 실제 코드 가드를 그대로 쓴다.
메모리의 가짜 원문·원문 사본·새 학습 TXT를 만들지 않는다. 원문·기존 캐시·체크포인트·모델·GPU·학습·타세션은 불변이다.
