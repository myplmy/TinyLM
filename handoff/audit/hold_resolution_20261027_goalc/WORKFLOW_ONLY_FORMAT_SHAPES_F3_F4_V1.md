# 잔여 처리 속도 질문 후의 전량 진단

사용자 질문은 이전 40만 규모 처리와 현재 10만 잔여의 속도 차이다. 현재 goal의 CPU 분석 승인 안에서 원인을 확인한다. 전량 metadata 집계는 ROOT32/roster23 잔여67,325고유 중66,411고유를 field/other 두 대기열에 연결했다. field16,249고유 중14,213고유/22,251위치는 기존 guard 모두 true이며 `remaining_reasons`가 비어 있다. 이것은 내용 품질 PASS가 아니다. 후보 사유까지 합쳤을 때 특정 결함 없이 작업흐름 판독 조건만 있는지 다시 확인한다.

| 접근 | 장점 | 한계·비용 |
|---|---|---|
| A. 현재처럼 모든 문서를 동일 순서로 전량 수작업 판독 | 각 문맥을 직접 확인한다 | 단순 차이와 복원 문제의 처리 비용을 동일하게 지불한다 |
| B. 실제 원형/후보 차이를 전량 계수해 형식 변화와 문맥 변화를 분리 | 단순 사례의 묶음 검토 가능량과 위험 사례를 실측할 수 있다 | 분류 후 독립 문맥 감사·채택 결정이 별도로 필요하다 |
| C. 누락 추출 원천을 찾아 복원 우선 | 수식·버전 조건의 실질 결손을 해결한다 | 원본 덤프가 확인되지 않았고 개별 primary 대조 비용이 든다 |

진단에서는 B를 먼저 수행한다. A의 기존 다섯 판독은 계속하고, C는 확인된 두 primary 사례에서 계속한다. 새로운 자동 채택 정책·표본 수·의미 품질 임계값을 이 진단으로 확정하지 않는다.

허용 경로는 현재 세션 audit의 새 진단 코드·작은 보고서와 data_cache의 새 metadata 조각뿐이다. 기존 원형/후보는 읽기만 하고 각각 SHA를 검증한다. guard5 제한 ID·부모 alias·원형/후보 hash는 열기 전에 건너뛴다. source cleanup/수치·의미 정책을 수정하지 않으며 정제 TXT를 생성하지 않는다.

코드 영향은 진단 한 개로 제한한다. 저장 데이터는 출처 pin과 차이 모양만 담고 각 파일4MB 미만으로 나눈다. 후보가 동일하다고 내용이 깨끗하다고 판정하지 않는다. 비교는 원래 문자의 접두/접미와 정확한 `()` 삭제 관계만 검사하며, 새 정제문을 쓰거나 실제 선택을 바꾸지 않는다. GPU·모델·학습·TinyDataset·외부 취득·타 세션 자료·삭제·Git 변경은 이 진단에 없다. 영향 정본은 WIP의 질문8/진행7과 진단 보고서이며 실험 기준표/METHODS/COMPASS의 조건 변경은 없다.
