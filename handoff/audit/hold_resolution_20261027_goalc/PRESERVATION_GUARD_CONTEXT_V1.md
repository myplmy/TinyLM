# 실제 값과 빈 예제 포장의 보존 구분

첨부 목표가 허가한 CPU 정제 구현·검사 범위의 새 파일만 만든다. 실행 중 v20의46생산파일과 원문·기존 캐시는 수정하지 않는다. 대상은 원문에 실제 값이 없는 `U+1B001()` 같은 빈 예제 포장과, 원문/본문/검토가 정확히 고정된6773의 검색 UI 한 쌍이다.

| 안 | 내용 | 장점 | 한계 | 영향도 | 비용 |
|---|---|---|---|---|---|
| A | 빈 예제 포장도 실제 글리프처럼 보호 | 이전 검사 그대로 | 없는 글리프를 복원하거나 빈 포장을 유지해야 함 | 낮음 | 불필요한 수작업 |
| B | 실제 글리프 예제는 모두 유지하고, 빈 포장만 코드포인트 값 보존을 추가 확인; Search는 정확 한 쌍만 연결 | 실제 값 소실을 막으면서 비본문 분리 가능 | 코드포인트나 글리프를 지우면 계속 거부 | 새 보존/검토 모듈 | 중간, 정반례·정확SHA 필요 |
| C | Unicode/backtick 검사를 생략 | 구현 간단 | 실제 코드·문자 정보 소실 검출 불가 | 광범위 | 낮음 |

선택 B. 문자 모양이나 Unicode 버전을 추정해 새 글리프를 넣지 않는다. 48585의 기존 guard 차이는 `U+1B001()`/`U+1B000()` 두 빈 포장이며 두 코드포인트 값과 채워진 실제 명칭/문자는 본문에 남는다. 6773의 삭제 차이는 프로그램 예제가 아닌 검색 버튼 `Search` 한 개이며 해당 exact source/body 이외에 적용하지 않는다.

| 축/경로 | 영향과 권한/검사 |
|---|---|
| 새 preservation_v1/literal_guard_v3 및 관련 시험 | 첨부 목표 CPU 구현/검사 허가; 이전 helper/10개 exact 근거 재사용, 새 한 쌍만 추가 |
| 데이터·스키마 | 원문 SHA/구간·토크나이저/분할 불변, 새 원문/본문 생성 없음 |
| 회귀 | 실제 글리프 소실·코드포인트 소실·한쪽만 맞는 exact ID/다른본문·실제 Search 코드 거부 |
| 정본·부채 | 실제 최종 cache에 반영할 때만 source pin/결과 연쇄; 미검산 상태를 완료로 바꾸지 않음 |
| GPU/모델·소유권 | CPU만, 보호 TinyDataset/타 세션 전용자료/프로세스 접근0 |
| 비교·증거 | 원래 source/body 쌍과 정확 리뷰/수치 조건만; 정적/의미/캐시/학습을 구분 |

zero-HOLD 계약과 전량 검산을 유지한다. 새로운 source/body가 이 검사로 통과했다는 사실만으로 의미 보존 전체나 모델 품질을 승인하지 않는다.
