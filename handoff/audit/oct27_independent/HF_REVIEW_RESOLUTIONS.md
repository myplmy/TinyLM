# 외부 HF 자원 계측의 실행 전 검토 회수

사용자96/97의 미완 작업·tmp 조율 범위다. 반 담당은 허용 텍스트만 읽었고 코드/시험/모델/GPU를 실행하거나 파일을 쓰지 않았다. 총괄이 구현·검증한다. 아래 조치는 외부 모델 실행 **이전**에 반영했으며 이전 v1~v5 프로필은 미실행 준비본으로 보존한다.

| 검토 지적 | 총괄 조치 | 증거와 한계 |
|---|---|---|
| 기본 EOS가 되살아나 고정길이 생성이 끝날 수 있음 | 모델 원본 config를 바꾸지 않고 최종 generate kwargs로 EOS 비활성화를 명시 | 첫 출력이 EOS가 되는 실제 tiny-HF에서 강제8토큰과 자연1토큰 종료를 함께 검사. 생성 옵션도 원형에 저장 |
| 같은 Gemma 구현 SHA 때문에 완료 보고서 연결을 혼동할 수 있음 | 모델 ID·초기/최종 core·전체 자산·모델 소스를 완료 보고서와 함께 검증 | 잘못 연결한 모델/최종core/자산의 거부 회귀. 현재4개 실제 완료 메타데이터도 통과 |
| 생성/감시/로더 정리의 이중 실패가 최초 오류를 대체할 수 있음 | 생성 오류를 정리 전 구조화하고 감시·로더 종료·보고서 저장 오류를 별도 기록 | 이중 실패3가지 CPU 회귀. 기존 엄격 로더는 변경하지 않음 |
| generation 설정/처리/중단 소스와 Falcon 종료 SHA 누락 | 7개 핵심 라이브러리 소스와 모델 구현의 시작/종료 SHA를 봉인 | 전 의존성/드라이버 전체의 재현 증명은 아님. 정확한 package/경로·SHA를 기록 |
| CPU행의 GPU 피크 구간이 혼합됨 | 엄격 CUDA 검증 피크, CPU 이동 후 생성 시작 allocator, 생성 구간 피크를 분리 | CPU행의 초기CUDA 사용 caveat는 유지. 예약량을 실제 생성 요구량이나 연속 물리peak로 해석하지 않음 |

초기 CPU cache 시험은 `DynamicLayer.update`가 K/V를 그대로 alias로 유지한다고 잘못 가정해1/11 실패했다. 실제 구현이 각각 복사함을 확인해 두 저장소를 먼저 검사하고 실제 alias를 따로 만든 경우의 중복 제거도 검증했다. 측정 코드를 느슨하게 바꾼 것이 아니다.

HF 경로 정적검사는 최초에 두 새 파일의 선행 `import tinylm` 누락을 검출했다. 이를 추가한 뒤 해당 검사0이다. 초기 직접 check-only0은 모델 실행을 뜻하지 않으며 v2/v3을 실행했다고 기록하지 않는다. 반 검토 반영 후 CPU17시험0·0.112초다. 혼합 GenerationConfig/kwargs의 설치판 경고를 피하려고 최종 호출은 모든 필요한 옵션을 명시 kwargs로만 전달한다.

전체 명시범위 정적 v1은69PASS/1ERROR/6NOT_RUN이었다. `check_attrs`는 `config`라는 변수 이름을 TMTConfig로 간주해 실제 HF GenerationConfig의 필드3개를 오탐했다. 실제 타입을 드러내는 `generation_options` 이름으로 고쳤고 공용 검사기는 변경하지 않았다. 최종 재검산은 별도 v2 감사로 회수한다. 임시 입력·해시 수집기는 현재 세션150개 명시 경로만 읽고 원래 판정함수를 사용한다. 다른 세션 전용 텍스트를 전역 재귀 수집하거나 검사 실패를 추가 NOT_RUN으로 숨기지 않는다.

정제 총괄이 자기 새 `--roster`의 등급표 행을 직접 등록한 뒤 공용 플래그 검사는 실제0이다. 상대 코드/원장·데이터를 이쪽에서 수정하지 않았다. source/protocol이 바뀌었으므로 최종 실행은 새 v6 봉인으로만 허용한다. 이 문서 작성시 외부 모델 자원 실행은0이고 추가300M 금지는 유지한다.

## 최초 실제 실행과 추가 회복

위 v6 준비 후 Stage11cW의 실제 부모18816은9였다. 8자식 모두 같은 늦은 HF초기화 오류였고 순전파0이다. 과거 CPU17과정적70 통과로이실제초기화까지검증됐다는해석은철회한다. 라이브러리 소스를 해시하려고 identity가 HF를 import한 것이 기존 cache policy의 최초 호출보다 빨랐다. 단순 `import tinylm` 확인과 mock/이미HF가import된시험만으로는 새 cold 프로세스의 조합 순서를 검증하지 못했다.

실패 원형은 `hf_v1_actual_closure.json`과 당시 source archive에 보존했다. 회복은 package 배포 메타데이터로 소스 파일만 읽고, 실제 entry에서 기존 cache policy를 먼저 적용하는 방법이다. 기존 cache 보호를 제거하지 않았다. 새 프로세스 identity→기존 policy를 실제 호출하는18번째 회귀가0이고, 실제 Gemma270 runtime probe가 성공해야8행을 여는 선결도 추가했다. 회복 source/profile·새 namespace는 별개이며 이전 v6 실행을 성공으로 바꾸지 않는다.
