## 1. 가장 중요한 세 가지

### 1.1 ★★★**LUT 은 g=5 여야 한다 — 바이트가 곧 인덱스다**

| | T-MAC 통례 g=4 | ★**우리 g=5** |
|---|---|---|
| 3^g | 81 | **243** < 256 |
| ★**저장 ↔ 인덱스** | 🚫**어긋난다**(5트릿/바이트 vs 4트릿/그룹) | ★★**같다** |
| 언팩 | **필요** | ★**없다** |
| bpw | 1.600 또는 2.000 | ★**1.600** |

★**int8 경로의 `_wq_from_i8()`(층당 2.1~2.2ms)에 해당하는 단계가 아예 없다.**

⚠️★**대가는 per-row α 다. 숨기지 않는다.** `768 = 2^8×3` 에 **5의 배수인 약수가 없어서**
`micro_group 128` 이 **원리적으로 불가능**하다. 대가는 **결과 028 이 이미 쟀다**
(**+0.0038~0.0068 bpb**, 분해능 0.008 미만). ★`_fused_int8_linear` 도 **같은 제약**을 갖는다.

### 1.2 ★★**P067 의 진짜 질문 — "KD 가 무익한가, 우리 교사가 무능한가"**

결과 038: 부모초기화 **+0.1386** vs KD **−0.0032**(43배) → *"KD 는 값어치가 없다"*.
🚫★**그런데 그 교사는 우리 코퍼스로 우리 크기로 학습한 dense** 였다.
***"KD 가 무익하다"* 와 *"우리 교사가 가르칠 것이 없다"* 는 같은 숫자를 낸다.**

★**교사 후보 실사(2026-08-22)**:

| 폴더 | arch | 텍스트 전용 | L | hidden | vocab |
|---|---|---|---:|---:|---:|
| ★**`Qwen3-0.6B-Base`** | `Qwen3ForCausalLM` | ✅ | 28 | 1024 | ★**151,936** |
| `gemma-3-270m` | `Gemma3ForCausalLM` | ✅ | 18 | 640 | 262,144 |
| `gemma-3-1b-pt` | `Gemma3ForCausalLM` | ✅ | 26 | 1152 | 262,144 |
| `Qwen3.5-0.8B-Base` | `…ForConditionalGeneration` | 🚫 | 24 | 1024 | 248,320 |
| `gemma-4-E2B` | `…ForConditionalGeneration` | 🚫 | 35 | 1536 | 262,144 |

★**Qwen3-0.6B-Base 가 1순위** — 어휘가 151,936 으로 가장 작아 **우리 임베딩 증가가 1.7배 적다**.

### 1.3 ★★★**`uint16` 오버플로 — 이것을 못 잡았으면 P067 전체가 쓰레기였다**

`prepare.py` 는 토큰을 **`uint16`**(0~65,535)로 저장했다.
🚫**Qwen3 151,936 · Gemma3 262,144 는 둘 다 넘는다** → **id 가 조용히 wrap 되고,
손실은 정상으로 보이고, 모델은 쓰레기를 배운다.**

✅**조치**: `meta.json` 에 **`token_dtype`** 기록, 어휘 > 65,536 이면 **`uint32`**.
★**`loader.py` 도 `meta.json` 에서 읽는다** — dtype 을 두 곳에서 정하지 않는다(함정 18).

## 6. 커밋 메시지 제안

**제목**

```
LUT 배포 경로 구현과 외부 교사 배관, 그리고 두 건의 지시 곡해 정정
```

**본문**

```
LUT 을 참조 구현에서 배포 경로로 올렸다. 설계를 g=4 에서 g=5 로 바꿨다.
5트릿이 정확히 한 바이트(0~242 < 256)이므로 패킹된 바이트가 곧 LUT 인덱스가
되고, 언팩 단계가 아예 사라진다. int8 경로의 _wq_from_i8() 이 층당 2.1~2.2ms
였는데 그것에 해당하는 것이 없다. TLinear.to_lut() 과 forward 분기,
transformer.to_lut(), mem_breakdown() 의 LUT 상주 회계, mem_runtime --lut,
그리고 통합 경로가 실제로 도는지 보는 L6 게이트를 넣었다.

대가는 per-row alpha 다. 768 = 2^8 x 3 에는 5의 배수인 약수가 없으므로
micro_group 128 은 g=5 와 원리적으로 맞지 않는다. 그 대가는 결과 028 이
이미 쟀다: +0.0038~0.0068 bpb 로 실무 분해능 0.008 미만이다.
_fused_int8_linear 도 같은 제약을 갖는데, 우연이 아니라 행당 스케일이
하나여야 커널이 누산 뒤에 한 번만 곱할 수 있기 때문이다. 그래서 LUT 의
로짓 동등성 게이트는 int8 과 달리 0 이 아니고, mem_runtime 이 그 조건을
따로 인쇄한다.

속도는 여전히 재지 않는다. PyTorch gather 는 GEMM 보다 메모리 대역을 더
쓰므로 GPU 에서 cuBLAS 를 이길 수 없고, 그것은 구현이 나빠서가 아니다.
다만 이것을 미구현이라고 부르지 않는다. 우리 목적함수는 상주 메모리이고
그것은 이제 실측된다. 속도는 P014B 의 U1 이 소유한다.

외부 교사 배관을 넣었다. --tokenizer-hf 는 외부 HF 모델의 tokenizer.json
으로 코퍼스를 토큰화하고 캐시 디렉터리를 분리한다. --kd-teacher-hf 는 KD
교사를 외부 AutoModelForCausalLM 으로 바꾸고, 교사는 bf16 으로 돌되 로짓은
fp32 로 올려 넘긴다. bf16 log_softmax 는 꼬리를 뭉개서 KL 이 교사가 아니라
반올림을 재게 된다.

여기서 uint16 오버플로를 잡았다. prepare.py 는 토큰을 uint16 으로 저장하는데
Qwen3 은 151936, Gemma3 은 262144 이라 둘 다 65536 을 넘는다. 그대로 두면
토큰 id 가 조용히 wrap 되고 손실은 정상으로 보이고 모델은 쓰레기를 배운다.
meta.json 에 token_dtype 을 기록하고 어휘가 65536 을 넘으면 uint32 로 올린다.
loader.py 도 같은 meta.json 을 읽는다 - dtype 을 두 곳에서 정하지 않는다.

교사 후보를 실사했다. 사용자가 준비한 순수 텍스트 세 모델은 전부
ForCausalLM 이다. Qwen3-0.6B-Base 28층 1024 vocab 151936,
gemma-3-270m 18층 640 vocab 262144, gemma-3-1b-pt 26층 1152 vocab 262144.
Qwen3.5-0.8B 와 gemma-4-E2B 는 ForConditionalGeneration 으로 멀티모달이다.
텍스트 탑만 떼어내는 것은 원리적으로 가능하지만 순수 텍스트 후보가 이미
있으므로 하지 않는다. Qwen3-0.6B-Base 를 1순위로 쓴다 - 어휘가 가장 작아
우리 임베딩 증가가 1.7배 적다.

지시 곡해 두 건을 원장에 등재했다. D17 은 "확인해서 준비 착수" 지시에서
확인만 하고 끝낸 것이다. 두 동사가 있으면 마지막이 목적인데 수단만 했고,
더 나쁘게도 그 수단으로 낸 제안(교사 구조 차용)이 목적(P067)을 교락시키는

큐가 이름을 받는다. experiments.tsv 에 한 줄만 추가해도 id 가 전부 밀려서
```
