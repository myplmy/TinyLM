## 1. ★가장 중요한 것 여섯

### 1.1 브랜치와 산출물 경계

- 현재 브랜치는 `moonshot`이다.
- 계획은 `plan/`, 배치는 `moonshot_batch/`, PM provenance와 향후 결과는 `moonshot_result/`만 쓴다.
- 식별자는 `PM000`, 예약 구분자는 `__MOONSHOT__`, 필드 구분자는 `__`다.
- `test_plan/`, `test_result/`, `experiments.tsv`, 일반 queue에 PM000을 넣지 않았다.
- `main`과의 merge/rebase/cherry-pick/push를 하지 않았다. 성능이 입증돼도 사용자가 별도 main 작업에서 필요한 증거와 변경만 재검토해 이식한다.

### 1.2 선택한 moonshot과 주장 범위

첨부 검토의 후보 중 **pass-dependent Latin GQA**를 PM000으로 선택했다. 실제 레이어의 방문 회차
`t`에서 query group `g`가 보는 KV head를 `KV_t(g)=(g+t) mod H_kv`로 순환한다.

- 추가 학습/배포 가중치: 0 예상
- 추가 KV 엔트리와 저장 bytes/token: 0 예상
- runtime scratch/latency: `torch.roll` 때문에 증가할 수 있음
- 비교 팔: `fixed`, `latin`, seed 결정적 균형 `random`
- 이번 단계의 CE·한 seed 결과만으로 일반지능 향상을 주장하지 않음

### 1.3 구현 불변식

1. 기본값 `fixed`는 기존 경로이며 K/V roll을 호출하지 않는다.
2. `pass_id`는 KV owner가 아니라 **각 실제 레이어의 방문 번호**다.
3. K와 V에 같은 shift를 소비 직전에 비파괴 적용한다.
4. R1의 `latin/random` 첫 shift는 0이라 fixed와 정확 동일해야 한다.
5. non-fixed는 `n_q_heads > n_kv_heads > 1`, `repeat_mode=uniform`, `reuse_attn_on_dup=False`에서만 허용한다.
6. random 순열은 전역 RNG를 소비하지 않고 같은 seed에서 결정적이다.

### 1.4 실험 사전등록

- Stage0: 파라미터/state key/R1 동일성/cached-full/gradient 계약 진단
- Stage1: R2, 100M actual tokens, fixed/latin/random matched triad
- Stage1E: 세 checkpoint 전부 존재한 뒤 600M clean paired full-val
- Stage2: Stage1 안정성 확인 뒤 R3 완전 균형 matched triad
- Stage2E: Stage2 세 checkpoint 전부 존재한 뒤 paired full-val
- Stage3: 양성 신호 뒤 300M·최소 3 seeds. **아직 배치 없음**

### 1.5 검증 상태 — 정적 통과와 동적 미실행을 섞지 않는다

PM000 namespace, batch flag, batch name, lint, strict dry-run, smoke coverage, smoke field,
flag whitelist, import/call/attribute/사용처, tag-architecture, run registry 격리는 모두 통과했다.
전체 torch-free suite는 **30/32**다.

1. `check_heldout_defects`: 기존 `E-157(touching)`, `E-205(part_of)` D6 두 건. PM000은 데이터셋을 수정하지 않는다.
2. `check_links`: 로컬에 없는 gitignored `data_cache/*/meta.json` 5개와 `runs/registry.tsv` 1개. 가짜 파일·복사본·symlink를 만들지 않았다.

이 결과는 동적 smoke나 모델 correctness 증명이 아니다. `run_smoke_check.bat`와 Stage0은 사용자 실행 대기다.

### 1.6 PM provenance 격리

공통 trainer JSON은 기술적으로 `runs/logs/`에 생성되지만 `_pm000__` tag를 강제한다.
일반 `runs/registry.tsv`의 scan/backfill은 PM tag를 제외하고, 성공한 PM 학습은
`moonshot_result/registry.tsv`로만 기록한다. PM name/tag/outdir이 일치하지 않거나 JSON이 없으면
runlog가 PM provenance 기록을 거절한다.
