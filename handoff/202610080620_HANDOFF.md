### 2.1 분류는 누가 어떻게 하는가

현재 json 프로필/3턴 마지막 형식은 질문 생성기가 직접 answer 항목 하나를 요구한다. 이 생산자 코드가 단순 계약을 붙인다.
예를 들어 교사 ANSWER의 `2016년`은 코드가 `{"answer":"2016년"}`으로 만든다. 기존 JSONL/ChatML 래퍼는 그대로다.

사람의 이름/나이 목록을 배열로 바꾸거나 people/count 중첩 객체를 요구하면, 과제 생성기가 예상 구조·항목·자료형 계약을 붙인다.
교사는 그 JSON 구조 자체를 ANSWER에 쓰고 코드는 파싱·선언 구조·닫힌 단일 코드펜스만 검사한다.
배열을 `{"answer":"배열 문자열"}`로 바꾸면 요구 불일치이므로 하지 않는다.

원천/자유 생성 질문에 신뢰된 계약이 없으면 UNKNOWN이다. JSON이라는 단어·괄호 수·교사의 자기분류나 원천 meta로 유형을 추정하지 않는다.
원답을 보존하며 구조 PASS·단순 포장을 자동 부여하지 않는다. 검수된 원천 계약을 추가할 때도 생산자 코드의 명시 어댑터·회귀가 필요하다.
전체 JSON Schema가 아니라 명시 부분집합만 지원하고 미지원 구조는 조용히 허용하지 않는다. 정답성은 후행 자료 검토다.

앞 A(모든 본문 단순화)/B(교사형식 회복)/C(펜스만)를 그대로 혼합한 것이 아니라, 사용자가 확정한 ‘코드 소유 단순 계약과 교사 소유 복잡 계약의 분리’만 구현했다.
반복 설명에서 기존 바깥 포장이 이미 있다는 사실과 새 답본문 렌더링을 처음부터 구분하지 못한 점을 정정했다.
