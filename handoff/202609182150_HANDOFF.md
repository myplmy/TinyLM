## 1. 가장 중요한 것 셋

1. manual compact는 **통과한 것이 아니라 사용자 결정으로 검증 범위에서 제외**됐다. M3 사용자
   승인 범위는 예외 종결하지만 manual 경로는 `NOT_RUN`이고 M3 전체를 `ACTIVE_VERIFIED`로
   승격하지 않는다.
2. 17건 whitelist FAIL은 구현이 깨진 17개 기능이 아니라, 이미 파서에 있는 CLI가 정본
   `scripts/flag_whitelist.tsv`에 등급·근거 없이 남은 **registry 정합성 실패**다. 전수 검토 결과
   모두 실험 축이 아닌 지원되는 관리·진단 경로라 `ok`가 권장된다.
3. 앞선 “17개 whitelist 분류 승인” 요청은 불충분했다. 승인 대상·개별 플래그·등급안·승인 후
   무엇을 하고 무엇을 하지 않는지 먼저 제공했어야 한다. 또한 별도의 metadata 날짜 FAIL 5건이
   있어 whitelist만 고쳐도 전체 static gate가 열리지 않는다. 정보가 없어서가 아니라 설명·전체
   gate 대조 단계를 생략한 절차 오류였다.

## 2. 무엇을 했나

- 사용자 결정에 따라 manual compact를 운영 선결에서 제거했다. 원래 설계와 미실행 사실은 보존하고,
  제안서·COMPASS·Codex 장기 문서에는 “사용자 검증 제외·manual `NOT_RUN`·전체 승격 금지”를 함께
  기록했다.
- whitelist 검사기는 모든 `argparse.add_argument("--...")`를 파서 정본에서 수집하고 TSV의
  `ok/exp/dead/rejected` 등급과 양방향 대조한다. 현재 파서 352개, 표 335행이라 정확히 17개가
  누락됐다. 이는 실행 결과 FAIL이 아니라 정적 registry FAIL이다.
- 17개의 코드 몸통과 안전장치를 읽었다. WIP 관리 5개, 문서 metadata 7개, handoff 링크 교정
  1개, SFT 감사 3개, POSIX smoke source 선택 1개다. 전부 구현된 도구 옵션이므로 `ok`가 맞고,
  `exp`는 모델 실험 축이 아니어서 부적합하며 `dead/rejected`로 볼 근거도 없다.
- `ok` 등급은 실행 승인이나 보호 데이터 권한이 아니다. 예컨대 `--root`를 `ok`로 등록해도
  `datasets/TinyDataset/**` 접근은 별도 승인이 필요하고, `--fix-handoff-renames`도 명시적 링크
  교정 승인 없이 실행할 수 없다.
- 이번 요청은 설명이므로 `scripts/flag_whitelist.tsv`는 수정하지 않았다. 사용자가 아래 정확한
  분류안을 승인하면 17행만 좁게 추가하고 checker와 비보호 unit을 재검사한다. `--sync`로 근거 없는
  자동 `ok`를 덧붙이지 않는다.
- 최종 검사에서 `scripts/check_doc_metadata.py --scope codex`가 선행 날짜 부채 5건으로 FAIL했다.
  대상은 Codex 00 한·영, 02, 03, 08이며 이번 사용자 범위의 17개와 별개다. B2 날짜 정정은 기존
  승인 전 금지 범위이므로 수정하지 않았다.
