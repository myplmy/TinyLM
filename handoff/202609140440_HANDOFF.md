## 1. 가장 중요한 것 셋

1. **v3.0은 독립 seed2 판정에서 실패했다.** D9 19.0%, 정보 0 65.2%, 난이도 `mid > hard > easy`라 승격할 수 없다.
2. **v2.9 대비 악화량을 그대로 판본 효과로 읽으면 안 된다.** v2.9는 `*_muon15`, v3.0은 `*_s2` 패널이다. 원시 D9는 30.2%→19.0%지만 같은 seed2로 v2.9를 재기 전에는 재작성 인과가 미확정이다.
3. **다음 census는 로그를 자동 보존한다.** JSON은 핵심 벡터를 보존하지만 difficulty/relation 출력·argv·traceback·exit code를 담지 않는다. 스크립트는 이제 콘솔과 같은 UTF-8 로그를 결과 옆에 별도 생성한다.

## 2. 무엇을 했나

### 2.1 v3.0 결과와 v2.9 원시 비교

- v3.0 JSON은 6모델, `ids/per_item_rate` 4,500개, 모델별 `per_ok/per_pick` 4,500개,
  모델쌍 15개와 family CI 누락 0으로 완결됐다.
- v2.9 Muon 패널 대비 원시 변화는 B1 +309(+6.9pp), B2 +416(+9.2pp), 일한 문항
  -725(-16.1pp), D9 -503(-11.2pp), 정보 0 +725(+16.1pp), 정보 합 -622.0 bit(-32.8%)다.
- v3.0 선택 위치는 모델별 24.1~26.1%로 균형이다. 조건 D9 2.1→33.6%와 부분전체
  11.5→17.2%는 후보 개선이지만, 패널이 달라 통제 개선으로 확정하지 않았다.
- 대조·상하위·반의·시간순서·인과·목적수단의 원시 D9는 각각 -15.5, -31.6, -18.0,
  -3.9, -27.6, -29.9pp다. 독립 패널 자체에서 목적수단 7.1%, 인과 9.9%이므로 관계별
  회귀 방지 장치가 필요하다.

### 2.2 이전 수정 지시가 품질을 보장하지 못한 이유

- 독립 seed2 패널을 최종 검증에 쓴 방향은 맞았지만, 같은 패널의 v2.9 baseline을 함께
  요구하지 않아 판본과 패널 효과가 섞였다.
- v3.0은 4,500개를 전면 재작성했다. v2.9에서 이미 일하던 문항 보존, 10% canary,
  full 전 rollback 게이트가 없었다.
- 의미형·위치·길이 같은 정적 proxy를 맞춰도 실제 모델 변별력과 난이도는 자동으로 맞지 않는다.
  독립 파일럿의 정확한 패널·로그·전면 생성 전 중단 조건도 제출 계약으로 닫지 못했다.
- 이전 요청의 우선 세 관계 최소 1,800개는 균형 총수 1,689개와 모순이었다. 이 모순은
  사후 폐기됐지만, 생성 전에 사양 가능성을 검사하는 단계가 없었다.
- 이 때문에 데이터셋 팀만의 단순 작성 오류로 인과를 확정하지 않고, AI가 만든 생성·검증
  절차의 통제군·canary·보존·반복 상한 누락을 주원인으로 기록했다.

### 2.3 품질저하 방지 제안

### 2.4 JSON 단독 판독과 자동 로그

JSON만으로 B1/B2/D9/bit, 정오·선택 벡터, 모델쌍 CI는 다시 계산할 수 있다. 그러나 현 JSON은
relation·difficulty 라벨, 실제 argv 전체 조건, 시작·종료시각, process exit code, JSON 저장 전
traceback을 보존하지 않는다. 따라서 JSON 단독으로 콘솔 판정과 실패 원인을 완전 감사할 수 없다.

`scripts/census_heldout_discrimination.py`는 이제 실제 run이면 `--out`의 같은 폴더에
`YYYYMMDDhhmmss_<out-stem>.log`를 자동 생성한다. stdout/stderr는 콘솔에도 유지하고,
같은 초의 기존 파일은 `_2` suffix로 보존한다. `--help`는 실행이 아니므로 로그를 만들지 않는다.
이번 기존 v3.0은 완결 JSON과 콘솔 사본이 있어 새 로그만 얻기 위한 GPU 재실행은 권하지 않는다.
