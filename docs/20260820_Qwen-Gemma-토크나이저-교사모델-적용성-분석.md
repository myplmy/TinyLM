## 0. 결론 세 줄

> ★★**① 원안의 구조 가정은 코드와 일치한다.** `emb(V×E) → emb_up(E→d)`, 그리고 **출력도 같은
> `emb`·`emb_up` 을 재사용**한다 — **완전 tied 이고 `r_in = r_out = emb_rank` 다.** 원안 §12·§13 은 옳다.
>
> 🚫★★**② 그런데 1차 매트릭스는 지금 돌릴 수 없다. 하드 블로커가 셋이다** —
> **uint16 토큰 저장(어휘 65,535 초과 불가)**, **KD 손실 VRAM 이 어휘에 선형(25~44 GiB 추정)**,
> **외부 HF 모델을 교사로 넣는 경로가 없다**(`load_dense` 는 우리 체크포인트만 받는다).
>
> ★★**③ 그러나 이 제안은 우리 최대 난제 하나를 정면으로 건드린다** — **KD 가 해로웠던 이유가
> "교사가 학생보다 나빴기 때문"(H1, 결과 042 §12)** 인데, **Qwen/Gemma 교사는 정확히 그 조건을 바꾼다.**
> **기각이 아니라 "선결 3건 뒤"** 다.
>
> ⚠️★**단 메모리 목표와는 정면 충돌한다** — 어휘가 4.6~8배 커지면 **임베딩만으로 L2+L3 예산(40MB)을
> 통째로 먹는다**(§3). **원안이 §2 에서 제외한 "임베딩 양자화" 가 사실은 선결 조건**이다.

## 2. 🚫하드 블로커 3건 — **이것들 없이는 어느 조건도 못 돌린다**

### 2.1 ★★블로커 A — **`uint16` 이 어휘를 65,535 로 막는다. 그리고 조용히 깨진다**

```
prepare.py:205   arr = np.concatenate(out)[:n_tokens].astype(np.uint16)
prepare.py:232   buf.append(np.array(ids + [eos], dtype=np.uint16))
loader.py:12     np.memmap(..., dtype=np.uint16, mode="r")
```

`numpy` 의 `astype(np.uint16)` 은 **넘치면 오류를 내지 않고 모듈로 래핑**한다.
Qwen 151,936 이면 **id 65,536 → 0**, **id 151,935 → 20,863** 이 된다.
→ ★**학습이 정상적으로 돌고, 손실도 그럴듯하게 내려가고, 결과는 쓰레기다.**

> ★**이건 우리가 이름을 붙여 둔 실패 유형이다** — 함정 30(*"스필은 조용하다"*)·
> 함정 37(*"필드가 기록된다 ≠ 그 경로가 실행된다"*)과 같은 계열.
> **가장 비싼 종류의 버그**다.

**필요한 변경**: `uint16 → uint32` (**9곳**: `loader.py` 1 · `prepare.py` 3 · 진단 스크립트 5).
**대가**: `data_cache/` 가 **2배**(600M 풀 = 1.2 GB → 2.4 GB). 학습 속도 영향은 거의 없다(디스크 read 는 병목이 아니다).
**+ 게이트**: `prepare()` 에 `assert ids.max() < 2**32` 와 **`vocab_size` 대조 단언**을 넣는다.

### 2.2 ★★블로커 B — **KD 손실 VRAM 이 어휘에 선형이다**

결과 038 · `docs/methods/09_training_memory.md` 실측:

> ★**학습 VRAM 의 최대 항목은 모델이 아니라 "어휘 전체 위의 KD 손실 계산"** 이다 —
> **+5.48 GiB alloc**, 그중 교사 파라미터는 945 MB 뿐.

그 5.48 GiB 는 `(M, V) = (8192, 32768)` 짜리 텐서 여러 벌이다. **`V` 에 비례**한다.

| 어휘 | 배수 | ⚙**KD 손실 VRAM 추정** | 16 GB 카드 |
|---:|---:|---:|---|
| 32,768 (현재) | 1.0 | **5.48 GiB**(실측) | 12.47 GB 로 성립 |
| 151,936 (Qwen 계열) | **4.64×** | ⚙**약 25.4 GiB** | 🚫**불가** |
| 262,144 (Gemma 계열) | **8.00×** | ⚙**약 43.8 GiB** | 🚫**불가** |

⚙**선형 외삽이다. 실측이 아니다** — 함정 1 규약에 따라 표시한다.

**해법 후보 셋**:

| # | 방법 | 우리 자산 | 비고 |
|---|---|---|---|
| 1 | ★**KD 청크**(P053) | ✅**이미 구현·측정됨 — 3.06 GiB 무상**(결과 048) | ★**KD 를 뺀다고 폐기하려던 것인데 여기서 되살아난다** |
| 2 | ★★**top-k KD** | 🚫 미구현 | 교사 상위 k(예: 64) 로짓 + 나머지 합. **V→65 로 줄어 근본 해법** |
| 3 | `micro_bs` 축소 | ✅ | ⚠️**M=8192 무릎을 깬다**(결과 007) — 속도 −8.7% 이상 |

### 2.3 ★블로커 C — **외부 HF 모델을 교사로 넣는 경로가 없다**

```python
trainer.py:233   teacher, _ = load_dense(kd if isinstance(kd, str) else CKPT / "dense.pt", device)
init_utils.py:76 def load_dense(path, device):
                     st = torch.load(path); cfg = TMTConfig(**st["cfg"])
                     m = TiedMLPTransformer(cfg) ...
```

★**교사는 `TMTConfig` 로 복원되는 우리 모델이어야 한다.** `AutoModelForCausalLM` 을 받을 자리가 없다.

**필요한 변경**: `--kd-teacher-hf <hf_id>` 경로 신설.
`teacher.forward(x) → logits (B,T,V)` 계약만 맞으면 나머지 코드는 그대로 쓸 수 있다(`trainer.py:531` 의 `tlog = teacher(x)`).
**단** HF 모델은 `(B,T)` 를 받아 `CausalLMOutput` 을 낸다 → **얇은 어댑터 1개**로 해결된다.
⚠️★**교사 VRAM 을 별도로 센다** — Qwen 0.8B bf16 = **약 1.6 GB 가중치** + 활성. 우리 교사(945 MB)보다 크다.

| 조건 | 임베딩 fp32 | 40 MB 예산 중 | 트랜스포머에 남는 것 |
|---|---:|---:|---:|

> ★★★**결론: 큰 어휘 + fp32 임베딩은 L2+L3 목표와 양립 불가능하다.**
> 그리고 **현재 어휘로도 이미 84% 다** — 큰 어휘가 문제를 만든 것이 아니라 **이미 있던 문제를 4.6배로 키운다.**

⚠️★**원안 §2 가 "임베딩 INT8"·"임베딩 ternary" 를 *제외* 목록에 두었는데,
우리 실측 기준으로는 그것이 *선결 조건* 이다.** 이 한 줄이 이 검토의 핵심 수정 제안이다.

## 4. ★★KD 를 다시 켤 이유 — **이 제안의 가장 강한 부분**

### 4.1 우리는 방금 KD 를 기각했다

결과 042 §12(2026-08-20): **α 를 0 → 0.7 로 올릴수록 품질이 단조롭게 나빠진다.**
`mC_initonly`(무KD) 3.6776 이 최소. **채택선을 아무도 못 넘었다.**

### 4.2 ★그런데 기각의 근거가 정확히 이 제안이 바꾸는 것이다

| 가설 | 상태 |
|---|---|
| H2 구현 결함 | ✅ **배제됨**(결과 042 §11) |
| ★**H1 교사가 나쁘다** | ✅★**지지됨** — 교사 full-val **3.8080** vs 학생 **3.6776**. **교사가 학생보다 +0.1304 나쁘다** |
| H3 기법 부적합 | 확정(우리 조건에서) |

> ★★**우리가 확정한 것은 "KD 가 나쁘다" 가 아니라 "학생보다 나쁜 교사로 KD 하면 나쁘다" 다.**
> Qwen 0.8B 는 우리 100M 보다 **파라미터가 8배**이고 **학습 토큰이 수백 배**다.
> **H1 을 정면으로 뒤집는 유일한 실험**이 이것이다.

⚠️★**단 반증 가능성도 크다** — 결과 006 은 **100M 예산에서만** KD 가 이겼다.
**300M 에서 이기려면 교사 품질이 아니라 예산이 문제일 수도 있다.** 그건 이 실험이 가른다.

### 4.3 ★교사 tokenizer 를 학생이 그대로 쓴다는 원안의 선택은 옳다

로짓 KD 는 **어휘 좌표가 같아야** 성립한다. 원안 §10 이 그걸 정확히 짚었다.
→ **따라서 어휘를 우리 32,768 로 유지하면서 Qwen 을 교사로 쓰는 것은 (로짓 KD 로는) 불가능**하다.
**어휘 교체와 교사 도입은 묶여 있다.** 원안이 둘을 함께 제안한 것은 구조적으로 옳다.

⏸**대안**: **hidden-state KD**(어휘 무관) 또는 **cross-tokenizer sequence KD**.
원안이 §10 에서 범위 밖으로 뺐고 **그 판단에 동의**한다 — 축을 하나만 연다.

## 5. ★untied 구현 — **원안 §12 의 핵심 비교에는 새 파라미터가 필요하다**

원안은 `Q64-T`(r_in=64, r_out=64, tied) vs `Q64/128-U`(r_in=64, r_out=128, untied) 를 핵심 비교로 둔다.
**우리 코드에는 `r_out` 이라는 개념 자체가 없다**(§1-11).

**필요한 구현**(`transformer.py`, 약 20줄):

```
현재:  logits = F.linear(F.linear(x, emb_up.weight.t()), emb.weight)      # d→E→V, 전부 공유
추가:  emb_out  = nn.Embedding(V, r_out)      # 신규 V×r_out
       emb_down = nn.Linear(d, r_out, ...)    # 신규 d×r_out
       logits   = F.linear(emb_down(x), emb_out.weight)
```

⚙**파라미터 대가**(V=151,936, r_out=128): `emb_out` **19.45M** + `emb_down` 0.098M
= ⚙**+78.2 MB fp32 상주**. ★**"untied 가 이겼다" 를 읽을 때 이 78 MB 를 함께 읽어야 한다.**

> ★**판정 규칙을 미리 못 박는다**: `Q64/128-U` 가 `Q64-T` 를 이겨도 **상주 −(78.2 MB) 를 상쇄할
> 만큼 이기지 않으면 채택하지 않는다.** 우리 레버 가격표(결과 032·044 §9.2)로 환산하면
> 78.2 MB 는 **어텐션 타잉으로는 0.0083 nats, MLP 타잉으로는 0.0342 nats** 어치다.
> ⚙**즉 채택선 = "0.008 nats 이상 이겨야 한다"**.

## 7. ⚠️예산 정의 충돌 — **원안 §18 이 옳게 걱정했다**

우리 규약: **기준 학습토큰 = steps × micro_bs × accum × seq**. **토큰 수가 예산**이다.
그런데 토크나이저가 바뀌면 **같은 토큰 수 = 다른 분량의 원문**이다.

⚙**현재 우리 값**: `p6d` val_loss 3.7045 / bpb 1.2216 → **bytes/token ≈ 4.375**
(한국어 UTF-8 3바이트/자 기준 **약 1.46자/토큰**).

Qwen·Gemma 는 다국어 대규모 코퍼스로 학습된 훨씬 큰 어휘라 **한국어 압축률이 더 좋을 가능성이 높다**
(⚙**추정. 0-b 가 잰다**). 그러면 **같은 300M 토큰이 더 많은 원문**을 보게 된다.

> ★★**대응: 두 예산을 모두 기록하고, 판정은 `common_bpb.py` 로 한다.**
> `scripts/common_bpb.py` 는 **토크나이저 무관 공통 원문 bpb** 를 계산하는 **유일한 유효 경로**다
> (CLAUDE.md 도구 목록). **val_loss 로 T0 와 Q* 를 비교하면 무효다**(함정 2).
> ⚠️**val 셋도 다시 만들어진다** — 결과 011 이 *"val 셋이 다르면 비교 불가"* 를 확정했다.
