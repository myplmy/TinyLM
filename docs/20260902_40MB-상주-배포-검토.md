# 2026-09-02 — TinyLM 40MB 상주 배포 검토

- **목적**: 현재 TinyLM 후보 중 일부가 추론 실행 시 40MB 이내 메모리에 상주할 수 있는지, 현재 구현과 실험 결과를 기준으로 검토한다.
- **범위**: 모델·KV 캐시·활성값·임시 버퍼·토크나이저·구동기를 포함한 배포 가능성, 배포 포맷과 구동기 선택, 별도 컴파일 및 애플리케이션 내장 방식을 다룬다.
- **조사 방식**: 저장소 문서와 코드를 정적으로 확인하고 공식 논문·공식 프로젝트 문서를 대조했다. 이 검토를 위해 모델 실행, 빌드, 성능 측정 또는 신규 실험은 수행하지 않았다.
- **핵심 제한**: 저장소의 19.6~38.5MiB 수치는 실제 프로세스 peak resident memory 측정값이 아니라, 특정 양자화 조건의 영구 텐서 합계와 공식으로 계산한 KV 캐시의 합이다.

---

## 1. 결론

판정은 `40MB`가 무엇을 의미하는지에 따라 달라진다.

| 판정 대상 | 결론 | 근거 |
|---|---|---|
| 현재 Python/PyTorch 프로세스 전체 | **불가능** | 모델 로드 전 Python+PyTorch 프로세스가 이미 약 386~388MB RSS다. |
| 배포용 모델 파일 또는 영구 모델 텐서만 | **여러 후보가 가능** | 1.600bpw LUT, int8 임베딩을 적용한 후보의 영구 텐서가 16.6~28.0MiB인 구간에 있다. |
| 영구 텐서 + bf16 KV, batch 1, context 1024 | **여러 후보가 계산상 가능** | P079에서 19.6~38.5MiB 후보가 확인됐다. |
| 현재 PyTorch 경로의 순간 최대 메모리 | **40MB 초과** | 출력 임베딩 복원, LUT gather, attention, PyTorch allocator와 런타임 메모리가 회계에서 빠져 있다. |
| 별도 네이티브 C/C++ 구동기에서 전체 40MiB | **소형 후보는 조건부로 가능** | 영구 사용량이 약 20~27MiB인 후보는 구동기·토크나이저·scratch에 13~20MiB를 남긴다. 단 아직 실측되지 않았다. |
| `d12_cla2_r20` 전체 40MiB | **가능성이 있으나 빠듯함** | 영구 텐서+KV가 30.7MiB여서 나머지 전체를 약 9.3MiB 안에 넣어야 한다. |
| `d16_cla2_r20` 전체 40MB/40MiB | **배포 후보로는 부적합** | 38.5MiB로 안전 여유가 1.5MiB뿐이며, 40MB를 십진 단위로 해석하면 이미 초과한다. |

따라서 다음과 같이 정리한다.

> **현재 코드 그대로 전체 프로세스를 40MB 안에 넣는 것은 불가능하다.**  
> **오프라인 전용 변환기와 작은 네이티브 구동기를 구현하면 일부 후보는 40MiB 안에 들어갈 현실적 가능성이 있다.**  
> **품질과 메모리의 절충 후보는 `d12_cla2_r20`, 확실한 메모리 달성을 위한 후보는 영구 텐서+KV 27MiB 이하 군이다.**  
> **아직 네이티브 배포물과 end-to-end peak 측정이 없으므로 달성이 입증된 상태는 아니다.**

## 2. 먼저 고정해야 하는 단위와 포함 범위

### 2.1 40MB와 40MiB는 다르다

| 표기 | 바이트 | 다른 단위로 환산 |
|---|---:|---:|
| 40MB | 40,000,000 B | 약 38.147MiB |
| 40MiB | 41,943,040 B | 약 41.943MB |

저장소의 P079는 32MiB·40MiB 예산을 사용한다. 사용자가 말한 40MB를 문자 그대로 40,000,000바이트로 적용하면 `d16_cla2_r20`의 38.5MiB는 약 40.37MB이므로 영구 텐서+KV만으로도 실패한다.

향후 합격 기준은 다음 중 하나로 명시해야 한다.

1. **엄격한 제품 기준**: peak resident memory `<= 40,000,000 bytes`
2. **현재 연구 문서 연속성 기준**: peak resident memory `<= 40.0MiB`

두 값을 함께 보고하되, 어느 하나를 사후에 바꾸어 합격시키면 안 된다.

### 2.2 포함해야 하는 메모리

40MB “상주 실행”은 최소한 다음을 모두 포함하는 것으로 정의하는 것이 안전하다.

- 접근되어 실제 RAM에 들어온 packed model page
- 모델 메타데이터와 실행 스케줄
- KV 캐시
- RoPE 또는 위치 인코딩 버퍼
- 활성값과 attention·LUT·출력 head scratch
- 토크나이저와 vocabulary 자료구조
- 스레드 stack, allocator와 네이티브 구동기 heap
- 정적/동적 라이브러리의 private page

`mmap`은 로딩 시 복사를 피할 수 있지만, 접근된 file-backed page가 RAM을 사용하지 않는다는 뜻은 아니다. 엄격한 상주 기준에서는 실제로 접근된 모델 페이지도 포함한다.

### 3.1 품질과 메모리 해석

- `d16_cla2_r20`은 `d16_dense`보다 품질과 회계 메모리 모두 좋지만, **40MiB 내부에서 실제로 구동할 여유가 있다는 뜻은 아니다.**
- `d12_cla2_r20`은 30.7MiB에서 full-val 3.6054를 얻어 현재 품질 중심의 40MiB 후보로 가장 합리적이다.
- 전체 상주 달성의 신뢰도를 우선하면 24.3~27.7MiB 이하 후보가 적합하다.
- `d8_g2`는 가장 큰 메모리 여유를 주지만 품질이 낮다. 제품이 요구하는 최소 품질을 별도로 통과해야 한다.
- P079의 `d12_cla2_r20`, `d16_cla2_r20` 등 다수 팔은 단일 seed이므로 품질 순위의 재현성이 아직 확정되지 않았다.

### 3.2 컨텍스트 증가 영향

KV 캐시는 컨텍스트 길이에 거의 선형으로 증가한다. 다른 조건이 동일하다고 단순 환산하면 다음과 같다.

| 후보 | 1024 | 2048 단순 환산 | 해석 |
|---|---:|---:|---|
| `mC_cla2_ag4` | 24.3MiB | 약 31.8MiB | 2048도 조건부 가능 |
| `mC_initonly_nc` | 27.3MiB | 약 34.8MiB | 2048은 매우 빠듯함 |
| `d12_cla2_r20` | 30.7MiB | 약 38.2MiB | 2048 전체 40MB는 사실상 불가능 |
| `d16_cla2_r20` | 38.5MiB | 약 49.0MiB | 실패 |

따라서 40MB 배포 프로필은 최소한 `batch=1`, `context<=1024`, `bf16 KV`를 고정해야 한다. 더 긴 컨텍스트가 필요하면 KV 양자화·sliding window·KV eviction 같은 별도 설계가 필요하며, 현재 품질 동등성이 검증된 것으로 간주하면 안 된다.

## 4. 현재 코드가 40MB 전체 상주를 달성하지 못하는 이유

### 4.1 Python/PyTorch 런타임 자체가 예산을 초과한다

현재 추론은 [`tinylm/infer/generate.py`](../tinylm/infer/generate.py)에서 `torch.load()`로 `.pt` 체크포인트를 읽고 PyTorch 모델을 구성한다. P034C의 분리 프로세스 조사에서 모델을 로드하기 전 Python+PyTorch RSS가 약 386.7~388.1MB였다. 따라서 현재 경로는 모델 크기와 무관하게 전체 40MB를 달성할 수 없다.

근거: [P034C RSS 결과](../test_result/061_20260830_P034C-RSS로는-MiB급-예산을-검증할-수-없다.md#92-rss-축을-닫는다), [`scripts/mem_runtime.py`](../scripts/mem_runtime.py).

P034C가 “RSS는 MiB급 KV 차이를 검증하는 계측기로 부적합하다”고 결론 낸 것과, Python/PyTorch 바닥이 이미 40MB를 넘는다는 사실은 구분해야 한다. 전자는 작은 증분의 신뢰성 문제이고, 후자는 현재 전체 프로세스가 40MB가 될 수 없다는 명백한 하한이다.

### 4.2 현재 메모리 회계는 peak가 아니다

`tensor_mb()`는 파라미터와 특수 packed tensor를 더하지만 다음을 포함하지 않는다.

- 활성값
- 실행 중 임시 버퍼
- 실제 KV 객체의 allocator overhead
- Python/PyTorch/tokenizer runtime
- 스레드 stack과 코드 페이지

P079는 여기에 KV를 결정론적 공식으로 더했다. 이는 후보 선별에는 유용하지만 peak resident memory 인증은 아니다.

### 4.3 int8 임베딩 출력 head의 일시 복원

[`TinyLM._head_logits()`](../tinylm/model/transformer.py#L372)는 `emb_chunk`가 0이면 양자화 임베딩 전체를 계산 dtype으로 복원한다. 현재 기본값은 0이며 P079의 메모리 명령에도 `--emb-chunk`가 없다. 따라서 영구 int8 임베딩은 작더라도 출력 head 순간에는 약 32MiB 규모의 fp32 임시 가중치가 추가될 수 있다.

코드 주석이 제시한 `emb_chunk=4096`도 E=256에서 약 4MiB scratch를 사용한다. 엄격한 40MB 구동기에서는 512~1024행 단위 또는 fused int8 output-head kernel로 0.5~1MiB 수준까지 낮추는 편이 안전하다.

### 4.4 LUT 구현이 참조용 PyTorch 경로다

[`tinylm/model/lut.py`](../tinylm/model/lut.py)는 현재 구현을 정확성·메모리 검증용 PyTorch 참조라고 명시한다. `lut_linear()`의 `gather` 결과가 큰 임시 텐서가 될 수 있으며 `out_chunk`로 분할해야 한다. 이 경로는 네이티브 SIMD LUT 커널이 아니므로 속도와 전체 메모리의 최종 배포 근거가 될 수 없다.

### 4.5 프리필과 attention peak가 미계측이다

현재 생성 경로는 첫 단계에 전체 prompt를 넣어 프리필하고 이후 1토큰씩 KV decode한다. CPU attention backend가 attention score를 물질화하는지, tiled 구현을 선택하는지에 따라 프리필 peak가 크게 달라질 수 있다. 1024토큰 상주 합계만 계산하고 프리필 peak를 재지 않으면 제품 실행 중 40MB 초과를 놓칠 수 있다.

### 4.6 배포용 산출물과 네이티브 커널이 없다

현재 확인된 실행 경로는 학습용 `.pt` 체크포인트를 전제로 한다. TinyLM 전용 compact binary, GGUF, `.pte` 또는 이에 대응하는 완성된 네이티브 exporter/runtime은 없다. 최신 P014D도 경로 인자 오류로 두 프로파일 팔이 모두 종료되어 LUT 디코드 처리량 측정값이 0이다.

근거: [P014D 결과](../test_result/069_20260902_P014D-디코드-프로파일이-경로이름을-양자화형식으로-넘겨-두-팔-다-죽었다.md).

## 5. 권장 배포 구조

### 5.1 1순위: 오프라인 변환기 + 애플리케이션 내장 소형 C/C++ 런타임

40MB 전체 상주가 절대 조건이라면 범용 프레임워크를 그대로 싣기보다 TinyLM에 필요한 기능만 포함한 런타임이 가장 예측 가능하다.

```text
학습 체크포인트(.pt)
        |
        | 오프라인 exporter/compiler — 배포 장치에서는 실행하지 않음
        v
TinyLM compact model file
  - config / tensor directory / execution schedule
  - 5-trit packed LUT weights + per-row alpha
  - int8 embedding + scales
  - small norm/gate tensors
  - tokenizer data
        |
        | mmap 또는 단일 직접 로드
        v
애플리케이션에 정적 링크된 TinyLM C/C++ runtime
  - ISA별 LUT kernels
  - fixed KV arena
  - fixed scratch arena
  - tiled prefill / one-token decode
```

#### 오프라인 exporter에 필요한 구현

1. 학습 체크포인트를 읽고 inference-only tensor만 선택한다.
2. latent 제거 이후의 확정 가중치를 5 trit/byte로 패킹한다.
3. 각 행의 alpha/scale과 shape·offset·alignment를 기록한다.
4. int8 임베딩과 row/group scale을 직렬화한다.
5. dense/tied, CLA group과 recurrence visit schedule을 명시적으로 저장한다.
6. tokenizer와 special-token 메타데이터를 포함하거나 별도 compact 파일로 고정한다.
7. 각 tensor의 hash, 전체 포맷 version과 endianness를 기록한다.
8. 변환 후 PyTorch 참조와 tensor-level/최종-logit 동등성을 검증할 수 있는 manifest를 만든다.

exporter는 Python으로 구현해도 된다. 빌드 또는 모델 변환 시에만 사용하고 제품에 Python/PyTorch를 포함하지 않는 것이 핵심이다.

#### 네이티브 runtime에 필요한 구현

1. 모델 파일을 복제하지 않고 읽는 loader/mmap reader
2. per-row alpha를 지원하는 1.600bpw ternary LUT GEMV/GEMM
3. x86-64 AVX2 baseline과 AVX-512 최적화 variant, 필요 시 ARM NEON variant
4. tiled/chunked 프리필 attention과 1토큰 KV decode
5. 고정 크기 bf16 KV arena
6. 작은 chunk 또는 fused 방식의 int8 embedding/output head
7. CLA와 recurrence를 새 텐서 복제 없이 실행하는 schedule executor
8. RoPE를 작은 buffer에서 계산하거나 재사용하는 구현
9. compact tokenizer
10. 단일 fixed scratch arena와 할당 실패 검사
11. peak resident/private memory와 arena high-water mark 계측

### 5.2 정적 라이브러리, DLL, 별도 프로세스 비교

| 배포 형태 | 장점 | 단점 | 40MB 관점 |
|---|---|---|---|
| 애플리케이션에 정적 링크 | 필요한 함수만 링크, 호출 비용·프로세스 중복 최소, 메모리 통제 용이 | 앱 재빌드 필요 | **권장** |
| 작은 DLL/shared library | 런타임 교체와 여러 앱 공유가 편함 | loader·relocation·공유 경계 관리 필요 | 조건부 권장 |
| 별도 CLI/server 프로세스 | 격리·다중 client 운영이 편함 | 프로세스·IPC·서버 heap과 tokenizer 중복 | 엄격한 40MB에는 비권장 |
| Python 서비스 | 개발·실험이 쉬움 | Python/PyTorch 바닥부터 예산 초과 | 불가 |

모델 하나를 단일 앱에서 구동한다면 정적 라이브러리가 가장 단순하다. 여러 앱이 동일 모델을 공유한다면 별도 서비스가 총 시스템 메모리를 줄일 가능성은 있지만, 그 경우 “구동기 프로세스 하나가 40MB 이하”인지 별도로 검증해야 한다.

## 6. 기존 구동기·커널 활용 가능성

### 6.1 T-MAC: 커널 기반으로 가장 유력하지만 완제품은 아니다

T-MAC은 LUT를 사용해 int1/2/3/4 가중치와 int8/fp16/fp32 활성값의 mixed-precision 행렬곱을 직접 수행하고, mainstream GPTQ 모델과 llama.cpp 통합 경로를 제공한다. group size를 포함한 shape별 kernel compile/code-generation 경로가 있어 TinyLM의 네이티브 커널 기반으로 검토할 가치가 높다.

그러나 TinyLM은 다음 때문에 그대로 실행할 수 없다.

- 5 trit/byte의 정확한 1.600bpw 포맷
- TinyLM의 per-row alpha와 shape
- factorized/tied embedding
- MLP/attention weight sharing
- CLA와 recurrence visit schedule
- TinyLM tokenizer·모델 아키텍처

일반 int2로 저장하면 ternary code stream이 1.6bpw에서 2bpw로 25% 증가한다. 메모리 여유가 큰 후보에는 허용될 수 있지만 `d16_cla2_r20`에는 맞지 않는다. 따라서 T-MAC의 codegen·kernel을 가져와 작은 전용 runtime에 연결하거나, TinyLM 전용 T-MAC backend를 추가하는 방식이 적합하다.

### 6.2 bitnet.cpp: 삼진 커널 참고에는 적합하지만 TinyLM은 비호환

bitnet.cpp는 BitNet b1.58 계열을 위한 공식 1-bit/ternary 추론 프레임워크이며 TL/I2_S 계열 CPU 커널을 제공한다. 다만 현재 공식 지원 모델의 tensor layout, scale 규약과 고정 kernel shape는 TinyLM의 per-row alpha·공유 구조·CLA·재귀 실행과 동일하지 않다.

따라서 “TinyLM 체크포인트를 GGUF로 바꾸기만 하면 실행된다”는 가정은 성립하지 않는다. packed tensor converter, 모델 아키텍처, graph와 kernel 규약을 함께 맞춰야 한다. bitnet.cpp는 삼진 패킹과 SIMD 처리의 참고 구현 또는 포크 기반으로 평가하는 것이 타당하다.

### 6.3 llama.cpp: 새 아키텍처 추가가 필요하다

llama.cpp 공식 안내는 새 모델에 대해 다음을 요구한다.

1. GGUF 변환
2. llama.cpp 안의 모델 아키텍처 정의
3. GGML graph 구현

TinyLM에는 여기에 custom ternary type/kernel, CLA와 recurrence schedule 처리가 추가된다. 구현 후에는 llama.cpp C/C++ API를 애플리케이션에 내장할 수 있지만, llama.cpp 전체 runtime의 코드·heap·thread·tokenizer를 포함해 40MB peak를 다시 측정해야 한다. 범용성은 높지만 최소 전용 런타임보다 통합 범위와 유지보수 비용이 크다.

### 6.4 ExecuTorch: 작은 core와 메모리 계획은 매력적이나 custom op가 필요하다

ExecuTorch 공식 문서는 kernel/backend를 제외한 core runtime이 50kB 미만이고, constant tensor가 `.pte` 파일을 직접 가리켜 복사를 피하며, mutable tensor memory를 사용자 할당 buffer에 사전 배치할 수 있다고 설명한다. 40MB 예산 관리에는 좋은 성질이다.

그러나 TinyLM을 사용하려면 다음이 필요하다.

- TinyLM graph export/lowering
- 5-trit packed LUT custom operator 또는 backend delegate
- CLA·recurrence·tied tensor 보존
- KV와 scratch memory plan
- 참조 PyTorch와의 수치 동등성 검증

모바일·다중 플랫폼 생태계가 우선이면 유력한 2순위다. 한 플랫폼에서 40MB만 우선하면 작은 전용 C++ runtime이 구현량과 메모리 예측성 측면에서 더 직접적이다.

### 6.5 ONNX Runtime·libtorch·일반 int8/int4

- **libtorch/PyTorch**: runtime 자체가 예산을 초과하므로 제외한다.
- **일반 int8**: 본체 가중치가 커져 현재 1.600bpw 이점을 잃는다.
- **일반 int4**: 저장은 줄지만 TinyLM의 삼진 전용 packing보다 2.5배의 code bit가 필요하고, custom 공유·재귀 구조 문제도 남는다.
- **ONNX Runtime**: custom low-bit operator와 execution provider를 구현하지 않으면 현재 포맷의 메모리 이점을 보존할 수 없다. 별도 범용 runtime overhead도 합격 시험에 포함해야 한다.

## 7. 후보별 배포 권고

### 7.1 메모리 우선 프로필

- 후보: `d8_g2`, `d12_g4`, `mC_cla2_ag4`
- 영구 텐서+KV: 19.6~24.3MiB
- 남는 40MiB 예산: 약 15.7~20.4MiB
- 용도: 40MB 달성 가능성 검증, runtime bring-up, 임베디드 우선 제품
- 위험: 품질이 `d12_cla2_r20`보다 낮을 수 있음

### 7.2 품질/메모리 절충 프로필

- 후보: `d12_cla2_r20`
- 영구 텐서+KV: 30.7MiB
- 40MiB까지 남는 예산: 약 9.3MiB
- 권장 조건: batch 1, context 1024, 고정 scratch, native tokenizer, output-head chunk <=1MiB
- 판정: **구현할 가치가 있는 주 후보이지만 합격을 보장하지는 않음**

### 7.3 연구용 40MiB 파레토 후보

- 후보: `d16_cla2_r20`
- 영구 텐서+KV: 38.5MiB
- 40MiB까지 남는 예산: 약 1.5MiB
- 40MB 십진 기준: 영구 합계부터 실패
- 판정: 모델 텐서/캐시 회계상 파레토 연구에는 유지할 수 있으나 **전체 40MB 제품 후보에서는 제외**

실제 제품 성공 가능성을 높이려면 영구 텐서+KV 목표를 28~30MiB 이하로 두고 나머지 10~12MiB를 runtime·tokenizer·scratch·stack에 예약하는 것이 타당하다. 이는 현재 실측값이 아니라 조사 결과에서 도출한 엔지니어링 안전 예산이다.

## 8. 반드시 필요한 합격 시험

현재 회계값을 실제 배포 가능성으로 승격하려면 네이티브 구현 후 다음 시험을 통과해야 한다.

### 8.1 고정 시험 조건

- 새로 시작한 네이티브 프로세스
- Python/PyTorch 미포함
- batch 1
- context limit 1024
- 1024토큰 프롬프트 프리필 후 최소 128토큰 decode
- greedy와 sampling 경로 각각 확인
- 1 thread와 제품 기본 thread 수 각각 확인
- cold load와 warm repeated decode 모두 측정
- 모델 파일의 모든 실제 weight page를 한 번 이상 접근한 뒤 측정

### 8.2 메모리 지표

Windows에서는 적어도 다음을 함께 기록한다.

- `PeakWorkingSetSize`
- private working set
- `PrivateUsage` 또는 commit peak
- runtime arena별 high-water mark

Linux에서는 다음을 기록한다.

- `/proc/<pid>/smaps_rollup`의 RSS와 PSS
- private clean/dirty
- anonymous와 file-backed page 구분
- allocator arena high-water mark

file-backed 모델 페이지를 제외한 private memory만으로 합격 처리하지 않는다. 제품 요구가 “실제 RAM 상주”라면 접근된 model page를 포함한 값을 주 판정으로 사용한다.

### 8.3 단계별 peak 분해

1. runtime만 시작
2. model mapping 직후
3. tokenizer 로드 후
4. 첫 weight touch 후
5. 1024토큰 프리필 중 peak
6. 첫 decode 중 peak
7. 128토큰 decode 후 steady state
8. 종료 직전

최종 합격값은 이 중 최대값이다. 로드 후 정상 상태만 재고 프리필 peak를 제외하면 안 된다.

### 8.4 정확성·품질 gate

- exporter 전후 tensor hash와 shape 일치
- 각 custom kernel의 fp32/PyTorch 참조 대비 오차
- 짧은 고정 prompt의 단계별 hidden/logit 오차
- greedy argmax 일치율
- bf16 KV 적용 전후 장문 prompt 오차와 generation divergence
- 기존 full-val 및 downstream 평가의 허용 손실 범위

현재 P077의 짧은 bf16 KV 진단은 긍정적이지만, teacher-forced 평가가 실제 cache generation 경로를 충분히 검증하지 않는다는 제한이 있다. 메모리 합격과 생성 품질 합격을 동시에 닫아야 한다.

### 8.5 속도 gate

메모리만 맞고 처리속도가 실용적이지 않으면 배포가 성립하지 않는다.

- prefill tokens/s
- decode tokens/s
- 첫 토큰 지연
- 1/2/4 thread scaling
- peak memory와 속도의 동시 측정
- scalar/AVX2/AVX-512 또는 NEON별 결과

T-MAC·bitnet.cpp 논문의 배수는 수십억 파라미터 모델과 특정 CPU 조건의 결과다. TinyLM의 작은 행렬에서는 LUT table 구성 비용의 상각이 달라질 수 있으므로 외부 배수를 직접 적용하지 않는다.

## 10. 현재 확인 상태와 미확정 사항

### 확인됨

- 현재 Python/PyTorch 전체 프로세스는 40MB가 될 수 없다.
- P079 조건에서 영구 텐서+KV가 40MiB 아래인 후보가 여러 개다.
- `d16_cla2_r20` 38.5MiB는 실제 runtime 여유가 없다.
- 기본 output-head 경로와 PyTorch LUT 경로에는 회계 밖 임시 메모리가 존재한다.
- 현재 저장소에는 완성된 TinyLM 네이티브 배포 구동기와 검증된 compact 배포물 경로가 없다.
- T-MAC, bitnet.cpp, llama.cpp, ExecuTorch 모두 참고·기반으로 쓸 수 있지만 TinyLM은 custom integration이 필요하다.

### 미확정

- 소형 후보의 실제 native peak resident memory
- tokenizer의 실제 native resident 크기
- 1024토큰 프리필의 peak scratch
- 1.600bpw 전용 LUT kernel의 TinyLM shape에서의 처리속도
- AVX2·AVX-512·NEON별 최적 kernel과 code size
- `d12_cla2_r20`이 전체 40MiB를 실제 통과하는지
- 단일-seed 품질 우위의 재현성
- bf16 KV의 장문 실제 생성 품질

## 11. 최종 권고

1. **현재 PyTorch 실행을 40MB 배포라고 부르지 않는다.** 현재 수치는 연구용 tensor/KV 회계다.
2. **제품 단위를 바이트로 고정한다.** 엄격한 40MB라면 38.147MiB가 상한이다.
3. **첫 구현은 24~27MiB 이하 후보로 한다.** 이를 통해 runtime 자체가 40MB를 달성하는지 먼저 검증한다.
4. **주 품질 후보는 `d12_cla2_r20`로 둔다.** 네이티브 runtime이 닫힌 뒤 승격한다.
5. **`d16_cla2_r20`은 전체 40MB 후보에서 제외한다.** 모델 회계 연구와 제품 배포 판정을 구분한다.
6. **배포 형식은 custom packed file, 구동기는 앱에 정적 링크한 C/C++ runtime을 1순위로 한다.** T-MAC kernel을 활용하되 TinyLM graph·scale·packing은 별도로 구현한다.
7. **모델 로드부터 프리필·디코드까지의 peak를 실제 새 프로세스에서 측정한 뒤에만 “40MB 상주 달성”으로 판정한다.**

## 14. 조사 한계

- 이 문서는 정적 코드·문서 조사와 기존 결과의 재해석이다. 신규 모델 실행, 컴파일 또는 메모리 프로파일을 수행하지 않았다.
- P079 메모리 표는 영구 텐서와 분석적 KV 합계이며 실제 프로세스 peak가 아니다.
- 외부 프로젝트의 공개 성능은 다른 모델 크기·shape·CPU·thread 조건에서 얻어진 값이다. TinyLM 성능 추정값으로 직접 대입하지 않았다.
- 운영체제의 working set, RSS, PSS, commit은 정의가 다르다. 최종 제품 지표를 하나로 고정하고 보조 지표를 함께 기록해야 한다.
- 네이티브 runtime이 아직 없으므로 “일부 후보는 40MiB 전체 상주가 가능하다”는 판정은 byte accounting과 구현 여유에 근거한 조건부 가능성이지 실행으로 입증된 결과가 아니다.
