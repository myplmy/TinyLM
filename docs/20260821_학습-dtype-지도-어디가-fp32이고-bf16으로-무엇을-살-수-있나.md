## 0. 결론 세 줄

> ★★★**① GEMM 은 이미 bf16 이다.** `trainer.py:521` 이 forward 전체를
> `torch.autocast(bf16)` 으로 감싸므로 **모든 `F.linear` 가 bf16 텐서코어로 돈다.**
> *"bf16 으로 가속"* 이라는 여지의 **대부분은 이미 소진돼 있다.**
>
> ★★**② `--opt-dtype bf16` 은 속도를 주지 않는다. VRAM 만 준다.**
> 실측 **ms/step +0.16%**(결과 035 §12.4 S4) · **reserved −1.02 GiB**.
> **산술은 항상 fp32** 이므로(`adamw_bf16.py`) 연산량이 안 준다 — 설계상 그렇다.
>
> ★★★**③ 남은 fp32 덩어리는 딱 하나 — `_wq` 재생성이다.**
> 매 스텝 **54.85M 삼진 가중치를 fp32 로 다시 만들고**(`refresh_quant`),
> 그걸 `F.linear` 마다 **fp32 → bf16 으로 캐스팅**한다.
> ⚙**스텝당 2~3 GB 의 메모리 트래픽**으로 추정되며 **한 번도 측정한 적이 없다.**
> → ★**이것이 유일하게 남은 후보이고, 재는 데 학습이 필요 없다.**

## 2. ★★★"bf16 으로 가속" 여지 — **항목별 판정**

| # | 후보 | 현재 | 속도 이득 | 판정 |
|---|---|---|---|---|
| **A** | **GEMM** | ★**이미 bf16** | — | ✅★**이미 되어 있다.** 더 할 것이 없다 |
| **B** | **Adam 상태** | 선택 가능 | 🚫**+0.16%**(느려짐) | ✅ 채택하되 **VRAM 이유로만**(§3) |
| **C** | **activation** | ★**이미 bf16** | — | ✅ 이미 |
| ★**D** | ★★**`_wq` 저장·생성** | **fp32** | ⚙**미지 — 유일한 후보** | ★**측정 필요**(§4) |
| **E** | **master weight** | fp32 | 이론상 있다 | 🚫★**하지 않는다**(§2.1) |
| **F** | **gradient** | fp32 | 이론상 있다 | 🚫★**하지 않는다**(§2.2) |
| **G** | RMSNorm 내부 | fp32 강제 | 미미 | 🚫 의도된 것 |
| **H** | softmax/CE | fp32 강제 | 미미 | 🚫 torch 가 강제. 그리고 **KD KL 정밀도를 지킨다**(042 §10.4) |

### 2.1 🚫**E — master weight 를 bf16 으로 내리지 않는다**

**이유 셋**:

| # | 이유 |
|---|---|
| 1 | ★**삼진화가 `w` 의 *크기 순서*를 읽는다.** `mask = (aw >= thr_ratio * aw.mean())` — bf16 은 유효숫자 약 3자리라 **문턱 근처에서 비교가 뒤집힌다.** 어느 가중치가 0 이 되는지가 바뀐다 |
| 2 | ★**우리는 STE 로 latent 를 학습한다.** `w` 는 **누적되는 양**이고 lr 1e-3 × 미세 gradient 를 bf16 에 더하면 **언더플로로 사라진다**(순수 bf16 학습이 실패하는 표준적 이유) |
| 3 | **상주·packed 를 안 바꾼다.** 배포는 삼진이고 `w` 는 **학습 전용**이다 |

⚠️★**단 VRAM 은 준다** — 63.5M × 4B = **254 MB**. **품질 위험 대비 이득이 작다.**

### 2.2 🚫**F — gradient 를 bf16 으로 내리지 않는다**

| # | 이유 |
|---|---|
| 1 | ★**`clip_grad_norm_(1.0)` 이 전역 노름을 잰다**(`trainer.py:539`). bf16 누적은 **63.5M 항 제곱합**에서 정밀도를 잃는다 |
| 2 | ★★**`grad_max` 가 우리 안정성 판정의 정본이다**(함정 4). **자를 바꾸면 과거 판정과 비교가 끊긴다** |
| 3 | **`accum 16` 으로 16번 누적**한다. bf16 누적은 **누적 횟수에 비례해 오차가 는다** |

⚠️**bf16 grad 는 `--no-ckpt` 를 열 만큼(약 4.4 GiB) 크지도 않다** — grad 는 254 MB 다.

## 3. ★`--opt-dtype bf16` 재검증 — **−1.02 GiB 는 맞다. 단 대조군을 골라야 한다**

사용자 질문이 *"`opt-dtype bf16` 옵션처럼"* 이라 했으므로 **그 옵션의 실측을 다시 확인**했다.

### 3.1 실측 (`runs/logs/*.json`, 전부 KD·2289스텝·grad_ckpt ON)

| 태그 | `opt_dtype` | 옵티마이저 경로 | **reserved** | alloc |
|---|---|---|---:|---:|
| `mC_wsd` | `None`(미기록) | torch fused AdamW, ★**구 세션** | **11.6875** | 10.3594 |
| ★**`mC_wsd_s2`** | `fp32` | torch fused AdamW | ★**12.4746** | 10.0359 |
| `mC_opt32_250`(250스텝) | `fp32` | 동 | 12.4746 | 10.0320 |
| ★**`mC_optbf16`** | ★**`bf16`** | `AdamWLowPrec` | ★**11.4531** | 9.8524 |
| `mC_optbf16_250`(250스텝) | `bf16` | 동 | 11.4512 | 9.8509 |

### 3.2 ✅**−1.02 GiB 는 두 쌍에서 독립 재현된다**

| 쌍 | Δ reserved |
|---|---:|
| 250스텝 `fp32` → `bf16` | **−1.0234** |
| **2289스텝 `mC_wsd_s2` → `mC_optbf16`** | ★**−1.0215** |

> ✅**결과 035 §12 의 −1.02 GiB 는 유효하다.** 서로 다른 예산의 두 쌍이 **0.002 안에서 일치**한다.

### 3.3 ⚠️★그런데 **결과 035 §12.3 표의 대조군 표기가 틀렸다**

그 표는 *"`mC_wsd`(대조) peak reserved **12.47**"* 이라고 적었는데
**`mC_wsd` 의 json 은 11.6875** 다. **12.4746 은 `mC_wsd_s2`·`mC_opt32_250` 의 값**이다.

| | 결과 035 §12.3 표기 | **json 실측** |
|---|---:|---:|
| `mC_wsd` reserved | ~~12.47~~ | ★**11.6875** |

⚠️★**판정은 안 바뀐다**(§3.2 가 같은 조건 두 쌍으로 −1.02 를 확인했다).
**바뀌는 것은 "어느 런이 대조군인가" 뿐이다.** → **정본 대조군 = `mC_wsd_s2`(12.4746).**

### 3.4 ★★부수 발견 — **VRAM reserved 에도 세션 드리프트가 있다**

`mC_wsd`(11.6875)와 `mC_wsd_s2`(12.4746)는 **같은 조건인데 reserved 가 0.787 GiB 다르다.**
둘 다 KD·2289스텝·`grad_ckpt` ON·`micro_bs 8`·`accum 16` 이고,
차이는 **시드(1337 vs 2024)와 실행 시점(구 세션 vs 신 세션)** 뿐이다.

> ★★**우리는 ms/step 세션 드리프트 7.5% 를 이미 안다**(결과 037 §11.4 — *"다른 날 런의 속도를
> 비교하지 않는다"*). ★**reserved 에도 같은 성질이 있다는 것은 이번에 처음 본다: 0.787 GiB (6.7%).**
>
> → ★**규칙 제안**: **VRAM 을 비교할 때도 같은 세션의 런끼리** 본다.
> 다른 날 런의 reserved 차이가 **0.8 GiB 미만이면 조건 탓으로 귀속하지 않는다.**
> ⚠️**표본 1건이다.** 자릿수 관찰이지 상수가 아니다.

### 3.5 ★`opt_state_mb` 회계

```
63.5M 파라미터 × 상태 2벌 × 2B = 254.0 MB      (json 실측 254.004)
fp32 라면                        508.0 MB
절감(계산)                       254.0 MB = 0.2365 GiB
```

⚠️★**reserved 절감(1.02)이 계산(0.24)의 4.3배**다. 결과 035 §12.2a 가 이미 짚었고
**할당자 파편화**로 설명했다. ★**alloc 기준 절감은 0.181 GiB = 계산의 77%** 로 **자릿수가 맞는다.**
→ **인용할 때 어느 쪽인지 명시한다**(함정 1 계열).

## 4. ★★★유일하게 남은 후보 — **`_wq` 경로**

### 4.1 무슨 일이 매 스텝 일어나는가

```python
# transformer.py:411  — forward 최상단, autocast 안
if not self._quant_frozen:
    self.refresh_quant()                     # 모든 TLinear 를 순회

# ternary.py:248
def refresh_quant(self, anneal, arena=None):
    w  = self._w()                           # fp32, 54.85M
    wq = ternary(w, self.cfg)                # ★fp32 elementwise 6~7 패스
    self._wq = wq + (1.0 - anneal) * (w - wq).detach()    # ★fp32 3 패스 더

# ternary.py:279  — 층마다, 그리고 타잉이면 같은 객체가 g 번
y = F.linear(x, wq)                          # ★autocast 가 wq 를 fp32→bf16 캐스팅
```

`ternary()` 안(`ternary.py:14-32`)에서 fp32 로 도는 것:
`reshape` → `abs` → `mean(dim=2)` → `>=` 비교 → `sum` → `sign` → `sign*mask*alpha`.

### 4.2 ⚙트래픽 추정 — **재 본 적이 없다**

| 항목 | 크기 |
|---|---:|
| 삼진 파라미터 | **54,853,632** |
| fp32 1벌 | **219.4 MB** |
| `ternary()` 패스 수 | ⚙약 6~7 (읽기+쓰기) |
| 어닐 항 패스 수 | ⚙약 3 |
| ⚙**`refresh_quant` 스텝당 트래픽** | ⚙**약 2.0~2.2 GB** |
| ⚙**`F.linear` 진입 캐스팅** | ⚙**219 MB 읽기 → 110 MB 쓰기, 호출마다** |

⚠️★**전부 ⚙추정이다.** 실측하지 않았다 — 그게 §5 의 요점이다.

### 4.3 ★★캐스팅이 몇 번 일어나는가 — **타잉 때문에 커질 수 있다**

`torch.autocast` 는 **leaf Parameter 의 캐스팅을 캐시**한다. 그런데 **`_wq` 는 leaf 가 아니다**
(`ternary()` 의 출력이고 autograd 그래프에 매달려 있다).
→ ⚙**캐시가 안 먹을 가능성이 높고, 그러면 `F.linear` 호출마다 다시 캐스팅**한다.

| 조건 | ⚙호출 횟수 |
|---|---:|
| `mlp_group=8`, 중간 16층 | 유니크 MLP 하나가 **8회** |
| `grad_ckpt` **ON**(현재 표준) | forward 를 **2번** 돈다 → ⚙**16회** |
| `attn_group=4`(`m100R1d`) | 유니크 어텐션 하나가 **4회** |

> ★★**타잉이 저장·상주를 줄이는 대신 "같은 텐서를 여러 번 캐스팅" 을 만들 수 있다.**
> **이건 우리가 한 번도 안 본 각도다** — 지금까지 타잉의 속도 영향은
> *"forward·backward 는 전 층을 지난다"*(연산량 불변)로만 설명했다.
> ⚠️**추정이다. `autocast` 캐시가 실제로 어떻게 도는지 확인해야 한다.**

### 4.4 ★그래서 무엇을 바꿀 수 있나 — **세 갈래, 위험이 다르다**

| # | 방법 | 이득 | 위험 | 비트 동일 |
|---|---|---|---|---|
| ★**D1** | ★**`_wq` 를 bf16 으로 *저장***(계산은 fp32) | 캐스팅 제거 + 트래픽 절반 | ⚠️**중간** — backward 가 bf16 으로 흐른다 | 🚫 아니다 |
| **D2** | `ternary()` **내부 계산까지** bf16 | 트래픽 절반 이상 | 🚫★**높다** — `alpha` 가 **128개 합의 평균**이고 `mask` 는 문턱 비교다. **어느 가중치가 0 이 되는지가 바뀐다** | 🚫 |
| ★**D3** | ★**`freeze_quant` 를 학습에도 부분 적용**(N 스텝마다 재계산) | ⚙**최대 1/N** | 🚫★**높다** — latent 학습이 STE 로 도는데 `_wq` 가 낡으면 **다른 함수를 학습한다**(함정 39 계열) | 🚫 |

> ★**D1 이 유일하게 현실적이다.** 그리고 **D2·D3 은 품질 축을 건드리므로 "가속" 이 아니라 "실험" 이다.**

⚠️★★**그리고 이득의 크기를 우리는 모른다.**
결과 014 §11 은 **배치1 디코드가 런치 바운드**라고 했지만 **학습은 다르다**(M=8192).
**메모리 바운드인지 연산 바운드인지 이 경로에 대해 잰 적이 없다.**

## 6. 🚫이 분석이 **답하지 않는 것**

## 7. ★한 줄 답 (사용자 질문에 대한)

> **`opt-dtype bf16` 같은 "공짜 bf16" 은 더 없다.**
> **GEMM·활성은 이미 bf16 이고, master·gradient·Adam 산술은 정밀도 때문에 fp32 여야 한다.**
> ★**남은 것은 `_wq` 하나**이고, 그것은 **"공짜" 가 아니라 "비트 동일이 깨지는 실험"** 이다.
> **그리고 이득의 크기를 아직 모른다** — §5 의 M2·M3 이 수 분에 답한다.
>
> ⚠️★**`opt-dtype bf16` 자체도 속도 이득이 아니다**(+0.16%). **VRAM −1.02 GiB 가 전부**이고,
> **REVIEW2 안 B2 가 그것 하나만 고정하는 이유**가 여기 있다.
