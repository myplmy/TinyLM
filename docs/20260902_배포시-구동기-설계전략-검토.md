# 2026-09-02 — 배포 시 구동기 설계 전략 검토

## 0. 문서 목적과 조사 범위

이 문서는 TinyLM을 장차 LM Studio, llama.cpp처럼 사용자가 이미 익숙한 플랫폼에서 실행할 수 있게 하려는 경우, 기존의 “40MB 이내 상주를 위한 최소 전용 구동기” 전략을 어떻게 바꾸어야 하는지 검토한다. 저장소의 현재 모델 구조·양자화 코드·실험 결과와 llama.cpp/GGUF 및 LM Studio의 공개 공식 문서를 함께 대조했다.

이번 조사에서는 코드·모델·실험을 실행하지 않았다. 따라서 아래 수치는 기존 문서와 기존 실험 결과의 재해석이며, 실제 GGUF 변환 성공, llama.cpp 실행 성공, LM Studio 호환, 40MB 이내의 프로세스 피크 메모리를 새로 입증한 결과가 아니다.

## 1. 결론

최종 배포 방법은 달라져야 한다. 공개 플랫폼 호환성이 장기 목표라면 독자 포맷과 독자 구동기만을 최종 배포물로 삼아서는 안 된다. 권장안은 다음의 이중 배포 구조이다.

1. **공개 호환 프로필:** GGUF + upstream llama.cpp를 기본 배포 경로로 삼는다. LM Studio 호환성은 이 경로가 공식/선택 가능한 LM Studio llama.cpp 런타임에 포함된 뒤 검증한다.
2. **엄격 메모리 프로필:** 최소 C/C++ 구동기와 현재의 5-trit/byte(1.600 bpw) 포맷을 40MB 특화 경로이자 정합성 기준기(conformance oracle)로 유지한다.
3. **공통 원천:** 두 배포물을 서로 다른 모델처럼 관리하지 않고, 하나의 체크포인트·토크나이저·배포 명세에서 생성한다. 레이어 재방문, CLA 소유권, KV 캐시 키, tied/factorized embedding 같은 의미론도 하나의 명세로 고정한다.

우선순위는 새 GGML 양자화 형식을 만드는 것이 아니라 llama.cpp에 이미 있는 `TQ1_0`을 실제 후보 체크포인트에 적용해 보는 것이다. 저장소의 기존 g256 재그룹 실험에서는 common bpb 악화가 약 `+0.0010~+0.0015`였기 때문에, 256개 단위 ternary 블록을 쓰는 `TQ1_0`은 품질상 유력하다. 성공하면 새 양자화 타입과 각 하드웨어 백엔드용 커널을 만들지 않고 **TinyLM 아키텍처·그래프·변환기만** 추가하는 경로가 열린다. 단, llama.cpp `TQ1_0`은 정확히 동일한 양자화 규칙이 아니므로 이 결과를 호환성 입증으로 간주해서는 안 된다.

## 2. 현재 저장소에서 확인되는 제약

### 2.1 Python/PyTorch 배포는 40MB 목표와 양립하지 않는다

기존 조사에서 Python/PyTorch의 모델 미적재 상태 프로세스만으로도 약 386~388MB RSS가 관측되었다. 따라서 PyTorch는 학습·기준 출력 생성·정합성 비교용으로는 유지하되, 40MB 배포 구동기로 사용할 수 없다. 네이티브 확장 연산만 추가해도 Python/PyTorch 런타임 자체의 메모리는 남는다.

### 2.2 P079의 수치는 런타임 전체 메모리가 아니다

기존 P079 계산은 본체 1.600 bpw LUT, per-row scale, embedding int8, KV bf16, batch 1, context 1024를 가정한 **텐서+KV의 산술 합계**다. 후보별 결과는 다음과 같다.

| 후보 | 기존 텐서+KV 추정 | 해석 |
|---|---:|---|
| `d8_g2` | 19.6 MiB | 구동기·scratch 여유가 가장 큼 |
| `d12_g4` | 22.2 MiB | 작은 호환성 기준 후보 |
| `mC_cla2_ag4` | 24.3 MiB | 구조 기능 검증 후보 |
| `mC_initonly_nc` | 27.3 MiB | 중간 후보 |
| `d12_cla2` | 27.7 MiB | CLA 기준 후보 |
| `d12_g4_r30` | 28.2 MiB | recurrence 계열 후보 |
| `d16_g4_r20` | 30.2 MiB | 경계 후보 |
| `mC_cla2_ag4_r20` | 30.3 MiB | 구조 복합 후보 |
| `d12_cla2_r20` | 30.7 MiB | 현재 32MiB 산술 승자, full-val 3.6054 |
| `d16_cla2_r20` | 38.5 MiB | 현재 40MiB 산술 승자, full-val 3.5642이나 런타임 여유 거의 없음 |

여기에는 실행 파일과 공유 라이브러리의 private page, GGUF 메타데이터, 로더, 그래프 객체, 토크나이저, 스레드별 버퍼, 임시 unpack/gather 버퍼, 메모리 정렬 손실, OS allocator 단편화가 포함되지 않는다. 따라서 `d16_cla2_r20`의 38.5MiB는 “40MB에서 실행 가능”이라는 증거가 아니다.

또한 `40 MB = 40,000,000 bytes`와 `40 MiB = 41,943,040 bytes`를 분리해 보고해야 한다. 엄격한 제품 요구가 MB라면 MiB 기준 통과만으로는 실패다.

### 2.3 TinyLM은 단순한 표준 decoder-only 모델이 아니다

현재 주요 구조적 의미론은 다음과 같다.

- ByteLevel BPE, vocab 32,768, pad/bos/eos 특수 토큰
- factorized embedding rank 256과 입력/출력 tied embedding
- QK RMS normalization 이후 RoPE
- 12 query heads, 3 KV heads인 GQA
- CLA에서 물리 레이어별 KV 소유자를 `owner = i - (i % cla_group)`로 결정
- recurrence에서 같은 가중치를 여러 번 방문하되, 기본적으로 KV는 `(owner, pass)` 단위로 구별
- ternary 본체와 별도의 embedding/head 양자화 정책

GGUF 파일 확장자만 붙이는 것으로 이 의미론이 구현되지 않는다. converter, 아키텍처 메타데이터, tensor name mapping, loader, graph builder, KV 캐시 계획, tokenizer/chat template가 모두 같은 계약을 구현해야 한다.

## 3. LM Studio와 llama.cpp의 실제 호환성 경계

### 3.1 LM Studio용 별도 독자 모델 형식을 만드는 문제가 아니다

LM Studio 공식 문서는 데스크톱에서 GGUF 모델을 llama.cpp 런타임으로 실행하고, Apple Silicon에서는 MLX 런타임도 사용할 수 있다고 설명한다. `lms runtime`은 사용 가능한 런타임을 조회·다운로드·선택·갱신하는 기능이며, `lms import`는 **호환되는 GGUF**를 가져오는 기능이다.

따라서 다음 세 명제는 구별해야 한다.

- GGUF로 변환되었다: 컨테이너가 생겼다는 뜻이다.
- 로컬 패치 llama.cpp에서 실행된다: 개발자 환경의 구현이 있다는 뜻이다.
- 일반 사용자의 LM Studio에서 실행된다: LM Studio가 제공·선택하는 런타임에 그 구현이 들어갔다는 뜻이다.

`model.yaml`은 카탈로그 표시와 기본 파라미터 같은 메타데이터를 관리하지만, 지원되지 않는 모델 그래프나 연산을 구현하지 않는다. 2026-09-02 현재 공개 공식 문서에서는 임의의 제3자 추론 런타임을 LM Studio에 일반 배포하는 공개 SDK를 확인하지 못했다. 따라서 공개 LM Studio 호환성은 사실상 llama.cpp upstream 지원 이후의 후속 게이트로 잡는 것이 안전하다.

### 3.2 llama.cpp에 필요한 것은 “변환기”보다 넓다

llama.cpp의 공식 새 모델 추가 절차는 대략 다음을 요구한다.

1. Hugging Face/원본 체크포인트를 GGUF로 변환하는 converter
2. `general.architecture`에 대응하는 새 architecture 식별자
3. 모델 하이퍼파라미터와 tensor 이름 매핑
4. GGML 계산 그래프와 KV 캐시 구성
5. tokenizer 및 chat template 전달
6. `llama-cli`, completion, imatrix/quantize, `llama-server` 검증
7. CPU를 시작으로 Metal/CUDA/Vulkan 등 주요 backend 검증

TinyLM에서는 같은 물리 weight를 recurrence 방문마다 중복 저장하지 않으면서, 계산 그래프에는 방문 순서를 명시해야 한다. CLA 역시 공유 KV와 recurrence pass를 혼동하지 않도록 해야 한다. 이는 표준 레이어 배열을 단순 복제하는 방식보다 architecture-specific graph builder가 필요한 이유다.

아키텍처 문자열은 공개된 GGUF의 ABI에 가깝다. 예를 들어 `general.architecture=tinylm`을 임시로 배포한 뒤 이름이나 metadata key를 바꾸면 기존 커뮤니티 파일이 깨질 수 있다. 이름·tensor key·schedule 표현·버전 거부 규칙을 먼저 고정해야 한다.

## 4. 양자화 포맷 선택: 기존 `TQ1_0`을 먼저 시험할 이유

### 4.1 현재 독자 포맷과 stock llama.cpp 포맷의 차이

| 항목 | 현재 TinyLM LUT 후보 | llama.cpp `TQ1_0` |
|---|---|---|
| 부호/값 | ternary `{-1,0,+1}` | ternary `{-1,0,+1}` |
| 명목 본체 비트율 | 1.600 bpw + scale | 1.6875 bpw |
| 블록/패킹 | 5 trits/byte, 기존 배포안은 per-row scale | 256-value block, 5-trit 및 4-trit 조합, fp16 scale |
| 장점 | 가장 작은 기존 산술치 | 포맷·quantizer·일부 kernel이 upstream에 이미 존재 |
| 위험 | 독자 kernel·loader·backend 유지비 | 현재 모델과 scale/rounding 규칙이 달라 품질·메모리 재검증 필요 |

코드 비트율만 비교하면 `TQ1_0`은 1.600 bpw보다 약 5.47% 크다. 그러나 이 비율을 P079의 전체 수치에 곧바로 곱하면 안 된다. embedding/head, scale, KV, 메타데이터는 서로 다른 형식과 비율을 쓰기 때문이다.

### 4.2 기존 실험이 주는 근거와 한계

P014C 결과에서 g256 scale 재그룹의 common bpb 손실은 네 모델에서 약 `+0.0010~+0.0015`였고, per-row는 `+0.0050~+0.0063`, per-tensor는 `+0.0465~+0.0862`였다. 이는 256개 블록 단위가 품질상 유력하다는 근거다.

그러나 stock `TQ1_0`은 기존 g256 실험과 다음이 다를 수 있다.

- scale 추정 공식과 fp16 scale 반올림
- block packing과 tensor별 fallback
- embedding/head의 별도 양자화
- 실제 GGML kernel의 누산 순서

따라서 “기존 g256 통과 → TQ1_0 통과”는 가설이지 결론이 아니다. `d12_cla2_r20`과 작은 sanity 후보에서 실제 round-trip, bpb, full-val, logits, peak memory를 재측정해야 한다.

### 4.3 권장 포맷 우선순위

1. **FP32/FP16 GGUF:** 그래프와 tokenizer 정합성을 먼저 검증하는 reference artifact. 40MB 제품 후보는 아니다.
2. **stock `TQ1_0` 본체 + 지원되는 embedding/head 양자화:** 가장 구현 부담이 작은 공개 배포 후보. embedding/head는 Q8_0, F16 등 실제 품질·메모리 결과로 선택한다.
3. **stock `TQ2_0` 등 대체 형식:** TQ1_0의 품질 또는 kernel 지원이 부족할 때 비교한다. 메모리는 커진다.
4. **TinyLM 전용 1.600 bpw GGML type:** 40MB가 stock 포맷에서 불가능하고 가치가 충분할 때만 추진한다. CPU뿐 아니라 원하는 backend마다 type traits, quant/dequant, dot kernel, test가 필요하다.
5. **전용 최소 런타임의 1.600 bpw artifact:** 공개 생태계 호환과 별도로 엄격 메모리 SKU에 유지한다.

## 5. 권장 배포 아키텍처

```text
checkpoint + tokenizer + model config
                 |
                 v
       versioned deployment manifest
  (tensor identity, alias, visit schedule,
   CLA/KV rule, tokenizer, quant rule, hashes)
          /                         \
         v                           v
GGUF exporter                    compact exporter
  - F32/F16 reference              - 1.600 bpw
  - TQ1_0 candidate                - fixed arenas
         |                           |
         v                           v
upstream llama.cpp              minimal C/C++ runtime
  - CLI/server                     - conformance oracle
  - LM Studio downstream           - strict-memory profile
```

### 5.1 하나의 배포 명세가 가져야 할 항목

- 명세 버전과 호환 가능한 최소 loader 버전
- config 원문 또는 정규화된 하이퍼파라미터와 SHA-256
- logical tensor와 physical tensor의 구분, shape/dtype/offset/hash
- tied/shared tensor alias 표: 동일 weight를 파일에 중복 저장하지 않음
- pre/middle/coda와 recurrence visit의 명시적 실행 순서
- CLA owner mapping과 KV key `(owner, pass)` 규칙
- QK norm, RoPE, GQA, norm/activation의 정확한 순서
- tokenizer JSON/vocab/merges/special token/chat template의 식별자와 hash
- tensor별 quant type, block size, scale dtype, fallback 사유
- alignment, endian, offset overflow 및 미지원 버전의 fail-closed 규칙

이 명세는 특정 C++ class나 GGUF 구현 세부가 아니라 모델 의미론을 정의해야 한다. 그래야 독자 런타임과 llama.cpp가 같은 fixture를 통과할 수 있다.

### 5.2 공개 호환 프로필

공개 프로필은 다음을 목표로 한다.

- 표준 GGUF 컨테이너
- upstream llama.cpp의 TinyLM architecture
- stock quant type 우선
- `llama-cli`와 `llama-server` 정상 동작
- 이후 일반 LM Studio 사용자가 추가 패치 없이 import/load/generate 가능

초기 구현은 x86-64 CPU로 제한하는 것이 합리적이다. llama.cpp 모델 추가 가이드도 새 모델과 모든 backend 최적화를 하나의 변경으로 끝낼 필요는 없다고 설명한다. 다만 CPU 성공을 Metal/CUDA/Vulkan 성공으로 표현해서는 안 된다. 특히 2026년 8월의 llama.cpp 이슈에는 Apple Silicon의 순수 CPU TQ1/TQ2가 최적 kernel 없이 느린 경로로 fallback하는 사례가 보고되어 있으므로, “로드 가능”과 “실용 속도”를 분리해 평가해야 한다.

### 5.3 엄격 메모리 프로필

최소 런타임은 다음 목적으로 남길 가치가 있다.

- mmap 또는 순차 로드와 고정 arena로 실제 peak memory 하한 측정
- scalar 연산을 통한 llama.cpp graph의 정합성 oracle
- stock GGUF/TQ1_0이 40MB를 넘을 때 1.600 bpw 제품 제공
- 임베디드·정적 링크·단일 실행 파일 같은 특수 배포

가능하면 이 구동기가 GGUF의 제한된 subset을 직접 읽도록 해 컨테이너를 하나로 합친다. 이것이 메모리나 구현 복잡도를 악화시키면, 공통 manifest에서 GGUF와 compact artifact를 각각 생성하되 tensor hash와 golden fixture를 공유한다.

## 6. 구동기 후보의 재평가

| 후보 | 초기 구현 난이도 | 공개 호환성 | 엄격 40MB 가능성 | 권장 역할 |
|---|---|---|---|---|
| PyTorch + native op | 가장 낮음 | 낮음 | 없음 | 연구 reference와 exporter 검증 |
| 최소 C/C++ 전용 구동기 | 중간 | 낮음 | 가장 높음 | oracle와 strict-memory SKU |
| upstream llama.cpp + stock TQ1_0 | 중간~높음 | 가장 높음 | 후보별 실측 필요 | 최종 공개 배포의 주 경로 |
| llama.cpp + TinyLM custom quant | 매우 높음 | 높음(merge 후) | 높음 | stock format 실패 시 후속안 |
| ExecuTorch | 중간~높음 | LM Studio 직접 호환 아님 | 실측 필요 | 모바일 앱 통합이 별도 목표일 때 |
| T-MAC/BitNet 직접 이식 | 높음 | 제한적 | 구조 적합성 재검증 필요 | kernel 아이디어/비교 연구 |
| esp32-ai/llama2.c식 초소형 전용기 | 모델별 상이 | 낮음 | 높은 편 | arena·파일 명세 설계 참고 |

“구현이 가장 덜 복잡한 것”은 시점에 따라 다르다. 즉시 작동하는 연구 bridge는 PyTorch + native op지만 40MB와 공개 플랫폼을 해결하지 못한다. 제품 전체 목표를 기준으로는 **stock TQ1_0을 재사용하는 llama.cpp architecture 추가**가 장기 중복 작업을 가장 적게 만든다. 다만 TinyLM 의미론을 검증할 작은 scalar reference가 없으면 graph 오류와 quant 오류를 분리하기 어려우므로 최소 reference runtime은 병행 자산이다.

## 7. 구현 시 필요한 항목

### 7.1 공통·export 계층

- 배포 manifest/schema와 버전 정책
- checkpoint tensor inventory 및 shared/tied alias 탐지
- recurrence visit schedule과 CLA owner/KV map 직렬화
- tokenizer/chat template export와 golden token fixture
- FP32/F16 GGUF exporter
- stock TQ1_0 적용 가능 tensor 검사와 fallback 목록
- embedding/head의 직접 양자화 matmul 경로; 전체 vocab weight 복원 금지
- round-trip validator: tensor 수·shape·dtype·hash·코드·scale·alignment

### 7.2 llama.cpp 계층

- 안정된 TinyLM architecture id와 GGUF metadata key
- converter registration과 tensor name mapping
- config loader 및 미지원 config의 명시적 거부
- factorized/tied embedding, QK norm, RoPE, GQA graph
- recurrence weight 재사용과 명시적 visit graph
- CLA owner 및 `(owner, pass)` KV 계획
- CPU reference graph와 stock quant 경로
- CLI/server 및 malformed-file 검증

### 7.3 최소 런타임 계층

- versioned loader와 bounds/overflow 검사
- scalar FP32/ternary reference op
- 고정 activation/KV/scratch arena와 high-water 계측
- mmap/streaming 선택과 page residency 계측
- 동일 tokenizer와 deterministic greedy decoder
- layer checkpoint/logit dump fixture

## 8. 검증·릴리스 순서

오류 원인을 섞지 않기 위해 다음 순서를 지켜야 한다.

1. 배포 의미론과 architecture 이름을 동결한다.
2. tokenizer와 FP32 tensor round-trip을 exact 검증한다.
3. PyTorch와 scalar FP32의 layer/logit/KV 정합성을 확인한다.
4. llama.cpp FP32 graph를 통과시킨다. 이 단계 이전에는 quant 오류를 디버깅하지 않는다.
5. stock TQ1_0과 embedding/head 후보를 적용해 bpb·full-val·생성·메모리를 측정한다.
6. clean process에서 file size, peak private working set/RSS, arena high-water, TTFT, prefill/decode 속도를 측정한다.
7. x86 CPU 통과 후 Linux, Apple Silicon CPU, 필요 backend 순으로 넓힌다.
8. upstream llama.cpp에 반영되고 일반 배포 runtime에서 지원되는지 확인한다.
9. 그 다음 LM Studio import/load/generate/server를 검증하고 model metadata를 발행한다.

40MB 판단은 모델 파일 크기나 tensor 합이 아니라, 프로세스 시작부터 load, context 1024 prefill, decode까지의 peak를 기준으로 한다. shared page와 private page를 구분하되 제품 한계에는 사용자가 실제 부담하는 포괄 수치도 함께 제시한다.

L2/L3/LLC 상주 역시 파일 크기만으로 보장되지 않는다. 실행 코드, activations, KV, page table, 다른 프로세스와 코어가 cache를 경쟁하고 replacement가 일어나기 때문이다. `model bytes < LLC capacity`는 가능성을 높이는 조건일 뿐이다. LLC load/miss와 memory bandwidth를 측정하고, warm 반복에서 miss가 안정적으로 낮아지는지를 확인해야 “LLC 친화적”이라고 표현할 수 있다.

## 9. 주요 위험과 대응

| 위험 | 잘못된 결론 | 대응 |
|---|---|---|
| GGUF 생성만 성공 | LM Studio 호환 완료 | stock llama.cpp와 LM Studio runtime을 별도 게이트로 둠 |
| local patched llama.cpp 성공 | 일반 사용자도 실행 가능 | upstream/mainline 또는 LM Studio 제공 runtime 포함 여부 확인 |
| tensor+KV가 40MiB 미만 | 프로세스가 40MB 미만 | clean-process E2E peak 측정 |
| g256 결과 양호 | TQ1_0 품질 보장 | 실제 exporter/scale/kernel로 재평가 |
| shared weight 논리 구현 | 파일에서도 중복 없음 | physical tensor inventory와 offset/hash 검사 |
| prefill 출력 일치 | KV decode도 정상 | incremental decode와 cache on/off 교차 비교 |
| CPU 로드 성공 | 모든 backend 실용적 | backend별 정확도·속도 표를 별도 유지 |
| 모델이 LLC보다 작음 | 항상 cache resident | hardware counter와 working-set sweep으로 검증 |
| model.yaml 작성 | 미지원 architecture가 지원됨 | model.yaml은 마지막 metadata 단계로 제한 |

## 10. 의사결정안

### 권장

- 공개 배포의 canonical container를 GGUF로 정한다.
- llama.cpp의 stock `TQ1_0`을 첫 양자화 후보로 삼는다.
- `d8_g2` 또는 작은 후보로 converter/graph를 먼저 검증한 뒤 `d12_cla2_r20`을 40MB 주 후보로 평가한다.
- `d16_cla2_r20`은 38.5MiB 산술치 때문에 공개 런타임의 엄격 40MB 후보가 아니라 품질 상한·경계 대조군으로 취급한다.
- 최소 C/C++ 구동기는 폐기하지 않고 conformance oracle와 strict-memory 프로필로 유지한다.
- `TQ1_0`이 품질·메모리·속도 중 하나를 통과하지 못할 때만 custom 1.600 bpw GGML type을 검토한다.

### 지금 확정하면 안 되는 것

- TinyLM GGUF가 현재 stock llama.cpp/LM Studio에서 이미 동작한다는 주장
- `d12_cla2_r20` 또는 `d16_cla2_r20`의 40MB E2E 통과
- TQ1_0의 현재 후보 품질 통과
- Apple Silicon/GPU backend의 실용 속도
- 공개 architecture id와 metadata key의 최종 명칭

이 항목들은 P083의 구현·실험 게이트를 통과한 뒤 결정해야 한다.
