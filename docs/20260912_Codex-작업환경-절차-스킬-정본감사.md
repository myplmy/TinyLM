> 감사일: 2026-09-12  
> 범위: 세션 시작 라우팅, Codex/Claude 분리, 스킬 이식, 핸드오프 계약, `.agents`/`.codex`,

## 1. 요약 판정

이전 P8 판정은 틀린 판정이 아니라 **범위가 좁은 판정**이다. 새 Code Mode 세션에서 관찰한
`PreToolUse` 위험 쓰기 차단은 `ACTIVE_VERIFIED`다. 그러나 이를 “Codex 작업절차 전체가 문제없다”로
확대할 수 없다. 이번 의미 감사에서 다음 결함을 확인했다.

1. 결과 074·075·077·078·079 뒤 `COMPASS.md` 연쇄 갱신이 빠졌다.
2. 핸드오프 정본·스킬·생성기·검사기의 §0 표 계약이 6열·설명상 5열·3열로 갈라져 있다.
3. 최신 핸드오프는 그 중 어느 계약에도 없는 4열을 썼고 실제 Codex 검사에서 오류 2건이다.
4. 완료 WIP를 두고 시작문이 “중단 작업을 이어라”라고 해 다음 작업이 무엇인지 불명확하다.
5. WIP 도구는 표 셀에 `<br>`을 자동 삽입하지만 저장소 규약은 표 안 `<br>`을 이미 렌더링 위험으로 본다.
6. `AGENTS.md` 축약 때 삭제 절대 금지의 강도가 약해졌고 사용자 전용 cleanup 배치가 명시되지 않았다.

따라서 환경 상태를 다음처럼 나눠야 한다.

| 범위 | 현재 판정 | 근거 |
|---|---|---|
| Code Mode `PreToolUse` 위험 쓰기 차단 | `ACTIVE_VERIFIED` | 사용자가 제공한 새 세션 deny 2/2 관찰 |
| P7 파일·구문·링크·훅 정적 계약 | `STATIC_ONLY` PASS | 환경 검사 20/20 역사 증거 |
| 시작→WIP→결과 연쇄→핸드오프 의미 정합 | **PARTIAL** | 이번 감사의 계약 불일치와 실제 최신 핸드오프 오류 |
| GPU·모델·프로젝트 스모크·보호 데이터 | `NOT_RUN` | 이번 범위 밖이며 AI 실행 금지 |

이번 변경을 반영한 `.codex/check_environment.py` 재실행은 **21개 중 20개 PASS**였다. 새로
추가한 작업규약 날짜·분류 대조를 포함한 Python·PowerShell·JSON·TOML·링크·훅 mock 검사는
통과했다. 유일한 실패는 Git for Windows의 `bash.exe`가 다섯 shell 구문 검사에서
`couldn't create signal pipe, Win32 error 5`로 시작조차 못 한 기존 샌드박스 권한 오탐이다.
따라서 이는 shell 파일 구문 FAIL도, 이번 규약 검사 회귀도 아니며 **환경 종합 판정은 20/21
PARTIAL**로 유지한다. 샌드박스 밖 재실행이나 권한 상승은 하지 않았다.

## 2. 사용자가 매번 지시해야 Codex 문서를 읽는가

**아니다.** 직접 지시가 없어도 `AGENTS.md` §3이 새 세션·재개 때 다음을 강제한다.

1. 현재 사용자 지시와 `AGENTS.md`.
2. `ai_dev_tool/Codex/README.md`.
3. Codex 00과 06.
4. 열린 WIP, 최신 유효 핸드오프, COMPASS, 기준표.
5. 작업 유형에 맞는 Codex 01~08과 해당 스킬.

Codex 문서를 안 읽는 것이 아니라 **매번 전부 읽지 않고 고정 3개와 작업 관련 문서만 읽는 것**이
의도한 점진적 로딩이다. 공유 핸드오프의 레거시 Claude 경로는 역사 데이터로만 읽고 현재 환경
지침으로 실행하지 않는다.

## 3. 이전 환경 검증을 왜 훅 검증으로 축소했는가

사용자가 제시한 입력이 P8 PASS 표와 README의 `NOT_RUN` 정정 여부에 집중돼 있었다. GPT는
이를 마지막 미완료 게이트인 훅 E2E의 수용 시험으로만 읽고, 원래 상위 목적이던 **전반 작업절차
검증**을 다시 펼치지 않았다. 이는 사용자 의도를 지나치게 좁힌 GPT 판단 오류다.

P7도 파일 존재, 금지 문자열, 구문, 링크, 훅 계약 같은 정적 anchor를 검사했기 때문에 다음과
같은 **의미 불일치**를 놓쳤다.

- 생성기는 §0 3열을 만들지만 검사기는 6개 의미 열을 요구한다.
- 스킬과 정본은 둘 다 compact 절을 요구하지만 공식 Codex 자동 compact와의 연결 증거가 없다.
- 스킬 파일이 존재하고 경로가 유효해도 그 절차가 실제 최신 핸드오프에 적용됐는지는 확인하지 않았다.
- 결과 문서 존재를 COMPASS·기준표 등 연쇄 완료와 대조하지 않았다.

따라서 향후 “환경 검증”은 최소한 **발견/권한/훅**, **절차 계약**, **실제 산출물 fixture** 세 층으로
분리해야 한다. P8 훅 성공은 첫 층의 일부만 승격한다.

## 4. 지난 핸드오프 양식 감사

### 4.1 확인된 계약 분기

| 원천 | §0 계약 | compact 절 | 관측 |
|---|---|---|---|
| Codex 02 §3 | 6열: 지시·목적·필요작업·실제작업·결과 포함 | 초기 정본에는 없음 | 의미가 가장 완전함 |
| Codex 02 §8.3 | 설명은 “5열”, 실제 예시는 위 의미를 축약 표기 | 필수 | 문서 내부부터 모순 |
| `session-handoff/SKILL.md` | Codex 02 사용 | 필수 | TinyLM 어댑터 의도는 맞음 |
| `scripts/new_handoff.py` | 3열: 지시·처리 | 필수 | 정본·검사기보다 낡음 |
| Codex 핸드오프 검사기 | 6개 의미 열 요구 | 필수 | 현재 가장 엄격한 구조 검사 |
| `202609120551_HANDOFF.md` | 4열: 지시·목적·처리 | 있음 | `필요했던 작업`, `실제로 한 것` 누락 |

실제 검사 결과는 `files=1 errors=2`였고 두 오류는 §0의 `필요했던 작업`, `실제로 한 것` 열
누락이다. 검사기가 낡아서 놓친 것이 아니라 **검사기는 더 엄격했는데 작성 뒤 실행하지 않았고,
생성기와 규약이 서로 달라 사람이 임의 4열을 만든 것**이 원인이다.

### 4.2 수정 방향과 권한

과거 핸드오프는 역사 기록이라 수정하지 않는다. 새 양식은 6열 의미 계약을 명확히 채택하고
정본·생성기·검사기 fixture를 함께 맞춰야 한다. 그러나 사용자는 이번에 스킬 수정안을 승인하지
않았으므로 `session-handoff` 스킬·생성기·검사기는 **감사만 했고 수정하지 않았다**.

## 5. Claude `session-handoff`를 왜 이식했는가

Claude 원본은 첫머리에서 “TinyLM에서는 이 범용 7절 양식을 쓰지 않는다”고 명시한다. 여기서
금지 대상은 **스킬 이름이나 핸드오프 행위 전체가 아니라 범용 양식**이다. 승인된 Codex 구축안은
이를 그대로 복사하지 않고, 같은 트리거 이름 아래 TinyLM Codex 02와 `handoff/`를 사용하는
전용 어댑터로 재설계하도록 명시했다. 따라서 `session-handoff`라는 스킬이 존재하는 것 자체는
승인안과 맞는다.

이식 품질은 **부분 적합**이다.

- 적합: `.claude` 호출·7절 범용 템플릿·`AskUserQuestion` 의존을 제거하고 TinyLM Codex 02와
  Codex 전용 검사기로 연결했다.
- 부적합: 정본·생성기·검사기 열 계약을 끝까지 동기화하지 않았고, compact 절의 Codex 실제
  소비 계약을 확인하지 않은 채 이전 요구를 보존했다.

17개 Claude 스킬을 이름 단위로 대조한 결과, 저장소 전체에서 “TinyLM에서는 이 스킬 양식을
쓰지 않는다”는 저장소 전역 금지는 `session-handoff` 1개뿐이다. 다른 스킬의 “사용하지 않음”
절은 해당 스킬의 부적합한 **작업 유형**을 나열한 negative trigger이지, TinyLM에서 스킬 자체를
금지한다는 선언이 아니다. Codex 17개 `SKILL.md`는 Claude 원본과 모두 다른 해시이며 단순 복사본은
아니지만, 이것이 의미 정합을 보증하지는 않는다.

## 6. `.agents`와 `.codex`의 역할과 우선순위

두 폴더는 승인된 구축안과 공식 Codex 계약에 따라 의도적으로 나뉘었다.

| 위치 | 역할 | Codex 네이티브 여부 |
|---|---|---|
| `.agents/skills/**` | 작업 유형별 지침·선택적 번들 스크립트 | 공식 저장소 스킬 발견 위치 |
| `.agents/project.json` | TinyLM 스킬들이 읽는 프로젝트 고유 메타데이터 | **사용자 정의**, 네이티브 config 아님 |
| `.codex/config.toml` | `project_doc_max_bytes` 등 Codex 네이티브 프로젝트 설정 | 네이티브 |
| `.codex/hooks.json`, `.codex/hooks/**` | Codex 이벤트 훅과 guard | 네이티브 |
| `.codex/check_environment.py` | 위 분리 계약의 저장소 자체 검사 | 프로젝트 도구 |

공식 문서는 Codex가 저장소 스킬을 `.agents/skills`에서 찾는다고 설명한다:
<https://learn.chatgpt.com/docs/build-skills>. 설정과 훅은 각각
<https://learn.chatgpt.com/docs/config-file/config-reference>, <https://learn.chatgpt.com/docs/hooks>가
소유한다.

“어느 폴더가 우선인가”라는 단일 순위는 없다. `.codex`는 런타임 설정·훅으로 **발견과 실행을
통제**하고, `.agents`는 선택된 작업 절차의 **내용**을 제공한다. 같은 키를 병합하는 경쟁 관계가
아니므로 한쪽으로 통합하면 공식 경로 또는 프로젝트 메타데이터 역할이 섞인다. 현재 분리를
유지하는 것이 맞다.

## 7. `AGENTS.md` 축약 안전감사

현재 파일은 14,076바이트이고 `.codex/config.toml` 한도는 32,768바이트라 **18,692바이트 여유**가
있다. 공식 문서도 합산 지침이 `project_doc_max_bytes`에 도달하면 이후 파일을 더하지 않으며 기본이
32 KiB라고 설명한다: <https://learn.chatgpt.com/docs/agent-configuration/agents-md>.

축약 전 기록과 대조해 하나의 실질적 약화를 찾았다.

| 항목 | 축약 전·Codex 00 | 현재 `AGENTS.md` | 판정 |
|---|---|---|---|
| 삭제 | 어떤 파일도 삭제하지 않고 삭제 권한도 요청하지 않음 | 삭제·정리에 사용자 승인을 받는 일반 규칙 | **영구 경계 약화** |
| cleanup 배치 | 사용자가 직접 실행 | 배치명이 명시되지 않음 | **반복 사고 방지 문구 누락** |

권장 추가문은 다음 두 줄이며 UTF-8 약 267바이트다.

```text
- Codex는 어떤 파일도 삭제하지 않으며 삭제 권한도 요청하지 않는다. 삭제 후보는 사용자에게 정확한 목록과 근거만 보고한다.
- run_cleanup_checkpoints.bat 실행은 사용자 전용이며 Codex는 실행하지 않는다.
```

이를 추가해도 총 약 14.3 KiB로 현재 한도 안이므로 **인식 크기 증가는 0바이트**다. 매 요청의
추가 context 비용은 한글 토큰화에 따라 달라지지만 대략 60~100 tokens 수준이다. 안전경계는
매 프롬프트 필요한 정보라 이 비용이 타당하다. 다만 이번 요청은 감사·보고이므로 `AGENTS.md`
실제 수정은 별도 사용자 승인 대상으로 남긴다.

## 8. autoContextCompact와 핸드오프의 compact 절

공식 설정에는 자동 압축을 일으키는 `model_auto_compact_token_limit`과 압축 프롬프트를 직접
덮어쓰는 `compact_prompt`가 있다. 공식 훅에는 수동·자동 trigger를 구분하는 `PreCompact`와
`PostCompact`가 있다. 그러나 저장소 핸드오프의 임의 Markdown 절인 `## compact 프롬프트`를
Codex가 특별 입력으로 찾아 읽는다는 계약은 없다.

따라서 다음은 **공식 문서로부터의 추론**이다. 그 절이 현재 대화 context에 이미 포함돼 있으면
일반 텍스트로 간접 영향을 줄 수는 있어도, 자동 compact 전용 입력으로 보장되지는 않는다.
확실한 제어점은 config의 `compact_prompt`와 compact hook이다.

핸드오프에서 compact 절을 제거한다면 가장 유용한 대체 항목은
`정본 동기화·미갱신 사유`다. 결과·계획·기준표·방법론·COMPASS 각각에 실제 diff 또는 미갱신
이유를 적으면 이번 COMPASS 누락을 직접 방지한다. 다만 Codex 02·스킬·생성기·검사기 동시 수정은
사용자 승인 전 수행하지 않는다.

## 9. 조치 우선순위

1. **완료:** 승인되지 않은 WIP 스킬·스크립트 변경을 원복하고 오류원장·재발방지 제안서에 기록.
2. **이번 지시로 조치:** COMPASS의 이미 완료·실패한 결과 축을 현재 결과 문서와 정합.
3. **이번 지시로 조치:** 규약 두 판의 날짜·분류 개수와 환경 검사기 검증 추가.
4. **승인 필요:** WIP 6열 v2, 핸드오프 6열 정본, compact 절 교체, 생성기·검사기·스킬 동시 수정.
5. **승인 필요:** `AGENTS.md`의 삭제 절대 금지와 cleanup 사용자 전용 두 줄 복원.

이번 감사에서 `.agents/skills/**`, 관련 번들 스크립트, 과거 핸드오프는 수정하지 않았다.
