### 3:4 준정형 삼진 (Sherry) — **★2026-07-31 전면 개정**(결과 016 §7)

> **이전 판의 서술 3건이 틀렸다.** 논문 원문(arXiv:2601.07892)과 실측(`diag_sparse34.py`)으로
> 정정한다. **이름의 "희소"부터 오해를 부른다.**

**논문이 실제로 말하는 것** — *Sherry: Hardware-Efficient 1.25-Bit Ternary Quantization via
Fine-grained Sparsification* (arXiv:2601.07892, Tencent AngelSlim).
연속 4-가중치 블록마다 **정확히 3개를 비영(±1), 1개를 0** 으로 고정 →
`N_perm = C(4,3)·2³ = 32 = 2⁵` 로 **5비트를 빈틈없이 포화**시켜 **power-of-two 정렬을 회복**한다.
- **문제의식은 메모리가 아니라 정렬·속도다.** 기존 삼진은 ① 2비트 정렬 패킹(비트 낭비) 또는
  ② 1.67비트 비정형 패킹(**정렬이 깨져 추론이 느려짐**) 중 하나를 골라야 했다.
- **보고 이득: 비트 25% 절약 + 속도 10%**(LLaMA-3.2 1B, Intel i7-14700HX, 정확도 손실 0).
  **25% 는 1.67bpw 대비**다(1.67 × 0.75 ≈ 1.25).
- **Arenas = annealing residual synapse.** 3:4 를 그냥 씌우면 **weight trapping**
  (gradient 균질화 → 가중치 국소 축적 → representational collapse)이 난다고 논문이 명시하고,
  그 대응으로 도입한 **별도 메커니즘**이다.

**우리 문서가 틀렸던 곳**

| # | 이전 서술 | 실제 | 근거 |
|---|---|---|---|
| 1 | "현 **1.95** 대비 **×1.56** 추가절감" | 1.95 는 **논문에 없는 숫자**(Bonsai/PrismML 출처를 섞었다). 동일 회계 실측 절감은 **15~18%** | 016 §7.4 |
| 2 | "**25% 강제-0 의 용량손실**" | **방향이 반대.** 우리 표준 TWN 경로는 이미 **43~46% 가 0** 이고, 3:4 는 0 을 **25% 로 줄인다** | 016 §7.2 |
| 3 | "Arenas = **우리 삼진 어닐의 특수형**(이미 보유)" | **근거 없는 동일시.** 우리 `quant_anneal` 은 STE 위 어닐 계수이고 residual synapse 가 아니다. **우리는 대응책 없이 3:4 를 씌웠다** | 016 §7.5 |

# ★★M.3 왜 L2+L3 탑재에 실패했나 — **원인 분해** (2026-08-19)

## M.3.1 목표와 현재

| | 크기 |
|---|---|
| 데스크톱 CPU L3 (이 프로젝트 판정 기준) | **32 MB** |
| L2 (코어당 1~2MB × 8) | 약 8~16 MB |
| **합계 목표** | **약 40 MB** |
| ★**현재 최선 상주(fp32)** | ★**323 MB** = 목표의 **8.1배** |
| ⚙현재 최선 상주(int8) | 70.4 MB = 목표의 **1.8배** |
| 현재 최선 저장(packed) | **9.6 MB** = ✅**목표 안** |

## M.3.2 ★원인 넷 — **크기 순**

| # | 원인 | 크기 | 상태 |
|---|---|---|---|
| **1** | ★★**상주식에 bpw 가 없다** — 삼진을 **fp32 로 들고 계산**한다 | **×32**(1.71bpw → 32bit 2벌 = 64bit) | 🚫**LUT 커널 없이는 못 고친다** |
| **2** | **fp32 2벌**(latent + dequant 사본) | ×2 | ⏸ **P034 단계2**(`drop_latent`) — 구현됨, **긴 런 검증 미완** |
| **3** | ★**임베딩 33 MB 가 fp32** | int8 상주 86.94 중 **33.0 MB = 38%** | 🚫**설계 미완**(헤드가 임베딩과 tie) |
| **4** | 활성·KV 캐시 | KV 7.5 KB/token → 1024ctx **7.5 MB** | 부차적 |

### ★원인 1 이 전부다 — 산술

```
mC_wsd 유니크 삼진 54.85M
  packed(1.71 bpw)             =  11.2 MB   ← 파일 크기
  fp32 1벌                     = 219.4 MB   (×19.6)
  fp32 2벌(현 구현)             = 438.8 MB   (×39.2)
  int8 1벌 + α                 =  54.9 MB   (×4.9)
```

> ★★**저장과 상주가 39배 벌어져 있고, 그 39배 전부가 "계산하려면 풀어야 한다" 에서 온다.**
> **1.71bpw 로 저장하는 기술은 우리에게 있고, 1.71bpw 상태로 곱하는 기술이 없다.**

## M.3.3 ★★그래서 유일한 길은 **LUT 커널**이다

`docs/methods/02_memory.md` 가 **2026-08-07 부터 "💡최우선"** 으로 적어 둔 그 항목이다:

| 물건 | 무엇을 해결하나 | 상태 |
|---|---|---|
| ★**T-MAC**(arXiv:2407.00088) | mpGEMM 을 **역양자화 없이** LUT 로 → **원인 1 을 없앤다** | 🚫**미착수** |
| ★**bitnet.cpp I2_S**(arXiv:2502.11880) | Int2+Scale **무손실**, shape 무관 | 🚫**미착수** |
| ~~`_weight_int8pack_mm`~~ | int8 GEMM. **삼진을 모르고** 실측 **6.5배 느렸다** | 🚫**종결**(028 §12·§13) |

### ⚙LUT 커널이 들어오면 얼마인가 (계산)

```
m100R1q 기준
  삼진 packed          9.6 MB   (LUT 는 이 상태로 곱한다)
  임베딩 fp32         33.0 MB   ← ★남는다
  기타                 0.2 MB
  ------------------------------
  상주 합계          약 42.8 MB   → L2+L3(약 40MB) **경계**
```

> ★★**LUT 커널만으로도 아직 목표를 못 넘는다 — 임베딩 33 MB 때문이다.**
> **두 개를 같이 해결해야 40MB 안에 들어간다.** 지금까지 우리는 **둘 다 안 했다.**

## M.3.4 ⚠️그리고 **한 번도 안 잰 것** — 실제 캐시 거동

우리가 쓰는 "상주" 는 전부 **`report()` 의 회계값**이다.
🚫**실제 L2/L3 히트율·작업집합·캐시 미스는 한 번도 측정하지 않았다.**

| 우리가 아는 것 | 우리가 모르는 것 |
|---|---|
| 파라미터 바이트 합계 | **동시에 살아 있는 작업집합**(타잉이면 한 번에 MLP 1벌만 필요할 수 있다) |
| 이론 L3 판정(`상주 < 32MB × 0.7`) | **실측 캐시 미스율** |
| int8 감속 −62~67%(CPU, 결과 014) | 그 감속이 **캐시 때문인지 언팩 때문인지** |

> ★**타잉의 숨은 이점이 여기 있을 수 있다** — g8 이면 **같은 MLP 를 8층 연속 재사용**하므로
> **작업집합이 유니크 개수만큼**이다. `report()` 는 그걸 못 본다.
> **그러나 우리는 그것을 측정할 도구가 없다.**
