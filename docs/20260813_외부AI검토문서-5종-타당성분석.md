### 1.2 🚫 최우선 제안이 틀렸다 — **우리 데이터가 상한을 준다**

문서 1순위 = **"학생 ternary quantization 캐시"**(§2·§5·§23, 예상 **10%+**).

★**P042 가 이미 상한을 실측했다.** 부하를 파라미터×호출수로 환산하면:

```
교사 refresh_quant = 123.86M 유니크삼진 × 16 micro-batch × 0.25(kd_every 4) = 495M / 스텝
학생 refresh_quant =  54.85M            × 16                                = 877M / 스텝
                                                                    비율 = 1.77배
```

**P042 는 교사의 495M/스텝을 통째로 없앴고**(`freeze_quant`), **속도 효과는 "측정 불가"** 였다
(effect +1.95%, drift 1.37%, |drift|/|effect| = 0.69 → 결과 034 §9).

> ★**따라서 학생 쪽 상한은 약 3.5%**(교사보다 학생 쪽이 autograd 그래프를 만들어 다소 비싸므로
> **넉넉히 5%** 로 잡아도) 이고, 문서의 **10%+ 는 최소 2배 과대**다.

**그리고 VRAM 이득은 0 이거나 음수다.** `_wq` 는 어차피 한 벌만 산다. 캐시하려면
`retain_graph=True`(그래프 전체 보존 → **VRAM 폭증**) 또는 커스텀 STE 누적이 필요하다.

| | 문서 | **우리 데이터 기준** |
|---|---|---|
| 속도 | 10%+ | **≤ 5%** |
| VRAM | 언급 | **0 또는 음수** |
| 위험 | "주의" | **STE 의미·비트동일성 파괴. 高** |

🚫 **판정: 최하위.** 같은 노력이면 **L5(KD 손실 청크, −2~3 GiB)** 가 크고 **위험이 없다**.

### 1.3 🚫 이미 답이 난 것

| 제안 | 판정 |
|---|---|
| **offline KD cache**(§19~20) | 🚫 **P015 에서 하고 기각**(결과 004 "부적합"). 문서가 모른다 |
| **top-k online KD**(§21) | ⚠️ 방향은 살아 있으나 **L5(청크)가 수학적으로 등가**라 품질 위험 0 이다. **top-k 는 근사이고 청크는 아니다** — 문서는 위험한 쪽만 제안한다 |
| `--kd-teacher-infer` 를 최우선으로(§18) | ✅ **이미 구현·측정 완료**(결과 034 §9: VRAM −0.48 GiB alloc, 속도 측정 불가) |

### 1.4 ✅ 값어치가 있는 것 — **T-1**

**eval/checkpoint 를 `ms/step` 타이밍에서 분리**(§11~14).
평균 오염은 1~2%로 작지만, **세션 드리프트 7.5% 를 발견한 지금**(결과 037 §11.4)
계측을 정직하게 만들 값어치가 올라갔다. **측정 전용이라 학습 무영향.**

## 2. 문서 B — 학습 VRAM

### 2.1 🚫 "최우선 코드 검토" 대상이 **죽은 코드다**

`aw` = 54.85M × 4B = **219 MB**, 한 벌. **문서가 걱정한 4텐서 저장은 우리에게 없다.**

### 2.2 ⚠️ 우리 실측과 충돌하는 것 2건

| 문서 주장 | 우리 실측 |
|---|---|
| **"no-checkpoint 는 유지한다"**(§16) | ⚠️ `--no-ckpt` 는 tied+KD 에서 **표준이 아니다**(여유 0.62 GiB, 결과 034 §10). 그리고 **이득 자체가 −6~−20% 로 미확정**(결과 037 §11.4) |
| **"VRAM 목표치를 8GB 로 잡으면 안 된다"**(§18) | 🚫 **`mC_initonly` 가 5.07 GiB 로 돌았다**(결과 038). **8GB 미만이 실제로 가능하다** — KD 를 빼면 |
| **"initialization SVD 우선순위 낮다"**(§19~20) | 🚫 **틀렸다.** 결과 030 §9 가 **초기화 핸디캡 0.1123**(1차 델타의 63.5%)을 드러냈다 |

## 3. 문서 C — FlashAttention

### 3.1 ✅ 코드로 확인: **이미 SDPA(Level 1). 학습 경로는 Flash 적격**

`modules.py` `Attention.forward`:

```python
if q_len == kv_len:                      # 학습·prefill
    o = F.scaled_dot_product_attention(q, k, v, is_causal=True)
else:                                    # KV 캐시 추론
    o = F.scaled_dot_product_attention(q, k, v, attn_mask=mask)
```

| 조건 | 상태 |
|---|---|
| SDPA | ✅ Level 1 |
| dtype | ✅ bf16(autocast + `apply_rope`·`RMSNorm` 이 `.to(x.dtype)`) |
| `head_dim` | ✅ **64** |
| 마스크 | ✅ **학습은 `is_causal=True`** — Flash 적격. `attn_mask` 는 **추론 전용** |

→ **문서 §21 Case C("이미 사용 중")가 가장 유력**하고 그러면 **속도 이득 0** 이다.
Level 2/3 검증은 1분이므로 **질문을 닫는 값어치**는 있다.

### 3.2 ★★문서가 놓친 것 — **GQA `repeat_interleave` (F-1)**

```python
n_rep = c.n_q_heads // c.n_kv_heads      # 12 / 3 = 4
if n_rep > 1:
    k = k.repeat_interleave(n_rep, dim=1)   # (B,3,T,64) -> (B,12,T,64)
    v = v.repeat_interleave(n_rep, dim=1)
```

**K·V 를 4배로 물리 복제해 SDPA 에 넘긴다.** torch 2.5+ 는 `enable_gqa=True` 로 복제 없이 처리한다
(우리는 **torch 2.10**).

**회계**: 복제 후 k = `8×12×1024×64×2B` = 12.6 MB, k+v = 25.2 MB, **× 20층 ≈ 0.5 GB**
(backward 를 위해 살아 있다). **GQA 의 존재 이유가 KV 를 3배 줄이는 것인데 어텐션 직전에 되돌린다.**

| | 기대 |
|---|---|
| VRAM | **약 −0.4 ~ −0.5 GiB** |
| 코드 | **3줄** |
| ⚠️ 위험 | `enable_gqa=True` 가 **Flash backend 를 유지하는지 확인 필요**. 수치 비트 동일 아닐 수 있다 |

### 3.3 문서 자체의 문제

- §8 이 *"GQA/CLA 때문에 Flash 가 거부되는가"* 를 걱정하는데 **학습은 `is_causal=True` 라 무관**하다.
  거부되는 것은 **추론 경로**다.
- **분량 대비 산출이 낮다**(23KB, 24절). §1~3 확인은 **코드 5줄**로 끝난다.

## 4. 문서 D — KV 캐시 효율화 **(신규 검토)**

### 4.1 ✅ 전제가 정확하다 — **가장 잘 쓴 부분**

> *"m100 은 GQA + CLA 로 이미 MHA 대비 **8×** 줄인 상태다. DeepSeek-V2 MLA 가 MHA 대비 보고한
> 감소율을 그대로 적용해서는 안 된다. m100 에서 MLA 는 **2차 압축**이다."*(§3)

★**이 문단이 이 문서 5종 전체에서 가장 값어치 있는 한 문단이다.**
`30,720 / 3,840 = 8×` 산술도 우리 `report()` 와 일치한다(`kv_dim=192`, owner 10/20층).
**"논문 감소율을 우리에 그대로 쓰지 말라" 는 것이 이 저장소의 함정 2·12 와 같은 규율이다.**

### 4.2 🚫 그런데 P0 제안이 **이미 절반 달성돼 있다**

문서 **P0 = "FP16 KV(2× 저장량 감소)"**. 그런데:

- `report()` 는 이미 **KV 를 2바이트로 회계**한다(`kv_kb = n_kv*2*kv_dim*2/1024`, `transformer.py` 548줄)
  → *"KV 캐시 7.5 KB/token"*. **문서의 "FP32 15.0 KiB" 는 우리 회계와 다르다.**
- `generate.py` 는 `torch.autocast(bfloat16, enabled=(dev_type=="cuda"))` (94줄)
  → **GPU 추론은 이미 bf16 캐시**다.

★★**그러나 CPU 는 autocast 가 꺼진다 → fp32 캐시 = 15 KB/token.**
**그리고 CPU 가 우리 배포 타깃이다**(`CLAUDE.md` 첫 줄).

> ★★★**즉 진짜 발견은 문서의 P0 가 아니라 이것이다:**
> **`report()` 의 "KV 7.5 KB/token" 은 GPU 기준이고, CPU 배포에서는 15 KB/token 이다.**
> **회계 문서와 배포 현실이 2배 어긋나 있다.** 함정 1(저장≠상주)·24(fp32≠int8)의 **KV 판**이다.
>
> → **조치는 "FP16 KV 도입"(문서)이 아니라 "회계에 경로를 명시"(우리)이고, 그다음이
> "CPU 경로에서 KV 를 bf16 으로 유지"** 다. **후자는 실제 레버이고 문서 P0 와 결론이 같다** —
> 다만 **이유와 크기가 다르다.**

### 4.3 방법론별 판정 — 참고문헌 **실제 확인함**

| 방법 | 문서 권장 | **우리 판정** |
|---|---|---|
| FP16 KV | **P0** | ⚠️ **GPU 는 이미 됨 / CPU 는 실제 레버**(§4.2). 회계 정정이 선행 |
| INT8 KV | **P0** | ⚠️ **결과 016 §12.3 이 이미 관련 수치를 갖고 있다** — CUDA int8 언팩 −12~15%, **CPU −62~67%**. KV 는 가중치와 다르지만 **CPU 에서 dequant 가 비싸다는 사실은 같다.** 배포 타깃이 CPU 이므로 **속도 대가를 먼저 재야 한다** |
| INT4 KV | P1 | 🚫 우선순위 없음. INT8 도 안 쟀다 |
| **GTA-like**(arXiv:2506.17286 ✅**실재 확인**) | P2 | ⚠️ **아키텍처 변경 = 재학습.** 우리 예산에서 3.5h × 여러 번. **그리고 P049(깊이)·P046(임베딩)이 먼저다** |
| **MLA-lite r=128/96** | P3/P4 | 🚫 **2차 압축이라 이득이 1.4~1.7× 뿐**이라고 문서 자신이 적었다(§9). **재학습 비용 대비 낮다** |
| **TransMLA**(변환) | P5 | 🚫 변환 후 healing 필요 = 재학습 |
| **CARE**(arXiv:2603.17946 ✅**실재 확인** — "Covariance-Aware, Rank-Enhanced MLA conversion") | P6 | 🚫 문서가 "구현 난이도 매우 높음" 이라 적었고 동의 |
| SVDq / TurboQuant | P7/P8 | 🚫 |
| **Kimi Linear**(arXiv:2510.26692 ✅**실재 확인**) | P9 | 🚫 **P004 에 이미 계획이 있고 미착수**다. `modules.py` 주석이 *"KV-bank 오케스트레이션도 함께 일반화해야 한다"* 고 이미 경고한다 |

**참고문헌 검증**: 의심스러운 4건을 **실제 조회**했다 —
`2603.17946`(CARE) ✅ / `2506.17286`(GTA) ✅ / `2510.26692`(Kimi Linear) ✅ /
`2606.06574`("Skip a Layer or Loop It?") ✅ **전부 실재**한다.
나머지(KIVI 2402.02750, DeepSeek-V2 2405.04434 등)는 널리 알려진 것과 일치한다.
→ **이 문서들의 참고문헌 신뢰도는 높다.**

### 4.4 ⚠️ 문서 D 의 가장 큰 맹점 — **KV 는 우리 병목이 아니다**

문서는 KV 를 27KB 분량으로 다루는데, **우리 실측 상주 분해**는 이렇다(결과 016·030):

| 항목 | 크기(mC, int8 배포) |
|---|---:|
| 삼진 가중치 | 약 54 MB |
| **임베딩(`emb.weight`)** | **32.0 MB** |
| 기타 | 약 1 MB |
| **KV 캐시 (1024 ctx)** | **7.5 MB** |

★**1024 컨텍스트에서 KV 는 상주의 8% 다.** 4K 컨텍스트라야 30 MB 로 임베딩 급이 된다.
**문서는 "컨텍스트가 길어지면" 을 전제하는데 우리 `max_seq_len` 은 2048 이고
학습은 1024 다.** → **KV 압축은 "긴 컨텍스트를 지원하기로 결정한 뒤" 의 문제다.**

## R1. ⚠️ 초판에서 **내가 틀린 것 2건**

### R1-a. 🚫 *"quant cache 의 VRAM 이득은 0 이거나 음수"* — **틀렸다**

초판 §1.2 는 *"`_wq` 는 어차피 한 벌만 산다"* 를 근거로 VRAM 이득을 0 으로 봤다.
**`_wq` 를 봤지만 `save_for_backward` 를 안 봤다.**

```python
# tinylm/model/ternary.py  _TernarySTE.forward
ctx.save_for_backward(aw, alpha)      # ← aw 는 weight 크기다
```

`aw = |W|` 는 **가중치와 같은 크기**이고 backward 까지 살아 있다.
유니크 삼진 54.85M × 4B = **약 219 MB**. 문서 A §20·문서 B §11 이 제안하는
**"`aw` 를 저장하지 말고 backward 에서 `abs(W)` 로 재계산"** 은 그만큼을 실제로 없앤다.

| | 초판 | **정정** |
|---|---|---|
| 속도 | ≤ 5% | ≤ 5% (**유지** — P042 상한 논증은 여전히 유효) |
| VRAM | **0 또는 음수** 🚫 | ★**−0.2 GiB 수준**(실측 필요) |

⚠️ 단 **−0.2 GiB 는 KD 손실 5.48 GiB 의 4%** 다. **순위는 안 바뀐다**(여전히 하위).
**틀린 것은 순위가 아니라 근거**다.

### R1-b. 🚫 *"문서 5종 중 문서 E 는 우리 로드맵과 겹친다"* — **부정확**

초판 §5.2 는 문서 E 를 *"방향은 우리 로드맵과 정확히 겹친다"* 로 정리했다.
**전문을 읽으니 겹치지 않는 것이 하나 있고, 그게 가장 중요하다** — §R5.

## R2. 문서 A(trainer) 전문 재검토 — **주장이 사실이다**

### R2.1 ✅ 코드 확인: **스텝당 16회 재양자화가 맞다**

```python
# tinylm/model/transformer.py  forward()
if not self._quant_frozen:
    self.refresh_quant()          # ← 조건이 이것뿐이다. micro-batch 마다 돈다
```

`_quant_frozen` 은 **추론 전용**이고 학습 중엔 항상 False.
→ `steps 2289 × accum 16 = 36,624`회. 문서가 계산한 숫자와 **정확히 일치**한다.

### R2.2 ✅ 설계도 옳다 — **`_wq` 재사용은 실제로 금지다**

문서 §4·§27①: *"`_wq` 를 16회 backward 에 재사용하면 graph 재사용 오류,
`retain_graph=True` 로 우회하면 VRAM 폭증"*. **맞다.** `_wq = wq + (1-anneal)*(w-wq).detach()`
는 autograd 그래프를 달고 있다. 문서의 **"무거운 통계는 1회, 그래프는 micro 마다 새로"**
분리는 정확한 해법이다.

### R2.3 ⚠️ 그래도 **상한 논증은 유지된다**

P042 가 **교사의 495M/스텝 재양자화를 통째로 없앴는데 속도 효과가 측정 불가**였다
(effect +1.95% vs drift 1.37%, 결과 034 §9). 학생 몫은 그 1.77배이므로 **≤ 5%** 다.
문서의 **10%+ 는 여전히 최소 2배 과대**다.

> ★**따라서 판정은 "틀렸다" 가 아니라 "작지만 실재하고, 공짜가 아니다"** 로 바뀐다.
> → **신규 계획 P056** 으로 등재 제안(§R8).

### R2.4 초판이 놓친 문서 A 의 유효 제안 2건

| 제안 | 판정 |
|---|---|
| **§22 eval 과 checkpoint 저장 주기 분리**(`eval_every` 100 / `save_every` 500) | ✅ **타당하고 값싸다.** 지금은 eval 마다 model+optimizer 를 통째로 저장한다. `--save-every` 추가는 소 |
| **§25 `mb=8, seq=1024` 를 먼저 바꾸지 않는다** | ✅ **문서가 우리 결과 007(무릎 M=8192)을 정확히 인용**했다. 외부 문서 중 **우리 데이터를 옳게 쓴 유일한 사례** |

## R4. 문서 D(KV) 전문 재검토 — **산술을 검산했다**

### R4.1 ✅ KV 회계가 맞다

```
head_dim = 768/12 = 64
owner 당 K+V = 3 × 64 × 2 = 384 scalar/token
owner 수 = 20 / cla_group 2 = 10
합계 = 3,840 scalar/token → fp32 15.0 KiB/token
```

★**우리 `report()` 인쇄와 일치한다** — 결과 040 로그의 dense(cla=1, 20 owner)가
*"KV 캐시 15.0 KB/token (20/20 층만 소유)"* 를 찍었고, tied(cla=2, 10 owner)는 그 절반.
**문서 D 는 우리 코드를 정확히 읽었다.**

### R4.2 ✅ MLA-lite r=128 의 파라미터 등식도 맞다

`2,304 × 128 = 294,912 = 768 × 192 × 2`. **검산 통과.**
cache 는 `128 + 12×8 = 224` vs 현재 384 → **41.7% 추가 감소**. 산술 정확.

### R4.3 ⚠️ 그런데 초판 §4.4 의 판정은 유지 — **KV 는 우리 병목이 아니다**

`report()` 기준 1K 컨텍스트 KV = **7.5MB**(tied), 상주 가중치는 **451.5MB**.
**KV 는 상주의 1.7%** 다. 문서 D 가 9단계 로드맵(P0~P9)을 제안하는데
**그 전부가 1.7% 를 대상으로 한다.**

> ★**문서 D 의 진짜 값어치는 로드맵이 아니라 §16(CPU 적합성)과 §29~31(평가 규약)이다.**
> 특히 §30 *"한 번에 하나의 축만 바꾼다"* 와 §31 *"2~3 시드"* 는 **우리 함정 2·σ 규약과 동일**하다.

### R5.1 ★초판이 놓친 것 — **문서 E §9 "Attention Sharing"**

> 문서 E §9: *"현재 TinyLM 은 middle MLP 를 공유하지만 **attention 은 layer 별로 독립적이다.**
> 이는 상당한 parameter reuse 여지를 남긴다. ... **Full-block sharing 전에 Attention-only
> sharing ablation 을 반드시 권장.**"*

★★**이것은 REVIEW2 §5.2 가 독립적으로 도달한 결론과 정확히 같다** —
*"삼진 54.85M 중 어텐션이 48.4%인데 어텐션은 타잉 대상이 아니다. MLP 축은 소진됐고
어텐션 축은 손도 안 댔다."*

> **초판은 문서 E 를 *"우리 로드맵과 겹친다"* 로 넘겼는데, 겹친 게 아니라 그쪽이 먼저 지목했다.**

### R5.2 ✅ 문서 E 의 설계 원칙 3개는 **채택 가치가 높다**

## R6. ★사용자 지시 (9) — **5비트 패킹 없이 3:4 희소의 가치를 판정할 수 있는가**

### R6.1 답: **부분적으로만 가능하고, 사용자 지적이 맞다**

| 회계 | `mA_g4s34_k4`(3:4) | `mC_g8_k4`(3:4 없음) | 출처 |
|---|---:|---:|---|
| **현행 A**(우리 packed 규약) | **11.6 MB** | 14.9 MB | 결과 016 §7.4 |
| (B) 코드+스케일 | 12.5 | — | 〃 |
| (C) B+컨테이너 | **14.6 MB** | — | 〃 |
| **fp32 상주** | 523.5 MB | **451.5 MB** | 결과 016 §1 |

★★**결정적 사실: 상주 메모리는 bpw 를 보지 않는다**(결과 016 §7.2).
상주 = 유니크삼진 × 4B × 2벌 + 나머지. **3:4 희소는 저장만 줄인다.**

> **그리고 우리는 저장 포맷으로 배포한 적이 없다.** `to_int8()`(단계3)은 **파라미터당 8비트**이고
> 이론값 1.25bpw 의 **6.4배**다. **5비트 패킹(단계4)이 없으면 3:4 의 이득이 실물로 나타나는
> 지점이 아예 없다.**

### R6.2 ⚠️ 그런데 "그래서 단계4 를 먼저 해야 한다" 는 **결론이 자동으로 나오지 않는다**

| 논점 | 데이터 |
|---|---|
| 3:4 의 품질 대가 | **+0.035~0.056**(결과 016) — 분해능 0.024 의 1.5~2.3배 = **실재한다** |
| 3:4 가 REVIEW1 승자에 있었나 | ✅ `mA_g4s34_k4` 가 승자(결과 012) |
| 단계4 의 대상 | **삼진 코드**. 그런데 결과 032 §4 는 **상주 최대 항목이 임베딩·어텐션**이라 했다 |
| 단계4 의 비용 | 커널 필요(**`code*alpha` 를 fp32 로 되돌리면 이론값의 7.6배에서 멈춘다**) |

> ★**정직한 정리**: *"5비트 패킹 없이는 3:4 의 값어치를 **저장 축에서** 판정할 수 없다"* 는 **맞다**.
> 그러나 *"그러므로 단계4 를 지금 해야 한다"* 는 **다른 명제**다 — 단계4 는 **커널을 요구**하고,
> `custom_ternary_kernel.md` §4 가 *"우선순위 낮음"* 으로 판정한 상태다.

### R6.3 ★권고 — **단계4 를 하기 전에 "패킹 회계 시뮬레이터" 를 만든다**(GPU 0)

**커널 없이** 5비트 패킹의 **저장 크기와 언팩 비용**을 계산·계측할 수 있다:

1. 실제 체크포인트에서 삼진 코드를 **비트 단위로 패킹**해 **실제 파일 크기**를 잰다(디스크)
2. 언팩 함수를 **numpy/torch 로만** 구현해 **토큰당 언팩 비용**을 잰다(커널 없이)
3. 그 둘로 **"단계4 가 얼마를 벌고 얼마를 내는지"** 를 **학습 없이** 확정한다

→ **그 결과가 좋으면 커널을 만든다.** 신규 계획 **P034 단계3.5**(§R8) 로 제안.
★**이게 "커널 먼저" 보다 값싸고, 함정 1(저장≠상주)에 걸리지 않는다.**

### R6.4 결과 028 제목 — ✅ **갱신 완료**

*"P014C 단계0"* → **"단계0·1"** 로 고치고, §11(단계1 = **커널을 짤 필요가 없다**)이
더 큰 결론임을 헤더에 명시했다. 제목만 보고 *"단계1 은 아직"* 으로 읽히면
**커널을 짜려는 판단으로 되돌아간다.**

## R7. ★사용자 지시 (10) — **어텐션 감축 축, 실험 가치 판정**

REVIEW2 §5.2 + 문서 E §9 가 같이 지목한 축이다. **네 후보를 값어치 순으로**:

| # | 축 | 무엇을 바꾸나 | 절감(계산) | 위험 | 선결 | **권고** |
|---|---|---|---:|---|---|---|
| **A1** | ★**어텐션 타잉**(`attn_group`) | 중간 16층의 Q/O(및 소유층 K/V)를 g층씩 공유 | ★**어텐션 삼진 26.54M → g2 면 −40%, g4 면 −60%.** 총 삼진 **−19~29%** | ⚠️**중~높음.** MLP 보다 층별 특화가 클 가능성 | `config` 필드 + `transformer` 층 스케줄 (**중**) | ★★**1순위.** 남은 최대 미탐색 축이고 MLP 타잉과 **완전히 같은 기법**이라 우리 코드에 자연스럽다 |

| **A4** | **층수**(깊이) | — | — | — | — | ✅ **이미 P049 다.** 중복 |

### R7.1 ★A1 을 1순위로 두는 근거 셋

1. **크기**: 어텐션이 삼진의 **48.4%**. g2 만 해도 총 −19% 로 **`mC_g16`(−8.6%)의 2배**
2. **기법 동일성**: MLP 타잉과 **같은 코드 패턴**(`mid_mlps[j//g]`). `attn_group` 은 그 복제
3. **문헌 근거**: **MobileLLM**(`2402.14905`, ✅조회)의 *immediate block-wise weight-sharing* 이
   **정확히 이것**이고 **125M/350M 에서 +0.7%/+0.8%** 를 보고했다 — 우리 규모와 같다

### R7.2 ⚠️ 미리 적어 두는 위험

- **어텐션은 위치 의존이 강하다.** MLP 는 채널 변환이지만 어텐션은 **어느 층이냐에 따라
  보는 패턴이 다르다**(초기=국소, 후기=전역). **MLP 타잉보다 대가가 클 것으로 예상**한다
- **CLA 와 상호작용한다.** `cla_group=2` 는 이미 K/V 를 공유 중이라
  `attn_group` 이 그 위에 겹치면 **어느 것이 대가를 냈는지 못 가른다** → **`cla_group=1` 대조 필요**
- **부모초기화**: 교사(dense)는 층마다 독립 어텐션이다 → **평균 이식**이 필요하고,
  그건 `mid_mlps` 의 그룹 평균과 같은 형태라 **기존 코드 패턴 재사용 가능**

> ★**사용자 확인 후 신규 계획으로 등재 제안**: **P057 `attn_group` 어텐션 타잉**
> (단계0 = 계산·프리셋, 단계1 = g2, 단계2 = g4, 대조 = `cla_group=1`).
