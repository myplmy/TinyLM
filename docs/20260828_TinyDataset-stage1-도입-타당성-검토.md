## 0. 결론 세 줄

> 1. 🚫**학습 데이터로는 쓸 수 없다.** train 전체가 **124,628 바이트 ≈ 28.5K 토큰**이고,
>    우리 표준 런은 **300,000,000 토큰**이다 — **0.0095%** 다. 100M 파라미터를 900 문장에 맞추면 암기다.
> 2. ✅★**held-out 300 은 값어치가 있다.** 우리에게 **한국어 의미 벤치마크가 하나도 없다.**
>    🚫**단 명세가 설계한 "자유생성 + 문자열 채점" 으로는 안 된다** — 결과 050 이 그 길이 **전부 0** 임을 실측했다.
> 3. ★★**가장 값싸고 확실한 채택안은 명세에 없다** — **train+val 1,000 문장을 `paired_eval` 의
>    CE 프로브로 쓰는 것**이다. 구현이 거의 0 이고, 우리가 지금 못 재는 것(한국어 의미 문장 우도)을 잰다.

## 1. 실사 — 파일이 실제로 무엇인가

| | train | val | held-out |
|---|---:|---:|---:|
| 레코드 | **900** | 100 | **300** |
| 텍스트 바이트 | **124,628** | 14,231 | 88,504 |
| 평균 문자 | 51.2 | — | prompt 26.3 / answer 34.0 |
| 형식 | `{"text": ...}` | 동 + 메타 | `{id, split, task, prompt, answer, key_relations, difficulty}` |

held-out 구성: `split` = unseen_concept **150** / novel_relation **90** / boundary **60**,
`task` = identity **150** / relation **90** / counterexample **60**, `difficulty` 1~4(117/139/38/6).

명세는 잘 쓰였다 — **train/val/held-out 3분할**, **외부 LLM judge 배제**, **2점 관계 단위 채점**,
**금지 관계로 과잉 일반화 감지**, **누수 방지 규칙**이 모두 명시돼 있다. 원칙에는 이견이 없다.

## 2. 🚫★★결함 — **일곱 가지. 전부 파일과 우리 실측으로 확인했다**

### F1. 규모가 학습 데이터의 1만분의 1 이다

```
train 124,628 바이트 ÷ 4.37 bytes/token ≈ 28,500 토큰
표준 런                                  300,000,000 토큰
                                         → 0.0095%
```

100 에폭을 돌려도 **2.85M 토큰 = 0.95%** 다. 그리고 **900 문장 vs 63.5M 파라미터**는
일반화가 아니라 **암기**다. 🚫**"Stage 1 학습 데이터" 라는 명세의 전제가 우리 조건에서 성립하지 않는다.**

### F2. ★**관계 어휘가 폭발해 있다 — 결정적 채점기를 못 만든다**

명세 §12 는 **정규 관계표 8종**(`is_a`·`not_is_a`·`part_of`·`inside`·`above/below`·`same_category`·`state`)을 제안한다.
**그런데 실제 데이터의 `key_relations` 는 약 130 종**이고 대부분 **1회짜리**다:

```
is_a 85 · not_is_a 31 · abstract_concept 28 · part_whole 7 · attribute_independence 7 ...
그리고 single-occurrence 라벨 약 100 종:
  same_subject_not_same_representation, absence_of_observation_not_nonexistence,
  spatial_containment_vs_part_whole, single_failure_not_impossibility, ...
```

🚫**관계마다 표층 패턴을 써야 하는데 라벨이 130 종이고 N=1 이 100 종이다.**
패턴을 쓸 수도 없고, 관계별 통계도 의미가 없다. **명세 §12 와 데이터가 서로 다른 물건이다.**

### F3. ★**명세의 가장 좋은 아이디어가 데이터에 없다**

명세 §13 의 **`forbidden_relations`**(과잉 일반화 감지)는 **held-out 레코드에 존재하지 않는다.**
실제 키는 `answer · difficulty · id · key_relations · prompt · split · task` 뿐이다.
→ 🚫**채점기의 핵심 장치가 미구현 상태로 배포됐다.**

### F4. 🚫★★**자유생성 채점은 우리 모델에서 전부 0 이다 — 이미 실측했다**

명세 §8~§16 은 **모델이 답을 생성하고 문자열을 정규화해 채점**하는 설계다.
우리 저장소는 그 길을 **이미 걸었고 결과를 갖고 있다**:

| 근거 | 내용 |
|---|---|
| `docs/methods/10_benchmarks.md` §1 | **생성 채점(EM/F1/pass@k) = 🚫전부 0.** SFT 없이는 무의미 |
| `scripts/eval_korean_bench.py` 머리말 | *"우리 모델은 100M 급 base LM 이고 SFT 를 한 적이 없다. 지시를 안 따른다. EM/F1 은 전부 0 이 나오고, **0 은 모델 간 서열을 못 만든다**"* |
| KorQuAD 2.0 논문 | BERT-multilingual **F1 46.0%**(사람 85.7%) — 그보다 **6배 작고 SFT 없는** 우리 모델 |

★**우리가 재려는 차이는 0.0034~0.0157 nats 다.** 전부 0 인 지표로는 그 차이가 안 보인다.

### F5. ★**300 문항의 분해능이 우리 목표 차이보다 크다**

2점 척도 300 문항의 unpaired 표준오차는 `√(p(1−p)/300) ≈ 0.029` = **±2.9%p**(p=0.5).
[결과 050](../test_result/050_20260821_P064-두번째-자는-24만문항이-필요하다.md) 이
*"두 번째 자릿수를 보려면 24만 문항"* 이라고 실측했다.

> ★**단 paired 면 달라진다.** 결과 049 가 증명했다 — **같은 문항 위에서 모델 간 차를 보면 SE 가 한 자릿수 내려간다.**
> `eval_korean_bench.py` 가 이미 그 설계로 돼 있다. → **§3 의 채택안은 전부 paired 다.**

### F6. `unseen_concept` 라벨이 **우리 조건에서 의미를 잃는다**

`split: unseen_concept` 은 *"train 900 에 없던 개념"* 이라는 뜻이다.
🚫**우리가 그 900 으로 학습하지 않으면 "unseen" 의 기준이 우리 학습 풀이 아니다.**
→ 그 라벨은 **난이도 태그로만** 읽고, 일반화 주장의 근거로 쓰지 않는다.

### F7. 오염 검증이 안 됐다 — 그러나 위험은 낮아 보인다

개념어(사과·파인애플·수달)는 우리 `ko-en` 풀(한국어 위키 24.3%)에 **확실히 있다.**
다만 문장 자체가 **합성**이라 축자 일치 가능성은 낮다.
→ ★**[P075 단계0](../test_plan/P075_토크나이저-어휘예산과-한국어-분절.md) 의 O1(13-gram 겹침)을 그대로 적용**한다. 도구를 두 번 만들 이유가 없다.

## 3. ✅★도입안 — **셋. 값싼 순서대로**

### 안 A ★★**train+val 1,000 을 `paired_eval` 의 CE 프로브로** (권장 1순위)

| | |
|---|---|
| **무엇** | 1,000 문장의 **토큰 CE 를 모델쌍 paired 로** 잰다. 생성 없음, 채점기 없음, 정답 없음 |
| **왜 값어치 있나** | 우리 판정은 지금 **ko-en val CE 하나**뿐이고, 그 val 은 **위키+웹크롤 혼합**이다. 이 1,000 문장은 **한국어 의미 관계 문장**이라 **다른 축을 잰다**. 결과 037(P037) 이 *"val 셋 자체가 판정을 왜곡하는가"* 를 묻고 답을 못 받았다 |
| **구현** | `paired_eval.py` 에 **`--text-file` 옵션**(임의 텍스트에서 크롭을 만든다). ⚙0.5h |
| **분해능** | 1,000 문장 paired → ⚙SE 0.001 대(결과 049 계열). **충분하다** |
| 🚫**한계** | *"CE 가 낮다 = 의미를 안다"* 가 **아니다.** 문체·어휘 친숙도도 함께 잰다. **보조 자**로만 쓴다 |

### 안 B ★**held-out 300 을 우도 채점 다지선다로 변환**

| | |
|---|---|
| **무엇** | `prompt` + 후보 답 N개 중 **PMI 정규화 로그우도 argmax**. `eval_korean_bench.py` 에 `--task stage1` 추가 |
| **왜 이 형식인가** | F4 — 생성 채점은 0 이다. 우도 채점은 base LM 이 **정당하게 할 수 있는 일**이고 **연속값**이다 |
| 🚫**막는 것** | **오답 후보(distractor)가 데이터에 없다.** `forbidden_relations` 도 없다(F3) |
| ★**사용자에게 요청할 것** | 각 항목에 **`forbidden_relations` + 오답 후보 3개**를 넣어 재생성. ★**이것이 이 데이터셋의 값어치를 가장 크게 올리는 한 가지**다 |
| **대안(요청이 어려우면)** | 같은 `task` 안의 다른 항목 `answer` 를 오답으로 쓴다. ⚠️**주제가 달라 너무 쉬워진다** — 변별력이 떨어진다 |

### 안 C ⏸**관계 단위 채점기** — **보류. 선결이 둘**

명세 §9~§15 의 결정적 채점기는 **F2(관계 130종)와 F3(금지관계 부재)** 때문에 지금 못 만든다.
🚫**만들어도 라벨 대부분이 N=1 이라 통계가 안 나온다.**
→ **선결**: ①관계 어휘를 **정규표 8~15종으로 축소**(명세 §12 대로) ②`forbidden_relations` 채우기.

## 8.3 ★★Q6-A 추가검토 — **"암기인가 이해인가" 를 CE 프로브가 구분할 수 있는가**

> 사용자: *"900개는 이미 모델이 본 데이터이므로 CE 가 낮아졌다고 해서 의미 이해가 향상되었다고
> 말하긴 어렵지 않은지. language-model likelihood 가 올라간 것인지 의미 이해가 향상된 것인지를
> 확인할 수 있어야 함."*
> 예시 — Train: `"사과는 과일의 한 종류다."` / Probe: `"사과는 과일의 한 종류다."`

### 8.3.1 🚫★**사용자 지적이 맞다. 안 A 는 원안대로는 성립하지 않는다**

원안(§3 안 A)은 **train+val 1,000 전체**를 프로브로 쓰자고 했다.
🚫**train 900 을 프로브로 쓰면 그것은 "본 문장의 우도" 이고, 정의상 암기다.**
⚠️**그리고 그 900 은 "본" 정도가 아니라 추가학습에서 수십 에폭 볼 수 있다**
(v2 검토 §4.2) — **암기가 아니라 완전 암송에 가깝다.**

★**내가 원안에서 이 구분을 안 했다.** 안 A 를 그대로 두면
*"CE 가 −0.3 내려갔다"* 같은 큰 수가 나오고 **그것은 아무 의미가 없다.**

### 8.3.2 ✅**고친 안 A — 세 갈래로 나눈다**

프로브를 **세 집합**으로 나누고 **셋을 함께 본다**. 하나만 보면 구분이 안 된다.

| 프로브 | 무엇 | 모델이 봤나 | 이 수가 오르면 |
|---|---|---|---|
| **P-seen** | train 900 | ✅**봤다** | **암기.** 정보 없음(단 **0 이면 학습이 안 된 것** — 건전성 검사로는 쓸모 있다) |
| **P-held** | val 100 | 🚫**안 봤다**(gradient 기준) | ⚠️**같은 풀·같은 문체**라 **문체 일반화**까지만 |
| ★**P-para** | ★**train 900 을 바꿔 쓴 문장** | 🚫안 봤다 · ★**내용은 같다** | ★**여기가 "이해" 에 가장 가깝다** |

★★**P-para 가 핵심이다.** 같은 사실을 다른 표면형으로 쓴다:

```
train    : "사과는 과일의 한 종류다."
P-para   : "사과라는 것은 과일에 속한다."          ← 같은 사실, 다른 문자열
P-neg    : "사과는 곤충의 한 종류다."              ← 같은 문체, 틀린 사실
```

★**그리고 `P-neg`(문체 동일·사실 거짓)를 넣으면 판정이 선명해진다**:

| 관측 | 해석 |
|---|---|
| P-seen ↓↓ · P-para ≈ · P-neg ≈ | 🚫**순수 암기.** 문자열만 외웠다 |
| P-seen ↓↓ · P-para ↓ · **P-neg ↓ 도 같이** | ⚠️**문체 학습.** 한국어 평서형 설명문 전반의 우도가 올랐다 |
| ★P-seen ↓↓ · **P-para ↓** · ★**P-neg ↑ 또는 불변** | ★★**내용 학습.** 참인 문장은 좋아지고 거짓 문장은 안 좋아졌다 |

> ★★**`P-para − P-neg` 가 우리가 원한 "의미 이해" 의 조작적 정의**다.
> **둘은 문체·길이·어휘가 같고 사실값만 다르다.**
> 이것은 v2 검토 §3.1 의 Model C 와 **같은 논리**이고, 데이터가 아니라 **프로브 쪽에서** 대조군을 만든다.

### 8.3.3 비용과 선결

| # | 무엇 | 비용 | 선결 |
|---|---|---:|---|
| 1 | `paired_eval --text-file` 구현 | ⚙0.5h | 없음 |
| ★**2** | **P-para 900 · P-neg 900 생성** | 🚫**사용자/생성기** | ★**이것이 안 A 의 진짜 선결이다** |
| 3 | 세 프로브 측정 | ⚙5분 | 1·2 |

> ★**사용자에게 요청할 것**: train 900 각각에 대해
> ①**같은 사실을 다른 표현으로 쓴 문장**(P-para) ②**문체는 같고 사실만 거짓인 문장**(P-neg)
> 을 하나씩 더 생성. **held-out_v2 의 오답 재생성과 같은 작업 성격**이므로 함께 요청하는 것이 낫다.

# 10. ★★★2026-08-29 — **채팅 템플릿과 지시 following 평가**(사용자 지시 7)

> 원문을 열어 확인한 조사다. 미확인 항목은 §10.5 에 분리했다.

## 10.1 ★**"포맷 표준" 은 없다. "메커니즘 표준" 만 있다**

HuggingFace 공식 문서 원문:

> *"There are many possible chat formats, and different models may use different formats or control
> tokens, **even if they were fine-tuned from the same base model**!"*
> *"Using a format different from the format a model was trained with will usually cause
> **severe, silent performance degradation**."*

사실상 표준 역할을 하는 것은 **특정 토큰 배치가 아니라 `chat_template`(Jinja) 이라는 전달 메커니즘**이다
(`tokenizer_config.json` 의 `chat_template` 키 → 최근 transformers 는 `chat_template.jinja` 파일로 분리).
`llama.cpp` 가 chatml/llama2/llama3/gemma/zephyr/vicuna/deepseek 등을 **각각 하드코딩**하고 있는 것이
표준이 없다는 가장 직접적인 증거다.

| 포맷 | 레이아웃 | ★**필요한 신규 vocab 항목** |
|---|---|---:|
| **Alpaca** | `### Instruction:\n…\n\n### Response:` | ★**0개**(완전 평문) |
| **Llama 2** | `[INST] <<SYS>>…<</SYS>> … [/INST]` | ★**0개**(`[INST]` 는 평문) |
| **Mistral v0.2** | `[INST] … [/INST]` | ★**0개** |
| **Zephyr / TinyLlama-Chat** | `<\|user\|>\n…</s>\n<\|assistant\|>\n` | ★**0개**(종결은 기존 `</s>` 재사용) |
| **ChatML / Qwen / SmolLM2** | `<\|im_start\|>role\n…<\|im_end\|>` | **2개** |
| **Gemma** | `<start_of_turn>…<end_of_turn>` | **2개**(+ system role **미지원**) |
| **Llama 3** | `<\|start_header_id\|>…<\|eot_id\|>` | **4개**(+256 예약 슬롯) |

## 10.2 ★★**우리에게 가장 중요한 사실 — 지금이 어휘에 슬롯을 파둘 마지막 시점이다**

- ★**SmolLM2-135M 의 *base* 모델 vocab 안에 이미 `<|im_start|>`=1, `<|im_end|>`=2 가 들어 있다.**
- ★**Gemma-2 *base* 에도 `<start_of_turn>`=106 / `<end_of_turn>`=107 과 `<unusedN>` 99개가 예약**돼 있다.
- 즉 **성공한 소형 모델들은 사전학습 어휘 단계에서 채팅 토큰 자리를 미리 비워 뒀다.**

> ★★★**P075 단계1 이 어휘를 16,384 로 재학습하려 한다. 그때가 슬롯을 넣을 수 있는 유일한 시점**이다.
> 지금 안 넣으면 나중에 `resize_token_embeddings` 로 붙여야 하고,
> **새 임베딩 2개를 SFT 1,000건으로 학습**해야 한다 — **그 예산으로는 위험하다.**
> → ★**P075 단계1 의 토크나이저 학습에 예약 슬롯 4~8개를 넣을 것을 권고한다.**
> **비용은 tied 임베딩 기준 `d_model × 슬롯수` = 768×8 = 6,144 파라미터(0.02 MiB)** — 사실상 0.

⚠️**단 대안도 실증돼 있다**: TinyLlama-1.1B-Chat 은 vocab 32,000 에 특수토큰 3개뿐인 채로
Zephyr 템플릿(평문 역할 마커 + 기존 `</s>` 종결)으로 동작한다.
★**평문 경로가 유효하다.** 단 **턴 종결자만은 단일 토큰이어야** 한다(기존 `eos` 재사용).
