## 2. 질문

기존 네 모델이 현재 공식 COMPS·Entity의 전량을 원래 scoring 경로로 완료하는가?
모델별 UID macro와 문항별 예측은 무엇이며, 동일 문항의 차이는 어느 cluster에 분포하는가?

## 3. 예측

짧은 원문이 많아 기존 네 모델의 전량 완료를 기대한다. 그러나 native tokenizer의 구분력 부족,
실제 oracle 음성, 모델당4시간을 넘는 forecast, 512MB 원행 저장 상한 또는 CUDA 종료 실패가
가능하다. 점수 방향은 미지이며 uniform 기대값 COMPS50/Entity20도 반드시 넘는다고 예측하지 않는다.

## 4. 단계 설계

1. CPU: 현재 소스, 원profile SHA와 모든 pins를 검증한다. 닫힌 두 tokenizer 전량 sweep을 재사용한다.
2. CPU: 새 제어기 회귀, 기존 관련 계약, launcher 구문과 registry 중복을 확인한다.
3. GPU: 기존 모델 하나를 FP32·TF32 off·MATH/noKV/eager로 로드한다. 합성과 실제 phrase/full-label oracle를 통과해야 한다.
4. GPU: 원래 입력 순서의 고정 cost 표본을 측정한다. 모든7파일의 실제 padded positions로 전체비용×1.5+120초를 계산한다.
5. GPU: 남은4시간 및 절대 마감에서 forecast가 들어올 때만 전체97,808행을 평가한다. 배치8·seed1337·원UID/정답0·동률 RNG·저장원형은 유지한다.
6. 종료: 모델/state/source/pins 불변과 allocated/reserved0을 확인한다. 독립 reader가 모든 shard/원행/UID/예측을 다시 계산한다.

## 5. 판정 기준

| 관측 | 판정 |
|---|---|
| 97,808행/7파일·원UID macro·수치 oracle·불변/종료 모두 충족 | 해당 frozen 모델의 전량 평가 완료 |
| oracle 실패/입력 또는 소스 drift | ERROR, 본평가 입장 거부 |
| 전량 forecast·시간·512MB 저장 예산 부족 | HOLD8, 완료한 cost를 공식 품질로 승격하지 않음 |
| CUDA 종료/소스 종료 검사 실패 | 종료9, 다음 모델 실행 중단 |

원 수치 허용오차 atol1e-5/rtol1e-4, 문항 제외·길이 절단0을 유지한다.
같은 조건의 새 seed 분해능은 없으며, 단일 점수를 새 학습법의 일반품질 승리로 판단하지 않는다.

## 6. 비용

모델당 내부14,400초, 외부 timeout14,460초, 후행 kill 여유60초다.
네 모델 편성 상한은4×14,520초=58,080초=16.1333시간이며 registry는16.2시간이다.
실측 시간은 실행 뒤 기록한다. GPU 자체 계산은11월18일16:30 이전 종료, 최종17시까지 기록 회수다.
모델별 owned allocated 상한8GiB, 원행512,000,000B, shard10,000,000B다.
8GiB는 자체 allocator 상한이며 전체 장치 VRAM이나 물리 peak의 측정값이 아니다.

## 7. 실행

`bash run_P106B_Stage8sem3Wc_long_semantics.sh --check-only` 후 같은 파일을 인수 없이 실행한다.
기존 core6_env_20261023만 사용한다. 모델별 독립 HOLD/error 후 다음 모델을 시도하되
종료9/124/137이면 전체 loop를 중단한다. 현재 새 승인으로 수행하며 종전 거절을 성공으로 바꾸지 않는다.

## 8. 한계

## 9. 실행 이력

착수 시점 DESIGNED. 새 profile/계약/CPU 검사 후 실제 네 모델을 수행하고 결과101에 회수한다.
종전 v1 준비0·자동검토거절2회/모델0은 원형으로 보존한다.

v2 준비는 실제0이었다. 네 worker 모두 sandbox의 OS NVML 접근 차단으로 입장 전1/모델0·CUDA미초기화로 종료했다. 권한 경로의 GPU 점조회는 성공했다. 새 v3는 version/tag·소스·런처 이름만 변경한 동일설계이고, 기존 v2 입력/소스/출력은 보존한다. 새 실행명은 Stage8sem4Wc이며 현재161의 직접 장시간GPU 승인으로 권한 경로에서 수행한다.

### v4 저장 이름 접점 수정 전 영향 분석

v3는 네 모델 모두 실제 로드·합성/실제 phrase oracle·처음 두 cost 파일까지 실행했다.
세 번째 공식 파일명의 하이픈을 artifact stem으로 그대로 넘겨 ASCII shard 규칙이 거부했다.
네 종료1/부분cost·source/state불변·CUDA allocated/reserved0은 보존한다. 전량 품질은NOT_RUN이다.

수정 대상은 새 v4 제어기의 score_file 저장 이름과 사전 검사, 대응 CPU 회귀, 새 런처/출력이다.
권한은 사용자161의 코드 구현·미완 실험 수행 허가다. 기존 v1/v2/v3·원공식 파일은 바꾸지 않는다.
호출 흐름은 v4 actual→v4 score_file→기존 core.RankAudit/원공식 scorer→기존 ShardWriter다.
하이픈을 밑줄로 대응하되 현재 모든7파일×2mode의 충돌을 모델 입장 전에 검사한다.
source_file/원행/UID/입력/점수/분모는 원래 문자열을 유지하며 artifact 이름만 달라진다.
데이터 스키마·수치/정답·공식 함수·메모리/시간 상한에 영향 없고, 기존 원형 reader는 manifest로
정확 파일을 읽을 수 있다. 새5 CPU 회귀는 시간/불변3과 실제7파일 writer호환·충돌거부2다.
정본 영향은 같은 계획의 기술 재시도 이력/새tag이며 별도 과학적 승자로 등록하지 않는다.
기술부채는 frozen 실패 재현을 보존하는 새버전이며 기존 실패 namespace를 재사용하지 않는다.

이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.
