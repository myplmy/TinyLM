# P107 후속 — 실제 optimizer 갱신·통계·전체 경계 재개 기술 계약

사용자104의 2026-11-01 11:00 KST까지 CPU/GPU 연구 승인을 적용한다. 이쪽 GPU는
8,000,000,000바이트 이내를 목표로 allocator를 더 낮게 제한하고 실행/마감 감시를 둔다.
다른 세션의 정제 전용 경로·자료·코드·원장·프로세스와 보호 TinyDataset은 접근하지 않는다.
정제 전 추가300M 학습과 소규모 품질 판정 금지는 유지한다.

## 목적과 이전 결과와의 차이

원장59·[결과107 §7~9](../../test_result/107_20261027131747_P107-가시성과-shift는-검산됐고-학습효과는-미확인.md)는
정책 단독 재개와 가상 로짓 전달·optimizer 없는 실제 F+B까지 완료했다. 완료 행렬을 재실행하지
않는다. 이번 독립변수는 같은 causal/MNTP 배치에서 **실제 observer/적응 선정을 연결했는지**다.
실제 optimizer 갱신과 model/optimizer/정책/source/RNG의 결합 경계 재개가 새 질문이다.

파일별 표의 상세 기록은 첫 어댑터/CPU prototype 작성 뒤 보완했다. 착수 전에는 사용자에게
새 어댑터·시험·진단·문서라는 범주만 보고했으므로 파일명까지 선행 고정하는 시점은 미흡했다.
타세션·보호 경로로 범위를 확장하지 않았으며 이후 진단/런처의 정확 경로는 위 표로 먼저 고정한다.

코드 영향은 독립 신규 모듈과 소비 진단뿐이다. 기존 정책·MNTP·모델·optimizer 구현을 재정의하지
않고 소비한다. 예측 ID는 기존 `diag_p107_adaptive_gpu_transfer.collect_ids`를 주입해 재사용한다.
등록은 기존 플래그로 하고 타세션 dirty `scripts/flag_whitelist.tsv`는 수정하지 않는다.
데이터 영향은 새 작은 감사 JSON뿐이다. 원CP·원로그·정제 캐시를 변경하지 않는다.
테스트는 완료 단위·거부·dirty 복원·dropout/RNG·source·실제 optimizer state를 다룬다.
기술부채는 문서 경계가 없는 기존 loader에 자동 적용하지 않는 명시 어댑터 경계로 남긴다.

## 사전 고정 조건과 수치 판정

- 실제 모델은 기존 native595-q, V32768·dim768·14층·같은 FP32 master/삼진 STE·grad checkpoint-on이다.
- micro8 × seq1024 × accum16 = 갱신당131,072 실행 입력. causal8/MNTP8을 배분하며 목적별
  target 합을 분모로 각각0.5 가중한다. target 수는 물리 입력 수/고유 코퍼스 양이 아니다.
- uniform / observe-only / adaptive-keep를 비교한다. observer-only는 uniform과 똑같은 선정·loss·
  model/optimizer 갱신이어야 한다. adaptive는 정답으로 가중한 이후 선정이 달라질 수 있다.
- 기본 Muon RMS4+AdamW·같은 상수 LR·clip을 사용한다. 새 LR/스케줄 승자를 고르는 실험이 아니다.
- 비용은 순서/역순의 각 warm1·실측3 갱신을 기록한다. RNG·부모·원 입력·본체 경로를 맞추고
  선정/준비, F+B+관측 포함시간, ID/CPU관측, clip/commit, optimizer와 전체 wall을 분리한다.
  포함 구간의 중앙값을 더해 새 전체시간으로 만들지 않는다.
- 전체 재개는 중간 완료 경계를 메모리 BytesIO에 직렬화·역직렬화한 뒤 같은 후속 갱신의
  model/optimizer/정책/source/RNG와 loss/선정량을 대조한다. 디스크 전원장애 복구 증거는 아니다.
- 성공은 모든 행 완결·정합·원본불변·GPU 해제다. strict 수치 불일치는 gate-negative로 남기며
  관찰 뒤 허용차를 완화하지 않는다. SIGALRM/외부 timeout·마감·VRAM 중단은 별도 보류다.

optimizer가 부분 실패하거나 forward 뒤 오류가 나면 dirty 상태로 재사용/저장을 거부한다.
정책·source·RNG만 되돌렸다고 모델 전체를 복원했다고 주장하지 않는다. 정상 전체 snapshot을
복원한 뒤에만 사용한다. zero-target을 강제 선정이나 재추첨으로 숨기지 않는다.

이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.
