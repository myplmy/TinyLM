# AdaMuon BF16 상태·전송·재개 계약

## 1. 왜

원장55/56은 FP32 V 적응판의 합성20회귀·실제 gradient 비용과 NS/tail 요인실험만으로
저자 BF16 optimizer·통신·저장/재개가 완료됐다고 할 수 없다. 사용자161의 기존 미완 전수
수행 범위에서 이 접점을 먼저 구현한다. BabyLM 실제 평가 소스와 기존 optimizer는 동결한다.

고정 원천은 [Chongjie-Si/AdaMuon 9c1ba5be의 adamuon.py](https://github.com/Chongjie-Si/AdaMuon/blob/9c1ba5be86ebd7dd7464a0bc43b28daccf40279e/adamuon.py)와 같은 commit의 opt_config.py다.
현재 GitHub 읽기에서 blob dd194bdb7fccf6bab5b5cfed3b3cba0df059c2af와
947149a50db6eaae92be9feddc8346ea874eb3a5를 다시 확인했다. Apache2 원천이며 새 패키지를
설치하거나 외부 optimizer를 import/실행하지 않는다.

## 2. 질문

저자 2D 연산순서와 BF16 tail을 유지한 상태에서 한 장치 및 Gloo2 전송이 같은 업데이트를
만드는가? None gradient를 조용히 건너뛰지 않고, state_dict 왕복 후 BF16 flat V와 다음 step이
보존되는가? 상태와 전송 scratch의 정확 byte 비용은 얼마인가?

## 3. 예측

같은 CPU backend/같은 합성 2D gradient에서는 기존 독립 author-factor helper와 비트 동률을
기대한다. 분산 전송은 BF16 값을 바꾸지 않아 rank별 가중치가 같아야 한다. 그러나 PyTorch의
load_state_dict dtype cast, 버퍼 별칭과 일부 rank만 None인 collective에서 실패할 수 있다.
일반 품질/속도 이득을 예측하지 않는다.

## 4. 단계

1. CPU 정적: 기존 적응판/라우팅/저자 source를 대조하고 새 클래스와 회귀를 만든다.
2. CPU 단일: tall/wide/square·Nesterov 두 분기·다단계 source순서와 raw bit·gradient 불변,
   state6B/원소 및 크기별 BF16 scratch를 확인한다.
3. CPU 단일: None assertion·변경 전 거부·zero gradient·형상/유한성·4D flatten/저자 scale·저장/재개를 확인한다.
4. CPU Gloo2: 기존 환경의 두 process만 사용해 size bucket·불완전 마지막 묶음·동일가중치·재개와
   rank 한쪽 None의 동시 거부를 검증한다. 자원/권한 제약은 원인별 NOT_RUN으로 남긴다.
5. 후속: GPU 평가 종료 후 명시 trainer 선택/메타데이터·resume 접점을 연결하고 합성 검증한다.
   정제/권리/편입 전 전체 본학습과 같은 품질까지 시간은 수행하지 않는다.

## 5. 판정

| 결과 | 판정 |
|---|---|
| 독립2D factor와 같은 uint8 bytes, 원gradient 불변 | 해당 CPU 수치 계약 통과 |
| flat BF16 V/FP32 momentum과 저장 뒤 동일 next-step | 해당 optimizer resume 통과 |
| Gloo2 양rank 동일weight/독립oracle/중단·재개 동률 | 해당 CPU 전송 계약 통과 |
| 실제 모델/본학습/다중GPU 없음 | 품질·전체wall·다중GPU 재현 NOT_RUN |

원 외부 코드는 None을 assert한다. 새판은 모든 참여 rank의 오류를 업데이트 전에 공유해
부분 갱신/통신 대기를 줄인다. 그룹 순서는 안정화하고 scratch를 checkpoint에서 제외한다.
이 방어와 단일장치 copy는 명시적 adaptation이며 외부 package 전체의 exact port라고 부르지 않는다.

## 6. 비용

CPU 합성 목표60초 이내·한process Torch1, Gloo 두 process도 각각1thread다. 기존 runtime만 쓴다.
설치/다운로드/새환경/모델/실제학습0. 상태는 소유 rank별 FP32 momentum+BF16 V, 전송 scratch는
rank마다 2B×world_size×서로다른 parameter numel 합이다. 실제 byte로 검산한다.

## 7. 실행

기존 tlm_torch Python으로 scripts/test_adamuon_author.py를 명시 실행한다.
첫 CPU 단일 검사 뒤 Gloo2를 별도로 실행해 원인을 섞지 않는다. raw 결과는 runlog078로 기록한다.
아직 학습 BAT/SH나 새 optimizer 기본값은 만들지 않는다.

## 8. 한계

동일 seed/5gradient는 실제 모델 분포가 아니다. World2 CPU 통신은 CUDA/NCCL·DDP 전체학습이
아니다. source의 모든 비정상 입력/모델형상을 재현했다는 주장도 하지 않는다. FP32 master와
2D/4D의 명시 범위이며 새 방법이 품질/시간/학습안정을 개선하는지는 본학습 후 별도 판정한다.

## 9. 실행 이력

현재 DESIGNED. 기존 FP32 적응판·요인/bit 회수는 완료 증거를 재사용하고 반복하지 않는다.
새 클래스의 실제 단일·Gloo 회귀와 후속 trainer 검증을 각각 결과078에 기록한다.

이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.
