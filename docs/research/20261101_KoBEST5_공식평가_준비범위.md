# KoBEST 5개 공식 test 연결 — 새 설치·모델 실행 전 CPU 준비

원장46은 공식 다섯 과제의 acc/macro-F1이 미착수다. 과거 COPA/HellaSwag 일부 문항의 로컬
프롬프트 점수는 재사용하지 않는다. 사용자104가 정제 외 미완 연구를11:00 KST까지 승인했다.
기존 평가 전용 환경과 고정 lm_eval 소스, 이미 로컬에 있는 공식 test만 사용한다.

## 방법 비교

| 안 | 내용 | 장점 | 단점 | 영향도 | 수행비용 |
|---|---|---|---|---|---|
| A | 기존 공식 harness·기존 adapter를 재사용하고 다섯 test의 소유/해시/분모/의존성을 먼저 고정 | 평가 조건 재정의와 중복 엔진을 피함 | 추가 지표 의존성 설치 승인 전 실제 점수는 남음 | 새 CPU 준비기/시험/문서만 | 낮음·모델/GPU0 |
| B | stdlib만으로 별도 프롬프트/metric 엔진 제작 | 설치 없이 진단 가능 | 공식 평가 경로와 달라지고 중복 구현이 됨 | 새 평가 엔진과 검증 부채 | 중간 이상 |
| C | 기존 두 과제 일부 점수만 보존 | 추가 변경 없음 | 공식5과제 요청을 충족하지 못함 | 없음 | 추가0·미완 유지 |

A로 진행한다. 예를 들어 WiC의 공식 질문·아니오/예 선택지와 macro-F1은 그대로 두고,
공식 test1,260행의 저장 위치만 고정한다. 시험 정답을 교사·학습·번역에 넘기지 않는다.

기존 `prepare_p106b_official_eval.py`의 캐시 정책·안전 출력과
`p106b_official_lm_adapter.py`의 공식 소스검증을 재사용한다. 제품/공용검사기·기존 adapter는
변경하지 않는다. 데이터는 평가 전용 로컬 복사이며 원본은 불변이다. 테스트는 정답의 내용이
아닌 형식·입력 경계·분모/해시·중복을 확인한다. TinyLM 어휘·cache·MC 길이 정규화는 기존
공식 adapter의 검산을 재사용하며, 새로운 평가 요청 연결은 실제 task init 뒤 별도 확인한다.

고정 소스는 lm_eval `d6de81643928d653435c431bae19945d41d32520`, 데이터 snapshot은
`a5ea15e3ac77ed694b79f6204eb31889a2ba989f`다. 공식 YAML의 F1은 `hf_evaluate:true`이고
최종 집계 함수는 sklearn의 macro-F1을 호출한다. 평가 환경의 evaluate/sklearn 및 관련 수치
의존성이 없음을 먼저 보고한다. 설치는 실행하지 않으며, 사용자 승인 전 이를 가짜 모듈이나
자체 지표로 우회해 공식 점수라고 보고하지 않는다. 추가 의존성이 정말 필요한 범위는 공식
MC 처리 경로를 읽어 구분한다. KoBEST group의 size-weighted 집계와 Core6 동일가중 평균도
혼동하지 않는다.

첫 실행 Stage8tW는 실제1이다. HF snapshot이 blob 심볼릭 링크일 것이라는 준비기의 가정과
달리 실제5파일은 snapshot 안의 일반 파일이었다. 최초 코드/13시험/SH는
`handoff/audit/nov01_independent/kobest_source_v1/`에 보존했다. 원 데이터 오류가 아니다.
정확 snapshot 일반 파일과 내부 blob 링크만 허용하고 부모/외부 링크를 거부하는 회귀2개를
추가해15시험으로 보완한다. 새 Stage8tWb/v2 출력으로만 다시 실행하며 원로그는 고치지 않는다.

## 공식 지표 의존성의 후속 설치 범위 — 현재는 설치하지 않음

현재 평가 전용 Python3.10.19의 numpy2.2.6/datasets5.0.0/pyarrow25.0.1/lm_eval0.4.14.dev0을
유지한다. 후보 버전은 아래와 같다. 설치 전 승인·wheel metadata/의존성 closure·CPU import와
공식 toy-F1 검산이 필요하며, 후보 조합의 실제 호환성을 이미 확인한 것으로 쓰지 않는다.

| 패키지 | 고정 설치 후보 | 필요한 이유 | 현재 |
|---|---|---|---|
| evaluate |0.4.6|공식 YAML의 HF metric 초기화 경로 |없음 |
| scikit-learn |1.7.2|공식 `utils.macro_f1_score`의 실제 함수 |없음 |
| scipy |1.15.3|scikit-learn 필수 수치 의존성 |없음 |
| joblib |1.5.2|scikit-learn 필수 런타임 의존성 |없음 |
| threadpoolctl |3.6.0|scikit-learn 필수 스레드 제어 의존성 |없음 |

[scikit-learn1.7 공식 설치 문서](https://scikit-learn.org/1.7/install.html)는 Python3.10 이상과
NumPy/SciPy/joblib/threadpoolctl의 최소 요건을 명시한다. [SciPy1.15 도구 표](https://docs.scipy.org/doc/scipy-1.15.3/dev/toolchain.html),
[evaluate0.4.6](https://pypi.org/project/evaluate/0.4.6/), [joblib1.5.2](https://pypi.org/project/joblib/1.5.2/),
[threadpoolctl3.6.0](https://pypi.org/project/threadpoolctl/3.6.0/)의 공식 배포정보도 확인했다.
이는 후보의 Python 버전 범위와 설치 목적 확인이지 현재 환경의 실제 실행 증거는 아니다.

dill0.4.1/pandas2.3.3/requests2.34.2/tqdm4.70.1/xxhash4.0.1/multiprocess0.70.19/
fsspec2026.4.0/aiohttp3.14.3/huggingface-hub1.24.0/packaging26.3은 현재 이미 설치돼 있다.
그 이름이 존재하는 것과 evaluate0.4.6의 모든 API가 맞는 것은 다르므로, 기존 패키지를
자동 업그레이드/다운그레이드하지 않는다. PyPI JSON/해당 evaluate tag setup 원문은 도구에서
확보하지 못해 정확 wheel Requires-Dist와 closure를 검증했다고 주장하지 않는다.

후속 대안은 A(권장) 평가 전용 환경에 위 다섯만 추가하고 기존 버전이 바뀌면 중단하는 방식,
B 별도 신규 환경 전체를 구성하는 방식, C 설치를 보류하고 현재 자료 준비 상태를 유지하는
방식이다. A는 기존 Core6 환경을 재사용해 변경을 줄인다. B는 분리는 명확하지만 환경 복제와
검증/디스크 비용이 늘며, C는 변경0이나 KoBEST 모델점수 미완이 남는다. 별도 HF `f1` metric
자원의 고정 revision·오프라인 캐시도 package 설치와 구분해 준비해야 한다. 실제 설치/취득0이다.
