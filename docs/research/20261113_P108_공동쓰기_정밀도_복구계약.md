# P108 공동쓰기 정밀도 복구 — FP32 실제 연산과 FP64 이상 응답을 구분한다

사용자115 위임으로 Stage19c의 실제 종료1을 보존한다. 원본 core의 selected_runtime 원복
메시지·소스불변·CUDA0/0은 확인했고 새 가중치 파일은 저장하지 않았다. 기존 actual189행에는
완결된 원본68/oracle52/이상 국소68과 첫 전체쓰기1행이 있다. 전체쓰기 팔은 완료되지 않았다.

## 1. 가설·세 안·영향

A를 선택한다. 같은 실제 입력/가중치의 FP32 F.linear를 재생해 원 모듈과 EXACT 비교하고,
FP64의 선형 응답과 FP32 출력 반올림을 별도 기록한다. 원오차 기준은 그대로 계산·보존한다.
B의 허용오차 상향은 잘못된 편집/캐시도 숨길 수 있어 선택하지 않는다. C의 전체 직접편집
연구 종결도 실제 연산의 정합을 아직 구분하지 못했으므로 선택하지 않는다.

새 helper/회귀/driver·Stage20 SH·새 namespace와 자기 문서/원장만 수정한다. 기존 동결된
Stage19 소스·실패·패킷·원답·모델/CP·검사기/수치허용오차·다른 정제·TinyDataset은 불변이다.
추가300M·optimizer/value 재학습·설치/다운로드·새환경·Git·삭제는0이다.

## 2. 검사의 의미

FP32에서 fl(W_after·x)-fl(W_before·x)는 (W_after-W_before)·x의 FP64 계산과
반드시 같은 반올림을 갖지 않는다. 예를 들어 실제 W가1e8→1e8+8로 바뀌고 x=FP32(1.1)이면
실제 출력 차이와 이상 선형 응답이 달라질 수 있다. 이것은 진단 가설이며 실제 기록으로 확인한다.

새 게이트는 원 입력 전체의 shape·stride/FP32를 보존해 전후 모듈 출력이 각각 같은 가중치의
F.linear 재생과 EXACT인지 확인한다. after 행렬이 원 행렬+봉인 패킷의 실제 FP32 실현과
같은지도 SHA로 검사한다. 별도 FP64의 차분과 실제 행렬차·입력의 곱은1e-10 기준으로 비교한다.
기존 atol1e-5/rtol1e-4 검사의 불일치 수와 최대차도 계속 보고하며 PASS로 재표기하지 않는다.
F32 재생 자체가 다르면 편집 경로 문제로 중단하고 반올림이라고 단정하지 않는다.

## 3. 재사용과 새 관측

기존4패킷의 left/right를 JSON에서 복원해 원 delta SHA와 대조한다. 새 공분산 수집/해결,
층 선택·값 최적화·random 재추출은 하지 않는다. 같은layer8/24key/5%한도·원68질문과
greedy64/EOT4·FP32 MATH·R1/untied를 유지한다. 실제 첫 전체쓰기1답은 새 실행과 별도
parity로 비교하며 원 오류 실행의 완료 증거로 사용하지 않는다.

원본68/oracle52/이상 국소68을 재사용하고 새 단일패킷 전체68답·random3×68답을 회수한다.
한 전체쓰기 context에서 모든 질문의 after-weight SHA가 같아야 한다. 새 국소68답은 원본
모델의 마지막 prompt 모듈 출력을 실제 전체쓰기에서 관측한 FP32 출력으로 한번 교체한다.
덧셈 반올림으로 다른 값을 만들지 않으며 관측/생성의 일회성 hook은 각기 새 context를 쓴다.
이것과 기존 FP64 이상 국소 주입은 다른 관측이다. 자동 채택/새 독립 holdout 주장은0이다.
