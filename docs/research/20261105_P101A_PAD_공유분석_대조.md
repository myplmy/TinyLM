## 2. 공유 분석에서 추가로 대조해야 하는 기존 완료 연구

[결과093 §14와§18](../../test_result/093_20260925_P102A-기능통과-T1-단일순서-속도관측.md)에는
CE/head 경로의 실제 gradient를 고정해 Muon을 재생한 실험이 이미 있다.
같은 입력의 재생은 exact였고, 원 BF16 Newton–Schulz에서 미세차가 증폭되는 과정도 관측했다.
FP32 NS의 최종 weight85/85 허용차 내 결과도 있으나 기본 채택·품질·전체 속도 효과는 미확정이다.

따라서 같은 gradient 두 번 넣기를 새 발견처럼 그대로 반복하지 않는다.
다만 **그 CE gradient 쌍의 증거가 PAD의 실제 gradient 쌍을 직접 재생한 증거는 아니다**.
PAD 원판은 gradient tensor를 메모리에서만 비교한 뒤 폐기했고 JSON에는 hash/통계만 남아 있다.
현재 `muon.py`도 BF16 변환 후 정규화/NS 반복을 하므로 공통 증폭 가설은 타당하지만,
PAD85개 실패의 경로를 확정하려면 필요한 한 update의 실제 두 gradient를 다시 회수해야 한다.
JSON의 작은 최대차만으로 그 tensor를 재구성할 수 없다. 허용차를 넓혀 과거 음성을 PASS로 바꾸지 않는다.

## 3. 중복하지 않을 후속과 권장 순서

1. 기존 q128 CPU7/322·4epoch membership·eager ABBA·기존 full704와 CE 동일gradient 재생을 재사용한다.
2. q32/64의 정확한 histogram/제곱폭·실제1024 tail·MTP h1~h4와 update 분모의 보존 범위만 보충한다.
3. PAD 특유의 두 실제 gradient를 필요한 한 update에서만 회수해 clip/NS cast/반복/갱신 위치를 비교한다.
   기존 CE 재생과 같은 optimizer/source 조건인지 먼저 확인하고 원값 및 FP32 대조를 구분한다.
4. 수치 기준을 닫은 뒤 실제 사용할 MTP와 compile 조건에서 짧은 정순/역순 비용을 측정한다.
   최초 shape/guard/recompile/fallback과 평가·후처리까지의 peak를 포함한다.

**권장 시작점은128배수**다. 이미 시간 이득의 실측이 있으며 남은 수치 쟁점이 구체적이다.
32/64는 슬롯이 적다는 사실만으로 최속/최저 VRAM이라 채택하지 않는다.
선행 수치가 닫히지 않은 상태에서704update 네 정책 전체를 다시 학습하지 않는다.

선택지를 비교하면 기존 fixed1024 유지는 비교 안정성/추가비용0, q128 후속은 검증된 시간 이득과
미해결 NS 비용, q32/64 선행은 더 적은 슬롯과 더 큰 compile 불확실성이다.
현재는 q128의 남은 수치·compile 검증을 먼저 준비하는 편이 비용 대비 타당하다.
CPU metadata 재집계는 완료했지만 실제 새 trace/compiled 비용은 NOT_RUN이다.
추가300M 금지와 다른 세션 정제 경계는 유지한다.
