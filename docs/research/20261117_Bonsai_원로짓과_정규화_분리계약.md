# Bonsai 원 로짓과 확률 정규화를 분리한다

## 1. 왜

원장45~47/68의 Bonsai2B 공식 비교는 기존 HTTP 전체분포 질량1.001087940이 사전 허용차
0.0005를 넘어서 막혔다. 원HOLD8과 강제순위3/B-A 미실행을 보존한다. 사용자161의 기존 미완
수행 범위에서 이 오류가 가중치/원로짓인지 정규화 경로인지 구분한다.

고정 [Prism server-common.cpp](https://github.com/PrismML-Eng/llama.cpp/blob/adfffbe41b2cabcd51fff326ab045662265062bb/tools/server/server-common.cpp)
blob b5e052a9e84c0d5d4e3859d765b2cb611a7dfbe0의1521~1537은 sorted logits의 expf 값을
float 변수에 순차 합산하고 그 분모로 나눈다. 저장 logprob의 합산순서 감도부터 확인한다.
원로그/원확률을 사후 재정규화해 기존 gate를 통과시키지 않는다.

## 2. 질문

저장 확률에서 FP32 순차 합산과 FP64 합산은 얼마나 다른가? 직접 읽은 원FP32 로짓을
FP64로 정규화하면 분모/질량을 검증할 수 있는가? 같은A를 B 전후에 처리해 원로짓/우도를
유지하는가? HTTP와의 차이는 같은 상수 분모 오프셋으로 설명되는가?

## 3. 예측

긴 작은 tail을 큰 값 뒤에 더하는 FP32 합산이 질량 초과와 관련됐다고 예상한다.
하지만 원로짓 미관측 상태에서는 원인 확정이 아니다. tokenizer/실행 설정·ABI·상태초기화가
달라 실제 vector 대조가 실패할 수도 있다. 원HTTP 허용차를 바꾸지 않는다.

## 4. 단계

1. CPU: 저장2shard의 원SHA/순서/전체ID를 확인하고 같은 확률 배열의 순서별 누적만 계산한다.
2. CPU: 같은commit header blob deb1e12828c6cead2a6c7a1793f4c4396b5121d2의 모델/context/batch
   구조체와 모든 사용 함수 선언을 대조한다. C와 ctypes field layout 및 값 범위를 먼저 검사한다.
3. GPU: BabyLM 종료 뒤 정확 기존library/모델·단일GPU를 입장시킨다. 새문맥 A/B/A에서
   memory data까지 clear하고 full prompt를 처리해 원248320 FP32로짓을 새 파일로 보존한다.
4. CPU: 두 독립 FP64 logsumexp/CE·전체분모/ID·A-B-A를 검산하고 HTTP의 상수 offset 가설을 대조한다.
5. 조건부 후속: native 우도·tokenizer boundary·공식 adapter와 전량비용을 입장시킨 뒤에만 공식평가한다.

## 5. 판정

| 관측 | 판정 |
|---|---|
| 저장 확률의 naive FP32/FP64 합이 다름 | 저장 합산순서 감도만 성립; 원인 확정/HTTP 복구 아님 |
| 정확source/ABI·실제rawvector·독립정규화·A-B-A·종료 모두 충족 | 해당새 native 기술경로 입장 |
| ABI/source/입력 불일치·raw비유한·부분prompt·상태불복원 | 모델 입장 거부 또는HOLD/ERROR |
| backend 기술 입장만 | 공식benchmark·교사품질·기존HTTP강제검증은 별도 NOT_RUN |

원logprob atol1e-5/rtol1e-4와 원HTTP 질량0.0005를 유지한다. 새 FP64 분모는 새 raw logits로
계산하며 저장 invalid 확률의 보정값을 정식 결과로 사용하지 않는다.

## 6. 비용

첫 저장CPU 분석은 약25MB·단일CPU·새모델0이다. ABI 검사는 기존 C compiler와 standard ctypes만
사용한다. GPU 카나리 최대20분/소유 자원만·미사용8GiB 점조회·11월18일16:30 이전 계산 종료다.
rawvector/metadata 합계 상한64MB, model/runtime SHA 회수는 별도다. 단일GPU 직렬을 유지한다.

## 7. 실행

첫 CPU 분석은 runlog101 Stage8pr1Wa다. native binding/launcher는 아직 미작성이다.
구현·CPU/ABI·source 봉인 후 정확 명령과 소유 process 종료 경로를 계획에 추가한다.

## 8. 한계

같은 크기의 tokenizer가 다른 모델과 같다는 뜻이 아니다. ABI 선언/C layout의 일치는 실제
binary 내부 ABI의 전범위 검증이 아니므로 같은version과 실제 기본값/모델검증이 필요하다.
한A/B/A는 전체 benchmark·긴continuation·일반한국어품질을 대신하지 않는다.

## 9. 실행 이력

현재 source 검토/설계다. 기존HTTP HOLD8과 임의 header 전시스템 부재주장 거부를 유지한다.
새 저장분석·ABI·실제 native 결과는 각 실행 원문과 함께 결과101에 누적한다.

### 구현·CPU 검증 회수

저장 원확률248320행은 FP64 합1.0010879403472284, 원내림차순 FP32 누적1.0,
역순FP32 누적1.00108802318573이었다. 원HOLD는 유지하며 합산순서 관여 가설만 지지한다.

새 scripts/p106b_prism_native.py와 대응7 CPU검사가 먼저 통과했다. 실제 모델 입장 시점을
잘못 기록하지 않도록 loader 호출/backend 초기화 플래그와 NULL-model 종료 회귀를 추가했고
최종8 CPU검사도 통과했다. 같은commit의3개 구조체 선언으로 만든
scripts/p106b_prism_abi_layout.c를 기존 cc로 컴파일해 ctypes의 모든 field offset/size/alignment를
대조했다. model80/context168/batch56B다. 이 Cprobe는 모델/library를 링크하거나 열지 않는다.

실행기는 scripts/diag_p106b_prism_native_raw.py이며 새 런처는
run_P106B_Stage8pr2Wc_native_raw.sh다. 기존8 binary/library와 backend 탐색의 같은bundle
libggml 실파일·내부 symlink를 봉인한다. 모델토큰화/UTF8 roundtrip·원native IDs·전체 raw FP32
벡터 A0/B/A1·원메모리 data clear·독립 FP64 분모·상수offset 진단을 수행한다.
원HTTP 확률의 보정값을 공식점수로 사용하지 않는다. 내부 계산1110초/parent1200초,
외부1280초+kill여유60초의 보수 편성0.4시간이며 실측값이 아니다.
BabyLM GPU 큐가 끝난 뒤에만 실행하고 외부library/모델 내부의 opaque weight fingerprint와
연속물리peak는 미계측으로 남긴다. 소유 native handles·재수거 child PID·NVML 점조회와
원파일 SHA를 별개 종료 근거로 쓴다.

이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.
