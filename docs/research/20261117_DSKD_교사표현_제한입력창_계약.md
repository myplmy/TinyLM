# DSKD 교사 표현의 제한 입력 창과 분할 읽기

## 1. 왜

현재 사용자161/원장61의 저장·상주 선결을 이어간다. `P107_DSKD_STATIC_FRONTIER_READBACK_v1.json`은 기존 P107의 제품 접점/재개와 DSKD의 현재 소스를 읽어 구분했다. P107의 선언된51소스는 과거 CPU30/파일CLI 당시와 같고, 파일CLI 논리2/물리3·49조각/781352215B 재개는 기존 결과다. 이 선언 집합 밖의 모든 import나 현재 Native 품질을 검증한 것은 아니다. 원장58의 제품 미구현 표현은 정정했으며 같은 기술실행을 반복하지 않는다.

기존 DSKD1024 selector는 선택된 샘플의 전체 feature array를 목록에 모은다. projector kernel은 행view를 목록에 남긴 뒤 모든 선택행을 stack해 GPU로 옮긴다. 원4113 위치 진단의 성공은 보존한다. 다만 teacher 위치75M·폭1024·FP32를 가정한 payload307200000000B/286.1023GiB를 같은 경로로 확장할 수 없다. student75M과 teacher 위치수가 같다는 가정도 성립하지 않는다.

## 2. 질문

한번에한feature array와복사한고정상한batch만사용해원FP32 bytes/selected position metadata를보존할수있는가? window quota와NPY header를payload 할당전에검사하며완전batch 경계의source cursor를복원하는가?

## 3. 예측

같은원position을복사하므로bytes/metadata 동률을기대한다. context-free 합성projector의CE sum을전체selected 분모로누적하면전체행렬의미분과double허용차안에서일치할것이다. 실제Native head의형상/정밀도·메모리peak/품질/가속은예측하지않는다.

## 4. 단계

1. window는명시teacher/tokenizer/mapping/data identity·단일split·원row/position·정확feature SHA와shape를가진다. identity 선언과실제권리/자료입장은다르다. metadata 크기·행/선택위치수·각feature/window 예상payload·batch payload를먼저검사한다.
2. root밖/상위경로·symlink/hardlink를거부한다. 원파일은읽기전용이다. [공식 NPY 규격](https://numpy.org/doc/stable/reference/generated/numpy.lib.format.html)에따라1.0/2.0의header 길이를먼저제한하고고정2D/little-endian FP32/C-order·정확파일크기/SHA·유한값을검증한다. object/pickle·structured·Fortran·임의압축은지원하지않고np.load/pickle을호출하지않는다.
3. 마지막원feature 하나만보유하고목적batch로row를복사한다. 반환배열은부모feature view가아니며원metadata/순서를그대로보존한다. 소비자가반환배열을계속보유하는메모리는reader의한도가아니므로전체RSS 보장으로쓰지않는다. 실제Native consumer는batch별backward/release와runtime peak gate가추가로필요하다.
4. prepare/finish 경계와source-only checksum/schema를둔다. pending/고장중checkpoint·다른window/shape/정책·중간batch 위치의재개를거부한다. model/optimizer/RNG를포함하는전체학습재개라고부르지않는다.
5. CPU합성 NPY 파일/수식으로검증한뒤새결과에회수한다. 기존feature와Native모델/본학습은실행하지않는다.

## 5. 판정

모든selected position이정확히한번·원label/metadata/FP32 bytes로읽혀야한다. source경계후다음batch가일치하고사전quota/파일오류가조용히제외되지않아야한다. 수치오류는고장상태로중단하고정상source경계에서새reader로복구한다. 실제논문학습효과나default채택은NOT_RUN이다.

## 6. 비용

CPU thread1·120초/1GiB 상한의작은scratch만사용한다. 초기정책은NPY header4096B·단일feature4MiB·window입력payload256MiB·batch128position/폭1024에서512KiB·metadata8MiB/최대1024row/65536selected 위치다. 이는 reader 소유payload의계약예산이며전체process RSS/OS page cache/사용자보유배열이 아니다. 새코드와테스트에서실제상한/관측bytes를대조한다.

## 7. 실행

태그p106b_feature_window_v1_20261117는registry조회충돌0이다. 새CPU계약만101 Stage8fw로runlog회수한다. 학습토큰0이며표준300M 산식/풀2배·품질통계자는해당없다. 새학습SH/실제모델명령은작성하지않는다.

## 8. 한계

window별입력/read quota는전량75M cache생산/디스크절감이나online 동시상주실측이아니다. teacher originalraw index가다른sample에반복될수있으므로Native head frame을하나로합쳤다고추정하지않는다. 원teacher_tokens/frame·sample별metadata를유지하고실제consumer의frame/grouping·full-vocab·양방향투영/global denominator를별도검증해야한다. 정식교과/권리·원root split/누설·독립test·전체본학습/최종품질은그대로미완이다.

## 9. 현재 이력

착수전현재소스와기존종결metadata만판독했다. 기존P107 접점과source51불변을회수하고DSKD의eager array/row view/full GPU stack을확인했다. 새reader/CPU결과는아직NOT_RUN이다. 이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.
