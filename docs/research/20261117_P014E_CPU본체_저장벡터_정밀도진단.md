사용자158/원장65의 독립 CPU 분석이다. 기존 CPU 연산 25개 중 본체 3건의 수치 음성은 유지한다. 모델·커널·ABBA를 다시 실행하지 않는다.

## 권한과 영향

새 CPU 숫자 분석 helper/시험/driver와 evidence만 만든다. `p014e_direct_cpu.c/.py`, 기존 모델·커널·profile·NPZ·packed 파일은 바꾸지 않는다. 기존 원소별 출력과 payload 해시를 읽고, 별도 NumPy 5트릿 복원과 FP64·512자리 Decimal 내적을 계산한다. 새 파일은 메타데이터/작은 oracle NPZ이며 weight/CP는 쓰지 않는다. 모델 클래스·Triton·C ABI·만료된 controller를 호출하지 않는다. 데이터 마이그레이션과 환경·패키지·GPU 영향은 없다. 단위시험3개는 그룹 끝 padding, 알려진 cancellation의 정확한 합, 잘못된 코드/shape 거부를 확인한다. 결과099/계획P014E·목록·기준표·METHODS·COMPASS를 실제 범위로 갱신한다. 후속의 원 FP32 경로 정합·전체 decode·40MiB/품질 검증은 남는다.

## 1. 왜

원 C는 FP32 weight를 만들고 FP64로 누적한 뒤 FP32로 출력한다. Torch 참조는 복원한 FP32 weight에 F.linear를 적용한다. 이런 연산 차이가 저장된 세 음성에 얼마나 관여했는지 아직 독립 기준과 대조하지 않았다.

## 2. 질문

원 payload를 독립 복원한 같은 FP32 행렬의 FP64 내적은 저장된 C 출력과 어떤가? 원 미달 원소에서 512자리 Decimal 내적에 더 가까운 쪽은 무엇인가?

## 3. 예측

FP64 누적 C가 독립 FP64 내적과 같거나 가깝고, 원 FP32 참조의 누적 차이가 음성 원소에 나타날 수 있다. 반대로 복원·입력·C 구현에 차이가 있으면 그 가설은 지지되지 않는다. 어느 결과도 원 FP32 참조 문턱을 바꾸지 않는다.

## 4. 단계

1. 기존 `model0_matrix000/002`의 M1/M8 네 조건을 고정한다. 세 원음성과 같은 행렬의 통과 M1 대조를 포함한 사후 진단이다. 원 profile·활성값/출력 NPZ와 native32K packed payload SHA를 확인한다.
2. 원 payload 하나를 weights_only/CPU로 읽어 지정 두 행렬의 코드·scale만 분리한다. 모델·operator 객체를 만들지 않는다. NumPy의 독립 5트릿 decode로 FP32 weight를 복원한다.
3. 네 조건에서 FP64 dense dot과 FP32 cast를 계산해 저장 actual/reference와 비교한다. 원 atol2e-6/rtol2e-5의 실패 집합이 원 report와 같은지 확인한다. 원 C/Torch 연산은 호출하지 않는다.
4. 원 실패 원소 전부에 FP32 입력/weight 값을 Decimal로 옮겨 512자리 곱·합을 한다. Inexact 플래그를 확인하고 각 저장 출력의 절대오차를 기록한다. 대상이256원소를 넘으면 줄여 채택하지 않고 중단한다.
5. 원 입력/source SHA 불변·CUDA 미초기화·payload tensor 해제와 프로세스 종료/실제 시간을 회수한다. NumPy 전체 참조의 weakref 해제 계측은 없으며 RSS는 종료 시점 표본이다. 별도 저장 결과 재검산에서 원 실패3·대조1과 Decimal 오차 관계를 다시 읽는다.

## 5. 판정

완료는 네 조건의 원자료/원 실패 집합·독립 계산·불변/프로세스 종료가 닫힌 상태다. 가설의 지지 여부는 따로 기록한다. 원 3건을 PASS로 바꾸거나 새 body 경로를 채택하지 않는다. 이 두 행렬의 수치 원인을 전체 모델·GPU·품질로 일반화하지 않는다.

## 6. 비용

CPU 최대5분·단일 process/기존환경·packed 입력 약23MB/작은 NPZ, 가용RAM1GiB 선결·출력20MB 이하/파일이다. 모델·원 체크포인트·C 실행/컴파일·GPU·설치·다운로드0이다.

## 7. 실행

새 `diag_p014e_stored_dot_error.py prepare/actual`을 기존 CPU Python/runlog099로 실행한다. 새 학습·모델 배치는 만들지 않는다. 현재16:40/17시 경계를 유지한다.

## 8. 한계

원 source의 합성 입력이며 실제 모델 hidden이 아니다. 선택은 원 음성을 본 뒤 했으므로 성능·일반화 추정이 아니다. FP64/Decimal에 가까워도 원 FP32 baseline과의 실제 decode 정합은 별도다. 새 속도/메모리 절감·언어품질이나 배포 기본 채택을 주장하지 않는다.

## 9. 이력

원 CPU1/CPU4 전체 ABBA는 재사용한다. 새 oracle 진단은14:31:03KST 실제0·1.217281초로 닫혔다. 네 조건의25,344개 C 출력이 독립 FP64 cast와 비트 동일했고 원 미달8원소의 정확 내적은 모두 C에 더 가까웠다. 별도 Fraction/저장 출력 readback도0이다. 원 FP32 게이트3음성·전체 본체 미완은 보존한다. 상세는 [결과099 §19](../../test_result/099_20260925_P014E-회전-동치만-통과하고-배포손익은-미측정.md#p014e-cpu-stored-dot-precision)이며 새 원명령/소스/NPZ를 보존했다.
