# 핸드오프 시각 검사의 경로 증거 복구

원장99의 미완인 Git 경로 추적 오탐을 사용자104의 정제 외 CPU 연구 범위에서 처리한다.
모델·학습·정제·과거 핸드오프 내용은 변경하지 않는다. 현재 GPU의 동결 source 두 목록에
수정할 시각 검사기는 포함되지 않음을 먼저 확인했다.

## 실제 원인과 대안

과거 한 파일의 최초 커밋을 찾는 `--follow --diff-filter=A`는 유사도가 높은 다른 이름의
핸드오프를 따라갔다. 현재 경로의 실제 추가는16:47:41인데 다른 이름의05:19:58을 가져와
15:36 파일명을 미래라고 거부했다. 동일 명령의 재현에서도 같은 시각 차이가 났다.

| 안 | 방법 | 장점 | 한계 |
|---|---|---|---|
| A | 정확 경로의 추가만 `--no-renames`로 조회 | 현재 파일명과 그 경로의 존재 증거를 직접 연결, 작은 수리 | 다른 이름으로 존재하던 내용의 최초 집필 시각은 주장하지 않음 |
| B | 실제 rename/copy 계보 전체를 별도 복원 | 내용의 오래된 계보도 보존 가능 | 유사도 추정과 파일명 시각을 다시 혼동할 위험, 구현 범위 큼 |
| C | 원 도구를 유지하고 사례를 수동 제외 | 소스 변경 적음 | 같은 오탐 재발과 무효 개명 위험 |

A를 적용한다. 허용10분·미래 방향만의 비교·author 시각·커밋 없을 때mtime fallback은
그대로다. 정확 경로의 최초 추가와 다른 이름의 내용 계보를 구분한다. 과거 원로그1과 원소스는
별도 감사 경로에 보존하고 해당 핸드오프를 개명하거나 본문을 고치지 않는다.

## 영향과 검증 계획

수정은 `scripts/handoff_time.py`의 Git 조회 옵션과 설명, 새 CPU 회귀와 공용 정적 suite의
시험 연결에 한정한다. 사용자 전체 정적에도 새 회귀가 하나 추가되지만 기존10분 기준과
모델 스모크 팔은 바꾸지 않는다. 새 시험이 실패하면 정적도 실패하며 예외 목록을 추가하지 않는다.
회귀는 잘못된 경로 추적을 막는 옵션, 여러 추가의 가장 이른 시각, 불완전 Git 출력·오류의
fallback, 경계10분과 실제 미래 오탐 방지를 포함한다. 실제 과거 한 사례와 공개 핸드오프
경로 metadata 전수도 별도 읽기 검사한다. 현재 파일 내용·정제 전용 경로는 읽지 않는다.

실제 완료와 새 정적 수는 회수 뒤 기록하며, 이 설계만으로 통과를 주장하지 않는다.

## 실제 CPU 회수

원 사례는 수리 전 실제1, 수리 뒤 실제0이었다. 새 CPU9는 실제0이며 공개 핸드오프 이름
200개도 실제0/정합200·모순0·건너뜀0이었다. 전수는 이름/파일 metadata와 Git 기록을
사용했고 과거 핸드오프 본문을 수정하지 않았다. `handoff/audit/nov01_independent/
handoff_time_repair_v1/`에 원소스·원실패·새 원로그3개와 before/after 영수증을 보존한다.
현재 저장소의 Git 변경·모델 실행·정제 작업은0이다. 새 공용 정적 suite의 회귀 항목은
1개 늘었으며, 후속 전수 실제 수는 별도 새 영수증으로 회수한다. 이전70 판정을71로 고쳐
쓰지 않는다. GPU에서 진행 중인 평가의 source 목록과 내용도 변경하지 않았다.


새 AFTER_PROVENANCE_STATIC_v1은 실제0/71PASS·0ERROR·6NOT_RUN이었고254개 명시
입력의 전후 hash가 같았다. 새 회귀1개가 실제 실행된 증가이며 기존 검사 항목을 빼거나
실패 문턱을 낮추지 않았다. 전용 입력 수집 범위와 전체 사용자 검사의 범위 차이는 별도
입력범위 정정문서의 한계를 그대로 따른다.
