# NVML 조회 지연의 복구 — 모델/평가기 본문과 감시 경로를 분리

MMLU Native5 전량이893.424초에 `nvidia-smi`3초 timeout 3회 연속으로 HOLD8이 됐다.
총 실패13회/유효조회1,122회·공유증가 최대약1.835GB였고 최종 소유CUDA0·source/CP 불변이다.
OOM/내용 품질 음성이 아니다. 원 report/로그/소스/부분 토큰길이는 보존한다. actual_rows0은
확정된 공식 결과0이라는 뜻이며15분 동안 GPU를 전혀 쓰지 않았다는 뜻이 아니다.

## 대안과 판단

| 안 | 내용 | 장점 | 단점 | 영향도 | 비용 |
|---|---|---|---|---|---|
| A | 지속 NVML C API 자식 프로브를 사용하되 전체 질의3초·연속실패3·주기0.5초·8GB제한 유지 | 매번SMI 생성 비용 제거·timeout은 자기 프로브만 종료·누락구간 공개 | API/IPC/자식종결 회귀와 실물 대조 필요 | 새 opt-in 감시·명시 복구 adapter | CPU fixture+최대3분 read-only GPU probe |
| B | SMI 한 조회 timeout을10초 이상으로 늘림 | 변경 작음 | 무계측 구간이 길어지고 근본 overhead가 남음 | 기존 감시 정책 변경 | 낮지만 안전 해석 변경 |
| C | 기존 SMI 유지·짧은 실험만 수행 | 코드 변화0 | 긴 전체평가가 다시 중단될 수 있고 확정 전 결과를 잃음 | 없음 | 재실행 비용 증가 |

A를 권장한다. 후보 모듈은 작성했으나 **아직 채택/실물 검증하지 않았다**. 이 비교/영향표와
CPU경계·idle/busy실측을 닫은 뒤에만 새 실험 adapter에 연결한다. A가 불가능하면 B를 자동
채택하거나 질의를 무시하지 않고 원HOLD를 남긴다. 3회 실패 정책과마감은 완화하지 않는다.

## 경로별 허용표와 영향

| 경로 | 동작 | 권한 | 제외 |
|---|---|---|---|
| `scripts/p106b_nvml_probe.py`·CPU시험 | read-only NVML IPC/owned subprocess·기존watcher상속 | 사용자104·8GB/11시 독립연구 | 새설치/CUDA모델/다른PID종료0 |
| 별도 실물 probe/복구 driver·CPU시험 | idle/busyAPI대조·고정한 old평가본문의 명시경계 주입·새source/profile/namespace | 같은 허가 | 원MMLU/GSM/P107 source 수정0·품질 기준 변경0 |
| 새 Stage13 CPU/GPU SH·registry·감사결과 | 회귀→실물→조건부복구 실행·실측 보존 | 같은 허가 | 정제/추가300M/삭제/Git0 |
| 결과101/계획/기준표/방법론/COMPASS·이쪽원장 | HOLD원인/새경로/미완/실제회수 기록 | 같은 연구절차 | 원실패 덮어쓰기0 |

코드 영향은 조회 경로/실험 실행 경계에 있다. 원 sampler/모델/likelihood/공식task/metric은
변경하지 않는다. 기존 P107 watcher의 run/3회중단을 상속한다. 새 adapter는 oldmodule을
private namespace로만 적재하고 허용 경계(감시·identity·profile검증·출력위치·계측)와 원함수
AST를 기록한다. 이전 성공 source파일은 그대로 남기므로 과거검증의 입력을 소급 바꾸지 않는다.

데이터/권한 영향은 새성공·부분결과의 별도저장뿐이다. 명시모델과 공식자료/0·5shot/한도는
보존한다. 실제삭제·설치·다운로드·정제전용경로는0이다. CUDA학습/optimizer/새체크포인트도0이다.
시험은 프로브timeout/재사용/형식·소유자식종결/3회정책·원평가본문동등성·실물메모리대조를
다룬다. 새문서/원장으로 원HOLD와 후속을 연결한다. 기술부채는 새opt-in 경계에 제한한다.

## 실측과 판정

설치된 `/usr/lib/wsl/lib/libnvidia-ml.so.1`의 `nvmlDeviceGetMemoryInfo`만 읽는다. CPU
fixture는 실제NVML/GPU를 열지 않는다. 실물은 idle와작은GEMM부하에서 SMI와지속프로브를
교대로 읽어값/시각/지연·실패·첫시작/재시작·마지막자식종결을 기록한다. 두 조회는 동시가
아니므로 공유GPU의변화를 API오류로단정하지 않는다. busy부하도8GB보다훨씬작은임시텐서만
사용하고 학습·모델·파일저장은0이다. Tensor/프로브해제와deadline을검산한다.

실물 대조가 맞고 자식/오류경계가닫힌경우에만 **새 단계와 source/profile**에서 MMLU5shot 및
GSM8K를 복구한다. 원래확정한0shot을 다시돌리지 않는다. query timeout을 묵인하거나 누락
구간의정확peak/OOM안전을 주장하지 않는다. 성공하면 조회 경로의 비용 개선이며 모델 학습/
생성 속도나 지능 향상으로 승격하지 않는다.

긴 MMLU의 후행계측은 중간중단에도 완료된forward요청/실제경과/메모리peak를 남기도록
별도wrapping한다. 공식점수는 여전히전량완료후만 확정한다. 저장한부분계측을 점수cache로
재사용하거나 자동재개하지 않는다.

이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.

## v1 실물 음성과 v2 정의 수리

Stage13bW는80쌍 모두 조회됐으나 v1 NVML used와 SMI used가 약314MiB 달라 종료9였다.
일차 구조를 데이터에 맞춰 억지 보정하지 않고 v1 코드3개와 원결과를 보존했다.
NVML v2는 예약 메모리를 별도 필드로 제공한다. 이 장치의 한 점 대조에서는 v2 used가
SMI used와 맞고 reserved 약315MiB가 별도로 나타났다. 수동 상수 차감은 사용하지 않는다.
문헌의 일반 설명만으로 OS별 의미를 단정하지 않고 같은 장치에서 used/free/total/reserved를
새80쌍으로 검산한다. CPU8개와 새 Stage13aWb/bWb·v2 출력에서만 진행한다.
이 단계는 모델/GPU 품질이나 장기 감시 신뢰성의 증거가 아니다.

- NVIDIA 공식 API: https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html
- NVML v2 구조: https://docs.nvidia.com/deploy/nvml-api/latest/api/structnvmlMemory__v2__t.html


v2 새80쌍은 실제0이고 used 최대차1,359,872B였다. busy 조회 중앙값은 SMI37.410ms 대
지속0.323ms였으며 모델속도 비교가 아니다. MMLU는 원51파일을 유지한 private복구를 사용한다.
GSM은 아직 GPU가 한 번도 실행되지 않아 별도GSM source/profile/출력에서 직접 경계를
연결한다. 과거56소스/원CPU계약과 bootstrap후56소스는 각각 별도로보존한다.
따라서 위의 원GSM source수정0은 이전예상이며, 실제허용범위는 새GSM driver 감시/계측
연결과 기존helper의경로bootstrap 수리이다. sampler/공식prompt/metric 변경은0이다.
