## 1. 왜 지금 이걸 보는가 — 우리 숫자가 말이 안 된다

| | 파라미터 | CPU 1스레드 tok/s | 방식 |
|---|---|---|---|
| T-MAC / BitNet-b1.58 | **3,000M** | **30** (M2-Ultra) | LUT, **역양자화 없음** |
| **우리 `p6d`** | **132M** | **36** | fp32 dequant 후 GEMM |
| **우리 `mC` int8** | 132M | **16.1** | int8 → **fp32 복원** 후 GEMM |

**모델이 23배 작은데 속도는 1.2배다.**
⚠️ CPU(M2-Ultra vs 사용자 x86)·컨텍스트·측정 방식이 달라 **정밀 비교가 아니다.**
그래도 자릿수 격차는 조건 차이로 설명되지 않고, **원인 후보가 하나로 좁혀져 있다.**

그리고 우리는 이미 그 원인을 세 갈래로 만났다:

| 관측 | 출처 |
|---|---|
| int8 저장이 **CPU 속도를 −62~67%** 로 만든다 | 결과 016 §10·§12 |
| 그 대가가 **층당 +2.1~2.2ms**, 세 모델이 거의 동일 = **분리된 unpack 고정비** | 결과 014 §11.4 |
| **CUDA 에서는 −12~15% 뿐**(1/5) = 대역폭 문제이지 알고리즘 문제가 아니다 | 결과 016 §12.3 |

T-MAC 초록의 한 문장이 우리 상황을 그대로 서술한다:

> *"Existing systems, lacking native support for mpGEMM, resort to dequantize weights for high
> precision computation. Such an indirect way can lead to a significant inference overhead."*

**우리 `TLinear._wq_from_i8()` 이 정확히 그 "indirect way" 다.**

## 2. 용어 정리 (이후 설명에 계속 쓴다)

| 용어 | 뜻 | 우리 코드에서 |
|---|---|---|
| **mpGEMM** | mixed-precision GEMM. **저정밀 가중치 × 고정밀 활성값** 행렬곱 | `F.linear(x, wq)` — 지금은 `wq` 를 fp32 로 올려서 한다 |
| **역양자화(dequantize)** | 압축된 가중치를 계산용 정밀도로 되돌리는 것 | `_wq_from_i8()` = int8 코드 × α → fp32 |
| **LUT (lookup table)** | 미리 계산해 둔 결과표. 곱셈 대신 **조회**한다 | 없음 |
| **bit-serial** | w비트 가중치를 **1비트 평면 w장**으로 쪼개 각각 처리 | 없음 |
| **그룹 스케일** | 가중치 N개마다 실수 배율 α 하나 | `micro_group=128`, α는 그룹 최대/평균 |
| **활성값 양자화** | 활성값도 int8 등으로 낮추는 것 | **안 한다**(fp32/bf16) |

## 3. T-MAC 의 원리 — **왜 곱셈이 사라지는가**

### 3.1 핵심 착상

1비트 가중치는 값이 **두 개**뿐이다(+1/−1). 그러면 **1비트 벡터 4개짜리 묶음**이 가질 수 있는
패턴은 `2⁴ = 16` 가지밖에 없다.

활성값 벡터 `a = [a₀, a₁, a₂, a₃]` 가 주어지면, **16가지 패턴 전부와의 내적을 미리 계산**할 수 있다:

```
표[0000] = −a₀ −a₁ −a₂ −a₃
표[0001] = −a₀ −a₁ −a₂ +a₃
...
표[1111] = +a₀ +a₁ +a₂ +a₃      ← 16칸짜리 표 하나
```

이 표를 만들어 두면, **가중치의 4비트 묶음은 그냥 표의 인덱스**가 된다.
행렬곱이 **"조회 + 덧셈"** 으로 바뀌고 **곱셈이 사라진다.**

### 3.2 여러 비트폭은 어떻게 하나 — bit-serial

2비트 가중치는 **1비트 평면 2장**으로 쪼개고 각각 LUT 를 돌린 뒤 자릿값(1, 2)으로 가중합한다.
그래서 논문이 *"kernels scale linearly to the weight bit-width"* 라고 한다.
**비트폭이 몇이든 같은 커널이 돈다** — 이게 T-MAC 의 "unified and scalable" 주장이다.

### 3.3 실제로 어려운 점 (논문이 든 두 가지)

| 문제 | 내용 | T-MAC 의 해법 |
|---|---|---|
| **표 접근이 무작위다** | 가중치·활성값은 연속 접근인데 LUT 는 인덱스가 흩어져 있다. 캐시를 놓치면 이득이 사라진다 | **표를 레지스터(온칩)에 상주**시킨다 — 축 재정렬(axis reordering)과 타일링으로 표 재사용 극대화 |
| **표가 온칩 메모리를 먹는다** | 활성값 × 모든 비트 패턴을 저장해야 하므로 종전 mpGEMM 보다 온칩 사용량이 **늘어난다** | **table quantization**(표 자체를 낮은 정밀도로) + **mirror consolidation**(부호 대칭성 이용 — `표[¬p] = −표[p]` 이므로 절반만 저장) |

> **★이 두 문제가 우리에게 그대로 온다.** 우리 모델은 작아서(dim 768) 표 재사용 기회가
> 3B 모델(dim 2560+)보다 적다 → **§6 의 최대 리스크**.

### 3.4 논문의 결론 문장 하나 — 우리 관측과 정확히 만난다

> *"T-MAC makes the LLM inference speed on a CPU comparable or even higher to the GPU on the same
> device, mainly because T-MAC has no conversion cost."*

**우리는 결과 016 §12.3 에서 이미 "GPU 가 CPU 1스레드의 1.18배뿐" 을 관측했다.**
논문은 그 현상을 **역양자화 비용 제거로 설명**하고, 우리는 **그 비용을 아직 지불하고 있다.**

## 4. bitnet.cpp 는 T-MAC 과 무엇이 다른가

| | **T-MAC** | **bitnet.cpp** |
|---|---|---|
| 논문 | arXiv:2407.00088, EuroSys 2025 | arXiv:2502.11880, ACL 2025 |
| 대상 | **임의 저비트**(1·2·3·4bit …) | **삼진 전용**(BitNet b1.58 계열) |
| 방식 | **bit-serial LUT** — 1비트 평면으로 쪼갠다 | **TL(Ternary Lookup Table)** — 삼진을 **직접** 색인 / **I2_S**(int2+scale, **무손실**) |
| 장점 | 범용. 비트폭에 선형 | 삼진에 특화돼 **공간 효율이 좋다**(논문이 "spatial inefficiencies of previous bit-wise methods" 를 지적) |
| 보고 성능 | llama.cpp 대비 최대 **4×**, 에너지 −70% | 전정밀 대비 최대 **6.25×**, **저비트 기존 대비 최대 2.32×**(= T-MAC 대비). x86 **2.37~6.17×**, ARM **1.37~5.07×**, 에너지 x86 −71.9~82.2% / ARM −55.4~70.0% |

### ★한 줄 정리

> **T-MAC = 범용 저비트 LUT 엔진. bitnet.cpp = 삼진 전용으로 더 조인 것.**
> **우리는 삼진이다 → bitnet.cpp 쪽이 원리적으로 더 맞고, 실제로 T-MAC 대비 최대 2.32× 를 보고한다.**
> 다만 **범용성은 T-MAC 이 높아**, 우리 `sparse34`(1.25bpw) 같은 비표준 포맷을 실험할 여지는
> T-MAC 쪽이 크다(단 §5.3 참조 — 그대로는 안 된다).

## 5. ★우리 구조와의 대조 — 같은 것, 다른 것, 안 되는 것

### 5.1 ✅ **잘 맞는 것** (그대로 이어진다)

| 우리 | 그쪽 | 왜 맞나 |
|---|---|---|
| 가중치가 **삼진 {−α, 0, +α}** | BitNet b1.58 = 삼진 | **완전히 같은 값 집합.** TL 커널의 설계 전제 그대로 |
| **CPU·엣지 배포가 목표** | 둘 다 CPU/엣지 전용 | 목표 함수가 같다 |
| **배치 1 디코드**가 주 시나리오 | 논문 벤치도 token generation | 우리가 재는 것과 같은 양 |
| 병목이 **역양자화** | 논문이 지목한 바로 그 문제 | 결과 014 §11.4·016 §12 가 실측으로 확인 |
| **`mC`(g8)가 유력 후보** | 순수 삼진, 특수 포맷 없음 | **TL/I2_S 가 그대로 받는다** |

### 5.2 ⚠️ **확인이 필요한 것** (맞을 수도, 아닐 수도)

| 항목 | 우리 | 그쪽(추정) | 왜 문제인가 |
|---|---|---|---|
| **스케일 단위** | **`micro_group=128`** — 가중치 128개마다 α 하나 | BitNet b1.58 은 **텐서 단위 absmean** 스케일이 원형. I2_S 의 "Scale" 이 어느 단위인지 **미확인** | 그룹 스케일이면 LUT 결과에 **그룹마다 다른 배율**을 곱해야 한다. 커널이 그걸 지원하지 않으면 **α 적용을 밖에서 해야 하고**, 그러면 이득이 깎인다 |
| **α 계산 방식** | TWN 임계(`thr_ratio=0.7`) + **L2-optimal α** | BitNet = absmean 반올림 | 값이 달라도 **커널은 상관없다**(코드 + 스케일만 받으면 된다). 단 **정확도 비교 시 조건이 다르다** |
| **활성값 정밀도** | **fp32/bf16** | BitNet b1.58 = **W1.58A8**(활성값 int8) | 활성값이 int8 이어야 LUT 표가 작아진다. 우리가 fp16/fp32 활성값을 유지하면 **표가 커져 온칩에 안 들어갈 수** 있다 |
| **모델 규모** | dim 768 / ffn 2048 / 20층 | 3B급(dim 2560+) | **표 구축 비용의 상각**이 다르다. 작은 행렬은 표 만드는 비용 대비 재사용이 적다 → **이득 축소 가능** |

### 5.3 🚫 **적용 안 되는 것** (구조적으로)

| 항목 | 왜 안 되나 |
|---|---|
| **`sparse34`(mA, 1.25bpw)** | 우리 3:4 준정형은 **4개 가중치를 5비트 코드 하나**로 묶는 포맷이다. TL 은 삼진 색인, T-MAC 은 **1비트 평면 bit-serial** — **둘 다 이 코드북을 모른다.** 쓰려면 **우리가 커널을 새로 짜야 한다** |
| **`--infer-repeat`(P031) 같은 동적 스케줄** | 커널 층위와 무관하므로 실제로는 문제없다. 다만 **GGUF 로 내보내면 그런 실험 플래그가 전부 사라진다** |
| **학습 경로** | 이 커널들은 **추론 전용**이다. 우리 STE·어닐·KD 는 PyTorch 에 남는다. **학습이 빨라지지 않는다** |
| **`paired_eval.py`·`common_bpb.py` 등 평가 도구** | PyTorch 텐서를 전제한다. GGUF 경로로 가면 **평가 체계가 갈라진다**(§7 의 최대 비용) |

### 5.4 ★★그리고 하나 — **P034 단계3C 는 P014 가 삼켜 버린다**

우리는 방금 **언팩 캐시**로 `mC` +17%(대가 걷어내면 약 1.7× 추정)를 만들었다(결과 016 §14).
**LUT 커널에는 언팩 자체가 없다.** 즉:

> **단계3C 는 P014 가 오면 무의미해지는 임시 방편이다.**
> ⚠️ **그렇다고 3C 가 헛일은 아니다** — P014 는 착수 조건이 크고 실패할 수 있는 반면
> 3C 는 **오늘 완료 직전**이고 순수 PyTorch 다. **보험으로 완주할 값어치가 있다.**

그리고 **타잉(g)은 LUT 이득과 직교한다** — LUT 표는 **활성값**에서 만들어지고 활성값은 층마다
바뀌므로, 가중치를 공유해도 **표를 재사용할 수 없다.** 3C 에서 얻은 "타잉이 속도를 번다" 는
**언팩 경로 한정의 성질**이다.

### 6.3 ★기대치를 미리 못 박는다

우리 `mC` int8 은 **16.1 tok/s(62.3 ms/토큰)** 이고, 결과 014 §11 의 분해로는
**고정비 a ≈ 4.2ms(모델 밖: LM 헤드 + top-k) + 층당 b**다.

- 언팩(약 2ms/층 × 20 = 40ms)이 **전부 사라진다**고 가정하면 → 약 22ms/토큰 = **45 tok/s**
- 여기에 LUT 자체의 덧셈·표 구축 비용이 더해지므로 **그보다 낮다**
- **고정비 4.2ms 는 커널로 안 줄어든다**(LM 헤드는 별개 문제 — §5.3)

> **★현실적 기대: `mC` int8 16.1 → 25~40 tok/s.**
> **"6.17×" 를 그대로 인용하면 안 된다** — 그건 **전정밀 대비**이고 **3B 모델**이며
> **우리 고정비를 포함하지 않는다.** 결과 016 §7.4 가 "2.64× 가 실제로는 2.11× 였다" 로 데인
> 것과 정확히 같은 종류의 오류가 된다.

>
> A 가 **이득 없음**을 보이면 P014 는 거기서 끝난다. **그게 값싼 결말이다.**

## 9. ★`mA` vs `mC` 에 미치는 영향 — REVIEW1 재확인

REVIEW1 은 **`m100R1c`(mC) 기본 확정 권고** 상태였고(결과 024), `mA` 가 앞서는 축은
**저장 MB 0.7% 하나**로 줄어 있었다(결과 021·024). 이번 실사가 하나를 더 뺀다:

| 축 | mA | mC |
|---|---|---|
| 품질 | 열세(021·024·011 §1, 부호 3/3 일치) | **우세** |
| 상주 | 96.2MB | **86.9MB** |
| 저장(이론) | **12.4MB** | 13.1MB |
| **LUT 커널 적용성** | 🚫 **비표준 포맷이라 불가** | ✅ **그대로 적용** |
| 3C 언팩 캐시 이득 | +11.3% | **+17.1%** |

> **→ `mA` 가 앞서는 유일한 축(저장 0.7%)은 R8 패킹이 있어야 실물이 되는데,
> 그 R8 을 실현할 가장 유력한 경로(LUT 커널)가 `mA` 포맷을 지원하지 않는다.**
> **REVIEW1 의 mC 권고가 한 단계 더 굳어졌다.**
> ⚠️ 단 이건 **"현 시점의 외부 도구 생태계" 근거**이지 아키텍처 근거가 아니다.
> 우리가 커널을 직접 짜면(안 C) 뒤집힐 수 있다.
