# P106B 교사 프롬프트 품질과 사고·출력 상한 재검토

> 최신 갱신일자: 2026-09-30 · 문서 유형: live
> 근거: [결과101 §36](../test_result/101_20260927_P106B-번역9건으로-문턱미달-학생학습0.md), [P106B 계획](../test_plan/P106B_Bonsai-자동번역-pseudo-SFT-온라인-교사학생-검증.md).
> 코드 구현·CPU 검사와 새 교사/학생 실행을 분리한다. GPT GPU·모델 실행0.

## 1. 결론

교사 생성·태그 파서·canonical 래퍼는 실행되고 있다. 새 v31에서는 한국어 다중답도 두 번 완결돼4행을 만들었다. 학생 교육이 시작되지 않은 직접 원인은 그 후보들의 잘못된 용어와 언어별 선별 문턱이며, 실험 전체가 구현 불가능하다는 증거가 아니다.

실제 요청은 질문을 보존하라고 하면서 입력 질문 자체의 오조어를 거부했다. 재시도에는 상태명만 전달돼 어떤 문구를 어디서 고쳐야 하는지도 불명확했다. 이는 프롬프트·게이트 계약의 개선 대상이다. 원형을 고치거나 옛 음성을 PASS로 바꾸지 않는다.

## 2. 프롬프트 품질 감사와 개선

| 실제 경로/문제 | 영향 | 구현한 개선 | 한계 |
|---|---|---|---|
| single/multi가 각각 긴 지시를 조립 | 같은 repair 목적의 문구가 갈라질 수 있음 | content_instructions를 공동 사용 | 실제 준수는 새실행 필요 |
| repair의 질문 보존 vs 잘못된 질문 용어 | `열불견증`이 질문에 복제돼 내용 검사에서 탈락 | 의도/요구범위/숫자/개체를 보존하되 질문의 오조어도 수리하도록 명시 | 자동으로 임상 정답을 보장하지 않음 |
| 상태명만 주는 retry_hint | 구체 문제·위치가 전달되지 않음 | 문제 문구·role/message/span과 행동 지시를 구조화한 retry_feedback | 심층 사실오류는 별도 검토 |
| answer와 answer_variants 첫 항목 중복 | 입력 토큰·반복 원문 노출 증가 | 교정 payload는 질문과 답 변형 목록만 전달 | 이전 payload와 다른 새버전 |
| 잘못된 전문용어를 supported fact처럼 보존 | 잘못된 원문이 교사 답에 복제 | 불확실하면 일반어/확인 필요 표현, 근거 없는 진단/사실/인용 추가 금지 | 기존 영어 초안도 독립 gold가 아님 |
| JSON/ChatML까지 교사에 맡길 가능성 | 역할/마스크/형식 혼동 | 콘텐츠 태그만 교사가 만들고 역할·JSON·ChatML·loss mask는 코드가 소유 | 라벨 완결≠진실성 |
| 내용과 배선 성공의 혼합 | 한 불량 문항이 모든 자료 확보까지 막음 | 사용자A: 소형은4프로필 파서/양어휘 배선, 전체96은 언어별75% 내용/문맥 선별 | 나쁜 행을 교육하지 않으며 전체 문턱 유지 |

새 repair 핵심은 “원문 문자열 자체”가 아니라 “의도·요구사항·부정·숫자·단위·개체·불확실성”을 보존하는 것이다. 질문/답에서 오조어를 고칠 수 있고, 내용 부족을 새 사실로 메우지 않는다. 전문 이름을 확정할 근거가 없으면 불확실성을 명시한다.

출력 예시와 학생 전달 경로:
`교사 최종 태그 → 엄격한 파서 → canonical messages/meta → 양어휘 길이/assistant-only mask → 내용선별 selected → 공통 train/val → 학생`.
사고 문자열은 raw sidecar에만 남고 학생 messages에는 넣지 않는다.

## 3. low가 medium보다 빨랐다는 실측을 어떻게 읽나

[Stage2h 원본](../test_result/101_log_20260928_P106B_Stage2hW_effort_profile.txt)은 같은4문항/seed/thinking sampler·ctx6144/max2048에서 요청 순서를 교차했다.

| 요청 라벨 | completion(사고+최종) | 요청 wall | completion/요청초 | 형식 완결 |
|---|---:|---:|---:|---:|
| low |5,166|83.406|61.938|4/4|
| medium |7,531|121.882|61.789|2/4|

**이 표본에서는 medium이 더 빠르지 않았다.** medium은 약1.458배 더 많은 token을 생성했고 요청시간도약1.461배였다. tok/s 차이는약0.24%로 작은 기술 관측이며 품질 우열/통계 유의성을 뜻하지 않는다. medium의 미완결2건은2,048 상한에서 최종답 전 length였다.

현재 [모델카드](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf#best-practices)는 low의 짧은 사고 수준을 모델이 안정적으로 지원하지 않으며 xhigh에 가까울 수 있다고 안내한다. 이것은 API가 low를 거부한다는 뜻과 다르다. 실제 로컬 GGUF template는 low/medium/xhigh를 허용하고 서로 다른 자연어 사고 지시를 넣는다. 따라서 low와 명시xhigh가 항상 같은 출력/시간을 내는 것은 아니다.

[공식 알려진 문제](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf/blob/main/KNOWN_ISSUES.md)는 medium이 적당한 출력 예산에서 덜 절단되는 일반 경향을 설명한다. 현재 네 문항 실측은 좁은 예산/특정 소스의 반대 관측으로 그대로 보존한다. 둘 중 하나를 모든 문제의 일반 법칙으로 만들지 않는다. 과거 online low/medium은ctx3072/max2048 대ctx6144/max4096·원천·성공수·업데이트수도 달라 직접 비교하지 않는다.

**명시xhigh의 대응 실측과 답안 정답성 평가는 없다.** “low가 짧았다→xhigh도 더 빠르고 정확하다”는 추론은 성립하지 않는다. 사용자 선택에 따라 새 대응 시험에서 세 라벨을 직접 비교한다.

## 4. 사고 상한·총 출력·문맥은 서로 다르다

| 값 | 의미 | 이번 준비값 |
|---|---|---:|
| thinking_budget_tokens | 서버가 사고에 적용하도록 요청하는 수치 예산 |8,192|
| max_tokens | 사고와 최종답을 포함하는 총 생성 상한 |16,384|
| ctx-size | 입력+생성의 슬롯 문맥 용량 |32,768|

16,384는 “최종답만16,384”가 아니다. 사고를8,192까지 썼다면 나머지 총 예산에서 종료 제어/최종답을 만든다. 끝내기 메시지·토큰 경계 오버헤드 때문에 “최종답 정확히8,192 보장”이라고 말하지 않는다.

현재 [공식 runtime 안내](https://github.com/PrismML-Eng/Bonsai-demo#thinking)는 모델의 effort와 UI의 고정 token budget을 구분한다. llama-server는 top-level `thinking_budget_tokens`를 사용하며 template_kwargs 내부 값은 효과가 없다고 [공식 이슈 문서](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf/blob/main/KNOWN_ISSUES.md)가 명시한다. 현 b10743의 server/common 라이브러리 문자열에서도 해당 API/CLI 키를 확인했다. 이는 정적 지원 근거이며 새 실제 budget 적용·정확 사고 토큰수의 관측은 NOT_RUN이다.

로컬 GGUF header를 약11.1MB만 읽고 tensor payload/모델은 로드하지 않았다. context_length262,144·KV head4·key/value length256·full_attention_interval4를 확인했다. **262K 지원은16GB GPU에그대로 올려도 된다는 뜻이 아니다.**

[공식 context 안내](https://github.com/PrismML-Eng/Bonsai-demo#context-size)의FP16 KV64KiB/token과 일치하는 계산:
8K≈0.5GiB,32K≈2GiB. 8K→32K의KV 증분은약1.5GiB다. 현8K teacher-only global peak7,768MiB에 그 증분만 더하면9,304MiB라는 단순 참고값이 나오지만, workspace/allocator/입력크기·동시학생은 제외돼 실제 peak/OOM 안전을 보장하지 않는다. 새32K는 교사 단독 시험으로 먼저 확인한다. 온라인 교사+학생의 공유 예산으로 이 값을 승격하지 않는다.

63.49 completion tok/s를 그대로 가정하면16,384 상한까지약258초/요청이다. 종전 HTTP240초보다 길 수 있어 큰출력 요청 timeout을600초로 준비했다. 새12요청 상한 외삽은약51.6분이고 hard2h이며, 실제 길이·effort·완결률에 따라 달라진다.

## 5. 승인된 실험·판정

사용자는 같은상한/시드/수정프롬프트로 low/medium/xhigh를 각4문항·합계12요청으로 비교하는 A안을 선택했다. 같은 서버/가중치 한 벌에서 순서를 교차하고 반복질문 재시도는 하지 않는다. 설정별 완결/양마스크·내용 이슈·총 token/wall·유효 후보율과 actual final을 별도 보존한다. 다른 설정에서 같은 답이 나오면 대응 관측으로 보존하고 전역 중복제거로 불이익을 주지 않는다.

자동으로“더 정확한 effort”를 선정하지 않는다. 사용자가 원답/분모를 확인해 기술적으로4프로필을 완성한 설정을 번호로 선택한다. 이후 새소형 배선→전체96 교정→공통자료→두부모4epoch→원답 비교 순서다. 전체 언어별75%와 데이터/마스크/계보 선결은 유지한다. 새단계는 v32와 별도 teacher/child 태그에만 기록한다.

과거 valid gate-negative는 유효한 당시 판정이다. 새로운 목적의 배선 gate로 이름을 바꿔 옛 결과를 PASS로 소급하지 않는다. 잘못된 후보를 교육에 넣지 않는다. CPU mock PASS나 모델카드 주장은 새로운 완결률·학생지능·정답성의 실측이 아니다.
