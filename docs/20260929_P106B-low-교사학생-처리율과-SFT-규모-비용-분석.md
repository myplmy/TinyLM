# P106B low — 교사·학생 처리율, 유한 SFT 규모와 자원 배분 분석

> 작성일: 2026-09-29. 근거는 사용자 [Wg low1 원본](../test_result/101_log_20260929_P106B_Stage2iWg_online1_public_low.txt), exact v17 manifest/샤드와 공개 source deck이다. 모델·GPU·학습을 재실행하지 않았다. 아래 `관측`, `계산`, `가정 외삽`, `미실행`은 서로 다른 증거 수준이다.

## 1. 결론 — 속도 숫자의 분모부터 구분한다

교사는 학습하는 것이 아니라 **고정 Bonsai 모델로 추론해 교육 자료를 만든다**. 가중치 업데이트는 학생에게만 있다. 사용자 교사 단독 약60토큰/초와 이번 **61.43 completion 토큰/초**는 수치상 비슷하지만 prompt·계측 구간이 같지 않아 공존 감속 없음의 정밀 대조는 아니다. 이번 **6.04토큰/초**는 교사 decode 속도가 아니라, 사고·형식·폐기와 다른 tokenizer를 거친 **학생용 비패딩 대화 공급량/교사 요청 wall**이다. 둘을 비교해 교사 커널이10배 느려졌다고 말하지 않는다.

이번 자원 구성은 full-GPU teacher·P076 mean parent·legacy32 tokenizer·micro8×accum16/ckpt-on·compile/default다. 학생이 교사 생성 동안 대부분 유휴이고 클라이언트도 HTTP 하나씩 기다린다. 학생 자원을 떼어 준다고 한 요청 교사 처리량이 자동 증가하는 구조가 아니다. 유효 자료를 더 빨리 만들려면 (a) **한 서버 여러 활성 요청으로 weight reuse/continuous batching 검증**, (b) **한 요청의 사고를 여러 답에 공유하는 출력 설계 검증**, (c) **완성 자료의 제한적 학생 재사용**을 구별해야 한다. RAM 버퍼만으로 생성 비용을 해결하지 않는다.

## 5. 자원 배분·버퍼·“속도를 맞춘다”의 뜻

이번 구성에서는 학생이 교사 자료를 기다리는 시간이 대부분이다. 학생 계산을 **완전히 무료로 겹치고 교사도 전혀 느려지지 않는다**고 가정해도 `4,332.154/4,158.396=1.0418×`가 현재 한 업데이트의 이상적 overlap 이득이다. 같은 GPU의 실제 경합은 더 나쁠 수도 있다. 따라서 학생을 느리게 만들거나 자료를 수십 번 반복해 GPU 사용률을 채우는 것은 품질 향상 방안이 아니다.

신규 자료 공급6.04토큰/초와 cold 학생149.79토큰/초 사이에도 약24.8배 차이가 있다. 정상상태 학생 속도는 아직 미측정이며 후속 코드가 첫 microbatch·나머지15개·optimizer를 따로 기록하도록 보완했다. 재사용은 교사에게 같은 질문을 매번 다시 묻는 대신 **한 번 보존한 질문·답을 학생이 정확2~4회 처리**한다는 뜻이다. 새로운 지식이나 신규 생성속도를 늘리지는 않는다. 교사가 다음 개념을 만드는 동안 학생이 이미 만든 조각을 읽는 구조도 가능하다.

### 5.1 RAM10GB는 생성 병목의 해결책이 아니다

현재 canonical은0.265MB뿐이고 같은 밀도의 전체 공개 source 외삽은 약14~21MB다. raw는 대략89MB 규모의 거친 외삽이다. 이 규모에서는10GB RAM이 필요조건이 아니다. 학생용300M 가상 코퍼스가 같은 JSON 밀도면 약3.17GB지만 Python 객체·토큰캐시·raw는 별도다. **10GB 안에 든다고 보증하지 않는다.**

새 큐는 최대32행/20MB에서 backpressure를 걸고, 원형/선정 후보를20MB 이하 조각으로 durable 저장한 다음 학생에게 넘긴다. RAM은 흐름·복구와 반복 파일 읽기를 줄일 수 있지만 교사 추론60토큰/초를600토큰/초로 바꾸지는 않는다.

### 5.2 자원 활용 후보와 한계

| 후보 | 무엇이 달라지는가 | 먼저 확인할 것 |
|---|---|---|
| A1: 한 서버에 서로 다른 질문2개 동시 요청 | 교사 가중치 한 벌을 공유하고 두 sequence를 continuous batching할 수 있음 | slot별 context·GDN·student 공존 peak·실제 유효 자료 tok/s; 두 프로세스/두 모델 복제가 아님 |
| A2: 생산자·학생 소비자 겹침 | 교사가 다음 답을 만드는 동안 학생이 먼저 완료된 자료를 학습 | durable 조각·bounded queue·자료 순서·실제 overlap 구간·OOM; 생성량 자체 증가와 구분 |
| B: 한 응답의 답2→4개 | 프롬프트/사고 비용을 여러 스타일 답에 상각할 가능성 | 길이절단·서로 모순·근접중복·파서·같은 concept/split; 독립 지식 수를 부풀리지 않음 |
| C4: 보존자료4epoch | 재노출마다 교사를 다시 호출하지 않음 | 작은 corpus의 held-out CE·기존 full-val 망각·실제 답안; 기존 큰 풀 반복 결과는 안전 보증 아님 |

[llama.cpp 공식 서버 문서](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)는 parallel slots/continuous batching을 지원하는 구조를 설명한다. 그러나 **현재 pinned Prism 바이너리의 실제2slot 속도·메모리는 NOT_RUN**이다. parallel 옵션만 올리고 클라이언트가 한 요청씩 기다리면 동시성 이득은 생기지 않는다. 모델 프로세스 두 벌은 가중치 VRAM을 복제하므로 권장하지 않는다. allocator 상한은 SM·대역폭 자동 배분 기능이 아니다.

공통 system prompt의 cache는 입력 처리 비용 후보일 뿐 긴 사고 decode를 없애지 않는다. 현재 반복 KV 경고3건의 시간은 분해하지 못했다. 더 작은 교사·speculative decoding·다른 GPU는 추가 모델·품질·지원 경로 검증이 필요한 별도 후보이며 이번에 다운로드하거나 실행하지 않았다.

현재 [Bonsai 카드](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf#best-practices)는 low를 지원 강도로 보장하지 않는다. 사용자가 low를 계속 시험하기로 선택했으므로 thinking sampler를 적용하고 비용을 실측한다. medium은 사용자 HOLD이며 자동 재개하지 않는다. none은 다른 생성 profile로 품질 대조가 먼저다.

## 6. 한 질문에2~4개의 답을 요청하면 빨라질까

한 prompt에 답4개를 **연속** 출력하는 것은 단일 autoregressive sequence다. 답4개가 병렬 decode되는 것이 아니다. 반면 별도 질문2개를 서버2slot에서 동시에 처리하는 것은 A1의 동시성 변경이다.

사고 비용을`R`, 답 본문을`A`, 답수를`m`이라 하면 이상적 상각 배수는 `m(R+A)/(R+mA)`다. 실제로 사고를 공유하는지, 본문·마커·질문 길이와 tokenizers의 비용은 측정해야 한다. 이번255,455/25,133을 R/A라고 오해하지 않는다.

B는 한 질문에 **짧은 직답·설명형**,4개일 때는 **두 항목 형식·대화형**을 요청한다. 다중답을 받아도 모두 같은 parent concept와 train/val split에 묶는다. reasoning은 raw sidecar로 보존하고 학생 target에는 최종 답만 들어간다. Canonical 역할·출처·ChatML·loss mask는 소프트웨어가 배정한다.

같은 답을 단어만 바꾼 변형은 고유 지식 확장이 아니다. 정확 중복은 파서가 거부하지만 의미 모순·근접중복은 원답을 보고 사후 검토해야 한다. 이미2048상한55건 실패가 있어 새2답/4답은 각각ctx6144/output4096, ctx12288/output8192로 별도 측정한다. 이 예산 확대가 효율 개선을 보증하지는 않는다.

## 7. 사용자 최종 승인과 구현된 시험 순서 (2026-09-30)

사용자는 B2→4, C4, A1/A2 모두를 채택했고, **독립 C4 뒤 통합1업데이트·그 다음 실제 교육**을 선택했다. 실험 계약은 [P106B Stage3 계획](../test_plan/P106B_Bonsai-자동번역-pseudo-SFT-온라인-교사학생-검증.md), 정확한 런처/id/시간은 새 핸드오프§7이 소유한다.

1. CPU 준비: 기존128행을 concept와 질문이 겹치지 않는 train100/val28로 분할한다.
2. 독립 A1·A2·B2/B4 및 C4를 시험한다. B4는 B2 통과 뒤4답 확장 진단이다.
3. A1은 두 순서 쌍 모두 유효 자료율>1.05·형식 손실 없음·OOM/계측 정상이어야 통합의2병렬 조건을 연다. A2는 실제 생산/소비 overlap을 확인한다.

## 8. 2026-09-30 후속 실측이 바꾼 선택

이 문서 §1~§7은 새 게이트를 **실행하기 전에** 작성한 원인·비용 분석이다. 사용자 [결과101 §31](../test_result/101_20260927_P106B-번역9건으로-문턱미달-학생학습0.md) 회수 뒤에는 다음을 함께 읽는다.

- A1은 한 교사 weight copy의 두 슬롯·학생 공존에서 OOM0/GDN 활성은 보였지만, 같은8문항의 유효자료율 순서쌍이1.140/1.015×여서 **두 쌍 모두>1.05**를 충족하지 못했고 한국어 완결도1~2/4였다. 2슬롯의 자동 채택은 금지한다.
- A2는 serial 한영16질문 중 한국어4/8에서 사전 형식 문턱6/8을 못 넘어 overlap 팔이 실행되지 않았다. 상위 `arms=[]`가 이미 생성한10행 partial 원형을 숨기는 코드 결함은 다음 버전에서 보완했다. 겹친 시간·속도차는 **미측정**이다.
- B2/B4는 같은8문항에서 모두 한영4/4 형식 완료했고 후보 대화 공급은12.142 대16.363토큰/교사요청초였다. 출력예산·문맥·답안 수가 함께 바뀌었으므로 B4의 개선을 답안4개의 단독 인과효과로 해석하지 않는다.
- C4는 실제4pass/4 optimizer·대화78,260토큰을 처리해 SFT-val CE−0.128862를 보였지만 기존 base full-val CE+0.018444 악화, 고정8답의 요구 정답+형식0이다. `PILOT_SAFETY_PASSED`는 운영중단선에 대한 것일 뿐 학생 지능이 아니다.
- 부모 legacy32의 `<|im_start|>`·`<|im_end|>`는 각각8·7개 분절ID이고 chat32에서는 각각 단일ID3·4다. 모델 원답의 머리말/질문 반복은 이 차이와 작은 지도량, EOS만 멈추는 생성기의 복합 가설이다. **chat32 계보 단독의 효과는 이 로그만으로 알 수 없다.**

사용자는 원래 A1+A2+B+C 통합을 소급 통과시키는 대신, 새 Stage3aWb/3bWb의 표본·예산을 늘리고 원답/토크나이저 계보를 먼저 판독하는 A안을 선택했다. 새 프로그램/SH는 모델 실행 전까지 STATIC_ONLY다. 현재 공개 원천의1.29M/4epoch5.14M 외삽도 변하지 않았으며, 이것을300M 교육 일정으로 바꾸지 않는다.
