## 0. 세 줄 결론

1. ★**KV 를 "작아서 무시" 한 것은 2026-08-23 이전 회계에서는 옳았다** — 그때 상주는 **86.9 MiB** 였고
   KV 는 15.0 이라 **17%** 였다. **안 B 조립으로 가중치가 16.8~19.8 이 되면서 KV 가 47~76% 가 됐다.**
   🚫**판단이 틀렸던 것이 아니라 전제가 바뀌었다.**
2. ★**무시했던 method 세 개**: **KV dtype 하향** · **`repeat_kv_reuse`** · **컨텍스트 축소**.
   앞의 둘은 **지금 1·2순위**이고, 셋째는 여전히 최후 수단이다.
3. ★★**가장 값싼 개선은 `bf16 KV`(⚙1h)** 이고, 그것 하나로 **표준모델과 `cla1` 계열이 예산 안으로 들어온다**.
   **두 번째는 `--repeat-kv-reuse`(구현 완료·⚙10분 측정)** 이고 **재귀 라인의 생사가 거기 달렸다.**

## 1. ★현황 — **무엇이 언제 바뀌었나**

| 시점 | 가중치 상주 | KV@1024 | KV 비중 | 그때의 판단 |
|---|---:|---:|---:|---|
| 2026-08 초(fp32 latent 2벌) | **451.5** | 15.0 | **3.2%** | ✅*"무시해도 된다"* — **옳았다** |
| int8 저장 후 | 86.9 | 15.0 | **14.7%** | ⚠️*"긴 컨텍스트에서만 값어치"* — **경계였다** |
| ★**안 B 조립 후**(LUT + emb int8) | ★**16.8~19.8** | 15.0~54.0 | 🚫★**47~76%** | 🚫**전제가 무너졌다** |

★★**이것이 "왜 갑자기 중요해졌는가" 의 전부다.** 우리가 가중치를 **27배** 줄이는 동안
**KV 는 한 바이트도 안 줄었다.** 분모가 사라지니 분자가 드러났다.

### 1.1 🚫우리가 무시했던 것 셋 — **하나씩 재판정**

| # | method | 그때의 기각 사유 | ★**지금의 판정** |
|---|---|---|---|
| ★**1** | **KV int8/4bit** (`02_memory.md` A-1) | *"~상주 −5.6MB. **상주 86.9MB 대비 작다** — 긴 컨텍스트를 목표로 할 때만 값어치"* | 🚫★**뒤집힌다.** −5.6 은 **86.9 의 6.4%** 였지만 지금은 **31.8 의 17.6%** 다. bf16 만으로 **−25%** |
| ★**2** | **`repeat_kv_reuse`** | *"대조 조건이지 기본이 아니다"* — **품질 대가만 보고 메모리 이득을 안 셌다** | 🚫★**뒤집힌다.** ⚙**36 → 20 엔트리 = −24.0 MiB.** 재귀 라인의 유일한 회생 경로 |
| **3** | **컨텍스트 축소**(seq 1024 → 512) | 명시적 기각은 없었다 — **논의 자체가 없었다** | ⚠️**여전히 최후 수단.** −50% 지만 **응용을 제약한다** |

⚠️★**1 과 2 의 기각 사유가 서로 다른 종류**다. 1 은 **회계가 바뀌어** 뒤집혔고,
2 는 ★**애초에 한쪽 축만 보고 내린 판단**이다 — *"품질에 나쁘다"* 는 봤고 *"메모리를 얼마나 버나"* 는 안 셌다.
→ ★**교훈: 레버를 기각할 때 두 축을 다 적는다.**(의사결정함정 후보)

## 2. ★현재 예산 실사 — **네 모델 × 네 dtype**

⚙**KV 만 dtype 으로 나눈 산술**(가중치 고정, seq 1024, 4스레드 예산 **36 MiB**):

| 모델 | 가중치 | fp32 | **bf16** | int8 | ⚙2bit |
|---|---:|---:|---:|---:|---:|
| ★`mC_cla2_ag4` | **16.8** | ✅**31.8** | ✅**24.3** | ✅20.6 | ✅⚙17.7 |
| `mC_initonly_nc` | 19.8 | ✅34.8 | ✅27.3 | ✅23.6 | ✅⚙20.7 |
| `mC_d36_ag4_nokd` | 18.2 | 🚫45.2 | ✅**31.7** | ✅24.9 | ✅⚙20.0 |
| `mC_cla1_ag4` | 16.9 | 🚫46.9 | ✅**31.9** | ✅24.4 | ✅⚙18.8 |
| `mC_cla1_ag4_r20` | 16.9 | 🚫70.9 | 🚫43.9 | ✅**30.4** | ✅⚙20.3 |

★★**bf16 하나로 예산 통과 모델이 2개 → 4개**가 된다.
★**int8 이면 5개 전부** 통과한다.

🚫**전부 산술이다. 품질 대가 측정 0회.**

## 3. ★★개선 제안 — **다섯. 값싼 순서**

### 3.1 ★★제안 1 — **bf16 KV** (⚙1h 구현, 최우선)

| | |
|---|---|
| **무엇** | `kv_bank` 에 넣을 때 `.to(torch.bfloat16)`, 조회 시 `.to(q.dtype)` |
| **이득** | **−25%**(15.0→7.5 · 54.0→27.0 KB/token) |
| **위험** | ⚙**낮다** — 학습 산술이 이미 `torch.autocast(bfloat16)` 이다. **K/V 는 이미 bf16 으로 계산되고 fp32 로 승격돼 저장되고 있었다** |
| **게이트** | `diag_kvcache.py` 의 로짓 동등성 — 🚫**0 이 아닐 것**이므로 **허용 오차를 정해야 한다** |

★**핵심 논거**: cuda 학습 경로에서 K/V 는 **이미 bf16 정밀도로 만들어진다.**
fp32 로 저장하는 것은 **없는 정밀도를 담는 그릇**이다.
⚠️**단 cpu 추론 경로는 fp32 로 돈다** — 거기서는 진짜 정밀도 손실이다. **그래서 재야 한다.**

### 3.2 ★제안 2 — **`--repeat-kv-reuse` 측정** (⚙10분, 학습 0)

**구현이 이미 끝나 있다.** 자세한 것은
[`20260830_재귀-KV증가-원인과-효율관리-검토.md`](20260830_재귀-KV증가-원인과-효율관리-검토.md) §3.1.

| | |
|---|---|
| **이득** | `mC_cla1_ag4_r20`: ⚙36 → 20 엔트리 = **70.9 → 46.9 MiB** |
| **조합** | `cla2` 몸통과 함께면 ⚙**31.8 MiB** = ★**예산 통과** |
| **위험** | 두 번째 통과가 낡은 K/V 를 본다. ⚠️**041 의 `reuse-attn-on-dup` 기각과 다른 물건** |

### 3.3 제안 3 — **int8 KV, KIVI 축 분리** (⚙2h)

📄[arXiv:2402.02750](https://arxiv.org/abs/2402.02750) 의 핵심은 비트폭이 아니라 ★**"K 는 채널별, V 는 토큰별"** 이다.
🚫**대칭 양자화로 시작하면 K 의 채널 이상치 때문에 나쁠 것**이고,
그 실패를 *"int8 KV 는 안 된다"* 로 읽으면 **틀린 결론**을 얻는다.
→ ★**처음부터 축을 나눠 구현한다.**

### 3.4 ⏸제안 4 — **StreamingLLM**(⚙3h) — *컨텍스트를 늘리는 쪽*

📄[arXiv:2309.17453](https://arxiv.org/abs/2309.17453). **학습 불필요**가 핵심 장점이다.
⏸**컨텍스트가 병목이 됐을 때** 연다. 지금 병목은 **컨텍스트가 아니라 dtype** 이다.

### 3.5 🚫제안 5 — `cla_group 4` **권하지 않는다**

g1→g2 가 이미 **+0.0195**(자의 19.5배)다. g2→g4 가 같은 기울기면 ⚙**+0.04**,
오목하면 더 크다. **KV 를 −7.5 MiB 사려고 품질을 0.04 주는 것은
§2 의 bf16(−7.5 MiB, ⚙품질 ~0)에 완전히 지배된다.**

## 4. ★컨텍스트 길이 — **얼마로 갈 것인가**(Q9 연계)

| seq | `mC_cla2_ag4` bf16 | 예산 36 | 판정 |
|---:|---:|---|---|
| 512 | ⚙**20.6** | ✅여유 15.4 | ⚠️**너무 짧다**(사용자 하한이 512~1024) |
| ★**1024** | ⚙**24.3** | ✅여유 11.7 | ✅★**지금. 안전** |
| ★**2048** | ⚙**31.8** | ✅여유 4.2 | ✅★**bf16 이면 도달 가능** |
| 4096 | ⚙**46.8** | 🚫초과 10.8 | 🚫**int8 + 축출 필요** |

★★**사용자 목표(*"적어도 512 또는 1024, 2048~4096 이면 좋겠다"*)에 대한 답**:
✅**1024 는 지금 된다.** ✅**2048 은 bf16 KV 하나로 된다.**
⚠️**4096 은 int8 KV + StreamingLLM 이 함께 필요**하고 **품질 대가가 셋 다 미측정**이다.

🚫★**단, 위 표는 KV 만 본다.** **seq 를 늘리면 학습 VRAM 도 는다**(M = micro_bs × seq,
무릎 M=8192). seq 2048 이면 `micro_bs` 를 4로 내려야 하고 **학습 시간이 는다.**
→ ★**컨텍스트 결정은 배포 예산과 학습 예산 **둘 다**의 함수다.** [P077](../test_plan/P077_KV캐시-정밀도와-컨텍스트-길이.md) 단계3 이 그것을 잰다.

★★**그리고 응용 계층 압축이 이 숫자를 바꾼다** — 재귀 요약으로 오래된 턴을 접으면
**2048 로 훨씬 긴 대화를 감당**할 수 있다(`04_context_length.md` §4.2.3).
🚫**그것은 아키텍처 결정이 아니므로 지금 정하지 않는다.**

## 6. ⚠️한계

- 🚫**§2·§4 의 모든 KV 수치는 산술**이다. **dtype 을 내렸을 때의 품질을 0회 쟀다.**
- ⚠️**KV 회계는 "동시에 살아 있는 K/V 쌍" 이고 할당자 실측이 아니다**(결과 016 §24.7).
- ⚠️**배치 1 기준**이다. 배치 B 면 KV 가 B 배다 — **서버 배포는 다른 계산**이다.
- ⚠️**§1 의 "그때는 옳았다" 는 사후 재구성**이다. 당시 문서에 *"분모가 줄면 다시 본다"* 는 조건이
  **적혀 있지 않았다.** ★**그것이 진짜 결함**이고, 재발 방지는 **기각 사유에 두 축을 다 적는 것**이다.
- ⚠️**KIVI·StreamingLLM 은 초록만 읽었다.** 수치를 우리 조건에 그대로 옮기지 않는다.
