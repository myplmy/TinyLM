## 0. 결론

1. **`dense 12/8이 20층 공유 모델보다 항상 낫다`고 말할 수 없다.** `d12_dense` 3.6130은 지금까지 측정한 20층 공유 후보들보다 분명히 좋았지만, `d8_dense` 3.6776과 `mC_initonly_nc` 3.6762의 차이 0.0014는 dense 분해능 0.0021보다 작다. 수치상 공유 모델이 앞서도 실무상 동급이다. 22MiB 이하처럼 더 낮은 원장에서는 공유 후보만 존재하므로 전 구간 파레토 지배도 아니다.
2. **질문에서 제시한 20층 `중간 g2 MLP + g2 attention + 중간 CLA2, 바깥 2+2층 CLA1·비공유`는 아직 실행되지 않았고 현재 설정으로 그대로 표현할 수도 없다.** MLP/attention g2는 가능하지만 `cla_group`은 절대 층 번호에 전역 적용된다. 목표 형상은 20번 계산하면서 12개의 고유 MLP와 12개의 고유 full-attention을 갖고, 12층 dense와 대형 정적 가중치 수가 같다. 추가되는 것은 8층의 layer-local scale/shift/gate 약 0.094MiB뿐이다. 성능 우열은 미측정이다.
3. **기존 실험은 공유의 ‘구현 패키지 비용’을 일부 분리했지만 순수한 weight sharing 비용은 분리하지 못했다.** `d12_g4` 대 `d12_cla2`, `d16_g4` 대 `d16_cla2`는 깊이·CLA·재귀를 맞춰 각각 +0.0708/+0.0839를 보였고 R2에서도 +0.0812였다. 그러나 공유 MLP에만 `lr/√g`가 적용되므로 표현력 손실과 optimizer 효과가 섞여 있다. 정확한 g2 MLP+g2 attention의 무KD 대조도 없다.
4. **MLP 비공유로도 40MB 하한 원장 내 후보는 있다.** `d12_cla2_r20`은 30.7MiB(약 32.19MB), `d12_cla2_r30`은 33.7MiB(약 35.34MB)다. 다만 RoPE·activation·scratch·allocator가 빠진 값이므로 전체 실행 peak 합격 증거는 아니다.
5. **현재 SwiGLU 수식과 8/3 비율은 올바르고, GQA도 의미론은 맞다.** 수정 대상으로 볼 것은 activation 수식이 아니라 동예산 폭/깊이/FFN 미탐색과 cached decode의 K/V 물리 복제다. 정상 구현에 관한 설명은 의사결정에 필요한 이 두 문장 수준으로 축약했다.
6. **한국어 원시 데이터의 절대량은 300M 학습의 병목이 아니지만, 품질 승인된 token 수가 병목이다.** 로컬 한국어 Wikipedia는 현재 혼합 tokenizer에서 300,186,620 token이 전량이며 정확한 1:1이면 총 약 600.37M token이 한계다. FineWeb2 `kor_Hang`은 공식 카드상 60,874,355문서·48,613,120,582 words·213.43GB UTF-8라 1B 이상 학습용 원시 pool은 충분하지만 TinyLM tokenizer token 수와 정제 후 잔량은 아직 측정하지 않았다.
7. **제안한 한국어 데이터는 어느 것도 그대로 모든 ‘고품질’ 기준을 만족하지 않는다.** Wikipedia도 범위·문체가 좁고, Korean WebText Edu는 로컬에서 SEO 오염이 실측됐으며, FineWeb2는 유해문서·언어분류 오류를 공식 카드가 경고한다. SFT 후보도 번역·사실성·license·저점 응답 문제를 각각 감사해야 한다.
8. **현재 loader는 Wikipedia와 Korean WebText Edu의 `text` 원문은 학습할 수 있지만 FineWeb2 한국어와 SFT는 drop-in으로 학습할 수 없다.** FineWeb2 `kor_Hang`은 `prepare.py::DATASETS`에 없고, SFT schema/대화 경계/assistant-only mask는 `prepare.py`와 `Loader`/trainer에 연결돼 있지 않다.
9. **FineWeb-Edu는 이 문서의 고품질 기준을 모두 만족하지 않는다.** 공식 classifier의 F1은 82%이고, 카드가 최종 corpus에 상당수 유해·toxic 문서가 남는다고 명시한다. score≥3은 평균 benchmark 효율을 높이는 선택이지 광고·UI·SEO·사실 오류·PII·평가오염이 0이라는 보증이 아니다.
10. **Falcon-H1-Tiny와 TinyLM의 격차를 아키텍처 하나로 설명하면 안 된다.** Falcon 90M은 24층 512폭의 parallel Mamba+attention, 비공유 가중치, 32k tied embedding이고 800GT를 Muon+LRM+µP로 학습했다. TinyLM은 순수 Transformer·768폭·공유/삼진 가중치이며 현재 표준은 300M token과 일반 CE다. 학습 token만 약 2,667배이고 Falcon은 STEM/code/reasoning 및 SFT/DPO까지 쓴다. 공식 표에서도 Falcon은 MMLU에서 Gemma3-270M보다 높지만 HellaSwag·PIQA·다국어 평균에서는 낮거나 동급이므로 ‘항상 더 지능적’이지 않다.
11. **구조 제안의 용량·지능 효과는 §9.3에 기준선 대비 수치와 신뢰도를 함께 제시한다.** 실측이 없는 제안은 방향만 확정한 사실처럼 쓰지 않고 범위 추정으로 표시한다.

가장 권하는 경로는 **계측·schedule 결함을 먼저 닫고 last-token-only native peak 경로 확보 → `d12_cla2_r20`을 보수적 기준선으로 고정 → 공유 LR 교락과 정확한 g2/ag2 형상 분리 → `d12_cla2_r30` 재현·다운스트림 확인 → 폭/깊이/FFN/GQA 동예산 탐색 → assistant-only 한·영 SFT 연결**이다. “월등한 지능”은 보장할 수 없으며, 각 단계가 압축손실·과제정답률·한국어 생성·지시이행을 모두 개선할 때만 승격해야 한다.

## 1. 현재 아키텍처 실사

### 1.1 기본 `m100` 형상

| 항목 | 현재 값/구현 | 판정 |
|---|---|---|
| 어휘/폭/FFN | vocab 32,768, `dim=768`, `ffn_dim=2048` | FFN 비율 8/3은 합리적이나 폭 탐색은 사실상 미실행 |
| attention | Q 12개, KV 3개, head dim 64, QK-norm+RoPE | 진짜 GQA 토폴로지이며 head 비율 4:1 |
| 깊이 | prelude 2 + middle 16 + coda 2 = 20층 | 깊이 축은 6~20층에서 측정됐고 20층에서도 loss 포화가 안 보임 |
| MLP | gate/up/down 3행렬의 bias-free SwiGLU | 구현은 정석적 |
| MLP 공유 | middle 4층당 MLP 1개, prelude/coda 독립 | 현 g4 패키지는 matched d12/d16에서 열세. g2/ag2 목표 형상은 미실험 |
| CLA | `cla_group=2`: 절대 층 번호 기준으로 모든 층에서 K/V projection·cache 공유 | KV 절반과 품질 대가의 교환. 중간만 CLA2/바깥 CLA1인 구간별 설정은 없음 |
| recurrence | 기본 1회, 실험에서 middle 재방문 R2/R3 | 정적 가중치 증가 없이 compute/KV로 품질을 사는 축 |
| 임베딩 | rank 256 factorization, 입출력 weight 공유 | 저장에는 유리. 실제 int8 변환·헤드 scratch는 별도 문제 |
| 가중치 | ternary/LUT 배포 회계, per-row alpha | 현재 품질 평가는 주로 일반 checkpoint, packed artifact 품질과 동일하다고 단정 불가 |
| norm/잔차 | 파라미터 없는 RMSNorm 뒤 층별 scale/shift, 학습형 attention/MLP gate | 공유 MLP여도 층별 변조는 남음. 단순 완전 반복 블록이 아님 |
| 초기화 | `o_proj`·`down_proj` scale `1/√(2L)`, residual gate `1/√L` | 깊이 안정화 의도이나 두 감쇠의 결합 효과는 독립 ablation 없음 |

근거는 [`config.py`](../tinylm/config.py), [`modules.py`](../tinylm/model/modules.py), [`transformer.py`](../tinylm/model/transformer.py)다. 특히 `dense_baseline()`은 `tie_mlp=False`뿐 아니라 `cla_group=1`도 함께 바꾸므로, **MLP 공유만 비교하려면 `dense + --cla-group 2`처럼 CLA를 맞춘 대조군**을 써야 한다.

### 1.2 의사결정에 필요한 구현 판정

- `pre_mlps`와 `coda_mlps`는 층별 독립이고, middle만 `tie_mlp/mlp_group`에 따라 공유된다. `mlp_group=2`면 middle 16층이 8개 MLP를 쓴다.
- `attn_group=2`면 middle 16층이 8개 **전체 attention 객체**를 공유한다. 바깥 2+2층은 공유하지 않는다.
- CLA owner는 `i % cla_group`으로 전체 20층에 정해진다. 따라서 현재 `cla_group=2`는 바깥층에도 적용된다.
- MLP는 bias-free SwiGLU이고 GQA는 Q12/KV3으로 projection/cache한다. 두 수식에서 정확성 오류는 찾지 못했다.
- 공유 middle MLP만 optimizer LR이 `base_lr/√mlp_group`이고 attention sharing에는 별도 LR 보정이 없다.
- 위 판정은 [`config.py`](../tinylm/config.py), [`transformer.py`](../tinylm/model/transformer.py), [`modules.py`](../tinylm/model/modules.py)의 실제 생성·참조·forward 경로를 확인한 결과다.

### 1.3 구조적 공백

- `_m100d`는 깊이만 늘리고 `dim=768`, `ffn_dim=2048`을 유지한다. 고정 바이트의 진짜 deep/thin 탐색은 아직 없다.
- 지역별 CLA schedule이 없어 질문 (2)의 형상을 표현할 수 없다. `cla_group` 하나가 전체 층에 적용된다.
- `n_kv_heads`가 실험 인자로 노출되지 않아 GQA의 품질/메모리 trade-off가 고정돼 있다.
- 현재 output head는 청크 결과를 다시 `cat`하고 prefill 전체 위치 logits를 반환하므로 정적 바이트가 작아도 40MB 실행을 보장하지 않는다.
- full-val CE는 압축률이며 일반지능·한국어 생성·지시이행의 대리값일 뿐이다.

### 1.4 구현상 결정 항목과 실제 결함

| 항목 | 코드에서 확인한 동작 | 이번 판단에 미치는 영향 |
|---|---|---|
| 중간 공유 | MLP와 attention은 각각 `j // group`으로 middle에서만 공유 | g2/g2이면 각각 8개, 바깥 4개를 합쳐 고유 모듈 12개 |
| CLA | `owner[i]=i-(i%cla_group)`을 전 층에 적용 | 목표인 바깥 CLA1 + 중간 CLA2는 신규 regional schedule이 필요 |
| GQA 실행 | KV3 cache 후 기본·cached 경로에서 K/V를 Q12로 물리 복제 | 정답 수식은 맞지만 peak·대역폭 이득이 불완전 |
| optimizer | 공유 middle MLP만 `lr/√g` | 기존 matched 비교도 순수 sharing 인과가 아님 |
| 메모리 | 선택 parameter/attribute와 공식 KV를 합산하고 buffers·forward peak는 제외 | 30.7/33.7MiB를 제품 합격값으로 쓰면 안 됨 |

실제 수정 대상으로 남는 결함/제약만 정리하면 다음과 같다.

1. `infer_repeat<1`의 `back/even`이 CLA non-owner만 남기면 K/V projection이 없는 객체를 호출할 수 있다. P079의 uniform R2/R3에는 해당하지 않는다.
2. dense `repeat_mode=block`도 `cfg.mlp_group`을 사용해 실제 층별 MLP 소유권과 block 번호가 어긋날 수 있다.
3. recurrence 안내는 메모리가 R과 무관하다고 하지만 실제 cache key는 `(owner, pass)`라 KV가 늘어난다.
4. `tie_mlp=False`에도 `n_middle % mlp_group == 0`을 요구하고, `attn_group` override는 `arch==tied`에 묶여 있어 독립 ablation을 방해한다.
5. 초기화의 `1/√(2L)` projection scale과 `1/√L` residual gate는 오류로 판정하지 않았으며, 깊은 형상의 별도 ablation이 없는 상태로만 기록한다.

## 2. A — MLP 공유를 풀어도 40MB인가?

### 2.1 답: 범위를 나누면 “예, 후보가 있다”

엄격한 상한은 `40,000,000 B = 38.147MiB`로 잡는다. 아래는 저장소 P079의 **LUT 1.600bpw + latent 해제 + int8 임베딩의 선택 텐서 합산 + bf16 KV 공식, seq 1024, batch 1** 회계다. 원문 결과가 이를 “상주”라고 부르지만, 코드 실사 후에는 전체 상주가 아니라 **제품 peak보다 낮은 원장값**으로 제한해 해석한다.

| 후보 | MLP | full-val | 영구 텐서+KV | 십진 MB | 40MB 판정 | 해석 |
|---|---|---:|---:|---:|---|---|
| `d8_dense` | 비공유 | 3.6776 | 24.6MiB | 25.79MB | 통과 | 가장 큰 약 14.21MB 여유, 안전한 runtime bring-up 후보 |
| `d12_cla2` | 비공유 | 3.6363 | 27.7MiB | 29.05MB | 통과 | recurrence 없는 보수 후보 |
| **`d12_cla2_r20`** | 비공유 | **3.6054/3.6050** | **30.7MiB** | **32.19MB** | **통과** | 2시드, 현재 가장 권할 균형점 |
| `d12_dense` | 비공유 | 3.6130 | 32.5MiB | 34.08MB | 통과 | CLA가 없어 KV가 더 큼 |
| **`d12_cla2_r30`** | 비공유 | **3.5926** | **33.7MiB** | **35.34MB** | **원장 통과** | strict 원장 내 최저 loss이나 1시드·downstream 없음, 여유 4.66MB |
| `d16_cla2` | 비공유 | 3.5967 | 34.0MiB | 35.65MB | 원장 통과 | 여유 4.35MB로 peak에는 위험 |
| `d16_cla2_r20` | 비공유 | 3.5642/3.5639 | 38.5MiB | 40.37MB | **실패** | 40MiB 표에서는 통과해도 십진 40MB는 초과 |
| `d16_dense` | 비공유 | 3.5757 | 40.4MiB | 42.36MB | 실패 | — |
| `d20_dense` | 비공유 | 3.5418 | 48.3MiB | 50.65MB | 실패 | 정적 가중치만 33.3MiB라 해도 KV 포함 실행 원장은 실패 |

### 2.2 무엇까지 확정됐는가

- **정적 가중치만** 묻는다면 `d20_dense`조차 33.3MiB(약 34.92MB)여서 MLP 비공유가 가능하다.
- **모델 영구 텐서+KV**를 묻는다면 `d12_cla2_r20/r30` 등 비공유 후보가 가능하다.
- **구동기만 제외한 모델의 전체 실행 peak**를 묻는다면 아직 합격 모델은 없다. activation, attention scratch, 임베딩 복원, 최종 logits, allocator 여유를 포함한 native peak를 재지 않았다. 현 PyTorch RSS 약 2GB는 구동기를 포함하므로 제품 판정값이 아니지만, 동시에 현 경로가 40MB 실행 경로가 아님은 분명하다.
- `scripts/mem_runtime.py::tensor_mb()`는 parameter와 일부 수동 attribute(`_lut_codes/_lut_alpha`, `_emb_code/_emb_scale`)만 센다. `model.buffers()`는 세지 않아 RoPE cos/sin도 빠진다. `seq=1024`, head dim 64이면 두 RoPE fp32 buffer만 합계 약 **0.25MiB**다. `_anneal`·Python 객체·allocator·모든 forward temporary도 별도다.
- 현재 생성 prefill은 모든 위치의 logits를 만든다. `1×1024×32768`은 bf16만 해도 **64MiB**, fp32면 **128MiB**다. 따라서 현재 Python 생성 경로는 모델 tensor 원장이 30.7MiB여도 strict 40MB 전체 실행에 구조적으로 실패한다.
- LUT 참조 경로는 입력을 `(batch×sequence, hidden)`으로 펴고 `(B,J,O)` gather를 만든다. `lut_out_chunk=0`이 기본이며, chunk를 켜도 마지막 출력은 `cat`한다. 이 구현은 포맷/정확성 참조이지 40MB production kernel이 아니다.

따라서 A의 실무 답은 **“비공유 자체는 가능하며 `d12_cla2_r20`이 가장 안전한 품질 후보다. 다만 30.7MiB는 합격 결과가 아니라 native peak 시험에 올릴 원장값이다”**이다. `d12_cla2_r30`은 품질 후보지만 4.66MB의 남은 공간으로 prefill·헤드 scratch까지 감당해야 하므로 더 위험하다.

### 2.3 “비공유가 항상 우월한가?”와 공유 비용의 분리 수준

**아니다.** 기존 문서의 `8/12/16층 공유 대 비공유 +0.0637/+0.0941/+0.1049` 표는 tied 팔이 기본 CLA2, dense 팔이 기본 CLA1이어서 MLP 공유만의 비교가 아니다. 또한 19.6~22.2MiB 구간에는 `d8_g2`·`d12_g4` 외에 더 작으면서 더 좋은 dense 점이 없으므로 “전 메모리 구간에서 모두 파레토 지배”도 과한 표현이었다.

현재 저장 결과에서 축을 더 잘 맞춘 비교는 다음과 같다.

| 비교 | 공통 조건 | 공유 − 비공유 full-val | 무엇이 분리됐나 | 남은 교락 |
|---|---|---:|---|---|
| `d12_g4` 3.7071 vs `d12_cla2` 3.6363 | 12층, CLA2, R1 | **+0.0708** | CLA·깊이를 고정한 구현상 MLP 공유 패키지 | tied MLP만 LR `1/2`; 부모→그룹 초기화 |
| `d16_g4` 3.6806 vs `d16_cla2` 3.5967 | 16층, CLA2, R1 | **+0.0839** | 위와 같음 | 위와 같음 |
| `d12_g4_r20` 3.6866 vs `d12_cla2_r20` 3.6054 | 12층, CLA2, R2 | **+0.0812** | recurrence까지 고정 | 위와 같음 |
| `d12_g4_r30` 3.6788 vs `d12_cla2_r30` 3.5926 | 12층, CLA2, R3 | **+0.0862** | recurrence까지 고정 | 위와 같음, 비공유 R3 1시드 |
| `mC_initonly_nc` 3.6762 vs `mC_cla2_ag4` 3.7061 | 20층, MLP g8, CLA2, R1 | **+0.0299** | attention g1→g4의 구현 패키지 | ag2가 아니며 초기화 세부 재감사 필요 |

따라서 이미 확인한 것은 **“현재 optimizer·초기화까지 포함한 g4 MLP 공유가 d12/d16에서 손해”**라는 사실이다. 확인하지 못한 것은 **동일 LR·동일 초기화에서 weight를 공유한 행위 자체의 순수 비용**, `g2`의 비용, 그리고 `MLP g2 + attention g2` 상호작용이다. 최소 대조는 같은 초기화에서 tied MLP multiplier `{1/2,1/√2,1}`와 attention `{g1,g2}`를 교차하고 CLA를 고정하는 것이다.

`d12_dense`는 현재까지의 20층 공유 팔보다 좋지만, `d8_dense` 3.6776은 `mC_initonly_nc` 3.6762와 **분해능 안 동급**이다. 따라서 “dense12가 현재 측정된 20층 공유보다 우선”은 말할 수 있어도 “dense8/12가 모든 공유 형상에서 항상 우월”은 말할 수 없다.

### 2.4 질문의 20층 g2/g2/regional-CLA 형상 대 12층 dense

질문의 형상을 `T20-regional-g2`라고 부르면 구조 차이는 다음과 같다.

| 항목 | `d12_dense` | `T20-regional-g2` | 차이 |
|---|---:|---:|---|
| 실행 layer/방문 | 12 | 20 | 목표 형상이 1.67배 깊음 |
| 고유 MLP | 12 | 바깥 4 + middle 8 = **12** | 같음 |
| 고유 full-attention | 12 | 바깥 4 + middle 8 = **12** | 같음 |
| KV owner/cache entry, R1 | 12 | 바깥 4 + middle 8 = **12** | 같음 |
| trainable 대형 행렬 | 12개 block 상당 | 12개 block 상당 | 사실상 같음 |
| layer-local fp32 scale/shift/gate | 12층 | 20층 | **98,368 B = 0.094MiB 증가** |
| P079 방식 하한 원장 | 32.5MiB 실측 | **약 32.6MiB 추정** | 약 +0.1MiB; native peak 아님 |
| 연산/지연 | 12층 | 20층, middle CLA에서 K/V 일부 재사용 | 대략 **1.5~1.7배 연산**, 실측 필요 |

핵심은 `T20-regional-g2`가 **12층 dense를 단순히 20층으로 늘린 모델이 아니라, 같은 12개 고유 block을 가지면서 middle의 각 block을 연속 두 번 쓰는 모델**이라는 점이다. 표현 파라미터 수는 거의 같고 계산 깊이만 늘지만, 두 번째 방문은 새 가중치가 아니라 같은 함수다.

현재 코드는 이 형상을 그대로 만들지 못한다. `mlp_group=2`와 `attn_group=2`는 middle에만 적용돼 의도와 맞지만, `cla_group=2`는 layer 0~19 전체에 적용돼 KV owner가 10개가 된다. `cla_group=1`로 바꾸면 바깥은 맞지만 middle CLA2가 사라진다. 따라서 regional CLA owner map이 필요하다. 전역 CLA2 근사형은 목표형보다 KV가 2 entry 적어 seq 1024 bf16에서 약 1.5MiB 작고, K/V projection도 2세트 적으므로 **서로 다른 모델**이다.

직접 성능 결과는 없다. 가장 가까운 P074 동예산 실험은 고유 block 8개의 `8층 dense`와 `20층 g4/ag4/CLA1`을 비교해 20층 blockwise 공유가 3.6571로 8층 dense 3.6767보다 0.0196 좋았다. 그러나 같은 고유 block을 `1234` 순환으로 네 번 방문한 `8층 dense R4`는 3.6413으로 blockwise 공유보다 다시 0.0157 좋았다. 즉 **추가 계산 깊이는 도움이 될 수 있지만, 연속 공유 순서는 최선이 아닐 수 있다.** 정확한 g2/ag2 점은 P074에서도 후속 미실행 항목으로 남았다.

성능 추측은 다음처럼 제한한다.

- **현재 tied LR 규칙까지 유지**: `d12_dense` 대비 full-val **동급~+0.04 nats 악화**를 중심 가설로 둔다. g4에서 관측된 공유 손실이 g2에서 줄 가능성은 있지만 `lr/√2` 교락이 남는다.
- **MLP LR을 matched sweep으로 보정**: 더 많은 계산 깊이의 이득과 공유 제약이 상쇄돼 **−0.02~+0.02 nats**를 탐색 범위로 둔다. 이는 실측 예측 band이지 증거가 아니다.
- 일반지능은 full-val 변화에서 환산하지 않는다. 동일 token·seed에서 한국어 생성/지시, HellaSwag·PIQA·ARC-Easy, latency와 strict peak를 함께 통과할 때만 12층 dense보다 낫다고 판정한다.

## 3. B — SwiGLU인가, 적절한가, 더 개선할 수 있는가?

### 3.1 현재 구현 판정

코드는 gate/up/down projection 뒤에 다음을 계산한다.

```text
g = gate_proj(x)
u = up_proj(x)
h = SiLU(g) * u
y = down_proj(h)
```

이는 bias-free **SwiGLU**다. `ffn_dim=2048`과 `dim=768`의 비율은 2.6667이며, GLU가 세 행렬을 쓰는 점을 고려해 일반 4d FFN과 파라미터/FLOP를 맞추는 Shazeer의 2/3 폭 규칙과 맞는다. MobileLLM 125M/350M도 각각 576→1536, 960→2560으로 같은 8/3 비율을 썼다. **현재 구현에서 고쳐야 할 수식 오류는 찾지 못했다.**

### 3.2 개선 우선순위

1. **SwiGLU 교체보다 MLP 공유 해제가 먼저다.** 현 손실은 activation 종류보다 동일 MLP를 여러 층에 강제한 데서 큰 신호가 나왔다.
2. **고정 바이트의 FFN 비율 sweep**을 한다. 예: 2.0, 8/3, 3.5, 4.0을 비교하되 FFN만 키워 총 파라미터를 늘리지 말고 `dim×깊이×ffn_dim`을 함께 조정한다. MobileLLM-Pro는 더 큰 1B급에서 4.8d FFN을 택했지만, 이를 100M·삼진 TinyLM에 그대로 옮길 근거는 없다.
3. **진짜 deep/thin 탐색**을 한다. 예를 들어 head dim 64를 유지하면서 `dim=512/576/640/704/768`과 총 깊이, FFN 폭을 동예산으로 조합한다. 현재 저장소는 깊이만 바꿨다.
4. **projection별 층 특화 민감도**를 잰다. gate/up/down 중 하나만 층별로 풀거나 낮은 rank residual을 두어, 전체 비공유 효과의 대부분을 싼 비용으로 얻는지 본다. 어느 projection이 중요한지는 아직 실측하지 않았으므로 미리 정하지 않는다.
5. **fused SwiGLU·정렬된 FFN 폭**은 주로 속도와 scratch 개선이다. 같은 수학식을 쓰는 한 지능 향상이라고 계상하지 않는다.
6. ReGLU/GEGLU/일반 SiLU FFN 교체는 낮은 우선순위다. Shazeer 논문은 SwiGLU의 강한 평균을 보였고, TinyLM에서 다른 activation이 더 낫다는 내부 증거가 없다.

비판적 판정: SwiGLU 내부를 미세 조정하는 것보다 **폭-깊이-FFN의 전체 할당**과 **층별 MLP 독립성**이 더 큰 기대값을 가진다.

추가 설명은 줄인다. 현재 SwiGLU에는 수정해야 할 수식 오류가 없으며, 후속 실험은 activation 교체가 아니라 **동일 packed byte에서 FFN 폭·model 폭·깊이를 함께 바꾸는 비교**로 한정하는 것이 타당하다.

## 4. C — GQA에서 무엇이 제대로 구현되지 않았고 어떻게 고칠까?

### 4.1 정확성은 맞다

- Q는 12개, K/V는 3개로 projection하고 cache도 3개 KV head로 보존한다.
- 기본 경로의 `repeat_interleave(4)`는 Llama 계열의 `repeat_kv`와 같은 의미이므로 attention 결과는 수학적으로 맞다.
- cached decode에서 `q_len < kv_len`일 때 좌상단 causal mask를 쓰지 않고 `past_len` offset을 반영한 mask를 만든 것도 맞는 처리다.

따라서 “GQA가 가짜라서 품질이 틀린다”는 진단은 부정확하다.

### 4.2 불완전한 부분

1. **기본 `sdpa_gqa=False`**에서는 `(B,3,T,64)` K/V를 attention 직전에 `(B,12,T,64)`로 물리 복제한다. KV cache 저장량은 작지만 일시 activation과 메모리 대역폭 이득을 잃는다.
2. **`sdpa_gqa=True`는 `q_len==kv_len`인 학습/비캐시 prefill에만 적용**된다. cached decode는 계속 물리 복제한다.
3. 로컬 P060에서 일반 `enable_gqa=True`는 dispatcher가 MATH backend를 골라 reserved VRAM이 5.066→6.449GB(+27.3%), median step이 2789→5461ms(+95.8%)로 악화됐다. 후속 진단에서 CUDNN은 강제 시 호출 가능했지만, **강제 CUDNN의 속도·메모리·동치성은 측정되지 않았다.** 그러므로 단순히 플래그를 기본 on으로 바꾸면 안 된다.
4. `n_kv_heads`를 실험 인자로 노출하지 않아 12(MHA), 6, 3, 1(MQA)의 품질/weight/KV trade-off를 같은 조건에서 비교하기 어렵다.
5. 진단용 `return_probs`는 전체 `(B,H,Q,K)` 확률을 물질화한다. 기본 off라 제품 버그는 아니지만 40MB 측정에서 반드시 꺼야 한다.

### 4.3 개선안

| 순서 | 개선 | 기대효과 | gate |
|---:|---|---|---|
| 1 | `n_kv_heads={12,6,3,1}`를 config/CLI/identity에 포함 | 품질 대 KV·weight의 실제 파레토 확보 | 같은 초기화·토큰·시드, full-val+다운스트림+KV 바이트 |
| 2 | Hq≠Hkv를 직접 받는 native prefill/decode kernel | K/V 복제 제거, 일시 메모리·대역폭 감소 | cached/non-cached logits, offset causal mask, peak, tok/s |
| 3 | backend 선택을 버전·장치별로 명시하고 CUDNN 강제 후보를 검증 | PyTorch 연구 경로 개선 가능 | off/on 동치, latency, allocated/reserved; 이득 없으면 유지하지 않음 |
| 4 | MHA checkpoint의 KV head를 mean-pool해 GQA로 변환 후 짧게 uptrain | scratch 학습보다 품질 보존 가능성 | GQA 논문의 5% uptraining은 T5 규모 결과이므로 TinyLM에서 재검증 |
| 5 | CLA와 GQA를 직교 ablation | head 공유와 layer 공유의 대가 분리 | MHA/GQA × CLA1/2 × R1/2 |

GQA 개선은 **같은 지능을 더 작은 peak/더 빠른 속도로 내는 것**이 1차 목적이다. KV head를 3→6으로 늘리면 품질이 오를 가능성은 있지만 cache와 K/V weight가 증가하므로 strict byte budget 안에서만 채택해야 한다.

### 4.4 GQA가 아니라 schedule/CLA 결합에서 발견된 정확성 위험

GQA attention 수식과 기본 R1 cache는 맞다. 별도의 위험은 recurrence schedule이 CLA owner 규약을 깨는 경우다. 축소 schedule이 non-owner만 방문하면 K/V projection이 없는 그 층에서 `compute_kv()`를 호출할 수 있다. 이는 **GQA head 반복 오류가 아니라 CLA 소유권과 동적 방문 순서의 결합 오류**다. 수정 후 다음 gate가 필요하다.

1. 모든 schedule에서 방문 non-owner보다 같은 pass의 owner가 앞서거나, owner module로 K/V를 계산했음을 정적으로 검증한다.
2. R<1의 `front/back/even` × CLA1/2 × cached/non-cached logits를 대조한다.
3. cache key 집합과 `kv_report()`의 key 집합을 같은 schedule 함수에서 만들고 완전 일치를 확인한다.
4. 정확성 통과 전에는 축소 recurrence의 속도·메모리 수치를 품질 후보로 인용하지 않는다.

## 5. D — MLP 공유 메모리를 유지하면서 비공유 효과를 얻는 방법

### 5.1 먼저 내릴 결정

현재는 비공유 `d12_cla2_r20`이 이미 영구 원장 30.7MiB에 들어가므로, **공유를 살리기 위한 복잡성을 먼저 추가할 이유가 약하다.** 아래 방법은 더 깊은 모델을 같은 바이트에 넣을 때만 가치가 있다.

### 5.2 후보와 옥석가리기

| 순위 | 방법 | 타당성 | 내부/외부 근거 | 비판적 판정 |
|---:|---|---|---|---|
| **1** | **tied 전용 LR scaling 재검증**: `{1/g,1/√g,1}` | 높음 | 현재 코드가 공유 MLP만 `lr/√g`로 낮춤 | 배포 바이트 0, 가장 싼 인과 분리. 발산·과업 악화 시 즉시 중단 |
| **2** | **공유 MLP + 층별 저랭크 residual** `W_l=W_shared+A_lB_l` | 높음 | 코드에 gate/up/down LoRA가 있고, 구 실험 r32가 tied 대비 약 −0.0337 개선. RRT는 반복별 LoRA와 SVD residual 초기화를 사용 | 현 표준(no-KD+parent) 재검증 없음, 구 r32 `grad_max=6.2`, 메모리 대가 있음. r4/8/16/32와 projection별 ablation 필요 |
| **3** | **학습된 비공유 부모를 layer similarity로 군집화한 뒤 shared basis+residual로 압축** | 중상 | RRT의 SVD residual init에서 착안 | 고정 modulo `mlp_group`보다 역할을 반영한다. 그러나 TinyLM에서는 새 아이디어이며 export·양자화까지 미검증 |
| **4** | **projection 부분 비공유**: gate/up/down 중 민감한 것만 독립 | 중상 | SwiGLU 3행렬의 비용이 분리돼 있음 | 가장 싼 구조적 ablation. 어느 projection인지 사전 단정 금지 |
| **5** | **소수의 저랭크 basis와 층별 coefficient** `W_l=W0+Σ a_lj B_j` | 중 | 공유와 완전 비공유의 연속형 | coefficient는 싸지만 basis가 실제 층 차이를 담는지 미측정; rank collapse 위험 |
| **6** | **전체 block 순환 공유 + iteration embedding/LoRA** | 중하 | RRT가 1B급에서 full-block sharing을 완화 | 현재 TinyLM은 attention은 독립이고 MLP만 공유한다. 구조가 달라 직접 이식 불가, 40MB에서는 KV/반복 compute도 문제 |
| **7** | FiLM | 낮음 | 현재 no-KD 표준에서 +0.0003 악화, 승률 50%, +65,536 params, 상주 +0.3MB, 시간 +7.1% | **종결/비권장** |
| **8** | hypernetwork로 층별 weight 생성 | 낮음 | 계획 P010만 있고 결과 없음 | 생성기 자체 메모리·런타임·양자화 복잡성이 크며 저랭크 residual보다 먼저 할 이유 없음 |

### 5.3 가장 권하는 구체안: “비공유 부모 → 구조화된 재공유”

1. 검증된 비공유 부모의 각 층 gate/up/down을 정본으로 둔다.
2. 각 projection에서 `W_l-W_shared`의 singular value decay와 층 간 cosine/CCA 유사도를 읽는다.
3. 고정 4층 묶음 대신 유사한 층만 묶고, 잔차를 r4/8/16/32 SVD로 초기화한다.
4. gate-only, up-only, down-only, 세 projection 모두를 같은 총 packed byte로 비교한다.
5. residual도 실제 배포 bit-width로 QAT하고, export 후 남는 alpha/metadata까지 바이트에 포함한다.
6. LoRA scale을 0으로 만들었다고 메모리 0으로 치지 않는다. P008에서 checkpoint에 파라미터가 남아 저장/상주가 증가함을 이미 확인했다. 실제 export에서 제거 또는 merge한 산출물로 검사한다.

이 안은 기존 `mlp_group=4`의 “층 번호가 가까우면 같은 역할”이라는 가정을 버리고, **학습된 층 차이 중 저랭크로 설명되는 부분만 저장**한다. 다만 비공유가 이미 예산에 들어가므로 예상 품질/복잡성 기준을 넘지 못하면 폐기한다.

## 6. E — 일반지능 학습 경로와 한국어 데이터

### 6.1 현재 경로의 실제 상태

- loader는 연속 토큰 `x/y`의 next-token objective를 만든다.
- trainer는 일반 CE를 계산한다. chunk CE는 음수/ignore label이 없다는 assert를 두므로 현재 형태로 assistant-only `-100` mask를 넣을 수 없다.
- chat serializer는 assistant 본문과 종료 토큰의 **문자 구간**을 계산하지만, 이를 tokenizer offset→token mask→loss로 소비하는 caller가 없다. `train_thinking=False`도 호출 경로가 생길 때까지 미구현이다.
- 따라서 “SFT JSON 파일이 있다”와 “모델이 SFT를 학습한다”는 다르다. 현재 일반지능용 instruction/SFT 경로는 완성되지 않았다.
- TinyDataset Stage7은 600-record pilot만 있고 추가 corpus 권한 대기 상태이며, 실제 tokenizer 분량 측정도 미실행이라고 문서에 적혀 있다. 품질이 확보된 대규모 학습 자산으로 계상하면 안 된다.

### 6.2 권장 학습 단계

1. **bilingual foundation/CPT**
   - 한국어 원문: 정제된 백과·책/소설·설명문·공식 문서·고품질 웹 문서.
   - 영어 원문: 교육·과학·상식·코드·수학·설명형 텍스트.
   - 문서 수가 아니라 **실제 token 비율**로 mix를 고정한다. 현재 `prepare.py`는 문서 sampling 비율이 0.5/0.5이고 소스 소진 시 비율이 무너지므로 token quota와 exhaustion fail-closed가 필요하다.
   - 언어별 dedup, train/val/eval decontamination, source/license manifest를 먼저 만든다.
2. **고품질 SFT**
   - assistant-only token loss를 구현하고 user/system/tool 영역은 mask한다. 종료 토큰은 loss에 포함한다.
   - 한국어·영어 모두 지시 다양성, 사실 정확성, 간결/장문, 제약이행, 요약, 변환, 추론, 안전 거절을 포함한다.
   - 응답 수보다 **서로 다른 task family와 고품질 답변**을 우선한다. LIMA는 강한 65B pretrained base에서 1,000개 curated example의 효율을 보였지만, 이것이 100M 모델에 지식 자체를 만들어 준다는 증거는 아니다.
3. **선택적 선호학습/거절표본**
   - SFT가 실제 지시이행을 보인 뒤에만 DPO 또는 rejection sampling을 소규모로 비교한다. 100M 모델에서 과도한 alignment는 base 능력을 지울 수 있다.
4. **정확한 배포 형상의 QAT/자기증류**
   - 마지막 단계에서 ternary/embedding/KV 형식을 포함한 산출물을 직접 학습·평가한다. 일반 checkpoint 성능을 packed 모델 성능으로 대신하지 않는다.

### 6.3 “영어 고품질 SFT + 한국어 일반 원문”으로 대체 가능한가?

**부분 대체는 가능하지만 충분한 대체는 아니다.**

- 영어 SFT는 대화 형식, 지시 분해, 답변 구조 같은 언어간 공유 능력을 줄 수 있다.
- 한국어 raw text는 어휘·문법·문체·배경지식을 next-token 방식으로 강화할 수 있다.
- 그러나 raw Korean에는 **한국어 사용자 지시 → 적절한 assistant 응답**의 조건부 신호가 없다. 작은 모델일수록 영어에서 배운 행동을 한국어로 옮길 여유가 적다.
- 따라서 최소한의 **감사된 한국어 SFT anchor**가 필요하다. 정확한 양은 미리 정하지 말고 한국어 SFT 비율 sweep으로 정한다.
- 영어 SFT를 Qwen/Gemma로 한국어 변환·재작성할 수는 있으나, 역번역 일치, 숫자/고유명사/근거 검증, 중복 제거, 사람이 읽는 표본 감사를 거친다. 이것은 logit KD가 아니라 teacher-generated sequence SFT다.
- 같은 source의 gold/reference, teacher answer-only, teacher rationale를 assistant token 또는 총 compute가 같은 조건으로 비교해 “교사 효과”와 “추가 학습 효과”를 분리한다.

권장 조합은 **정제 raw Korean(CPT) + 영어 고품질 raw(CPT) + 영어 SFT + 사람이 감사한 한국어 SFT anchor + 한·영 병렬/동일지시 subset**이다. raw와 SFT를 같은 flat CE 자산으로 취급하지 않는다.

### 6.5 현재 데이터 로더 호환성

현재 `prepare.py`는 `ko-en`, `ko-edu-en`, `ko`, `en` 네 이름과 각 source의 단일 `text` 필드만 안다. 문서를 tokenizer로 평탄화해 `train.bin/val.bin`을 만들고, `Loader`는 memmap에서 무작위 연속 crop을 뽑아 `x=t[:-1], y=t[1:]`만 반환한다.

- **바로 가능한 raw text**: 한국어 Wikipedia, Korean WebText Edu, 영어 FineWeb-Edu. 이미 `DATASETS`에 등록돼 있다.
- **형식상 단순 추가 가능한 raw text**: FineWeb2 `kor_Hang`. `text`가 있으므로 source 등록은 가능하지만, 현재 코드에는 subset·revision·필터·token quota가 없으므로 지금 상태에서는 학습 대상이 아니다.
- **불가능한 SFT 의미 보존**: KULLM/KoQuality/KoAlpaca/K2-Feedback. 현 경로는 messages/instruction/input/output, example boundary, role, assistant mask, preference pair를 보존하지 않는다. 문자열로 평탄화하면 user prompt까지 loss를 주므로 proper SFT가 아니다.
- `tinylm/chat`의 `loss_spans()`는 문자 구간만 만들고 학습 루프에 연결되지 않았다. trainer의 chunk CE도 현재 음수/ignore label을 허용하지 않는다.

즉 Loader가 **이미 전처리된 flat token cache를 읽을 수 있다**는 것과 제안 SFT를 **올바른 objective로 학습할 수 있다**는 것은 다르다.

### 6.6 구현이 필요한 최소 항목

1. canonical conversation dataset reader와 example/document boundary
2. 문자 span→token offset의 정확한 assistant mask, 종료 토큰 포함
3. valid-target 수로 나누는 chunk CE와 padding/ignore-index 지원
4. packed SFT에서 서로 다른 conversation 사이 attention/loss 누출 방지
5. source별 **token quota** mixer와 source exhaustion 즉시 실패
6. tokenizer·dataset revision·license·hash·filter version provenance
7. 한국어 생성, 제약이행, 사실성, 독해, 상식, 안전을 분리한 held-out evaluator
8. train contamination 검사와 exact-cache identity

### 6.7 Qwen/Gemma 교사 경로와 40MB의 실제 코드 충돌

trainer는 `tokenizer_hf` 또는 `kd_teacher_hf`가 지정되면 모델 생성 전에 **학생 `cfg.vocab_size`를 교사의 전체 vocab으로 바꾼다.** 즉 현재 직접 logit-KD 경로는 teacher tokenizer가 평가용으로만 붙는 것이 아니라 학생 embedding/head 크기까지 바꾼다.

현재 `emb_rank=256`, 구현된 int8 embedding 형식은 행당 256-byte code와 fp32 scale 1개를 저장하고, `emb_up(256×768)`은 fp32로 남긴다. 따라서 transformer 본체를 하나도 세기 전의 최소 embedding subsystem은 다음과 같다.

| 학생 vocab | 코드+행별 scale+fp32 `emb_up` | MiB | strict 40MB 판정 |
|---:|---:|---:|---|
| 현재 32,768 | 9,306,112 B | 8.875 | 여유 있음 |
| Qwen3 151,936 | **40,289,792 B** | **38.423** | **embedding만으로 40,000,000B 초과** |
| Gemma 3 262,144 | **68,943,872 B** | **65.750** | 실패 |

이는 기존 문서의 “int8이면 대략 1 byte/parameter” 단축 회계에 **현재 코드의 행별 fp32 scale과 fp32 `emb_up`을 다시 넣은 값**이다. 결론은 다음과 같다.

- P067의 Qwen/Gemma full-vocab `emb_rank=256` 학생은 KD 원리/토크나이저 연구 팔이지 strict-40MB 배포 팔이 아니다.
- `emb_rank=64` 등으로 낮추면 바이트는 다시 들어올 수 있지만, 내부 Qwen 실험에서 Q64는 Q256보다 common-text bpb가 **+0.0636** 악화됐다. 메모리 해결이 곧 품질 해결은 아니다.
- 40MB와 교사 지식을 동시에 원하면 우선순위는 **학생 32k를 유지한 teacher-generated sequence SFT**, cross-tokenizer alignment/hidden-state KD, 검증된 vocab pruning/adaptive embedding이다. 현재의 동일-vocab KL을 학생 32k에 그대로 적용할 수는 없다.
- 연구 팔과 배포 팔은 tokenizer ID, vocab, embedding rank, packed bytes, evaluator tokenizer를 별도 identity로 기록한다. Qwen/Gemma 교사 우위와 큰 vocab 효과를 한 숫자로 섞지 않는다.

## 7. F — 고품질 학습 토큰의 기준과 FineWeb-Edu 판정

### 7.1 “좋은 토큰”은 토큰 하나의 속성이 아니다

LLM 데이터 품질은 보통 **문서/구간/출처/mixture가 고정 compute에서 목표 평가에 주는 한계효용**으로 판단해야 한다. 같은 문서도 모델 크기, 언어, tokenizer, 중복률, 학습 단계에 따라 효용이 달라진다.

### 7.2 권장 기준

| 층 | 기준 | 실패 예 |
|---|---|---|
| 0. 사용 가능성 | license·출처·동의·재배포 조건, PII/비밀/악성 content | 출처 불명, 사용권 불명, 개인정보 |
| 1. 무결성 | 올바른 언어/encoding, 문장 완결, 본문 추출, 낮은 OCR·HTML 오류 | 메뉴 조각, 깨진 표, 잘린 문장 |
| 2. 신뢰성 | 사실 정확성, 내부 일관성, 인용/근거, 최신성 | 환각 Q&A, 모순, 낡은 사실 |
| 3. 정보 밀도 | 설명·관계·원인·예시·문제해결이 충분, 낮은 boilerplate | 광고, cookie 문구, 버튼/UI, SEO keyword 반복 |
| 4. 학습 적합성 | 독립적으로 이해 가능, 목표 언어·도메인·난이도에 맞음 | 맥락 없는 댓글, 제목만 있는 페이지 |
| 5. 다양성 | 주제·문체·길이·task family·관점의 범위 | 같은 template/FAQ의 대량 치환 |
| 6. 비중복/비오염 | exact/near dedup, train-val-test 및 benchmark decontamination | 같은 답변의 반복, 평가 문항 노출 |
| 7. 안전·편향 | 독성·혐오·불법·편향 tail을 목적에 맞게 통제 | 무검토 web tail |
| 8. 실증 효용 | 같은 token/compute에서 clean held-out와 downstream을 개선 | classifier 점수는 높지만 실제 성능 악화 |

tokenizer의 bytes/token이 낮은 것은 **효율**이지 내용 품질이 아니다. perplexity가 낮은 문서도 흔한 boilerplate일 수 있고, 너무 높은 문서는 오류일 수도 희귀한 유용 지식일 수도 있다. 단일 PPL 임계값으로 high quality를 정의하지 않는다.

### 7.3 FineWeb-Edu는 고품질인가?

**아니다. 이 문서 §7.2의 모든 기준을 만족하는 gold corpus가 아니라, 평균 교육성·학습 효율이 높은 후보 pool이다.**

| 기준 | FineWeb-Edu 판정 | 근거 |
|---|---|---|
| 교육성/aggregate 효용 | **강함** | score≥3가 공개 ablation에서 FineWeb보다 MMLU·ARC·OpenBookQA 등을 개선 |
| classifier 정확성 | **불완전** | 공식 카드의 score-3 binary classifier F1이 **82%**이므로 false positive/negative가 존재 |
| 광고·UI·SEO 0% | **보증 없음** | score 3 rubric도 일부 extraneous information을 허용하고, 별도 UI/SEO 완전 제거율을 제시하지 않음 |
| 사실 정확성 | **문서별 보증 없음** | 교육성 점수와 사실 검증은 다르며 Common Crawl 원문을 전수 fact-check하지 않음 |
| 유해성/편향 | **기준 불충족** | 공식 카드가 URL-level NSFW/toxicity 필터 뒤에도 최종 dataset에 **상당수 toxic/harmful 문서**가 남는다고 명시 |
| PII/license | **개별 문서 보증 없음** | ODC-By 배포와 Common Crawl 약관은 제시되지만 개별 페이지 권리·PII가 모두 해결됐다는 보증은 아님 |
| 중복/평가오염 | **추가 gate 필요** | 공개 filtering/dedup이 있어도 목표 benchmark와 TinyLM held-out의 exact/near overlap 0%를 보증하지 않음 |
| code·도메인 완결성 | **불충분** | 카드가 filtering 결과 code가 드물 수 있어 별도 code corpus를 권고 |

로컬 P047의 좁은 SEO signature 감사에서는 표준 `ko-en` 366,819문서 중 6개, 전체 문자 0.06229%가 양성이었고 source별로 Wikipedia 0%, 영어 FineWeb-Edu 약 0.082%였다. 이 수치는 **특정 대형 한줄 스팸 서명만** 찾은 것이므로 “영어 FineWeb-Edu가 깨끗하다”는 전수 품질 증명이 아니다. 반대로 Korean WebText Edu source의 약 34.4% 문자 양성을 영어 FineWeb-Edu에 귀속해서도 안 된다.

`ko-edu-en` SEO filter 학습의 common-text bpb 1.5182→1.4124(−0.1058 bpb, 환산 −0.296 nats)는 데이터 정제가 큰 레버임을 보였지만, 한국어 source 오염 제거와 영어 token 비중 변화가 섞여 있다. 결론은 **FineWeb-Edu를 버리라는 것이 아니라, source별 필터·층화 사람 감사·matched-token 학습을 거친 뒤 사용할 것**이다.

### 7.4 권장 데이터 gate

1. **hard reject**: 사용권 불명, PII, 악성/유해, 언어 오류, 문서 파손, exact/near duplicate, eval overlap.
2. **내용 점수**: 정확성·일관성·설명 밀도·자립성·구조를 더하고 광고/UI/SEO/반복/affiliate 문구를 뺀다.
3. **source cap과 diversity quota**: 높은 점수 한 도메인이 전체를 잠식하지 않게 한다.
4. **한국어 native audit**: 점수 구간·출처·길이별 층화표본을 사람이 읽고 precision과 tail failure를 기록한다.
5. **matched-token proxy train**: 동일 tokenizer, 같은 실제 언어 token 수, 같은 seed/steps에서 원본 대 정제본을 비교한다.
6. **최종 판정**: full-val 하나가 아니라 한국어 생성/지시/지식·영어 과제·오염 없는 공통 원문을 함께 본다.

## 8. 현재 후보와 일반지능 증거의 한계

### 8.1 현 파레토 후보

| 용도 | 후보 | 장점 | 미확정 |
|---|---|---|---|
| 안전한 40MB runtime bring-up | `d8_dense` | 24.6MiB 원장, 큰 scratch 여유 | 품질 3.6776, 일반지능 낮을 가능성 |
| **현재 권장 기준선** | **`d12_cla2_r20`** | 30.7MiB, 두 시드 3.6054/3.6050, 비공유+CLA2+R2 | native peak·충분한 downstream·생성/SFT |
| 공격적 strict 후보 | `d12_cla2_r30` | 33.7MiB, full-val 3.5926 | 1시드, downstream 없음, scratch 여유 작음 |
| 40MiB 연구 후보 | `d16_cla2_r20` | 두 시드 3.5642/3.5639 | 십진 40MB 실패 |
| 정적 weight 연구 | `d20_dense` | loss 3.5418, weight만 33.3MiB | KV 포함 48.3MiB, 실행 목표 실패 |

### 8.2 downstream이 말하는 것

P079 후속 400문항 표본에서:

- `d12_cla2_r20`: HellaSwag 29.8%(chance 25), PIQA 56.0%(chance 50), ARC-Easy 39.0%(chance 25)
- `d16_cla2_r20`: HellaSwag 27.5%, PIQA 55.2%, ARC-Easy 39.8%

로그 자체가 pairwise CE 서열화에 필요한 N을 수천~십만으로 추정하고 400문항으로 서열을 매기지 말라고 경고한다. HellaSwag는 chance 근처이며, 모델은 SFT 없는 100M base LM이다. 따라서 **“문장작성·지시이행 등 일반 LLM 지능이 월등하다”는 결론은 현재 근거에서 나오지 않는다.** 현 수치는 다음 실험 후보를 고르는 약한 신호다.

### 8.3 Falcon-H1-Tiny 90M과 TinyLM의 차이

비교 대상은 [Falcon-H1-Tiny 기술 보고 페이지](https://tiiuae-tiny-h1-blogpost.hf.space/), [공식 90M Base config](https://huggingface.co/tiiuae/Falcon-H1-Tiny-90M-Base/blob/main/config.json), [공식 GGUF 파일 목록](https://huggingface.co/tiiuae/Falcon-H1-Tiny-90M-Instruct-GGUF/tree/main)이다. 공개 수치는 제작자 보고이며 TinyLM과 동일 harness로 독립 재현한 값이 아니다.

| 항목 | Falcon-H1-Tiny 90M | TinyLM `d12_cla2_r20` 중심 | 격차 해석 |
|---|---|---|---|
| parameter/형상 | 공식 collection 91.1M; 24층, hidden 512, FFN 768, Q8/KV2 | dense train parameter 82.94M; 12개 고유 layer, hidden 768, FFN 2048, Q12/KV3, middle R2로 20번 방문 | parameter 수는 비슷하지만 계산 그래프는 다름 |
| mixer | 매 layer의 **parallel Mamba SSM + attention** hybrid | 순수 causal Transformer attention+SwiGLU | Falcon은 SSM 768 채널로 sequence mixing 용량을 추가 |
| 공유/정밀도 | 공개 config에 cross-layer tying 없음, BF16 원본 | MLP는 비공유지만 CLA2와 recurrence로 K/V/weight 방문 공유, ternary/LUT+int8 embedding 배포 가정 | TinyLM은 40MB를 위해 훨씬 강한 압축 제약을 받음 |
| vocab/head | 32,768 tied embedding, `num_logits_to_keep=1` | 32,768 rank-256 tied embedding, 현재 prefill은 모든 위치 logits 생성 | Falcon의 last-logit 경로는 TinyLM이 바로 참고할 구현점 |
| 학습량 | **800GT** total, 100GT decay | **300M token** 표준 | 약 **2,667배** 차이; 가장 큰 설명 변수 |
| 데이터 | 최종 base는 20% web, 나머지 80% STEM/code/reasoning; instruct는 25% pure SFT를 pretraining mix에 넣고 DPO | Wikipedia+FineWeb-Edu raw mix 중심; proper assistant-only SFT 미연결 | 일반지능·지시이행 격차의 직접 원인 |
| optimizer | 4M-token batch, WSD, µP 35 multipliers, Muon, row/column Learnable Multipliers | 약 131k-token step, AdamW, WSD, ternary STE, tied MLP만 별도 LR | 최적화 recipe도 큰 차이이며 단일 요소 기여 분리 불가 |
| 배포 크기 | BF16 safetensors 182MB; 공식 GGUF TQ1_0 파일 31.1MB, TQ2_0 34.6MB | P079 하한 원장 weight+KV 30.7MiB | Falcon의 GGUF 파일 크기도 40MB **runtime peak** 증거는 아님 |

Falcon 제작자 표는 “모든 일반지능에서 우월”을 보여주지 않는다.

- English base: Falcon은 MMLU 32.3 대 Gemma3-270M 26.2, MMLU-Pro 7.18 대 0.8로 높지만, HellaSwag 37.52 대 41.5와 PIQA 65.13 대 68.3은 낮다.
- Multilingual 101M: MMLU 32.62 대 Gemma 26.2는 높지만 English commonsense 평균은 27.55 대 30.35, multilingual 평균은 19.87 대 19.99로 낮거나 사실상 같다.
- English instruct의 SFT-pretrain+DPO는 IFEval 66.08과 LiveBench 15.69로 Gemma3-270m-it의 27.44/9.08보다 높지만, HellaSwag 36.43 대 36.21은 동급이고 일부 reasoning/coding 항목은 뒤진다.
- TinyLM의 400문항 결과는 HellaSwag 29.8%, PIQA 56.0%, ARC-Easy 39.0%이지만 표본·prompt·tokenizer·harness가 Falcon 표와 달라 숫자를 직접 빼면 안 된다. TinyLM에는 MMLU/IFEval 및 문장작성의 동등 평가도 없다.

따라서 Falcon 격차의 우선 설명은 **800GT 고품질·과업지향 데이터 + SFT/DPO + 최적화 recipe + 비압축 독립층**이고, hybrid Mamba만의 효과로 귀속할 수 없다. TinyLM에 옮길 우선순위는 다음과 같다.

1. **높음**: last-logit-only head, 32k vocab 유지, fixed-byte depth/width/FFN/GQA sweep, STEM/code/reasoning과 한·영 instruction을 별도 평가 가능한 mixture로 구성.
2. **조건부**: Muon과 Learnable Multipliers를 AdamW와 같은 token·seed·packed artifact로 ablation. Falcon의 200GT/800GT 이득을 300M ternary 학습에 그대로 외삽하지 않는다.
3. **후순위**: parallel Mamba+attention 전면 이식. 상태·conv·kernel·양자화·KV/SSM state를 포함한 40MB 원장이 새로 필요하고, 아키텍처 독립 기여가 공개 결과에서 분리되지 않았다.

## 9. 개선 아이디어 우선순위와 비판적 판정

### 9.1 아키텍처 중심 순위

| 순위 | 제안 | 기대 | 근거 강도 | 주요 반론/중단 조건 |
|---:|---|---|---|---|
| **1** | **last-token-only head + native/fused LUT/GQA + 단계별 peak 계측** | 실제 40MB 제약을 만족하는 기반 | **높음: 현 코드에서 64/128MiB prefill logits 확인** | 지능을 직접 올리진 않음. 그러나 없으면 모든 40MB 후보 판정이 성립하지 않음 |
| **2** | **MLP 비공유 `d12_cla2_r20`을 기준선으로 승격** | 현 공유 패키지 열세 제거, 원장 여유 | **높음: 로컬 직접 실측·2시드** | native peak가 40MB를 넘거나 packed 품질이 무너지면 형상 축소 |
| **3** | **공유 MLP LR multiplier 대조** | 배포 바이트 0으로 공유 성능 일부 회수 가능 | 높음: 실제 코드의 명확한 교락 | 발산/gradient·최종 품질 악화 시 종료; 표현력 병목은 남을 수 있음 |
| **4** | **진짜 width-depth-FFN 동예산 탐색** | 현재 고정 폭의 미탐색 파레토 발견 | 중상: MobileLLM/Flash + 로컬 깊이 무포화 | deep-thin이 실제 모바일 latency에는 불리할 수 있음; 바이트·latency 실측 필수 |
| **5** | `d12_cla2_r30` 재현·다운스트림 | 정적 weight 증가 없이 loss 개선 | 중: 1시드 full-val 강함 | KV 10.5MiB, 원장 여유 4.66MB 미만으로 축소, 일반지능 미평가 |
| **6** | GQA head 수 sweep + native decode | KV/품질/속도 파레토 개선 | 중상: GQA 논문, 현 구현 분석 | 품질 개선은 보장 안 됨; backend별 역전 가능 |
| **7** | 비공유 부모의 SVD residual 재공유 | 더 깊은 층을 적은 weight로 | 중하: 구 LoRA 신호+RRT 외삽 | 비공유가 이미 맞으므로 복잡성이 이득보다 클 수 있음 |
| **8** | exact deployment QAT와 artifact eval | 양자화 손실 회수·판정 정직성 | 중: 외부 QAT 사례, 내부 packed 불일치 | 새 지능 생성보다 손실 보존 성격 |
| **9** | hardware-in-loop skip-attention/NAS | 특정 장치 latency 파레토 | 중하: MobileLLM-Flash | 40MB·삼진·목표 구동기와 다른 조건, 구현비 큼 |
| **10** | FiLM/hypernetwork | 공유층 특화 | 낮음 | FiLM은 내부 기각, hypernetwork는 미실험·복잡 |

### 9.2 전체 품질 중심 순위

아키텍처만 보면 위 순서지만, 실제 일반지능 향상은 다음 순서를 병행해야 한다.

1. **평가·SFT loss 경로 완성**: assistant-only objective와 한국어 지시이행 held-out이 연결되지 않으면 일반지능을 직접 최적화하거나 판정할 수 없다.
2. **데이터 품질·token mix·decontamination**: 로컬 SEO 필터가 큰 개선을 이미 보였다.
3. **40MB 실제 실행 경로와 계측 정정**: 전체 logits·LUT gather·RoPE/temporary 누락을 닫는다.
4. **비공유 d12 구조 + R2/R3 확인**, 동시에 tied LR 교락을 싼 대조로 분리한다.
5. **폭/깊이/FFN/GQA byte-constrained search**.
6. **한·영 CPT → assistant-only SFT → 선택적 preference → QAT**.
7. KD는 teacher가 목표 평가에서 실제 우월하고 matched no-KD/control이 통과할 때만 다시 연다. MobileLLM에서는 Llama2-7B KD가 125M/350M 평균을 오히려 소폭 낮추고 학습을 2.6~3.2배 늦췄으며, MobileLLM-Pro의 1B·초대규모 recipe에서는 full-vocabulary KD가 유리했다. 즉 KD 효과는 규모·teacher·데이터·compute에 조건적이다. Qwen/Gemma는 full-vocab 연구 팔과 학생-32k 배포 팔을 분리한다.

### 9.3 제안별 용량 변화와 지능 변화 추정

다음 표는 **실행 peak가 아니라** §2.1과 같은 `LUT 1.600bpw + int8 rank-256 embedding + bf16 KV, batch 1, seq 1024` 하한 원장이다. 기준선은 `d12_cla2_r20`의 30.7MiB와 두 시드 평균 full-val 3.6052이며, loss 변화는 음수가 좋다. 일반지능은 full-val에서 수치 변환할 수 없으므로 별도 방향과 gate로 적었다. `추정`은 실험 결과가 아니라 다음 실험의 사전 가설이다.

- `FFN +256`은 단순 증량 예시다. 실제 권장안은 다른 폭/깊이를 줄여 **같은 총 바이트**로 비교하는 것이다.
- 표의 `0~−x nats`는 채택 약속이 아니라 사전 탐색 범위다. 범위를 벗어나거나 악화하는 결과도 허용해야 한다.
- CPT 데이터 정제, assistant-only 한·영 SFT, preference, KD, Muon/LRM은 **최종 모델 바이트를 원칙적으로 바꾸지 않는 비구조 기법**이다. 그중 한국어 지시이행에는 SFT 경로의 기대값이 가장 크지만, 현재 loader가 objective를 보존하지 않으므로 수치 향상을 예측할 근거는 없다. KD도 최종 학생 크기는 같지만 기존 dense KD 열세 때문에 teacher 우위·matched no-KD를 통과하기 전에는 개선으로 계상하지 않는다.

## 10. 새로 도출한 실험 아이디어

### 10.1 Byte-constrained allocation search

파라미터 수가 아니라 다음 합을 직접 목적함수 제약으로 둔다.

```text
packed weights + scales/metadata + embedding/head + KV cache
+ activation arena + attention/output scratch <= 40,000,000 bytes
```

후보마다 `dim/depth/ffn/n_kv/cla/repeat`를 바꾸고 native runtime의 실제 peak와 품질을 Pareto 최적화한다. MobileLLM-Flash가 보여준 핵심도 FLOPs/params가 실제 장치 latency의 좋은 대리변수가 아니라는 점이다. TinyLM에서는 여기에 **바이트 peak**를 함께 넣어야 한다.

### 10.2 Layer-role clustered residual sharing

현재 `mlp_group=4`의 연속층 modulo 공유 대신, 비공유 부모에서 관측한 layer residual 유사도로 군집을 만든다. cluster별 shared SwiGLU와 층별 저랭크 residual만 저장한다. 이는 RRT의 SVD residual 초기화와 로컬 비공유 승자를 결합한 **새 제안**이며 TinyLM 실측은 없다.

### 10.3 Train-wide, deploy-narrow GQA

MHA 또는 KV6 부모를 학습한 뒤 KV projection을 group mean-pool하여 KV3/KV1로 변환하고 짧게 uptrain한다. 같은 최종 cache 크기에서 scratch KV3보다 품질이 나은지 확인한다. GQA 논문의 checkpoint conversion을 TinyLM에 적용한 제안이며, 5% uptraining 수치를 그대로 규칙으로 쓰지 않는다.

### 10.4 Dual-route bilingual alignment

raw Korean은 CPT objective, 영어/한국어 instruction은 assistant-only SFT objective로 분리하고, 동일 의미의 한·영 지시쌍을 작은 bridge batch로 둔다. “영어 instruction 행동”과 “한국어 표현능력”이 같은 hidden space에서 만나게 하되, raw Korean을 SFT 대용으로 오인하지 않는다.

### 10.5 Output-head streaming as an architecture enabler

현재 `sample()`의 첫 prefill은 전체 prompt를 모델에 넣고, `_head_logits()`는 모든 T 위치에서 전체 V logits를 만든 뒤 caller가 마지막 위치만 자른다. `T=1024,V=32768`이면 이 반환 tensor만 bf16 64MiB/fp32 128MiB다. 추론에서는 transformer가 마지막 hidden state만 head로 보내도록 인터페이스를 분리해야 한다. 양자화 어휘 청크도 전부 `cat`하지 말고 online top-k/argmax 또는 sampling에 필요한 누산만 유지한다. 학습 CE는 별도의 token/vocab streaming log-sum-exp가 필요하다. 이는 지능을 직접 높이지 않지만 scratch를 줄여 같은 40MB에서 더 많은 layer/FFN/KV를 허용할 수 있어 **간접적인 품질 레버**다. cached/non-cached greedy 결과, full-head/streaming 확률·loss의 수치 동치 gate가 필요하다.

### 10.6 Schedule-safe CLA와 단일 메모리 원장

방문 schedule을 먼저 “절대 layer, CLA owner, pass, MLP object” 튜플로 컴파일하고 forward와 `kv_report`, block repeat, cache key가 그 하나의 결과만 소비하게 한다. 그러면 축소에서 owner가 사라지는 오류와 dense block의 그룹 불일치를 같은 계층에서 막을 수 있다. 메모리 원장도 parameter/attribute만 수동 열거하지 말고 packed weights·모든 buffers·KV·arena·단계별 peak를 구분해 출력한다. 이 제안은 새 지능 기법이 아니라 **잘못된 후보 승격을 막는 선결 정확성 작업**이다.

## 11. 권장 검증 순서

1. **정의 고정**: 40MB=40,000,000B, engine 제외 범위와 모델 scratch 포함 여부, seq/batch를 명시한다.
2. **정확성 선결**: CLA owner-safe schedule, dense block 규약, recurrence 메모리 안내, forward/`kv_report` cache-key 일치부터 닫는다.
3. **실제 추론 경로**: last-token-only head, native/fused LUT와 Hq≠Hkv attention, 고정 arena를 마련한다. 참조 PyTorch LUT는 제품 판정에 쓰지 않는다.
4. **native peak gate**: load→prefill→first token→steady decode 단계별 peak에 RoPE·모든 buffers·KV·scratch를 포함한다. R2 우선, R3는 여유가 작아 후순위다.
5. **현 후보 확증**: `d12_cla2_r30` 추가 시드, R2/R3 전체 downstream, 한국어 생성·지시 held-out. 3개 과제를 평균 하나로 뭉개지 않는다.
6. **MLP 인과 분리**: tied LR multiplier sweep 후 공유 자체의 대가를 판정한다.
7. **packed artifact gate**: 일반 checkpoint와 실제 ternary/int8 export의 logits·loss·생성 비교.
8. **폭/깊이/FFN proxy search**: 고정 token의 작은 screening 뒤 상위 후보만 충분한 token으로 재학습. 현 “deep” preset을 thin 증거로 쓰지 않는다.
9. **GQA/CLA 분해**: KV head와 layer 공유를 독립 sweep하고 native kernel까지 평가한다.
10. **SFT 경로 연결**: mask·boundary·token quota·provenance·한국어 평가가 모두 통과한 뒤 데이터 비교.
11. **부분 재공유**: 비공유가 byte gate를 못 넘거나 더 깊은 후보가 분명히 유리할 때만 residual sharing을 연다.

승격 기준은 최소한 다음을 동시에 만족해야 한다.

- strict byte peak 통과
- 2개 이상 시드의 full-val/common-bpb
- HellaSwag·PIQA·ARC-Easy의 충분한 표본과 한국어 독립 평가
- 오염 없는 한국어 생성·지시이행·사실성 평가
- packed artifact 품질

## 15. 최종 판정

- **A**: MLP 비공유로도 strict 40MB **하한 원장** 내 후보가 있다. `d12_cla2_r20`이 가장 보수적인 권장안이고 `d12_cla2_r30`이 현재 loss상 공격적 후보다. 다만 dense8은 한 20층 공유 팔과 분해능 안 동급이고 저용량 구간에는 공유 파레토가 남으므로 비공유가 항상 우월하다고 일반화하지 않는다. 현 prefill logits만 64/128MiB이고 계측에서 RoPE/temporary가 빠지므로 전체 모델 실행 peak 합격 모델은 아직 없다.
- **B**: 현재는 올바른 SwiGLU이며 8/3 비율도 합리적이다. activation 교체보다 MLP 비공유, tied 전용 LR 교락 분리, 동예산 폭/깊이/FFN 탐색이 우선이다. 출력/down 초기화와 residual gate의 이중 depth scaling은 버그가 아니라 미검증 가설이다.
- **C**: GQA 의미론과 cache 저장은 맞다. 문제는 기본/디코드 경로의 K/V 물리 복제와 backend 선택이다. 별도로 축소 schedule이 CLA owner를 생략하면 non-owner의 없는 K/V projection을 호출할 수 있으므로, owner-safe schedule을 먼저 고친 뒤 native Hq≠Hkv kernel과 KV-head sweep을 평가한다.
- **D**: 공유를 꼭 유지해야 하면 먼저 배포비 0인 tied LR multiplier를 재검증하고, 그다음 층별 저랭크 residual, projection 부분 비공유, similarity cluster를 본다. FiLM은 기각, hypernetwork는 후순위다.
- **E**: 영어 고품질 SFT+한국어 raw는 보조 조합이지 한국어 SFT의 완전 대체가 아니다. 현재 loader/loss부터 assistant-only SFT를 실제로 소비하도록 연결해야 한다. 한국어 dataset은 후보 pool은 있으나 단일 검증된 gold는 없다. 현재 Qwen/Gemma full-vocab·rank256 학생은 embedding subsystem만으로 strict 40MB를 넘으므로, 학생 32k sequence SFT/cross-tokenizer 경로와 연구용 full-vocab 경로를 분리한다.
- **F**: high-quality는 광고/UI가 없다는 단일 필터 점수가 아니라 적법성·정확성·정보밀도·다양성·비중복·비오염·안전성과 matched-token 실증 효용의 결합이다. FineWeb-Edu는 유력 pool이지만 추가 필터와 표본 감사가 필요하다.
- **정확한 20층 regional-g2**: 12층 dense와 고유 대형 block·KV owner 수는 같고 layer-local 약 0.094MiB만 늘지만 20번 계산한다. 현재 코드로 형상을 표현할 수 없고 직접 성능도 없으므로 12층 dense보다 좋거나 나쁘다고 판정하지 않는다.
- **Falcon-H1-Tiny**: 공개 성능 격차의 우선 설명은 800GT, 과업지향 mixture, SFT/DPO, optimizer, 비압축 독립층의 결합이다. hybrid Mamba만 떼어 TinyLM의 즉시 개선안으로 승격하지 않는다.
- **제안별 예상**: strict 후보에서 가장 근거 있는 직접 개선은 `d12_cla2_r30`의 약 −0.0126 nats지만 1시드다. LR 교락 분리·부분 비공유·GQA/FFN 동예산 탐색은 §9.3의 낮은 신뢰도 범위이며, 일반지능 향상은 한국어 생성·지시이행과 충분한 downstream에서 별도로 확인한다.

가장 중요한 원칙은 **“작게 저장된다”, “loss가 낮다”, “일반지능이 높다”, “실행 peak가 40MB다”를 서로 다른 주장으로 유지하는 것**이다. 현재 증거는 첫 두 주장에 강하고, 뒤 두 주장은 아직 필요한 실험이 남아 있다.
