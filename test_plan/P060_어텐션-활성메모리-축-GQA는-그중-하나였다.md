## 0. ⚠️ 절차 결함 — **계획 없이 배치만으로 돌았다**

F-1 은 `experiments.tsv` 한 줄과 배치 헤더가 설계의 전부였다.
그래서 **예측(`reserved −0.4~0.5 GiB`)의 근거가 어디에도 적혀 있지 않았다.**
결과문서가 그것을 *"커널이 GQA 를 네이티브 지원한다는 가정"* 으로 **사후 복원**했는데,
**복원은 기록이 아니다.**

> ★**규약**(결과 046 §7): 배치를 만들 때 계획 번호가 없으면 `exp-plan` 으로 계획서를 먼저 만든다.
> `runlog --name` 이 `P0NN` 을 요구하는 것과 같은 이유다 — **로그와 결과를 이어 붙일 자리**가 있어야 한다.
> 이 실험은 `--name P060_gqa` 로 돌았으므로 **P060 이 그 번호**다.

### 0.1 ★예측의 근거를 이제 적는다 (사후, 정직하게 표시)

`Attention.forward` 는 K/V 를 `repeat_interleave(n_rep=4, dim=1)` 로 **물리 복제**한다.

```
K 또는 V 한 개  (B=8, n_kv=3, T=1024, hd=64) bf16 = 3.0 MiB
복제 후          (B=8, n_q=12, T=1024, hd=64) bf16 = 12.0 MiB
층당 증분 (K+V) = 18.0 MiB
```

20층 × 18.0 MiB = **360 MiB**. 여기에 SDPA 내부 임시분을 얹어 **−0.4~0.5 GiB** 를 기대했다.
⚠️**그러나 우리 표준은 `grad_checkpoint=True`** 라 forward 중 동시에 살아 있는 층이 1개다.
**즉 이 계산 자체가 낙관적이었고, 그것이 계획서에 안 적혀 있어서 검토되지 못했다.**

## 1. ★★축의 정의를 바로잡는다 — **GQA 플래그가 축이 아니다**

> **사용자 지적**: *"애초에 실험 목적이 GQA 만이 아니었을 텐데 왜 벌써 축을 닫는가?"*
> **맞다. 결과 046 의 "축 기각" 은 과잉이었고 §5 에서 정정한다.**

| 층위 | 무엇 |
|---|---|
| **축** | ★**어텐션 활성 메모리를 줄인다**(학습 VRAM · 배포 KV) |
| 수단 1 | `enable_gqa=True` — 커널에 GQA 를 맡긴다 → 🚫**이 빌드에서 기각**(결과 046) |
| 수단 2 | ★**융합 커널을 실제로 쓰게 만든다**(FLASH/mem-efficient) → **미검증** — 단계 A2 |
| 수단 3 | KV 헤드 수·`cla_group`·head_dim 조정 | ⏸ 미착수 |
| 수단 4 | KD 손실 청크(P053)·`--no-ckpt` 상호작용 | 별도 계획 |

**수단 1 이 죽었다고 축이 죽은 것이 아니다.** 결과 046 이 닫은 것은
**"이 빌드에서 이 플래그"** 뿐이다.

## 2. ★사용자 질문 3건 — 답

### Q1. **flash attention 이 실제로 작동하는가는 왜 검증하지 않았는가**

**답: 검증했어야 했고, 안 했다. 이것이 이 실험의 가장 큰 설계 결함이다.**

단계 A 의 `G-c` 는 **`enable_gqa=True` 로만** 세 백엔드를 찔렀다.
**`enable_gqa=False`(= 우리 학습 경로)로는 한 번도 안 찔렀다.**
그래서 로그의 두 줄을 **구분할 수 없다**:

| 로그 | 무엇을 뜻하는지 |
|---|---|
| *"Torch was not compiled with flash attention"* | ⚠️**빌드에 FLASH 가 없다** — `enable_gqa` 와 무관 |
| *"both fused kernels require query, key and value to have the same num_heads"* | ⚠️**`enable_gqa` 때문에 거부** |

**두 원인이 섞여 있는데 기준선이 없어 귀속이 안 된다.**

> 🚫🚫**그리고 여기에 더 큰 질문이 숨어 있다**:
> **우리 학습 경로(off)는 지금 어떤 백엔드로 돌고 있는가?**
> 만약 그것도 **MATH** 라면 — **모든 학습이 융합 커널 없이 돌고 있다**는 뜻이고,
> 그건 F-1 보다 **훨씬 큰** 문제다(어텐션 활성 메모리·속도 전체에 걸린다).
> **우리는 이것을 한 번도 확인한 적이 없다.**

→ **단계 A2 신설**(`scripts/diag_sdpa_backends.py`, **학습 0 · 수 초**):
`enable_gqa` **off/on × FLASH/MEM_EFFICIENT/CUDNN/MATH** = **2×4 행렬** + 기본 디스패치 속도비.

### Q2. **`repeat_interleave` 는 코드상의 버그가 아닌가**

**답: 버그가 아니다. 표준 GQA 구현이고 수학적으로 정확하다.**

```python
k = k.repeat_interleave(n_rep, dim=1)      # (B,3,T,64) -> (B,12,T,64)
v = v.repeat_interleave(n_rep, dim=1)
```

| | |
|---|---|
| **정확성** | ✅ 각 Q 헤드가 자기 그룹의 KV 를 보는 것과 **완전히 동일**하다. 참조 구현(Llama `repeat_kv`)과 같다 |
| **대가** | ⚠️ **활성 메모리 n_rep(=4)배.** 층당 K+V 가 6.0 → 24.0 MiB |
| **성격** | **버그가 아니라 트레이드오프다** — *"커널이 GQA 를 모르면 복제해서 먹인다"* 가 정석이다 |

**⚠️그런데 "고칠 수 없다" 도 아니다.** 정확히 말하면:

| 대안 | 왜 안 되나 / 되나 |
|---|---|
| `expand` 로 뷰만 만든다 | 🚫 `expand` 뒤 `reshape` 이 **결국 복사**를 강제한다(비연속 → contiguous). 이득 0 |
| `enable_gqa=True` | 🚫 **이 빌드에서 MATH 강제** → 결과 046 이 실측. **이득이 아니라 대가** |
| ★**융합 커널(FLASH/mem-eff)을 쓸 수 있게 한다** | ✅ **이것이 진짜 해법**이다. 그때 `enable_gqa` 도 살아난다. ★**한 번도 확인 안 했다** → 단계 A2 |
| 어텐션 자체를 줄인다(`cla_group`·kv헤드) | ✅ 다른 수단(§1 수단 3). 별도 실험 |

> ★★**정리: 우리 코드에 고칠 것이 없다. 고칠 곳은 우리 코드가 아니라 커널 가용성이다.**
> **그리고 그것이 가능한지를 아직 안 봤다.** 그게 이 계획이 다시 열리는 이유다.

### Q3. **왜 벌써 축을 닫는가**

**답: 닫으면 안 됐다. 결과 046 의 "축 기각" 을 "수단 1 기각" 으로 정정한다.**(§5)

닫힌 것: **`--sdpa-gqa` 플래그, 이 torch 빌드, 이 GPU.**
안 닫힌 것: **어텐션 활성 메모리 축 전체.**
