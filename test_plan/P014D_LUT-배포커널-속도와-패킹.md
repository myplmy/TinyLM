## 0. ★왜 새 번호인가

P014 는 **2026-07-25 에 "커스텀 삼진 커널 검증"** 으로 시작해서
**LUT 설계 → per-row α 대가 → 배포 회계**까지 **13개월치 서술이 한 파일에 쌓였다**(222줄 + B + C).
🚫**끝난 이야기와 안 끝난 이야기가 섞여 있어 "지금 무엇이 남았는가" 를 못 읽는다.**

★**이 문서는 P014 계열에서 *아직 안 한 것만* 옮겨 온다.** P014·B·C 는 **종결**한다.

## 2. 🚫**남은 것 — 전부 "속도" 다**

★★**P014 계열이 한 번도 안 한 것이 정확히 하나**다: **LUT 커널의 실제 속도.**

P014 §0.5·§1.5 가 **두 번** 적어 뒀다: *"🚫이 단계가 하지 않는 것 — 속도."*
그 이유도 적혀 있다 — **진짜 커널이 없어서**다.

| # | 질문 | 왜 아직 못 하나 |
|---|---|---|
| ★★**Q1** | LUT 경로가 **CPU 에서 얼마나 빠른가/느린가** | 🚫**커널이 없다.** 지금 `--lut` 은 **상주 회계용**이고 계산은 여전히 dequant |
| ★**Q2** | **5비트 패킹**(g=5, 바이트=인덱스)이 실제 파일 크기를 줄이는가 | 🚫**패킹 라이터가 없다** |
| **Q3** | T-MAC / bitnet.cpp **I2_S** 를 그대로 쓸 수 있는가 | ⚠️**shape 무관**이라 가능성은 있다(P014 실사) |

## 3. ★현황 재평가 — **속도가 얼마나 급한가**

⚠️★**결과 014 §13 이 이 질문의 무게를 바꿨다.**

| | 값 |
|---|---|
| 배포 경로(int8) CPU 1스레드 | `mC_cla2_ag4` ⚙12~13 tok/s |
| 디코드 시간 모형(타잉) | `13.67 + 3.128 × 방문` ms/token |
| ★**시간의 통화** | **방문 수**(결과 014 §13.1 — 재귀도 깊이와 같다) |

★★**속도는 "방문 수" 가 지배하고 LUT 은 "방문당 비용" 을 바꾼다.**
LUT 이 **방문당 비용을 절반**으로 만들면 기울기 3.128 → ⚙1.6 이 되고,
**20방문 모델이 76 → ⚙46 ms/token = 13 → ⚙22 tok/s** 가 된다.

★**그러나 반대 위험도 있다** — 결과 014 가 **int8 언팩이 CPU 에서 −62~67%** 임을 이미 쟀다.
**LUT 이 그보다 나쁠 수도 있다**(테이블 조회가 캐시를 때린다).
🚫**우리는 어느 쪽인지 모른다.**

## 4. 단계 설계

### 4.1 ⏸단계1 — **LUT 커널 프로토타입**(⚙6h 구현)

| | |
|---|---|
| **무엇** | g=5 LUT 조회로 `y += LUT[byte][j]` 를 하는 CPU 커널(numpy/C 확장) |
| **게이트** | ★**로짓 동등성** — per-row α 재추정 때문에 **0 이 아니다**. 허용 오차는 결과 028 의 **+0.0038~0.0068 bpb** 에 대응하는 값 |
| ⚠️**위험** | 🚫**우리가 커널을 써 본 적이 없다.** T-MAC·bitnet.cpp 가 **이미 있는 물건**이라 **직접 만드는 것이 옳은지부터** 재판정해야 한다 |

★★**그래서 단계1 전에 단계0 을 둔다.**

### 4.2 ★단계0 — **직접 만들 것인가 가져올 것인가** (⚙2h, 코드 0)

| 후보 | 우리 요구 | 실사 결과(P014 §실사, 2026-08-07) |
|---|---|---|
| **T-MAC** 📄arXiv:2407.00088 | mpGEMM, dequant 없음 | ✅MIT · ✅활성 F32 · 🚫**스케일이 텐서당 1개**(우리 g128 = 428K개) |
| **bitnet.cpp TL** 📄arXiv:2502.11880 | 삼진 LUT | 🚫**shape 하드코딩**(3200/8640) |
| ★**bitnet.cpp I2_S** | Int2+Scale, **무손실** | ★**shape 무관** · x86 **2.37~6.17배** |
| 직접 제작 | g=5 per-row α | ⚙6h + 유지보수 |

★**단계0 이 답할 것**: ***"I2_S 를 우리 per-row α 로 쓸 수 있는가."***
🚫**만약 된다면 단계1 을 안 만든다** — 6시간과 영구적 유지보수를 아낀다.

⚠️★**이것이 D1 규약의 사례다**: *"미룬다" 고 쓸 때 무엇이 선결이고 얼마인지를 숫자로.*
**선결 = ⚙2h 실사.** 그것 없이 *"커널이 필요하다"* 고 6시간을 쓰지 않는다.

### 4.3 ⏸단계2 — 5비트 패킹 라이터 (Q2, ⚙3h)

⏸**단계1 이 끝난 뒤.** 패킹은 **저장(packed) 회계**이고 **상주에는 영향 없다**(함정 1).
→ ★**우선순위가 낮다.** 우리 1순위 목표는 **상주**다.

## 5. ★판정 기준

| 관측(CPU 1스레드, 같은 모델) | 판정 |
|---|---|
| LUT 이 int8 dequant 경로보다 ★**1.5배 이상 빠르다** | ✅**채택.** 배포 경로를 바꾼다 |
| 1.0 ~ 1.5배 | ⚠️**보류** — 유지보수 비용을 생각하면 애매하다 |
| ★**1.0배 미만**(느리다) | 🚫**LUT 은 상주 레버로만 남긴다.** 지금이 그 상태이고 **그것도 충분히 값어치 있다**(5.03배) |

★★**세 번째 칸이 중요하다** — **LUT 은 이미 성공한 레버**다(상주 −35.8 MiB).
**속도가 안 나와도 손해가 아니다.** 🚫**"속도까지 얻어야 한다" 는 압박으로 6시간을 쓰지 않는다.**

## 8. 2026-09-20 Stage0bW 결과

교정 재실행은 두 모델×세 경로를 모두 완주했다. int8 언팩 대역은 23.9~43.9%로 기존 유도와
겹쳐 판정 불가이고, LUT는 25.1~36.3%로 유도 하한 아래다. reference LUT 전체 경로도 fp32보다
`mC_cla2_ag4` +1%, `_r20` +23% 느렸다. 이는 profiler가 켜진 순위·비중이지 tok/s가 아니다.

사전등록 20% 중단선에는 들지 않아 LUT 축 자체는 열어 두지만, 40~55% 개방선에도 들지 않으므로
직접 커널 6h는 `HOLD`다. §4.2의 I2_S per-row-alpha 호환성 정적 실사(⚙2h)를 먼저 수행하고,
재사용 가능성이 없고 profiler상 제거 가능한 비용이 1.5× 채택선을 지지할 때만 직접 구현을 연다.

## 9. 2026-09-20 custom kernel 현황 재감사와 native CPU v0

재감사 결과 기존 구현은 세 층이었다.

1. `lut.py`: 5트릿/byte 패킹과 PyTorch `einsum+gather` reference — 모델에 연결됐지만 native가 아님.
2. `_weight_int8pack_mm`: per-row int8 융합 — 결과028에서 언팩 cache보다 6.5배 느리고 삼진
   1.6bpw를 직접 읽지 않으므로 P014D 해법이 아님.
3. `ternary_kernel.py`: GPU 학습용 Triton 실험 — CPU decode 목표와 다르며 LUT packed code를 읽지 않음.

따라서 “custom LUT kernel 구현 완료” 주장은 거짓이었다. 외부
[T-MAC](https://github.com/microsoft/T-MAC)과 [BitNet](https://github.com/microsoft/BitNet)은
고성능 SIMD·전용 layout/build 체계를 요구하고, 현 g=5 code/per-row alpha/TLinear ABI에 바로
연결되지 않는다. 이번 단계에서는 외부 소스를 vendoring하지 않고 다음 최소 native 기준선을 구현했다.

- `tinylm/csrc/lut_cpu.cpp`: packed uint8 code를 직접 읽는 float32 CPU C++ LUT v0.
- `tinylm/model/lut_cpu.py`: explicit `lut_backend=native_cpu`일 때만 lazy build; Ninja가 없으면
  로컬 C++17 compiler fallback. 실패 시 reference로 조용히 fallback하지 않음.
- `TLinear.forward`: default `reference`는 불변, native는 CPU/per-row alpha만 fail-closed.
- 정합: 2-D·3-D·TLinear dispatch compiled PASS.
- 합성 M=1, 1 thread 두 차례: native/reference 1.36~2.42×, native/dense
  0.288~0.731×. 즉 Python overhead 감소 방향은 재현됐지만 짧은 microbenchmark 분산이 크고,
  dense를 이긴 형상은 없어 SIMD 최적 kernel은 아직 아니다.

`run_P014D_Stage1W_native_lut_kernel.sh`는 compile 정합→TinyLM shape→두 actual model
decode를 같은 세션에서 실행한다. native LUT가 int8 경로보다 1.5× 빠른 모델이 하나도 없으면
exit8 음성이다. 이는 per-row 재양자화 speed gate이며 품질 채택은 아니다.

> 이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.
