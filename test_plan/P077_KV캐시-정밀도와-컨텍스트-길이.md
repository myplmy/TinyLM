## 3. 단계0 — ★**`--repeat-kv-reuse` 프로브** (⚙10분, 학습 0, **지금 된다**)

### 3.1 무엇

이미 학습된 `mC_cla1_ag4_r20nc` 를 **두 가지로 평가**한다:


## 4. 단계1 — bf16 KV 구현 (⚙1h, 큐가 빈 뒤)

### 4.1 설계

```
--kv-dtype {fp32,bf16,int8}      기본 fp32 = ★비트 동일(R28)
```

`kv_bank[key] = (k.to(dt), v.to(dt))` 저장, 조회 시 `.to(q.dtype)`.
🚫**RoPE 는 그대로 fp32 로 적용**하고 **회전 뒤**를 저장한다(KIVI 와 같은 위치).

### 4.2 ★게이트 — **로짓 동등성이 0 이 아니다**

`diag_kvcache.py` 는 지금 **teacher-forced 로짓 동등성 0** 을 요구한다.
🚫**bf16 KV 는 0 이 안 나온다.** → ★**허용 오차를 미리 정한다**:

| dtype | ⚙기대 `max\|dlogit\|` | 근거 |
|---|---|---|
| fp32 | **0.000e+00** | 비트 동일 |
| bf16 | ⚙**1e-2 ~ 1e-1** | bf16 유효자릿수 ~3 |
| int8 | ⚙**1e-1 ~ 1e0** | — |

⚠️★**이 기대값은 근거가 약하다**(함정 34 — 기준값을 먼저 의심한다).
★**게이트가 실패하면 모델보다 기준값을 먼저 본다.**

## 단계4A. P109 16층 G4의 1,024토큰 INT8 KV 저장 대조

원장 65의 40 MB 제약과 P077의 축 분리를 확인한다. 동결 P079 16층 G4 R2·32K·INT8 어휘표·동일 CPU 경로에서 KV 저장만 바꾼다. 32토큰 단위 K 채널별 scale과 토큰·헤드별 V scale을 FP16으로 저장한다. 남은 미완 그룹은 FP16이며 다음 그룹을 닫을 때 한 번만 INT8로 인코딩한다. 복원은 FP16과 기존 어텐션 경로를 사용한다.

이전 합성·영어·한국어 세 1,017토큰 입력의 8개 기존 응답 ID를 참조한다. 첫 prefill 로짓은 공유하고, 이후 같은 기존 greedy 토큰을 두 경로에 공급해 전어휘 로짓 차이와 다음 토큰 선택을 대조한다. 1,024토큰의 FP16 캐시 11,010,048 B와 INT8 코드·scale·잔여분의 실제 저장 용량을 비교한다. 기존 `0.001` 로짓 문턱과 ID 동률을 함께 보며, 수치 기준을 벗어나면 근사 저장 방식으로 남긴다.

태그 `p109_g4_grouped_int8_cache_v1_20261119`. 단일 CPU와 기존 runtime에서 230초 상한을 적용한다. 모델과 토크나이저·첫 prefill·FP16 원답은 기존 증거에 맞춘다. 어텐션 전 전체 FP16 복원을 사용하므로 이 단계의 저장 바이트에는 복원 중 peak RSS와 실제 장치 지연을 귀속하지 않는다. [이전 FP16 결과](../test_result/109_20261119004016_P109-기존G4-방문-세정책-실제갱신.md#p109-g4-int8-kv1024) · [CPU 검증기](../scripts/diag_p109_g4_grouped_int8_cache.py)

**결과 회수**  1,024토큰에서 실제 KV 저장 5,763,072 B와 기존 24개 선택을 확인했다. 로짓 오차는 0.001 문턱을 넘어 근사 저장으로 유지한다. 블록 복원을 연결한 전체 메모리와 지연은 별도로 확인한다. [결과109 §15](../test_result/109_20261119004016_P109-기존G4-방문-세정책-실제갱신.md#p109-g4-grouped-int8-cache)

## 단계4B. 그룹 INT8 KV를 연결한 네이티브 전체 텍스트 요청

원장 65의 실사용 메모리 대조다. 동결 32K 16층 G4의 R4 정적 AVX2 실행기에서 캐시 저장·복원만 바꾼다. 현재 어텐션에 필요한 owner 슬롯의 코드와 scale을 8원소씩 기존 FP32 K/V 작업공간에 바로 복원한다. FP16 잔여분은 다음 그룹이 완성될 때만 인코딩한다. 끝까지 재사용할 잔여분 용량과 변환 작업공간도 계수한다. 1,024토큰의 상주 캐시 할당은 6,096,384 B와 약 4.9 MB 작업영역 감소를 예상한다.

같은 신호 경로의 FP16과 전어휘 8위치씩을 대조한다. 31·63토큰 접두는 새 그룹이 닫힌 뒤 처음 읽는 경계를 포함한다. 이전 한영 1,017토큰 요청도 사용하며 prefill 전어휘 동률과 공통 생성 이력의 로짓 오차를 집계한다. 새 네이티브 경로의 전체 UTF-8 요청은 한영이 각각 두 회다. 토큰화·네이티브·복원이 동일 PID인지, 원본 ID·텍스트·40 MB와 40 MiB를 확인한다. 수치 문턱은 `0.001`을 유지한다.

태그 `p109_g4_native_int8_cache_v1_20261119`, 기존 CPU0·정적 GCC·240초 상한이다. 속도와 RSS는 이전 AVX2의 네 독립 전체 요청을 재사용하고 실행 시점이 다른 관측으로 보고한다. 숫자 경로의 로짓 파일 기록은 전체 텍스트 RSS에 포함하지 않는다. 대상 기기와 대어휘 토크나이저에는 별도 검증이 필요하다. [기존 AVX2 기준](../test_result/109_20261119004016_P109-기존G4-방문-세정책-실제갱신.md#p109-g4-avx2-lookup-speed) · [네이티브 캐시](../scripts/p109_g4_grouped_int8_cache.hpp) · [CPU 검증기](../scripts/diag_p109_g4_native_int8_cache.py)

**결과 회수**  WSL 전체 요청의 최고 RSS는 34,754,560 B였다. 두 긴 입력의 ID·텍스트와 짧은 경계 입력의 선택을 보존했다. 최대 로짓 차이는 긴 입력 0.008163, 경계 입력 0.038136이었다. 1,024토큰 메모리 우선의 근사 후보이며 실장 속도·품질 판정을 이어간다. [결과109 §16](../test_result/109_20261119004016_P109-기존G4-방문-세정책-실제갱신.md#p109-g4-native-int8-cache)

## 단계4C. G4의 입력 구간과 출력 로짓 배열을 줄인다

원장 65의 40 MB 목표를 위해 네이티브 INT8 KV를 유지하고 두 작업영역을 줄인다. 일반 greedy는 가장 큰 점수와 첫 ID만 유지한다. 검증에서만 전어휘 점수를 받아 65토큰 입력에서 기존 선택·로짓 동률을 확인한다. 입력 처리는 기존 전체와 256·64토큰 구간을 대조한다. 중간 구간은 캐시만 쓰고 이후 구간의 어텐션은 앞 구간의 INT8 저장값을 읽는다. 구간별 활성값의 FP32 연산을 유지하며 이 저장 경계 변화에 따른 점수 차이는 측정한다.

1,024토큰 네이티브에서 256·64 설정이 FP32 활성값을 각각 2,359,296·2,949,120 B 줄일 것으로 예상한다. greedy가 제거하는 배열은 32K 기준 131,072 B이고 객체 오버헤드는 별도다. 동일 한영 1,017토큰 접두에서 전어휘 로짓·다음 ID와 네이티브 작업 공간을 대조한다. 한 PID 전체 요청은 언어별로 1024→256→64→64→256 순서다. 입출력·최고 RSS·첫 토큰과 전체 시간을 회수한다. 기존 0.001을 수치 차이의 기준으로 사용하고 생성 출력 동률을 함께 기록한다.

태그 `p109_g4_bounded_prefill_v1_20261119`. 기존 CPU0·정적 GCC·봉인 모델·토크나이저를 쓰고 전체 320초를 상한으로 둔다. GPU의 독립적인 옵티마이저 작업과 병행한다. 두 언어 입력에서 나온 결과는 이 WSL 32K의 관측이며, 대어휘 테이블과 토크나이저를 넣은 RSS는 아직 계산 범위다. [검증 실행기](../scripts/diag_p109_g4_bounded_prefill.py)

**결과 회수**  greedy 배열 제거의 전어휘 비트 동률을 확인했다. 256·64 입력은 엔진 최고 32.27·31.68 MB, 전체 최고 33.91·33.96 MB였다. 한영 모든 생성 선택과 출력이 같았고 구간 경계의 로짓 차이가 수치 문턱을 넘었다. 256을 우선 자원 후보로 두고, 64는 엔진 메모리가 더 필요한 조건에서 시간을 확인한다. [결과109 §17](../test_result/109_20261119004016_P109-기존G4-방문-세정책-실제갱신.md#p109-g4-bounded-prefill)

## 단계4D. 전체 문맥과 입출력 길이의 별도 확장 연구

P109C의 첫 실사용은 문맥 1,024·서식 포함 입력 896·응답 128토큰이다. 여기서는 같은 CPU 배포 예산으로 더 긴 근거와 답변을 다루는 방법을 검증한다. 기준 길이의 일반 답변과 긴 문맥에서만 풀 수 있는 한영 독립 질문을 함께 봉인한다.

| 후보 | 설계 | 예상 교환비 |
|---|---|---|
| A | 2,048 전구간 FP16 KV와 블록 어텐션 | 같은 길이의 품질 기준이다. 작업공간을 줄여도 긴 KV 저장량은 늘어난다. |
| B | 기존 그룹 INT8 KV와 고정 크기 K/V 복원 작업공간 | P109의 그룹 scale, FP16 잔여, 현재 전구간 복원 결과를 기준으로 삼는다. 복원 블록을 작게 유지하며 기존 연산 순서를 우선 검증한다. |
| C | 짧은 구간 고정밀 KV와 오래된 구간 저정밀 KV | B가 메모리와 답 기준을 함께 만족하지 못할 때 채널별 K·토큰별 V의 오차와 복원 비용을 측정한다. 필요한 과거 근거는 계속 참조한다. |

기존 1,024 FP16 및 같은 2,048의 A·B에서 먼저 동일 입력·출력 예산을 비교한다. 그 뒤 입력만 늘린 경우와 출력만 256·512로 늘린 경우를 따로 검증한다. 한 PID 전체 최고 RSS와 상주 KV, 첫 토큰 지연, 생성 처리량, 실제 답 완결·조기 종료·반복을 기록한다. 독립 정답의 보존과 기존 기준의 전체 RSS를 함께 판단하며 수치 차이는 원인 진단으로 남긴다.

연구 선행은 [FlashAttention](https://arxiv.org/abs/2205.14135), [메모리 효율 어텐션](https://arxiv.org/abs/2112.05682), [KIVI](https://proceedings.mlr.press/v235/liu24bz.html), [TurboQuant](https://proceedings.iclr.cc/paper_files/paper/2026/hash/5c802ef38ab6e366c2ea06eee554c088-Abstract-Conference.html)이다. 우선 GPU나 모델 없이 블록 복원의 CPU 수치와 작업 배열을 검증한다. 실제 2,048 모델의 위치표, 입력 보존과 독립 장문 문항을 확정한 뒤 배포 대조에 들어간다. 신규 의존성은 현재 계획에 필요하지 않다. 상태는 `DESIGNED`다.

### 4,096토큰 전체 보존에서 근거 거리와 KV 정밀도 대조

현재 2,048에 쓴 소형 G4 가중치·32K ChatML·64행 선채움을 고정한다. 구간 RoPE의 절대 위치를 4,096까지
사용한다. 오래된 KV는 K4·V3와 K2·V2, 최근 최소 128토큰은 두 조건 모두 그룹 INT8 및 FP16 잔여로 처리한다.
한영 각 한 표의 값 교환 문항에서 표를 질문 직전 또는 긴 본문 앞에 놓고, 같은 토큰 수를 유지한다. 실제
숫자·ChatML 종료, KV 저장량, 전체 UTF-8 요청의 최대 RSS와 첫 토큰 지연을 회수한다. 2,048에서 확보한
근접 답을 참조하고 실사용 기본 설정은 현재 정본을 따른다.

먼 근거를 선택하는 방식은 완전 보존의 품질과 비용을 먼저 확인한 뒤 다룬다. InfLLM의 GPU 작업공간 관리에는
CPU에 보관한 전체 과거 KV가 있으므로 CPU의 전체 RSS에는 대표 키·인덱스와 함께 그 저장소를 포함해야 한다.
선택을 추가할 때에는 같은 예산의 정답 블록 강제 접근, 질의 기반 선택, 최근창을 따로 대조한다.
[InfLLM §3.2](https://proceedings.neurips.cc/paper_files/paper/2024/file/d842425e4bf79ba039352da0f658a906-Paper-Conference.pdf) · [실행기](../scripts/diag_p077_g4_context4096.py)

두 정밀도에서 한영 총 16요청과 ChatML 종료를 회수했다. 최대 전체 RSS는 30,318,592 B였고 같은 근접
원천의 2,048 보관 정답 네 개를 4,096에서는 모두 잃었다. 같은 소스에서 정답 블록을 짧은 읽기 범위로
재제시하는 대조와, 전체 길이에서 위치만 바꾸는 대조를 먼저 둔다.

### 기존 그룹 INT8의 구간 복원

첫 CPU 대조는 현재 G4의 14슬롯, KV 폭 192, 32토큰 그룹에서 임의 시작·길이의 복원만 바꾼다. 기존 전체 복원 소스를 고정해 대조하고 32토큰 경계, 미완성 FP16 잔여분, 2,048토큰과 64행 작업 배열을 검증한다. 저장 바이트와 복원 작업 배열의 합을 1,024 FP16 경로와 비교한다. 모델·전체 RSS·지연·품질은 후속 판정의 대상이다.

CPU 구간 복원 8,918회에서 기존 전체 복원과 비트 일치했다. 2,048 그룹 INT8의 저장·64행 복원·변환 배열 합은 11,982,336 B이며 1,024 FP16 전체 복원의 해당 배열 합 12,582,912 B보다 작다. [결과065 §10](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-grouped-int8-block-restore-result)

저장 쪽 대조는 각 호출에서 새 토큰의 K·V 배열만 넘기고, 미완성 그룹이 닫힐 때 기존 FP16 잔여분을 합친다. 동일 분할 순서의 기존 전체 배열 입력을 기준으로 32토큰 완성·잔여·2,048 끝 경계에서 저장 후 복원을 확인한다.

새 토큰만 담은 182개 입력 배열에서 기존 저장·복원과 비트 일치했다. 실제 경로에 연결할 때는 같은 슬롯의 현재 방문이 FP32 투영값을 모두 읽은 뒤 저장하고, 출력 구간의 어텐션은 기존 합산 순서를 먼저 대조한다. [결과065 §10.1](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-grouped-int8-recent-append)

기존 G4는 답 위치마다 점수 최대값, 지수합과 V 가중합을 구한다. 구간 복원이 맞으면 두 번 읽는 경로는 점수 배열을 두고 K와 V를 차례로 복원해 기존 합산 순서를 유지할 수 있다. 온라인 누적은 점수 배열도 없앨 후보이며 블록 순서에 따른 부동소수 차이를 별도로 평가한다. KIVI의 K 채널별·V 토큰별 방식은 저장 레이아웃을 바꾸는 후속 후보로 둔다. [FlashAttention 알고리즘 1](https://proceedings.neurips.cc/paper_files/paper/2022/file/67d57c32e20fd0a7a302cb81d36e40d5-Paper-Conference.pdf) · [KIVI 논문](https://proceedings.mlr.press/v235/liu24bz.html)

두 번 읽는 CPU 경로에서 K와 V는 하나의 64행 작업 배열을 번갈아 쓴다. 실제 G4의 내적과 V 누적을 재사용하고, 같은 INT8 과거와 현 요청의 FP32 K·V에서 전체 복원과 비교한다. 각 이전 길이에서 유효한 새 위치까지만 인과 참조한다. 이 대조는 어텐션 값과 배열 크기를 판정한다.

CPU에서 252회·193,536개 출력이 비트 일치했다. 점수와 공용 복원 배열은 합해 147,456 B다. 전체 1,024의 기존 압축 구현과 로짓을 대조한 뒤 2,048 위치표 및 긴 실제 답의 품질·지연·RSS를 검증한다. [결과065 §10.2](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-grouped-two-pass-attention-result)

첫 실제 모델 시험은 기존 32K G4와 토크나이저를 고정하고, 64토큰씩 처리하는 1,024문맥의 한국어·영어 요청을 한 번씩 실행한다. 저장된 동일 조건의 입력 ID·출력 ID·텍스트·전체 RSS·시간을 대조 자료로 재사용한다. 후보는 과거 K·V를 구간별로 읽고 같은 슬롯이 사용을 마치면 새 행을 저장한다. 예상 1~4분이다. 모델의 2,048 위치와 그 길이에서만 풀리는 독립 과제는 이후 별도로 검증한다. [실행 경로](../scripts/p077_g4_blocked_runtime.py)

1,024문맥 한영 두 요청의 출력과 텍스트를 보존했다. 엔진 작업공간은 2,037,000→656,696 B, 전체 최고 RSS는 33,792,000 B였다. 고정 위치표를 2,048로 확장하고 같은 가중치·내용의 장문 실행을 대조한다. [결과065 §10.3](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-g4-blocked-runtime-result)

2,048 기술 시험은 `TLMG4R5`의 분리된 파일 형식을 사용한다. R4의 가중치와 0~1,023 RoPE를 그대로 가져오고, 같은 식으로 계산한 1,024~2,047을 뒤에 붙인다. 작성한 한국어·영어 두 질문은 각각 2,041 입력과 8 생성, 근거 시작은 0부터 세는 토큰 위치 6과 1,204다. 같은 PID로 두 요청의 토큰·출력 원문·최고 RSS·시간을 남긴다. 짧은 진단의 첫 단어 정답은 기록하고 정식 장문 품질의 표본은 별도로 확정한다.

같은 R5 파일과 실행 바이너리를 재사용해 채움 구두점만 뺀 두 질문을 짧은 조건에서 다시 확인한다. 두 경우의 답변 원문과 정답을 함께 남긴다. 채움과 길이가 함께 달라지므로 두 문항 차이는 해당 질문의 진단 범위에서 해석한다.

2,048 길이의 실제 기술 실행을 완료했고 두 요청의 최고 RSS는 36,368,384 B였다. 짧은 대조와 긴 두 문항 모두 첫 단어 정답 0/2다. 이 결과를 제품의 품질 판정에 쓰려면 짧은 대조에서 먼저 해결되는 문제와 독립 장문 문항을 확정해야 한다. 메모리는 1,024 블록 INT8의 보관값과 기존 FP16 전체 요청의 보관값을 각각 참조한다. [결과065 §10.4](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-g4-extended-context-result)

### 오래된 1,024행의 4비트 저장 대조

현재 2,048 경로의 KV 저장은 11,859,456 B다. 같은 FP16 스케일·잔여 배열을 쓰면서 앞쪽 1,024행의 K 또는 V만 4비트로 바꾸면 한쪽당 1,376,256 B를 아낄 수 있다. 양쪽 4비트는 2,752,512 B를 아낀다. 이 값은 코드 배열의 예상 절감이다. 전체 RSS는 실제 배포 프로세스에서 다시 측정한다.

동일 FP16 입력을 가진 세 종류의 작성 텐서에서 전량 INT8와 앞부분의 K 4비트, V 4비트, 양쪽 4비트를 비교한다. 기존 K 채널별·V 행의 헤드별 스케일 축을 유지한다. 4비트 경로는 두 코드를 실제 한 바이트에 저장하고 다시 읽는다. 최근 1,024행의 복원값을 비트 대조하고, 일반 쿼리와 앞·뒤 근거를 찾는 쿼리의 K·V 오차, 어텐션 값 오차, 최대 점수 위치를 기록한다. 이 자료는 C++ 후보와 정식 품질 대조의 조건을 고르는 데 사용한다.

세 합성 조건에서 앞부분의 근거를 찾은 INT8 헤드 140개를 모두 보존한 후보 중 K와 V에 함께 4비트를 적용하는 경로의 저장 절감이 가장 컸다. 같은 R5 모델 파일 지문, 64토큰 prefill, CPU, 동일 PID의 토큰화·요청 경로와 2,041 입력·8 생성을 고정해 실제 자원 후보로 검증한다. 앞선 두 INT8 요청을 대조로 재사용한다. 최신 1,024 블록 INT8 요청에서 회수한 최고 RSS를 문맥 확장의 메모리 목표로 삼는다. 기존 장문과 단문 문항의 적중이 0/2여서 이번 두 응답은 생성 동작과 차이 확인에 사용한다. 품질 채택은 짧은 입력에서 정답을 내는 독립 평가에 맡긴다.

실제 C++ 저장과 두 장문 요청을 완료했다. 최고 RSS는 36,368,384→33,959,936 B였고 1,024통계 목표까지 167,936 B가 남았다. 정답은 두 팔 모두 0/2였고, 일회씩 측정한 전체 요청 시간은 각각 40.48%, 19.56% 증가했다. 메모리 후보로 유지하며 다음 기술 대조는 복원과 어텐션 시간의 원인을 분리한다. [결과065 §§10.5~10.6](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-old-kv-int4-pack-result)

### KV 헤드별로 연속 쿼리의 과거 복원을 공유

현재 prefill에서는 과거 K와 V의 64행을 각 쿼리마다 복원한다. 전량 FP32 복원 재사용은 2,048토큰을 기준으로 K와 V에 약 3.15MB가 필요하다. 전체 헤드에서 쿼리 두 개를 동시에 처리하면 점수 배열이 98,304 B 증가한다. 세 번째 방식은 같은 KV 헤드를 보는 네 Q 헤드와 연속 쿼리 최대 세 개를 한 번에 처리한다. 현재 12개 점수 행과 64행 복원 배열 안에서 계산할 수 있어 이 방식부터 시험한다. 저장 형식과 최근 FP32 입력은 그대로 사용하고, 각 쿼리는 자기 인과 경계까지 읽는다. 디코드의 쿼리 한 개는 현재 코드를 사용한다.

CPU 작성 입력의 전량 INT8과 앞부분 K·V INT4에서 기존 쿼리별 경로와 묶음 경로를 비교한다. 인과 경계, INT4/INT8 경계, FP16 잔여, 슬롯 0과 마지막 슬롯, 점수 크기와 묶음 크기의 나머지를 포함한다. 같은 어텐션 계산에서 모델 없이 복원 시간과 전체 시간을 따로 계측한다. 같은 저장 조건의 어텐션 출력이나 작업공간이 달라지면 원인을 확인한다. 통과하면 앞선 R5의 모델·2,041 입력·8 생성·스레드 조건과 대조해 실제 지연과 RSS를 확인한다. 제품 기본값과 330M 학습 경로에는 적용하지 않는다.

실제 한영 각 한 요청의 prefill 시간 변화는 서로 다른 방향이었다. 시간이 늘어난 영어의 2,041개 ID와 같은 R5 파일을 고정해 기존·묶음·묶음·기존 순으로 네이티브 시간만 대조한다. 각 프로세스의 CPU 시간과 실제 경과를 함께 재고, 2,048 용량·작업공간·출력 ID를 고정한다. 토큰화와 별도 문항 채점은 앞선 결과를 사용한다.

<a id="p077-phase-workspace-reuse"></a>
### 어텐션 작업공간을 FFN에서 다시 쓰는 후보

현재 `visit`의 쿼리와 어텐션 출력은 Q 투영부터 O 투영까지 필요하다. 이후 FFN의 `up` 투영에 쓰는 배열은 그 기간에 비어 있다. `up`의 두 분리된 구간을 두 어텐션 배열로 쓰고, O 투영 뒤에 FFN이 전체 배열을 사용한다. 원본 C++의 타일 32를 대입한 초기 절감 예상에는 R5 렌더링에서 타일을 8로 바꾸는 단계가 빠졌다. 실제 예상 절감은 `2 × 8 × 768 × 4 = 49,152 B`다. 현재 타일과 연산 순서를 사용한다. 타일을 더 줄이면 가중치 행 복원 횟수가 달라지고, KV 복원 블록을 64에서 32로 줄이면 24,576 B를 아끼면서 구간 호출이 늘어난다.

같은 R5 모델·2,048 용량·INT4 앞부분·쿼리 묶음에서 작업공간 재사용만 바꾼다. 실제 요청의 8토큰 선택과 가능하면 전체 로짓을 비교하고, 엔진 배열·실제 RSS·시간을 각각 회수한다. 보관한 1,024 경로와의 RSS 비교는 같은 CPU에서 나온 참고값으로 해석한다.

작업공간 실측 49,152 B 절감과 영어 262,144개 로짓 동일을 확인했다. 네이티브 RSS는 감소했지만 전체 피크는 해당 두 표본에서 증가했고, 2,048의 네이티브 RSS가 1,024보다 약 3.28MB 높았다. 다음 품질 대조는 단문에서 답을 맞추는 같은 모델의 독립 과제에서 근거 거리와 캐시 정밀도를 따로 비교한다. [결과065 §10.10](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-phase-workspace-result)

<a id="p077-r5-long-choice"></a>
### 짧은 입력에서 근거에 반응한 한영 문항의 장문 대조

같은 P079 G4 R2·32K의 보관 Winogrande 및 KoBEST COPA 점수에서 정답을 고른 문항을 찾는다. 두 과제의 공식 요청과 토큰 배치 지문을 기존 결과에 대조한다. 보관 정답 점수차가 0.08 nat 이상이고, 두 보기의 문맥 토큰수 및 지도 토큰수가 각각 같으며, 같은 근거와 질문 끝을 분리할 수 있는 경우를 고른다. 정답 위치별 고정 해시 순서를 사용한다. Native R5가 단문에서 0.05 nat 이상으로 맞히고, 같은 길이의 중립 토큰으로 앞 근거를 바꿀 때 정답 마진이 0.10 nat 이상 내려가면 입장한다. 언어별 정답 위치당 최대 두 문항을 장문 점수를 읽기 전에 고정한다.

장문의 전체 모델 입력은 2,048토큰이다. 같은 중립 토큰 블록을 문항 근거 앞에 놓는 조건과 근거와 질문 사이에 놓는 조건을 만든다. 각 보기는 근거·중립 블록·문항 끝·지도 ID가 같고 블록 순서가 달라진다. 2,048 용량, 64토큰 prefill, 쿼리 묶음 및 어텐션·FFN 배열 공유를 고정하고 전량 INT8, 앞쪽 1,024의 K·V INT4를 각각 실행한다. 짧은 경로와의 차이에는 길이·채움·위치가 포함된다. 긴 경로의 같은 위치에서 KV만 바꾼 차이를 따로 낸다. 강제 입력 전체 continuation의 로그확률 합, 적중, 정답 마진과 바뀐 선택을 회수한다. 새 변형의 점수는 이 진단에 사용한다. 기존 INT4 Greedy ID를 강제한 전체 로짓 지문 일치를 입력 방식의 사전 검증으로 사용한다.

반 검토는 근거 가림만으로 어휘 단서의 영향과 관계 사용을 가를 수 없다는 최소 반례를 확인했다. 별도로 작성한 단문 쌍은 두 개체의 위치와 정답 후보 ID를 그대로 두고 설명하는 속성만 교환한다. 두 표본 모두 정답 순위가 뒤집히는 문항을 확인해 후속 거리 실험 후보로 둔다. 이미 고정한 공식 유래 여덟 문항의 해석은 근거 가림에 민감한 어휘 선택으로 제한한다.

32개 장문 조합을 완료했다. 모든 조건의 정답은 6/8로 같았고 KV 정밀도만 바꾼 선택 전환은 0건이었다. 작성 속성 반전은 토큰 조건을 만족한 7쌍에서 동시 정답 0쌍이었다. 앞부분 INT4는 장문 메모리 후보로 이어가며, 1,024 대비 상주 메모리 차이와 일반 품질은 추가로 검증한다. [결과065 §§10.11~10.12](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-r5-long-choice-result)

### 앞부분 K와 V의 합계 6비트 배분

기존 2,048 R5의 네이티브 상주 증가 3,280,896 B를 저장 배열에서 우선 상쇄할 후보를 고른다. 같은 2,048에서 현재 앞 1,024 K·V INT4와 뒤 INT8을 기준으로 둔다. 앞 1,920행을 K·V 대칭 3+3비트, affine K 2비트와 기존 V 4비트, 기존 K 4비트와 affine V 2비트로 각각 바꾼다. 뒤 128행과 미완성 FP16은 유지한다. K 32행·채널별 및 V 행·헤드별의 FP16 스케일과 affine 오프셋을 포함한다. 이 분모로 배열을 계산하고 실제 패킹과 해제를 CPU에서 검산한다.

기존 코드가 저장하는 RoPE 이후 K를 검증 대상으로 둔다. 근거 위치를 보는 합성 쿼리에서 K 변경이 순위·softmax 확률에 미치는 영향과 기준 가중치를 고정한 V 변경의 가중합 오차를 잰다. INT8과 현 INT4 기준을 모두 비교한다. 이 수치로 실제 품질을 대신하지 않고, 가장 작은 기계적 손실을 보이는 후보의 네이티브 복원과 실제 긴 입력을 따로 검증한다. K의 채널별·V의 토큰별 오차와 RoPE 전후 효과는 대형 모델에서 따로 관측된 바 있다. [KIVI](https://proceedings.mlr.press/v235/liu24bz.html) · [KVQuant 표 9~10](https://papers.neurips.cc/paper_files/paper/2024/file/028fcbcf85435d39a40c4d61b42c99a4-Paper-Conference.pdf)

세 후보가 배열에서 필요한 3,280,896 B를 각각 상쇄했다. 2+4는 출력 오차가 가장 작았고 4+2는 근거 최고점을 모두 보존했다. 3+3은 저장을 가장 많이 줄였다. 네이티브 대조에서는 배열 차이가 실제 상주·속도에 반영되는지와 같은 장문에서 선택이 바뀌는지를 확인한다. [결과065 §10.13](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-kv-six-bits-result)

### 2,048 네이티브 KV에서 두 비트 배분 적용

같은 C++ 그룹 구조에서 앞 K·V 비트를 각각 지정한다. 기존 INT8·INT4 생성자는 기존 동작을 유지한다. 새 3비트의 대칭 스케일과 2비트의 FP16 최솟값·스케일을 사용하고, AVX2에서 8개 복원을 처리한다. 먼저 보관된 기존 헤더의 네이티브 출력과 새 코드의 INT4 출력, CPU 참조 포장과 새 세 후보의 전량 복원, 첫·마지막 슬롯과 1,920 격자·FP16 잔여 경계를 확인한다. 이어서 앞 답이 유지된 4+2 및 출력 오차가 작았던 2+4의 실제 R5를 기존 고정 장문 문항에서 평가한다. 품질의 이전 비교 팔은 보관 로그를 사용한다. [네이티브 KV](../scripts/p109_g4_grouped_int8_cache.hpp)

네이티브 복원 세 후보의 수치와 기존 INT4의 바이트가 일치했다. 실제 R5의 먼 근거 문항에서 K2·V4와 K4·V2는 각각 6/8, 기존 선택과 변경 0건이었다. ### 64행 블록의 온라인 softmax

기존 같은 2,048 K4·V2 캐시와 Q/K/V를 사용한다. 그룹별로 K와 V를 64행씩 복원하고, 쿼리별 최대값과 분모 및 가중 출력만 이어서 누적한다. 최대값이 커질 때 분모와 이미 누적한 출력을 같이 다시 비례 조정한다. 인과 경계 안의 신규 KV도 같은 방식으로 처리한다. 점수 배열은 전체 문맥에서 64행으로 줄고, 분모로 나누는 계산을 최종 출력에서 수행한다. ### 실제 답이 회복된 소형 G4의 네이티브 KV 대조

결과065 §10.21의 가까운 표 고정 팔은 먼 근거 기준에서 가중치를 보관하지 않았다. 동일 192갱신의 첫 재현에서는 48갱신부터 손실 차이가 있었고 지문이 달랐다. 같은 학습조건에서 새 한 팔을 고정하고 그 지문과 기존 지문을 별도로 기록한다. 보관된 PyTorch 답은 기존 모델의 참고로 쓴다. 머리·꼬리와 공유 MLP·KV의 전체 재귀 경로를 같은 형태로 컴파일하고, 새 모델 하나의 같은 압축 가중치에서 1,024 INT8, 2,048 INT8과 2,048 K4·V2를 비교한다. 2,048의 두 팔에서 같은 문항을 읽어 전체 답 ID·정답·종료, KV 바이트, 네이티브 prefill RSS와 전체 요청 최고 RSS 및 첫 토큰 시간을 기록한다. 기존 장문 토큰은 ID 경로에서 그대로 읽고 전체 텍스트 요청은 같은 사례에서 다시 토큰화한 UTF-8 입력을 봉인해 두 2,048 팔에 일치시킨다. ### 동일 2,048에서 오래된 값 캐시에 한 비트 추가

결과065 §10.23에서 앞 1,920행 K4·V2는 한국어 개별 답 다섯 건을 잃었다. 같은 K4에 V3을 쓰면 대칭 값 스케일과 코드의 배열 추정은 4,035,584 B다. 1,024 INT8보다 28,672 B 낮은 범위다. 같은 압축 모델 해시, 입력 ID 64쌍, 별도 UTF-8 여덟 입력에서 K4·V3 한 팔을 실행한다. 기존 두 2,048 팔의 답과 요청을 비교에 재사용한다. 품질은 한국어에서 복구된 답과 새로 잃은 답을 확인한다. 시간은 이전 실측과 실행 시각을 같이 적고 최종 속도 채택은 다시 교차 측정한다. [코덱 대조 실행기](../scripts/diag_p077_grounded_near_native.py)

K4·V3에서 같은 2,048 INT8의 정답 82개와 추가 한국어 답 하나를 얻었다. 캐시 배열은 예상 크기였고 1,024 대비 전체 최고 RSS 차이 32,768 B와 prefill RSS 차이 256,000 B가 남았다. R5의 전체 RoPE 위치표를 현재 prefill 구간에서 한 번 계산해 층과 재귀 방문에 재사용하는 후보를 먼저 검증한다. 실제 각도와 생성 답, 모델에 포함되는 바이트와 작업 배열, 동일 UTF-8 요청의 상주·처리 시간을 기존 K4·V3과 교차 비교한다. [결과065 §10.26](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-grounded-small-native-k4v3-result)

### RoPE의 절대 위치를 64행씩 계산

기존 2,048의 사인·코사인 표는 524,288 B다. 같은 정밀도의 역주파수 128 B만 자산에 보관하고, 모델의 현재 입력 구간을 읽는 호출에서 절대 위치로 두 배열을 만든다. 64행 전체 작업공간은 16,384 B이며 모든 물리 층과 재귀 방문이 공유한다. 과거 KV에는 당시 절대 위치로 회전한 키가 계속 남는다. 각도 131,072개와 63·64·65 및 127·128·129의 실제 배치를 대조한다. 2,048 UTF-8 여덟 입력에서 같은 K4·V3의 기존 표와 구간 계산 순서를 교차 배치하고, 고정 64쌍의 품질 대조는 기존 표의 완료 기록을 사용한다. [구간 계산기](../scripts/p077_rope_tile.py)

실제 64쌍의 답 ID를 보존했고, 2,048 네이티브 prefill RSS 중앙은 보관 1,024 INT8보다 낮았다. 두 2,048 팔의 전체 요청 최고 RSS는 16건 모두 텍스트 디코딩 단계였다. 다음 CPU 순서는 기존 출력 바이트의 정확성을 유지하면서 인코딩용 BPE 병합표를 로드하지 않는 출력 전용 디코더의 메모리와 경과를 대조하는 것이다. 실제 한국어·영어 답 ID와 ByteLevel의 UTF-8 경계, 예약 토큰 제거, 잘못된 바이트 교체를 포함한다. [결과065 §10.28](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-grounded-rope-tile-result)

### 먼 표의 값 위치 선택을 실제 숫자 반환에 연결

소형 표 학습에서 보관한 값 위치 헤드를 그대로 로드한다. 2,048에서 표가 앞에 있고 질문이 뒤에 있는 값 교환과 질문 변경을 각각 두 종류의 무관 본문으로 대조한다. 입력에 쓰인 네 숫자의 끝 토큰과 질문 끝만 모형에 전달한다. 선택한 숫자의 실제 토큰열을 읽어 반환하고, 일반 생성 답은 같은 입력에 이미 완료한 기록을 우선 쓴다. 질문 변경의 새 장문은 같은 입력에서 일반 생성도 함께 측정한다. 양쪽 정답, 실제 네 값 중 선택, 답을 변경해야 하는 두 조건 및 한국어·영어를 따로 센다. 이 대조는 구조화된 표의 후보 위치를 사용할 수 있는 숫자 답 경로다. [실행기](../scripts/diag_p077_grounded_value_readout.py)

기존 헤드는 먼 표의 값을 바꾼 조건에서 16/64쌍이고 질문을 바꾼 조건에서 0/64쌍이었다. 질문이 바뀌어도 선택 위치를 한 번도 바꾸지 않았다. 동일 본체를 동결하고 기존 작성 교과의 긴 문맥에서 보이는 네 값 위치와 실제 질문 끝 특징으로 값 위치 헤드만 192갱신한다. 원래 별도 시험의 두 장문 본문과 두 질문 조작을 그대로 유지한다. 목표 위치가 답 이전의 인과 상태에서 계산되는지와 새 헤드의 실제 값 선택 및 두 답 정확도를 함께 검증한다. 헤드만 학습한 실행에서 먼 질문 변경을 두 본문 유형 각각 5/64와 4/64쌍 회복했고, 모두 영어였다. 동일 시작점·자료·학습과 헤드 갱신을 유지하며 마지막 물리 층의 Q와 O 사영에만 낮은 학습률을 추가한 한 팔을 대조한다. 실제 기울기와 전체 변경 이름을 확인한다. 같은 먼 두 조건과 한영, 기존 단문 자유 답의 정답·정상 종료 보존을 함께 확인한다. [마지막 어텐션 사영 옵션](../scripts/train_p077_grounded_value_readout.py)

### 외부 저장 KV의 구간 읽기와 실제 근거 활용을 대조한다

첫 실사용 기본값은 입력 896·출력 128·전체 1,024다. 별도 확장 연구는 같은 모델에서 입력과 근거 거리, 출력 상한을 한 축씩 바꾼다. 기존 4,096 대조는 32MB 안에 들어왔지만 근접·원거리 모두 0/4였다. 같은 4,096 원문의 올바른 표를 질문 가까이 다시 제시하면 4/4가 복구됐으며, 표 제목을 직접 적지 않은 표현에서는 자동 선택 실패가 남았다. [4,096 실측](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-context4096-full-cache-result) · [근거 선택과 실제 답](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-evidence-window-result)

| 방식 | 기대 효과 | 확인할 비용 |
|---|---|---|
| 일정 폭의 파일 읽기와 기존 온라인 합산 | KV 값과 전체 인과 가시성을 보존한 채 프로세스 안의 작업 배열을 고정한다. 동일 KV 상주 경로와의 산술·생성 대조로 쓴다. | 저장량과 페이지 캐시는 문맥에 따라 늘며, 과거 전량을 다시 읽는 비용이 있다. 첫 토큰 및 지속 생성 시간을 각각 측정한다. |
| K/V 축을 나눈 정밀도 선택 | 최근 블록을 높은 정밀도로 두고 공유 KV 그룹마다 과거 K의 채널과 V의 행을 별도로 압축한다. | KV 저장량과 복원 시간, 실제 답·종료 변화가 양자화 수준에 따라 달라진다. |
| 여러 근거 구간을 선택해 짧게 다시 제시 | 원래 자리의 근거를 질문 가까이 읽힐 수 있으며 활성 문맥의 크기를 고정한다. | 표 이름이 없는 질문, 같은 이름의 다른 값, 두 구간을 함께 써야 하는 질문에서 선택 실패를 직접 센다. |

구간 읽기의 온라인 합산은 기존 P077 커널의 수식을 재사용한다. 파일에 KV를 두는 방식은 FlexGen의 외부 저장과 아이디어를 공유하며, TinyLM에서는 공유 KV 소유자별로 고정 폭을 읽고 실제 x86 단일 요청에서 RSS·페이지 캐시·읽기량·지연을 각각 검증한다. 압축은 KIVI의 K 채널·V 토큰 분리부터 비교한다. DuoAttention에서처럼 일부 헤드만 전체 이력을 두는 방안은 공유 KV 그룹과 둘째 방문의 근거 사용을 다 읽은 뒤 검토한다. [FlashAttention](https://proceedings.neurips.cc/paper_files/paper/2022/hash/67d57c32e20fd0a7a302cb81d36e40d5-Abstract-Conference.html) · [FlexGen](https://proceedings.mlr.press/v202/sheng23a.html) · [KIVI](https://arxiv.org/abs/2402.02750) · [DuoAttention](https://arxiv.org/abs/2410.10819)

1. **산술 검증 완료.** 1,023~8,192행의 같은 합성 FP16 KV를 64행씩 임시 파일에서 읽었다. 읽기 블록 최대는 16KiB였고 FP64 참조 대비 최대 절대 오차는 1.36×10⁻¹⁶ 미만이었다. 장치 속도와 전체 RSS는 같은 x86 모델을 연결한 다음 단계에서 잰다. [CPU 결과](../handoff/audit/P077_EXACT_BLOCK_KV_FILE_CPU_20261124.json)
2. **모델·자원 대조 대기.** 입력만 896→1,792, 출력만 128→256, 둘을 합친 2,048의 세 대조를 준비한다. 2,048에서 같은 모델의 답과 전체 RSS가 기본 조건의 허용 범위에 들면 4,096으로 옮긴다. 각 길이에서 전체 KV와 블록 읽기의 짝을 맞추고 짧은 원답, 근접·중간·먼 근거, 값 교환, 다중 근거, 정상 종료를 각각 평가한다. 장문 성공은 길이 상한 도달이나 단일 숫자 검색에 그치지 않는다. [RULER](https://arxiv.org/abs/2404.06654)

**실제 요청의 백엔드 대조.** 기존 x86 G4·Chat32와 64행 온라인 어텐션을 고정한다. 메모리에 보관하는 기존 전체 INT8 KV와, 같은 INT8 복원값을 FP16으로 임시 파일에 저장해 헤드별 최대 64행씩 불러오는 방식을 비교한다. 기존 2,041토큰의 한영 각 한 요청과 같은 모델에서 4,086토큰의 원거리 한영 각 한 요청을 쓴다. 원답·정답·종료는 같은 입력으로 다시 대조하고, 속도와 RSS는 각 요청의 두 경로를 교차 순서로 측정한다. 최대 프로세스 RSS, 첫 토큰, 전체 지연, 파일의 실제 할당과 누적 읽기·쓰기를 기록한다. 전체 파일은 요청 종료로 반환되는 임시 저장이며, 운영 기본 문맥에 반영할지는 실측 뒤 결정한다. [격리 측정기](../scripts/diag_p077_file_grouped_cache.py) · [입력과 소스 봉인](../handoff/audit/P077_FILE_GROUPED_CACHE_20261124.json)

### 2026-11-25 P109C v3의 층 공유 구간별 KV 작업 메모리

P109C v3 약 1,770토큰에서 BF16 KV를 보관하더라도 요청 중 RSS는 약 900토큰 FP32보다 높았다. 현재 본체는 어텐션을 계산한 뒤 모든 KV 소유자의 FP32 작업 배열을 유지하고, 순회 끝에서 한꺼번에 BF16으로 바꾼다. 동일 입력에서 소유자 단위로 FP32 작업 배열을 만들고 마지막 소비층을 지나면 반환하는 CPU 경로를 검증한다. 두 경로의 어텐션 사영과 산술은 실제 G4 R2를 그대로 사용한다. |---|---|
| 산술 대조 | 기존 장문 BF16과 후보의 고정 두 요청에서 프리필과 후속 입력을 순서대로 공급한다. 저장된 캐시 값과 최상위 토큰은 같고 마지막 위치 로짓은 절대차 0.00005 이하여야 한다. |

### 2026-11-25 후속 후보 — 짧은 두 구역 비교를 거쳐 8K 질의 형식을 검증한다

§10.63에서 짧게 단일값을 맞힌 일곱 건(한국어 4, 영어 3)의 4K·8K 직접 처리 결과는 모두 오답이었다. 보관 입력을 확인하니 두 길이에서 각각 7건의 답이 원문 어느 숫자와도 일치하지 않았다. 직접 입력의 두 구역·요청 표기·방해 표를 짧은 입력에서도 처리할 수 있는지 먼저 확인한다. [보관 값 대조](../test_result/065_20260831_P077-bf16-KV-는-정확히-절반이고-cla2-재귀가-32MiB-예산에-들어왔다.md#p077-8k-answer-provenance-20261125)

1. **짧은 두 구역 대조.** 기존 일곱 문항의 8K 원문에서 배경 문장만 덜어낸다. 두 표의 순서, 구역 표기, `[request …]`, 원래 질문, ChatML 경계, 본체·토크나이저·INT8 24행 파일 KV와 32토큰 상한을 보존한다. 같은 단일 표의 보관 정답과 비교해 7/7 정확 일치·정상 종료를 확인한다. 여기서 잃는 문항이 있으면 두 구역 구조와 표 선택이 남아 있는 짧은 조건부터 조사한다. 짧은 두 구역 입력이 모두 맞으면, 길이와 무관한 이 구조의 처리 가능성을 확인하고 다음 비교로 넘어간다. CPU 한 코어, 일곱 요청과 봉인 점검에 약 2–5분으로 추산한다.
2. **8K 질의 형식 대조.** 같은 일곱 8K 원문의 근거 위치와 배경을 유지한 채 질문 끝에서 지정 구역과 요구 필드를 강조한다. 질문의 토큰 길이와 생성 설정을 맞춘다. 본체·엔진·원문·채점 봉인이 일치하면 기존 8K 원답을 기준으로 재사용한다.
