# P058 — **eval 과 체크포인트 저장 주기 분리**

> **신설 2026-08-13**(사용자 승인). 출처: 외부 검토문서 A §11~14·§22.
> **성격: 도구 개선.** 아키텍처 실험이 아니다.

---

## 1. 왜

`_do_eval()` 이 **eval 마다** `model.state_dict() + opt.state_dict()` 를 통째로 직렬화한다.
`eval_every 100` 이면 2289스텝 런에서 **23회**다. AdamW 상태를 포함하므로 **학생 모델보다 크다**.

⚠️ **그리고 그 시간이 인쇄 `ms/step` 에 섞인다**(t0 기준 누적 평균).
T-1(`ms_step_median`)이 그것을 분리했으므로 **이제 크기를 잴 수 있다.**

## 2. ✅ 구현 완료 (2026-08-13)

`--save-every N`: N 스텝 경계에서만 저장. **0 = 종전 = 매 eval.**
★**best 와 마지막 스텝은 항상 저장한다** — 안 그러면 판정에 쓸 체크포인트가 없다.

```python
is_best = m["val_loss"] < best_val - 1e-4
due = (save_every <= 0) or (step % save_every == 0) or (step >= steps)
if due or is_best:
    blob = {...}                      # ★직렬화 자체를 건너뛴다(비용의 대부분)
    if due:  torch.save(blob, ck)
    if is_best: torch.save(blob, ck_best)
```

## 3. ★예측

| # | 예측 | 근거 |
|---|---|---|
| **P1** | 벽시계 **−1 ~ −5%** | 23회 × (직렬화 + 디스크). 문서 A 는 "5~20%" 라 했으나 **우리는 SSD 이고 모델이 작다** |
| **P2** | `ms_step_median` 은 **거의 안 변한다** | T-1 이 이미 eval 을 스텝 시간에서 뺐다 → **인쇄 `ms/step` 과 벽시계만 변한다** |
| **P3** | 🚫**품질은 완전히 불변** | 저장 주기는 학습에 영향 없다. best 는 계속 저장된다 |

★**P2 가 이 계획의 검증 방식**이다 — `ms_step_median` 이 변하면 **T-1 구현에 문제**가 있다는 뜻이다.

## 4. 검증 — 별도 런 불필요

**다음 학습 런에서 `--save-every 500` 을 켜고** 벽시계와 `ms_step_median` 을 본다.
⚠️ **세션 드리프트 7.5%** 때문에 **−5% 는 단독으로 검출 불가**다.
→ ★**같은 배치 안에서 250스텝 × 2(off/on)** 로만 잰다.

## 5. 한계·위험

- ⚠️★**`--resume` 이 저장 주기만큼 뒤로 간다.** 크래시 복구 지점이 성겨진다.
  긴 런에서 `--save-every` 를 크게 잡으면 **몇 시간을 잃을 수 있다.** 500 이하 권장.
- ⚠️ **`best` 저장은 그대로**라 best 가 자주 갱신되는 초반에는 이득이 작다.
- 품질 무영향이므로 **결과문서가 아니라 방법론 문서**에 기록한다.
