# P034 — 실행시(런타임) 메모리 실측 + 패킹 추론 경로 — **저장 11.7MB 는 배포 메모리가 아니다**

> 제안 계기: 결과 014(P030 단계 2) 및 사용자 지적 —
> "fp/bf16 GEMM 때문에 실행시 dequant 되어 커지면, 저장만 11.7MB 고 실제 감축이 안 되는 것 아닌가.
> 실행시 차지하는 메모리를 별도 측정해야 하는 것 아닌가."

## 1. 이 지적이 정확한 이유 — 지금 우리가 보고하는 숫자의 정체

`mem_breakdown()` 은 **"삼진 가중치를 1.95(또는 1.25) bpw 로 패킹했다면 몇 MB 인가"** 를 계산한다.
그건 **디스크·전송 크기**이고 **아직 존재하지 않는 패킹 포맷의 이론값**이다.
현재 코드가 실행 중 실제로 들고 있는 것은 다음과 같다.

| 텐서 | 무엇 | dtype | dense 기준 크기 |
|---|---|---|---|
| `TLinear.weight` | latent(고정밀) 가중치 — **체크포인트에 저장되는 실체** | fp32 | 120.9M × 4B = **461MB** |
| `TLinear._wq` | `refresh_quant()` 가 만든 **dequant 된 삼진값** ({-α,0,+α}) | fp32 | **461MB** |
| 활성값·KV | 시퀀스 길이에 비례 | bf16/fp32 | 별도 |

**즉 최악의 경우 두 벌이 동시에 상주한다.** `_wq` 의 값이 삼진이라도 **저장 형식은 fp32** 이므로
메모리 이득이 **0** 이다. 보고서의 30.9MB / 11.7MB 는 **이 상태를 전혀 반영하지 않는다.**

> **★그러므로 "2.64× 감축"은 현재 조건에서 '전송·저장 기준'으로만 참이다.**
> 실행시 상주 메모리 기준으로는 **아직 측정된 적이 없고, 감축이 없을 가능성이 높다.**
> 이건 프로젝트의 1순위 목표("연산이 아니라 메모리 최적화")에 **직접 걸리는 문제**다.

## 1.1 ★저장↓ 이 상주↓ 와 단조인가 — **아니다. 그리고 순위가 역전한다**

두 감축 레버가 **서로 다른 양**을 줄인다.

| 레버 | 무엇을 줄이나 | 저장 MB | **상주 MB** |
|---|---|---|---|
| **MLP 타잉**(g↑) | **유니크 파라미터 수** | 줄어듦 | **줄어듦** |
| **삼진**(16→1.95bpw) | 가중치당 비트 수 | 줄어듦 | **그대로**(fp32 로 들고 있으므로) |
| **3:4 희소**(1.95→1.25bpw) | 가중치당 비트 수 | 줄어듦 | **그대로** |

상주량은 `유니크 파라미터 × 4바이트 × (latent + dequant 사본)` 이라 **bpw 와 무관**하다.
즉 **저장 감축의 일부만 상주로 전이되고, 전이율은 레버마다 다르다** → 단조도 비례도 아니다.

**그래서 순위가 뒤집힌다**(검정 가능한 예측):

| 모델 | 삼진 유니크 파라미터 | 저장 MB | 상주 예측 |
|---|---|---|---|
| `mC_g8_k4` | **54.9M** | 14.9 (더 큼) | **더 작음** |
| `mA_g4s34_k4` | **64.3M** | 11.7 (더 작음) | **더 큼** |

> **`mA` 는 저장이 가장 작은데 상주는 `mC` 보다 크다.** 우리는 REVIEW1 에서 **저장 MB 를
> 기준으로 A 를 승자로 뽑았다**(A vs C 가 노이즈 안이라 "메모리 작은 쪽"을 택했다).
> **상주 기준이었다면 C 를 뽑았어야 한다.** 단계 1 이 이 역전을 확인하면
> **REVIEW1 의 승자 선정 근거를 재검토해야 한다.** — 이게 이 계획의 최대 파급이다.

## 1.2 저장 ≈ 상주 로 만들 수 있는가 — **가능하다. 다만 커널이 필요하다**

원리적으로 가능하고 업계 표준 해법이 있다(llama.cpp 계열 Q-포맷, bitsandbytes 등).
핵심은 **"패킹된 채로 들고 있다가 GEMM 타일 단위로만 즉시 풀기"** 다.
그러려면 세 가지를 동시에 만족해야 한다.

1. **latent `weight` 를 버린다** — 추론엔 역전파가 없으므로 불필요하다. (단계 2)
2. **dequant 전체 사본을 만들지 않는다** — 지금은 `_wq` 가 전체 텐서다. 타일 단위로 풀어
   레지스터/L1 에서 소비하고 버려야 한다. (단계 3~4)
3. **패킹 포맷으로 저장** — int8(단계 3) → 5비트 무낭비 패킹(단계 4).

이걸 다 하면 상주 ≈ 저장 + 활성값 + KV 로 수렴한다. **단 커스텀 커널 없이는 불가능**하고,
`F.linear` 를 쓰는 한 dequant 된 전체 텐서가 필요하다. **그게 이 계획의 본질적 비용이다.**

**중간 목표로도 의미가 크다**: 단계 2(latent 해제)만으로 **상주가 절반**이 된다.
커널 없이, 되돌릴 수 없는 전환 하나로 얻는다.

## 3. 단계 설계 (싼 것 → 비싼 것, 각 단계가 다음의 게이트)

### 단계 0 — **선결**: 결과 014 의 계측 결함 수정 ✅ **완료(2026-07-31)**

**최초 진단이 틀렸었다.** "`load_model()` 이 `refresh_quant()` 를 안 부른다"가 아니라
**`transformer.forward()` 가 매 호출마다 `refresh_quant()` 를 무조건 부른다**가 실제 원인이다
(학습 중에는 latent 가 스텝마다 바뀌므로 **그게 맞다**. 추론에서만 낭비다).
→ `freeze_quant()` 를 만들어 1회만 계산하고 forward 가 건너뛰게 했다.
`clear_quant()` 가 플래그를 되돌린다(학습 재개 시 안전). `evaluate()` 에도 적용해
eval 루프의 `iters` 배 낭비를 제거했다.

### 단계 1 — **실행시 메모리 실측** (Q1, Q2, Q5) ★GPU 불필요, 수십 분

- **측정 방법**: CPU 는 `psutil.Process().memory_info().rss` 를 (a) 로드 전 (b) 로드 후
  (c) `refresh_quant()` 후 (d) forward 중 피크 로 4점 측정.
  GPU 는 `torch.cuda.max_memory_allocated()`(이미 trainer 에 있는 방식 재사용).
- **모델**: `p6d` / `mC_g8_k4` / `mA_g4s34_k4` — 결과 014 와 같은 3종으로 대조 가능하게.
- **★단조성 검정(Q6)**: 저장 기준 순위와 상주 기준 순위를 나란히 인쇄해 **역전 여부를 직접 본다.**
  `mA < mC`(저장) 인데 `mC < mA`(상주) 로 나오면 §1.1 예측이 맞은 것이다.
- **전이율** = `(상주감축−1)/(저장감축−1)` 을 모델별로 계산한다. 100% 면 완전 전이,
  0% 면 저장만 줄고 상주는 그대로. **레버별로 다를 것**이라는 게 §1.1 의 요지다.
- **동시에 `mem_breakdown()` 의 이론값을 같은 표에 인쇄**해 **이론 대 실측의 괴리를 명시**한다.
  이 표 하나가 P034 의 핵심 산출물이다.
- **판정**: 실측 감축비가 이론 감축비(2.64×)에 **얼마나 못 미치는지**를 배수로 기록한다.

> **예상(정직하게)**: 실측 감축은 **타잉분만** 나타날 것이다. 세 모델 모두 fp32 latent 를
> 들고 있고, 타잉 모델만 유니크 가중치가 적다(mC 는 dense 의 45%).
> **즉 "타잉의 메모리 이득은 실행시에도 진짜, 삼진·희소의 이득은 아직 이론값"** 일 가능성이 높다.
> 그 구분이 나오는 것만으로도 이 단계는 값어치를 한다.

**실행**: `run_P034_memory.bat` (→ `scripts/mem_runtime.py`). CPU·GPU 각 1회, 수 분.

### 단계 2 — **`_wq` 단독 상주 모드** (Q2) — 구현 소, 이득 클 가능성

추론에서는 latent `weight` 가 **필요 없다**(역전파가 없으므로). `refresh_quant()` 후
`weight` 를 해제하면 **즉시 절반**이 된다.

- 구현: `to_inference()` 같은 메서드로 `_wq` 만 남기고 `weight` 를 `None` 또는 meta 로 교체.
- **주의**: `_w()` 의 `center_weights` 경로와 `clear_quant()` 가 `weight` 를 다시 요구하므로
  **되돌릴 수 없는 단방향 전환**으로 설계하고 그 사실을 문서화한다.
- 판정: 단계 1 대비 **RSS 가 실제로 절반**이 되는지. 안 되면 다른 곳에 사본이 있다는 뜻.

### 단계 3 — **int8 저장 경로** (Q3) — 패킹 전 중간 단계

삼진값 {-1,0,+1} + 그룹별 스케일 α 로 분해해 **int8 + fp16 스케일**로 들고,
GEMM 직전에만 dequant 한다.

- fp32 대비 **4배** 절감(1.95bpw 이론 대비로는 여전히 4배 손해지만, **실현 가능한 첫 이득**).
- GEMM 마다 dequant 하면 연산이 늘어난다 → **메모리는 줄고 속도는 나빠지는 교환**.
  CLAUDE.md 의 "연산 증가는 감수" 원칙과 정합하지만 **얼마나 나빠지는지 실측이 필요**하다.
- 판정: 메모리 4배 절감 대비 tok/s 하락이 **2배 이내**면 채택 검토.

### 단계 4 — **5비트 패킹 커널** (Q4) — 조건부·최고비용

3:4 희소 삼진은 `C(4,3)·2³ = 32 = 2⁵` 로 **4가중치당 5비트 무낭비 패킹**이 가능하다(P016 설계).
이게 1.25bpw 의 실현이다. **단계 3 이 "메모리는 주는데 너무 느리다"로 끝나면
이 단계가 유일한 출구**이고, 단계 3 이 충분하면 보류할 수도 있다.

- `scripts/bench_fp8_gemm.py` 와 `ternary_kernel.py` 의 기존 자산을 재활용한다.
- **선행 조건**: P030 단계 1(KV 캐시)이 끝나 있어야 커널 이득이 측정 가능한 비중이 된다.

|---|---|
| 실측 감축 ≈ 이론 감축 | **가정이 맞았다.** P034 조기 종결, 보고서 수치 그대로 사용 |
| 실측 감축 ≈ 타잉분만 (예상) | 단계 2 → 3 진행. **보고서에 "저장/실행" 두 수치를 병기하도록 규약 변경** |
| 실측이 이론보다 **더 나쁨** | 어딘가 예상 못 한 사본이 있다. 먼저 그것부터 찾는다 |

## 5. ★문서 규약에 미치는 영향 (단계 1 결과와 무관하게 필요)

지금 `docs/`·`test_result/`·리뷰 전반이 **"배포 메모리 11.7MB"** 를 단일 수치로 쓴다.
그게 **저장 기준**임이 명확해졌으므로 표기를 바꾼다:

- `deploy_mb` → **`packed_mb`(이론·저장)** 로 의미를 명시하고,
- **`runtime_mb`(실측)** 를 새로 도입해 **둘을 항상 병기**한다.
- 소급 정정은 하지 않되, **§요약·리뷰의 "2.64× 감축" 문장에 "저장 기준" 을 붙인다.**

## 7. 한계·리스크

- **RSS 는 할당자(allocator) 영향을 받는다.** PyTorch 는 해제한 메모리를 OS 에 즉시 돌려주지
  않는다 → **RSS 가 실제 사용량보다 클 수 있다.** `torch` 텐서 크기 합산과 **두 방식 병기**가 필요하다.
- **단계 3·4 는 품질을 바꾸지 않아야 한다.** 수치적으로 동일한 값을 다른 형식으로 담는 것이므로
  **val_loss 가 비트단위로 같아야** 하고, 다르면 구현이 틀린 것이다. 이 검증을 반드시 넣는다.
- 단계 4 는 공수가 크다. **단계 1~3 의 실측 없이 착수하지 않는다.**
- 이 계획은 **메모리를 다루지 속도를 다루지 않는다.** 속도는 P030 소관이고,
  단계 3~4 는 오히려 **속도를 희생**할 수 있다.
- **§1.1 의 역전 예측이 맞더라도 REVIEW1 의 품질 결론은 그대로다.** 바뀌는 것은
  "어느 모델이 더 작은가"의 기준이지 val_loss 가 아니다. 두 판단을 섞지 않는다.
- 단계 2 의 `to_inference()` 는 **단방향**이다. 같은 프로세스에서 학습을 재개하려면
  체크포인트를 다시 로드해야 한다. 이걸 문서화하지 않으면 나중에 조용한 버그가 된다.
