# P014E — 고정 회전·삼진 민감도와 직접 패킹의 조건부 검증

> **2026-09-26 현황**: G0 합성 PASS, 사용자 선택 A/B/C 실제 checkpoint Stage1Wa 사용자 CPU 진단 코드·독립 SH 3건 준비. Stage1Wa 모델 실행과 전체 G1b의 CPU decode/RSS·G2 품질은 NOT_RUN; 기본 커널·회전은 변경하지 않는다.

> 제안 계기: 사용자 2026-09-25 [회전·삼진 제안 B안 승인](../proposal/20260925_회전-삼진-민감도와-직접패킹-단계검증-제안서-approved-on-going.md). 기존 [P014D 결과069 §11](../test_result/069_20260902_P014D-디코드-프로파일이-경로이름을-양자화형식으로-넘겨-두-팔-다-죽었다.md)는 native/int8 실제 decode 1.314×/1.231×로 채택선1.50× 미달, [P025B 결과082 §13](../test_result/082_20260913_P025B-import-실패로-2대4-게이트는-미실행이다.md)은 M8192 GPU event 양성에도 동기 wall 음성이다. 두 역사 음성은 유지한다. P014D의 기본 커널 교체가 아니라 새 독립 P014E 계열이다.

## 1. 왜 — 순수 커널 수치만으로 배포 이득을 말할 수 없다

고정 Hadamard 회전은 FP 실수에서 선형 함수가 불변이어도 g128 삼진화 *뒤*에는 오차가 달라진다. 또한 768→1024 padding, 온라인 activation 회전, scale, unpack, 독립 예외 tensor가 상주·CPU decode를 잠식할 수 있다. 수학 동치, 실제 가중치 민감도, CPU/GPU wall, 배포 byte를 서로 다른 게이트로 나눠야 한다.

## 2. 질문

| # | 질문 | 왜 중요한가 |
|---|---|---|
| Q1 | 3×256 또는 1024-pad 고정 회전이 FP64/FP32 함수를 보존하고 g128 quant를 안전하게 계산하는가 | 구현 부호·padding 실수 차단 |
| Q2 | 같은 checkpoint에서 quant 오차가 층별로 실제 줄고, 어느 tensor가 오히려 나빠지는가 | 합성 fixture의 품질 외삽 금지 |
| Q3 | pack·온라인 회전·호출 준비를 포함한 CPU p95·GPU 동기 wall과 실제 runtime/RSS에 순이득이 있는가 | 배포 채택에 필요한 분모 |
| Q4 | 소수 고정밀 예외가 byte 대가보다 품질을 충분히 복구하는가 | 전역 FP16 예외·무분별한 용량 증가 차단 |

## 3. 예측 — 양성보다 실패 경로가 많다

FP64 직교 동치와 FP32 작은 반올림 오차는 합성 G0에서 통과할 가능성이 높다. 그러나 1024-pad는 코드·scale의 이론 byte를 33% 늘리고 activation 회전도 호출마다 필요하다. 현재 P014D CPU wall 음성과 P025B 동기 wall 음성이 있으므로 **실제 배포 속도·상주 동시 개선은 미확인이고 실패할 가능성이 높다**. 한 seed·한 층의 quant NRMS 개선을 전체 모델 품질 개선으로 해석하지 않는다.

## 4. 단계 설계 — 각 단계가 다음의 조건

### G0/Stage0W — 독립 무모델 수학·회계 계약 사용자 완료(결과099)

[진단기](../scripts/diag_p014e_rotation_contract.py)는 합성 weight 8×768·activation 4×768에서 fixed seeds 1337/2024/31415, 3×256과 1024-pad, FP64/FP32 총 12행을 검사한다. 정규화 Hadamard의 역변환, `RᵀR=I`로 인한 dot-product 보존, 실제 `TLinear` 기본값 g128·threshold0.7·group α의 독립 forward-only 미러를 분리한다. 사전 문턱은 FP64 최대절대차≤1e-10, FP32 NRMS≤1e-5다. 회전 후 삼진 오차는 **보고만** 하고 합성 오차가 낮다고 채택하지 않는다. 2-bit code+fp32 scale의 이론 byte는 저장 하한의 일부일 뿐 실제 packed/runtime/RSS가 아니다. Codex CPU self-test와 사용자 Stage0W SH 모두 합성 12행 PASS([결과099](../test_result/099_20260925_P014E-회전-동치만-통과하고-배포손익은-미측정.md)). 실제 checkpoint·CPU wall·GPU·full-val은 `NOT_RUN`.

### G1/Stage1W — 기존 P014D/P025B 병목 같은 분모 재계측

G0 사용자 로그 exit0과 같은 checkpoint·입력·dtype을 먼저 고정한다. P014D CPU M1 native/int8/LUT의 decode p50/p95와 unpack, P025B M1/M8192의 PyTorch wall·GPU event·host/pack을 각각 같은 세션에서 대조한다. 역사 결과를 덮지 않고 새 suffix/로그로 보존한다. **CPU wall과 실제 상주에 개선 가능 위치가 없으면 G2는 열지 않는다.** checkpoint 선정·새 모델 로딩·GPU 실행은 사용자 소유이며 이 단계의 SH는 아직 미작성이다.

### G2/Stage2W — 고정 회전·예외 독립 arm

G1에서 가능성이 확인된 정확 한 형상/계보만 대상으로 같은 checkpoint의 무회전, 3×256, 1024-pad를 별도 arm으로 비교한다. 예외 off와 고정밀 예외 on은 각기 다른 독립변수로 나누고 seeds≥3을 사전 고정한다. fp32 원함수, g128 quant 출력, full-val/한·영 과제, 실제 packed/runtime/RSS·KV·CPU p95를 함께 기록한다. 다른 pool/tokenizer/초기화는 `DESCRIPTIVE_ONLY`. **조건부 단계이며 구현·런처·모델 실행은 `NOT_RUN`**이다.

### G3/Stage3W — 양성 후에만 학습형 회전 또는 직접 packed 커널

G2 품질 비퇴행과 배포 wall·상주 순이득이 재현되면 learnable rotation, softened threshold, packed 직접 커널 중 **하나씩** 별도 suffix로 계획/승인한다. 기본 TLinear 경로와 P014D/P025B 음성 판정은 자동 변경하지 않는다. GPU 학습 예산·tag·pool·판정자는 그때 `exp-preflight`를 다시 수행한다.

## 5. 판정 기준

| 결과 | 판정 |

기존 계열별 품질 판정자와 표준 조건은 [기준표](../docs/EXPERIMENT_BASELINES.md)와 `scripts/_rulers.py`를 실행 전 다시 읽는다. G0는 학습 0·tag 0이어서 토큰·2배 pool·registry 충돌 항목이 해당 없고, 보호 `runs/` 전체 조회는 하지 않았다. G1/G2는 실제 checkpoint·재현 조건이 고정되기 전 preflight `NOT_RUN`이다. 이 점검은 알려진 설계 실수만 걸러낸 것이고, 실제로 그런지는 돌려봐야 압니다.

## 10. 2026-09-26 Stage1Wa — 사용자 선택 A/B/C 세 계보 실제 가중치

사용자는 A/B/C 세 체크포인트를 모두 분석하는 안을 선택했다. 세 가지 편성법은 (1) 한 SH로 묶으면 한 모델 실패가 나머지를 가리고, (2) 한 모델 후 조건부 확대는 세 계보 회수가 늦고, (3) **공통 CPU fixture 뒤 각 모델을 독립 SH로 실행**하면 실패 격리와 같은 수치 계약이 함께 가능하다. 3안을 권장·준비했다. 모델 **안에서만** 무회전/3×256/1024-pad를 paired로 대조하며, A/B/C **사이**는 dense/tied·부모·seed·재귀 방문이 다르므로 DESCRIPTIVE_ONLY다.
