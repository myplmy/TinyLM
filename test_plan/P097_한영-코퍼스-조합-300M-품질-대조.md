## 1. 왜 — 현재 문제를 구조와 데이터로 분리한다

현 `ko-en`은 한국어 Wikipedia와 영어 FineWeb-Edu를 문서 단위 0.5/0.5로 추첨한다. 실제
1.2B cache는 한국어 소스 고갈 때문에 토큰 비율 25/75, val 한국어 0%까지 움직였다. 동시에
사전학습 base model은 SFT가 없어 질문응답·대화 지시이행을 원래 보장하지 않는다.

따라서 이 계획은 “대화가 되는가”를 직접 성공 기준으로 삼지 않는다. source/tokenizer bundle을
바꿨을 때 한국어·영어 continuation, 주제 관련성, gold-margin/정확도가 개선되는지 먼저 잰다.
대화형 SFT는 이 비교의 승자와 별도 계획에서 다룬다.

후보 근거:

- [FineWeb2](https://huggingface.co/datasets/HuggingFaceFW/fineweb-2)는 언어별 dedup/filter를
  적용한 ODC-By multilingual corpus이며 한국어 config는 `kor_Hang`이다.
- [Korean Webtext Edu](https://huggingface.co/datasets/eliceai/korean-webtext-edu)는 교육성
  score 기반 한국어 subset이지만 기존 TinyLM에서 SEO spam이 실측돼 `--doc-filter`가 필수다.
- [MADLAD-400](https://huggingface.co/datasets/allenai/MADLAD-400)는 document-level audited
  multilingual corpus이고 `ko`/`en` clean split을 제공하지만 카드도 잔여 noise를 경고한다.

## 2. 질문

| # | 질문 | 왜 중요한가 |
|---|---|---|
| Q1 | 실제 token 50:50·source-stratified val이 언어 구성 drift를 없애는가 | dataset 효과와 loader 효과를 분리 |
| Q2 | FineWeb2-ko, Korean-Webtext-Edu, MADLAD-ko 중 한국어 벤치·prompt 관련성이 가장 나은가 | 한국어 Wikipedia의 좁은 문체 대체 가능성 |
| Q3 | 한국어 이득이 영어 ARC/HellaSwag와 공통 bpb를 악화시키는가 | 한 언어 개선을 전체 개선으로 오독하지 않음 |
| Q4 | source bundle마다 새 tokenizer를 학습했을 때 결과가 재현 가능한가 | val_loss 직접비교 금지와 배포 tokenizer 비용 확인 |

## 3. ★예측 — 정직하게

- FineWeb2-ko는 주제 폭과 한국어 continuation을 개선할 가능성이 가장 크지만 일반 웹
  boilerplate·유해 문서가 남아 정성 관련성이 오히려 나빠질 수 있다.
- edu-v2는 국소 문장과 설명체가 좋아질 가능성이 있지만 기존 SEO signature가 다시 발화할
  가능성이 있다. 그래서 filter 후에도 drop 수와 문서 길이 분포를 기록한다.
- MADLAD는 source diversity 대조로 유용하지만 clean도 noise-free가 아니며 교육성에서는
  FineWeb 계열보다 뒤질 가능성이 있다.
- 어느 팔도 SFT가 아니므로 제대로 된 다회전 대화가 생길 가능성은 낮다. 데이터 recipe가
  continuation을 고쳐도 “chat 해결”로 부르지 않는다.

## 4. 단계 설계

### Stage0 — recipe·HF 경로 계약

- `ko-en-control-v2`: 현재 source를 실제 token 50:50으로 다시 구성
- `ko-en-fw2`: FineWeb2 `kor_Hang` + FineWeb-Edu
- `ko-en-edu-v2`: Korean Webtext Edu(`--doc-filter`) + FineWeb-Edu
- `ko-en-madlad`: MADLAD clean `ko` + clean `en`

모두 기존 이름을 수정하지 않고 새 cache/tokenizer namespace를 쓴다. `tinylm` import가
`HF_HOME`, `HF_HUB_CACHE`, `HF_DATASETS_CACHE`를 `/home/uranus/tinyLM/HF` 아래로 강제하며
launcher가 다운로드 전에 `scripts/check_hf_runtime.py`를 실행한다.

### Stage1 — 600M pool 생성·300M 학습

| 팔 | data | 바뀌는 축 | 학습 조건 |
|---|---|---|---|
| C | `ko-en-control-v2` | 새 exact-token/stratified-val pipeline | 아래 공통 조건 |
| A | `ko-en-fw2` | 한국어 source를 FineWeb2로 | 아래 공통 조건 |
| B | `ko-en-edu-v2` | 한국어 edu source + spam filter | 아래 공통 조건 |
| D | `ko-en-madlad` | 한·영 source를 MADLAD clean으로 | 아래 공통 조건 |

공통 조건: `m100s10`, dense, CLA2, Muon RMS4×4, matrix WD 기본 0, KD off, WSD 0.60,
`2289×8×16×1024=300,023,808` draw tokens, nominal pool 600M, seed 1337, `--no-ckpt`.

### Stage2 — 공통 과제·정성 panel

- 한국어: KoBEST COPA/HellaSwag, KLUE YNAT/NLI의 accuracy와 gold margin
- 영어: ARC-Easy full/HellaSwag의 accuracy와 gold margin
- 공통 byte 원문 bpb는 같은 원문에서만 비교
- `scripts/interactive_infer.py`의 고정 한국어·영어 continuation prompt와 `:val`

각 모델 tokenizer가 다르므로 **자기 val_loss·ppl을 팔 사이 순위로 쓰지 않는다.** 같은 문항의
정답 선택·margin과 공통 byte-level bpb만 비교한다.

### Stage3 — 조건부 재현

Stage2에서 한 recipe가 한국어 두 과제 이상에서 같은 방향이며 영어 과락 없이 최소 3pp 또는
family-bootstrap CI 하한 우세를 보일 때만 seed 2024 한 팔을 연다. 아니면 전 recipe를
`DESCRIPTIVE_ONLY`로 보존하고 기본 데이터셋을 바꾸지 않는다.

**Stage2Wb 판정:** 조건을 만족한 팔이 없어 원래 seed 2024 복제는 닫는다.
FineWeb2의 YNAT 강점과 control의 공통 bpb 강점을 섞는 후속은 단순 seed 복제가
아닌 **새 recipe 구성 실험**이므로 별도 단계·독립변수·tokenizer 계약을 먼저 고정한다.

### Stage3R~4 — 승격이 아닌 **교환 재현성** 패널

FineWeb2의 YNAT +23.6pp는 한 seed에서 문항 family CI가 0을 멀리 벗어났지만
학습 seed 분산은 포함하지 않았다. 반면 control은 common-bpb에서 0.0062 앞선다.
이 패널은 **어느 recipe도 기본으로 승격하지 않은 채**, control/FineWeb2 두 교환이
seed2024/31415에서도 유지되는지만 재다.

- 학습: 두 recipe×추가 seed2 = 4팔, 모두 300M.
- 평가: YNAT/NLI/ARC/HellaSwag/common-bpb의 3-seed panel.
- 판정: YNAT 및 bpb 교환의 부호가 세 seed에서 유지되어도 기본 교체는 아니며,
  혼합 recipe 실험을 설계할 근거로만 쓴다.
