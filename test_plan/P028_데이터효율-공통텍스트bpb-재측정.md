# P028 — 데이터효율 재측정: 공통 원문 bpb + 캐시 진단 (P012 후속)

근거: 결과 [009](../test_result/009_20260730115100_P012-큐레이션한국어-데이터효율.md) 에서 P012 가
**측정설계 결함으로 판정 불가**로 끝났다. 이 계획은 그 두 결함을 제거하는 것만을 목표로 한다.
데이터셋: `eliceai/korean-webtext-edu`, `wikimedia/wikipedia`(20231101.ko),
`HuggingFaceFW/fineweb-edu`.

## 왜 (결함 재확인)

1. **bpb 는 코퍼스 불변이 아니다.** 현재 bpb 는 각 캐시의 **자기 val.bin** 에 대해 계산된다.
   두 데이터셋의 val 텍스트가 다르므로 "데이터효율 차이"와 "평가셋 난이도 차이"가 섞인다.
   토크나이저도 데이터셋별로 따로 학습되므로 val.bin 교차 투입은 원천적으로 불가.
2. **ko-edu-en 캐시가 의심스럽다.** dense 가 train 3.03 / val 6.17 (**+3.14 nats**) 로 끝났다.
   같은 코드의 ko-en 은 이런 괴리가 없다. 300M 토큰·132M 삼진 파라미터에서 정상 과적합이 아니다.

**결함 1을 고치기 전에 데이터셋 비교 실험을 더 돌리는 것은 GPU 낭비다.**

## 단계 0 — 캐시 진단 (GPU 불필요, 수 분) — ✅ **구현 완료**

`scripts/diag_cache.py` + `run_P028_diag.bat`(작성 완료). 학습 없이 캐시만 읽는다.
**ko-en 을 정상 대조군으로 함께 돌린다** — ko-edu-en 에서만 [!] 가 붙는 항목이 원인 후보다.
합성 캐시(중복·분포이동 주입)로 검출 로직을 검증했다.

| 검사 | 방법 | 무엇을 잡나 |
|---|---|---|
| 문서 중복률 | `train.bin` 을 eos 로 분할, 각 문서 **앞 256토큰** blake2b 해시 → 중복 비율 | train 쪽 near-duplicate (가설 1) |

**판정**: 중복률이 ko-en 대비 유의하게 높거나 val 구간의 JS divergence 가 다른 구간보다 크면
**ko-edu-en 캐시 폐기·재생성**(문서 해시 dedup + val 을 무작위 추출로 변경).

## 단계 0.5 — ★인과 확인 (신설 2026-07-30, GPU 거의 불필요)

단계 0 은 **통계**를 줬을 뿐 인과가 아니다. 그리고 정직하게 보면 **크기가 안 맞는다**:
관측된 괴리는 **3.14 nats**(train ppl 20.7 → val ppl 478, **23배**)인데,
유니그램 JS 0.057 과 한글비율 +6.3pp, 중복 5.69% 를 다 합쳐도 이 규모가 자연스럽게 나오지 않는다.
**뭔가 더 있을 가능성을 배제하지 못한다.**

### 결정적이면서 값싼 테스트: **train 의 앞부분 vs 뒷부분**

핵심 착상 — **둘 다 모델이 학습한 구간**을 비교하면 "본 적 없음(generalization)" 변수가 제거되고
**"그 구간이 원래 어려운가"만 남는다.**

```
train.bin 앞 1.5M 토큰   (구간 1/10 영역, 학습함)
train.bin 뒤 1.5M 토큰   (구간 10/10 영역, 학습함, val 바로 앞)
val.bin    1.5M 토큰     (학습 안 함)
```

| 관측 | 해석 |
|---|---|
| 앞 ≈ 뒤 ≪ val | 순수하게 **"본 적 없음"** 때문 → 중복·암기(H1)가 주범 |
| 앞 ≪ 뒤 ≈ val | **꼬리 구간이 원래 어렵다** → 분포이동(H2) 확정. val 은 그 꼬리의 연장일 뿐 |
| 앞 ≈ 뒤 ≈ val | 캐시 통계로 설명 안 됨 → 학습설정·토크나이저 등 다른 원인 |

ko-en 을 같은 방식으로 재면 **정상 코퍼스의 기준선**이 나온다(ko-en 은 val−train ≈ 0 이었다).

### 구현
`scripts/eval_slices.py` 신설(약 60줄, eval 전용 · 학습 없음 · 수 분):
체크포인트 + 캐시를 받아 **임의 오프셋 구간**의 teacher-forcing 손실을 계산.
`--slices head,tail,val` 로 위 세 구간을 한 번에.

### 추가로 볼 것 (단계 0 도구의 사각지대)
- **val 문서 길이 분포** — `diag_cache.py` 는 train 만 출력한다. ko-edu-en 최대 문서가
  **879,817 토큰**(train 전체의 0.29%)이었으므로, **val 안에 거대 문서가 있으면 그것 하나가
  val 손실을 지배**할 수 있다. val 555문서/1.5M토큰(평균 2,703)이라 가능성이 있다.
- **문서별 손실 상위 10개** — 한두 개의 병리적 문서(표·코드·base64 등)가 평균을 끌어올리는지.
  이게 원인이면 데이터 자체가 아니라 **필터링** 문제다.

## 단계 1 — 공통 원문 bpb 구현 (핵심)

`eval --bpb-text <path>` 를 추가한다.

```
python run100m.py eval --tag <TAG> --data <DATA> --tokens <N> --bpb-text data_cache/common_eval.txt
```

동작:
1. 공통 **원문 텍스트 파일**(UTF-8)을 읽는다. 총 바이트 `B` 를 센다.
2. **그 모델의 토크나이저**(`tok-{data}-32768.json`)로 인코딩 → 토큰 `T`.
3. 모델로 teacher-forcing NLL 합 `L_nats` 를 계산.
4. `bpb = L_nats / ln2 / B`.

이러면 분모가 **같은 바이트**이므로 토크나이저·데이터셋이 달라도 비교가 성립한다.
(토크나이저가 좋으면 `T` 가 줄어 토큰당 손실은 커지지만 바이트당은 정직하게 나온다 — 이게 요점.)

**공통 eval 셋 요건**(중요 — 여기서 실수하면 다시 무의미해진다):
- **두 학습 데이터 어느 쪽에도 치우치지 않아야** 한다. ko-en(위키)로 만들면 위키 모델이 유리하고
  ko-edu-en(웹텍스트)로 만들면 그쪽이 유리하다.
- 제안: **제3 출처**에서 한/영 각 ~1MB. 예 = `HAERAE-HUB/KMMLU` 본문 · `klue` 문서 ·
  영문은 `Salesforce/wikitext`(103-raw) test split. 최종 선택은 착수 시 확정하고 HF id 를 기록한다.
- 두 학습 코퍼스와의 **중복 검사 필수**(단계 0 의 해시 재사용).
- 파일로 고정 저장(`data_cache/common_eval.txt`)하고 **해시를 계획서에 적어** 이후 모든 데이터
  실험이 같은 셋을 쓰게 한다.

# 부록 A — ko-en 결함을 어떻게 처리할 것인가 (2026-07-30 검토)

결과 011 에서 **ko-en 에도** val→train 누설 1.8% · 스트림 비정상성(한글비율 40.7%→23.0%) ·
val JS 1.26× 가 확인됐다. 선택지는 넷이다.

| 안 | 내용 | 비용 | 부작용 |
|---|---|---|---|
| **A. 방치** | 아무것도 안 한다 | 0 | 절대값이 낙관적인 채로 남는다 |
| **B. 전면 재생성** | `prepare()` 수정 + 모든 캐시 재생성 + **모든 기준선 재학습** | **수십 시간** | 기존 결과 001~012 와 **단절** |
| **C. 독립 eval 셋 추가** | 단계 1(공통 원문 bpb)을 도입하고 **두 지표 병기** | **낮음** | 없음 — 기존 이력 전부 유효 |
| **D. 신규 데이터셋만 수정** | `prepare()` 는 고치되 기존 캐시는 그대로. 버전 표기 | 낮음 | 데이터셋별 val 규칙이 달라짐(기록 필수) |

## 권고: **C 지금 → D 다음 데이터셋부터 → B 는 하지 않는다**

**C 를 먼저 하는 이유**: 공통 원문 eval 셋은 **내부 val.bin 을 아예 우회한다.**
제3 출처 held-out 텍스트로 재면 누설·분포이동·중복이 **그 지표에는 원천적으로 영향을 못 준다.**
즉 **캐시를 재생성하지 않고도 정직한 절대값을 얻는다** — 이게 단계 1 의 숨은 가치다.

**B 를 하지 않는 이유**: 결과 011 이 확인했듯 ko-en 의 결함은 **모든 런에 공통 오프셋**으로
들어간다(같은 val.bin·같은 val 시드 99). 따라서 **아키텍처 비교라는 이 프로젝트의 목적에는
영향이 없다.** 수십 시간을 써서 얻는 것은 "절대값의 정직성"뿐인데, 그건 C 가 훨씬 싸게 준다.

**D 의 조건**: `prepare()` 를 고치는 순간 **새 val 과 옛 val 은 비교 불가**가 된다.
반드시 캐시 이름에 버전을 넣고(`ko-en-v2_600000000`) 기준표 §2 레지스트리를 분리한다.

## 부록 B — "더 좋은 한국어 데이터가 필요한가?" / "SFT 손실 마스킹이 필요한가?"

### B-1. 더 좋은 한국어 데이터
**지금은 아니다 — 이유는 두 가지.**
1. **측정이 고장난 상태에서 데이터를 바꾸면 무엇이 좋아졌는지 알 수 없다.** 단계 1 이 먼저다.
2. **이 프로젝트의 목적은 아키텍처(메모리)다.** val CE 는 아키텍처 A vs B 의 **비교 지표**로 쓰이고,
   데이터 품질은 **양쪽에 똑같이** 작용해 상쇄된다. 데이터를 바꿔도 타잉 격차·희소 비용은
   거의 그대로일 것이다(결과 009 에서 ko-edu-en 의 tied+KD 격차도 정상적으로 측정됐다).
   → **데이터는 최종 제품 품질의 문제이지 지금 결정의 병목이 아니다.**

단, 결과 011 이 드러낸 **ko-en 의 스트림 비정상성**(한글 40.7%→23.0%)은 별개로 기록해 둘 값어치가
있다. `_stream()` 이 **문서 개수** 기준 0.5/0.5 로 섞는데 소스별 문서 길이가 다르면
**토큰 기준 비율이 흐른다.** 데이터를 손댈 때가 오면 **토큰 기준 혼합**으로 바꾸는 것이 첫 수정이다.

### B-2. SFT 손실 마스킹
**해당 없음.** SFT 마스킹은 `prompt` 토큰의 손실을 가려 `response` 에만 학습시키는 기법으로,
**instruction 데이터의 구조를 전제**한다. 우리는 **raw text 사전학습**이라 prompt/response 구분이
없고, 가릴 대상 자체가 존재하지 않는다. 3.14 nats 괴리와도 무관하다.

**다만 사전학습에도 "손실 마스킹"이라 부를 만한 인접 이슈는 있다** — 혼동하지 않도록 정리:

| 이슈 | 우리 상태 | 판단 |
|---|---|---|
| **문서 경계 넘는 어텐션** | Loader 가 문서를 이어붙인 스트림에서 무작위 크롭 → 한 크롭이 **여러 문서에 걸치고 서로 어텐션한다** | 표준 관행이며 대형 모델도 대부분 이렇게 한다. 문서 경계 마스킹은 손실을 소폭 낮추지만 **구현·속도 비용**이 있고 **모든 런에 공통**이라 비교에 영향 없음 → **보류** |
| **크롭 앞부분 토큰** | 문맥이 거의 없는 첫 토큰들도 손실에 포함 | 절대값을 올리지만 **모든 런에 공통** → 무시 |
| **패딩 마스킹** | 패딩이 없다(sequence packing) | 해당 없음 |

즉 **B-2 는 "필요 없다"가 답**이고, 3.14 nats 의 원인 후보에서 제외한다.

### B-3. "P028 단계 1이 해결하는가?"
**절반만.** 두 문제를 구분해야 한다.

| 문제 | 단계 1 이 해결? |
|---|---|
| **데이터셋 간 비교 불가**(토크나이저·val 셋 상이) | ✅ **해결** — 이게 단계 1 의 설계 목적 |
| **절대값의 정직성**(누설·분포이동) | ✅ **우회** — 외부 held-out 이라 내부 val 결함이 영향 없음 |
| **ko-edu-en 캐시 자체의 오염**(중복 5.69%) | ❌ **미해결** — 그 데이터로 학습하면 여전히 중복 노출. 재생성 필요 |
| **`prepare()` 의 말미 val 분할** | ❌ **미해결** — 코드 수정 별건 |

→ **단계 1 은 "측정"을 고치고, 캐시 재생성은 "데이터"를 고친다.** 둘 다 필요하지만
**단계 1 이 훨씬 싸고 먼저다.**
