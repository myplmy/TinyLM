# P083 — 구동기 설계 초기실험 및 플랫폼 검증 : TinyLM 배포 의미론을 고정하고 GGUF/llama.cpp와 최소 런타임의 정합성·메모리·호환성을 단계적으로 검증한다

> **상태:** 계획만 작성됨 · 코드 미구현 · 실험 미실행 · 배치 미등록
>
> 이 문서 작성 시에는 저장소 조회만 수행했다. 이 계획의 존재는 TinyLM GGUF, llama.cpp, LM Studio, 40MB 상주 중 어느 것도 통과했다는 뜻이 아니다. 실제 구현·빌드·모델 실행·외부 저장소 반영은 별도 승인 후 수행한다.

## 제안 트리거

P079에서 40MiB 산술 후보가 선별되었고, 기존 40MB 배포 조사에서 Python/PyTorch 전체 프로세스는 목표를 만족할 수 없음이 확인되었다. 장기적으로 LM Studio와 llama.cpp 같은 공개 플랫폼에서 실행하려면 독자 최소 런타임만 설계해서는 안 된다. 모델 의미론, exporter, GGUF, llama.cpp graph, 최소 reference runtime, 실제 peak memory, LM Studio downstream 호환성을 한 번에 섞지 않고 순서대로 검증할 계획이 필요해 P083을 제안한다.

P083은 P014D의 LUT kernel 속도·packing 연구를 대체하지 않는다. P014D가 “kernel이 빠른가”를 담당한다면, P083은 “같은 모델을 내보냈는가, 그래프와 KV가 맞는가, stock 공개 런타임에서 실행되는가, 프로세스 전체 메모리가 목표를 만족하는가”를 담당한다.

## 1. 왜 이 실험이 필요한가

### 1.1 현재 알려진 사실

- Python/PyTorch idle 프로세스부터 약 386~388MB RSS여서 40MB 제품 구동기가 될 수 없다.
- P079의 `d12_cla2_r20` 30.7MiB, `d16_cla2_r20` 38.5MiB는 1.600 bpw 본체·int8 embedding·bf16 KV를 가정한 텐서+KV 산술치다.
- 현재 LUT op는 PyTorch reference이며 큰 gather/scratch가 생길 수 있고, 기존 fused 경로는 unpack-cache 기준보다 약 6.5~8.4배 느렸다.
- 현재 모델은 factorized/tied embedding, QK norm, GQA, CLA, recurrence와 pass별 KV를 포함해 표준 decoder layer의 단순 복사가 아니다.
- 저장소에는 GGUF exporter, TinyLM llama.cpp architecture, 독립 네이티브 runtime, E2E peak memory 검증 결과가 없다.
- 기존 g256 scale 실험의 common bpb 손실은 약 `+0.0010~+0.0015`여서 llama.cpp stock `TQ1_0`의 256-value ternary block은 유력하지만, 동일 quantizer는 아니다.

### 1.2 풀어야 할 핵심 불확실성

1. PyTorch의 모델 의미론을 독립 구동기와 llama.cpp graph가 정확히 재현하는가?
2. tied/shared weight를 중복 저장하지 않으면서 recurrence visit과 CLA/KV를 표현할 수 있는가?
3. stock `TQ1_0`을 쓰면 새 quant type 없이도 품질과 메모리를 만족하는가?
4. `d12_cla2_r20`이 clean process 전체 기준으로 40MB 또는 40MiB를 통과하는가?
5. llama.cpp 실행 성공이 upstream과 LM Studio의 일반 사용자 호환성까지 이어지는가?
6. 모델이 LLC보다 작을 때 실제 miss와 bandwidth가 감소하는가, 아니면 code/KV/scratch에 의해 계속 축출되는가?

## 3. 사전 예측

### 3.1 성공 예측

1. **FP32 graph:** TinyLM의 연산은 기존 GGML primitive로 표현 가능하므로, architecture-specific schedule과 KV 계획이 정확하면 별도의 새 연산 없이 FP32 정합성을 달성할 가능성이 높다.
2. **TQ1_0 품질:** 기존 g256 손실이 작았으므로 `TQ1_0`도 본체 품질을 크게 해치지 않을 가능성이 높다.
3. **작은 후보:** `d8_g2`와 20~28MiB급 후보는 최소 런타임에서 40MB headroom을 확보할 가능성이 높다.
4. **공개 배포:** stock quant type을 재사용하면 custom quant type보다 upstream 검토·backend 유지 부담이 크게 낮아질 것이다.

### 3.2 실패·부정 예측

1. **d16 경계 실패:** `d16_cla2_r20`은 기존 산술치만 38.5MiB이므로 E2E 40MB는 실패할 가능성이 매우 높다.
2. **llama.cpp 40MB 실패:** `d12_cla2_r20`은 최소 런타임에서는 가능성이 있지만, 일반 llama.cpp 프로세스의 code/graph/tokenizer/scratch까지 포함하면 엄격 40MB를 넘을 수 있다.
3. **TQ1_0 비동일성:** fp16 scale, rounding, embedding/head quant가 기존 g256 probe보다 큰 품질 손실을 만들 수 있다.
4. **KV 오류:** CLA owner와 recurrence pass를 한 축으로 합치거나 동일 KV를 잘못 재사용하면 prefill은 그럴듯해도 incremental decode가 어긋날 수 있다.
5. **backend 편차:** x86 CPU에서 맞아도 Apple Silicon CPU 또는 GPU backend는 느린 fallback이거나 미지원일 수 있다.
6. **LM Studio 지연:** 로컬 patched llama.cpp 성공 후에도 upstream merge와 LM Studio runtime 갱신 전에는 일반 LM Studio 호환이 성립하지 않는다.

### 3.3 반증 가능한 판정 원칙

- FP32 reference가 불일치하면 quantization을 원인으로 돌리지 않는다.
- tensor 합계가 40MB 미만이어도 process peak가 넘으면 40MB 실패다.
- local fork에서만 실행되면 공개 플랫폼 성공이 아니다.
- common/full-val 차이가 저장소의 측정 해상도보다 작으면 “개선”으로 순위를 매기지 않고 동등 범위로 보고한다.

## 4. 실험 설계: 싼 단계에서 비싼 단계로

### 4.0 고정 조건과 대조군

#### 고정할 입력

- 기존 checkpoint는 읽기 전용 입력으로 사용하고 재학습하지 않는다.
- config, tokenizer JSON/vocab/merges, special token id, chat template를 hash로 고정한다.
- 같은 prompt, seed, sampler 설정, context length, thread 수를 route 간 공유한다.
- greedy 정합성 시험은 temperature 0 또는 deterministic greedy로 고정한다.
- 품질 평가 데이터와 기준선은 기존 평가 규약을 사용하고 training 데이터로 재사용하지 않는다.

#### 모델 후보

| 역할 | 우선 후보 | 이유 |
|---|---|---|
| 구조 sanity | `d8_g2` 또는 가장 작은 현존 후보 | 빠른 exporter/graph 오류 탐지, 메모리 headroom 큼 |
| 주 제품 후보 | `d12_cla2_r20` | 30.7MiB 산술치와 현재 32MiB 기준 성능 |
| 40MB 경계 대조 | `d16_cla2_r20` | 38.5MiB 산술치와 더 좋은 full-val, E2E 실패 가능성 검증 |
| 필요 시 기능 대조 | CLA/recurrence가 없는 동일 폭 후보 | CLA·pass 오류를 일반 graph 오류와 분리 |

#### 비교 route

| Route | 표현/구동기 | 목적 |
|---|---|---|
| R0 | 현재 PyTorch FP32/학습 dtype reference | canonical 출력과 layer fixture |
| R1 | scalar native FP32 reference 또는 동등한 최소 oracle | 프레임워크 독립 의미론 검증 |
| R2 | TinyLM FP32/F16 GGUF + llama.cpp CPU | exporter와 graph 검증 |
| R3 | stock `TQ1_0` 본체 + 후보 embedding/head quant + llama.cpp CPU | 공개 배포 후보 |
| R4 | 1.600 bpw compact artifact + 최소 runtime | strict-memory 대조, 필요 시 제품 후보 |

R4의 native optimized LUT kernel 속도는 P014D 결과를 참조한다. P083에서는 우선 scalar/명확한 reference로 정확성을 통과시키고, 성능 최적화가 정합성 기준을 바꾸지 못하게 한다.

### Stage 0 — 배포 의미론과 fixture 동결

#### 코드상 구현해야 할 것

1. **versioned deployment manifest/schema**
   - architecture/config version
   - logical tensor와 physical tensor 목록
   - shared/tied alias와 중복 금지 규칙
   - pre/middle/coda 및 recurrence visit schedule
   - CLA owner와 KV key `(owner, pass)`
   - tensor별 quant type/block/scale dtype
   - tokenizer/chat template id와 hash
2. **tensor inventory 도구**
   - 이름, shape, dtype, strides, logical owner, physical storage id, hash 기록
3. **golden fixture 생성/검증 도구**
   - tokenizer token id
   - embedding, block별 hidden state, final norm, selected logits
   - prefill 및 매 decode step의 KV shape/key와 logits
4. **미지원 config 거부 규칙**
   - 알 수 없는 manifest/version, 잘못된 layer schedule, offset overflow를 묵인하지 않고 실패

#### 필요한 추가 결정

- 공개 architecture 문자열과 metadata key는 외부 파일을 발행하기 전에 안정화한다.
- GGUF와 compact artifact가 같은 manifest를 내장할지, 공통 생성 단계에서 각자 최소 metadata만 가질지 결정한다.
- tied embedding의 물리 저장 tensor를 하나로 할지, backend 제약 때문에 alias metadata를 둘지 결정하되 파일 byte 중복은 검출한다.

#### Gate G0

- 모든 후보에서 logical/physical tensor inventory가 완전하다.
- recurrence visit 수와 CLA owner/KV key가 현재 PyTorch schedule과 exact 일치한다.
- tokenizer/config/tensor hash가 기록된다.
- 미정 항목이 있으면 architecture id를 외부에 발행하지 않는다.

G0 실패 시 exporter 구현으로 진행하지 않는다.

### Stage 1 — FP32/F16 GGUF exporter와 structural round-trip

#### 코드상 구현해야 할 것

1. TinyLM GGUF converter/exporter
2. architecture metadata writer와 tensor-name mapping
3. tokenizer/special token/chat template writer
4. shared tensor를 한 번만 기록하는 physical tensor writer
5. FP32 또는 FP16 reference artifact 출력
6. GGUF reader 기반 structural validator
7. malformed/truncated/unknown-version fixture와 fail-closed test

#### 정확성 검사

- tensor 개수, 이름, shape, dtype, byte offset, alignment를 exact 비교한다.
- FP32 tensor는 byte/hash exact, FP16은 정해진 cast 결과와 exact 비교한다.
- tied/shared weight가 두 개의 payload로 중복 기록되지 않았는지 offset와 physical id로 확인한다.
- tokenizer 전체 vocab, merge, special id를 비교한다.
- row/block 크기가 선택 quant type의 제약을 만족하지 않으면 묵시적 변환 대신 명시적 fallback 목록을 출력한다.

#### Gate G1

- FP32 round-trip mismatch 0개
- 누락/추가 tensor 0개
- shared payload 예상 밖 중복 0개
- tokenizer metadata mismatch 0개
- corrupt/unknown artifact가 정상 모델로 load되는 사례 0개

G1 통과 전에는 quantized GGUF를 품질 후보로 평가하지 않는다.

### Stage 2 — scalar semantic oracle

#### 코드상 구현해야 할 것

- factorized/tied embedding 및 직접 output head
- RMSNorm, QK RMSNorm, RoPE
- GQA attention
- CLA KV owner mapping
- recurrence visit schedule과 pass별 KV
- ternary/dequantized linear의 명확한 scalar reference
- deterministic tokenizer/greedy decode
- layer checkpoint와 selected logits dump

최적화는 이 단계의 목적이 아니다. 읽기 쉬운 계산 순서와 bounds 검사를 우선하며, 큰 weight를 매 token 전체 복원하는 구현은 reference 한정 여부를 명시한다.

#### fixture 세트

- 빈 문자열과 BOS/EOS-only
- 짧은 한국어·영어·숫자·공백 반복
- UTF-8 다중 byte, emoji, punctuation
- context 경계 1/2/127/128/511/512/1023/1024
- CLA owner가 바뀌는 layer와 recurrence pass 경계
- prefill 전체 입력 대 token-by-token 입력

#### 잠정 수치 gate

- tokenizer token id: 100% exact
- FP32 scalar selected tensor/logit: `max_abs <= 1e-4`, normalized RMSE `<= 1e-5`
- golden prompt의 FP32 greedy top-1: 100% 일치
- NaN/Inf: 0개
- prefill과 incremental decode의 같은 위치 logits: 위 FP32 허용치 안에서 일치

연산 순서 차이만으로 FP32 reference끼리 잠정 허용치를 넘는다면 quantized 결과를 보기 전에 원인을 분석하고, 관측 결과를 보지 않은 상태에서 새 허용치를 사전 등록한다. 임계값을 결과에 맞춰 사후 완화하지 않는다.

#### Gate G2

모든 exact 항목과 사전 등록된 FP32 수치 gate를 통과한다. 특히 cache를 끈 전체 재계산과 cache를 켠 incremental decode가 일치해야 한다.

### Stage 3 — llama.cpp FP32 architecture 통합

#### 코드상 구현해야 할 것

llama.cpp의 공식 새 모델 절차에 따라 다음이 필요하다.

1. TinyLM `MODEL_ARCH`, metadata key, tensor key 등록
2. converter/`gguf-py` architecture 등록
3. model parameter loader와 config validation
4. tensor mapping과 shared weight pointer 재사용
5. factorized/tied embedding, QK norm, GQA, RoPE graph
6. recurrence visit graph와 CLA/pass KV allocation
7. tokenizer/chat template 연결
8. `llama-cli`, `llama-server`, model-load test
9. CPU backend의 graph test; GPU backend는 초기 필수 범위에서 제외

#### 수행 절차

1. 가장 작은 후보의 FP32 GGUF를 load한다.
2. 한 token forward에서 embedding부터 selected logits까지 layer checkpoint를 R0/R1과 비교한다.
3. 짧은 prefill, incremental 1 token, 다중 decode 순으로 넓힌다.
4. CLA 없는 후보, CLA 후보, recurrence 후보 순으로 기능을 추가한다.
5. `llama-cli` greedy 출력과 `llama-server`의 동일 요청 출력을 비교한다.
6. 경계 context와 malformed GGUF를 시험한다.

#### Gate G3

- load/config/tensor mapping 오류 0개
- llama.cpp FP32 selected logits `max_abs <= 1e-3`, normalized RMSE `<= 1e-4`
- golden prompt FP32 greedy top-1 100% 일치
- prefill vs incremental 및 CLI vs server의 deterministic 결과 일치
- CLA owner/pass KV fixture 100% 일치
- invalid file/version/config fail-closed

G3 실패 중에는 TQ1_0의 품질·속도를 평가하지 않는다. FP32 graph 오류와 quant 오류를 섞으면 안 된다.

### Stage 4 — stock `TQ1_0` 및 embedding/head 형식 비교

#### 코드상 구현해야 할 것

- tensor별 `TQ1_0` 적용 가능성 검사
- 적용 불가능/부적합 tensor의 명시적 F16, Q8_0 등 fallback 정책
- factorized embedding과 tied output head의 직접 quantized matmul
- quant code/scale round-trip 검사
- 같은 checkpoint에서 F32와 quantized artifact를 함께 생성하는 manifest
- tensor별 byte 수와 전체 포맷 overhead report

#### 비교할 최소 조합

| 조합 | 본체 | embedding/head | 목적 |
|---|---|---|---|
| Q0 | FP32/F16 | FP32/F16 | graph 기준 |
| Q1 | TQ1_0 | F16 | 본체 손실 격리 |
| Q2 | TQ1_0 | Q8_0 또는 지원 int8 | 공개 메모리 후보 |
| Q3 | 현재 1.600 bpw reference | 기존 int8 정책 | strict-memory 대조 |
| Q4 | 필요 시 TQ2_0 | 동일 embedding/head | TQ1 품질/속도 실패 대안 |

#### 평가

- tensor별 dequant reconstruction error와 scale 분포
- common bpb와 full-val bpb
- selected logits max_abs/NRMSE/cosine/top-k agreement
- greedy generation의 최초 divergence 위치
- NaN/Inf, 반복 폭주, EOS 이상, cache on/off divergence
- GGUF file size와 tensor별 byte breakdown

#### 품질 gate

- common bpb quant-only 회귀가 FP32 route 대비 `+0.008` 이내인지 engineering gate로 본다.
- full-val 차이 `0.024 bpb` 미만은 저장소의 실용 해상도 아래로 취급하며, 그 안의 작은 차이로 모델 우열을 주장하지 않는다.
- full-val이 `+0.024 bpb` 이상 악화하면 제품 후보에서 중단하거나 embedding/head 및 scale 정책을 분리 진단한다.
- 모든 필수 prompt에서 NaN/Inf와 비결정적 greedy 결과가 없어야 한다.

common `+0.008`과 full-val `0.024`는 서로 다른 용도의 기준이다. 전자는 기존 quant probe와 연결한 조기 경고선이고, 후자는 전체 모델 품질을 유의미하게 서열화할 때의 실용 해상도다.

#### Gate G4

Q1/Q2가 품질 gate를 통과하면 stock `TQ1_0` 경로를 우선한다. 실패하면 다음 순서로 원인을 분리한다.

1. TQ1 본체만 사용한 Q1
2. embedding quant 추가 영향
3. output head quant 추가 영향
4. fp16 scale/rounding과 기존 g256 reference 차이
5. graph/kernel 누산 차이

이 원인 분리 전에 custom GGML quant type 구현으로 건너뛰지 않는다.

### Stage 5 — 프로세스 전체 메모리·속도·LLC 검증

#### 코드상 구현해야 할 것

- runtime 내부 arena별 예약/실사용/high-water 계측
- weight mmap, KV, activation, scratch, tokenizer, graph의 category report
- clean child process 실행과 peak private/working-set 수집 harness
- TTFT, prefill tok/s, decode tok/s의 warm-up 및 반복 측정
- peak가 발생한 단계(load/prefill/decode)를 표시하는 marker
- 선택적 hardware-counter 수집: LLC load/miss, memory bandwidth

#### 측정 조건

- batch 1
- context `1, 128, 512, 1024`
- decode 길이 `1, 32, 128` 중 가능한 범위
- thread `1, 4`, 필요 시 물리 core 수
- cold load와 warm 반복 분리
- 같은 OS·CPU·전원 정책·runtime commit·compiler flags 기록
- 매 반복을 새 프로세스에서 수행한 peak와 동일 프로세스 warm peak를 모두 기록
- Windows x86-64 CPU를 첫 기준으로 하고 Linux x86-64를 재현 대조로 추가

#### 반드시 분리할 메모리 수치

1. artifact file bytes
2. weight mapped virtual bytes
3. resident mapped pages
4. private dirty/committed bytes
5. process working set/RSS
6. peak working set/RSS
7. runtime arena high-water
8. shared library/code page 포함 여부

#### 40MB 판정

- **Gate M40-SI:** E2E peak `<= 40,000,000 bytes`
- **Gate M40-MiB:** E2E peak `<= 41,943,040 bytes`
- 두 결과를 모두 보고하고 하나를 다른 것으로 표기하지 않는다.
- load 직후만이 아니라 context 1024 prefill과 decode가 포함된 최대치를 사용한다.
- file size나 P079 산술치만으로 통과 판정을 내리지 않는다.

#### 속도와 LLC 판정

속도에는 사전에 제품 최소치를 정해야 한다. 아직 제품 SLA가 없으므로 P083 첫 실행에서는 절대 합격선을 사후에 만들지 않고 다음을 보고한다.

- TTFT, prefill tok/s, decode tok/s의 median과 p95
- scalar reference, llama.cpp TQ1_0, native 1.600 route의 상대 배수
- thread scaling과 cold/warm 차이
- LLC miss per token, miss rate, memory bandwidth

`model bytes < LLC capacity`만으로 “항상 LLC 상주”라 판정하지 않는다. warm 반복에서 working set이 안정되고 LLC miss와 DRAM traffic이 유의하게 줄어드는 경우에만 “LLC 친화적”이라고 표현한다. 다른 core·process 경쟁과 KV 증가 조건도 별도 표기한다.

#### Gate G5

- correctness G4를 유지한 route만 성능 후보가 된다.
- M40-SI/M40-MiB 통과 여부를 route와 후보별로 기록한다.
- scratch/arena의 미계측 영역이 없어야 한다.
- OOM, out-of-bounds, context 증가에 따른 비정상 초선형 메모리 증가가 없어야 한다.
- 속도는 P014D의 optimized kernel 결과와 합쳐 후속 제품 SLA를 결정한다.

### Stage 6 — llama.cpp 공개 플랫폼 범위 확대

#### 순서

1. Windows x86-64 CPU
2. Linux x86-64 CPU
3. Apple Silicon CPU
4. 필요성에 따라 Metal/CUDA/Vulkan
5. `llama-cli`, `llama-server`, OpenAI-compatible endpoint
6. llama.cpp upstream contribution과 CI

#### backend별 평가

- load 지원 여부
- tokenizer exactness
- FP32/quantized logits 허용 오차
- deterministic greedy token
- TTFT/prefill/decode
- fallback kernel 사용 여부
- peak memory와 backend 전용 allocation

초기 PR은 CPU correctness를 목표로 할 수 있다. 그러나 Metal/CUDA/Vulkan을 시험하지 않았으면 지원 표에 `미검증`으로 남긴다. Apple Silicon에서 load되더라도 TQ1/TQ2가 scalar fallback이면 실용 속도 통과로 보지 않는다.

#### Gate G6

- upstream 기준 commit에서 build/test가 통과한다.
- 로컬에만 존재하는 patch가 없어도 공개 artifact를 load할 수 있다.
- backend 지원표가 `통과/실패/미검증`을 구별한다.
- architecture id와 metadata가 upstream review 중 변경되면 공개 전 artifact를 다시 생성한다.

### Stage 7 — LM Studio downstream 검증

이 단계는 G6 이후에만 수행한다. 로컬 patched llama.cpp를 LM Studio 호환으로 포장하지 않는다.

#### 필요한 것

- TinyLM 지원이 포함된 LM Studio selectable llama.cpp runtime 버전
- 호환 GGUF artifact와 hash
- 필요 시 model.yaml과 모델 카드; 이는 기능 구현이 아니라 metadata 단계
- 동일 deterministic prompts와 API fixture

#### 절차

1. LM Studio와 선택 runtime 버전·플랫폼을 기록한다.
2. `lms import` 또는 공식 UI import로 GGUF를 가져온다.
3. 모델 load 시 architecture/tensor/tokenizer 오류가 없는지 확인한다.
4. 동일 prompt에서 greedy generation을 llama.cpp CLI 결과와 비교한다.
5. context 1/128/512/1024에서 prefill/decode를 시험한다.
6. LM Studio local server의 동일 요청과 llama-server를 비교한다.
7. unload/reload, 잘못된 파일, 지원하지 않는 runtime 버전의 오류 메시지를 확인한다.
8. 모든 기능 게이트 뒤에 model.yaml/카탈로그 정보를 검증한다.

#### Gate G7

- 일반 배포 LM Studio와 공식 선택 runtime에서 추가 binary 교체 없이 load/generate 성공
- tokenizer와 deterministic output이 기준 route와 일치
- local server와 UI가 동일 모델을 정상 종료·재로드
- 지원 플랫폼과 runtime 최소 버전이 문서화됨

G7을 통과해야만 “LM Studio 호환”이라고 표기한다.

## 5. 결정 기준

### 5.1 Route 선택표

| 결과 | 결정 |
|---|---|
| R3(TQ1_0)가 G4·G5를 통과 | GGUF/TQ1_0을 공개 배포 기본으로 채택 |
| R3 품질 통과, llama.cpp E2E 40MB 실패, R4 통과 | 공개 호환 GGUF와 strict-memory compact의 이중 artifact 채택 |
| R3 품질 실패, Q1 본체가 원인 | TQ2_0 또는 scale 정책 비교 후 custom quant의 비용/효익 재심사 |
| R3 품질 통과, 특정 backend만 지나치게 느림 | CPU 공개 지원부터 시작하고 해당 backend는 미지원/미검증으로 분리 |
| R2 FP32 graph 실패 | exporter/schedule/KV 수정; quant·성능 단계 중단 |
| R4도 40MB 실패 | 더 작은 후보, context/KV dtype, tokenizer/runtime overhead를 재설계; 40MB 주장 중단 |
| upstream은 통과하나 LM Studio runtime 미포함 | llama.cpp 호환만 표기하고 LM Studio 호환 표기는 보류 |

### 5.2 custom GGML quant type 착수 조건

다음을 모두 만족할 때만 TinyLM 전용 1.600 bpw type을 검토한다.

1. FP32 architecture G3가 통과했다.
2. stock TQ1_0 실패 원인이 graph가 아니라 format의 메모리·품질·속도임이 분리되었다.
3. native 1.600 route가 동일 후보에서 실질 이득을 실측했다.
4. CPU 및 목표 backend별 kernel 유지 비용을 감수할 제품 가치가 있다.
5. upstream 수용 가능성을 사전에 논의했다.

## 6. 실험 시 주의사항과 중단 규칙

### 6.1 즉시 중단 조건

- tensor 수·shape·hash·alias 불일치
- tokenizer token id 불일치
- FP32 layer/logit gate 실패
- prefill과 incremental cache 결과 불일치
- NaN/Inf, out-of-bounds, offset overflow, corrupt-file 정상 load
- tied/shared tensor의 예상 밖 payload 중복
- 결과를 본 뒤 threshold·prompt·후보를 바꾸려는 경우

### 6.2 해석상 금지

- 모델 파일 크기를 process resident memory로 부르지 않는다.
- 40MiB 통과를 40MB 통과로 부르지 않는다.
- patched fork 성공을 upstream/LM Studio 성공으로 부르지 않는다.
- CPU 성공을 GPU/Metal/Vulkan 성공으로 확장하지 않는다.
- 작은 bpb 차이가 0.024 미만일 때 우열을 확정하지 않는다.
- LLC 용량보다 작다는 이유만으로 상시 cache resident라고 단정하지 않는다.
- G3 이전의 quantized generation을 품질 근거로 사용하지 않는다.

### 6.3 재현성 기록

- checkpoint/config/tokenizer/artifact SHA-256
- exporter와 runtime commit
- compiler, flags, target ISA, backend
- OS, CPU, cache 용량, RAM, thread affinity, 전원 정책
- prompt/eval dataset hash
- quant type과 tensor별 fallback
- context, batch, seed, sampler, thread 수
- raw memory/latency/counter log와 요약 생성 버전

캐시된 평가 결과는 model/tokenizer/evaluator/quant/runtime identity가 정확히 일치할 때만 재사용한다. 경로명이나 짧은 모델 별칭만으로 재사용하지 않는다.

## 8. 예상 결과

### 가장 가능성 높은 결과

- FP32 GGUF는 graph 정합성 reference로 성공하지만 40MB 제품 artifact는 아니다.
- stock `TQ1_0`은 본체 품질을 상당 부분 보존해 custom quant 구현을 뒤로 미룰 가능성이 높다.
- `d12_cla2_r20`은 최소 runtime의 40MiB 후보로 남지만, 일반 llama.cpp의 엄격 40MB 통과 여부는 불확실하다.
- `d16_cla2_r20`은 품질 상한 대조로 유용하지만 E2E 40MB는 실패할 가능성이 높다.
- x86 CPU correctness가 가장 먼저 통과하고, Apple Silicon/GPU는 kernel 지원 편차 때문에 별도 최적화가 필요할 수 있다.
- LM Studio 호환은 기술적으로 llama.cpp upstream 지원 이후에 가능하며, merge/runtime 배포 일정이 전체 일정의 가장 큰 외부 변수다.

### 성공 시 얻는 것

- 하나의 체크포인트에서 공개 GGUF와 strict-memory artifact를 재현 생성하는 경로
- PyTorch와 독립적인 모델 의미론 oracle
- 실제 40MB 가능/불가능의 E2E 증거
- llama.cpp/LM Studio 지원 범위와 최소 runtime 버전
- custom quant/backend 최적화에 착수할지 말지의 근거

### 실패해도 얻는 것

- 실패가 exporter, graph, KV, quant, runtime overhead, backend 중 어디에서 생겼는지 분리된 결과
- 더 작은 모델 또는 다른 embedding/KV 정책으로 이동할 정량 근거
- 공개 호환 프로필과 40MB 프로필을 하나의 artifact로 강제할 필요가 없다는 제품 결정 근거

## 11. 한계

1. 본 계획은 기존 P079/P014C 결과를 이용한 설계이며 TQ1_0 GGUF를 실제로 만들지 않았다.
2. llama.cpp와 LM Studio는 지속적으로 변하므로 구현 시작 시 공식 문서, API, runtime 버전을 다시 고정해야 한다.
3. 40MB는 OS별 RSS/working-set 의미가 달라 공통 artifact라도 플랫폼별 결과가 다를 수 있다.
4. P014D optimized kernel 결과가 확정되지 않으면 strict runtime의 실용 속도를 예측할 수 없다.
5. upstream merge 가능성과 LM Studio runtime 반영 일정은 프로젝트 내부에서 통제할 수 없다.
6. 0.008/0.024 bpb 기준은 기존 저장소의 engineering/실용 해상도이며 과제별 통계적 유의성을 자동 보장하지 않는다.
7. 본 사전 검토는 알려진 설계 오류를 거르는 절차일 뿐이며, 실제 결과는 구현 후 실행해야만 알 수 있다.
