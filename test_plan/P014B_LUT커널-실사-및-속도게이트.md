## 1. 왜 — 우리가 반복해 온 실수를 여기서 안 하려고

이번 세션에만 **같은 실수를 두 번** 했다(결과 016 §13·§14): **설계를 덜 마치고 구현부터 했고,
대조군이 아니었으면 둘 다 이득으로 기록될 뻔했다.**

P014 는 그보다 훨씬 비싸다 — 외부 C++ 의존, 포맷 변환, 플랫폼 빌드. 그래서 **먼저 잰다.**

### 1.1 아직 모르는 것 세 가지 (이게 게이트다)

| # | 미지 | 왜 치명적인가 |
|---|---|---|
| **U1** | **우리 모델 크기(dim 768)에서 LUT 가 이득인가** | 논문들은 **3B급(dim 2560+)** 에서 잰다. LUT 는 **표 구축 비용을 재사용으로 상각**하는데, 작은 행렬은 재사용 기회가 적다. **이득이 0 이거나 음수일 수 있다** |
| **U2** | **`micro_group=128` 그룹 스케일을 커널이 받는가** | BitNet b1.58 원형은 **텐서 단위 absmean** 스케일이다. 커널이 그룹 스케일을 모르면 α 를 **밖에서** 곱해야 하고, 그게 또 하나의 fp32 순회가 된다 |
| **U3** | **활성값 int8 을 요구하는가** | 요구하면 **정확도 영향**이 생긴다. 지금 우리 int8 경로는 로짓 게이트 `0.000e+00` 인 **무손실**인데 그 성질을 잃는다 |

**셋 중 하나라도 부정이면 P014 의 비용-이득이 뒤집힌다.**

## 2. 질문

| # | 질문 |
|---|---|
| Q1 | T-MAC / bitnet.cpp 커널이 **우리 가중치 포맷을 받는가** (삼진 코드 + g128 α) |

## 3. ★예측 — 정직하게

| # | 예측 | 근거 | 틀리면 |
|---|---|---|---|
| P1 | **`mC` int8 16.1 → 25~40 tok/s (1.5~2.5×)** | 결과 014 §11 분해: 언팩이 층당 약 2ms × 20층 = 40ms 를 62.3ms 중에서 차지. 고정비 4.2ms 는 안 줄어든다 | **6.17× 가 나오면 우리 계측을 의심한다** — 그건 3B·전정밀 기준 숫자다 |
| P2 | **U2 는 부정일 가능성이 높다** | BitNet 원형이 텐서 스케일이다 | 그룹 스케일을 받으면 통합이 훨씬 쉬워진다 |
| P3 | **U1 이 가장 위험하다** | 표 구축은 활성값당 고정비, 재사용은 행렬 폭에 비례. dim 768 은 3B 의 1/3.3 | 이득이 크면 P014 즉시 진행 |
| P4 | **`mA` 는 이 경로에서 배제된다** | 5비트/4가중치 코드북을 두 구현 다 모른다 | 확장 가능하면 mA 가 되살아난다 |

> **★P1 을 계획서와 배치 양쪽에 적어 둔다.** 그래야 결과가 나왔을 때
> "예상대로" 로 뭉개지지 않는다. **그리고 "몇 배" 를 인용할 때는 항상 기준선을 함께 적는다.**

## 4. 단계 설계

### 단계 0 — **문헌·코드 실사** ⏸ · GPU 0 · **사람 시간 수 시간** · 배치 없음

**이건 실험이 아니라 조사다. 배치를 만들지 않는다.**

체크리스트(전부 **근거 링크와 함께** `docs/methods/08_paper_review_202608.md` 에 기록):

- [ ] **bitnet.cpp 본문**(arXiv:2502.11880)에서 **I2_S 의 "Scale" 단위** 확인 → **U2**
- [ ] TL 커널이 요구하는 **활성값 정밀도** → **U3**
- [ ] 두 구현의 **가중치 파일 포맷**(GGUF 변형인가, 자체인가)
- [ ] **라이선스**(`microsoft/T-MAC`, `microsoft/BitNet` 의 LICENSE)
- [ ] **빌드 요구**: SIMD(AVX2/AVX-512), 컴파일러, Windows 지원 여부
- [ ] 커널 **호출 인터페이스**(C API 인가, llama.cpp 내부 전용인가)
- [ ] 논문의 **정확도 표** — "lossless" 주장의 실제 조건

**게이트 G0**: 라이선스가 허용되지 않거나 Windows 빌드가 불가하면 **여기서 종료**.

### 단계 1 — **포맷 변환기** ⏸ 단계0 통과 후 · GPU 0 · 구현 소~중

우리 체크포인트 → 그쪽 포맷. **읽기 전용 내보내기이고 `tinylm/` 을 건드리지 않는다.**

- `scripts/export_ternary.py`(신설 예정): `TLinear._i8`(int8 코드) + `_alpha`(g128) 를 내보낸다
- **U2 가 부정이면** 여기서 **α 를 텐서 단위로 재계산**해야 하고, 그건 **가중치를 바꾸는 것**이다
  → **로짓 동등성이 깨진다** → 그 경우 **품질 재검증이 별도로 필요**하다(비용 증가)
- **게이트 G1**: 변환 후 **같은 프롬프트에서 로짓/출력이 우리 PyTorch 경로와 일치**하는가.
  ⚠️ U2 가 부정이면 완전 일치는 불가능하므로 **허용 오차를 미리 정한다**

### 단계 2 — **속도 게이트** ⏸ 단계1 통과 후 · GPU 0 · 수 분

**같은 기계·같은 프롬프트·같은 max_new 로** 세 조건을 나란히:

| 조건 | 값 |
|---|---|
| 우리 PyTorch int8 (기준선) | `mC` **16.06 tok/s** (결과 016 §14 [3/5]) |
| 우리 PyTorch int8 + 언팩 캐시 | `mC` 18.76 (3차 수정 후 재측정 예정) |
| **LUT 커널** | ? |

- **측정 위생**(결과 016 §12.5): 단독 실행 · 직전 5분 유휴 · **같은 세션에 기준선 포함해 비율로**
- **게이트 G2**: **1.3× 미만이면 P014 를 접는다.** 그 아래면 언팩 캐시(순수 PyTorch, 이미 완료
  직전)로 충분하고 외부 의존을 질 이유가 없다

### 단계 3 — **P014 로 인계** ⏸ G2 통과 후

여기서부터는 P014 본체(커널 통합·정확도 검증·메모리 실측)가 소유한다.

## 5. 판정 기준

| 게이트 | 통과 조건 | 실패 시 |
|---|---|---|
| **G0** 실사 | 라이선스 허용 + Windows/x86 빌드 가능 | **종료.** 안 C(직접 구현)만 남고 그건 별도 판단 |
| **G1** 정합 | 변환 결과가 우리 출력과 일치(또는 정해 둔 허용 오차 안) | 포맷 불일치 원인을 기록하고 종료 |
| **G2** 속도 | **≥ 1.3× vs 우리 int8 기준선** | **P014 접는다.** 언팩 캐시로 만족 |

> **★G2 를 1.3× 로 잡은 이유**: 언팩 캐시가 이미 `mC` 에서 약 1.17×(대가 포함) 를 냈고
> 3차 수정 후 1.7× 추정이다. **외부 의존을 지려면 그보다 확실히 나아야 한다.**

## 7. 한계

- **U1(모델 크기 효과)은 단계2 에서만 답이 나온다.** 단계0·1 을 다 해야 알 수 있다는 뜻이고,
  그게 이 계획의 **매몰 비용 리스크**다. 대신 단계0·1 이 GPU 0 이고 본체를 안 건드린다.
- 단계2 는 **두 런타임(PyTorch vs C++)** 을 비교한다. 프레임워크 오버헤드가 섞이므로
  **"커널만의 이득" 이 아니다.** 그래도 **배포 관점에서는 그게 맞는 비교**다.
- `mA` 는 이 경로에서 배제된다(§P4). **아키텍처 판정이 아니라 도구 생태계 판정**이다.
- 우리 측정은 Windows·x86·1스레드다. 논문은 M2-Ultra·Raspberry Pi 다. **배수를 옮겨 쓰지 않는다.**
