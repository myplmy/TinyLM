## 2. 🚫**남은 것 — 둘**

### 2.1 ★**Q1 — 회계와 할당자가 얼마나 다른가**(단계1, ⚙10분)

우리 `runtime_mb` 는 **텐서 합산**이다. 결과 016 이 매번 적어 왔다:

> *"⚠️RSS 는 할당자 때문에 과대, 텐서합산은 임시버퍼를 빼서 과소. **둘을 함께 읽는다.**"*

🚫★**그런데 "얼마나 다른가" 를 한 번도 표로 만들지 않았다.**
결과 016 §24.7 이 스스로 한계로 적었다: *"RSS 로 교차확인한 적이 없다."*

★**왜 지금 중요해졌나** — 예산이 **36 MiB** 이고 우리 수가 **31.8~34.8** 이다.
**여유가 1.2~4.2 MiB 뿐**인데 **회계 오차를 모른다.**
🚫**할당자가 3 MiB 를 더 쓰면 "들어간다" 가 거짓이 된다.**

| 재는 것 | 어떻게 |
|---|---|
| 안 B 조립 상태의 **RSS 증가분** | `mem_runtime` 이 이미 로드 전/후 RSS 를 찍는다 |
| **KV 를 채운 뒤**의 RSS | ★**`--max-new` 를 seq 까지 올려 캐시를 실제로 채운다** |
| 회계값과의 차 | `RSS증가 − (runtime_mb + kv_mb)` |

★★**이것이 이 문서의 1순위**다. **학습 0 · GPU 0 · ⚙10분.**

## 3. 단계1 — RSS 교차확인 (⚙10분, GPU 0)

```
python scripts/mem_runtime.py --device cpu --preset m100R1c ^
  --models mC_cla2_ag4 mC_initonly_nc --drop-latent --lut --emb-quant int8 ^
  --kv-seq 1024 --max-new 512
```

★**`--max-new 512` 가 핵심**이다 — 기본 32 로는 **KV 가 거의 안 찬다.**
⚠️**`--max-new` 를 512 로 올려도 seq 1024 의 절반**이라 **KV 회계값의 절반**만 실현된다.
→ ★**그 비율을 함께 읽는다**(회계가 맞으면 RSS 증가가 `kv_mb × 512/1024` 를 따라야 한다).

### 3.1 ⚙예측

| # | 예측 | 근거 |
|---|---|---|
| **M1** | RSS 증가분이 회계값의 ★**1.2 ~ 2.0배** | 파이썬·torch 할당자 오버헤드 |
| **M2** | `--max-new` 를 32 → 512 로 올리면 RSS 가 ⚙**+7.5 MiB** 증가 | `kv_mb 15.0 × 480/1024` |
| ★**M3** | M2 가 안 맞으면 ★**KV 가 실제로 안 잡히고 있다**(생성 경로가 캐시를 안 쓴다) | 함정 37 |

★**M3 이 이 단계의 진짜 값어치다** — **회계가 세는 것과 코드가 잡는 것이 같은지** 처음 본다.

## 4. ★판정 기준

| 관측 | 판정 |
|---|---|
| RSS 증가 / 회계값 **< 1.5** | ✅**회계를 그대로 인용한다.** 여유 계산에 안전계수 1.5 를 곱한다 |
| 1.5 ~ 3.0 | ⚠️**안전계수를 명시**하고 예산 판정을 다시 한다 |
| ★**> 3.0** | 🚫★**예산 결론이 흔들린다.** *"31.8 MiB 면 들어간다"* 를 철회하고 다시 잰다 |
| M2 가 **안 맞는다** | 🚫**결함이다.** 코드를 먼저 본다(결과가 아니다) |

## 5. ⚠️한계

- ⚠️**RSS 는 프로세스 전체**다. 파이썬·torch 런타임이 섞여 **증가분만** 의미가 있다.
- ⚠️**Windows RSS 는 working set** 이고 리눅스와 정의가 다르다. 🚫**절대값을 다른 OS 와 비교하지 않는다.**
- ⚠️**할당자는 반환을 미룬다** — 최대 RSS 는 **한 번 잡은 것의 누적**일 수 있다.
- 🚫**이것은 "L2/L3 에 실제로 상주하는가" 를 안 본다.** 그것은 캐시 미스율이고
  ★**`docs/methods/02_memory.md` M.3.4 가 "한 번도 안 잰 것" 으로 적어 둔 항목**이다.
