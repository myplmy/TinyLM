## 1. 왜 — P045B가 닫은 문과 닫지 않은 문을 분리한다

P045B Stage1의 같은 Muon·d12·CLA2·무재귀 비교에서 dense 3.5745에 비해
정확한 MLP 객체 공유 `g2`는 +0.0340, `g4`는 +0.0579 나빴다. 따라서 **현 폭·현 배치·현
optimizer 규약의 `g2/g4`를 그대로 다시 돌리는 문은 닫혀 있다**.

그러나 사용자가 승인한 확장 질문은 “공유 MLP의 구조나 학습 규약까지 바꾸어도 직접공유가
계속 지는가”이다. 다음 세 가족은 서로 다른 모델이므로 한 결론으로 묶지 않는다.

| 가족 | 정의 | 현 증거 |
|---|---|---|
| **E0 기존 정확공유** | 현재 `ffn_dim`, 연속 `j//g` 배치, 동일 optimizer 규약으로 같은 MLP 객체를 반복 | 🚫P045B에서 기각; 재실행 금지 |
| **D 구조조건부 직접 코어 공유** | MLP 코어 weight는 그대로 공유하되 공유 코어의 폭·전문가 배치 또는 공유 사용횟수에 맞춘 최적화 규약을 바꿈 | ⚠️우리 조건 0런; 이 계획에서 조건부 개방 |
| **R 완화 공유** | 공유 base에 층별 low-rank residual·계수 등 고유 파라미터를 추가 | ⚠️우리 tied 몸통 0런; 엄밀한 직접공유가 아님 |

TinyLM은 이미 prelude/coda를 독립으로 두고 각 층 norm·gate를 소유한다. 따라서 외부의
“sandwich”나 per-layer norm 성공을 **새 후보인 것처럼 중복 실행하지 않는다**.

## 2. 외부 근거와 TinyLM으로 옮길 수 있는 범위

| 근거 | 보여 준 것 | 이 계획에서 허용하는 추론 | 허용하지 않는 추론 |
|---|---|---|---|
| [One Wide Feedforward is All You Need](https://arxiv.org/abs/2309.01826) | 단일 공유 FFN을 넓혀 원래 크기로 되돌렸을 때 MT Transformer Big 대비 정확도·latency 개선 | **공유 코어 폭**은 E0와 다른 독립 변수 | encoder-decoder MT 결과가 TinyLM causal scratch에서도 이긴다는 주장 |
| [Lessons on Parameter Sharing across Layers](https://arxiv.org/abs/2104.06022) | sequence/cycle/cycle-rev 배치가 단일 universal 공유와 다른 결과 | 공유 모듈의 **층 배치 순서**를 정적 후보로 둘 수 있음 | P061·P074와 겹치는 순서를 다시 학습 |
| [Understanding Parameter Sharing in Transformers](https://arxiv.org/abs/2306.09380) | 공유 weight는 반복 사용 때문에 gradient 범위와 수렴 규약이 달라짐 | 사용횟수별 update/weight RMS를 먼저 계측 | 사후 LR 튜닝으로 P045B 열세가 반드시 사라진다는 주장 |
| [Go Wider Instead of Deeper](https://arxiv.org/abs/2107.11817) | depth 공유에 MoE FFN과 층별 norm을 결합해 ALBERT보다 개선 | width/expert 배분은 가능한 구조 후보 | MoE 파라미터·dispatch 비용을 숨기거나 이미 있는 층별 norm을 새 기법으로 셈 |
| [Relaxed Recursive Transformers](https://arxiv.org/abs/2410.20672) | 공유 블록에 depth-wise LoRA를 붙여 제약을 완화 | R 가족의 실재성과 부모근사 게이트 | pretrained 변환 결과를 scratch 품질값으로 복사 |

외부 근거는 D/R 가족을 **측정할 자격**만 준다. 후보 채택은 아래 TinyLM 저장·FLOPs·품질
게이트를 모두 통과해야 한다.

## 4. 후보와 회계 단위

Stage0에서 아래 후보를 **설계 ID**로만 사용한다. 아직 CLI tag나 실행 명령이 아니다.

| ID | 핵심 | 직접공유 여부 | 대조·중복 처리 |
|---|---|---|---|
| `E0-g2` | 현 `g2`, 현 폭 | 정확 직접공유 | 결과 079를 조건서명 일치 때만 재사용 |
| `D1-wide-core` | 더 강한 공유(`g4`)와 약 2배 FFN 폭으로 중간 MLP 유니크 weight를 `E0-g2`와 맞춤 | **공유 코어는 정확 직접공유** | prelude/coda를 포함한 총 byte와 실제 FLOPs를 다시 계산 |
| `D2-use-normalized` | 현 `g2` 구조에서 공유횟수별 gradient/update 규약만 교정 | 정확 직접공유 | anneal audit이 아니라 optimizer audit 확장 질문; 별도 계측 선결 |
| `D3-cycle` | 같은 유니크 MLP를 연속이 아닌 cycle/cycle-rev로 배치 | 정확 직접공유 | P061 형상·P074 방문순서와 동치면 폐기하고 기존 결과 인용 |
| `R1-depth-lowrank` | 공유 base + 층별 low-rank residual | 완화 공유 | P008의 제거형 LoRA와 수명이 다르고, P086 tied-body 미측정을 승계 |

`D1-wide-core`의 “같은 크기”는 **중간 MLP weight만의 산술 동률**이다. 전체 packed/상주에는
독립 edge·attention·scale·metadata가 있고, 실행 FLOPs는 폭에 비례하므로 Stage0 회계를 통과하기
전에는 메모리 동급이나 속도 개선이라고 부르지 않는다.

## 5. 단계와 중단 게이트

| 단계 | 무엇 | 다음 단계 조건 | 비용 |
|---|---|---|---:|
| **Stage0a ✅ 정적** | P008·P045B·P061·P074·P076·P086과 후보 의미 중복표 | E0 closed, D3 duplicate HOLD, D2는 P091 의존으로 분리 | GPU 0 |
| **Stage0b ✅ 정적** | D/R 후보별 unique weight, packed·상주 lower bound, optimizer state, FLOPs, layer visit, metadata 회계 | R1 r4/8/16 기본 트랙; D1은 +62.4% FLOPs라 고계산 트랙 | GPU 0 |
| **Stage0c** | 기존 부모의 층별 MLP를 shared base+residual로 근사해 rank/width별 weight 오차와 logit 오차 측정 | 복잡도 증가에 따라 오차가 단조 감소하고 E0보다 명확히 작음 | 사용자 모델 로딩, ⚙0.2h |
| **Stage1** | default-off·save/load·optimizer ownership·unique-module·조건서명 계약 구현 | off 경로 동일, 계약 오류 0, 사용자 스모크 PASS | GPU 0~0.1h |
| **Stage2** | 가장 싼 D 후보 1개와 R 후보 1개의 250-step 진단 | NaN/skip 0; update/weight 비가 사전 범위; wall/VRAM 별도 기록 | ⚙0.8~1.5h |
| **Stage3** | E0 대조와 Stage2 생존 후보의 300M 최소 본런 | 아래 품질·저장 gate 동시 통과 | ⚙3.2~5.0h |
| **Stage4** | Stage3 승자만 seed 또는 600M 한 축 전이 | 두 조건 부호 일치 | ⚙3.2~6.2h |

Stage0b에서 FLOPs +10%를 넘는 `D1-wide-core`는 자동 폐기하지 않지만 **별도 고계산 Pareto
트랙**으로 분리한다. 이 경우 wall 또는 배포 latency가 E0보다 좋아야 하며, 품질만 좋아졌다는
이유로 기본 후보에 합치지 않는다.

**정적 preflight(2026-09-15):** Stage2의 `250 × 8 × 16 × 1024`는 32.8M 학습토큰이고
최소 권장 풀은 약 66M이다. Stage3의 `2289 × 8 × 16 × 1024`는 300.0M 학습토큰이다.
P045B E0가 사용한 `--pool-tokens 600M --exact-cache`를 대조 조건으로 고정하면 두 단계 모두
2배 풀 규약을 만족한다. 조건서명이 다른 E0를 재사용하지 않으며, 아직 실행 tag·명령·배치는
배정하거나 작성하지 않았다.

## 6. 품질·효율 판정

```text
회복률 = (L_E0 - L_candidate) / (L_E0 - L_dense)
남은 대가 = L_candidate - L_dense
순절감 = dense 배포 bytes - (shared core + layer-specific + metadata bytes)
```

- Stage3 계속: **회복률 ≥50%**, 남은 대가가 해당 계열 현재 ruler 안, 순배포 절감 ≥15%를 모두 만족.
- D 후보는 layer-specific trainable matrix를 붙이는 순간 R 가족으로 재분류한다. 이름만 직접공유로 남기지 않는다.
- 속도는 계측 off 팔에서만 판정한다. 계측 on의 ms/step은 진단 비용이 섞여 인용 금지다.
- 풀·토크나이저·학습토큰·초기화·seed·eval 경로·optimizer/anneal을 한 팔 안에서 하나만 바꾼다.
- 단일 seed나 Stage0 부모근사로 기본 프리셋을 바꾸지 않는다.

## 7. 승인·실행 경계

사용자는 2026-09-15에 원 제안의 권장안과 **구조조건부 직접공유까지 포함한 계획 작성**을
승인했다. 이 승인은 연구 질문과 P093 계획의 승인이지 다음 항목의 자동 승인이 아니다.

- `ffn_dim`/공유 배치/optimizer group을 바꾸는 코드 구현
- 체크포인트 모델 로딩과 Stage0c
- GPU 학습, 스모크, 실험 배치 작성·실행
- 기존 E0 종결 판정을 “직접공유 승리”로 변경

Stage0a·0b 회계 결과로 기본 Pareto 트랙에 남은 것은 R1 rank 4/8/16이고, D2는 P091 의존,
D1은 고계산 트랙이다. 보존 로그를 회수했으며 다음 관문은 Stage0c 부모 근사
오차와 Stage1 구현 범위를 별도로 고정하는 것이다.

## 8. 현재 결론과 한계

**판정:** 기존 정확공유 E0는 계속 닫는다. 다만 `D1-wide-core`처럼 **공유 weight 자체는
직접 공유하면서 코어 구조·학습 규약을 바꾸는 가족**에는 외부 근거와 내부 미측정성이 있어
조건부 가능성이 열린다. 그 가능성은 `DESIGNED`이며 TinyLM 품질 증거는 0런이다.

외부 연구 대부분은 encoder-decoder MT, BERT류, 또는 pretrained 압축이다. TinyLM의 causal
scratch pretraining, ternary STE, Muon, 작은 300M 예산으로 전이되는지는 알 수 없다. 특히 현재
TinyLM이 이미 독립 edge·층별 norm/gate를 쓰므로 그 요소만으로 P045B 열세가 뒤집힐 근거는 없다.
