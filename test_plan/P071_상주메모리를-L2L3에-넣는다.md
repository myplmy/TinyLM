## 0. ★★목표를 다시 못 박는다 — **packed 가 아니라 상주다**

> **사용자 지시(2026-08-20)**: *"현재 중요한 것은 저장메모리(packed 상태)보다
> 실제 추론시에 사용되는 상주메모리가 L2+L3 이내로 들어가야 한다는 점."*

| | 현재 최선 | 목표 | 배수 |
|---|---:|---:|---:|
| **packed(저장)** | ★**9.6 MB**(`m100R1q`) / 11.2 MB(`mC_d36_ag4`) | 40 MB | ✅**이미 통과** |
| ★★**fp32 상주** | ★**379.7 MB**(`mC_d36_ag4`, 결과 044 §9) | **40 MB** | 🚫**9.5배** |
| ⚙int8 상주 | ⚙70.4 MB(`m100R1q` 추정) | 40 MB | 🚫**1.8배** |

> ★★**packed 를 더 줄이는 실험은 이 목표에 기여하지 않는다.**
> **상주식에 bpw 가 없기 때문**이다(함정 1). `packed −10%` 는 **상주 0% 다.**
> → ★**이 계획서의 모든 판정 지표는 `runtime_mb` 와 실측 RSS 다.** `packed_mb` 는 참고만 한다.

## 1. ★원인 넷과 각각의 크기 (02_memory §M.3.2 요약)

| # | 원인 | 크기 | 우리 자산 |
|---|---|---|---|
| **1** | ★★**삼진을 fp32 로 들고 곱한다** — 상주식에 bpw 가 없다 | **×32** | 🚫**LUT 커널 없이는 못 고친다** |
| **2** | fp32 **2벌**(latent + dequant) | ×2 | ✅**`--drop-latent` 구현됨**(P034 단계2). ⚠️**긴 런 검증 미완** |
| **3** | ★**임베딩 34.3 MB 가 fp32** | int8 상주의 약 38% | 🚫**설계 미완** — 헤드가 임베딩과 tie 돼 있다 |
| **4** | 활성·KV 캐시 | 1024ctx 약 7.5 MB | 부차 |

★**산술로 확인**: `mC_d36_ag4` 삼진 45.42M → packed 11.2 MB / fp32 1벌 181.7 MB / **2벌 363.3 MB**.
**임베딩 34.3 + 기타 0.4 를 더하면 약 398 MB**(보고값 379.7 과 약 5% 차 — ⚠️**회계 미세차 미확인**).

## 2. ★단계0 — **오늘 돌아간다. 신규 구현 0** (수 분, CPU)

> ★**왜 지금 하나**: M.4 가 *"미수행"* 이라고 적은 7개 중 **3개는 도구가 이미 있다.**
> 그리고 **`mC_d36_ag4` 가 새 최선 상주(379.7 MB)인데 int8·drop_latent 경로에서 몇인지 모른다.**
> ★**함정 24**: *"레버 순위가 경로에 따라 뒤집힌다."* **경로별로 재지 않으면 REVIEW3 을 잘못 시작한다.**

| 팔 | 명령 | 답하는 것 |
|---|---|---|
| **0-a** | `mem_runtime.py --device cpu` (fp32 기준) | 네 후보의 **배포 경로 상주 실측** |
| **0-b** | `+ --drop-latent` | ★**원인 2(×2)가 실제로 절반을 주는가.** 로짓 동등성 게이트 포함 |
| **0-c** | `+ --drop-latent --int8-store` | ★**원인 1 의 부분 완화(×4)** |
| **0-d** | `+ --unpack-cache` | 언팩 1회/유니크모듈. ★**`attn_group` 이 캐시 히트를 4배로 만들었는지**(20260806 §7.2.2) |

**대상 4종**: `mC_wsd`(기준) · `mC_initonly`(무KD 기준) · ★**`mC_d36_ag4`**(최선 상주) · `mC_p1c1g16`(최선 packed).

### 2.1 기준 모델 선정 이유

| 태그 | 왜 넣는가 |
|---|---|
| `mC_wsd` | ★**모든 레버표의 공용 대조군**(기준표 §2.2c). 이것이 없으면 다른 숫자를 못 읽는다 |
| `mC_initonly` | ★**REVIEW2 가 채택할 조건**. 표준이 바뀌면 기준선도 바뀐다 |
| ★**`mC_d36_ag4`** | ★★**현재 최선 상주 379.7 MB.** 이 계획의 목적함수 위 1등이다 |
| `mC_p1c1g16` | ★**최선 packed 9.6 MB.** ★**"저장 1등과 상주 1등이 다른가" 를 직접 본다**(함정 1의 실증) |

### 2.2 예측 (결과 전에 고정)

| # | 예측 | 근거 |
|---|---|---|
| **P1** | `--drop-latent` 가 상주를 **0.50~0.55배**로 | 원인 2 는 정확히 ×2 |
| **P2** | `+int8-store` 가 다시 **약 0.28배**로(fp32 대비 최종 약 0.14~0.15) | 삼진 4B → 1B |
| **P3** | ★**그래도 `mC_d36_ag4` 는 40 MB 를 못 넘는다** — ⚙**약 90 MB** 예상(삼진 45.4 + 임베딩 34.3 + 기타) | ★**임베딩이 남는다**(원인 3) |
| **P4** | ★**packed 1등과 상주 1등이 다르다** — `m100R1q` packed 9.6 < `mC_d36_ag4` 11.2 인데 **상주는 역전** | 함정 1·24 |
| **P5** | `--unpack-cache` 의 로짓 차가 **0.000e+00** | 캐시는 비트 동일이어야 한다 |

### 2.3 🚫단계0 이 결정하지 못하는 것

- **속도**를 재지 않는다. `mem_runtime.py` 는 32토큰만 생성하고 **정상상태가 아니다**.
- **실제 캐시 히트율**을 못 본다(§4-4). RSS 와 텐서합산은 **바이트 회계**지 캐시 거동이 아니다.
- **품질**을 못 본다. int8 상주의 품질 대가는 **별도 eval** 이 필요하다.

## 3. ⏸단계1 이후 — **설계만. 배치를 만들지 않는다**

> ★**규약**(CLAUDE.md): *"실험용 배치는 '지금 돌아갈 때' 만 만든다.
> 구현이 선결이면 계획서에만 설계를 남긴다."* 아래는 **전부 구현이 선결**이다.

| 단계 | 무엇 | 선결 | ⚙기대 |
|---|---|---|---|
| **1** | ★★**LUT mpGEMM 커널**(T-MAC arXiv:2407.00088 / bitnet.cpp I2_S arXiv:2502.11880) | **커널 구현 + 플랫폼 SIMD**. 크다 | ★**원인 1 소거** → 삼진 상주 = packed |
| **2** | ★**임베딩 양자화**(P034 단계5 / Qwen 분석 §3.4-1) | **헤드-임베딩 tie 해체 설계** | 34.3 → ⚙8.6 MB(int8) |
| **3** | **`drop_latent` 긴 런 검증** | 없음 — 단계0-b 가 1차 확인 | 원인 2 확정 |
| **4** | ★**캐시 작업집합 실측** | 신규 도구(`perf`/PAPI 또는 대리 지표) | ★**타잉의 숨은 이점**(§4) |
| **5** | ⏸ 활성·KV 축소 | — | 부차 |

### 3.1 ⚙LUT + 임베딩 양자화를 **둘 다** 했을 때의 산술

```
mC_d36_ag4 기준
  삼진 packed(LUT 가 이 상태로 곱한다)      11.2 MB
  임베딩 int8 (32768×256 × 1B + α)          8.6 MB
  기타                                       0.4 MB
  ------------------------------------------------
  상주 합계                              약 20.2 MB   → ✅ L2+L3(40MB) 안
  + KV 캐시 1024ctx                          7.5 MB
  ------------------------------------------------
  합계                                   약 27.7 MB   → ✅ 여유 12 MB
```

> ★★**둘 다 해야 들어간다. 하나만으로는 안 된다.**
> LUT 만: 11.2 + 34.3 + 0.4 = **45.9 MB** → 🚫**초과**
> 임베딩만: 363.3 + 8.6 + 0.4 = **372.3 MB** → 🚫**논외**

⚠️**전부 계산값이다.** LUT 커널의 **테이블·워크스페이스 상주**를 세지 않았다 —
T-MAC 는 LUT 를 들고 있어야 하고 **그 크기를 우리는 모른다**(§5-2).

## 4. ★그런데 먼저 물어야 할 것 — **우리가 재는 "상주" 가 캐시 압력인가**

`report()`·`mem_runtime.py` 는 **파라미터 바이트 합계**를 센다. 그런데 L2+L3 판정에 필요한 것은
**동시에 살아 있는 작업집합(working set)** 이다.

★**타잉이면 둘이 다를 수 있다** — `g8` 은 **같은 MLP 를 8층 연속 재사용**하므로
**한 순간에 필요한 MLP 는 1벌**이다. `attn_group 4` 도 같다.
**바이트 합계는 유니크 전체이고 작업집합은 그보다 작을 수 있다.**

> ★★**이것이 참이면 우리는 이미 목표에 훨씬 가까울 수 있고, 거짓이면 §3.1 산술이 정본이다.**
> **한 번도 안 쟀다.** ⚠️**단 이걸 재려면 하드웨어 카운터가 필요하고, 우리에겐 도구가 없다.**
> → **단계4.** ★**대리 지표**: 층 순회 순서를 바꿔 가며 tok/s 를 재면 **간접 증거**는 얻는다.

## 5. ⚠️한계 — **추측으로 메우지 않는다**

| # | 미확인 |
|---|---|
| 1 | ★**L2+L3 = 40 MB 는 "데스크톱 CPU" 가정**이다. **배포 대상 기기를 아직 안 정했다** — 모바일이면 L3 가 없거나 4~8 MB 다 |
| 2 | ★**LUT 커널의 테이블·워크스페이스 상주 미지.** §3.1 이 그것을 0 으로 놓았다 |

| 4 | 🚫**품질 대가 미지.** int8 상주·LUT 커널이 손실을 얼마나 바꾸는지 안 쟀다 |
| 5 | ★**속도 미지.** 결과 014: **int8 이 CPU 에서 −62~67%**. **메모리를 줄이면 느려질 수 있다** — 목적함수가 메모리라도 **못 쓸 만큼 느리면 실패**다 |
